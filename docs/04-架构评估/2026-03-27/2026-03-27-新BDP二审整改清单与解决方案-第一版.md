# 新 BDP 二审整改清单与解决方案（第一版）

## 目的

这份文档不是再次重复“哪里不好”，
而是把二审已经确认的高风险问题，
整理成一份可执行的整改清单。

它回答的是：

- 现在最该先解决什么
- 每个问题的第一性原理根因是什么
- 应该怎样改，才不是头痛医头
- 什么叫改完了，如何判断收口

## 使用口径

本清单统一按以下原则使用：

- 项目宪章与正式需求高于当前局部代码便利性
- 旧 BDP 只作为历史事实与踩坑证据，不作为结构模板
- 不以“先能跑”为收口标准，而以“真值 owner 是否诚实、链路是否闭环”作为收口标准
- 不允许再引入为了临时方便而存在的第四 owner、镜像 runtime 或伪抽象层

## 临时验证说明

为避免本轮整改过程中出现“改到中段但无法快速判断断链点”的情况，
允许临时补一套最小 smoke 停点。

但这套设施有明确边界：

- 只服务于本轮架构整改
- 只承担阶段停点回归
- 不是长期测试基建
- 不是正式开发标准
- 整改完成后必须删除

本项目本轮整改后的正式验收，仍以游戏实测为准。

当前状态更新：

- 本轮代码侧整改主线已完成
- 临时 smoke 已按约定删除
- 普通 UI 读取路径中的默认诊断热路径已移除
- 后续最终验收仍需游戏内实测完成，不能用编译通过替代

## 总体判断

当前新 BDP 的主要问题不是功能少，
而是核心真值边界还没有被足够强硬地守住。

如果继续一边补业务一边容忍这些结构问题存在，
后面大概率会重新长出：

- 运行时镜像层
- 兼容胶水层
- UI 驱动状态层
- 单实现接口堆
- Patch 反向侵入核心

所以本清单的原则很简单：

- 先缩 owner
- 再拆镜像
- 再压抽象
- 再切 compat 侵入
- 最后再补业务

## 整改优先级总表

### P0：必须优先处理

- 表达系统收缩，禁止继续充当第四 owner
- Trigger 去协调器化，退回真值 owner 本位
- VerbHosting 拆除或降级为瞬时投影层
- 攻击执行链去 compat 侵入，切出核心主链

### P1：紧随其后处理

- 压缩 `SurfaceAccess + 单实现接口` 伪抽象体系
- 切断 UI 读取路径对运行时同步的副作用
- 补齐正式闭环，清理预留脚手架进入正式路径的问题

### P2：在结构收缩后处理

- 统一快照、刷新、诊断的触发口径
- 对热点路径做最小性能基线与回归核对

## 一、表达系统膨胀为第四 owner

### 风险等级

- P0

### 问题表现

当前 `Expressions` 已不只是“根据 Trigger 真值做解析”，
而是在持续长成一个总汇聚层。

它已经同时承担或试图承担：

- host 组织
- slot 读取
- 结果解析
- 主表达选择
- 投影入口
- 刷新与同步入口
- 外部查询面

这会使“表达结果层”逐渐退化为“事实中控层”。

### 根因

第一性原理上，表达系统只应回答：

- 从正式 owner 输入中，得到什么正式表达结果

它不应回答：

- 谁持有 host 生命周期
- 谁负责协调 UI、refresh、compat、投影

当前问题本质是：

- 把“结果建模”悄悄扩大成了“运行时汇聚”

### 解决方案

1. 明确表达系统唯一职责：
   - 输入：来自 Trigger / CombatBody / Trion 的正式读取事实
   - 输出：正式表达结果对象
2. 禁止在表达层常驻拥有 host、refresh、投影、兼容编排职责。
3. 将表达层对外暴露面压缩为两类：
   - 正式结果读取
   - 正式重算请求
4. 所有 UI、攻击入口、兼容入口只能消费表达结果，不得反向把表达层当总协调器调用。
5. 任何“需要方便集中调用”的新入口，默认先判定为可疑设计。

### 验收标准

- 表达模块不再持有独立 host 生命周期
- 表达模块不再暴露带 runtime 意味的刷新/同步总入口
- 表达系统对外 API 能用“输入事实 -> 输出结果”一句话解释清楚
- 业务新增时，不再需要把更多外围职责挂进表达层

## 二、Trigger 仍在承担运行时协调器职责

### 风险等级

- P0

### 问题表现

`CompTriggerBody` 虽然已经比旧版收缩，
但仍明显保留了初始化、时钟推进、同步、外部刷新、销毁清理等混合职责。

这意味着 Trigger 还没有彻底退回：

- 装载真值 owner
- 局部激活真值 owner

而仍部分保留了“系统调度中心”的惯性。

### 根因

Trigger 在业务上天然靠近装备、按钮、切换、宿主，
因此最容易因为“离问题最近”而继续吞掉协调职责。

旧 BDP 的事实已经证明：

- 一旦 Trigger 再次兼任协调器，它最终就会重新吸附表达、Verb、UI、兼容与恢复

### 解决方案

1. 把 `CompTriggerBody` 内职责按性质硬拆成三类：
   - 真值 owner 读写
   - 生命周期钩子转发
   - 外围消费适配
2. 任何需要“协调多核心”的事务，不允许继续长回 Trigger。
3. Trigger 只负责：
   - 槽位
   - 装载
   - 启停
   - 局部禁用
   - 多形态切换真值变化点
4. Tick 只能推进 Trigger 自己的合法时间过程，不能承担跨模块对齐。
5. Cleanup 与外部刷新应从 Trigger 主类剥离为外围流程，不得和 owner 本体继续捆绑膨胀。

### 验收标准

- 可以用一句话定义 Trigger：只拥有装载与局部激活事实
- 删除某个外围投影或 UI 服务时，Trigger 不需要跟着改内部真值逻辑
- `CompTriggerBody` 不再作为跨模块协调器被频繁调用

## 三、VerbHosting 是重复事实的镜像运行时层

### 风险等级

- P0

### 问题表现

当前 `VerbHosting` 看起来像“把表达结果接到宿主”的独立层，
但实际上已经有长成稳定镜像 runtime 的倾向。

它正在保存或维护：

- host 列表
- host refresh
- host sync
- host 查询入口

这很容易变成“表达层旁边再长一套事实副本”。

### 根因

verb host 本质上应是：

- 为接原版宿主协议而产生的投影结果

它不是新的真值层，
也不该拥有独立、长期、可膨胀的运行时身份。

### 解决方案

1. 将 VerbHosting 定位改为：
   - 原版宿主投影适配层
2. 原则上不允许它持有独立业务真值。
3. 能按需瞬时生成的投影，不保留常驻缓存。
4. 必须保留缓存时，只允许缓存“已可由正式结果唯一推出的派生数据”。
5. 把所有带“管理器”意味的 host refresh / sync 服务重新审查：
   - 能内联到投影更新的就内联
   - 能下降为局部辅助函数的就下降
   - 不能解释清楚存在必要性的就删除

### 验收标准

- VerbHosting 无法单独解释业务状态，只能解释投影状态
- 移除 VerbHosting 后，正式表达结果和 Trigger 真值仍完整成立
- 不再出现“先 sync host，再让系统恢复正确”的链路依赖

## 四、攻击执行链被 compat 与入口侵入

### 风险等级

- P0

### 问题表现

当前攻击执行主链与：

- `TryGetAttackVerb`
- 目标选择
- melee / ranged 入口
- damage 语义传递
- patch 兼容

仍缠得很近。

这正是旧 BDP 历史上最危险的腐化点之一。

### 根因

攻击执行链天然靠近 RimWorld 原版入口，
如果不严控边界，
compat 与 patch 会因为“必须接原版”而反向进入核心主链。

一旦这样发展，
后面就会出现：

- 为 patch 修 patch
- 为 compat 修 compat
- 核心结构反过来配合外围脏入口

### 解决方案

1. 明确攻击执行核心主链只负责：
   - 接收正式攻击意图
   - 完成正式目标解析
   - 调用正式执行流程
   - 下传正式语义上下文
2. 所有 Patch 只允许做入口桥接，不允许承载业务决策。
3. `TryGetAttackVerb` 类桥接口必须视为 compat 外围层，不得再回写核心状态。
4. melee / ranged 入口统一收敛到正式攻击意图对象，不允许各走半套逻辑。
5. damage 语义、伤口来源、爆炸传播等后果链统一从正式执行上下文取值，而不是沿 patch 口临时拼接。

### 验收标准

- Patch 代码删掉后，核心攻击执行对象模型仍自洽
- 原版入口变化只影响桥接层，不强迫核心重构
- 近战和远程入口最终进入同一正式执行主链

## 五、伪抽象层过厚：`SurfaceAccess + 单实现接口`

### 风险等级

- P1

### 问题表现

当前 `Core` 中接口数量明显偏多，
而大量接口只有单实现，
再叠加静态 `SurfaceAccess` 门面，
形成了“抽象很多，但替换性很弱”的结构。

这类结构的直接后果是：

- 文件膨胀
- 跳转成本高
- 责任解释变难
- 重构阻力变大

### 根因

真正有价值的抽象，应服务于：

- 真正的多实现
- 明确的边界隔离
- 测试替代点

如果接口只是为了“看起来分层”，
但最后所有调用又汇总回静态 surface，
那本质上是在交双重抽象税。

### 解决方案

1. 建立接口保留规则：
   - 有真实多实现需求才保留
   - 有明确隔离边界才保留
   - 能被直接具体类替代而不损边界的就删
2. 对 `SurfaceAccess` 统一审查：
   - 正式边界面保留
   - 只是转手调用的门面删除
3. 将“单实现接口 + 默认实现类 + SurfaceAccess”三件套视为默认可疑结构。
4. 对核心链优先采用：
   - 明确结果对象
   - 明确 owner
   - 少层、短链、可追踪调用

### 验收标准

- 核心目录接口数量明显收缩
- 删除单实现接口后，业务解释力上升而不是下降
- 从一个入口追到真值逻辑的跳转层数下降

## 六、UI 读取路径带运行时副作用

### 风险等级

- P1

### 问题表现

当前 gizmo / 外部 provider 路径与 host 同步、表达刷新存在耦合风险。

这意味着“读取 UI 展示内容”可能触发：

- 状态同步
- host 重建
- 运行时对齐

这属于非常危险的隐式副作用。

### 根因

UI 应只读取正式结果，
最多触发明确的用户命令。

如果 UI 读取路径还能顺手修正系统状态，
说明系统真实闭环没有建立，
而是把“展示时顺便补正”当成补丁机制。

### 解决方案

1. 明确 gizmo / 外部 provider 只读正式结果快照。
2. 所有同步、刷新、重算必须通过明确命令口触发，不允许藏在读取路径里。
3. 为 UI 相关服务建立硬规则：
   - 无副作用读取
   - 命令与读取分离
4. 对现有 gizmo 构造链做一次副作用扫描，逐项清除隐藏同步。

### 验收标准

- 多次打开同一 UI 不会触发状态变化
- 调试日志中，UI 绘制与运行时重算不再耦合出现
- UI 服务可以在脱离游戏主 Tick 的情况下安全读取正式结果

## 七、正式闭环不足，预留脚手架提前进入主路径

### 风险等级

- P1

### 问题表现

当前已有部分“未来扩展点”或“条件骨架”提前进入正式路径，
但其对应的正式业务闭包并未成立。

这会造成：

- 主链中出现空心接口
- 生产路径提前承受未来复杂度
- 当前系统长期兼容尚未定义清楚的扩展

### 根因

这类问题的本质不是“预留得不够优雅”，
而是：

- 把未来不确定性提前债务化到当前主链

一旦进入正式路径，
后续所有整改都得反过来顾忌这些空壳扩展点。

### 解决方案

1. 区分三类扩展点：
   - 已有真实调用方，保留
   - 近期必接且边界已明，受控保留
   - 纯预留、无真实调用方，删除
2. 空接口、空 registry、空条件分支默认视为待清洗对象。
3. 主路径只允许保留“当前已闭环”的扩展结构。
4. 对未来需求统一改用文档裁定，不提前把壳写进核心运行链。

### 验收标准

- 主路径中不再存在无法说明当前价值的空扩展点
- 新增扩展点必须能回答“当前谁在用、为何现在必须存在”
- 代码主链比现在更短、更闭合

## 八、快照、刷新、诊断链叠加导致性能隐患

### 风险等级

- P2

### 问题表现

现在真正的性能风险不一定已经表现为单个慢函数，
而是多个看似合理的小动作叠加：

- 状态变化后重算
- host 刷新
- 结果投影
- UI 读取
- 诊断生成
- 快照构建

在业务补齐后，这些动作很可能相互放大。

### 根因

当系统缺少稳定 owner 与清晰事件边界时，
为了“保险正确”，
就容易出现重复重建、重复读取、重复同步。

性能问题往往只是结构问题的后果。

### 解决方案

1. 先统一事件与重算触发点，不允许多层各自判断“顺手重算一下”。
2. 明确哪些对象是：
   - 真值
   - 派生结果
   - 短期快照
   - 调试诊断
3. 调试诊断默认不进入热路径。
4. 对以下场景做最小基线采样：
   - 选中装备
   - 开关 gizmo
   - 装载/卸载芯片
   - 切换主攻击表达
   - 进入攻击执行
5. 在结构收缩后再做热点微调，避免拿缓存掩盖架构问题。

### 验收标准

- 同一业务动作只触发一轮可解释的重算
- UI 打开不再诱发额外热路径重建
- 调试关闭后，热路径日志与诊断开销明显下降

## 建议整改顺序

1. 先给三核心重新画一次“谁拥有真值，谁只读结果，谁只能桥接”的红线图。
2. 第一刀处理表达系统，切掉其作为总汇聚层的趋势。
3. 第二刀处理 Trigger，剥离协调器残留。
4. 第三刀处理 VerbHosting，把它压回投影适配层。
5. 第四刀处理攻击执行 compat 侵入，切桥接与核心。
6. 第五刀压缩伪抽象层，减少单实现接口与无意义 surface。
7. 第六刀清理 UI 副作用和空扩展点。
8. 最后再做性能基线和热路径核对。

## 禁止事项

- 不要一边保留镜像 runtime，一边继续补业务
- 不要把 patch 入口当核心业务入口继续深化
- 不要为了“未来也许会扩展”继续保留空接口和空 registry
- 不要用新增缓存掩盖事实 owner 混乱
- 不要把 UI 读取变成补正系统状态的隐式修复点

## 最终收口标准

本轮整改真正完成，不以“删了多少文件”作为标准，
而以以下结果作为标准：

- 三核心 owner 可以被清楚定义，且外围层无法越权持有真值
- 表达、Trigger、攻击执行之间的关系可以用一句话各自说明
- 投影层、兼容层、UI 层都只能消费正式结果，不能反向塑造核心事实
- 新业务接入时，首先落在正式 owner 与正式结果模型上，而不是再长 runtime 胶水层

如果达不到这些结果，
那么即使局部代码更干净，
也不能算完成本轮架构整改。
