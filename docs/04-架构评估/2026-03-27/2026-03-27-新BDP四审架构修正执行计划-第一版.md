## 阶段一：表达管线去接口化（M1 + M2）

### 目标

删除表达系统中所有"只有单一实现的接口"，把6步管线内联为一个类的内部方法链。

### 1.1 删除Pipeline接口和合并实现

**要做什么：**

1. 新建 `Core/Expressions/Pipeline/ExpressionSnapshotBuilder.cs`，将以下7个Default实现类的全部逻辑合并进来：
   - `DefaultExpressionSourceCollector`
   - `DefaultExpressionSourceFilter`
   - `DefaultSingleSideExpressionBuilder`（如存在）
   - `DefaultSpecialWeaponOverrideResolver`
   - `DefaultCompositeExpressionResolver`
   - `DefaultExpressionSnapshotAssembler`
   - `DefaultExpressionSnapshotPipeline`

2. `ExpressionSnapshotBuilder` 对外只暴露一个方法：
   ```csharp
   public ExpressionSnapshot Build(Pawn pawn, ITriggerLoadoutReader reader)
   ```

3. 删除以下接口文件：
   - `IExpressionSourceCollector.cs`
   - `IExpressionSourceFilter.cs`
   - `ISingleSideExpressionBuilder.cs`
   - `ISpecialWeaponOverrideResolver.cs`
   - `ICompositeExpressionResolver.cs`
   - `IExpressionSnapshotAssembler.cs`
   - `IExpressionSnapshotPipeline.cs`

4. 删除以下实现文件（逻辑已迁入）：
   - `DefaultExpressionSourceCollector.cs`
   - `DefaultExpressionSourceFilter.cs`
   - `DefaultSpecialWeaponOverrideResolver.cs`
   - `DefaultCompositeExpressionResolver.cs`
   - `DefaultExpressionSnapshotAssembler.cs`
   - `DefaultExpressionSnapshotPipeline.cs`

5. 所有引用上述类型的地方统一改为使用 `ExpressionSnapshotBuilder`

6. 在 `ExpressionSnapshotBuilder.Build()` 方法上添加 XML 文档注释，明确说明：每次调用会重建内部对象图（per-call allocation），这是现有行为延续，非本次优化范围

**保留不动：**
- `IExpressionConditionInterpreter.cs`（有3个实现，保留）
- `CombatBodyExpressionConditionInterpreter.cs`（保留）
- `TrionExpressionConditionInterpreter.cs`（保留）
- `ModeExpressionConditionInterpreter.cs`（保留）
- `DefaultExpressionConditionEvaluator.cs`（保留）
- `IExpressionReader.cs`（对外正式口，保留）
- `IExpressionSourceDeclarationProvider.cs`（芯片桥接点，保留）

**禁止做的事：**
- 禁止改变 `ExpressionSnapshot`、`FormalExpressionResult`、`SingleSideExpressionSet`、`CompositeExpressionSet` 等Model类的结构
- 禁止改变对外读取口 `IExpressionReader` 的签名
- 禁止把条件解释器（`IExpressionConditionInterpreter`）的接口也一并删除

**完成标准（不达到不算完成）：**
- 编译通过，无报错
- `ExpressionSnapshotBuilder.Build()` 调用结果与原 `DefaultExpressionSnapshotPipeline.Build()` 逻辑等价
- 7个接口文件已从项目中删除
- 6个Default实现文件已从项目中删除
- `ExpressionSnapshotBuilder.Build()` 已有注释标注 per-call allocation 现状

---

## 阶段三：VerbHosting扁平化（M3 + M5部分）

> ⚠️ 此阶段风险最高，需要最谨慎执行

### 目标

消除全局VerbHost容器，把Verb宿主管理收回CompTriggerBody实例内部。

### 3.1 CompTriggerBody内增加VerbHost管理

**要做什么：**

1. 新建 `Core/VerbHosting/TriggerBodyVerbHostManager.cs`，将以下类的逻辑合并进来：
   - `DefaultVerbHostRefreshService`（翻译表达快照 → 清空旧宿主 → 创建新宿主）
   - `DefaultVerbHostFactory`（宿主实例构建逻辑）
   - `DefaultExpressionToVerbHostSpecTranslator`（表达结果 → BuildSpec 翻译逻辑）
   - `DefaultVerbHostResolver`（主远程/主近战宿主选取逻辑）

   对外暴露：`Refresh(ExpressionSnapshot snapshot)`、`GetPrimaryRangedHost()`、`GetPrimaryMeleeHost()`、`Clear()`

2. 在 `CompTriggerBody` 中只增加一个成员对象：
   ```csharp
   private TriggerBodyVerbHostManager verbHostManager;
   ```
   在构造函数中初始化。**不在 `CompTriggerBody` 上新增任何方法**（避免加剧 P5 上帝膨胀）。

3. 在 `CompTriggerBody.Notify_Unequipped()` 中调用 `verbHostManager.Clear()`，在 `RefreshProjectedOutputs()` 中调用 `verbHostManager.Refresh(snapshot)`

4. 将所有原通过 `VerbHostSurfaceAccess` 调用 Container/Resolver 的调用点，改为通过 `TriggerSurfaceAccess` 取得 `CompTriggerBody`，再调用 `verbHostManager` 对应方法；**所有访问点须加 null guard**（防止 `pawn.equipment.Primary` 为 null 的边界情况）

**保留不动的文件：**
- `VerbHostInstance.cs`（数据类，保留）
- `VerbHostBuildSpec.cs`（数据类，保留，但不再作为外部传递的DTO，改为内部临时结构）
- `VerbHostAutoProxyVerb.cs`（原版桥接Verb，必须保留）
- `VerbHostSlot.cs`（如果只是枚举，保留）

**修改但不删除：**
- `VerbHostSurfaceAccess.cs`：移除内部静态单例（Container/Factory/RefreshService），改为只提供从CompTriggerBody读取的快捷方法
- `AttackExecutionSurfaceAccess.cs`：`AutoEntryService` 改为通过 `TriggerSurfaceAccess` 取得 `CompTriggerBody`，再调用 `verbHostManager` 对应方法，须加 null guard

**删除的文件：**
- `DefaultVerbHostContainer.cs`（全局字典消失）
- `DefaultVerbHostFactory.cs`（工厂逻辑封装进TriggerBodyVerbHostManager）
- `DefaultVerbHostResolver.cs`（解析器逻辑封装进TriggerBodyVerbHostManager）
- `DefaultVerbHostRefreshService.cs`（刷新逻辑封装进TriggerBodyVerbHostManager）
- `DefaultExpressionToVerbHostSpecTranslator.cs`（翻译逻辑封装进TriggerBodyVerbHostManager）
- `IVerbHostContainer.cs`
- `IVerbHostFactory.cs`
- `IVerbHostResolver.cs`
- `IExpressionToVerbHostSpecTranslator.cs`
- `VerbHostAutoEntryService.cs`（功能内联）

**禁止做的事：**
- 禁止改变 `VerbHostAutoProxyVerb` 的任何逻辑（它是原版自动远程入口的桥接，改错了攻击链就断了）
- 禁止改变 `AttackExecutionSurfaceAccess.TryCreateAutoRangedProxyVerb()` 的对外行为
- 禁止改变 `AttackExecutionSurfaceAccess.TryExecuteAutoMelee()` 的对外行为
- 禁止修改任何Harmony Patch的逻辑

**完成标准（不达到不算完成）：**
- 编译通过，无报错
- `VerbHostSurfaceAccess` 不再持有任何静态可变实例
- 全局 `DefaultVerbHostContainer` 字典已消失
- `CompTriggerBody` 只新增 `verbHostManager` 一个字段，无新增方法
- 所有外部访问 `verbHostManager` 的调用点已加 null guard
- 自动远程代理Verb仍然能正确创建（`TryCreateAutoRangedProxyVerb` 能通过）
- 自动近战执行仍然能正确触发（`TryExecuteAutoMelee` 能通过）
- 装备/卸装武器后 `RefreshProjectedOutputs()` 仍然正确触发宿主刷新

## 阶段四：静态依赖链清理（M5剩余部分）

### 目标

确认剩余静态类中没有运行时可变状态残留。

### 4.1 审查并清理

**要做的事：**

1. 逐一检查以下文件，确认是否还持有运行时可变状态：
   - `ExpressionSurfaceAccess.cs`
   - `AttackExecutionSurfaceAccess.cs`
   - `ExpressionVerbBridge.cs`
   - `ExpressionManualGizmoBridge.cs`

2. 如果 `ExpressionSurfaceAccess` 中的 `hostSynchronizer` 静态实例持有可变状态，把它移到CompCombatBodyHost或按需创建

3. 如果 `AttackExecutionSurfaceAccess` 中的 `ExecutionEntry` 是无状态的（只是把请求路由到对应执行器），保留静态单例；否则同步清理

**完成标准：**
- 所有保留的静态类只做以下两件事之一：（a）无状态工具方法，（b）从ThingComp/Pawn上读取数据的查询转发
- 无任何静态类持有 `List<>`、`Dictionary<>` 等运行时可变集合

## 全局禁止事项

整个修正过程中，以下事项**严格禁止**：

1. **禁止修改CombatBodyCoordinator、CombatBodyState、CombatBodyEnterPipeline、CombatBodyExitPipeline中的任何逻辑**

2. **禁止修改CompTrion中的任何字段或方法逻辑**

3. **禁止修改任何Harmony Patch文件**

4. **禁止修改表达系统的Model层数据类**（ExpressionSnapshot、FormalExpressionResult、SingleSideExpressionSet等）

5. **禁止修改Trigger真值相关字段**（TriggerSlotState、SwitchContext的数据字段）

6. **禁止增加新功能**——本次修正只减少，不增加

7. **禁止在删除接口时顺带"优化"实现逻辑**——只做结构变化，不改业务逻辑

8. **禁止跨阶段执行**——每个阶段必须先编译通过才能进入下一阶段
