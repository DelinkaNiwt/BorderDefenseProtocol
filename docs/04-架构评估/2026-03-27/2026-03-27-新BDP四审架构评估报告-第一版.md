# 新BDP四审架构评估报告

## 一、评估基础数据

### 1. 规模对比

| 指标 | 旧BDP (Legacy) | 新BDP (当前) |
|------|---------------|-------------|
| .cs 文件数 | ~93 (不含obj) | 255 |
| 总代码行数 | ~25,089 | ~6,670 |
| 接口文件数 | ~8 | 52 |
| 模块数 | ~6 | 10+ |

关键事实：新BDP文件数是旧BDP的2.7倍，但代码行数只有旧BDP的26%。这意味着大量文件是只有接口定义、枚举、数据模型、空壳预留的"骨架文件"。

### 2. 模块文件分布

| 模块 | 文件数 | 占比 |

| Expressions（表达系统） | 92 | 36% |
| Trigger（触发体） | 48 | 19% |
| Chips（芯片定义） | 24 | 9% |
| AttackExecution（攻击执行） | 24 | 9% |
| CombatBody（战斗体） | 17 | 7% |
| VerbHosting（宿主投影） | 15 | 6% |
| Trion（资源） | 7 | 3% |

| 其它 | 22 | 9% |

## 二、第一性原理分析：需求本质是什么

### 这个模组到底要做什么

从旧BDP的真实实现和需求文档提炼，BDP的需求本质是：

1. 给Pawn装一把特殊武器（Trigger），这把武器有左右两个芯片槽
2. 芯片装入后产生攻击能力（近战/远程/技能）
3. 进入战斗体状态后芯片才能激活
4. 战斗体消耗Trion资源，资源耗尽会崩解
5. 攻击走原版Verb链路，不伪造
6. 左右芯片组合可能产生第三表达（组合技）
7. 手部损坏影响对应侧槽位

这是一个单机游戏模组。它的用户是玩家，不是其他开发者。它的运行环境是RimWorld单线程Tick循环。

### 合理的架构复杂度上限

对于这个体量的模组，合理的架构应该是：
- 3个ThingComp（Trion、CombatBody、TriggerBody）作为真值owner
- 表达规则作为纯函数/静态方法，输入槽位状态，输出表达结果
- Verb宿主直接挂在Comp上或用简单容器
- Harmony Patch做最薄的接线
- 总文件数控制在80-120个

## 三、问题清单

### 问题 P1：表达系统严重过度抽象

严重程度：高
类别：过度抽象

表达系统92个文件、5501行代码，占整个项目82%的代码量。其中：
- Pipeline子目录21个文件，包含8个接口+8个Default实现
- Projection子目录19个文件，包含8个接口
- Model子目录26个文件，大量是只有几个字段的数据类
- Config子目录12个文件
- Contract子目录11个文件

具体问题：
- `IExpressionSourceCollector` → `IExpressionSourceFilter` → `ISingleSideExpressionBuilder` → `ISpecialWeaponOverrideResolver` → `ICompositeExpressionResolver` → `IExpressionSnapshotAssembler` 这条6步管线，每一步都是接口+单一实现。这是典型的"为了可替换而抽象"，但在单机模组中没有任何替换场景。
- `IExpressionConditionInterpreter` 有3个实现（CombatBody/Trion/Mode），但它们被 `DefaultExpressionConditionEvaluator` 内部组合调用，外部永远不会单独替换其中一个。
- Projection层8个接口（`IManualEntryProjector`、`IPrimaryExpressionSelector`、`IVisualProjectionBuilder`、`IExpressionInfoProjector`、`IManualEntryGizmoResolver`、`IExpressionAbilityHostSynchronizer`、`IExpressionHediffHostSynchronizer`），每个都只有一个实现。

本质原因：把"表达规则的计算步骤"当成了"可插拔的服务组件"来设计。但表达规则本身就是BDP的核心业务逻辑，它不需要被外部替换，它需要的是清晰可读。

建议：表达管线应该是一个类内部的方法调用链，不是6个接口串联。条件解释器可以保留策略模式但不需要独立接口文件。Projection层的接口全部可以删除，直接用具体类。

### 问题 P2：SurfaceAccess静态单例模式形成隐式全局状态

严重程度：高
类别：错误设计 / 耦合风险

当前有7个SurfaceAccess静态类：
- `ExpressionSurfaceAccess`
- `VerbHostSurfaceAccess`
- `AttackExecutionSurfaceAccess`
- `TriggerSurfaceAccess`
- `CombatBodySurfaceAccess`
- `TrionSurfaceAccess`
- `ChipSurfaceAccess`

其中 `ExpressionSurfaceAccess`、`VerbHostSurfaceAccess`、`AttackExecutionSurfaceAccess` 内部持有静态单例实例：

```csharp
private static readonly DefaultVerbHostRefreshService RefreshService = new DefaultVerbHostRefreshService();
private static readonly DefaultAttackExecutionEntry ExecutionEntry = new DefaultAttackExecutionEntry();
```

问题：
1. 这些静态单例在模组加载时就创建，但它们依赖的其他静态单例可能还没初始化，存在初始化顺序隐患
2. `VerbHostSurfaceAccess` 持有的 `DefaultVerbHostContainer` 是一个全局可变状态容器，所有Pawn的VerbHost都存在这里。这实质上是一个全局字典，绕过了RimWorld的Comp生命周期
3. `TriggerSurfaceAccess`、`CombatBodySurfaceAccess`、`TrionSurfaceAccess` 是纯查询转发，没有问题。但前三个持有运行时状态的静态单例，打破了"真值在Comp上"的设计原则

本质原因：试图用Service Locator模式解耦模块间依赖，但在RimWorld的ThingComp体系中，Comp本身就是天然的依赖容器。静态单例反而引入了Comp体系之外的第二套生命周期。

建议：
- `TriggerSurfaceAccess`、`CombatBodySurfaceAccess`、`TrionSurfaceAccess` 保留，它们只是查询快捷方式
- `VerbHostSurfaceAccess` 中的Container和Factory应该挂在CompTriggerBody上，跟随装备生命周期
- `AttackExecutionSurfaceAccess` 中的ExecutionEntry应该是无状态的，可以保留静态但不应持有运行时状态
- `ExpressionSurfaceAccess` 中的HostSynchronizer应该跟随Pawn生命周期

### 问题 P3：VerbHosting层是一个不必要的中间层

严重程度：中
类别：过度抽象

VerbHosting有15个文件，包含4个接口（`IVerbHostContainer`、`IVerbHostFactory`、`IVerbHostResolver`、`IExpressionToVerbHostSpecTranslator`）。

它做的事情是：
1. 表达结果 → 翻译成VerbHostBuildSpec → 工厂创建VerbHostInstance → 存入Container → Resolver读取

但在RimWorld中，Verb天然挂在ThingWithComps的VerbTracker上。旧BDP的做法是直接在CompTriggerBody上管理Verb，没有这个中间层。

问题：
- 这个层引入了一个全局的 `DefaultVerbHostContainer`（静态字典），所有Pawn的Verb宿主都存在这里
- 每次表达变化都要走"清空→重建"的全量刷新
- 这个Container的生命周期完全脱离了RimWorld的Thing/Comp体系

建议：VerbHost应该直接挂在CompTriggerBody上，作为Comp的内部状态。不需要全局容器、工厂、解析器这套服务化架构。

### 问题 P4：Chip定义系统过早展开

严重程度：低
类别：过度抽象（但影响有限）

Chips目录24个文件，包含：
- Config: 6个配置类
- Contract: 8个契约类 + 1个解析器
- Access: 3个读取面

当前阶段芯片还没有真正的运行时实例，这些都是定义层的预结构。虽然文件数多，但每个文件都很小，且作为XML定义的C#映射是合理的。

评估：这不算严重问题。芯片定义结构本身是需要的，只是展开得比当前阶段需要的更完整。由于这些都是数据定义类，不会造成运行时问题。

### 问题 P5：CompTriggerBody仍然偏大

严重程度：中
类别：上帝膨胀趋势

CompTriggerBody通过partial class分成了5个文件：
- `CompTriggerBody.cs`（主体 + 装卸 + 启停）
- `CompTriggerBody.Reads.cs`（读取）
- `CompTriggerBody.Lifecycle.cs`（生命周期）
- `CompTriggerBody.Integrity.cs`（完整性）
- `CompTriggerBody.Contexts.cs`（上下文构建）

虽然用partial拆分了，但它仍然是所有Trigger逻辑的汇聚点。它持有：
- 3组槽位列表
- 3个SwitchContext
- 1个芯片容器
- 1个激活协调器
- 6个Surface对象
- 1个InteractionInterpreter
- 1个DisableSyncCache
- 4个事件

这不是当前的紧急问题，因为partial拆分让每个文件的职责还算清晰。但随着后续功能加入（组合技、多形态、特殊槽完整规则），它有继续膨胀的风险。

建议：当前可以接受，但后续应注意把新增的独立子流程（如组合技判定）提取为独立的协调类，而不是继续往CompTriggerBody上加partial。

### 问题 P6：Trigger Switching子系统过度分层

严重程度：中
类别：过度抽象

Trigger/Switching目录包含：
- Contexts: 4个上下文类（`TriggerActivationRequestContext`、`TriggerBindingEngineContext`、`TriggerDisableSyncContext`、`TriggerSwitchEngineContext`）
- Flow: 7个文件（`TriggerActivationCoordinator`、`TriggerActivationRequestService`、`TriggerActivationRules`、`TriggerBindingEngine`、`TriggerDisableSync`、`TriggerSwitchEngine` + 接口）
- Model: 4个模型类

"切换一个槽位"这个操作被分成了：请求服务 → 规则检查 → 协调器 → 绑定引擎 → 切换引擎 → 禁用同步，每一步都有独立的Context对象。

对于"左右各一个槽位，同时只能激活一个"这个简单规则来说，这个分层过重了。

建议：合并为2-3个类：`TriggerSwitchService`（处理切换请求和规则）、`TriggerDisableSync`（处理身体约束同步）。Context对象可以用方法参数替代。

### 问题 P7：Interaction子系统预留过多

严重程度：低
类别：过度抽象（但影响有限）

Trigger/Interaction目录8个文件，定义了交互语义的完整模型：
- `TriggerInteractionAvailability`
- `TriggerInteractionOperationKind`
- `TriggerInteractionReason`
- `TriggerInteractionTransitionMode`
- `TriggerSideInteractionSnapshot`
- `TriggerSlotInteractionSnapshot`
- `TriggerInteractionInterpreter`

这套系统的目的是把"这个槽位当前能做什么操作"翻译成正式的交互语义结果。对于GUI层来说这是有价值的，但当前GUI不是验收目标。

评估：这些都是轻量枚举和快照类，运行时开销可忽略。作为预留可以接受，但不应继续在这个方向上展开更多。

### 问题 P8：静态服务类的隐式依赖链

严重程度：中
类别：耦合风险

多个静态类之间存在隐式依赖：
- `AttackExecutionSurfaceAccess` 依赖 `VerbHostSurfaceAccess`
- `DefaultVerbHostRefreshService` 依赖 `ExpressionSurfaceAccess` 和 `VerbHostSurfaceAccess`
- `ExpressionVerbBridge` 是静态类，桥接表达和Verb
- `ExpressionManualGizmoBridge` 是静态类，桥接表达和Gizmo

这些静态依赖在编译时不会报错，但在运行时如果初始化顺序不对，会产生null引用。而且这些依赖关系在代码中是隐式的，不像构造函数注入那样显式可见。

建议：对于无状态的桥接（如`ExpressionVerbBridge`），静态是可以的。但对于持有状态的服务（如`DefaultVerbHostRefreshService`），应该改为实例化并显式传递依赖。

## 四、不算问题的地方

以下是审查中确认没有问题的部分：

1. 三大真值owner边界清晰：`CompTrion`只管资源、`CombatBodyState`只管相位、`CompTriggerBody`只管装载。这条线守住了。

2. CombatBody模块设计精炼：17个文件，职责清楚，CombatBodyCoordinator只串联三件事，CombatBodyState只回答三类问题。这是整个项目中设计最好的模块。

3. Harmony Patch克制：只有8个Patch，每个都是最薄的接线，不承载业务逻辑。符合"patch只负责接线"的原则。

4. 语义上下文轻量正确：SemanticContext是纯数据载荷，不是事件总线，不是真值owner。

5. 事件使用克制：事件只用于广播变化（`SlotLoadoutChanged`、`PhaseChanged`等），没有被滥用为控制流。

6. 存读档正确：CompTrion和CombatBodyState的ExposeData实现正确，读档后主动结算冷却。

7. 时间原则遵守：查询口主动结算（`ResolveCooldownIfFinished`），不要求外部先跑tick。

## 五、总体评估

### 架构方向正确的部分
- 三核心owner分离
- 贴RimWorld宿主
- Patch克制
- 事件不替代真值
- 时间原则

### 需要修正的部分
- 表达系统过度抽象（P1）——最严重
- 静态单例持有运行时状态（P2）——设计缺陷
- VerbHosting不必要的中间层（P3）——过度工程
- Trigger Switching过度分层（P6）——过度工程
- 静态依赖链隐患（P8）——耦合风险

### 一句话总结

新BDP的架构方向是对的（三核心分离、贴RimWorld、Patch克制），但在"如何组织内部实现"这个层面上，犯了典型的"企业级架构病"——用接口+服务+工厂+容器+管线的模式来组织一个单机游戏模组的内部逻辑。这导致255个文件中有大量是只服务于架构形式而非业务需求的胶水代码。
