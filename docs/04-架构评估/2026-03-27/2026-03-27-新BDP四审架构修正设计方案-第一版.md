# 新BDP四审架构修正设计方案

## 设计原则

本方案的修正原则是：

1. 只修正真正的架构问题，不做美化性重构
2. 保持三核心owner边界不变
3. 保持Patch层不变
4. 保持CombatBody模块不变（它是设计最好的模块）
5. 修正方向是"减少"而非"增加"——删接口、合并类、消除不必要的中间层

## 修正项 M1：表达管线去接口化

### 目标

把表达系统的6步接口管线收缩为1个类内部的方法调用链。

### 当前结构

```
IExpressionSourceCollector (接口)
  └─ DefaultExpressionSourceCollector (实现)
IExpressionSourceFilter (接口)
  └─ DefaultExpressionSourceFilter (实现)
ISingleSideExpressionBuilder (接口)
  └─ DefaultSingleSideExpressionBuilder (实现)
ISpecialWeaponOverrideResolver (接口)
  └─ DefaultSpecialWeaponOverrideResolver (实现)
ICompositeExpressionResolver (接口)
  └─ DefaultCompositeExpressionResolver (实现)
IExpressionSnapshotAssembler (接口)
  └─ DefaultExpressionSnapshotAssembler (实现)
IExpressionSnapshotPipeline (接口)
  └─ DefaultExpressionSnapshotPipeline (实现)
```

共14个文件（7接口 + 7实现）。

### 修正后结构

```
ExpressionSnapshotBuilder (单一类，内部方法链)
  ├─ Collect()
  ├─ Filter()
  ├─ BuildSingleSide()
  ├─ ResolveSpecialOverride()
  ├─ ResolveComposite()
  └─ Assemble()
```

1个文件。原来各Default实现中的逻辑直接变成这个类的私有方法。

> ⚠️ 已知现状：`Build()` 每次调用仍会重建内部对象（per-call allocation），这是 `BuildPipeline()` 的现有行为延续，不在本次修正范围内。须在 `Build()` 方法上加注释显式标注，避免后续维护者无感知地踩坑。

### 保留的接口

- `IExpressionConditionInterpreter`：保留，因为它有3个真实不同的实现（CombatBody/Trion/Mode），这是合理的策略模式
- `IExpressionReader`：保留，这是对外正式读取口
- `IExpressionSourceDeclarationProvider`：保留，这是芯片定义到表达来源的桥接点，后续芯片类型扩展需要

### 删除的接口

- `IExpressionSourceCollector`
- `IExpressionSourceFilter`
- `ISingleSideExpressionBuilder`
- `ISpecialWeaponOverrideResolver`
- `ICompositeExpressionResolver`
- `IExpressionSnapshotAssembler`
- `IExpressionSnapshotPipeline`

### 预期效果

表达Pipeline从14个文件减少到1个文件 + 3个保留接口。

## 修正项 M2：表达Projection去接口化

### 目标

删除Projection层所有只有单一实现的接口。

### 删除的接口

- `IManualEntryProjector`
- `IPrimaryExpressionSelector`
- `IVisualProjectionBuilder`
- `IExpressionInfoProjector`
- `IManualEntryGizmoResolver`
- `IExpressionAbilityHostSynchronizer`
- `IExpressionHediffHostSynchronizer`

### 保留

所有Default实现类保留，只是不再实现接口，直接作为具体类使用。

### 预期效果

Projection从19个文件减少到12个文件（删7个接口文件）。

## 修正项 M3：VerbHosting层扁平化

### 目标

消除VerbHosting作为独立中间层的存在，把Verb宿主管理收回CompTriggerBody内部。

### 当前结构

```
VerbHostSurfaceAccess (静态，持有全局单例)
  ├─ IVerbHostContainer → DefaultVerbHostContainer (全局字典)
  ├─ IVerbHostFactory → DefaultVerbHostFactory
  ├─ IVerbHostResolver → DefaultVerbHostResolver
  └─ DefaultVerbHostRefreshService
IExpressionToVerbHostSpecTranslator → DefaultExpressionToVerbHostSpecTranslator
VerbHostAutoEntryService
VerbHostAutoProxyVerb
VerbHostBuildSpec
VerbHostInstance
VerbHostSlot
```

15个文件。

### 修正后结构

```
CompTriggerBody 内部:
  └─ verbHostManager (TriggerBodyVerbHostManager，实例级成员对象)

TriggerBodyVerbHostManager (新增类，由CompTriggerBody生命周期驱动):
  ├─ Refresh(ExpressionSnapshot snapshot)   （刷新宿主列表）
  ├─ GetPrimaryRangedHost() : VerbHostInstance
  ├─ GetPrimaryMeleeHost() : VerbHostInstance
  └─ Clear()   （卸装时清空）

VerbHostInstance (保留，数据类)
VerbHostAutoProxyVerb (保留，原版桥接需要)
```

关键变化：
- `DefaultVerbHostContainer` 的全局字典消失，VerbHost跟随CompTriggerBody的生命周期
- `VerbHostSurfaceAccess` 简化为只暴露查询快捷方式，不再持有运行时状态
- 工厂、翻译器、刷新、解析的逻辑全部封装在 `TriggerBodyVerbHostManager` 内部
- CompTriggerBody 只新增一个成员对象（`verbHostManager`），不新增任何方法，不加剧 P5 上帝膨胀问题

### 预期效果

VerbHosting从15个文件减少到4-5个文件（含新增的 `TriggerBodyVerbHostManager`）。全局可变状态消除。

## 修正项 M4：Trigger Switching合并

### 目标

把切换子系统从"请求→规则→协调→绑定→切换→同步"6步合并为2-3步。

### 当前结构

```
Contexts/
  ├─ TriggerActivationRequestContext
  ├─ TriggerBindingEngineContext
  ├─ TriggerDisableSyncContext
  └─ TriggerSwitchEngineContext
Flow/
  ├─ ITriggerActivationCoordinator (接口)
  ├─ TriggerActivationCoordinator (实现)
  ├─ TriggerActivationRequestService (静态)
  ├─ TriggerActivationRules (静态)
  ├─ TriggerBindingEngine (静态)
  ├─ TriggerDisableSync (静态)
  └─ TriggerSwitchEngine (静态)
Model/
  ├─ SwitchPhase
  ├─ TriggerDisableReason
  ├─ TriggerDisableSyncCache
  └─ SwitchContext
```

15个文件。

### 修正后结构

```
TriggerSwitchService (静态，合并请求+规则+协调+绑定+切换)
TriggerDisableSync (保留，身体约束同步是独立关注点)
SwitchContext (保留)
SwitchPhase (保留)
TriggerDisableReason (保留)
TriggerDisableSyncCache (保留)
```

关键变化：
- 4个Context类删除，用方法参数替代
- `TriggerActivationRequestService` + `TriggerActivationRules` + `TriggerBindingEngine` + `TriggerSwitchEngine` 合并为 `TriggerSwitchService`
- `ITriggerActivationCoordinator` 接口删除（只有一个实现）
- `TriggerActivationCoordinator` 的逻辑合并进 `TriggerSwitchService`

### 预期效果

Switching从15个文件减少到6个文件。合并后 `TriggerSwitchService` 单文件有效逻辑行数须控制在200行以内；若超出，则改用"Rules+Request合并体、Binding+Switch合并体"双类方案，不可将超量逻辑强行压入单类。

## 修正项 M5：静态单例状态清理

### 目标

消除静态类中持有的运行时可变状态。

### 具体操作

1. `VerbHostSurfaceAccess`：随M3一起重构，不再持有Container/Factory/RefreshService单例
2. `AttackExecutionSurfaceAccess`：`DefaultAttackExecutionEntry` 如果是无状态的可以保留静态；`VerbHostAutoEntryService` 随M3重构后改为从CompTriggerBody读取
3. `ExpressionSurfaceAccess`：`ExpressionReaderSurface` 如果是无状态的可以保留；`DefaultExpressionHostSynchronizer` 应改为按需创建或挂在Comp上

### 判断标准

静态单例只允许存在于以下情况：
- 完全无状态的工具类
- 纯查询转发（如 `TriggerSurfaceAccess`）
- 不持有任何运行时可变数据

## 修正项总览

| 编号 | 修正项 | 删除文件数 | 风险 |
|------|--------|-----------|------|
| M1 | 表达管线去接口化 | ~10 | 低 |
| M2 | 表达Projection去接口化 | ~7 | 低 |
| M3 | VerbHosting扁平化 | ~9（删10新增1） | 中 |
| M4 | Trigger Switching合并 | ~7 | 低 |
| M5 | 静态单例状态清理 | 0（重构） | 中 |

预期总效果：文件数从255减少到约220，但更重要的是消除了不必要的抽象层和全局可变状态。

## 不修正的部分

以下明确不在本次修正范围内：

1. CombatBody模块——设计良好，不动
2. CompTrion——设计良好，不动
3. Harmony Patches——克制正确，不动
4. Semantics模块——轻量正确，不动
5. Chip定义系统——虽然展开较早，但都是数据类，不造成运行时问题，不动
6. Trigger Interaction子系统——轻量预留，不造成问题，不动
7. BodyConstraints模块——职责清晰，不动
8. 表达系统的Model类——数据类本身没问题，只是数量多，但每个都有明确用途
