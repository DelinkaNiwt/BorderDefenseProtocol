### R1 — HasExclusionConflict 中的 O(n×m) LINQ 标签匹配

**文件/行**：`TriggerSwitchService.cs:115`

```csharp
if (targetTags.Any(activeTags.Contains))   // IReadOnlyList.Contains 是 O(m) 线性扫
```

**问题说明**：
- `activeTags` 是 `IReadOnlyList<string>`，其 `.Contains()` 是线性扫描 O(m)。
- `.Any(activeTags.Contains)` 对 `targetTags` 每个元素都调用一次 O(m) 的 Contains。
- 外层还有一层 `foreach (activeSlots)`，每个 activeSlot 都重复这个过程。
- 实际复杂度：**O(activeSlots × targetTags.Count × activeTags.Count)**。
- 额外问题：每个 activeSlot 都调用 `GetChipLoadout(chip)` → `ChipSurfaceAccess.Read(chip)`，是一次完整的芯片读取链，非内联操作。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 临时 HashSet 替换 | 在方法内将 `activeTags` 转为 `HashSet<string>`，Contains 变 O(1) | ★ 推荐，改动最小 |
| B. TriggerSlotState 缓存 ExclusionTagSet | 装载时一次性建立 `HashSet<string> CachedExclusionTags`，免除每次读芯片 | 推荐，根治重复读芯片 |
| C. 全局 tag → slot 反向索引 | 按 tag 维护 `Dictionary<string, List<TriggerSlotState>> activeTagIndex`，激活/停用时更新 | 过度设计，当前槽位数量不值得 |

**推荐 A+B 组合**：A 消除嵌套 Contains 开销，B 消除每 activeSlot 的芯片读取链。

**复杂度变化**：

```
优化前：O(activeSlots × targetTags × activeTags)  ≈ O(3 × 4 × 4) = O(48) 次比较 + 3次芯片读取
优化后：O(activeSlots × targetTags)               ≈ O(3 × 4)    = O(12) 次比较 + 0次芯片读取（方案A+B）
改善幅度：比较次数约 ×4 倍减少；芯片读取完全消除
```

### R2 — EnsureFormalBindings 在每帧 Tick 路径上重复执行

**文件/行**：`TriggerBodyVerbHostManager.cs:94`（Tick 第一行调用）、`cs:210`（实现）

```csharp
public void Tick()
{
    EnsureFormalBindings();   // ← 每帧调用，内含 FormalHostSlots.Length 次 ContainsKey
    foreach (...) { ... }
}

private void EnsureFormalBindings()
{
    for (int i = 0; i < CompTriggerBody.FormalHostSlots.Length; i++)
    {
        if (!bindings.ContainsKey(slot))   // 初始化后永远为 true，每帧白做 N 次字典查找
        {
            ...
        }
        else
        {
            // 还有两次 null 检查
        }
    }
}
```

**问题说明**：
- `EnsureFormalBindings` 是"懒初始化"防护，设计意图是在第一次调用时建立 binding 表。
- 但它被 `Tick()`、`Refresh()`、`Clear()`、`TryGetByResultId()` 等多处调用，导致已初始化之后每帧仍全量遍历 `FormalHostSlots`（推测为 8 个）。
- 初始化后，每次调用的实际工作是：8 次 ContainsKey + 8×2 次 null 检查 = 24 次无效操作/帧/每个已装备 Trigger。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 加 `_bindingsReady` bool 标志 | 首次初始化完成后置 true，后续 EnsureFormalBindings 直接 return | ★ 推荐，改动最小，收益明确 |
| B. 将初始化移到构造函数/PostSpawnSetup | 构造时就建立全部 binding，彻底消除懒初始化模式 | 更彻底，但需确认生命周期安全 |
| C. 保持现状 | 8次操作代价极低，仅在极端情况下有问题 | 不推荐，存在隐性浪费 |

**推荐方案 A**：加一个 `private bool _bindingsReady` 字段，初始化完成后置 true，EnsureFormalBindings 开头判断 `if (_bindingsReady) return`。

**复杂度变化**：

```
优化前：O(N_slots) = O(8) 字典查找，每帧，每个带 Trigger 的装备
优化后：O(1) bool 检查，每帧
改善幅度：Tick 路径上完全消除初始化保障代码的重复执行
```

### R3 — Tick 遍历包含全部 binding，含空/无活动 verb 的槽位

**文件/行**：`TriggerBodyVerbHostManager.cs:93-109`

```csharp
public void Tick()
{
    EnsureFormalBindings();
    foreach (KeyValuePair<BdpFormalVerbHostSlot, BdpFormalVerbBinding> pair in bindings)
    {
        BdpFormalVerbBinding binding = pair.Value;
        if (binding?.RangedVerb != null) binding.RangedVerb.VerbTick();
        if (binding?.MeleeVerb != null) binding.MeleeVerb.VerbTick();
    }
}
```

**问题说明**：
- `bindings` 包含全部 `FormalHostSlots.Length`（约 8）个槽位，大多数时候只有少数 slot 实际绑定了活跃 Verb。
- Dictionary 枚举器本身是 struct，不分配堆，但每次都遍历全部条目，对未绑定 slot 做空值检查。
- 在大量 pawn 同时战斗时（100+ 个 pawn），此路径的累计开销不可忽视。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 维护活跃 verb 缓存列表 | 在 `Refresh()`/`Clear()` 时重建 `List<Verb> _activeVerbs`，Tick 只遍历此列表 | ★ 推荐，Refresh 不频繁，Tick 收益高 |
| B. 改 Dictionary 为数组 | FormalHostSlots 固定数量，改为定长数组+索引，减少字典枚举开销 | 可选，与 A 正交，可叠加 |
| C. 保持现状 | 规模小（8个），实际影响很小 | 可接受但有优化空间 |

**推荐方案 A**：`Refresh` 时同步更新一个 `List<Verb> _activeVerbsForTick`，Tick 只遍历这个列表。

**复杂度变化**：

```
优化前：O(N_bindings) = O(8)，每帧，固定成本
优化后：O(N_active_verbs)，通常 0-4，节省无活动时的遍历
改善幅度：空载时节省 100%，半载时节省约 50%
```

### R4 — TryGetByResultId 全表线性字符串扫描

**文件/行**：`TriggerBodyVerbHostManager.cs:123-145`

```csharp
public bool TryGetByResultId(string resultId, out BdpFormalVerbBinding binding)
{
    ...
    foreach (KeyValuePair<...> pair in bindings)
    {
        if (current.ResultId == resultId)   // 逐条字符串比较
        {
            binding = current;
            return true;
        }
    }
    return false;
}
```

**问题说明**：
- 每次按 resultId 查 binding 都遍历全部 8 个条目做字符串比较。
- 此方法在攻击执行路径上被调用（`VerbHostSurfaceAccess` → 攻击执行阶段），属于中频路径。
- 字符串比较（即使有引用优化）比整数/枚举查找慢。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 维护反向 resultId → binding 字典 | `Dictionary<string, BdpFormalVerbBinding> _byResultId`，在 Refresh 时同步 | ★ 推荐，O(1) 查找 |
| B. 小集合线性扫接受 | 规模 ≤ 8，字符串比较 8 次，实际毫秒级无感 | 可接受，但有正确优化路径 |
| C. 使用 StringComparer.Ordinal 加速 | 将比较改为 `string.Equals(a, b, StringComparison.Ordinal)` | 小幅提升，非根治 |

**推荐方案 A**：与 R3 的方案 A 一起在 `Refresh` 时维护 `_byResultId` 字典，增量同步成本极低。

**复杂度变化**：

```
优化前：O(N_bindings) = O(8) 字符串比较，每次查询
优化后：O(1) 字典查找，无字符串遍历
改善幅度：渐进复杂度从 O(n) → O(1)；规模固定时绝对提升约 8x
```

### R5 — ResetBindings/SyncFormalShells 每次 Refresh 产生多次堆分配

**文件/行**：`TriggerBodyVerbHostManager.cs:280`（ResetBindings）、`cs:290`（SyncFormalShells）

```csharp
// ResetBindings
foreach (...) pair.Value.State = CreateUnavailableState(pair.Key);   // 每次 new 一个对象

// SyncFormalShells
binding.RangedVerb.SyncFormalBinding(
    bindRanged ? binding.State : CreateUnavailableState(binding.Slot),   // 条件 new
    ...);
```

**问题说明**：
- `CreateUnavailableState` 每次返回 `new BdpFormalVerbBindingState {}`，共 6 个字段。
- `ResetBindings` 为每个 binding（8 个）各创建 1 个，`SyncFormalShells` 又可能再创建多个。
- 每次表达快照变化时产生 8-16 个短命小对象，增加 GC 压力。
- 虽然快照变化不是每帧，但在战斗中切换武器时会连续触发。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 静态预建 UnavailableState 字典 | `static readonly Dictionary<BdpFormalVerbHostSlot, BdpFormalVerbBindingState> s_unavailable`，按 slot 预建，免除 new | ★ 推荐，彻底消除分配 |
| B. 用 `null` 代表未绑定 | `binding.State = null` 表示未绑定，调用方检查 null 而非 IsAvailable | 语义略变，需同步修改使用方 |
| C. 对象复用/重置 | 保留 State 对象，调用 Reset() 方法清空字段 | 可行但麻烦，方案A更简洁 |

**推荐方案 A**：用 `static readonly` 字典在类加载时预建全部槽位的"不可用状态"对象，后续直接引用，零堆分配。

**复杂度变化**：

```
优化前：每次 Refresh → 8-16 次 new，GC 压力随武器切换频率线性增长
优化后：0 次 new，引用静态预建对象
改善幅度：每次 Refresh 分配量归零
```

### R6 — AppendSourceResultIds 用 List.Contains 做去重

**文件/行**：`RangedBurstEmissionAssembler.cs:160`

```csharp
private static void AppendSourceResultIds(List<string> target, IReadOnlyList<string> source)
{
    for (int i = 0; i < source.Count; i++)
    {
        string resultId = source[i];
        if (!string.IsNullOrWhiteSpace(resultId) && !target.Contains(resultId))   // O(n) per item
            target.Add(resultId);
    }
}
```

**问题说明**：
- `target.Contains(resultId)` 是 `List<string>.Contains`，对 target 做线性扫描 O(n)。
- 循环内调用 → O(n²) 总复杂度。
- **实际规模极小**（通常 2-5 个 resultId），O(n²) 在此规模下绝对开销可忽略。
- 但算法语义不正确，未来规模增长时会成为隐患。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 传入 HashSet<string> 替代 List 做中间去重 | 装配时先收集到 HashSet，最后转回 List | ★ 推荐，语义正确 |
| B. 保持现状 | 当前规模下 O(n²) ≈ O(25)，实测无感 | 可接受，但算法不正确 |
| C. 改 target 本身为 HashSet | 改变接口契约，对外仍暴露 IReadOnlyList | 接口变化大，不推荐 |

**推荐方案 A**：调用方（`TryBuild`）内部用一个局部 `HashSet<string> seenIds` 辅助去重，最后赋给 `sourceResultIds`。

**复杂度变化**：

```
优化前：O(n²)，n = sourceResultIds 总量（通常 2-5）
优化后：O(n) 摊销
改善幅度：规模小时无感；规模增长时从 O(25) → O(5) 等，5x 提升
```

### R7 — PrepareNextCast 每施放重复服务查找与 Request/Context 对象分配

**文件/行**：`JobDriver_BdpRangedAttackExecution.cs:221-264`

```csharp
private bool PrepareNextCast(Verb verb, LocalTargetInfo target)
{
    ...
    AttackExecutionService entry = AttackExecutionSurfaceAccess.ResolveEntry();    // 每次施放查找服务
    entry.TryPreparePlan(
        new AttackExecutionRequest { Pawn = pawn, ResultId = ..., ... },           // 每次施放 new
        out AttackExecutionResolvedRequest resolvedRequest);

    RangedAttackExecutionContext.TryCreateForStep(..., out RangedAttackExecutionContext context);  // 每次施放 new

    RangedAttackProtocolService protocolService = RangedAttackProtocolSurfaceAccess.Resolve();    // 每次施放查找服务
    ...
}
```

**问题说明**：
- `ResolveEntry()` 和 `RangedAttackProtocolSurfaceAccess.Resolve()` 是静态服务查找，每施放调用 2 次，但这两个服务实例在 job 生命周期内不会改变。
- `new AttackExecutionRequest` 每次施放产生 1 个小对象（含 5 个字段）。
- `RangedAttackExecutionContext.TryCreateForStep` 若内部 new 则每施放 +1 对象。
- **触发频次**：这是"每施放"不是"每帧"，一次标准远程攻击约每几秒一次，影响相对可控。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 缓存服务引用到 JobDriver 字段 | `initAction` 时一次性存储 `_entryService` 和 `_protocolService` | ★ 推荐，零成本消除重复查找 |
| B. 预分配可复用 AttackExecutionRequest | 在 JobDriver 上保持一个实例，每次施放前更新字段 | 有益，但需确认无并发/复用问题 |
| C. 保持现状 | 每施放几次 new，频次低，GC 压力极小 | 可接受，但方案 A 几乎无代价 |

**推荐方案 A**：服务引用缓存收益明确且零风险，方案 B 依需求判断是否有必要。

**复杂度变化**：

```
优化前：每施放 2 次静态方法解析 + 2 次 new 分配
优化后：每施放 0 次解析（缓存）+ 1-2 次 new（视方案B是否实施）
改善幅度：消除静态查找开销；若实施方案B，则分配进一步减少
```

### R8 — Patch_Pawn_EquipmentTracker_EquipmentTrackerTick 对全装备 TryGetComp 每帧扫描

**文件/行**：`Patch_Pawn_EquipmentTracker_EquipmentTrackerTick.cs:27-32`

```csharp
for (int i = 0; i < equipmentList.Count; i++)
{
    CompTriggerBody triggerBody = equipmentList[i]?.TryGetComp<CompTriggerBody>();   // 每帧每装备
    triggerBody?.TryFinalizePostLoadProjectionRefresh();
    triggerBody?.VerbHostManager?.Tick();
}
```

**问题说明**：
- 对 pawn 全部装备逐个调用 `TryGetComp<CompTriggerBody>()`。
- `TryGetComp<T>()` 是遍历该 Thing 的 `comps` 列表的线性搜索，绝大多数普通装备没有 CompTriggerBody，每次都是一次完整扫描后返回 null。
- 此 Postfix 挂在 `Pawn_EquipmentTracker.EquipmentTrackerTick` 上，**每帧、每个有装备的 pawn** 都会触发。
- 大规模战斗（100+ pawn × 2-3 装备）时，每帧产生 200-300 次无效 TryGetComp 调用。

**优化建议**

| 方案 | 说明 | 推荐 |
|------|------|------|
| A. 在 CompTriggerBody 装备/卸载时注册到 Pawn 级缓存 | 利用 CompTriggerBody 的 PostSpawnSetup/PostDeSpawn 主动维护 pawn → triggerBody 的映射，Patch 中直接查缓存 | ★ 推荐，根治问题 |
| B. 在 Patch 中缓存每个 pawn 的 triggerBody 引用 | 用 `ConditionalWeakTable<Pawn, CompTriggerBody>` 缓存，装备变化时失效 | 可行，但需要额外的失效逻辑 |
| C. 优化为只检查 AllEquipmentListForReading 中最后装备的 Thing | 仅对已知可能含 CompTriggerBody 的 ThingDef 做 comp 查找 | 不推荐，侵入 def 判断，脆 |

**推荐方案 A**：CompTriggerBody 在 `PostSpawnSetup` 时通过 Pawn 的某个字典注册自己，Patch 中直接取已知列表，避免每帧全扫。

**复杂度变化**：

```
优化前：O(equipment_count × avg_comp_count) 每帧每 pawn，≈ O(3 × 4) = O(12)
优化后：O(known_triggers_count) 每帧每 pawn，通常 O(1)（每 pawn 最多 1 个 Trigger 装备）
改善幅度：大规模战斗时总调用量从 ~1200次/帧(100pawn) → ~100次/帧，约 12x
```

## 优化优先级建议

综合**收益/改动成本**比：

| 优先级 | 风险点 | 理由 |
|--------|--------|------|
| **P1** | R2 — EnsureFormalBindings bool guard | 每帧路径，改动 2 行，零风险，立竿见影 |
| **P1** | R8 — 装备 Comp 缓存 | 大规模战斗时每帧节省最显著，但需设计缓存失效机制 |
| **P2** | R3 — Tick 活跃 verb 列表 | 与 R4 可一同在 Refresh 时更新，共享成本 |
| **P2** | R4 — TryGetByResultId 反向字典 | 与 R3 同步实施，在 Refresh 时一并维护 |
| **P3** | R1 — 标签匹配 HashSet + 芯片读缓存 | 切换逻辑正确性优先，性能收益附带获得 |
| **P3** | R5 — 静态预建 UnavailableState | 减少 GC，改动安全，可选实施 |
| **P4** | R7 — PrepareNextCast 服务引用缓存 | 改动轻量，顺手做 |
| **P4** | R6 — AppendSourceResultIds HashSet | 语义正确性优先，规模下影响微小 |

## 说明补充

- 以上分析均基于代码静态审查，无 profiling 数据支撑。实际热点可能与分析有偏差，建议 P1/P2 项实施前先在实战场景跑 profiler 确认。
- BDP 当前核心路径中已有较好的"事件驱动 + 版本号缓存"思路（如 `TriggerDisableSync` 的版本号提前退出），属于良好实践，应继续沿用。
- 所有优化建议以**不破坏架构边界**为前提——特别是 R8 方案 A，Comp 自注册的目标字典需设计在 BDP 内部，不能污染原版 Pawn 对象。
