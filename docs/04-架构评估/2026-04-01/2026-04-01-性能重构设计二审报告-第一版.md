# 新BDP主线性能重构设计二审报告

> 审查对象：`docs/plans/2026-04-01-bdp-performance-core-refactor-design.md`
> 审查依据：当前实际代码实现（不参考历史文档）
> 审查结论：方向正确，设计扎实，但有3处关键遗漏会直接影响实施可行性，需要在定稿前补齐。

---

## 一、设计强处确认

以下部分经审查认为正确，无异议：

1. **三层分工（真值/投影/消费）** 逻辑清晰，划分有理有据。
2. **版本号校验** 作为 AttackExecution 入口的新鲜度保障，是正确且必要的机制。
3. **刷新/失效矩阵（Section 7）** 覆盖充分，未遗漏主要状态变化入口。
4. **`CompTriggerBody.RuntimeTick()` 统一化** 是当前最佳解法，把散落多处的推进职责收口。
5. **"发布后只读、整包替换"** 规则正确，防止 UI/targeting/攻击执行读到同一对象被中途改写。
6. **Section D4 "formal host 只承接，不推导"** 边界锁正确，认可。

## 二、关键遗漏（实施前必须补）

---

### 遗漏1：`CompositeReferences` 未纳入 `TriggerCombatProjectionState`

**代码依据**：`AttackExecutionService.Stages.cs:701`

```csharp
private static CompositeExpressionReference FindCompositeReference(
    AttackExecutionResolvedRequest request,
    FormalExpressionResult result)
{
    if (request?.Snapshot?.CompositeReferences == null ...) ...
    // 线性扫 request.Snapshot.CompositeReferences
}
```

**问题**：设计 Section 5.1 列出了 `TriggerCombatProjectionState` 的字段，但**遗漏了 `CompositeReferences`**。

`BuildDualWeaponCasts()` 在双持执行时必须通过 `Snapshot.CompositeReferences` 找复合引用。同样，`FindSourceResult()` 也依赖 `request.Snapshot.Results` 做线性扫描。

如果按设计删除 `AttackExecutionResolvedRequest`（`Snapshot` 字段随之消失），这两个方法将找不到数据源，双持攻击编排会完全失效。

**需补充**：`TriggerCombatProjectionState` 必须新增：
- `IReadOnlyList<CompositeExpressionReference> CompositeReferences`

同时建议 `FindSourceResult` 的实现改为优先从新增的 `ResultIndex`（O(1)）查找，不再依赖线性扫描 `Snapshot.Results`。

---

### 遗漏2：`TryPreparePlan()` / `TryPrepareCast()` 接口命运未交代

**代码依据**：`DefaultAttackExecutionEntry.cs:113-171`、`JobDriver_BdpRangedAttackExecution.cs:221`

设计 Section 9 只描述了 `TryExecute(AttackExecutionRequest request)` 的新语义，但当前实际还有两个对外入口：

- **`TryPreparePlan()`**：`JobDriver_BdpRangedAttackExecution.PrepareNextCast()` 每次施放都调用它
- **`TryPrepareCast()`**：另一条对外公开路径

这两个入口内部都走了 `resolver.TryResolve()` → `SnapshotAttackExecutionResolver`，即**仍会触发现算**。设计把 `SnapshotAttackExecutionResolver` 标注为应删除，但没有给这两个入口指明目标态形态。

**需补充**：Section 9 里明确这两个入口的命运：
- 是合并进 `TryExecute`？
- 还是也改为接受已解析请求的版本（`TryPreparePlan(AlreadyResolvedRequest)`）？
- 还是在新模型下直接删除？

---

### 遗漏3：`AttackExecutionPlanRuntimeStore` 处置未交代

**代码依据**：`AttackExecutionPlanRuntimeStore.cs`

这是一个静态全局 `Dictionary<string, AttackExecutionPlan>`，按 `attackInstanceId` 存储执行计划，用于攻击会话持续推进阶段读取计划数据。

设计 Section 11 列了"重点重写模块"，但**未提及这个 Store**。

在新设计下，此 Store 的存在意义取决于 `PrepareNextCast` 的目标形态：
- 如果 `PrepareNextCast` 每次施放仍然重新编排（当前行为），Store 无意义，可删除。
- 如果新模型下"版本未变 = 计划可复用"，Store 需要保留并与版本号绑定。

**需补充**：明确 `AttackExecutionPlanRuntimeStore` 的命运：保留（与版本号绑定复用）、整合进 `TriggerCombatProjectionState`，还是直接删除。

## 三、设计问题（不影响实施可行性，但影响架构干净程度）

---

### 问题1：`ManualProjection` 和 `VisualProjection` 不应该在核心投影状态里

**设计位置**：Section 5.1

```
TriggerCombatProjectionState 字段：
  ManualEntryProjection ManualProjection
  VisualExpressionProjection VisualProjection
```

这两个是 **UI 消费层的呈现数据**，不是战斗逻辑的核心数据。把它们塞进核心投影状态，会让 `CompTriggerBody` 知道 UI 呈现细节，违反了 Section 6 定义的"消费层不影响投影层"分工原则。

**建议**：从 `TriggerCombatProjectionState` 分离出去。可以让 UI 读取时按需从 `TriggerCombatProjectionState` 派生/转换，或单独维护一个 `TriggerUIProjection` 衍生对象，在 UI 需要时由 `ExpressionReadService` 从核心投影构建。

---

### 问题2：`CompTriggerBody` 职责过重，建议内部委托

**设计位置**：Section 5.2

新设计给 `CompTriggerBody` 增加了大量职责：持有 `TriggerCombatProjectionState`、触发 `RebuildProjectionState()`、协调 projected hosts 和 formal host manager 同步、提供统一 `RuntimeTick()` 入口——叠加上它本身已有的 CompEquippable + IThingHolder + IVerbOwner，职责总量很重。

当前 CompTriggerBody 已经有 5 个 partial 文件（`cs / Lifecycle / FormalHosts / Integrity / Reads / Contexts`），新增职责后有继续膨胀的风险。

**建议**：考虑把"协调刷新"这一新职责委托给一个内部协调者对象（例如 `TriggerRuntimeCoordinator`），`CompTriggerBody` 持有它，不把所有协调逻辑直接内联。这不是强制要求，但可以防止文件数量进一步失控。

---

### 问题3：`TriggerCombatProjectionState` 非序列化性质需显式说明

**设计位置**：Section 5.1

设计描述了"发布后视为只读对象"，但**没有说明这个对象不参与存档**。

在 RimWorld 的 `ExposeData()` 机制下，如果实现者没有特别注意，可能误以为持有在 `CompTriggerBody` 上的字段需要序列化。

**建议**：Section 5.1 补充一条明确规则：
> `TriggerCombatProjectionState` 是纯运行时对象，不参与存档。每次读档恢复完成后，由 `RebuildProjectionState()` 重建；存档时直接忽略此字段。

---

### 问题4：Trion 运行时条件是否触发失效需澄清

**设计位置**：Section 7（刷新与失效矩阵）

当前失效矩阵覆盖的全部是 Trigger 状态变化（装入/卸出/激活/禁用/读档/切换结算）。

如果存在**以 Trion 资源可用量为前提条件**的表达（例如某个 combo 需要 Trion ≥ 阈值才成立），则 Trion 耗尽或恢复也可能使当前投影失效——而此事件未出现在矩阵中。

**建议**：明确回答以下问题：
- 当前表达系统是否存在以运行时 Trion 状态为判断条件的表达路径？
- 如果有：失效矩阵补充"Trion 可用状态变化"触发器。
- 如果没有：矩阵下方加一条说明，明确当前投影不依赖 Trion 实时状态，故不触发重建。

---

### 问题5：版本失效后的恢复策略没有闭环

**设计位置**：Section 8.4

设计说：
> "任何时候只要发现 version 不一致 → 当前请求废弃 → 上层重新准备"

但**"上层"是谁、怎么重新准备**，没有明确。

当前代码中：`JobDriver_BdpRangedAttackExecution.TryTickExecution()` 在 `PrepareNextCast()` 返回 false 时，调用 `EndJobWith(Incompletable)` 结束 job。

版本失效的语义是"快照更新了，不是真的攻击失败"，直接结束 job 并让 AI 重新选目标是否合理？还是 job 层应当**自动重试**（重新读 `CurrentProjectionState`、准备新请求、继续攻击同一目标）？

**建议**：Section 8.4 补充版本失效的恢复策略，明确选择以下其中一种：
- **自动重试**：job 层侦测到版本失效后，在本帧重新读 `CurrentProjectionState` 准备新请求，不中断攻击会话。
- **结束重选**：job 结束，由原版 AI 重新走 `TryGetAttackVerb` 选目标。并说明这是有意为之（例如表达变化意味着武器切换，需要重新评估攻击意图）。
