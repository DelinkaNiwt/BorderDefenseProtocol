# 2026-04-01 新BDP现阶段性能问题清单与优化建议

## 一、结论先看

### 1. 玩家视角结论

当前新 BDP 的性能风险等级可定为：**中高风险**。

它不是那种“刚进游戏就必卡死”的模组，但已经存在比较明显的**后期性能债**。  
真正最危险的点，不是特效粒子，也不是子弹飞行本身，而是：

- **自动战斗入口太爱重算**
- **同一次攻击前后存在重复解析**
- **每把 BDP 武器都带着一笔常驻 tick 税**

如果后面继续加芯片、组合技、复杂表达，而不先收掉这些热点，玩家在中后期更容易遇到：

- 战斗时 TPS 下滑
- 单位越多越黏
- 自动战斗频繁换目标时更明显
- 选中 BDP 单位后 UI 也开始发沉

### 2. 一句话判断

**现在最该优化的不是“子弹飞得更省”，而是“不要每次开打前都重新想一遍自己是谁、该怎么打”。**

### 3. 本文范围

本文基于当前源码做静态审查，不是游戏内 profiler 实测。  
因此这里给出的不是“精确耗时数据”，而是“结构性热点判断 + 优先级建议”。

## 二、问题总表

| 编号 | 问题 | 风险等级 | 对玩家的体感 | 优先级 |
| --- | --- | --- | --- | --- |
| P1 | 自动战斗热路径重复重建表达快照 | 高 | 多人自动战斗时最容易掉 TPS | 最高 |
| P2 | 同一次攻击请求里快照可能被重复解析 | 高 | 单次攻击准备偏重，人多时持续放大 | 最高 |
| P3 | 每把 BDP 武器都有固定 formal host tick 税 | 中高 | 武器数量越多，CPU 税越稳定 | 高 |
| P4 | 组合技匹配与表达解释缺少运行期索引/缓存 | 中高 | 内容一多后性能会明显变差 | 高 |
| P5 | UI 与手动瞄准链路仍会重复走表达构建 | 中 | 选中单位、手动操作时更容易发沉 | 中 |
| P6 | Trigger 读取口不是纯读，读取时仍会做状态准备 | 中 | 单次不重，但会放大前面几类热点 | 中 |

说明：以下“方案 A / B / C”除非特别注明，否则默认不是互斥关系。  
我的推荐会优先给出更适合当前阶段的**组合方案**，而不是强行定死单选。

复杂度说明：

- 这里写的 `O(1)` / `O(n)` 是**理论上的结构复杂度**，不是游戏内 profiler 的真实毫秒数
- 这里的 `n` 不是固定同一个东西，会按场景变化，可能表示表达条目数、组合技定义数、formal host 数、UI 投影项数等
- 对这类模组来说，很多优化的价值不只是把 `O(n)` 变成 `O(1)`，也包括把“每次读都做一次 `O(n)`”改成“只有状态变化时才做一次 `O(n)`”，或者把 `3 次 O(n)` 压成 `1 次 O(n)`

## 三、详细清单

## P1. 自动战斗热路径重复重建表达快照

### 基本描述

当前 BDP 已经接入原版自动攻击入口：

- `Source/BDP/Patches/Patch_Pawn_TryGetAttackVerb.cs`
- `Source/BDP/Patches/Patch_Pawn_MeleeVerbs_TryMeleeAttack.cs`

这两个入口都非常高频。  
问题在于，BDP 在这些入口里不是“读取一个现成结果”，而是会继续向下构建新的表达快照：

- `Source/BDP/Core/AttackExecution/AttackExecutionSurfaceAccess.cs`
- `Source/BDP/Core/Expressions/Access/Surfaces/ExpressionFormalSurfaces.cs`
- `Source/BDP/Core/Expressions/Pipeline/ExpressionSnapshotBuilder.cs`

而且 `ExpressionSnapshotBuilder.Build()` 代码里已经明确写了：当前行为是 **per-call allocation**。

### 问题解释

这意味着每次 AI 想决定：

- 这次该用远程还是近战
- 当前主攻击是谁
- 组合技要不要成立
- 这把武器该映射到哪个 formal host

它往往都不是查一份“当前已准备好的战斗结果”，而是又从 Trigger、芯片表达、条件判断、组合结果一路现算一遍。

对于玩家来说，这种问题最可怕的地方在于：

- 平时少量单位时不一定明显
- 一旦进入多人自动战斗，会被成倍放大
- 它属于“每次做决定都要交税”，不是偶发 spike

### 玩家体感

- 小规模战斗可能还能接受
- 中后期多人自动战斗时更容易掉 TPS
- 频繁换目标、频繁重新选攻击方式时更明显

### 优化建议方案

#### 方案 A：做事件驱动的“已选表达快照缓存”

思路：

- 以 `CompTriggerBody` 或表达系统为 owner
- 只在正式状态变化时失效
- 普通读取口只读缓存

适用性：

- 最符合当前架构路线
- 对玩家收益最大
- 也是最应该优先做的方案

风险：

- 需要严格定义哪些事件会让快照失效
- 不能把缓存重新升级成真值 owner

理论复杂度（直观理解）：

- 平时读取：接近 `O(1)`
- 状态失效后重建：`O(n)`
- 这里的 `n`：一次完整表达快照需要处理的表达条目、条件判断和组合判断数量

#### 方案 B：至少给自动战斗入口做“同 tick / 同版本”轻缓存

思路：

- 先不给全系统做完整缓存
- 只针对 `TryGetAttackVerb` / `TryMeleeAttack` 做短生命周期缓存
- 例如按 `Pawn + 当前 trigger 版本 + 当前 tick` 复用结果

适用性：

- 改动较小
- 可以快速压住最危险热点

风险：

- 只是止血，不是根治
- 后面仍要回到正式的事件驱动快照缓存

理论复杂度（直观理解）：

- 同一 tick / 同一版本内：第一次 `O(n)`，后续重复读取接近 `O(1)`
- 跨 tick 或跨版本后：又回到一次新的 `O(n)`
- 这里的重点：大 O 不一定彻底变了，但把“一帧里反复交税”压成了“只交一次税”

#### 方案 C：将“自动入口选主攻”与“完整表达总表构建”拆层

思路：

- 单独做一个更轻的主攻击选择结果
- 自动入口先只拿“当前主攻是谁”
- 不是每次都拉起整份表达总表

适用性：

- 对自动战斗性能很友好
- 适合作为中期优化

风险：

- 会引入“双层读取”
- 如果边界没定清，容易再次出现真值分裂

理论复杂度（直观理解）：

- 如果只做主攻击选择：更接近 `O(主攻候选数)`
- 如果仍要完整表达总表：还是 `O(n)`
- 这个方案的价值：把“每次都扫整张表”改成“很多时候只扫更小的一层”，理论上通常还是线性，但 `n` 变小了

### 我的推荐

- 推荐组合：**A + B**，C 作为中期增强项
- 推荐理由：A 是真正的主线解法，能把“每次都现算”改成“状态变了才重建”；B 改动更小，适合先把自动战斗最危险的热点压下来
- 如何理解 C：C 不是 A/B 的替代品，而是把自动入口再做轻一点的结构优化，适合在快照边界已经清楚后继续推进
- 是否需要单选：**不需要**。更合理的节奏通常是先上 B 止血，再把 A 做完整，C 视重构空间补上

## P2. 同一次攻击请求里快照可能被重复解析

### 基本描述

自动近战入口在接管前，已经先解析一次主攻击：

- `Source/BDP/Core/AttackExecution/AttackExecutionSurfaceAccess.cs`

但真正进入正式执行后，执行器又会再走一次快照解析：

- `Source/BDP/Core/AttackExecution/DefaultAttackExecutionEntry.cs`

也就是：

1. 入口先算“能不能打、该用谁打”
2. 正式执行再算“这次正式结果到底是谁”

### 问题解释

这不是“逻辑错”，但它会让一次攻击请求的前置成本偏高。  
单个 pawn 看起来问题不大，但当：

- 多个单位同时自动近战
- 连续 burst / 连续攻击会话不断重建
- 玩家后期战斗单位很多

这部分重复工作会稳定累积。

### 玩家体感

- 单次攻击响应显得更重
- 战斗规模变大后，卡顿不是爆一下，而是持续偏黏

### 优化建议方案

#### 方案 A：把已解析快照和命中结果沿调用链直接传下去

思路：

- 自动入口既然已经拿到了 `snapshot/result`
- 就不要在执行器里再重新解析一次
- 把解析结果直接挂到 request 或 resolved context 上继续传递

适用性：

- 收益直接
- 逻辑上也最顺

风险：

- 要注意请求对象生命周期
- 不能让旧快照跨过失效边界继续使用

理论复杂度（直观理解）：

- 一次攻击请求里：从“多次 `O(n)` 重复解析”压到“首次 `O(n)`，后续传递接近 `O(1)`”
- 严格按大 O 写：整体仍主要是 `O(n)`
- 这个方案主要减少的是**重复次数**，不是把线性问题神奇改成常数问题

#### 方案 B：在执行入口层做“单请求解析缓存”

思路：

- 一次攻击请求只允许解析一次
- 后续 plan、step、executor 都复用同一份解析结果

适用性：

- 不必立刻做全局缓存
- 比较容易控制边界

风险：

- 只能解决“同一次请求”的重复
- 解决不了不同请求之间的重复计算

理论复杂度（直观理解）：

- 单请求内部：第一次 `O(n)`，后续同请求复用接近 `O(1)`
- 多个不同请求累计：仍可能是 `O(请求数 x n)`
- 也就是说，它能收掉“同单次攻击里多算几遍”，但收不掉“下一次攻击再算一遍”

#### 方案 C：把 `TryExecuteAutoMelee` 改成“先选主攻再直接下发 resolved request”

思路：

- 自动入口不是只生成 `ResultId`
- 而是直接产出已经确认过的 resolved request

适用性：

- 对近战链最直接
- 可以减少中间层重复折返

风险：

- 会让入口层职责变重
- 需要防止入口层知道太多执行细节

理论复杂度（直观理解）：

- 入口解析：`O(n)`
- 后续执行阶段：如果直接消费 resolved request，接近 `O(1)` 读取
- 严格来说总复杂度通常仍落在 `O(n)`，但把后段重复折返扫表去掉了

### 我的推荐

- 推荐组合：**A + B**，C 作为近战链重构时顺带推进
- 推荐理由：A 直接消灭重复解析，收益最直观；B 则在“单次请求”这个边界上补一层保险，避免 plan、step、executor 各自再算一遍
- 如何理解 C：C 更像近战执行链的形态整理，能减少中间折返，但它不是眼下最先要解决的核心重复点
- 是否需要单选：**不需要**。A 和 B 本来就能叠加，C 也不冲突，只是更适合放到链路重构阶段做

## P3. 每把 BDP 武器都有固定 formal host tick 税

### 基本描述

BDP 在装备 tick 链上追加了 formal host 推进：

- `Source/BDP/Patches/Patch_Pawn_EquipmentTracker_EquipmentTrackerTick.cs`

其中会每 tick 调：

- `triggerBody.TryFinalizePostLoadProjectionRefresh()`
- `triggerBody.VerbHostManager.Tick()`

而 `TriggerBodyVerbHostManager.Tick()` 会遍历全部 formal host binding，把远程壳、近战壳都推一遍：

- `Source/BDP/Core/VerbHosting/TriggerBodyVerbHostManager.cs`

同时，当前固定 formal host 槽位一共有 8 个：

- `Source/BDP/Core/Trigger/State/CompTriggerBody.FormalHosts.cs`

### 问题解释

这意味着只要玩家装备着 BDP 武器，哪怕当前没真正开火，系统也可能还在维护一批 formal host 壳的运行时生命周期。

它的问题不在于“单次特别重”，而在于：

- 它是常驻税
- 会随着 BDP 武器数量线性增长
- 后期会和自动战斗重算热点叠加

### 玩家体感

- 武器越多，整体越容易发黏
- 即使不是所有人都在射击，也会有后台成本

### 优化建议方案

#### 方案 A：只 tick 当前已绑定且正在进行会话的 formal host

思路：

- 不要全表 `VerbTick()`
- 只推进当前处于活动会话中的壳
- 未绑定、未开火、无会话的壳不推进

适用性：

- 收益很直接
- 不容易破坏整体架构

风险：

- 要确认哪些 Verb 状态确实允许不 tick
- 不能把合法续接的会话误判成空闲

理论复杂度（直观理解）：

- 当前更像：每 tick `O(formal host 总数)`
- 做完后更像：每 tick `O(活跃 formal host 数)`
- 如果同时开火的 host 很少，这个成本在实战中会非常接近 `O(1)`

#### 方案 B：把 formal host 壳分成“常驻壳”和“活跃队列”

思路：

- 壳对象仍可长期存在
- 但运行时单独维护一个活跃列表
- tick 只遍历活跃列表

适用性：

- 比方案 A 更清晰
- 后续也利于扩展统计和诊断

风险：

- 需要额外维护活跃列表一致性

理论复杂度（直观理解）：

- tick 主循环：`O(活跃 formal host 数)`
- host 进出活跃队列：通常可做到接近 `O(1)`
- 和方案 A 相比，它的优势不只是快，而是把“为什么只扫活跃项”做成更稳定的结构

#### 方案 C：把 post-load 收尾从常规装备 tick 热路径中拆出去

思路：

- `TryFinalizePostLoadProjectionRefresh()` 不应该长期混在常规装备 tick 里
- 只在确实处于 post-load 待完成状态时才走

适用性：

- 改动不大
- 是明显的热路径清理动作

风险：

- 需要确认读档恢复时机不会被漏掉

理论复杂度（直观理解）：

- 正常战斗中的常规 tick：把额外收尾检查从热路径移走，稳态更接近纯 `O(host 遍历)`
- 真正需要 post-load 收尾时：按需付出一次 `O(待收尾项数)`
- 这个方案很多时候不改变主循环的大 O，但能明显降低热路径常数项

### 我的推荐

- 推荐组合：**A + C**，后续再视情况演进到 B
- 推荐理由：A 能最快减少“每把武器都要交的常驻 tick 税”；C 改动小、风险低，适合顺手把明显不该长期挂在热路径里的逻辑拆掉
- 如何理解 B：B 的结构更整齐，长期也更利于诊断和扩展，但它更像把 A 做成正式形态，不一定需要一开始就一步到位
- 是否需要单选：**不需要**。当前更建议先做 A/C 验收益，再决定是否把 B 作为第二阶段整理方案

## P4. 组合技匹配与表达解释缺少运行期索引/缓存

### 基本描述

表达快照构建时，如果主副手都有结果，会去尝试重算组合技：

- `Source/BDP/Core/Expressions/Pipeline/ExpressionSnapshotBuilder.cs`

而组合技匹配当前是按 `DefDatabase<ComboDef>.AllDefsListForReading` 线性扫描：

- `Source/BDP/Core/Combos/Access/ComboDefinitionReaderSurface.cs`

同时，芯片定义读取与表达契约解释也没有看到运行期缓存：

- `Source/BDP/Core/Chips/Access/ChipDefinitionReaderSurface.cs`
- `Source/BDP/Core/Expressions/Contract/DefaultChipExpressionContractInterpreter.cs`

### 问题解释

现在组合技内容量还不算大，所以问题还没完全炸出来。  
但结构上它已经具备“以后越做越慢”的典型特征：

- 先重建快照
- 快照里再尝试找组合技
- 找到后再重新解释组合技条目
- 芯片定义读取和校验还会继续重复做

这属于**内容规模一上去就会放大**的热点。

### 玩家体感

- 当前版本可能还只是“潜在问题”
- 后面芯片、组合技、形态越多，越容易突然变重

### 优化建议方案

#### 方案 A：为组合技建立启动期索引

思路：

- 模组启动时就按 `chipA/chipB` 建好查表
- 运行期直接 O(1) 或接近 O(1) 命中

适用性：

- 收益稳定
- 最符合组合技“定义表”特性

风险：

- 要处理无序匹配
- 要保证索引和 Def 加载结果一致

理论复杂度（直观理解）：

- 启动建索引：`O(组合技定义总数)`
- 运行期查组合技：从 `O(组合技定义总数)` 降到平均接近 `O(1)`
- 这是最典型、最干净的“用启动期一次成本换战斗期持续收益”

#### 方案 B：缓存芯片定义读取结果与表达契约解释结果

思路：

- 对 `ThingDef` 级芯片定义读取做缓存
- 对“芯片 + 当前模式”级表达契约解释做缓存

适用性：

- 很适合当前结构
- 玩家收益通常比较明显

风险：

- 需要清楚区分静态配置缓存和运行时状态缓存
- 不能把依赖当前 Trigger 状态的结果错缓存成静态结果

理论复杂度（直观理解）：

- 首次读取/解释：`O(n)`
- 同一芯片定义、同一模式下重复读取：接近 `O(1)`
- 这里的 `n` 主要指一次芯片定义读取或表达契约解释要处理的条目数

#### 方案 C：组合技解释结果预编译

思路：

- 在 Def 装载阶段就把组合技表达条目翻译成更接近运行时的结构
- 战斗时只做最少量参数拼装

适用性：

- 长期收益很高
- 适合内容继续扩张时做

风险：

- 实现成本较高
- 更适合作为第二阶段优化

理论复杂度（直观理解）：

- Def 装载/预编译阶段：大约 `O(组合技总数 x 单条解释成本)`
- 运行期真正开打时：从原本的 `O(n)` 解释，降到接近 `O(1)` 读取加少量参数拼装
- 本质上是把运行期的线性成本，前移到启动期一次性支付

### 我的推荐

- 推荐组合：**A + B**，C 作为第二阶段储备
- 推荐理由：A 先把组合技匹配从线性扫描改成索引命中；B 再把芯片定义读取和表达解释结果复用掉，两者分别处理“找得慢”和“解释得慢”
- 如何理解 C：C 的长期收益很高，但实现和验证成本也最高，适合在后续内容规模继续上升时再投入
- 是否需要单选：**不需要**。A/B 本来就是互补关系，C 也不是冲突选项，而是后续继续深挖时的加强版方案

## P5. UI 与手动瞄准链路仍会重复走表达构建

### 基本描述

当玩家选中装备了 BDP 的单位时，按钮构建会走：

- `Source/BDP/Core/Trigger/External/TriggerEquippedGizmoService.cs`
- `Source/BDP/Core/Expressions/Projection/ExpressionManualGizmoBridge.cs`

它会继续调用：

- `GetManualProjection()`

而手动瞄准时，`AttackExecutionTargetingSource` 虽然做了“同 tick 缓存”，但跨 tick 仍会继续刷新解析上下文：

- `Source/BDP/Core/AttackExecution/AttackExecutionTargetingSource.cs`

### 问题解释

这块不是当前最大的炸点，因为它只对：

- 当前被选中的 pawn
- 当前正在操作的 targeting 会话

产生影响。  
但如果表达系统本身太重，那么玩家就会更容易感觉：

- 选中单位后按钮冒得慢
- 手动瞄准时界面不够利索

### 玩家体感

- 主要影响手动操作流畅度
- 对全局 TPS 的伤害小于自动战斗热点

### 优化建议方案

#### 方案 A：让 UI 读取口优先消费已缓存快照

思路：

- `GetManualProjection()` 不再自己拉起全量构建
- 直接读取当前有效快照

适用性：

- 和 P1 属于同一收益方向
- 玩家操作时会更顺

风险：

- 仍要保证 UI 看到的是最新状态

理论复杂度（直观理解）：

- UI 普通读取：接近 `O(1)`
- 快照失效后刷新：`O(n)`
- 这里的 `n` 还是一次完整表达/投影所需的处理量，只是消费方从自动战斗换成了 UI

#### 方案 B：对 gizmo 投影做短生命周期缓存

思路：

- 选中同一 pawn 时，按钮投影按 tick 或版本缓存
- 只有表达状态变化时才重新生成

适用性：

- 成本低
- 对手感改善直接

风险：

- 只改善 UI 层，不解决下层表达构建过重

理论复杂度（直观理解）：

- 同一选中状态下：首次生成 `O(投影项数)`，后续读取接近 `O(1)`
- 状态变化或缓存过期后：再付一次新的 `O(投影项数)`
- 它更像“把连续点选/连续显示的重复 UI 开销压平”

#### 方案 C：让 targeting 会话缓存跟 trigger 版本绑定，而不是只看 tick

思路：

- 当前 targeting cache 更偏向“同 tick 复用”
- 可以升级成“同状态版本复用”

适用性：

- 对手动瞄准更友好
- 也能减少无意义重复解析

风险：

- 需要更清晰的 trigger/version 标识

理论复杂度（直观理解）：

- 当前偏向：跨多个 tick 的连续瞄准，可能反复付 `O(n)`
- 改完后：同一状态版本下通常只需首次 `O(n)`，后续多 tick 复用接近 `O(1)`
- 这个方案的收益点在于：玩家持续瞄准时，不会因为 tick 在跳就被迫反复重算

### 我的推荐

- 推荐组合：**A + B**，如果手动瞄准仍然发沉，再加 C
- 推荐理由：A 先避免 UI 再次把下层表达快照整套拉起来；B 在 gizmo 投影层补短缓存，能最快改善玩家“点选和出按钮”的手感
- 如何理解 C：C 更偏向 targeting 会话专项优化，适合在玩家手动操作占比较高，或者 A/B 做完后仍感觉瞄准链偏黏时再补
- 是否需要单选：**不需要**。A/B 是通用收益，C 是场景增强，三者可以逐层叠加

## P6. Trigger 读取口不是纯读，读取时仍会做状态准备

### 基本描述

当前 `CompTriggerBody` 的很多读取口，在真正返回数据前都会先执行：

- `SyncDisabledStateFromOwnerPawn(false)`
- `ResolveDueSwitchTransitions()`

见：

- `Source/BDP/Core/Trigger/State/CompTriggerBody.Reads.cs`

### 问题解释

这块单次开销不一定很夸张，因为禁用同步已经有版本缓存。  
但它会带来两个问题：

1. 读取口不是纯读，外部很难判断一次“读”到底有多重  
2. 当前凡是依赖 Trigger 读口的系统，都会顺带承担这部分准备动作

所以它更像“热点放大器”：

- 自己不一定是头号大问题
- 但会把 P1、P2、P5 这些高频读取进一步放大

### 玩家体感

- 单独看它未必明显
- 和其它热点叠加后，会让整体更黏

### 优化建议方案

#### 方案 A：把读取前准备和纯读取拆开

思路：

- 保留现有“安全读取”路径
- 新增内部纯读取路径给热路径使用

适用性：

- 有利于降低热路径负担
- 架构边界更清楚

风险：

- 需要严格规定谁可以走纯读取

理论复杂度（直观理解）：

- 纯读取路径：接近 `O(1)`
- 真正需要准备/结算时：`O(待同步或待结算项数)`
- 这是把“每次读都先做准备”改成“只有确实要准备时才付线性成本”

#### 方案 B：把切换结算改成明确的刷新点，不挂在普通读口上

思路：

- 在状态变化、命令提交、tick 驱动点明确结算
- 普通读口只读现成状态

适用性：

- 更符合“读写分离”思路

风险：

- 需要确保不会漏掉合法到期结算

理论复杂度（直观理解）：

- 普通读取：接近 `O(1)`
- 刷新点结算：`O(待结算项数)`
- 如果以前是 `读取次数 x 准备成本`，改完后更接近 `刷新次数 x 准备成本 + 读取次数 x O(1)`

#### 方案 C：保留现状，但为读取准备增加更细粒度短路

思路：

- 继续允许读口做准备
- 但让准备动作更早发现“当前什么都不用做”然后快速返回

适用性：

- 改动小
- 适合先做保守优化

风险：

- 仍然没有解决“读口不纯”的根问题

理论复杂度（直观理解）：

- 最坏情况：大 O 往往还是原来的 `O(n)`
- 最常见的空路径/无变化路径：更容易快速返回，接近 `O(1)`
- 所以它主要优化的是稳态常数和空转次数，不是根本性的复杂度降阶

### 我的推荐

- 推荐组合：**短期先 C，长期落到 A，B 视后续架构整理程度推进**
- 推荐理由：C 最稳妥，适合先减轻“明明没有状态变化也要准备一遍”的额外税；A 才是把热路径真正做轻、把边界拉清楚的核心方向
- 如何理解 B：B 更接近完整的读写分离，方向是对的，但改动面和时序风险都更大，通常适合作为 A 稳住后的进一步演进
- 是否需要单选：**不需要**。这里更像分阶段推进，不是三选一；C 止血、A 收口、B 深化，可以连续做

---

## 四、建议的优化顺序

### 第一梯队：先做，收益最大

1. **给表达快照建立正式缓存与失效机制**
2. **消灭同一次攻击请求内的重复解析**
3. **把 formal host tick 从“全量常驻”改成“只推进活跃会话”**

### 第二梯队：内容变多前尽快做

4. **给组合技匹配建索引**
5. **给芯片定义读取与表达契约解释建运行期缓存**

### 第三梯队：体验优化

6. **让 UI / targeting 尽量复用已解析快照**
7. **把 Trigger 读口逐步收回为更纯的读取接口**

## 五、最终判断

如果只站在玩家角度给一句结论：

**新 BDP 现阶段最真实的性能隐患，是“战斗判断链条太重”，而不是“表现层太花”。**

也就是说：

- 现在还能玩
- 但已经不适合继续一边加内容、一边放着不管
- 如果不先治理表达快照和自动战斗热路径，后面性能问题大概率会比功能问题更早爆出来
