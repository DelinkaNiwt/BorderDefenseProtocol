# FormalHostVerb 存档持久化设计分析

## 一、v3 的任务

v2 已经把问题拆成了三层：

1. formal host 壳进入存档树
2. 读档后的第一次重绑不清空已恢复状态
3. burst 中段依靠持久化 cursor 续接

但用户随后又提出了两个更关键的问题：

1. 这条路线会不会把 BDP 架构重新耦死
2. 旧 BDP 当年是怎么存读攻击行为的，能不能取其所长

因此 v3 的任务不是推翻 v2，而是把 v2 变成一份真正可作为最终架构依据的文档：

- 明确旧版可继承的部分
- 明确旧版必须禁止回潮的部分
- 明确现版这条路线新增的正式存档契约
- 给出“新版分层 + 旧版对象级续接”的最终组合方案

---

## 二、最终概念结论

最终推荐方向只有一句话：

**保留新版的表达分层，吸收旧版的固定对象续接，但禁止具体芯片攻击 verb 重新变成原版攻击入口。**

把这句话展开，就是：

1. 原版触发体本体攻击继续自然保留，BDP 不替换它。
2. BDP 的攻击入口继续独立存在，不成为原版攻击候选池的一部分。
3. 自动攻击应由 BDP 表达系统选出的默认主攻击负责，而不是原版自己去抓某个 BDP 攻击对象。
4. 如果 BDP 的攻击已经进入暖机或 burst，中途存档再读档，应继续这次 BDP 会话，而不是打断重来。
5. 为了做到这一点，真正要跨存档活下来的，不应该是“具体芯片 verb 池”，而应该是“固定 formal host 壳对象”。

---

## 三、旧 BDP 为什么更容易续接

旧 BDP 更容易做存读档续接，不是因为它更先进，而是因为它更扁平。

它的攻击体系大致是：

- `CompTriggerBody` 直接缓存一组具体攻击 verb
- 存档时把这些具体 verb 直接 deep-save
- 读档后按固定 `loadID` 把旧 verb 实例找回来复用
- 原版 `Verb.ExposeData()` 自动把 warmup、target、burst 这些基础状态一起带回来

旧版的真正优点有 4 个：

### 3.1 固定对象续接

旧版让“同一个攻击对象”跨存档继续活着。

这意味着：

- 原版引用它的 `Job.verbToUse`
- 原版引用它的 `Stance_Warmup.verb`

在读档后都容易重新对上。

### 3.2 稳定身份恢复

旧版不是自由重建一批新 verb，而是按固定 `loadID` 复用旧对象。

这让“这是同一次攻击会话里的同一个宿主对象”这件事，有了稳定的技术落点。

### 3.3 借原版存原版擅长的状态

旧版没有试图重造整套 verb 基础状态机。

它更多是借原版已有的：

- `state`
- `currentTarget`
- `burstShotsLeft`
- `ticksToNextBurstShot`

这部分思路是对的。

### 3.4 运行时派生数据不全部硬存

旧版并没有把所有运行时会话对象都塞进存档。

这说明一个事实：

**真正需要持久化的，不是所有运行时细节，而是能让会话重新接上的最小真值。**

---

## 四、旧 BDP 为什么不能直接回退

旧版虽然在“续接”上有可取之处，但它有几个部分绝不能回潮。

### 4.1 具体芯片 verb 过于贴近原版攻击体系

旧版的具体攻击 verb 本体长期存在于 TriggerBody 自己的缓存里，并直接参与：

- 手动攻击
- 自动攻击代理
- 存读档续接

这在旧架构里能工作，但在现版需求下会造成一个严重问题：

**表达系统、宿主壳、自动攻击入口三者重新塌回一层。**

### 4.2 “攻击真身就是具体芯片 verb”违背现版分层

现版的目标已经明确：

- 表达系统负责决定“现在应该打什么”
- formal host 负责作为稳定宿主壳
- 执行层负责把结果落成动作

如果回退到“左手 verb / 右手 verb / dual verb / combo verb 本体直接跨档续接”，那表达层会再次被具体攻击对象反向绑架。

### 4.3 容易再次把原版攻击候选池污染回来

用户已经明确要求：

- 触发体本体攻击必须自然保留
- BDP 攻击不能成为原版入口候选
- 自动攻击必须由 BDP 自己独立接入

如果重新让具体芯片攻击 verb 成为长期暴露的核心对象，那么未来非常容易再次发生：

- 原版在补丁前先抓到 BDP 攻击对象
- UI 上原版本体攻击被替代
- 近战池、远程池重新混杂

这条路和“彻底分家”是直接冲突的。

---

## 五、v3 的最终架构主张

v3 采用的是“新旧结合，但边界严格”的路线。

### 5.1 继承旧版什么

只继承旧版这 3 件事：

1. 固定对象续接
2. 稳定 `loadID` 复用
3. 尽量借原版已有 verb 基础状态

### 5.2 绝不继承旧版什么

绝不继承旧版这 4 件事：

1. 具体芯片攻击 verb 直接作为跨档主宿主
2. 具体芯片攻击 verb 重新成为原版攻击候选
3. 自动攻击依赖原版先抓到某个 BDP 攻击对象
4. 把表达系统的选择结果固化成一套长期常驻的具体 verb 池

### 5.3 现版真正应该跨档存活的对象

v3 结论非常明确：

**跨存档真正存活的对象，应该是固定 formal host 壳，不是具体芯片攻击 verb。**

也就是说：

- 会话载体是固定 formal host 壳
- 业务真值来源是表达结果
- 执行动作仍由现版执行层完成

这样既拿到了旧版“对象级续接”的稳定性，又保住了现版“表达与原版彻底分家”的结构。

---

## 六、v3 的第一性原理

v3 建立在 5 条不可动摇的原则上。

### 6.1 原版攻击入口和 BDP 攻击入口是两套系统

原版的本体攻击入口属于原版。

BDP 不应该去篡改“触发体本体能不能被看见、能不能被点、能不能存在”这件事。

### 6.2 BDP 自动攻击不等于原版自己抓到一个 BDP verb

“自动攻击用 BDP 默认主攻击”这句话的正确含义是：

- 默认主攻击由 BDP 表达系统给出
- 自动攻击由 BDP 自己独立接入并驱动
- 不是让原版自己去候选池里挑一个 BDP 攻击对象

### 6.3 会话宿主必须稳定

只要 `Job` 和 `Stance` 还引用某个对象，这个对象就必须在读档后还能被找回。

所以 formal host 壳必须变成正式 deep-save 对象。

### 6.4 业务真值必须最小化持久化

必须持久化的，是会话续接最小真值：

- 这个壳当前代表哪个表达结果
- 这轮 burst 已经打到哪

不应持久化的，是大批派生运行时结构：

- 完整表达快照
- 完整 emission plan 对象
- 各类服务对象

### 6.5 派生表面可以重注入，运行态不应被误清

读档后，`verbProps`、`tool`、`maneuver` 这些派生表面应该重新注入。

但如果是同一槽位、同一结果、同一会话，就不能因为“重新注入表面”而把 warmup / burst 运行态清空。

---

## 七、v3 的正式分层

v3 下，攻击体系分为 4 层。

### 7.1 表达层

职责：

- 根据 Trigger 真值、芯片激活状态、组合关系
- 给出当前可用攻击结果
- 给出默认主攻击

这一层仍然是业务真值来源。

### 7.2 formal host 壳层

职责：

- 为每个固定宿主槽位提供长期存在的稳定 verb 壳
- 被 `Job.verbToUse` 和 `Stance_Warmup.verb` 引用
- 持有最小会话身份

这一层是跨存档续接的正式宿主层。

### 7.3 执行层

职责：

- 根据当前表达结果与目标，准备执行上下文
- 生成 emission plan
- 让宿主 verb 实际发射

这一层仍然负责“如何打出来”，但不负责持久化整包派生计划。

### 7.4 恢复与降级层

职责：

- 读档后把 formal host 壳重新挂回固定槽位
- 对同会话做保态重绑
- 对失效会话做安全终止

这一层不是正常业务层，而是跨存档边界的恢复层。

---

## 八、v3 的正式持久化契约

这部分是 v3 最关键的新增内容。

不是所有字段都重要，真正重要的是“以后什么一旦改了，会影响旧档兼容”。

### 8.1 对象级契约

以下对象必须进入正式存档树：

- 每个固定槽位的 `BdpVerb_FormalHostShoot`
- 每个固定槽位的 `BdpVerb_FormalHostMelee`

注意：

- 是固定 formal host 壳
- 不是一批具体芯片 verb

### 8.2 稳定身份契约

以下身份必须保持稳定：

- formal host 固定槽位顺序
- formal host `loadID` 生成规则
- `HostResultId` 语义

这意味着：

- 以后不能随便改槽位顺序
- 以后不能随便改 `HostResultId` 生成规则
- 改了就要视为存档兼容边界变化

### 8.3 原版基础状态契约

以下运行态继续借原版 verb 基类持久化：

- `state`
- `currentTarget`
- `currentDestination`
- `burstShotsLeft`
- `ticksToNextBurstShot`

这部分不应重复发明一套 BDP 自己的平行状态。

### 8.4 BDP 最小会话真值契约

以下字段属于 BDP 自己必须持久化的最小真值：

- `HostResultId`
- `pendingWindowIndex`
- `pendingWindowProjectilePlanIndex`

必要时可持久化：

- `pendingEmissionConsumedCount`

但它更多是诊断值，不是 gameplay 真值核心。

### 8.5 明确不入档的内容

以下内容继续保持“读档后重建”，不进入正式存档契约：

- `verbProps`
- `tool`
- `maneuver`
- `pendingVerbEmissionPlan`
- `pendingEmissionWindows`
- `SemanticContext`
- 表达快照对象本身
- 协议服务对象本身

## 九、v3 的恢复流程

### 9.1 存档前

正常战斗过程中：

- `Job.verbToUse` 指向 formal host 壳
- `Stance_Warmup.verb` 指向 formal host 壳
- formal host 壳本身被 `CompTriggerBody -> TriggerBodyVerbHostManager` deep-save

因此引用关系和对象本体都在同一存档树里。

### 9.2 读档阶段一：对象恢复

在 `LoadingVars` 阶段：

- `CompTriggerBody` 确保内部状态已存在
- `TriggerBodyVerbHostManager` 读取 deep-saved formal host 壳列表
- 这些壳对象连同原版 verb 基础状态一起恢复

这一阶段只解决“对象活回来”。

### 9.3 读档阶段二：槽位回挂

在 `PostLoadInit` 阶段：

- 把已恢复的壳按固定槽位重新挂回 bindings
- 重新注入 owner、slot、verbTracker、caster 等运行时引用
- 给已恢复的壳打上“首次 post-load 重绑保态”标记

这一阶段只解决“对象重新接回宿主结构”。

### 9.4 读档阶段三：表达重绑

之后再执行：

- `RestoreSlotTruth()`
- `RebuildContainerFromSlotTruth()`
- `RefreshProjectedOutputs()`
- `verbHostManager.Refresh(snapshot)`

此时 formal host 壳会重新拿到当前表达结果的派生表面。

关键规则：

- 如果是同槽位、同 `HostResultId`、同会话，不能 `Reset()`
- 如果结果身份变了，或者绑定已失效，才允许 `Reset()`

### 9.5 读档阶段四：惰性续接

当 warmup 倒计时结束，或 burst 继续推进时：

- 如果当前没有 pending emission plan
- 但 formal host 壳还持有合法 `HostResultId`
- 且目标仍有效

则按 `HostResultId + currentTarget` 重新组装 plan。

如果是 burst 中段，还要把 plan 快进到：

- `pendingWindowIndex`
- `pendingWindowProjectilePlanIndex`

然后继续剩余部分。

### 9.6 读档阶段五：安全降级

以下任一条件失败，都不硬续：

- 壳对象未恢复
- `HostResultId` 失效
- 当前表达结果已变化
- cursor 不合法
- 当前结果与旧会话结构不兼容

此时必须主动终止旧会话，而不是强行接上。

## 十、v3 新增的架构耦合，哪些是好的，哪些是不允许的

### 10.1 新增的“好耦合”

v3 会新增 3 条正式内部耦合：

1. formal host 壳 <-> 固定槽位
2. formal host 壳 <-> `HostResultId`
3. formal host 壳 <-> burst 消费游标

这是允许且必要的耦合。

原因很简单：

- 不把壳绑定到固定槽位，就没有稳定宿主
- 不把壳绑定到 `HostResultId`，就不知道它代表谁
- 不把壳绑定到消费游标，就无法中段续接

这些耦合都发生在 BDP 内部，而且都服务于“独立攻击体系的连续性”。

### 10.2 不允许出现的坏耦合

以下耦合一旦出现，就说明架构又歪回去了：

1. 原版攻击候选池再次能直接抓到 BDP formal host 之外的攻击对象
2. 具体芯片攻击 verb 重新变成长期持久化的主攻击宿主
3. 表达系统结果必须依赖某个具体缓存 verb 才能存在
4. 为了续接，把整包表达快照或整包执行计划硬塞进存档

这些都必须在设计上禁止。

## 十一、v3 对旧版与 v2 的统一评价

### 11.1 旧版的价值

旧版最大的价值不是“那套就对”，而是它证明了两件事：

1. 攻击宿主对象只要稳定存在，原版基础状态就很容易续上
2. 读档续接不一定需要存整包运行时结构

### 11.2 v2 的价值

v2 最大的价值是把问题从“想办法别报错”提升成了：

- 对象持久化
- 首次重绑保态
- burst 游标续接

这三层结构判断是对的，仍然成立。

### 11.3 v3 的补完

v3 做的事情，是把“旧版对象级续接的优点”正式接到 v2 的三层结构里。

因此 v3 不是否定 v2，而是给 v2 增加两个决定性说明：

1. 为什么这条路不会把现版架构带回旧版
2. 为什么必须让 formal host 壳，而不是具体芯片 verb，成为正式跨档宿主

## 十二、最终推荐方案

### 12.1 总体方案

采用：

**fixed formal host shell persistence**

中文可以理解为：

**固定 formal host 壳持久化方案**

它的定义是：

- 用固定 formal host 壳作为唯一正式跨档宿主
- 用 `HostResultId` 把壳接回表达结果
- 用最小 burst cursor 恢复中段消费位置
- 用读档后首次重绑保态机制，避免自己把恢复态清空

### 12.2 这条方案为什么是当前最优

因为它同时满足了 4 件事：

1. 满足用户对“原版入口和 BDP 入口彻底分家”的要求
2. 满足用户对“自动攻击应继续使用表达系统默认主攻击”的要求
3. 吸收旧版“固定对象续接”的稳定性
4. 避免旧版“具体芯片 verb 回流为原版候选”的结构问题

### 12.3 这条方案的代价

它的代价不是性能暴涨，也不是逻辑复杂度爆炸。

真正的代价是：

- `HostResultId` 成为正式存档契约
- fixed slot 顺序成为正式存档契约
- post-load 恢复顺序成为正式架构约束

也就是说：

以后改这些地方要更谨慎，但这是合理代价。

---

## 十三、实施边界

v3 只回答设计，不在这里扩写施工细节。

但它明确给出 5 条实施边界：

1. 只让 formal host 壳入档，不让具体芯片 verb 回流入档。
2. 只持久化最小会话真值，不持久化整包派生执行结构。
3. 第一轮 post-load rebind 必须支持保态。
4. recovery 只能做 safety net，不能再一刀切清空所有 BDP 会话。
5. 一旦当前表达结果与旧会话不兼容，必须安全终止，不能强续。

---

## 十四、完成标准

只有同时满足以下条件，v3 方案才算真正落地成功：

1. 触发体本体攻击继续自然存在，UI 不被 BDP 替代。
2. BDP 自动攻击继续由表达系统默认主攻击负责。
3. 原版攻击入口不会直接候选到 BDP 具体攻击对象。
4. 攻击暖机中存档，读档后能继续暖机并正常发射。
5. burst 中段存档，读档后从正确位置继续，而不是从头重复。
6. 结果失效时旧会话能安全终止，不刷异常。

---

## 十五、v3 最终结论

v3 的最终判断是：

**这条路线可行，而且是当前最符合需求本质的路线。**

理由不是“它能把报错压下去”，而是：

- 它继续坚持 BDP 与原版攻击入口彻底分家
- 它让 BDP 自动攻击继续服从表达系统，而不是服从原版候选逻辑
- 它吸收了旧版对象级续接的优点
- 它把续接所需的新增耦合严格限制在 BDP 内部的正式契约上

因此，v3 不是“折中方案”，而是：

**在不回退旧架构的前提下，把旧版最有价值的续接经验，正式并入现版分层体系。**
