# Trigger单一真值收口设计裁定（第一版）

## 裁定目的

本裁定只回答一件事：

- Trigger 的正式业务真值到底是什么

当前运行时问题已经证明，`chipContainer` 与 `TriggerSlotState.loadedChip` 同时承担“芯片存在性真值”会在读档阶段发生分叉。后续整改不得再保留这种双真值结构。

## 正式裁定

### 1. `TriggerSlotState` 是唯一正式业务真值

以下事实只允许由 `TriggerSlotState` 表达：

- 某个槽位装了什么芯片
- 某个槽位是否激活
- 某个槽位是否禁用
- 某个槽位的绑定关系

### 2. `chipContainer` 不是业务真值

`chipContainer` 的职责被裁定为：

- Trigger 对芯片 `Thing` 的物理持有容器
- 配合 RimWorld 存档系统持有和保存实际对象

`chipContainer` 不再回答：

- 某枚芯片属于哪个槽位
- 哪些芯片当前激活
- 哪些芯片参与表达、宿主或攻击决策

### 3. 读档恢复链必须单向

正式顺序固定为：

1. 恢复 slot 真值
2. 校验并收束 slot 真值
3. 从 slot 真值重建 `chipContainer`
4. 刷新表达快照
5. 重建 VerbHost

不允许：

- `chipContainer` 和 slot 各自恢复后再互相补
- expression / host 在 slot 真值尚未稳定前提前刷新

### 4. 一致性修复只允许 `slot -> container`

允许：

- slot 有芯片，container 缺芯片时，把芯片补回 container

不允许：

- container 有芯片，slot 没引用时，反向猜测该芯片应该回到哪个槽位

后一种情况属于正式真值缺失，应当显式暴露并阻断后续投影，而不是偷偷修洞。

### 5. 若需增强序列化，仍然只能增强 slot

如果后续证明 `TriggerSlotState.loadedChip` 使用 `Scribe_References` 恢复不稳定，本轮允许增强 slot 的序列化方案，例如：

- 增加 slot 级稳定标识
- 增加 slot 级引用恢复辅助字段

但不允许把业务真值迁移给 `chipContainer`，也不允许引入“双向猜测”的补丁恢复。

## 当前代码的直接违例

### 违例 1：`chipContainer` 与 slot 并行恢复

`CompTriggerBody.PostExposeData()` 目前同时恢复：

- `mainSlots/subSlots/specialSlots`
- `chipContainer`

但读档后只做了局部一致性修复，没有明确单向恢复链。

### 违例 2：完整性修复仍然是“修补式”而不是“重建式”

`RestoreSlotContainerIntegrity()` 当前只修：

- slot 有 chip，但 container 没 chip

它没有把 `chipContainer` 明确降级成从属存储，也没有定义 container 孤儿 chip 的正式处理方式。

### 违例 3：下游层默认假定 loadout 已经稳定

expression、VerbHost、auto ranged 都依赖 loadout 已经正确恢复；一旦 slot 真值为空，下游会看到：

- snapshot 空
- host 空
- auto ranged 无 verb

这说明恢复链没有在 Trigger 内部收口。

## 本轮整改要求

### 必做

- 收口 `TriggerSlotState` 为唯一正式业务真值
- 把 `chipContainer` 改为 slot 从属容器
- 重写读档恢复顺序
- 删除任何 `container -> slot` 猜测路径

### 不做

- 不引入新的大状态对象
- 不做兼容旧双真值结构的长期保留层
- 不从攻击层兜底 Trigger 恢复缺口

## 预期结果

本轮整改完成后，应当自然满足：

- 读档后如果 slot 真值恢复成功，则 expression/host/auto ranged 自然恢复
- 读档后如果 slot 真值恢复失败，也会在 Trigger 真值层显式暴露，不再以下游 `Stance_Warmup` 空引用的形式出现
