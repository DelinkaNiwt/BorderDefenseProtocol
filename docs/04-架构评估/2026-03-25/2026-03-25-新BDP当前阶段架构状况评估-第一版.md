# 新 BDP 当前阶段架构状况评估（第一版）

## 目的

这份文档用于基于以下三类材料，对新 BDP 当前阶段的架构状况做一次正式评估：

- 第一性原理与项目宪章
- 需求说明目录中的当前正式裁定
- 旧 BDP 的代码事实与当前新 BDP 的代码事实

它回答的重点不是：

- 旧 BDP 以前具体写成什么样
- 新 BDP 现在已经补回了多少零散功能

而是：

- 新 BDP 当前的架构方向是否正确
- 当前已经真正成立的正式骨架是什么
- 哪些关键协议已经有样板，哪些仍停留在文档层
- 哪些地方如果继续按旧习惯补功能，会把结构重新带偏

## 评估口径

本次评估固定按以下口径执行：

### 1. 需求文档高于旧 BDP 的结构做法

旧 BDP 仍然是：

- 外在本质表现的重要事实来源
- 旧问题和旧复杂度的暴露来源

但它不是：

- 新 BDP 当前架构结构的直接模板

如果需求文档已经对旧 BDP 的某些问题做了重新讨论、重新裁定、重新分责，
则本次评估优先采用需求文档定义的新边界。

### 2. 旧 BDP 主要回答“行为曾经是什么”

旧 BDP 在本次评估中的核心作用是：

- 证明哪些外在表现曾真实存在
- 暴露哪些历史实现把 owner、事件、缓存、UI、表现、恢复缠成一锅
- 证明某些复杂度不是凭空想象，而是后续必须正式承接的问题

### 3. 新 BDP 主要回答“当前正式架构已经做到哪里”

本次评估不按类名想象功能，
而按当前代码里真正已经接通的正式链路来判断。

### 4. 最终判断标准

新 BDP 的优劣，不按“像不像旧 BDP 的代码结构”判断，
而按下面这条标准判断：

- 是否保留旧 BDP 的外在本质表现方向
- 是否落实了需求文档里重新裁定后的正式边界
- 是否正在形成一套贴 RimWorld、真值 owner 清楚、协议边界诚实、可继续演化的新架构

## 一、总判断

## 1. 当前阶段总体定性

新 BDP 当前处于：

- 架构方向已基本选对
- 第一阶段最小主链已打通
- 多个关键协议仍停留在“文档已裁定、代码未闭环”的阶段

它不是：

- 还没有架构、只是零散试写

也不是：

- 主体架构已经完整，只差补外围功能

更准确地说，它现在是：

- 已经验证了核心路线可行
- 但仍处在“正式协议与正式事务闭环尚未完全落地”的阶段

## 2. 总体评价

如果只看架构方向，
当前评价偏正面。

如果看正式闭环完成度，
当前仍明显偏早期。

因此更合适的结论是：

- 新 BDP 当前不是“功能回收中后期”
- 而是“正确骨架已经立起来，正在从样板链走向正式体系化”的阶段

## 3. 和旧 BDP 的本质差异

旧 BDP 的主要问题，不是没有复杂能力，
而是：

- Trigger、战斗体、Verb、UI、恢复、显示、事件、临时状态彼此长期纠缠
- 局部能力常常直接长成总控层
- 很多行为虽然能跑，但 owner 边界不诚实

新 BDP 当前已经明显没有继续沿这条路走。

现在的新代码更明显在做这些事：

- 把 Trion / CombatBody / Trigger 三类真值 owner 拆开
- 给正式读取口、正式命令口、正式事件口做分层
- 把表达、投影、协调、patch、语义传播拆成不同层

这说明它已经跨过了最危险的一步：

- 没有继续把旧 BDP 的混合结构原样重抄

## 二、当前已经成立的正式架构

## 1. 三核心骨架方向已经成立

当前代码已经明确围绕三核心骨架组织：

- `CompTrion`：资源真值 owner
- `CombatBodyState`：战斗体相位真值 owner
- `CompTriggerBody`：装载与局部激活真值 owner

这与项目宪章和需求文档的长期硬约束一致。

这也是当前新 BDP 最大的正面结论之一：

- 真值边界至少已经被正式承认

虽然业务还没全部接回，
但“谁原则上不该持有什么”已经比旧 BDP 清楚得多。

## 2. Trigger 最小正式主链已经成立

当前新 BDP 在 Trigger 这一块已经真正落地了最小正式主链：

- 槽位结构
- 芯片装载与卸载
- `ThingOwner` 正式容器
- 局部激活与局部关闭请求
- 基本切换上下文
- 正式读取面 / 命令面 / 事件面

这说明 Trigger 已经不再主要靠：

- UI 侧临时状态
- Verb 侧副作用
- 调试式缓存

来勉强维持事实。

但这里必须加一条限制判断：

- 它现在成立的是“最小 Trigger 正式 owner”
- 不是“Trigger 全业务规则已经完整接回”

## 3. 表达最小解析样板已经成立

当前表达系统最重要的正面进展不是功能丰富度，
而是已经形成了一条样板链：

- 从 Trigger 正式激活来源收集来源
- 进入独立表达解析层
- 解析出默认主近战 / 主远程
- 交给自动攻击桥和手动按钮桥做最小投影

这条链证明了两件事：

- “来源 -> 结果 -> 投影”这个分层方向可行
- “贴原版宿主而不是自造平行攻击系统”这条路线可行

但它目前仍然只是：

- 最小表达解析样板

还不能视为：

- 需求文档意义上的完整多表达系统

## 4. 语义下传是当前最扎实的一块

当前新 BDP 最扎实的一块，
不是战斗体，也不是多表达，
而是攻击语义上下文的下传链。

现在它已经证明：

- `Verb` 能携带语义
- `Projectile` 能继续带语义
- 爆炸链能继续带语义
- 伤害下游能看到“攻击行为名”而不是粗糙来源名

这说明新 BDP 已经不是单纯在做逻辑接线，
而是在开始形成：

- 链路级信息语义
- 执行后果解释能力

这块是后续远程链、崩解链、信息兼容层非常值得保留的正式样板。

## 5. CombatBody 与 Trion 已有正确骨架，但主业务尚未真正接回

`CompTrion` 已经有正式资源语义骨架：

- `Cur / Max / Allocated / Reserved / Available`
- 一次性消耗
- 正式占用与释放
- 持续消耗注册与结算
- 自然恢复
- 冻结
- 边界事件

`CombatBodyState + CombatBodyCoordinator + Host` 也已经形成了：

- 相位真值 owner
- 主链协调者
- 薄宿主位

这说明：

- 战斗体与资源这两块的“正确边界框架”已经写出来了

但当前仍不能说：

- 战斗体正式主业务已经回到新 BDP 主链中

因为它现在更像：

- 正确的边界骨架与事务预留

而不是：

- 已经完整接管旧 BDP 战斗体主流程的正式系统

## 三、当前没有完成的关键正式协议

这一节不是说“还少哪些功能”。

这里要强调的是：

- 当前真正没完成的，是决定后续所有实现怎么长的正式协议

## 1. Trigger 完整装载规则还未闭环

需求文档已经把 Trigger 的正式边界重新裁定得很清楚：

- `Special` 是正式槽位侧
- 双手锁定属于 Trigger 层跨侧约束
- 局部禁用属于正式真值
- 多形态切换属于 Trigger 真值变化点与整链重算触发点

但当前代码还没有把这些要求完整接回。

因此 Trigger 当前的真实状态是：

- owner 收缩方向对
- 最小闭环成立
- 完整规则未闭环

这意味着后续如果急着往 Trigger 上继续叠业务，
很容易再次把它从“诚实 owner”推回“大总管”。

## 2. 表达系统还不是需求文档意义上的“多表达系统”

需求文档已经重新界定表达系统：

- 单侧结果先成立
- 双侧关系后重算
- 攻击型与非攻击型表达都要有正式结果地位
- 按钮层、主攻击层、外部兼容层、非攻击读取层必须分层

当前代码离这个目标还有明显距离。

现在已经有的只是：

- 当前激活来源收集
- 默认主近战 / 主远程选择
- 最小按钮与自动攻击投影

因此当前表达系统更准确的描述是：

- 表达样板解析器

而不是：

- 多表达正式结果模型

## 3. CombatBody 正式闭环仍未成形

需求文档已经把 CombatBody 的结构重新钉死了：

- 整体相位闭环
- 多来源 -> 单崩解入口 -> 收尾
- 局部失效与整体崩解分层
- Coordinator 统一编排
- Cleanup 不能再长成平行总控

当前代码虽然明显朝这个方向做了，
但还没有把以下事项真正接回主行为：

- 激活前检查与资源锁定的正式接线
- 宿主变换的正式实现
- `Collapsing` 后续链
- 收尾与恢复的正式事务闭环
- 与 Trigger / Trion / 身体恢复的正式整合

因此当前 CombatBody 的判断应是：

- 架构边界意识正确
- 代码骨架已搭
- 正式业务闭环仍然缺口很大

## 4. 远程链还没有进入“协议化阶段”

旧 BDP 的远程链已经证明：

- 远程能力绝不是“一个自定义 Projectile + 一些特效”这么简单

但需求文档已经把口径更新为：

- 不按旧玩法名复刻
- 要按正式阶段协议、标准字段、标准合并、标准冲突裁定来重建

这意味着新 BDP 当前不能按“已经有自定义 Verb / Projectile”就判断远程架构差不多了。

当前更准确的判断是：

- 宿主方向选对了
- 最小语义桥接也选对了
- 但统一阶段协议、阶段结果对象、意图合并器、扩展挂点声明面还没有真正落地

所以远程链目前仍然属于：

- 方向已证实
- 体系未成形

## 5. 外部兼容、视觉投影、信息分层基本还在预留态

需求文档已经把这块重新讨论过了：

- 视觉不是附属美术问题
- 外部兼容不能反过来扭曲真实多表达系统
- 单主表面只是回退，不是系统本体

但当前代码几乎还没有进入这一阶段。

这意味着当前不能误判为：

- 后面只要加点 UI、加点纹理、补点说明字段就行

更准确的判断是：

- 视觉与兼容层的正式读取模型还没真正开始落地

## 四、按系统分项判断

## 1. Trion 资源系统

### 当前判断

- 架构状况：偏好
- 完成度：中低
- 稳定度：中等

### 理由

Trion 是当前少数“真值 owner 语义已经比较像正式系统”的部分。

它已经具备：

- 真值集中
- 对外通过 surface 暴露正式读取与命令
- tick 仅用于合法时间过程

这非常符合需求文档和宪章对资源系统的要求。

### 当前不足

- 还没有与 CombatBody 主链真正接紧
- 还没有进入完整崩解 / 收尾 / 恢复闭环
- 后续资源语义在更多表达和能力中的接法还没展开

### 结论

- Trion 当前属于“骨架质量较好，可作为正式样板继续扩展”的部分

## 2. CombatBody 系统

### 当前判断

- 架构状况：方向正确但未闭环
- 完成度：低
- 风险：高

### 理由

它是当前文档约束最明确、但代码实际闭环最弱的一块。

原因不是没写类，
而是：

- 文档要求的是一条整体相位事务主链
- 当前代码还主要停在阶段 owner、协调器、宿主位这些边界骨架上

### 当前不足

- 主链未真正接入游戏主行为
- `Collapsing` 只是相位预留，不是正式闭环
- Snapshot / Cleanup / Host 的自然位置虽然已被文档裁定，但代码仍未完全收束

### 结论

- CombatBody 是当前最需要谨慎推进、最不能靠“边写边补”解决的系统之一

## 3. Trigger 装载系统

### 当前判断

- 架构状况：较好
- 完成度：中等偏低
- 风险：中高

### 理由

它是当前实际主链里最成熟的一块，
也是最容易因为“已经能跑”而被过度扩张的一块。

当前它的正面价值在于：

- 终于比较诚实地回到了装载 owner / 局部激活 owner 的位置

### 当前不足

- `Special`、双手锁定、禁用、多形态都还没有真正进入正式规则层
- 如果下一步直接把更多表达、投影、兼容、恢复职责塞回来，会再次失真

### 结论

- Trigger 当前最该做的不是继续吞业务，而是把需求文档已经裁定的完整装载规则补齐

## 4. 表达系统

### 当前判断

- 架构状况：样板方向正确
- 完成度：低
- 风险：高

### 理由

表达系统是当前最容易被表面误判的部分。

因为它已经有：

- collector
- resolver
- projection
- manual command

这些名字看上去很像已经成体系。

但按需求文档口径，
它离正式表达系统还差得很远。

### 当前不足

- 单侧结果集合尚未正式成立
- 非攻击型表达尚未进入正式结果模型
- 双侧高层结果尚未正式建模
- 按钮层 / 主攻击层 / 非攻击读取层尚未正式分层

### 结论

- 当前表达系统只能算“最小解析样板”，不能算“已进入可扩展状态”

## 5. 远程攻击链

### 当前判断

- 架构状况：方向正确
- 完成度：低
- 风险：高

### 理由

当前代码已经证明：

- 远程表达进入原版宿主是可行的
- 语义下传到伤害链也是可行的

但需求文档要求的重点是：

- 统一阶段协议
- 标准字段
- 合并规则
- 冲突裁定
- 扩展挂点

这些都还没有正式形成代码层体系。

### 结论

- 当前远程链不能按“已经有远程能力样板”来乐观估计
- 它仍是后续架构成败的关键战场

## 6. 外部兼容 / 视觉 / 信息投影

### 当前判断

- 架构状况：尚未真正展开
- 完成度：很低
- 风险：中高

### 理由

这块现在不是代码复杂，
而是还没真正进入正式实现阶段。

但需求文档已经明确：

- 它不是后面随手补的表皮
- 它关系到真实多表达如何被外界看到、理解、兼容

### 结论

- 当前阶段对这块不能假装“以后自然会长出来”
- 后续必须单独按正式读取模型推进

## 五、当前架构的主要优点

## 1. 没有继续复刻旧 BDP 的总控式混合结构

这是当前最重要的优点。

只要这一条没丢，
后续即使返工某些局部，
整体仍有机会维持在正确轨道上。

## 2. 文档体系已经先于代码，把很多高风险边界钉死了

这意味着当前并不是：

- 没想清楚就直接写

而是：

- 很多关键问题已经先在需求文档里重新思考过了

这会显著降低后续继续沿旧误区滑回去的概率。

## 3. 最小样板链已经证明路线可行

当前至少已经证明了这些方向可行：

- Trigger owner 化
- 表达解析分层
- 原版宿主投影
- 语义下传

这说明新 BDP 不是纸面设计，
而是已经开始有可执行架构样板。

## 六、当前架构的主要风险

## 1. 最大风险不是功能不够，而是协议没落地前就开始大规模补功能

如果在以下协议还没定成代码骨架前就大量回收旧功能：

- Trigger 完整装载规则
- 多表达正式结果模型
- CombatBody 主链闭环
- 远程阶段协议

那么后续极容易发生的不是“小返工”，
而是：

- 整个 owner 边界再次污染

## 2. Trigger 再次膨胀成总系统的风险很高

因为当前最成熟的链路在 Trigger 附近，
所以后续任何：

- 按钮
- 多表达
- 兼容
- 视觉
- 恢复

都很容易继续往 Trigger 身上挂。

这正是当前最需要主动压制的风险。

## 3. 表达系统被误做成“假多表达系统”的风险很高

如果后续继续只围绕：

- 主远程一个按钮
- 主近战一个按钮
- 一个默认主表面

往前补，
那么最后很容易出现一个表面上“有表达系统”、
本质上仍是“默认武器选择器”的伪体系。

## 4. CombatBody 被继续做成空骨架或临时拼接层的风险都很高

它当前已经有两种相反风险：

- 一种是长期空骨架，不真正接回主链
- 另一种是为了赶功能，又把恢复、快照、Trigger、资源、表现重新揉进去

这两种都危险。

## 5. 远程链重新退化为“玩法模块清单”的风险很高

如果后续有人继续按：

- 追踪模块
- 引导模块
- 爆炸模块
- 齐射模块

这样的玩法名直接组织新远程架构，
而不是先回到“阶段协议 + 标准字段 + 合并语义”，
那当前需求文档对远程链做的升级会直接失效。

## 七、当前阶段最需要的后续任务类型

这一节不直接给实现计划，
只给后续任务的优先级方向。

## 1. 第一优先级：把正式协议写成代码级骨架

当前最优先的，不是多做几个旧功能案例，
而是把这些正式协议真正做成代码骨架：

- Trigger 完整装载规则骨架
- 多表达正式结果对象与分层投影骨架
- CombatBody 主链闭环骨架
- 远程链阶段结果 / 意图 / 合并骨架
