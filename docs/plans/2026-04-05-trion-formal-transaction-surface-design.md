# Trion 正式事务接口设计（第一版）

## 目的

这份文档只回答一个问题：

- 在 BDP 当前架构下，哪一层应该作为中性的资源事务边界

这份文档不回答：

- 某个具体系统何时应该发起事务
- 某个具体系统为什么要消耗资源
- 某个具体系统的资源数值如何得出

这份文档的目标是：

- 明确中性的资源事务边界
- 复用现有正式表面
- 避免新增名字误导的中间门面
- 保持架构最小化

## 一、设计前提

当前 BDP 里已经有一条完整且正式的 Trion 访问链：

1. `CompTrion` 是唯一资源账本 owner
2. `ITrionCommands` 已经定义了一次性事务和持续性事务能力
3. `TrionSurfaceAccess` 已经提供了统一正式入口

因此这里不再新增：

- `CombatBodySession` 级通用事务门面
- 新的资源事务专用接口族
- 新的资源事务宿主对象

这里采用的原则是：

- 资源事务直接走 Trion 正式表面
- 业务协调层不冒充中性资源边界
- 共享基础设施只提供资源能力，不解释业务语义

## 二、问题定义

这里要解决的问题，不是“谁来代表某种业务”，而是：

- 哪个共享接口负责承接一次性资源事务
- 哪个共享接口负责承接持续性资源事务

本设计只承认两类资源事务：

### 1. 一次性事务

特征：

- 在某个明确时刻发生一次
- 成功则立刻记账
- 失败则不记账
- 不要求后续显式清理

### 2. 持续性事务

特征：

- 有开始和结束
- 开始时进入账本注册表
- 结束时从账本注册表移除
- 生命周期由调用方拥有

## 三、核心设计结论

### 1. `ITrionCommands` 就是正式事务接口

中性的资源事务边界直接使用现有 `ITrionCommands`。

它已经提供：

- `TryConsume`
- `RegisterDrain`
- `UnregisterDrain`

这三类能力已经足以表达：

- 一次性事务
- 持续性事务注册
- 持续性事务注销

因此当前阶段不再新增新的共享事务接口。

### 2. `TrionSurfaceAccess` 就是正式接入路径

所有下游运行时系统都统一通过：

- `TrionSurfaceAccess.ResolveCommands(pawn)`

拿到正式事务接口。

这样可以保证：

- 所有调用方都走同一条正式边界
- 下游系统不需要摸 `CompTrion`
- 不需要再通过 `CombatBodySession` 间接转发

### 3. `CombatBodySession` 不承担中性资源门面职责

`CombatBodySession` 现有职责是服务战斗体会话编排。

它不是一个真正中性的资源事务边界。

如果把中性资源事务入口再挂到 `CombatBodySession` 上，会带来两个问题：

- 名字会误导资源事务语义从属于战斗体会话
- 会人为制造一层没有必要的共享中间门面

因此这里明确：

- `CombatBodySession` 可以继续处理它自己已有的资源协作逻辑
- 但不再扩展成通用资源事务入口

### 4. 表达层继续保持纯声明

表达层仍只负责：

- 声明资源参数
- 携带资源参数
- 把资源参数交给下游运行时系统使用

表达层不直接：

- 扣除 Trion
- 注册持续消耗
- 注销持续消耗

## 四、接口边界

### 1. 一次性事务

共享基础设施直接使用：

```csharp
bool TryConsume(float cost);
```

语义：

- 调用方提交一个一次性资源事务
- 账本判断能否支付
- 成功则立刻扣除
- 失败则不扣除

这里不要求共享层统一携带 `sourceKey`。

原因是：

- 一次性事务的共享语义只需要“能否支付并扣除”
- 调试、日志、审计若有需要，应通过独立诊断机制解决，而不是把它混入资源正式接口

### 2. 持续性事务注册

共享基础设施直接使用：

```csharp
void RegisterDrain(string key, float perDay);
```

语义：

- key 表示一条持续性资源事务来源实例
- `perDay` 表示当前注册值
- 同 key 重复注册时覆盖旧值

### 3. 持续性事务注销

共享基础设施直接使用：

```csharp
void UnregisterDrain(string key);
```

语义：

- 若 key 存在，则移除
- 若 key 不存在，则安全忽略

## 五、持续事务 key 规范

### 1. 为什么持续事务必须有 key

持续性事务必须能被稳定识别。

账本需要知道：

- 这是不是同一条持续事务
- 新注册是新增还是覆盖
- 结束时该注销哪一条

### 2. key 的职责

持续事务 key 只承担一件事：

- 表示“这一条持续性资源事务来源实例”

它不承担：

- 业务语义解释
- 成本计算
- 配置查询

### 3. key 的规则

一条合法 key 应满足：

1. 在同一运行期间稳定
2. 能区分不同来源实例
3. 不依赖 cost 数值区分实例
4. 不依赖定义名区分实例
5. 能被调用方在结束时再次构造出来

### 4. 明确禁止的做法

禁止把下面这些东西当成唯一 key：

- `amount`
- 定义名
- 某个广义状态名本身

因为这些都不能稳定区分不同来源实例。

## 六、职责划分

### 1. Trion 账本

职责：

- 保存资源真值
- 执行一次性事务
- 保存持续事务注册表
- 周期性结算持续事务

不负责：

- 推导业务时机
- 生成持续事务 key
- 理解调用方业务状态

### 2. Trion 正式表面

职责：

- 向外暴露中性的资源事务能力
- 隔离调用方与 `CompTrion` 的直接耦合

不负责：

- 替调用方做业务决策
- 提供 caller-specific helper

### 3. 业务协调层

职责：

- 继续处理自己已有的编排逻辑
- 在需要时调用 Trion 正式事务接口

不负责：

- 代表全局中性资源边界

### 4. 下游运行时系统

职责：

- 判断何时提交一次性事务
- 判断何时开始和结束持续性事务
- 提供稳定 key
- 提供正确 amount

## 七、设计决议

### 1. 不新增共享事务门面

当前阶段不新增新的共享资源事务接口。

理由：

- `ITrionCommands` 已经满足中性事务需求
- 新增门面只会复制一层相同能力

### 2. 不把中性资源事务挂到 `CombatBodySession`

理由：

- `CombatBodySession` 名称和职责都偏向战斗体会话编排
- 把中性事务挂上去会扩大语义误导

### 3. 一次性事务不在共享层要求 `sourceKey`

理由：

- 共享正式语义只需要消费结果
- 额外诊断需求不应反向污染最小事务接口

### 4. 持续事务继续采用同 key 覆盖

理由：

- 现有 `CompTrion` 注册表行为已经支持这种幂等模式
- 这比“重复注册报错”更适合运行时重复发布场景

### 5. 持续事务清理由调用方负责

调用方在自己的生命周期结束时负责注销。

共享资源接口不额外保存 caller-owned 生命周期状态。

理由：

- 谁拥有状态边界，谁负责结束清理
- 共享层不应反向拥有下游运行时状态

### 6. 共享层不做业务阶段校验

共享资源事务接口只做资源合法性判断，不承担业务阶段校验。

理由：

- 阶段是否合法属于调用方自己的业务边界
- 若共享层做这件事，就会重新长出 caller-specific 语义

## 八、不做什么

这一版明确不做：

- 新的 CombatBodySession 事务 facade
- 新的资源事务宿主对象
- 新的统一资源使用模型
- 统一 caller key 生成器
- 统一 caller 生命周期托管
- 任何业务逻辑接入

## 九、为什么这个方案成立

这个方案成立，不是因为它最丰富，

而是因为它同时满足：

- 中性
- 最小
- 低耦合
- 复用现有正式表面
- 不制造新的名字误导
- 不引入没有必要的中间层

它把问题收束成一句话：

- 中性的资源事务直接通过 `ITrionCommands` 和 `TrionSurfaceAccess` 暴露，下游系统在需要时自己调用。
