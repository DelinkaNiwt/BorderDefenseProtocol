# Trion资源GUI设计-第二版

> 本稿基于主工程当前真实代码重写，替代 `2026-04-04-Trion资源GUI设计-第一版.md` 中“未看到 CombatBodySession、直接由 CompTrion 挂 GUI”的错误前提。

## 1. 这次修订到底改了什么

第一版里，视觉方案大体没问题，但**架构前提错了**：

- 主工程当前其实已经有 `CombatBodySessionService`
- `CompCombatBodyHost` 已经正式接入 `CombatBodySessionService`
- `CombatBodySessionService` 已经是跨 `CombatBody / Trigger / Trion` 的真实协调层

所以第二版的核心修订只有一句话：

> **Trion GUI 的 Pawn 侧承载入口改回 gene；三系统协调继续以 CombatBodySession 为准；CompTrion 继续只做资源真值。**

---

## 2. 当前主工程真实设施

### 2.1 已经存在的正式设施

- `CompTrion`
  - Trion 真值宿主
  - 负责 `Cur / Max / Allocated / Reserved / Available / Frozen / Drain`
- `CombatBodySessionService`
  - 战斗会话协调层
  - 负责 `CombatBody / Trigger / Trion` 跨系统事务顺序
- `CombatBodySessionPolicy`
  - 会话侧的跨系统判断策略
- `CompCombatBodyHost`
  - Pawn 上的战斗体主链宿主
  - 已正式持有 `CombatBodySessionService`
- `TriggerRuntimeCoordinator`
  - Trigger 自己的运行时发布协调器
  - 不是会话编排器

### 2.2 当前缺失的设施

- 主工程当前**没有** Trion 基因系统
- 主工程当前**没有** Trion 专用 GUI 承载 gene
- 主工程当前**没有** Trion stat defs / gene defs / 对应 `DefOf`
- 主工程当前 `PawnTrionCompInjector` 仍默认给所有人形 Pawn 接入一个可工作的 `CompTrion` 宿主

---

## 3. 第二版的架构结论

## 3.1 五层职责重新钉死

### A. `CompTrion`

只负责：

- Trion 真值
- 资源结算
- 锁定 / 释放
- 聚合消耗
- 恢复冻结
- 正式读写 / 事件 surface

不负责：

- GUI 挂载入口
- 战斗体启停
- Trigger 槽位控制
- CombatBodySession 编排

### B. `CombatBodySessionService`

只负责：

- 战斗会话开始/结束事务顺序
- 激活时 Trion 正式锁定
- 退出时释放 / 紧急耗尽
- 激活态恢复冻结
- 会话状态变化后通知 Trigger runtime 重裁定

它是：

- **唯一的三系统协调层**

它不是：

- Trion 真值宿主
- GUI 承载点
- Gene 逻辑容器

### C. `CombatBodyService / CompCombatBodyHost`

只负责：

- CombatBody 相位真值
- 宿主变换
- 崩解倒计时与相位推进

### D. `TriggerRuntimeCoordinator`

只负责：

- Trigger 投影 dirty / rebuild / publish

它会参考 `CombatBodySessionPolicy` 决定“当前该不该发布战斗投影”，但它本身不是跨系统编排器。

### E. `Gene_TrionGland`（第二版新增）

只负责：

- 表达“这个 Pawn 有 Trion 腺体”这一基因事实
- 对 Pawn 提供 Trion 相关 stat 贡献
- 承载 Pawn 侧 Trion GUI 入口
- 在基因增删时通知 Trion 宿主刷新派生 stat

不再负责：

- 战斗体 runtime
- 战斗体快照
- 快照回滚
- 激活 / 解除主流程
- 紧急脱离
- 读档重建 runtime
- 任何 CombatBodySession 事务

---

## 4. 为什么 GUI 要改由 gene 来承载

## 4.1 这是当前主工程下最自然的 Pawn 侧入口

旧 BDP 里，Trion 相关 Pawn 侧显示入口就在 `Gene_TrionGland.GetGizmos()`。

第二版继续沿用这个思路，但只保留**真正属于 gene 的职责**：

- gene 是 Pawn 身上的“天赋身份入口”
- GUI 是 Pawn 侧呈现
- 所以由 gene 承载 GUI 入口是自然的

## 4.2 这能避免再去拍脑袋选错误显示通道

第一版犯错的根因，是把 GUI 直接挂到了 `CompTrion.CompGetGizmosExtra()`。

从主工程现状看，这条路至少在当前 Pawn 显示链上并不可靠。

改由 gene 挂 `GetGizmos()` 后：

- 入口明确
- 语义明确
- 更贴近旧版真实经验

## 4.3 这不等于让 gene 重新变成 God Object

第二版不是“回退到旧版 gene 管一切”，而是：

- **入口在 gene**
- **真值在 CompTrion**
- **会话在 CombatBodySession**
- **战斗体相位在 CombatBody**

也就是说：

> gene 只当“前台接待”，不再当“后台总包工头”。

---

## 5. Trion 宿主与基因的关系

## 5.1 `CompTrion` 仍然保留为通用宿主

因为 Trion 是独立资源，不应被 gene 本体吞掉。

所以：

- `CompTrion` 继续存在
- 非 Pawn 宿主以后仍可复用 `CompTrion`
- 只是 Pawn 侧的主要 GUI 承载入口改成 gene

## 5.2 人形 Pawn 的默认 Trion 宿主要改成“休眠底座”

当前 `PawnTrionCompInjector` 默认给人形 Pawn 注入一个可工作的 `CompTrion`，这和“Trion 腺体由 gene 表达”有冲突。

第二版建议改成：

- 人形 Pawn 仍可统一接入 `CompTrion`
- 但默认值改成**休眠底座**
  - 没有 gene 时：
    - Trion 容量为 0
    - 恢复速率为 0
    - GUI 不显示
  - 有 gene 时：
    - 通过 stat 贡献获得真实容量与恢复
    - GUI 才显示

这样可以同时满足：

- `CompTrion` 仍是通用资源宿主
- gene 才是真正的 Pawn 资格入口

## 5.3 Pawn 的 Trion 派生值应由 stat 驱动

第二版建议补出：

- `BDP_TrionCapacity`
- `BDP_TrionRecoveryRate`

然后让：

- `Gene_TrionGland` 通过 gene def / stat offsets 贡献这些值
- `CompTrion` 在 Pawn 宿主上读取这些 stat 来决定：
  - 最大容量
  - 每日恢复

这样：

- gene 负责“我给 Pawn 什么先天加成”
- `CompTrion` 负责“按当前宿主派生值结算资源”

边界更干净。

## 6. 第二版 GUI 承载方案

## 6.1 核心思路

第二版保留第一版已经确认的视觉方案，但改掉显示入口：

- **GUI 渲染核心**：仍然是一条 Trion 主条
- **GUI 入口承载者**：`Gene_TrionGland.GetGizmos()`
- **GUI 数据来源**：`TrionSurfaceAccess.ResolveReader(pawn)`

也就是说：

```text
Pawn 被选中
  -> Gene_TrionGland.GetGizmos()
      -> TrionSurfaceAccess.ResolveReader(pawn)
          -> Gizmo_TrionStatus(...)
```

## 6.2 核心显示内容不变

保留第一版已经敲定的主条设计：

- 一条资源条
- 左上 `可用 / 总量`
- 上中：
  - 未正式锁定时：`恢复 x/天`
  - 已正式锁定时：`消耗 x/秒`
- `恢复冻结` 指示跟在中间文字后面
- 下方不放任何说明
- 未激活：分隔线表示预测锁定
- 已激活：锁定实心块 + 分隔线
- 右上预留扩展区

## 6.3 右上扩展区仍然保留

但它的语义仍然不变：

- 不是 Trion 核心真值
- 只是 GUI 扩展区
- 以后如果要挂“战斗会话中”“紧急状态”等图标，只能通过正式 surface + provider
- 不能让 `CompTrion` 或 gene 去直摸 CombatBodySession 内部字段

---

## 7. Gene 相对于旧 BDP，明确删掉什么

旧 BDP 的 `Gene_TrionGland` 里混过这些东西：

- 战斗体 runtime
- snapshot
- snapshot 回滚
- orchestrator
- 激活 / 解除按钮主逻辑
- 紧急脱离
- 读档后 runtime 重建

第二版全部不保留。

第二版 gene 的最小职责，只剩：

- 基因身份
- stat 贡献
- GUI 入口
- 与 `CompTrion` 的最小 stat 刷新协作

这条是第二版最重要的边界修正。

---

## 8. 第二版的边界原则

### 8.1 `CompTrion` 不依赖 gene

`CompTrion` 只认：

- 宿主是不是 Pawn
- 如果是 Pawn，就读正式 stat

它不认：

- `Gene_TrionGland`
- `CombatBodySessionService`
- `CompTriggerBody`
- `CompCombatBodyHost`

### 8.2 gene 不依赖 CombatBodySession 事务

gene 只负责显示入口与 stat 身份，不负责：

- 激活战斗体
- 锁定 Trion
- 关闭 Trigger
- 紧急退出

这些继续交给 `CombatBodySessionService`。

### 8.3 CombatBodySession 不反向依赖 gene

CombatBodySession 继续通过正式 surface 协调三系统，不要求自己知道 gene GUI 细节。

### 8.4 GUI 核心不依赖 CombatBodySession

Trion 主条核心仍然只读 Trion。

如果将来右上角扩展想显示会话图标，那也是：

- 扩展 provider 去读正式 surface
- 不是主条核心去关心 CombatBodySession

---

## 9. 最终裁定

第二版正式裁定如下：

1. **Trion GUI 的 Pawn 侧承载入口改为 gene**
2. **`CompTrion` 继续做独立资源宿主**
3. **`CombatBodySessionService` 继续做三系统唯一协调层**
4. **新增 `Gene_TrionGland`，但只保留 gene 应有职责**
5. **旧 BDP 中那些不该由 gene 管的战斗体 / snapshot / runtime 职责全部删除，不再回归**

一句话总结：

> **第二版不是“回到旧版 gene 大包大揽”，而是“借旧版的 gene GUI 入口，按新 BDP 的 CombatBodySession 架构重做边界”。**
