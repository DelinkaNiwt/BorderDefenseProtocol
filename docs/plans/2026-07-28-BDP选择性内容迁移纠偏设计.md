# BDP 选择性内容迁移纠偏设计

## 一、纠偏目的

撤回事项 01 中“一次性把原测试模组全部内容机械并入主模组”的做法。

主模组只保留已经确认的事项 01、02、03；其余候选业务恢复到原测试模组。以后每确认一个事项，只迁入该事项和它真正必需的依赖，禁止提前把未确认内容塞入主模组。

## 二、已经确认的决定

1. 原测试模组 `BorderDefenseProtocol.DevHarness` 恢复为完整候选内容库。
2. 测试模组保留自己的 `About.xml` 和 `LoadFolders.xml`；是否让 RimWorld（边缘世界）读取由用户控制。
3. 主模组暂时只保留：
   - 原主模组既有内容。
   - 单模组正式包与 `BDP.Core.dll`、`BDP.Content.dll` 双程序集工程外壳。
   - Core（核心程序集）零本模组程序集依赖门禁。
   - 正式但暂不注册任何候选业务的 Content（内容程序集）启动入口。
   - 主模组正式 Trion（触粒子）腺体基因所需的新图标。
4. 未确认内容采用“移动”而不是“复制”；迁入主模组后从候选测试模组移除，避免重复 DefName（定义名称）、重复补丁和双份真值。
5. 不使用旧临时基因图标。主模组使用新生成的简单正立方体平面几何图标；原版基因物品继续使用游戏原版物品贴图。
6. 不处理旧存档、旧 DefName 或旧命名空间兼容。

## 三、采用方式

采用“按事项 01 提交清单精确反向搬回”的方式，不整体回滚 Git（版本控制）提交。

理由：

- 整体回滚 `9ec835ca` 会同时冲击已经完成的事项 02、03。
- 精确按迁移清单恢复可以保留现 Core 的正式改动、依赖门禁和双程序集工程。
- 文件来源明确，可检查每个候选文件是否已回到测试模组。

## 四、主模组目标状态

```text
BorderDefenseProtocol
│
├─ 原主模组 Def、资源与 Core 源码
├─ 1.6/Assemblies
│  ├─ BDP.Core.dll
│  └─ BDP.Content.dll
├─ 1.6/Textures/UI/Icons/Genes/Gene_TrionGland.png
└─ Source
   ├─ BDP
   │  └─ Core 正式骨架
   └─ BDP.Content
      ├─ BDP.Content.csproj
      └─ ContentBootstrap.cs
```

主模组不再保留：

- `1.6/ContentRoot`。
- `1.6/ContentVersion`。
- `docs/DevHarness`。
- 候选测试模组的具体业务源码、Def、贴图、声音、测试和文档。
- 未确认的触发体面板、诊断按钮、护盾补丁、光束拖尾和上层应用。

## 五、测试模组目标状态

`BorderDefenseProtocol.DevHarness` 恢复事项 01 实施前的完整候选内容结构，包括：

- `About.xml` 与 `LoadFolders.xml`。
- 原 `BDP.DevHarness` 工程和测试工程。
- 原 Def、贴图、声音、业务源码、测试和文档。
- 测试模组自己的程序集发布路径。

恢复以 `9ec835ca^` 的测试模组树为基准，不从旧版模组取内容。

## 六、事项 03 的纠偏

正式 `BDP.Content.ContentBootstrap` 继续存在，但暂时只保留：

```csharp
new Harmony("niwt.bdp.content").PatchAll();
```

清理后 Content 程序集中没有 Harmony（补丁框架）补丁，因此这条调用不会改变游戏行为，只保留以后接入已确认补丁的正式入口。

下列接线暂时移除：

- `DevHarnessTriggerGizmoProvider`：涉及事项 06。
- `TrionTriggerLoadoutPanelProvider`：涉及事项 05。
- 两个护盾补丁：涉及事项 14，随具体业务源码移回测试模组。

## 七、Trion 腺体基因图标

主模组的正式基因定义引用：

`UI/Icons/Genes/Gene_TrionGland`

旧图标原本只存在于测试模组，造成主模组正式基因对测试资源的隐性依赖。纠偏时：

- 测试模组恢复旧图标。
- 主模组新增独立生成的 64×64 透明 PNG（便携式网络图形）图标。
- 新图标为单个正立方体、冷色三面、简单平面几何风格。
- 不新增基因物品贴图，继续使用 RimWorld 原版基因物品表现。

## 八、测试与报错控制

自动验证至少包括：

1. 候选测试模组恢复清单完整。
2. 主模组迁入候选文件清单清零，仅允许明确白名单文件。
3. 主模组 `LoadFolders.xml` 不再加载 `ContentRoot` 或 `ContentVersion`。
4. `BDP.Content.dll` 只编译最小正式启动入口。
5. Core 依赖门禁通过。
6. 主模组和测试模组分别完成 Release（发布）构建。
7. 主模组全部活动 XML（可扩展标记语言）可解析。
8. 主模组正式 Def 引用的类、贴图和声音不存在已知缺失。
9. 主模组发布目录只含 `BDP.Core.dll` 与 `BDP.Content.dll`。
10. 重新建立与“只完成事项 01 至 03”一致的自动测试基线。

工程验证只能证明没有已知构建、引用和静态加载错误。由于用户自行控制实际游戏目录，最终 RimWorld 启动和地图实测由用户执行；若出现红字，再以游戏日志追查根因。

## 九、后续单项迁移规则

以后每个事项都按以下顺序处理：

1. 从测试候选库介绍当前内容。
2. 用户确认范围和正式处理方式。
3. 写该事项的小设计与实施计划。
4. 只移动该事项及必要依赖到主模组。
5. 从测试模组删除已迁入的同名候选文件。
6. 更新 Content 启动接线或定义加载入口。
7. 构建、测试并独立提交。
8. 更新总计划检查点，再介绍下一项。
