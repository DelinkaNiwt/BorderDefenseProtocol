# 主模组现阶段架构自省与对象裁定（第一版）

## 目的

这份文档不是继续补某一个局部功能，
也不是重复上一轮“高风险修复计划”。

它只回答当前最直接的问题：

- 现阶段主模组里，哪些对象应该继续保留为正式骨架
- 哪些对象虽然可以保留，但必须重定职责
- 哪些对象应该降级成局部模块
- 哪些对象应该删除、压平、内化，避免继续污染架构

这份裁定的核心视角不是“现在代码能不能跑”，
而是：

- 是否在重蹈旧 BDP 的上帝膨胀
- 是否正在制造不必要耦合
- 是否用过度抽象占掉未来真正需要的扩展位置
- 是否让后续非核心能力失去自然接入口

## 裁定前提

- 旧 BDP 代码事实仍是行为真标准
- 当前新 BDP 只完成第一阶段最小主链，不能把已建骨架误判成主体完成
- 三类真值 owner 不变：
  - `CompTrion`：资源真值
  - `CombatBodyState`：战斗体相位真值
  - `CompTriggerBody`：装载与局部激活真值
- 事件只通知，不持有真值
- patch 只接线，不承载复杂业务
- 允许保留“薄、硬、诚实”的源码级长期记忆锚点
- 不允许保留会让后续开发者误以为“功能已经正式接通”的空 runtime、空 coordinator、空 bridge

## 一、总判断

当前主模组并不是“整体都错了”，
但它正同时面临两类相反的风险：

- 一类是 `CompTriggerBody` 这类真实主链对象，容易继续吸功能、吸规则、吸接线，重新长成旧 BDP 式上帝模块
- 另一类是 `CombatBody / Projections / Semantics` 周边，容易为了未来而先铺出过多接口和桥位，结果主链没接通、认知层数先变厚

因此现阶段最正确的动作不是继续堆新功能，
也不是一刀把所有预留骨架全砍光，
而是做一次对象裁定：

- 核心必须更像核心
- 模块必须更像模块
- 接线必须更像接线
- 空骨架必须要么接回主链，要么退出正式层

## 二、对象裁定标准

## 1. 保留为核心

满足以下条件的对象，可以继续留在正式主骨架：

- 它本身持有正式真值，或者是不可替代的正式主链门面
- 它的位置贴近 RimWorld 自然宿主
- 它当前已经真实参与主链，而不是只停留在概念上

## 2. 保留但重命名或重定职责

满足以下情况的对象，不必删除，但必须改口径：

- 方向是对的，但名字或说明容易让人误会它是更大的东西
- 它的存在有必要，但当前职责描述过宽
- 它正处于“从错误位置往正确位置回收”的过渡期

## 3. 降级为局部模块

满足以下情况的对象，不应继续占“系统级对象”位置：

- 它不持真值
- 它只做局部规则、局部转换、局部接线、局部桥接
- 它有价值，但价值来自被 owner 或主链调用，而不是自己成为平行中心

## 4. 删除 / 压平 / 内化

满足以下情况的对象，应优先退出正式公开层：

- 只有单实现、没有真实替换点、没有近期独立扩展价值
- 当前没有正式接线，却已经占了一个系统级名字
- 它的存在让主链更难理解，却没有换来真实边界收益

## 三、按对象族裁定

## A. 三核心真值族

### A1. `CompTrion`

裁定：

- `保留为核心`

理由：

- 它是当前三核心里最干净的一个
- 资源总量、可用量、已占用量、预占用量、持续消耗、自然恢复都收束在一个 owner 内
- 它没有越位去替战斗体或 Trigger 持相位、槽位、表达真值

当前要注意的问题：

- 它未来很容易被“方便”地要求直接驱动战斗体崩解或 Trigger 关闭
- 这类要求必须继续拒绝，最多只允许返回结果或广播事件

结论：

- 保持核心地位
- 不继续抽象出新的资源总控层

### A2. `CombatBodyState`

裁定：

- `保留为核心`

理由：

- 当前相位、冷却、崩解时间与战斗体锁定量都已明确留在这个 owner
- 它已经遵守“暂停下立即成立的状态要在读取时立刻收束”的原则
- 它比 `CombatBodyCoordinator` 更像真实 owner，而不是过程壳

当前要注意的问题：

- 它还没有被完整接回正式战斗体闭环
- 若长期只保留定义，不接事务链，会让外围对象反过来代持阶段事实

结论：

- 保留核心地位
- 后续要围绕它接通主链，不围绕它再造新 state 包

### A3. `CompTriggerBody`

裁定：

- `保留为核心`
- `但继续强制瘦身`

理由：

- 它确实是 Trigger 装载、局部激活、局部禁用、容器持有的正式 owner
- 两轮瘦身后，它已经比之前明显更像 owner 门面，而不是全功能总控
- 但它仍然过重，仍然是当前最容易复发旧 BDP 痛点的对象

当前保留在它身上是合理的内容：

- 槽位真值
- 容器真值
- 存读档
- 正式读取口
- 正式请求口
- 事件广播口
- `IThingHolder` 宿主职责

当前仍需警惕的内容：

- 它还保留着较多一致性修复、绑定包装、运行时桥接汇聚
- 它仍是 `TriggerProjectionFacade`、`TriggerCommandFacade` 的事实输入中心
- 它一旦继续吸战斗体、视觉、模块化芯片解释、外部扩展注册细节，就会重新上帝化

结论：

- 继续保留为核心
- 但后续所有新增 Trigger 能力都必须先证明“为什么不能放到局部模块或正式外层门面”

## B. CombatBody / Cleanup / Host 族

### B1. `CombatBodyCoordinator`

裁定：

- `保留但重定职责`

理由：

- 战斗体必须有一条正式的进入 / 离开 / 崩解编排主链
- 这个对象的方向是对的，它应该成为那条单主链
- 但当前它还只是“最小流程协调者”，没有真正接住恢复、收尾、宿主变化、资源后续和整体闭环

当前问题：

- 它与 `CombatBodyCleanupCoordinator` 形成了“双轨都像主协调者”的危险状态
- `Trigger / Snapshot / Hediff / Host` 还没有通过它被编排进一条正式事务链

正式裁定：

- 保留
- 后续应强化为唯一主协调者
- 但不要把它做成第四个真值中心

### B2. `CombatBodyCleanupCoordinator`

裁定：

- `降级为局部模块`

理由：

- 收尾是必要的
- 但收尾不是另一条平行主链
- 当前这个对象最危险的地方，不是它做错了什么，而是它的命名和位置太像“第二个主协调者”

它更自然的位置应该是：

- 战斗体离开事务里的收尾协作者
- 由 `CombatBodyCoordinator` 显式调用
- 专注于释放、关闭、恢复、清残留

不应继续让它承担的含义：

- 战斗体退出总控
- 崩解总控
- 正式相位裁定者

正式裁定：

- 降级
- 允许保留实现
- 接口与命名都应考虑进一步收窄，避免继续占系统级位置

### B3. `ICollapseCleanupCoordinator`

裁定：

- `删除 / 内化优先`

理由：

- 当前只有单实现
- 没有真实多实现替换价值
- 也没有已经成立的独立扩展生态

如果后续确实出现：

- 多种正式收尾事务策略
- 或多个合法宿主需要替换清理实现

再恢复接口也不迟。

现阶段继续公开它，只会让 `Cleanup` 看起来像与主协调者平起平坐的体系。

### B4. `PawnCombatBodyHost`

裁定：

- `保留但必须尽快接回主链`

理由：

- 战斗体必须有贴 RimWorld 宿主的正式挂接点
- 这个对象的方向也对，它把“战斗体流程”和“Pawn 侧变换”分开了
- 但它当前还是空桥位，空得过头

为什么不能简单删除：

- 因为用户已经明确要求未来一些非核心需求也要有源码级记忆锚点
- 宿主桥正是战斗体接回 `Pawn / Hediff / Snapshot / 视觉恢复` 的必要自然位置

为什么不能继续空着：

- 空桥位长期存在，会诱导后续代码绕开它直接互连
- 最后会把 `Trigger / Cleanup / 战斗体恢复` 重新织成多点耦合网

正式裁定：

- 保留
- 但必须在近阶段进入最小正式主链
- 若短期仍做不到，就应把注释进一步收束为“仅占宿主挂接位，不代表宿主行为已成立”

## C. Expressions / Runtime / Projections 族

### C1. `BdpProjectionRuntime`

裁定：

- `保留但重定职责`

理由：

- 当前从 Trigger 正式读取口出发，收集表达、解析结果、再投影到 RimWorld 入口，需要一个汇总运行时
- 这个对象作为“表达读取主链”是成立的

当前问题：

- 它内部直接 `new collector / resolver / registry / projection`
- 说明当前真正的主链还比较短，而周边接口层偏多
- 它容易变成“虽然不持真值，但什么都从这里路过”的厚 runtime

正式裁定：

- 保留为表达读取主链的薄运行时
- 但不要继续把视觉、Ability、Hediff、FireMode、模块拼装等都往这里堆

### C2. `TriggerProjectionFacade`

裁定：

- `保留但收窄正式边界`

理由：

- 外层门面是对的
- Trigger owner 不应直接兼任投影入口

当前问题：

- 当前门面仍直接吃 `CompTriggerBody`
- 这说明它还没有完全长成正式边界，而是 owner 的薄外壳

正式裁定：

- 保留
- 后续优先把入参收窄到最小正式读取面和投影宿主面
- 不再把具体 owner 类写死成长期正式边界

### C3. `TriggerResolvedExpressionCache`

裁定：

- `降级为局部模块`

理由：

- 它只是在 Trigger 侧缓存表达快照
- 价值来自局部性能与重复读取收束
- 不应该被理解成“第四层表达真值”

正式裁定：

- 继续保留
- 只作为 owner 持有的局部缓存协作者
- 不给它扩成新的 runtime 中心

### C4. `TriggerExpressionCollector / BasicExpressionResolver / ResolvedExpressions / ExpressionSource`

裁定：

- `保留为表达主链最小骨架`

理由：

- 这几层虽然抽象味道偏重，但它们承接的是芯片表达来源 -> 解析结果 的正式协议骨架
- 用户已经明确要求芯片、表达、远程链、视觉读取等未来都要有统一标准和可扩展性
- 这类骨架属于“薄、硬、诚实”的长期锚点，而不是空桥位

需要控制的边界：

- 不把各种未来具体业务结果先塞进当前最小结果结构
- 不为单一武器场景继续长出更多只服务当前阶段的临时接口

正式裁定：

- 保留
- 但尽量减少“为了多态而多态”的附属接口壳

### C5. `IAutoMeleeProjection / IAutoRangedProjection / IManualCommandProjection / ISurfaceProjection`

裁定：

- `删除 / 内化优先`

理由：

- 当前都是单实现
- 主要被 `BdpProjectionRuntime` 直接 new
- 没有真实替换点，也没有外部扩展作者要直接实现它们的现实场景

保留实现类本身可以接受，
因为：

- 自动远程
- 自动近战
- 手动命令
- 表层读取

这四种投影切面本身是真需求。

但继续把它们公开成一组接口，
现阶段带来的更多是认知成本，而不是边界收益。

正式裁定：

- 优先删接口
- 实现类可保留或进一步并入 runtime
- 视下一轮主链瘦身结果决定压平程度

### C6. `IVisualProjection`

裁定：

- `删除优先`

理由：

- 当前没有实现
- 没有正式接线
- 只是在源码里声明了“未来视觉会有一层”

这类需求不应被遗忘，
但现阶段应该把“视觉读取模型”的长期约束留在文档和更贴近结果对象的正式结果层，
而不是保留一个没有任何真实着陆点的接口。

正式裁定：

- 退出主模组正式代码层
- 待视觉主链真正接入时，再按当时的正式读取模型重建

## D. Semantics / Damage Bridge 族

### D1. `BdpDamageSemanticBridge`

裁定：

- `保留但明确为局部桥接核心，不升级为总语义系统`

理由：

- 当前伤害来源名桥接、爆炸跨宿主桥接、Verb/Projectile 语义传递都需要一个明确工具
- 它确实解决了 RimWorld 原版宿主字段不够用的问题
- 这属于“patch 只接线、业务仍回到正式对象”的正确配套

当前要防止的问题：

- 不要因为它很好用，就把更多业务解释、伤害决策、兼容裁定都塞进来
- 它应该是桥，不是语义总线

正式裁定：

- 保留
- 但继续把它限制在“语义搬运与写入现有宿主字段”范围

### D2. `SemanticRuntimeScope`

裁定：

- `保留为局部运行时工具`

理由：

- 当前近战和投射物伤害链确实需要一个极小作用域，把当次攻击语义压到调用链里
- 它没有持真值，也没有装系统级责任

正式裁定：

- 保留
- 但不围绕它继续长出“全局语义上下文平台”

### D3. `IBdpSemanticCarrier / SemanticContext / SemanticDamageRecord / ISemanticContext`

裁定：

- `保留为正式协议骨架`

理由：

- 伤害来源、攻击语义、未来视觉/信息兼容读取，都需要一层正式语义结果对象
- 这类协议骨架比“空视觉接口”更诚实，因为它们已经真实接入当前攻击链

正式裁定：

- 保留
- 但协议字段增长必须继续克制，只加已被正式读取链消费的内容

### D4. `ISemanticDamageSource`

裁定：

- `删除优先`

理由：

- 当前没有看见它形成真实主链价值
- 它更像上一轮为未来预留的抽象位
- 它会诱导后续把“伤害来源”再做一层假总线

## E. Trigger 外部扩展口族

### E1. `TriggerExternalGizmoRegistry / ITriggerExternalGizmoProvider / TriggerExternalGizmoContext`

裁定：

- `保留但规范化为正式扩展口`

理由：

- 用户已明确裁定，这不是测试污染，而是未来留给其它模组作者的正式扩展口
- 这类扩展口必须存在，而且要设计得正式

当前问题：

- 当前消费方主要还是 DevHarness
- 上下文虽然已经比之前干净，但仍紧贴 Trigger 当前实现阶段

正式裁定：

- 保留
- 继续限制其能力面：
  - 只读什么
  - 能请求什么
  - 能诊断什么
- 不让它演化成“拿到 context 就能顺便干任何事”的万能插件口

### E2. `TriggerCommandFacade`

裁定：

- `降级为局部接线门面`

理由：

- 它的存在是正确的，说明按钮拼装责任已从 owner 外移
- 但它本质只是接线门面，不应再升格为系统层对象

正式裁定：

- 保留
- 明确它只负责命令汇总和分发
- 不在这里扩写业务判定

## F. BodyConstraints / Patches 族

### F1. `PawnBodyConstraintSignalHub / TriggerBodyDisableEvaluator / TriggerBodyDisableSignalSnapshot`

裁定：

- `保留为局部模块骨架`

理由：

- 这是一次明显正确的去耦调整
- patch 只发布中性上游信号
- Trigger 再把身体事实解释为自身局部禁用
- 没有把原版身体变化直接绑死到 Trigger owner 私有实现

正式裁定：

- 保留
- 后续继续坚持“中性信号 -> 局部 owner 自裁定”的模式

### F2. 身体约束 patch

裁定：

- `保留`

理由：

- 当前原版没有自然事件口可直接覆盖“暂停下立即同步”的需要
- patch 只做信号发布，不做禁用业务判定
- 这符合“patch 只接线”的允许边界

正式裁定：

- 保留
- 严格限制前置条件和职责，不向 patch 塞更多业务

### F3. 自动攻击与伤害来源相关 patch

裁定：

- `保留但持续复查`

理由：

- 这些 patch 当前承担的是原版宿主入口桥接
- 它们的存在是因为原版没有自然通道能完整承接当前表达链

需要持续复查的点：

- 它们是否仍只是“把正式结果送进原版入口”
- 是否开始偷做业务选择、业务补偿或状态真值回写

若出现后者，
就必须回切。

## 四、删除 / 压平优先清单

现阶段优先从正式代码层退出或内化的对象：

- `ICollapseCleanupCoordinator`
- `IAutoMeleeProjection`
- `IAutoRangedProjection`
- `IManualCommandProjection`
- `ISurfaceProjection`
- `IVisualProjection`
- `ISemanticDamageSource`

说明：

- 这不等于相关能力本身不需要
- 只是否定“现在就把它们放成系统级公开抽象”的做法

## 五、现阶段应保留的源码级长期记忆锚点

这部分是本轮不能误删的内容，
因为它们直接关系到后续非核心能力还有没有自然接入口：

- `CompTrion / CombatBodyState / CompTriggerBody` 三核心 owner 骨架
- `CombatBodyCoordinator` 作为未来战斗体单主链位置
- `PawnCombatBodyHost` 作为宿主挂接位
- `ExpressionSource / ResolvedExpressions / TriggerExpressionCollector / BasicExpressionResolver`
- `TriggerExternalGizmo*` 正式扩展口
- `BdpDamageSemanticBridge / SemanticContext` 语义桥接骨架
- `BodyConstraints` 这一组“中性信号 -> owner 自裁定”的解耦模式

这些对象之所以要留，
不是因为它们已经完整，
而是因为它们已经明确回答了：

- 未来能力应该接到哪里
- 不应该接到哪里

## 六、整顿后建议骨架

```text
Pawn
├─ CompTrion                     [资源真值 owner]
├─ CombatBodyState               [战斗体相位真值 owner]
├─ CombatBodyCoordinator         [战斗体单主链协调]
│  ├─ PawnCombatBodyHost         [宿主挂接点]
│  └─ Cleanup/Restore modules    [离开侧局部事务协作者]
└─ Equipped Trigger
   └─ CompTriggerBody            [装载/局部激活/局部禁用 owner]
      ├─ TriggerActivationRules  [局部规则]
```

## 七、当前正式进入点

基于这份裁定，
当前最合理的继续顺序是：

1. 先按裁定继续整顿主模组结构
2. 优先处理 `CombatBody / Cleanup / Host` 这一组“位置已占、主链未接”的问题
3. 再处理 `Expressions / Projections` 这组“能力真实存在、接口层偏厚”的问题
4. 最后再补那批“源码级长期记忆锚点”，把必须为未来保留的位置做得更薄、更硬、更诚实

## 八、一句话结论

当前主模组最需要的不是继续新增功能，而是把“核心、模块、桥接、扩展口、空骨架”这五类对象重新排位：三核心继续保留，战斗体主链对象回到单主链，Cleanup 与命令拼装等退回局部模块，投影与语义链删掉无效空抽象，只保留真正已经接入主链或必须作为长期正式锚点存在的薄骨架。
