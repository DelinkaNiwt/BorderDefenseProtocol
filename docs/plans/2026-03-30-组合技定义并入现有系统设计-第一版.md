# 组合技定义并入现有系统设计-第一版

## 1. 设计目标

- 把组合技正式并入 BDP 当前主模组系统，而不是继续停留在旧 BDP 的专用分支写法。
- 组合技不作为芯片 Def 本体存在，但在结构上尽量像“无实体第三芯片定义”。
- 表达系统根据当前输入的两个芯片去匹配组合技；有就载入，没有就没有。
- 第一阶段只正式打通 `Verb` 型组合技，但整体定义结构保持中性，不把未来非 `Verb` 组合技写死堵死。
- 攻击系统尽量复用现有单结果 `Verb` 渠道，不新增组合技专用攻击链。
- 本轮先补“组合技定义 + 表达结果 + 攻击系统接通”缺口，不先引入协议模块配置。

## 2. 当前代码事实

### 2.1 表达系统已经有的预留

- `CompositeExpressionKind` 已经有 `Combo`。
- `CompositeExpressionSet` 已经有 `ComboResults`。
- `ExpressionSnapshotBuilder` 在装配结果总表时，会把 `ComboResults` 追加进 `ExpressionSnapshot.Results`。

### 2.2 当前真正缺的地方

- `ResolveComposite(...)` 里目前只真正构建了 `DualWeaponResults`，`ComboResults` 还是空表。
- 默认主表达选择器不会把 `Combo` 当默认主攻击。
- 攻击系统当前只对 `DualWeapon` 做专门分支，不存在组合技专用执行分支。

### 2.3 当前必须坚持的边界

- `Combo` 不作为默认主攻击。
- `Combo` 不是新的攻击类型。
- `Combo` 在表达层是复合结果，在攻击层应尽量表现为普通单条结果。
- 远程与近战都属于 `Verb`，当前第一阶段一起纳入，不做“只服务远程”的偏置设计。

## 3. 核心设计结论

### 3.1 组合技的本体定位

组合技在主模组中的正确定位是：

- 它不是实体芯片。
- 它不是专用 Verb 类体系。
- 它不是第二套攻击系统。
- 它是一个由两个芯片组合匹配出来的、无实体的第三芯片式定义。

一句话：

`ComboDef = 去掉实体装载语义后的芯片定义同构体`

### 3.2 表达系统中的输入口

组合技在表达系统中的输入口允许为空。

这代表：

- 表达输入阶段不需要用户或上游显式“选择组合技”。
- 表达系统只读取当前两侧芯片输入。
- 若命中某条 `ComboDef`，就生成组合技结果。
- 若未命中，则系统不生成任何组合技结果。

正确的理解是：

`组合技不是被主动输入的东西，而是被匹配出来的东西。`

## 4. 并入现有系统后的整体流向

### 4.1 运行时总流向

```text
Main/Sub 当前芯片
-> 表达系统读取单侧结果
-> 复合匹配阶段读取 chipA/chipB
-> 若命中 ComboDef，则生成 ComboResult
-> ComboResult 进入 ExpressionSnapshot.Results
-> 后续执行器若明确命中 ComboResult，则按普通单条 Verb 结果继续走
-> WeaponMode = Ranged 时进入远程攻击链
-> WeaponMode = Melee 时进入近战攻击链
```

### 4.2 为什么不需要新开组合技攻击链

因为在业务定义上，`Verb` 型组合技只是：

- 来源不是单个芯片 Def
- 结果是一个新的普通 `Verb`

它不是：

- 两条结果并行推进的 `DualWeapon`
- 两条攻击链同时消费的复合执行器
- 需要独立宿主生命周期的新武器类型

所以当前正确路线是：

- 在表达层特殊
- 在攻击层普通

## 5. ComboDef 最小结构

### 5.1 外层块

组合技定义建议最小拥有以下块：

- `defName`
- `label`
- `description`
- `chipA`
- `chipB`
- `Trion`
- `Expression`

第一阶段不需要：

- `Loadout`
- `Extensions`

原因：

- `Loadout` 是实体芯片装载语义，组合技没有实体，不需要。
- `Extensions` 当前不是打通主链的必要项。

### 5.2 与芯片 Def 的关系

组合技定义不应长成“一个小型 Combo 专用配置”，而应尽量复用芯片定义的正式块结构：

- `Expression` 尽量复用芯片表达配置结构
- `Trion` 尽量复用芯片 Trion 结构
- 外层仅最小增加组合来源声明

同时必须明确：

- `chipA/chipB` 不只是匹配键，也是正式依赖声明
- 组合技天然依赖这两个来源芯片的定义结构
- 来源芯片定义一旦变更，组合技必须重新校验自己是否仍然成立

正确原则不是：

- 芯片改了，系统自动替组合技猜出新写法

而是：

- 芯片改了，系统必须能正式发现哪些 `ComboDef` 需要跟着调整

### 5.3 最小示例结构

```xml
<Defs>
  <BDP.ComboDef>
    <defName>BDP_Combo_Tomahawk</defName>
    <label>战斧</label>
    <description>由两枚芯片组合形成的无实体第三芯片式结果。</description>

    <chipA>BDP_Chip_Viper</chipA>
    <chipB>BDP_Chip_Meteora</chipB>

    <Trion>
      <activationCostResolve>Average</activationCostResolve>
      <capacityCostResolve>Max</capacityCostResolve>
    </Trion>

    <Expression>
      <Entries>
        <li>
          <Kind>PrimaryVerb</Kind>
          <WeaponMode>Ranged</WeaponMode>

          <VerbProps>
            <rangeResolve>Average</rangeResolve>
            <warmupTimeResolve>Average</warmupTimeResolve>
            <burstShotCountResolve>Average</burstShotCountResolve>
            <ticksBetweenBurstShotsResolve>Average</ticksBetweenBurstShotsResolve>
            <defaultProjectile>BDP_Bullet_GuidedExplosive</defaultProjectile>
          </VerbProps>

          <Execution>
            <RangedRhythm>Simultaneous</RangedRhythm>
          </Execution>
        </li>
      </Entries>
    </Expression>
  </BDP.ComboDef>
</Defs>
```

## 6. Trion 设计

### 6.1 为什么必须有 Trion

当前芯片定义正式结构中，`Trion` 是独立声明块。

组合技既然要像“第三芯片”一样进入系统，就不能把它的 Trion 语义丢给后续模块现猜。

所以组合技也必须有自己的 `Trion` 声明块。

### 6.2 最小字段

建议与芯片当前 Trion 结构同构，至少保留：

- `CapacityCost`
- `ActivationCost`

### 6.3 自动计算支持

对于和芯片 Def 同义的数值字段，组合技允许：

1. 自己显式填写固定值
2. 不填固定值，而声明自动计算策略

优先级：

1. 先取显式值
2. 没显式值再取自动计算策略
3. 两边都没有则视为缺失

## 7. Expression 设计

### 7.1 为什么必须有 Expression

组合技最终进入系统的真正方式，不应是“直接生成一段攻击逻辑”，而是：

- 先作为正式表达结果成立
- 再进入现有攻击执行链

因此 `Expression` 是组合技的核心块。

### 7.2 与芯片表达条目的同构原则

组合技表达条目应尽量复用现有芯片表达条目结构，至少继续允许这些字段存在：

- `Kind`
- `RelationKind`
- `ParentEntryId`
- `WeaponMode`
- `VerbProps`
- `Tool`
- `Maneuver`
- `Execution`
- `ExecutionStyle`
- `AbilityDefName`
- `HediffDefName`
- `ApplyModeKey`
- `PassiveKey`
- `ExposedData`

第一阶段虽然只正式消费 `Verb` 型条目，但设计上不要把结构写死成“只有 Verb”。

### 7.3 当前第一阶段的真实消费范围

第一阶段真正打通的字段，主要会是：

- `Kind`
- `WeaponMode`
- `VerbProps`
- `Tool`
- `Maneuver`
- `Execution`
- `ExecutionStyle`

其它字段当前可以保留结构，不一定立刻接通消费。

## 8. 自动计算策略设计

### 8.1 最小正式策略枚举

建议最小只支持：

- `FollowChipA`
- `FollowChipB`
- `Sum`
- `Average`
- `Max`
- `Min`

说明：

- 你提到的“取最值”在契约层最好明确拆成 `Max / Min`。
- 这样代码实现和作者理解都更稳定。

### 8.2 适合支持自动计算的字段

推荐第一阶段支持自动计算的字段：

- `Trion.ActivationCost`
- `Trion.CapacityCost`
- `VerbProps.range`
- `VerbProps.warmupTime`
- `VerbProps.burstShotCount`
- `VerbProps.ticksBetweenBurstShots`
- `VerbProps.minRange`
- `VerbProps.forcedMissRadius`
- `Execution.HitCount`
- `Execution.HitIntervalTicks`

### 8.3 推荐缺省默认策略

若作者未显式填写 resolve，建议当前候选默认值如下，后续可逐条再拍板：

- `Trion.ActivationCost = Average`
- `Trion.CapacityCost = Max`
- `VerbProps.range = Average`
- `VerbProps.warmupTime = Average`
- `VerbProps.burstShotCount = Average`
- `VerbProps.ticksBetweenBurstShots = Average`
- `VerbProps.minRange = Min`
- `VerbProps.forcedMissRadius = Average`
- `Execution.HitCount = Average`
- `Execution.HitIntervalTicks = Average`

### 8.4 不建议默认自动计算的字段

以下字段建议要求作者显式写，或只允许 `FollowChipA/B`，不做数值式自动计算：

- `WeaponMode`
- `Kind`
- `VerbProps.defaultProjectile`
- `Tool`
- `Maneuver`
- `Execution.RangedRhythm`
- `Execution.MeleeRhythm`
- `AbilityDefName`
- `HediffDefName`
- `PassiveKey`
- `ApplyModeKey`

原因：

- 这些字段要么是对象引用
- 要么是离散模式
- 要么直接决定攻击链分流

不适合做 `Average/Sum/Max/Min`

## 9. ComboResult 设计

### 9.1 目标

`ComboResult` 应该尽量复用现有 `FormalExpressionResult`，而不是另造一套组合技结果类型。

### 9.2 必要字段

在现有 `FormalExpressionResult` 基础上，组合技结果至少应具备：

- `Id`
- `ResultKind = Verb`
- `WeaponMode`
- `OriginKind = Composite`
- `CompositeKind = Combo`
- `DisplayLabel`
- `VerbAttackRole`
- `Tags`
- `IsAvailable`
- `CanProject`
- `SemanticContext`
- `ModeKey`
- `ExecutionStyle`
- `VerbProps`

新增最小必要挂点：

- `ComboDefName`

### 9.3 为什么必须新增 ComboDefName

否则下游只能知道：

- 这是一条 `Combo` 结果

但不知道：

- 它具体来自哪一个 `ComboDef`

而后续无论是攻击链消费还是配置回溯，都需要稳定知道具体来源。

## 10. 表达系统并入点

### 10.1 匹配规则

表达系统在复合阶段读取当前两侧芯片：

- 若两侧芯片为空，不做组合技匹配
- 若只存在一侧芯片，不做组合技匹配
- 若两侧芯片同时存在，则按 `chipA/chipB` 不分顺序匹配 `ComboDef`

由于当前业务规则已经确定：

- 一对芯片最多只会命中一个组合技

因此第一阶段不需要做多结果竞争裁决系统。

### 10.2 结果生成规则

命中 `ComboDef` 后：

- 读取其 `Expression.Entries`
- 按与芯片表达同样的翻译流程生成正式结果
- 把结果加入 `CompositeExpressionSet.ComboResults`

### 10.3 输入口允许为空

组合技输入口为空时，系统行为应为：

- 不报错
- 不生成组合技结果
- 继续只输出普通单侧结果或双持结果

这必须被视为正常情况，而不是异常情况。

### 10.4 来源芯片变更后的依赖校验

由于 `ComboDef` 显式依赖 `chipA/chipB`，所以来源芯片定义发生变化后，组合技必须重新做一致性检查。

最小正式规则应为：

- 载入 `ComboDef` 时，读取器/校验器必须同时读取它依赖的两个芯片定义
- 若 `chipA/chipB` 对应芯片不存在，则该 `ComboDef` 直接视为无效
- 若 `ComboDef` 声明要跟随或计算某字段，但来源芯片已不再提供可用来源，则该 `ComboDef` 直接视为无效
- 无效时要在读取/校验阶段明确报出原因，而不是拖到攻击执行阶段才暴露

这层要解决的问题是：

- 芯片改版后，组合技不会“悄悄错着跑”
- 开发者能明确知道是哪个 `ComboDef`、依赖哪枚芯片、哪一个字段失效了

不建议做的事：

- 不要让芯片 Def 反向维护“有哪些组合技依赖我”
- 不要做复杂观察者、事件总线、自动联动改写
- 不要在运行时临场猜测怎么替组合技补配置

最小可落地流向应为：

```text
ChipDef 变化
-> ComboDef 重新读取
-> ComboValidator 读取 chipA/chipB 并重做一致性校验
-> 合法：允许进入表达系统
-> 不合法：在载入期或测试期明确报错
```

## 11. 攻击系统并入点

### 11.1 当前目标

攻击系统不应为组合技新开攻击渠道。

当前第一阶段的目标是：

- 让 `ComboResult` 作为普通单结果被消费

### 11.2 正确消费原则

- `DualWeapon` 仍保持现有特殊处理
- `Combo` 不进入默认主攻击选择
- 当上游明确命中某条 `ComboResult` 时，攻击系统应把它当成普通 `Verb` 结果继续执行

### 11.3 远程与近战分流

`ComboResult` 进入攻击系统后，按其 `WeaponMode` 自然分流：

- `Ranged` -> 现有远程链
- `Melee` -> 现有近战链

这也是为什么当前设计必须保持中性，不能写成只服务远程。

## 12. 当前阶段不做的内容

- 不做组合技专用攻击执行器
- 不做组合技专用 Verb 宿主链
- 不做默认主攻击自动选中组合技
- 不做非 `Verb` 组合技的真实消费闭环
- 不做协议模块配置
- 不做多组合技竞争裁决
- 不做实体装载层 `Loadout`
- 不做复杂扩展块 `Extensions`

## 13. 最终预期结构

### 13.1 定义层

```text
ChipDef
ComboDef
```

其中：

- `ChipDef` = 实体芯片定义
- `ComboDef` = 无实体第三芯片定义

### 13.2 表达层

```text
SingleSideResults
DualWeaponResults
ComboResults
```

### 13.3 执行层

```text
FormalExpressionResult
-> 普通单结果消费
-> WeaponMode 分流
-> Ranged / Melee
```

组合技不需要第二套攻击入口。

## 14. 一句话结论

组合技并入主模组现有系统的最小正确方式是：

- 把 `ComboDef` 设计成“去掉实体装载语义后的芯片定义同构体”
- 保留 `Trion + Expression` 两个正式核心块
- 允许同义字段显式填写或按 A/B 自动计算
- 在表达系统复合阶段按两枚芯片匹配并产出 `ComboResult`
- 让 `ComboResult` 作为普通单条结果继续进入现有攻击系统

这样最小、务实、结构稳定，也最符合当前 RimWorld 模组体量与主模组架构原则。
