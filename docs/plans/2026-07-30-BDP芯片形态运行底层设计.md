# BDP 芯片形态运行底层设计

日期：2026-07-30

所属事项：07A“正式化芯片形态底层系统”

前置事项：07“正式化芯片 Def（定义）公共基线”

## 一、目标

让已经成立的静态多形态定义成为真正可切换、可保存、可恢复的运行状态。

本项完成后：

- 多形态芯片正式启用时从默认形态开始。
- 玩家可通过独立 Gizmo（游戏操作按钮）立即切换形态。
- 形态切换统一刷新武器、Ability（技能）、Hediff（状态）、被动和视觉表达。
- 多个形态共同引用的表达保持原有宿主状态。
- 当前形态可随正式启用状态存读档。

本项不迁入“光魂”或其它具体多形态业务芯片，不实现形态切换耗时、切换费用或动作收尾队列。

## 二、现状与根因

主模组 Core（核心程序集）已经具备：

- `Expression.DefaultModeKey（默认形态键）`。
- `Modes（形态列表）`与 `ActiveEntryIds（启用表达条目标识）`。
- 单形态与多形态严格结构校验。
- 按当前形态选择表达并隔离缓存的解释器。
- 统一重建并发布武器、技能、状态、被动和视觉的投影链。

当前缺口只有运行真值和正式命令：

- `ITriggerLoadoutReader.GetChipModeKey`已经预留，但实现固定返回空。
- Trigger（触发体）没有保存启用中芯片的当前形态。
- 没有形态切换命令和玩家按钮。

因此多形态芯片只能固定落到默认形态。候选测试模组中不存在另一套可迁移的形态运行实现，本项是在主模组既有通用骨架上补齐运行闭环。

## 三、程序集与职责边界

### 3.1 Core

Core 负责全部中性运行能力：

- 当前形态真值。
- 可选形态与当前形态正式读取。
- 切换到指定形态和切换到下一形态的正式命令。
- 启用状态、多形态契约和目标形态校验。
- 存读档、无效形态回退和诊断。
- 原子切换与失败回滚。
- 表达重新发布及失效攻击中断。

Core 不认识“光魂”“大盾”“巨刃”等具体业务，也不依赖 Content（内容程序集）。

### 3.2 Content

Content 只负责玩家按钮：

- 启动时注册一个通用形态 Gizmo Provider（按钮提供器）。
- 通过 Core 正式读取口和命令口工作。
- 不为每枚具体芯片编写 C#（C#语言）注册代码。
- 复用现有 `TriggerLoadoutPanelExtension（触发体玩家芯片控制许可）`决定是否显示通用形态按钮。

没有玩家芯片控制许可的触发体不显示通用形态按钮。具体内容如需其它受控入口，仍可调用 Core 正式命令，但不得重新实现形态真值。

### 3.3 具体芯片

具体芯片只在 XML（定义文件）中声明形态数据和表达引用，自动接入通用底层，不需要代码注册。

## 四、形态配置补充

现有形态块补充玩家显示数据：

```xml
<li>
  <ModeKey>shield</ModeKey>
  <DisplayLabel>大盾</DisplayLabel>
  <GizmoIconTexPath>可选贴图路径</GizmoIconTexPath>
  <ActiveEntryIds>
    <li>dash</li>
    <li>shield_guard</li>
  </ActiveEntryIds>
</li>
```

规则：

- `ModeKey`必须填写且保持唯一，供程序识别。
- `DisplayLabel`必须填写，供玩家界面显示；缺失时整枚多形态芯片定义无效。
- 不允许把内部形态键直接当作玩家名称回退显示。
- `GizmoIconTexPath`选填；没有专用图标时使用芯片物品图标。
- 本项不增加形态描述、颜色、切换耗时或切换费用字段。

## 五、当前形态生命周期

当前形态只属于芯片正式启用期间：

```text
未启用
  ↓
没有当前形态
  ↓
启用正式完成
  ↓
建立默认形态
  ↓
启用期间允许立即切换
  ↓
停用正式完成
  ↓
清除当前形态
```

详细规则：

- 未启用芯片没有当前形态，不能预先选择形态。
- 启用过程尚未正式完成时不建立形态。
- 启用正式完成时使用 `Expression.DefaultModeKey`。
- 停用过程中旧形态继续随正式激活态生效。
- 停用正式完成后清除当前形态。
- 无论关闭前是什么形态，下次启用都从默认形态开始。
- 卸下、存放或换到另一把触发体时不保留形态记忆。
- 不给芯片物品增加保存形态的 ThingComp（物品组件）。

## 六、状态归属

当前形态保存在正式启用芯片的根 `TriggerSlotState（触发体槽位状态）`。

- 单槽芯片由自身槽位保存。
- 成对主副槽芯片只由根槽保存，镜像槽统一读取根槽。
- 不建立 `CompTriggerBody`额外的芯片编号映射表。
- 关闭或卸下时清空根槽形态。
- `GetChipModeKey`按实际芯片解析正式启用根槽，再返回当前形态。

这种归属与芯片启用生命周期一致，也能直接复用现有槽位存读档。

## 七、切换规则

### 7.1 时序与费用

- 形态切换立即完成。
- 不新增过渡阶段、进度条或独立切换状态机。
- 不借用芯片启用或停用延迟。
- 切换动作本身不消耗 Trion（触粒子）。
- 新形态中的攻击、技能、状态和持续表达继续按原有规则收费。

### 7.2 共享表达

两个形态引用同一个表达条目 `Id（标识）`时，该条目视为同一运行来源。

- 共用 Ability 的冷却继续保留。
- 共用 Hediff 和被动宿主不得无故删除重建。
- 只撤下旧形态独有表达，加入新形态独有表达。

### 7.3 正在执行的动作

当前暂定：

- 允许玩家立即切换形态。
- 旧形态尚未完成的攻击立即中断。
- 已经实际扣除的费用不返还。

这是后续游戏实测复查点。连续射击或连段如果显得突兀，再单独设计“已开始动作自然收尾后切换”；本项不提前加入等待队列。

### 7.4 原子提交

切换必须要么完整成功，要么完全不改变正式状态：

```text
校验启用状态、形态契约和目标
        ↓
暂时写入新形态
        ↓
重建并发布正式表达
        ↓
成功：提交新形态
失败：恢复旧形态并保留旧投影
```

规则：

- 未正式启用、不是多形态芯片或目标形态不存在时直接拒绝。
- 目标等于当前形态时不重复发布。
- 发布失败或异常时恢复旧形态。
- Content 向玩家提示“无法切换形态”。
- Core 诊断记录芯片、旧形态、新形态和失败原因。
- 不允许形态真值、按钮和实际表达处于不同状态。

## 八、Gizmo 交互

### 8.1 数量与顺序

- 每枚正式启用的多形态芯片显示一个按钮。
- 成对主副槽芯片只显示根槽对应的一个按钮。
- 多枚按钮按主槽、副槽、特殊槽及槽位编号稳定排列。

### 8.2 左键

- 按 XML `Modes`书写顺序切换到下一形态。
- 最后一个形态继续点击时循环回第一个。

### 8.3 右键

- 打开完整形态列表。
- 菜单顺序与 XML `Modes`一致。
- 明确标记当前形态。
- 选择当前形态不重复发布。

### 8.4 显示

- 按钮显示当前形态的名称和专用图标。
- 没有专用形态图标时显示芯片物品图标。
- 提示文字显示芯片名称、当前形态、左键将切换到的下一形态，并说明右键可精确选择。
- 切换成功后按钮立即显示新的当前形态。

## 九、存读档

- 只为正式启用中的多形态芯片保存当前形态键。
- 读档后芯片仍在原槽位且保持启用时恢复有效形态。
- 保存形态已经不存在时回退默认形态，并输出一次明确诊断。
- 未启用芯片清除任何残留形态。
- 没有形态记录时直接采用默认形态。
- 不建立旧字段迁移或兼容链。

## 十、验证内容

### 10.1 自动测试

至少覆盖：

- 启用完成建立默认形态。
- 未启用芯片没有形态且拒绝切换。
- 指定形态切换与下一形态循环。
- 最后一项回绕第一项。
- 成对槽只保存和显示一次。
- 关闭、卸载后清除形态，再次启用回到默认。
- 存读档恢复有效形态。
- 失效形态回退默认并记录诊断。
- 目标相同不重复发布。
- 非法目标和发布失败保持旧形态。
- 共用 Ability、Hediff 和被动宿主保持。
- 切换后旧形态独有表达撤下、新形态独有表达加入。
- Core 零本模组程序集依赖门禁继续通过。

### 10.2 游戏内验证

候选测试模组新增一枚强隔离、易搜索删除的“形态运行校验芯片”：

- 只包含验证两个形态、共用表达、Gizmo 和存读档所需的最小内容。
- 不进入主模组。
- 不提前制作“光魂”。
- 最终随整个候选测试模组在事项20物理退役。

游戏内至少实测：

- 启用后从默认形态开始。
- 左键循环和右键指定均正确。
- 按钮名称与图标反映当前形态。
- 共用技能冷却不被刷新。
- 存档后读档保持启用中的当前形态。
- 关闭再启用回到默认形态。
- 切换时旧形态攻击按暂定规则立即中断。

## 十一、明确不做

- 不迁入“光魂”或其它具体多形态业务。
- 不让未启用芯片预选形态。
- 不让芯片物品跨装载记忆形态。
- 不加入形态切换耗时、费用、冷却或队列。
- 不处理使用者输出功率门槛；该能力属于事项07B。
- 不改变芯片启用互斥、启用延迟和停用延迟。
- 不向没有玩家芯片控制许可的触发体显示通用形态按钮。
- 不为架构扩展而新增事件总线、注册中心或第二套投影系统。

## 十二、完成条件

- Core 当前形态、命令、存读档和表达刷新闭环成立。
- Content 通用 Gizmo 提供器按许可显示并正确操作。
- 具体多形态芯片只写 XML 即可自动接入。
- 全部专项测试通过。
- 三个程序集 Release（发布）构建成功。
- Core 零本模组程序集依赖门禁通过。
- 全部 XML 可解析。
- 全量回归不增加既有基线之外的新失败。
- 候选验证芯片完成游戏内实测，且未进入主模组。
