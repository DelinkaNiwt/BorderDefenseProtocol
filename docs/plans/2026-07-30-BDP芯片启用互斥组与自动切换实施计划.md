## 正式配置与运行语义

作者配置：

```xml
<Loadout>
  <SlotRegion>MainSub</SlotRegion>
  <SlotOccupancy>Single</SlotOccupancy>
  <ActivationExclusionGroups>
    <li>BDP_ExampleExclusionGroup</li>
  </ActivationExclusionGroups>
</Loadout>
```

Core 类型：

```csharp
public sealed class ChipExclusionGroupDef : Def
{
}
```

冲突判定：

```text
无共同组                     → 不冲突
共享任意一个 Def 身份         → 冲突
同一芯片重复引用同一个组       → 定义错误
空引用或无法解析的引用         → 定义错误
```

自动切换：

```text
点击目标 B
  ├─ 同侧当前活动 A 开始正常关闭
  ├─ 跨侧冲突活动 C 开始正常关闭
  ├─ 跨侧冲突活动 D 开始正常关闭
  └─ B 进入等待
        └─ A/C/D 全部正式关闭后
              └─ B 开始正常开启
```

后续指令：

```text
B 与新目标 D 同侧             → D 覆盖尚未启用的 B
B 与跨侧新目标 D 互相冲突      → D 覆盖 B
B 与跨侧新目标 D 不冲突        → B、D 并行保留
重复点击等待/开启中的 B        → 无操作
B 正式激活后再点击 B           → 正常关闭 B
```

**Step 3：一次性扫描并同时启动全部阻挡者**

`TriggerService.RequestActivate`在正式接受新目标时完成：

1. 归一镜像槽到根槽。
2. 找出目标控制范围内必须让位的同侧活动芯片。
3. 找出其它侧所有与目标共享互斥组的逻辑活动芯片。
4. 根槽去重，镜像不作为第二枚阻挡者。
5. 在同一个 `currentTick（当前游戏刻）`为全部阻挡者建立正常 `WindingDown`。
6. 已经在关闭中的阻挡者保留原结束刻，不重置计时。
7. 目标若尚有任一阻挡者则进入 `WaitingForConflicts`；没有阻挡者则沿用正常开启流程。

关闭时长仍逐枚来自既有 `ResolveChipWinddownTicks（解析芯片关闭时长）`，不取总和，不强行统一为最慢值。

**Step 4：处理已有目标的覆盖与并行**

新命令提交前检查三侧现有目标：

- 同一控制侧的旧目标被新目标覆盖。
- 其它侧与新目标共享互斥组的旧目标被覆盖。
- 其它侧与新目标不冲突则保留并行。
- `PairedHands`目标占据主、副两侧控制范围，覆盖必须同步处理两侧。
- 旧目标若处于 `WarmingUp`，清除其开启上下文。
- 旧目标若仍连带某枚活动芯片 `WindingDown`，只改写/清除目标，保留旧芯片剩余关闭计时。
- 重复选择完全相同的等待或开启目标直接视为无操作成功，不改写上下文。

**Step 5：结算等待阶段**

每次现有 Trigger runtime tick（运行刻）结算时：

1. 先做目标身份和可用性校验。
2. 按当前活动槽位重新扫描全部阻挡者，不读取存档阻挡名单。
3. 新出现的阻挡者立即进入自己的正常关闭阶段。
4. 仍有活动或关闭中的阻挡者时继续等待。
5. 全部阻挡者正式关闭后，才构造目标完整 `WarmingUp`。
6. 开启延迟为0时沿现有即时提交路径。
7. 正式启用通知及一次性激活费仍只在开启完成时发生；支付失败沿现有通知链关闭目标并清理状态。

`WindingDown`到期准备转入目标开启时也必须经过相同复查，不能绕过等待门槛。

**Step 6：保持成对主副槽单次逻辑结算**

- 成对目标的主副上下文保存同一根芯片身份。
- 主、副等待与开启同步推进。
- 阻挡者可以包含同侧让位的成对芯片，但只按根槽关闭一次。
- 正式启用/关闭通知继续只由根槽发布一次，不能重新引入重复激活费。
