# BDP 芯片启用互斥组与自动切换设计

日期：2026-07-30  
状态：已确认，尚未实施

## 一、目标

把自由文本 `ExclusionTags（排斥标签）`替换为 RimWorld（边缘世界）式受控 Def（定义）引用，并把当前“发现冲突就拒绝新芯片启用”的行为改为玩家友好的自动切换：

```text
选择目标芯片
→ 同时关闭同侧让位芯片和全部跨侧冲突芯片
→ 等所有阻挡者真正关闭
→ 目标芯片再执行正常开启程序
```

本项只规范启用互斥规则和它直接需要的切换时序，不定义任何具体业务互斥组。

## 二、现状与问题

当前 `Loadout.ExclusionTags（装载配置.排斥标签）`是任意字符串列表。目标芯片与已激活芯片共享至少一个字符串时，`TriggerService（触发体服务）`直接拒绝目标芯片的启用请求。

现状存在四个问题：

1. 拼写错误不会被发现，只会静默形成一个新标签。
2. 标签没有统一 Def 身份、说明和内容归属。
3. 拒绝新启用要求玩家手动关闭旧芯片，再次点击目标芯片，操作繁杂。
4. `ExclusionTags`还被复制进表达运行快照，但表达系统没有消费者，属于无用传递。

候选内容中唯一使用者是 `BDP_TestChipDualWieldRanged（测试双持远程芯片）`的临时 `DualWieldTest（双持测试）`。它只会阻止同时启用两枚该样本，并不代表已经确认的正式业务关系。

## 三、受控互斥组

### 3.1 Core 类型

Core（核心程序集）新增：

```csharp
public sealed class ChipExclusionGroupDef : Def
{
}
```

该类型只提供稳定身份。Core不预设护盾、武器或其他具体业务分组，也不在组 Def 中维护成员列表。

### 3.2 芯片配置

芯片在自己的 `Loadout（装载配置）`中主动引用互斥组：

```xml
<ActivationExclusionGroups>
  <li>BDP_ExampleExclusionGroup</li>
</ActivationExclusionGroups>
```

正式配置与契约类型分别为：

```csharp
List<ChipExclusionGroupDef> ActivationExclusionGroups;
IReadOnlyList<ChipExclusionGroupDef> ActivationExclusionGroups;
```

### 3.3 规则

- 字段可省略；省略表示该芯片没有启用互斥关系。
- 两枚芯片共享任意一个组即构成冲突。
- 一枚芯片可以属于多个不同组。
- 同一枚芯片重复引用同一个组属于定义错误。
- 空引用或无法解析的引用属于定义错误。
- 互斥只限制同时启用，不限制共同搭载。
- 具体组由 Content（正式内容程序集）或其他内容模组定义。

### 3.4 旧内容处理

- 物理删除 `ExclusionTags`配置、契约、运行判断和表达快照传递链。
- 删除候选 XML 中的临时 `DualWieldTest`，不建立对应正式组。
- 改造完成后，底层互斥能力正式可用，但当前主模组与候选内容可以暂时没有任何具体互斥组实例。
- 不做旧字段兼容。

## 四、切换状态

现有 `SwitchContext（切换状态）`继续作为唯一状态来源，不建立第二套待启用队列。

`SwitchPhase（切换阶段）`在现有：

```text
WindingDown（关闭中）
WarmingUp（开启中）
```

基础上增加：

```text
WaitingForConflicts（等待冲突解除）
```

等待阶段保存在目标所在侧的既有切换状态中。`PairedHands（成对主副槽）`目标继续由主副两侧同步上下文表示，但只是一份逻辑启用请求。

## 五、一次自动切换

玩家选择目标芯片B时，系统在同一个指令时点完成两类扫描：

1. 找出B同侧当前必须让位的活动芯片，不要求它与B共享互斥组。
2. 找出其他侧中与B共享互斥组的全部逻辑活动芯片。

所有阻挡者同时进入各自现有的正常关闭程序：

```text
点击B
  ├─ 同侧A开始关闭
  ├─ 跨侧冲突C开始关闭
  ├─ 跨侧冲突D开始关闭
  └─ B等待
        └─ A、C、D全部正式关闭后，B开始开启
```

### 5.1 时间规则

- 所有阻挡者的关闭程序在同一个游戏刻开始。
- 每枚阻挡者读取自己的关闭时长，不串行相加。
- 已经处于关闭阶段的阻挡者继续原计时，不重置。
- B等待期间不生效、不发布表达、不扣激活费用。
- B进入正常开启阶段后才开始计算自己的开启时长。
- B正式开启完成时才扣除一次激活费用并发布正式事件。
- A、C、D在各自正式关闭前仍保持原有效果和费用。

### 5.2 安全复查

目标准备从等待转入开启时重新按当前真值扫描：

- 没有阻挡者：进入正常开启阶段。
- 仍有正在关闭的阻挡者：继续等待。
- 新出现活动冲突者：让它进入正常关闭程序，目标继续等待。

安全复查不是首次发现跨侧冲突的时机；初次点击B时就必须一次性发现并同时关闭当前全部阻挡者。

## 六、后续指令

### 6.1 覆盖与并行

- B、D同侧：后点击的D覆盖仍未正式启用的B。
- B、D跨侧但互相冲突：后点击的D覆盖B。
- B、D跨侧且互不冲突：两项请求各自保留并行推进。
- 成对主副槽目标占用主副两侧控制范围；新的成对目标会覆盖主、副两侧尚未完成的目标。
- 已经开始关闭的旧芯片不倒退，也不因目标被覆盖而自动重新开启。
- 新目标出现时立即扫描它自己的全部阻挡者，并让新增阻挡者同时开始关闭。

### 6.2 不提供主动取消

等待中的B和开启中的B都不能通过重复点击主动取消：

```text
重复点击B → 无效
明确点击D → 按覆盖或并行规则处理
B正式开启后再点击B → 正常关闭B
```

这样可避免玩家连续点击同一位置导致目标在等待、关闭和重新选择之间反复跳变。

## 七、存读档与身份校验

等待阶段直接进入现有 `SwitchContext`存读档。除现有阶段、目标侧别和槽位索引外，增加目标芯片 `ThingID（物品身份）`，避免槽位内容在长时间等待中发生变化后误启用替代物。

不保存阻挡者名单。读档后按当前真实槽位重新扫描：

- 目标芯片仍位于原槽位且身份一致：继续等待或进入开启。
- 目标已卸下、替换、销毁或身份不一致：清除等待。
- 目标被禁用、战斗体解除、崩解或不可用：清除等待。
- 正式开启时激活费用支付失败：目标保持关闭，等待状态清除。

取消无效请求后不自动恢复已经关闭或正在关闭的旧芯片。

## 八、玩家界面

等待状态必须与禁用状态区分：

- 目标图标保持正常亮度。
- 使用亮琥珀黄色专用描边。
- 提示文字显示“等待冲突芯片关闭”。
- 重复点击目标不执行操作。
- 不显示固定进度条，因为等待时长取决于全部阻挡者的实时状态。
- 冲突解除后进入现有开启阶段，继续使用正常开启进度表现。
- 正式开启后改为现有绿色描边。

首版只固定语义，不把具体琥珀色色值当成长期不可调整参数；后续可按游戏实测微调。

## 九、错误处理

定义校验至少拒绝：

- `ActivationExclusionGroups`中的空项。
- 同一芯片重复引用同一互斥组。
- 无法解析为 `ChipExclusionGroupDef`的引用。

运行时只相信已经通过定义校验的契约，同时保留最后一道安全边界：

- 读取不到合法目标契约时取消请求。
- 目标槽位或目标身份变化时取消请求。
- 不能把镜像槽当成第二枚冲突芯片或第二份请求。
- 遇到异常状态时清除无效等待，不自动猜测并恢复旧芯片。

诊断信息只记录真正异常的状态丢失或非法定义，不为正常等待每个游戏刻刷日志。

## 十、验收边界

实施测试至少覆盖：

1. 自由文本旧字段和运行快照传递链物理删除。
2. Def 引用缺失、空项、重复项被定义校验拒绝。
3. 无共享组不冲突，共享任意组即冲突，多组关系正确。
4. 同侧让位芯片和全部跨侧冲突芯片在同一个游戏刻开始关闭。
5. 目标等待最慢阻挡者关闭后才开始开启。
6. 已在关闭中的阻挡者不重置计时。
7. 等待转开启前发现新冲突时继续关闭和等待。
8. 同侧后请求覆盖前请求。
9. 跨侧冲突后请求覆盖前请求。
10. 跨侧非冲突请求并行保留。
11. 重复点击等待或开启中的同一目标无效。
12. 成对主副槽目标同步等待、同步开启且只结算一次。
13. 等待状态和目标身份完成存读档往返。
14. 目标替换、禁用、战斗体失效和激活支付失败能安全清理。
15. Content 面板使用亮琥珀色等待描边且不把图标置灰。
16. 当前候选临时 `DualWieldTest`删除，不擅自增加具体正式互斥组。
17. 三个程序集构建、版本 XML 解析、Core 零本模组程序集依赖门禁和全量既有基线不回归。

## 十一、明确不做

- 不限制互斥芯片共同搭载。
- 不建立任意文本标签兼容层。
- 不建立全局操作队列或第二套待启用系统。
- 不让重复点击等待目标成为主动取消。
- 不自动重新开启已经关闭的旧芯片。
- 不在本项定义具体业务互斥组。
- 不修改芯片攻击、表达、Trion（能量）、槽位占用、启停时长或其它业务参数。
- 不进入事项07A、事项07B或后续应用事项。
