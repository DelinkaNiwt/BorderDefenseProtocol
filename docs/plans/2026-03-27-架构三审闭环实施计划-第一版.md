# 架构三审闭环实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 把 BDP 当前“表面已收口、但运行时闭环仍有缺口”的状态，推进到“结构、运行时、复查口径、游戏实测口径同时闭合”的状态，避免再次出现“按计划执行完却仍然复查不过”的结果。

**Architecture:** 本计划不再以“继续删层、继续压抽象”作为主目标，而是改成“先补运行时最小闭环，再拆错误协调点，再把读取和重算拆开，最后用强复查门卡死回潮”。核心原则是：真值 owner 不新增，运行时对象必须满足原版最小前提，读取路径不得偷偷修系统，任何阶段完成都必须同时过结构复查门和游戏验证门。

**Tech Stack:** RimWorld 1.6、C# 7.3、Harmony、ThingComp、CompEquippable、Pawn_MeleeVerbs / VerbTracker 原版约束、现有 BDP Surface/Reader/Command 分层、以游戏实测为最终验收。

## 一、这份计划为什么和上一轮不同

上一轮计划的问题，不是“完全做错”，而是“切层做得比闭环做得更彻底”。

说白一点：

- 上一轮擅长处理“谁不该管谁”
- 但没有把“谁必须把事情做完整”写死
- 所以结构上变薄了，运行时闭环却没有一起补齐

最后就出现了这种局面：

- 表达层、Trigger、VerbHosting 的耦合确实比以前小了
- 但近战执行链里动态 Verb 还是半成品
- Trigger 还是在 owner 身份之外偷偷编排下游
- 表达层还是“你来读，我现算”
- 复查时自然还能继续挑出硬伤

这不是一句“执行不认真”能糊过去的事。

这次结论明确：

- **上一轮主要是计划不到位**
- **执行层也有问题，但不是主因**

本计划因此增加三类上轮没有写死的东西：

1. **运行时最小闭环表**
2. **阶段性硬验收门**
3. **最终复查否决条件**

只要其中任何一项没过，就不允许说“本阶段完成”。

## 二、本轮目标不是“更漂亮”，而是“复查不会再翻车”

本轮完成标准不是：

- 类更少了
- 接口更少了
- 图更整齐了

本轮完成标准是：

1. 动态运行时对象不再是半成品。
2. Trigger 不再直接编排表达重算和宿主刷新。
3. 表达层读取和重算彻底分开。
4. 攻击执行链按路径分清“桥接、启动、持续推进、原版前提”。
5. 每一阶段结束后，复查只能给出“剩余风险已明确但不影响本轮目标”，不能再给出“核心问题没解决干净”。

## 五、本轮绝不妥协的设计约束

### 1. 不新增第四个事实 owner

不允许为了省事，临时造一个“总状态中心”“战斗运行时总线”“全局宿主缓存事实层”。

### 2. 不允许读取路径修系统

以下动作都必须是纯读取：

- `GetSnapshot`
- `GetInfoProjection`
- `GetManualProjection`
- `GetVisualProjection`
- gizmo 构建
- UI 说明生成

如果某条读取链仍然会触发：

- 重算
- 宿主刷新
- 状态补齐
- 兼容兜底

则本轮视为未完成。

### 3. 不允许“编译通过 = 阶段完成”

编译通过只能证明“代码还能编”，不能证明：

- 原版前提满足
- 动态对象可用
- Trigger 不再越界
- 读取和重算已分离

### 4. 不允许为了规避问题而恢复旧式总协调器

不能因为要补闭环，就重新走回：

- `CompTriggerBody` 总控
- 全局 refresh 自愈链
- patch 层补业务规则
- UI 读取顺手修状态

## 六、实施总路线

本轮按下面顺序执行，顺序不能乱：

1. **Task A：建立运行时最小闭环基线**
2. **Task B：修正攻击执行链，先让运行时对象合法**
3. **Task C：把 Trigger 退出下游编排**
4. **Task D：把表达层改成“显式重算 + 稳定读取”**
5. **Task E：把 VerbHosting 收成受控投影层**
6. **Task F：清理扩展口、兼容口和回潮入口**
7. **Task G：做最终结构复查和游戏实测复查**

原因很简单：

- 不先补运行时闭环，后面任何“切层”都可能只是把 bug 藏起来
- 不先把近战链跑通，最终复查一定会继续被原版运行时约束打脸
- 不先拿掉 Trigger 的下游编排，表达和宿主层就无法真正独立
- 不把读取/重算拆开，所有性能和职责分析都不可信

### 改造原则

Trigger 只能做两件事：

1. 改变自己的真值
2. 报告“真值发生了什么变化”

Trigger 不能再做：

- `BuildSelectedSnapshot`
- `Sync(...)`
- `Refresh(...)`
- 任何下游层的直接 new / 直接调度

### 推荐落地方式

不是引入复杂事件总线，而是引入一个窄协调器：

- Trigger 把变更原因交给协调器
- 协调器决定是否触发表达重算
- 协调器决定是否触发宿主投影刷新

这样做的目的不是“多一层优雅”，而是把责任从 owner 身上拿走。

### 目标流向图

```text
旧:
Trigger 改真值
   |
   +--> 直接重算表达
   +--> 直接刷新宿主

新:
Trigger 改真值
   |
   v
ExpressionRebuildCoordinator.Invalidate(reason)
   |
   +--> 需要时重算表达状态
   |
   +--> 需要时通知宿主投影更新
```

### 验收门

#### 结构门

- `CompTriggerBody` 内不再出现直接调用表达重建和宿主刷新的代码。
- Trigger 生命周期方法只处理 Trigger 自身数据与容器完整性。

#### 行为门

- 装载、卸载、启用、停用、读档恢复后，仍能触发正确的后续更新。
- 更新原因可追溯，不再是“谁先读到了谁就顺手修一下”。

#### 游戏门

- 装卸芯片后，UI、手动入口、自动攻击宿主结果能正确更新。
- 读档后，不需要打开界面或触发一次读取才能恢复正确状态。

### 否决条件

- Trigger 只是把旧逻辑换个文件继续直接调
- 仍然依赖 UI/gizmo 读取来触发最终状态正确化
- 读档恢复依然要靠“顺手刷新”

## 十五、为防止再次“自己打自己脸”，本轮新增四个硬机制

### 机制 1：任何“完成”都必须绑定否决条件

不是只写“做完什么”，还要写“什么情况下不能算做完”。

### 机制 2：结构验收和游戏验收分开写

上轮的问题之一，就是太容易把“结构上看起来对了”和“运行时真的闭环了”混在一起。

这次必须分开：

- 结构对不对
- 运行时成不成立
- 游戏里能不能稳定工作

### 机制 3：每阶段先写允许保留什么，再写必须删除什么

比如：

- VerbHosting 可以暂时保留显式全量重建
- 但不能继续挂在热路径上

这样能防止团队为了“彻底”而过度重构，也防止为了“省事”而把危险逻辑继续留着。

### 机制 4：最终结论必须允许说“这项本轮不做”

真正避免打脸，不是嘴硬说全做完，而是把：

- 已解决
- 未解决
- 故意延后

分清楚。

只要分类真实，复查就不会再出现“你自己说完成，结果核心缺口还在”。
