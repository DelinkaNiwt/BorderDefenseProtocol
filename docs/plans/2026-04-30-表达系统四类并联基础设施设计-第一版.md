# 表达系统四类并联基础设施设计（第一版）

## 目的

这份设计文档回答一个核心问题：

- 新 BDP 怎样让 `Verb`、`Ability`、`Hediff`、`Passive` 四类表达作为并联设施各自跑通，并作为一个整体稳定接入表达系统。

本轮设计不新增第五类表达，不重做原版系统，也不把某一类表达改造成另一类的附属物。

本轮重点是：

- 四类表达并联成立。
- 四类表达共享中性结果管线。
- 四类表达各自有清楚的发布或读取方式。
- `Dual` 继续只接收 `Verb`。
- `Combo` 面向多类别，但必须通过统一的来源属性获取和计算机制生成结果。

---

## 一、总定位

表达系统当前的四个顶层类别保持不变：

```text
ExpressionResultKind
├─ Verb     攻击入口
├─ Ability  原版 Ability 宿主发布
├─ Hediff   原版 Hediff 宿主发布
└─ Passive  钥匙/开关/许可信号
```

这四类是并列关系。

```text
芯片表达来源
      |
      v
正式表达结果表
      |
      +--> Verb 通道
      +--> Ability 通道
      +--> Hediff 通道
      +--> Passive 通道
```

其中 `Passive` 的本轮正式定位是：

- 它是四大顶层类别之一。
- 它默认独立成立。
- 它像钥匙、开关或许可标记。
- 它自身不一定执行动作。
- 其它系统需要时，可以查询它是否成立。

`Passive` 不以“挂接到 Verb / Ability / Hediff”为当前核心语义。

## 二、当前代码事实

### 1. 类别定义已经收口

源码里当前只存在四类正式结果：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

作者配置层把 `PrimaryVerb`、`SecondaryVerb` 分开，是为了表达主副攻击入口；它们进入结果层后仍然归为 `Verb`。

### 2. 四类实现深度不一致

当前实际情况更接近：

```text
Verb
  已有完整宿主、选择、手动入口、自动攻击和执行链

Ability
  已能发布到原版 AbilityTracker，但缺少更完整的结果级发布追踪

Hediff
  已能发布到 BDP 表达宿主 Hediff，但缺少更完整的结果级发布追踪

Passive
  已能出现在正式结果表，但主要靠业务方手动扫描结果
```

因此本轮不是“改类别”，而是把四条并联通道的基础设施补齐。

### 3. 组合表达已有结构，但来源求值不够统一

当前 `Dual` 和 `Combo` 都属于复合表达。

```text
Dual
  只面向 Verb
  表示双侧攻击入口

Combo
  由两个来源芯片匹配出无实体的第三表达定义
  结构上应允许生成 Verb / Ability / Hediff / Passive
```

当前问题在于：

- `Combo` 的来源字段计算主要围绕少量 `Verb` 字段。
- `Combo` 结果生成时存在字段直接抄主侧或副侧的情况。
- 缺少一个类别中性的“来源属性获取与计算”设施。

## 三、目标结构

本轮目标结构如下：

```text
芯片 A / 芯片 B
      |
      v
来源声明层
      |
      v
正式结果构建层
      |
      +-----------------------------+
      |                             |
      v                             v
单来源结果                    复合结果
                               |
                               +--> Dual: 只接 Verb 来源
                               |
                               +--> Combo: 可生成四类结果
      |
      v
正式表达结果表
      |
      +--> Verb 发布/读取
      +--> Ability 发布/读取
      +--> Hediff 发布/读取
      +--> Passive 发布/读取
```

关键点：

- `FormalExpressionResult` 继续作为四类共同的结果载体。
- 四类通道共享上游管线，不各造一套表达系统。
- 四类通道在下游按原版机制或 BDP 读取面分别落地。
- `Combo` 通过统一求值设施决定结果字段，不在各处临时拼装。

## 四、四类并联通道

### 1. Verb 通道

`Verb` 继续作为攻击入口通道。

它负责：

- 进入正式 Verb 宿主。
- 支撑手动攻击入口。
- 支撑自动攻击选择。
- 支撑远程与近战执行链。

本轮对 `Verb` 的原则：

- 保持现有主链稳定。
- 不把 `Ability`、`Hediff`、`Passive` 硬塞进 Verb 宿主。
- 把 `Verb` 中已经成熟的结果身份、宿主绑定、执行读取经验，提炼成可供其它通道参考的中性规则。

### 2. Ability 通道

`Ability` 继续发布到原版 `Pawn_AbilityTracker`。

它负责：

- 当前表达成立时，Pawn 拥有对应 Ability。
- 当前表达不成立时，回收由表达系统补入的 Ability。

本轮需要补强：

- 保留按 `AbilityDefName` 的轻量同步。
- 增加结果级可追踪信息，让系统能知道哪些正式结果要求了哪些 Ability。
- 不引入第二套 Ability 运行时。

### 3. Hediff 通道

`Hediff` 继续发布到 BDP 表达宿主 Hediff。

它负责：

- 当前表达成立时，Pawn 身上存在对应表达宿主 Hediff。
- 当前表达不成立时，回收表达系统发布的 Hediff。
- 在 `countToSeverity` 模式下，把成立数量映射为强度。

本轮需要补强：

- 保留 `BdpExpressionHostHediff` 边界。
- 保留现有轻量同步。
- 增加结果级可追踪信息，让后续排查能知道 Hediff 来自哪些正式结果。

### 4. Passive 通道

`Passive` 是钥匙、开关和许可通道。

它负责：

- 把“某个被动许可当前成立”发布到正式读取面。
- 让业务系统按 `PassiveKey` 查询当前是否允许某件事。
- 携带轻量 `ExposedData`，供需要的业务系统读取。

它不负责：

- 自己执行攻击。
- 自己添加 Hediff。
- 自己施放 Ability。
- 默认挂接到某个 Verb 上。

目标读取方式应接近：

```text
问：当前 Pawn 的表达结果里，PassiveKey = EmergencyEscape 是否成立？
答：成立 / 不成立，并能返回对应结果与暴露数据。
```

这样业务层不需要再手动扫描 `snapshot.Results`。

## 五、并联整体的共同设施

四类表达需要共享下列中性设施。

### 1. 正式结果身份

每条正式结果都应有稳定 `Id`。

这个 `Id` 不是只服务 `Verb`，而是四类通道共同使用：

```text
result.Id
result.ResultKind
result.SourceReference
result.ComboDefName
result.ModeKey
```

用途：

- 调试时能定位结果来源。
- 发布层能知道自己处理的是哪条结果。
- 组合表达能记录自己由哪些来源结果生成。

### 2. 类别中性读取面

需要在表达读取面上提供四类通道的基础查询：

```text
GetVerbResults(...)
GetAbilityResults(...)
GetHediffResults(...)
GetPassiveResults(...)
HasPassiveKey(...)
TryGetPassive(...)
```

其中 `Passive` 的读取面优先级最高，因为它当前最缺正式读取口。

### 3. 发布快照

发布层不一定要把四类都做成同一种宿主，但应形成统一的观察结构：

```text
表达结果
  -> 发布需求
  -> 发布结果或读取项
```

对应关系：

```text
Verb     -> Formal Verb Host
Ability  -> Pawn_AbilityTracker
Hediff   -> BdpExpressionHostHediff
Passive  -> Passive 读取索引
```

这样四类依然按自己的原版落点工作，但整体上可被统一观察。

## 六、组合表达的统一来源求值

这是本轮最重要的公共基础设施。

### 1. 总原则

`Combo` 不应在结果生成时到处临时复制字段，而应通过统一求值器生成结果。

```text
来源结果 A ----\
               -> 统一来源求值器 -> Combo 正式结果
来源结果 B ----/
```

统一求值器要回答：

- 这个字段是否由 Combo 自己显式声明？
- 如果没有显式声明，是否从来源 A / B 获取？
- 如果两边都有值，按什么规则计算？
- 如果仍然没有值，是否使用现有默认回退？

### 2. 字段优先级

统一优先级建议为：

```text
1. Combo 条目显式声明
2. Combo 条目的 Resolve 规则
3. 来源结果的既有字段
4. 该类别的默认回退
```

这条规则必须对四类保持一致。

### 3. 基础求值模式

先保留最小通用模式：

```text
Explicit       显式值
FromA          取来源 A
FromB          取来源 B
FirstNonEmpty  取第一个非空值
Min            取较小数值
Max            取较大数值
Average        取平均值
Sum            求和
Merge          合并集合
```

不需要一开始支持复杂表达式。

### 4. 先覆盖的字段范围

第一阶段建议覆盖已有模型中已经存在、且风险可控的字段：

```text
共同字段
- DisplayLabel
- RoleKey
- Tags
- Trion
- ModeKey

Verb 字段
- WeaponMode
- VerbAttackRole
- VerbProps 中现有已支持的数值字段
- ExecutionStyle 中现有已支持的节奏字段
- RangedModules

Ability 字段
- AbilityDefName

Hediff 字段
- HediffDefName
- HediffApplyModeKey

Passive 字段
- PassiveKey
- ExposedData
```

后续如果要扩展字段，只补求值器适配，不再在 `CompositeExpressionResolver` 里继续堆临时代码。

### 5. Dual 与 Combo 的分工

`Dual` 继续保持窄语义：

```text
Dual = 两侧 Verb 的双武器攻击入口
```

它只接收：

- `ResultKind = Verb`
- 兼容的 `WeaponMode`

`Combo` 承担更通用的复合定义：

```text
Combo = 两个来源芯片匹配出的无实体第三表达定义
```

它可以生成：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

但所有类别都必须经过同一套来源求值协议。

## 七、Mode 与关系元信息

`Mode` 和 `RelationKind` 属于表达系统的公共元信息。

它们不是四类表达的第五类，也不属于某一类专用设施。

### 1. Mode

`Mode` 表示芯片当前形态。

本轮目标：

- 让运行时能读取当前芯片形态。
- 让已有 `Modes` 配置真正参与表达解释。
- 默认从 `InitialModeKey` 进入。

本轮不急于做：

- 新 UI。
- 复杂切换操作。
- 多阶段形态状态机。

### 2. RelationKind

`RelationKind / ParentEntryId` 表示表达条目之间的关系。

本轮目标：

- 作为中性元信息贯穿结果链。
- 不把它变成 `Passive` 的默认语义。
- 不要求四类结果必须互相挂接。

后续若需要类别间挂接，可以在这个基础上继续做。

## 八、实施分期

### 第一期：四类并联读取面与结果身份收口

目标：

- 保持现有 `Verb`、`Ability`、`Hediff` 行为稳定。
- 给 `Passive` 增加正式读取面。
- 给四类结果补统一查询能力。
- 记录必要的结果级发布信息。

验收：

- 现有 `EmergencyEscape` 被动不再需要业务层手扫结果。
- 现有 Ability / Hediff 样本仍能正常发布。
- 现有 Verb 攻击链不回退。

### 第二期：Combo 统一来源求值器

目标：

- 抽出类别中性的来源字段求值设施。
- 修正 `Combo` 结果字段来源不统一的问题。
- 让 `Combo` 对四类结果都按同一规则生成。

验收：

- `Combo` 的 `Trion` 使用统一规则。
- `Verb` 型 Combo 现有攻击行为不回退。
- `Ability`、`Hediff`、`Passive` 型 Combo 可以生成正式结果。

### 第三期：Mode 运行时真值接入

目标：

- `GetChipModeKey` 返回真实形态。
- `InitialModeKey` 成为默认入口。
- 现有无形态芯片保持原行为。

验收：

- 没写 `Modes` 的芯片行为不变。
- 写了 `Modes` 的芯片能按当前形态解释表达。

### 第四期：发布观察与诊断收口

目标：

- 让四类表达的发布状态可观察。
- 为游戏内实测准备可插拔诊断日志。
- 不把诊断日志混入正式业务逻辑。

验收：

- 能定位某条结果来自哪个芯片或 Combo。
- 能定位某条结果发布到了哪个通道。
- 诊断设施可搜索、可关闭、可删除。

---

## 九、非破坏约束

本轮所有改造必须遵守：

- 不新增表达顶层类别。
- 不改变 `Verb` 现有攻击链入口语义。
- 不改变 `Ability` 发布到原版 AbilityTracker 的基本语义。
- 不改变 `Hediff` 发布到 BDP 表达宿主 Hediff 的基本语义。
- 不把 `Passive` 改成附属类别。
- 不要求现有芯片补写新字段才能继续工作。
- 不让无 `Mode` 的芯片因为形态系统接入而失效。
- 不让 `Dual` 接收非 `Verb` 结果。
- 不把业务原型写回主模组。

遇到需要扩大影响范围的改动，应先停下来单独裁定。

## 十、作者侧最终理解

业务作者最终只需要理解：

```text
要攻击：写 Verb
要能力：写 Ability
要状态：写 Hediff
要许可：写 Passive
```

组合表达最终只需要理解：

```text
Dual 是双 Verb 攻击入口
Combo 是两个芯片组合出的第三表达定义
Combo 的字段由统一来源求值规则决定
```

---

## 十一、一句话结论

BDP 表达系统下一步的重点，是把 `Verb`、`Ability`、`Hediff`、`Passive` 四类表达作为并联设施完整接入，并把 `Combo` 的来源属性获取和计算收成统一机制；当前不扩类，也不把 `Passive` 改造成任何其它类别的从属物。
