# BDP 芯片槽位占用方式规范化设计

日期：2026-07-30
状态：用户已完整确认，并授权实施计划完成后直接执行

## 一、要解决的问题

当前 `Loadout.IsDualWieldBinding（装载配置.是否双持绑定）`的名字把底层槽位结构和具体“双持”业务混在了一起。

它实际不承诺两把武器、两次攻击或双持外观，只负责：

1. 一枚芯片同时占用主、副两侧相同编号的槽位。
2. 以一侧作为根槽，另一侧作为不可独立控制的镜像槽。
3. 让成对槽位同步装卸、启用、关闭和切换。
4. 让容量、芯片定义和表达来源按同一枚芯片去重。
5. 保存和恢复根槽、镜像槽之间的绑定关系。

因此底层字段应改成中性的“槽位占用方式”，具体双持效果继续由表达和上层应用决定。

## 二、现状复查结论

当前16个合法候选芯片中：

- 15个芯片没有填写旧布尔字段，依赖默认 `false（否）`。
- 1个双武器候选芯片显式填写 `IsDualWieldBinding=true（启用双持绑定）`。

现有运行链已经做到：

- 成对占槽的容量占用只计算一次。
- 表达收集忽略镜像槽，只发布一次芯片表达。
- 镜像槽不能单独拖动、装卸或直接控制。
- 成对槽位同步启用、关闭和切换。

但复查发现一个既有错误：

```text
根槽与镜像槽一起激活
  → 根槽发送一次启用完成通知
  → 镜像槽再发送一次启用完成通知
  → 两次通知分别扣除一次芯片激活费
```

这会导致一枚成对占槽芯片可能被扣两次一次性激活费用；第二次支付失败时，还可能出现第一次费用已经扣除、随后整组又被撤销的错误结果。

## 三、方案比较

### 方案一：必填强类型枚举

```xml
<SlotOccupancy>Single</SlotOccupancy>
```

优点：

- 可以可靠识别漏填。
- 定义含义直接，不再带双持业务倾向。
- 以后只有出现真实新占用方式时才扩展枚举。

采用本方案。

### 方案二：改名后的布尔值

例如 `UsesPairedSlots（是否使用成对槽位）`。

它虽然改动较小，但漏填仍会静默变成 `false（否）`，也无法清楚承载未来可能出现的第三种真实占用方式，因此不采用。

### 方案三：开放式槽位数量或槽位列表

它会允许作者写出“三个主槽”“主槽加特殊槽”等运行系统不支持的组合，增加无意义的校验和分支，违背当前简单二选一需求，因此不采用。

## 四、正式配置结构

### 4.1 字段与枚举

单槽芯片：

```xml
<Loadout>
  <SlotRegion>MainSub</SlotRegion>
  <SlotOccupancy>Single</SlotOccupancy>
</Loadout>
```

成对主副槽芯片：

```xml
<Loadout>
  <SlotRegion>MainSub</SlotRegion>
  <SlotOccupancy>PairedHands</SlotOccupancy>
</Loadout>
```

正式代码命名：

- 配置和契约字段：`SlotOccupancy（槽位占用方式）`
- 枚举类型：`ChipSlotOccupancy（芯片槽位占用方式）`
- 枚举值：`Unspecified / Single / PairedHands（未指定/单槽/成对主副槽）`
- 运行快照字段：`SlotOccupancy（槽位占用方式）`

`Unspecified（未指定）`只用于发现漏填，不是合法作者配置。

### 4.2 合法组合

| SlotRegion（槽位区域） | SlotOccupancy（槽位占用方式） | 结果 |
|---|---|---|
| `MainSub（主副槽区）` | `Single（单槽）` | 合法 |
| `MainSub（主副槽区）` | `PairedHands（成对主副槽）` | 合法 |
| `Special（特殊槽区）` | `Single（单槽）` | 合法 |
| `Special（特殊槽区）` | `PairedHands（成对主副槽）` | 定义错误 |

以下情况都必须产生定义错误：

- 没有填写 `SlotOccupancy`
- 显式填写 `Unspecified`
- 填写未知枚举值
- 特殊槽区选择 `PairedHands`

运行时不得把缺失或非法值猜成 `Single`。

## 五、正式运行行为

### 5.1 单槽

`Single（单槽）`只占当前选中的一个槽，保持现有普通芯片装卸、启停和切换行为。

### 5.2 成对主副槽

`PairedHands（成对主副槽）`继续使用现有根槽和镜像槽结构：

1. 可以从主槽或副槽发起装入。
2. 自动占用另一侧相同编号的槽位。
3. 对侧同编号槽不存在或已经被占用时，整次装入失败。
4. 根槽拥有直接控制权；镜像槽不能单独装卸、拖动、启用或关闭。
5. 从根槽卸下时，两侧一起清空。
6. 两侧同步启用、关闭和切换。
7. 两侧指向同一个真实芯片 Thing（游戏物品对象），不复制物品。
8. 根槽、镜像槽及其存读档关系继续使用现有中性状态结构。

### 5.3 单芯片单次结算

一枚成对占槽芯片始终是一个逻辑芯片：

- 容量占用只计算一次。
- 一次性激活费只扣一次。
- 持续费用只按一份有效表达计算。
- 芯片定义只读取一次有效来源。
- 表达效果只发布一次。

成对激活的正式顺序：

```text
根槽与镜像槽一起进入激活态
  → 只由根槽提交一次激活结算
  → 支付成功：发布一次战斗投影和一次正式启用事件
  → 支付失败：整组一起撤销，不保留单边激活
```

关闭时也只由根槽代表整组发布一次正式关闭事件。镜像槽的 `IsActive（是否激活）`状态仍可被正式读取，但不再作为第二枚芯片单独结算。

## 六、命名迁移边界

本次不兼容删除：

- `IsDualWieldBinding（是否双持绑定）`
- 配置、契约和运行快照中仅表达占槽结构的双持布尔字段
- 纯粹识别占槽关系的 `DualWield（双持）`方法名
- 界面中的“双持绑定”文字

继续保留：

- `IsBindingMirror（是否绑定镜像）`
- `BindingRoot / BindingPartner（绑定根/绑定对侧）`
- 根槽与镜像槽的存读档字段

这些名称描述的是中性关系结构，不带具体双持业务含义。

## 七、候选内容迁移

16个合法候选芯片全部显式填写：

- 15个 `Single（单槽）`
- `BDP_TestChipDualWieldRanged`填写 `PairedHands（成对主副槽）`

具体候选芯片 `BDP_TestChipDualWieldRanged`的名称和双武器表达保持不变。它作为上层业务确实可以表现为双武器，但底层 `SlotOccupancy`不保证这种效果。

临时 `DualWieldTest`排斥标签继续保留，统一留到后续互斥组字段小项处理。

故意非法的 `BDP_TestChipInvalidDefinition`继续缺少整个 `Loadout（装载配置）`块，不为本次迁移补齐。

## 八、本次不处理

- 不改变攻击数量、双武器表现或具体芯片表达。
- 不调整任何 Trion 数值，只修正同一激活费用被重复结算的错误。
- 不处理 `ExclusionTags（排斥标签）`及互斥组。
- 不处理 `WarmupTicks / WinddownTicks（切入/切出时长）`。
- 不实施事项07A的形态切换。
- 不实施事项07B的功率门槛。
- 不重命名候选库中的 Test（测试）、DevHarness（开发测试框架）或 Sample（示例）语义。

## 九、验证要求

实施时至少验证：

1. 所有合法芯片必须显式填写 `SlotOccupancy`。
2. 漏填、未指定、未知值和“特殊槽区＋成对主副槽”都会产生定义错误。
3. 单槽芯片的装卸、启停和切换行为不变。
4. 成对芯片继续占用主副同编号槽，且对侧不存在或被占用时拒绝装入。
5. 镜像槽不能独立控制，存读档后仍恢复成对关系。
6. 成对芯片容量、激活费、持续费用和表达来源均只计算一次。
7. 激活费不足时两侧一起撤销，不留下单边激活。
8. 正式源码、版本 XML 和字段全表不再包含旧布尔字段。
9. 只表示占槽结构的双持命名被中性化，真实双武器业务命名不误删。
10. 三个程序集构建成功，Core（核心程序集）继续不依赖其他本模组程序集。
