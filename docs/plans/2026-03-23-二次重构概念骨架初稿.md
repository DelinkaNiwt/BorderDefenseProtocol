# 二次重构概念骨架初稿

## 目的

这份初稿不是实现方案，不是类图，不是任务清单。

它只回答一件事：

- 二次重构时，BDP 的核心骨架应该长成什么样，才能既回到 RimWorld，又保住旧 BDP 的本质表现

## 一、总思路

二次重构不再用“微内核 + 到处挂模块 + 触发体超级协调”那种走法。

更合适的方向是：

- 事件总线 + 多核心骨架 + 局部模块化

但这里要非常明确：

- 事件总线不是中心
- 多核心才是骨架
- 模块只是在局部提供表达或规则

换句话说：

- 真值在核心
- 事件做通知
- 模块做表达
- 宿主负责投影

## 二、建议的四层骨架

### 1. 真值层

这一层只放真正持有状态的核心。

建议至少有三个核心：

- 资源核心
  - 对应 `CompTrion`
  - 真正持有 `cur / max / allocated / reserved / drain`
- 战斗体相位核心
  - 对应 `CombatBodyState`
  - 真正持有外层相位与相位时间
- 触发体装载核心
  - 对应 `CompTriggerBody` 收缩后的本体
  - 真正持有槽位、装载、侧切换、激活表达状态

这一层的原则是：

- 不重复持有同一真值
- 不靠事件推真值
- 不让镜像状态冒充 owner

### 2. 协调层

这一层只做跨核心事务编排。

例如：

- 激活战斗体
- 主动解除
- 被动崩解
- 切换芯片
- 组合成立或失效

这层可以用事件总线辅助，
但它自己也不该成为真值 owner。

更准确地说，它应该像：

- 事务导演

而不是：

- 第四个超级核心

### 3. 表达层

这一层是二次重构最重要的一层。

它不直接关心玩家按钮，也不直接关心原版 AI。

它只关心：

- 当前有哪些表达来源
- 这些表达如何被合成
- 每个表达最终要投到哪种 RimWorld 宿主

建议把表达统一分成两步：

- 表达来源
- 表达投影

#### 表达来源

来源至少包括：

- 单侧芯片表达
- 双侧合成表达
- 组合第三表达

#### 表达投影

投影目标至少包括：

- `Verb`
- `Ability`
- `Hediff`
- 必要时的特殊投射 / 生成 / 范围效果宿主

### 4. 入口与展示层

这一层只负责对外投影，不做业务 owner。

至少要分三类入口：

- 玩家手动入口
- 原版自动攻击入口
- 默认外部表面入口

以及一类展示：

- Label / Inspect / Tip / Stat / 持武绘制 / 枪口位置

这一层的原则是：

- 只读核心与表达结果
- 不再偷偷推进状态
- 不再重新计算业务规则

## 三、建议的核心对象边界

### 1. 资源核心

职责：

- 管当前值、最大值、占用值、预占用值、持续消耗
- 提供消费、锁定、释放、冻结等统一资源操作
- 对外只暴露明确的资源语义

不该负责：

- 战斗体激活逻辑
- 芯片表达逻辑
- 组合逻辑

### 2. 战斗体相位核心

职责：

- 管外层相位
- 管冷却、崩解倒计时、激活时刻
- 管相位是否合法切换

不该负责：

- 芯片装载
- 具体攻击实现
- UI

### 3. 触发体装载核心

职责：

- 管槽位
- 管装载
- 管按侧切换状态机
- 管当前哪些芯片处于激活表达状态
- 提供“当前表达来源”的查询

不该再直接负责：

- 资源正式占用写入
- 战斗体正式相位写入
- 所有对外入口生成

### 4. 组合表达核心

这里不建议再把组合散在多个地方。

建议单独做一个很薄的组合表达协调点：

- 输入：当前左右表达来源
- 输出：当前成立的第三表达列表

它不直接做按钮，不直接做 AI，不直接做伤害。

它只决定：

- 此刻多出来了哪些第三表达

## 四、建议的统一规则

### 1. 一切都从“表达来源”开始

不要再从：

- 左键攻击
- 右键攻击
- 自动射击
- 组合技按钮

这些入口去倒推业务。

正确顺序应该是：

1. 当前芯片和状态产生哪些表达来源
2. 表达来源如何合成
3. 合成结果如何投影到不同宿主
4. 各入口只读取自己的投影结果

### 2. 组合是“额外生成”，不是“覆写已有”

组合成立后：

- 不应该默认吃掉原有左右表达

更合理的默认是：

- 左右原表达还在
- 组合额外增加第三表达

除非某个明确规则指定：

- 这个组合会替代某个默认投影

### 3. 主攻击投影只是默认投影，不是全部表达

必须保留这个边界：

- 手动入口可以并列多个表达
- 自动攻击和外部默认表面只读“主攻击投影”

所以主攻击投影应该只是：

- 一个明确查询口

而不是：

- 整个表达系统的唯一结果

### 4. 宿主投影必须按类型回到 RimWorld

建议明确规则：

- 能回 `Verb` 的回 `Verb`
- 能回 `Ability` 的回 `Ability`
- 能回 `Hediff` 的回 `Hediff`
- 必须自定义的才进特殊宿主

## 五、事件总线该怎么用

建议事件总线只承担三种作用：

### 1. 状态变化广播

例如：

- 槽位激活完成
- 槽位关闭完成
- 战斗体进入激活 / 冷却 / 崩解
- 组合成立 / 失效

### 2. 横切协作触发

例如：

- 展示层刷新
- 入口层刷新
- 缓存失效

### 3. 非关键副作用通知

例如：

- 日志
- 调试
- 辅助显示

不建议事件总线做的事：

- 资源扣减真值写入口
- 发射底层唯一写入口
- 战斗体状态唯一切换入口

## 六、建议保留的旧 BDP 成熟经验

### 1. 标准远程主链尽量原版化

自定义的应继续停留在：

- 发射编排
- 发射原点修正
- 双手调度

不要重写整套命中学。

### 2. 真正绘制点与发射点共基准

视觉和发射原点不能脱钩。

### 3. 自动远程入口和自动近战入口继续分开

RimWorld 本来就是两条宿主口。

### 4. Ability 与 Hediff 继续优先回原版宿主

不要重新包装成 BDP 自己的伪能力系统。

## 七、建议的最小起步顺序

不是立刻全面重写。

但这里要先强调：

- “起步”不等于“只做表达和攻击”
- 起步真正要先建立的是整个系统的骨架边界
- 只是第一批验证闭环里，不能一下把所有业务都同时重写

所以更准确的起步顺序应该分成两层：

- 先定“全系统骨架”
- 再选“第一条验证闭环”

## 八、起步时必须同时纳入骨架的系统块

二次重构从第一天起，就必须同时考虑下面这些系统块：

### 1. 资源系统

包括：

- Trion 当前值
- 最大值
- 预占用
- 正式占用
- 持续消耗
- 冻结 / 恢复
- 可用值耗尽与总量耗尽

这一块不是表达系统的附属物。

它是独立核心。

### 2. 战斗体系统

包括：

- 外层相位
- 激活
- 主动解除
- 被动崩解
- 冷却
- 战斗体期间的身体变化

这一块也不是触发体的附属物。

它是独立核心。

### 3. 触发体装载系统

包括：

- 槽位
- 装载
- 禁用
- 双手锁定
- 切换状态机
- 特殊槽

这是触发体真正该长期持有的主业务。

### 4. 表达系统

包括：

- 单侧表达
- 双手合成表达
- 组合第三表达
- Verb / Ability / Hediff / 特殊表达投影

这是第四块关键系统，
但不是唯一中心。

### 5. 入口与展示系统

包括：

- 手动入口
- 自动远程入口
- 自动近战入口
- 默认外部表面投影
- 视觉投影

这一块必须从第一天就知道它存在，
但实现优先级可以晚于前四块。

### 6. 崩解与异常收尾系统

包括：

- Trion 可用值耗尽
- 受伤 / 手部损坏
- 卸下触发体
- 组合失效
- 表达撤销
- 资源回收

这块不能到最后再补，
因为它决定骨架是否真的闭环。

## 九、正确的起步顺序

建议按这个顺序起步：

### 阶段 A：先做“概念骨架”，不碰大量具体业务

先把全系统边界明确下来：

- 资源核心
- 战斗体相位核心
- 触发体装载核心
- 表达来源
- 表达结果
- 组合第三表达
- 主攻击投影
- 入口投影
- 崩解 / 收尾触发点

这一步不是先做攻击。

这一步是先确认：

- 哪些系统块并列存在
- 谁是 owner
- 谁只是协调
- 谁只是投影

### 阶段 B：先落“全系统最小骨架”

这一阶段就要把五块系统都立起来，
但都只做最小能力：

- 资源核心先能算：可用 / 预占用 / 正式占用 / 扣减 / 释放
- 战斗体核心先能跑：Inactive -> Active -> Cooldown
- 触发体核心先能跑：装载 / 激活 / 关闭 / 基本切换
- 表达系统先能跑：单侧近战 + 单侧远程 + 主攻击投影
- 入口系统先能跑：一个手动入口 + 自动近战 / 自动远程桥接

这里的关键是：

- 五块都出现
- 但每块都只做最小闭环

### 阶段 C：先证明“全系统最小闭环”成立

第一条验证闭环建议是：

- 有 Trion
- 能激活战斗体
- 能激活左/右单侧芯片
- 能得到正确主攻击投影
- 手动可攻击
- 自动可攻击
- 解除后资源、表达、状态都正确回收

也就是说，第一条闭环虽然攻击表现上只用单侧，
但底下其实已经同时覆盖了：

- 资源
- 战斗体
- 触发体
- 表达
- 入口
- 收尾

### 阶段 D：再加双手与组合

加入：

- 双近战
- 双远程
- 混合主攻击投影
- 双手切换关系
- 组合成立 / 失效

### 阶段 E：再加非 Verb 表达与复杂投影

加入：

- Ability
- Hediff
- 组合第三表达
- 视觉投影
- 枪口一致性
- 特殊显示
- 崩解链细节补齐

## 十、为什么第一条验证闭环不能直接上双手或复杂组合

不是因为那些不重要。

而是因为第一条闭环的任务是验证：

- 骨架边界有没有立对
- 真值有没有打架
- 收尾能不能闭环

如果第一条闭环就直接上：

- 双手调度
- 组合第三表达
- Ability
- Hediff
- 视觉投影

那一旦出问题，就很难判断到底是：

- 骨架错了
- 还是高层业务叠加太多

所以第一条闭环必须小，
但它必须同时穿过全系统。

## 十一、当前不建议立刻定死的东西

下面这些方向我认为现在还不该拍板得过细：

- 事件总线具体 API 长什么样
- 表达对象最终叫什么名字
- 组合核心是否独立成单独类还是挂在表达层服务里
- 各模块是否按文件夹还是按宿主分组

这些都可以晚一点定。

现在该先定的是：

- 核心边界
- 数据流方向
- 禁区
- 最小闭环顺序

## 十二、我当前的建议

我建议二次重构就按这个方向推进：

- 用“表达系统”替代“攻击系统”做上位骨架
- 用“资源核心 + 战斗体核心 + 触发体核心 + 表达层 + 薄协调层 + 事件总线辅助”替代超级触发体
- 用“不同宿主投影口”替代单一入口中心

如果你认可这条大方向，
下一步我就不再抽象讨论，
直接把它进一步压成：

- 二次重构概念模型 v1
- 第一阶段最小闭环范围
- 第一批必须建立的接口草案
