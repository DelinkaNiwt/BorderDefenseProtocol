# Trion资源GUI设计-第一版

## 1. 这次设计到底要解决什么

这次不是做一个“战斗体状态面板”，而是做一个**Trion 资源本体自己的 GUI**。

核心要求只有三条：

1. **以旧 BDP 的真实 Trion 语义为标准**
2. **新 BDP 里不打破系统边界**
3. **界面尽量简单：一条资源条 + 必要文字**

所以这次的最终方案是：

- `CompTrion` 继续只负责自己的资源真值
- `Trion GUI` 只画 Trion 自己能独立表达的东西
- 右上角留一个**扩展区**
- 其它系统如果以后想加图标，只能走 **GUI 扩展接口**
- 扩展是可插拔的，**不是 Trion 本体的一部分**

---

## 2. 旧 BDP 真实语义整理

按旧 BDP 真实实现，Trion 这几个量的关系是：

- `Cur`：当前池子里还剩多少总量
- `Allocated`：已经被正式锁住、不能自由挪用的量
- `Available = Cur - Allocated`
- `ReservedAllocation`：预测占用，只是“将来可能会锁多少”，还不算正式锁定

旧 BDP 的关键行为：

- 未激活时：`ReservedAllocation` 用来表达“如果现在开战斗体，大概要占多少”
- 激活时：正式执行 `Allocate(...)`，`Allocated` 增加，但 `Cur` 不会因为“锁定”而减少
- 战斗中的真实消耗：通过 `Consume/TryConsume` 扣 `Cur`
- 崩解判断看的是 `Available <= 0`，不是单看 `Cur <= 0`
- 正常解除：释放 `Allocated`
- 强制崩解 / 紧急脱离：直接耗尽可用部分，锁定部分不按正常释放路线回退

---

## 3. 新旧 BDP 映射关系

| 旧 BDP 语义 | 新 BDP 对应 | 说明 |
| --- | --- | --- |
| `Cur` | `ITrionReader.Cur` | 当前总量 |
| `Max` | `ITrionReader.Max` | 最大容量 |
| `Allocated` | `ITrionReader.Allocated` | 已正式锁定量 |
| `ReservedAllocation` | `ITrionReader.Reserved` | 预测占用量 |
| `Available` | `ITrionReader.Available` | 当前可自由使用量 |
| 持续消耗总速率 | `ITrionReader.TotalDrainPerDay` | 以日为基准登记，GUI 再换算 |
| 自然恢复速率 | `CompTrion/Reader 正式补出 RecoveryPerDay` | GUI 需要读，不该偷摸 `Props` |
| 恢复冻结 | `ITrionReader.Frozen` | Trion 自身状态 |

这次还要明确一条：

- **“战斗体激活图标”“紧急脱离图标”不再属于 Trion 核心语义**
- 它们以后如果要显示，应该通过 **Trion GUI 扩展区** 来挂

---

## 4. 边界原则

### 4.1 `CompTrion` 必须保持独立

`CompTrion` 不应该依赖：

- `CompTriggerBody`
- `CompCombatBodyHost`
- `CombatBodySessionService`
- 任何别的业务协调对象

它只应该维护：

- 当前量
- 最大量
- 锁定量
- 预测量
- 恢复冻结
- 持续消耗登记

### 4.2 Trion GUI 也不能偷摸内部对象

Trion 主条只允许读：

- `TrionSurfaceAccess`
- `CompTrion` 自己正式暴露出来的读口

不允许：

- 直接 `TryGetComp<CompTriggerBody>()`
- 直接进 `CombatBodySessionService` 看内部字段
- 从 Trigger / CombatBody 内部状态“顺手摸个真值”

### 4.3 右上角扩展区可以存在，但它属于 GUI 组合层

扩展区的定位是：

- Trion 主条右上角预留一小块区域
- 这块区域允许其它系统注册“徽标/图标”
- 这些图标不是 Trion 真值
- Trion 主条只负责排版和绘制入口，不负责理解扩展业务

换句话说：

- **Trion 主条独立**
- **右上角是可插拔 GUI 扩展位**

## 5. 最终界面设计

## 5.1 主布局

- 左上：`可用 / 总量`
- 上中：
  - 未锁定时显示 `恢复 x/天`
  - 存在正式锁定时显示 `消耗 x/秒`
  - `恢复冻结` 图标紧跟在这段文字后面
- 右上：预留扩展区
- 下方：不放任何文字
- 中央主体：一条几乎铺满宽度的 Trion 资源条

### 5.2 判定规则

Trion GUI 的核心切换**不依赖战斗体对象**，而依赖 Trion 自己的账本：

- `Allocated <= 0`：按“未正式锁定”态显示
- `Allocated > 0`：按“已正式锁定”态显示

这样 `CompTrion` 仍然完全独立。

### 5.3 资源条语义

#### A. 未正式锁定

- 填充长度表示 `Cur / Max`
- 在已填充区域内部画一根分隔线
- 分隔线位置表示：**预测锁定边界**
- 计算方式：`Cur - Reserved`
- 分隔线右侧那一小段已填充区，表示“如果现在正式锁定，会被占掉的那部分”

#### B. 已正式锁定

- 填充长度仍表示 `Cur / Max`
- 左侧 `Allocated` 区间画成锁定色块
- 分隔线仍然保留
- 分隔线位置表示：**正式锁定边界**
- 分隔线右侧到当前填充末端，表示仍可继续消耗的当前量

### 5.4 上方文字规则

- 左上永远显示：`可用 / 总量`
- 上中永远显示资源变化速率
- 恢复用 **天**
- 消耗用 **秒**

换算规则：

- 恢复：直接显示 `RecoveryPerDay`
- 消耗：`TotalDrainPerDay / 1000`
  - 因为 RimWorld 一天 `60000 ticks`
  - 一秒 `60 ticks`
  - 所以“每秒” = “每天 / 1000”

### 5.5 冻结图标规则

- `Frozen = false`：显示未冻结图标
- `Frozen = true`：显示冻结图标
- 图标跟在“恢复 / 消耗”文字后面，一起居中

### 5.6 右上扩展区规则

右上扩展区是空位，不是核心信息。

默认情况：

- 没有 provider 时，右上角什么都不显示

有扩展时：

- 由外部 provider 提供一组小图标
- Trion 主条只负责从右向左排
- 每个图标带自己的 tooltip

扩展区不允许承载：

- 多行文字
- 复杂按钮
- 反向改 Trion 真值的逻辑

建议只放：

- 小图标
- 小徽标
- 短 tooltip

## 7. 为什么这样设计最稳

优点很直接：

- 旧 BDP 资源语义能保住
- 新 BDP 系统边界不会被打穿
- `CompTrion` 仍然是一个可独立复用的资源宿主
- 同一套 GUI 可以复用到没有 Trigger / CombatBody 的单位
- 甚至未来只要宿主有 gizmo 入口，非 Pawn 也能复用主条

一句话总结：

> **Trion 主条只表达 Trion，自身保持独立；右上角扩展区只负责“挂别人”，不把别人并进 Trion 本体。**

## 8. 当前实现裁定

本次正式落地范围分两层：

### 第一层：必做

- Trion 主条
- `可用 / 总量`
- `恢复 x/天 / 消耗 x/秒`
- 冻结图标
- 未锁定预测分隔线
- 已锁定色块 + 分隔线
- 右上扩展区骨架

### 第二层：条件式接入

像下面这些，不属于 Trion 主条核心，只有在**其它系统已经提供正式真值**时才允许挂扩展：

- 战斗体激活图标
- 紧急脱离图标
- 其它跨系统状态徽标

如果其它系统没有正式接口，就先不接，不准从内部对象硬摸。
