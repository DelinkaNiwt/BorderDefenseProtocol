# 战斗体切换闭环重建 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在新 BDP 现有主链上补齐战斗体切换闭环，让“进入 / 主动解除 / 被动崩解 / 可选紧急脱离附加段 / 宿主恢复 / GUI 映射”全部回到正式事务里。

**Architecture:** 继续以 `CompCombatBodyHost -> CombatBodyService -> CombatBodySessionService` 为主链，不新增第四个真值 owner。缺口 1 与缺口 2 一起落地：由 `PawnCombatBodyBridge` 承接宿主事务，由 `CombatBodySnapshotService` 承接快照与恢复；退出语义收束为“主动解除 / 被动崩解”，紧急脱离只作为被动崩解链中的可选附加段，通过一个窄协调层解析，不让 Trigger / 芯片 / GUI 互相硬访问。

**Tech Stack:** C#、RimWorld/Verse、现有 CombatBody/Trigger/Trion surface、XML Def、PowerShell smoke tests、`dotnet msbuild`

---

## 范围护栏

- 本计划只补 `BDP` 直辖事务：宿主切换、快照/恢复、退出语义、崩解收尾、紧急脱离解析、玩家入口与 GUI 映射。
- 不重做 `Trion`、`Trigger`、`Hediff_CombatBodyActive` 的内部机制；它们继续做各自真值或表现承载。
- 不把战斗体做成第四个 owner；`Trion / CombatBodyState / TriggerBody` 三真值边界不变。
- 不把 GUI 写成业务判断器；GUI 只读正式 surface / 正式解析结果。
- 不做“大管理器拆分”；保留最小结构：`CompCombatBodyHost`、`HostState`、`PawnCombatBodyBridge`、`CombatBodySnapshotService`、`CombatBodyEmergencyEscapeResolver`。

**Step 4：把退出事务收成单入口**

- 先接收顶层退出语义

### Task 5：补完整退出/恢复链，让主动解除与被动崩解共用宿主恢复闭环

**Files:**
- Modify: `Source/BDP/Core/CombatBody/Bridge/PawnCombatBodyBridge.cs`

- Modify: `Source/BDP/Core/CombatBodySession/CombatBodyExitTransaction.cs`
- Modify: `Source/BDP/Core/CombatBodySession/CombatBodySessionService.cs`
- Modify: `Source/BDP/Core/CombatBodySession/CombatBodySessionTrionBinding.cs`

**Step 1：把宿主恢复顺序写实**

`RestoreFromCombatBody()` 内部固定顺序：
1. 撤掉战斗体前台与战斗期残留
2. `SnapshotService.Restore`
3. 做最终 cleanup
4. 清空 `HostState`

其中 `SnapshotService.Restore` 的恢复顺序固定为：
1. 穿戴
2. 携带物
3. Need
4. Hediff

**Step 2：主动解除走正式链**

主动解除时顺序固定：
1. 释放战斗体锁定资源
2. 关闭全部 Trigger 局部激活
3. 恢复宿主
4. 进入 `Cooldown` 或 `Inactive`
5. 广播状态变化

**Step 3：被动崩解走统一收尾链**

被动崩解时顺序固定：
1. `Active -> Collapsing`
2. 播放崩解表现期
3. 到时后调用 `FinalizeCollapse()`
4. 进入统一退出事务
5. 再决定是否插入“紧急脱离附加段”

### Task 6：补紧急脱离解析层，切开它与 Trigger / 芯片 / GUI 的硬耦合

**Files:**

**Step 1：做一个窄协调点，不做新 owner**

`CombatBodyEmergencyEscapeResolver` 只负责三件事：
- 读取 Trigger 正式读取口
- 读取芯片正式能力声明
- 产出只读解析结果

它不负责：
- 改 CombatBodyState
- 改 Trigger 真值
- 自己执行退出链

**Step 2：把“紧急脱离”落成被动崩解附加段**

`CombatBodyExitTransaction` 在处理“被动崩解”时：
- 先问 resolver 是否存在紧急脱离能力
- 有则插入紧急脱离附加段
- 无则直接走统一宿主恢复

这一步只改变被动崩解链内部细节，不改变本次退出的顶层分类。

**Step 3：把 Trion 额外消耗与后果留在附加段**

紧急脱离相关的额外 `Trion` 处理、位置处理、日志或后果，都只在附加段里做；不要再冒充成一个独立退出模式。
