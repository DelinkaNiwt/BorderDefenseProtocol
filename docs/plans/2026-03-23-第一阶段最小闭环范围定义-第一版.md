# 第一阶段最小闭环范围定义（第一版）

## 目的

这份文档只回答一个问题：

- 二次重构第一阶段到底做到哪里算“可以起步写代码”

它不是长期路线图。

它只负责把第一阶段的边界钉死，避免后面又因为想一步到位而失控。

## 一、第一阶段的完成标准

第一阶段完成，不等于 BDP 重构完成。

第一阶段完成，指的是下面这条最小闭环被真正打通：

1. 小人有 Trion 资源语义
2. 小人能激活战斗体
3. 触发体能装载并激活 Main / Sub 基本芯片
4. 激活后的芯片能产出基础表达
5. 表达能投影成可手动使用、可自动使用的原版可理解入口
6. 解除或异常结束后，状态能正确收尾

只要这条闭环不通，后面再多功能都不算稳。

## 二、第一阶段必须打通的六块系统

### 1. 资源系统

第一阶段必须做到：

- 有 `Cur / Max / Available` 基本读值
- 有正式占用 `Allocated`
- 有预占用 `Reserved`
- 有基本一次性消耗
- 有持续消耗聚合读值
- 有释放逻辑
- 有“可用值耗尽”边界通知

第一阶段暂不追求：

- 所有高级恢复规则一次补全
- 所有 UI 显示细节一次补全
- 所有极端异常路径一次补全

这里的标准是：

- 资源语义必须真
- 资源表现可以先朴素

### 2. 战斗体系统

第一阶段必须做到：

- `Inactive / Active / Cooldown` 三个相位真能跑通
- 能手动激活
- 能手动解除
- 资源不足时能拒绝激活
- 解除时能走正确收尾

第一阶段可以先弱化：

- `Collapsing` 的完整演出细节
- 所有受击关联变化
- 所有无敌窗口和复杂状态分支

这里的标准是：

- 相位切换必须真
- 复杂表现细节可以后补

### 3. 触发体装载系统

第一阶段必须做到：

- Main / Sub 基本槽位存在
- 芯片能装入与卸下
- Main / Sub 能分别激活
- 已激活槽位能切换
- 装载状态能被表达系统读取

第一阶段明确不强求：

- 所有特殊槽一次到位
- 所有双手锁定细节一次补全
- 所有 GUI 操作体验一次补全

这里的标准是：

- 装载和激活规则必须真
- GUI 不是当前目标

### 4. 表达系统

第一阶段必须做到：

- 能收集当前激活芯片的表达来源
- 能区分单侧近战表达和单侧远程表达
- 能给出当前默认主近战投影
- 能给出当前默认主远程投影
- 能把表达投向 `Verb` 宿主

第一阶段先不要求：

- Ability 全链路落地
- Hediff 全链路落地
- 组合第三表达真落地
- 多形态表达全覆盖

这里要特别强调：

- 第一阶段不是只做“攻击系统”
- 而是先把“表达 -> 投影 -> 宿主”这条基础通路打通

### 5. 入口与展示系统

第一阶段必须做到：

- 至少 1 条玩家手动入口
- 自动远程入口桥接
- 自动近战入口桥接
- 一个默认外部表面投影

第一阶段可以先不追求：

- 所有按钮样式与信息卡细节
- 所有绘制与枪口表现细节
- 所有观察展示一次补全

这里的标准是：

- 入口必须回到 RimWorld 原版可理解通道
- 展示先够用，不追求漂亮

### 6. 崩解与收尾系统

第一阶段必须做到：

- 主动解除时撤销表达
- 主动解除时释放资源
- 主动解除时恢复宿主状态
- 入口投影能清理干净
- 装载相关状态不会残留脏数据

第一阶段可以暂缓：

- 完整被动崩解演出
- 所有复杂组合失效回滚
- 所有伤残导致的局部功能收缩

这里的标准是：

- 收尾必须完整
- 不允许留脏状态

## 三、第一阶段只留接口、不真做的东西

这些东西第一阶段可以先留位置，但不强行落地：

- Ability 投影
- Hediff 投影
- 组合第三表达
- FireMode 深化
- 多形态
- 特殊槽完整规则
- 因子值的具体业务作用
- 独立测试模组
- 大部分展示优化

原则是：

- 先留接入口
- 不抢跑做假完整

## 四、第一阶段明确暂缓的旧功能

下面这些不是“不重要”，而是“现在先不做”：

- 复杂组合技
- Ability / Hediff 芯片完整链路
- 高级资源恢复细节
- 复杂枪口与绘制表现
- 全量调试展示
- 外围扩展内容

暂缓原因不是忽略它们，
而是第一阶段先保住主闭环，不让范围炸开。

## 五、六块系统的第一阶段 owner 约束

### 1. `CompTrion`

第一阶段只做资源真值 owner。

不让它越界去做：

- 战斗体相位 owner
- 触发体装载 owner
- 表达规则 owner

### 2. `CombatBodyState`

第一阶段只做战斗体相位 owner。

不让它越界去做：

- 资源记账
- 芯片装载
- 表达合成

### 3. `CompTriggerBody`

第一阶段只做：

- 装载 owner
- 局部激活表达 owner
- 局部切换协调

不再继续膨胀成全能核心。

### 4. 表达系统

第一阶段只负责：

- 读当前来源
- 按规则给出结果
- 把结果投向宿主

不负责：

- 自己持有资源真值
- 自己持有战斗体相位真值

### 5. 入口与展示系统

第一阶段只负责读取结果并投给外界。

不负责倒过来持有真值。

### 6. 崩解与收尾系统

第一阶段不单独造一个大核心。

它更像一条跨系统收尾事务链：

- 关表达
- 释放资源
- 恢复宿主
- 清入口

## 六、第一阶段的验收问题

后面真正开写代码时，每做完一轮都至少反问这几件事：

1. 资源、战斗体、触发体三类真值有没有又被混起来
2. 表达系统是不是还贴着 RimWorld 宿主在走
3. 自动远程和自动近战是不是还保留分层
4. 手动入口和自动入口是不是被错误合流
5. 主动解除后是否真的没有残留状态
6. 这次新增抽象是不是确实让代码更容易理解，而不是更漂亮

## 七、当前结论

第一阶段真正要保的是：

- 真值边界清楚
- 最小闭环打通
- 收尾完整
- 接口留得住后续扩展

第一阶段不该追求的是：

- 功能全覆盖
- 表现全补齐
- 架构一次定终局
