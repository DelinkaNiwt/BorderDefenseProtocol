# 第一阶段接口草案（第一版）

## 目的

这份文档不是最终代码接口。

它的作用是：

- 把第一阶段最小闭环真正需要的接口先列出来
- 明确每个接口属于哪块系统
- 明确哪些接口第一阶段必须做成真东西
- 明确哪些接口第一阶段只先留口

这里统一使用：

- `Main = 右`
- `Sub = 左`

阅读约定：

- 下面每个接口都尽量用最直白的话说明“它是什么、它管什么”
- 代码块里的注释不是装饰，而是以后真正写代码时也应保留的风格参考
- 默认假定读者可能不是专业程序员，所以优先解释作用，再谈抽象

## 一、第一阶段接口目标

第一阶段要打通的是一个穿过全系统的最小闭环：

- 有资源
- 能激活战斗体
- 能激活 Main/Sub 基本芯片
- 能产出单侧近战 / 远程表达
- 能给出主攻击投影
- 玩家手动能攻击
- 自动近战 / 自动远程能攻击
- 主动解除后能正确收尾

所以接口草案也只围绕这条闭环来定。

## 三、资源系统接口

### 1. `ITrionState`

职责：

- 提供统一资源读写语义

建议接口：

```csharp
public interface ITrionState
{
    // 当前 Trion 总量
    float Cur { get; }
    // 当前最大 Trion 容量
    float Max { get; }
    // 已经被正式占用、不能拿来随便消耗的量
    float Allocated { get; }
    // 预留给战斗体或芯片配置的量，还不等于正式占用
    float Reserved { get; }
    // 当前真正还能自由使用的量
    float Available { get; }
    // 当前所有持续消耗源聚合后的总消耗速度（按天）
    float TotalDrainPerDay { get; }
    // 是否冻结自然恢复
    bool Frozen { get; }

    // 只检查够不够，不扣
    bool CanAfford(float cost);
    // 全额扣除或完全不扣
    bool TryConsume(float cost);
    // 尽力消耗，直到可用值见底
    void ConsumeUntilDepleted(float amount);
    // 更新预占用
    void SetReserved(float amount);
    // 把预期占用变成正式占用
    bool Allocate(float amount);
    // 释放正式占用
    void Release(float amount);
    // 注册持续消耗源
    void RegisterDrain(string key, float perDay);
    // 取消持续消耗源
    void UnregisterDrain(string key);
    // 读取当前聚合消耗注册表快照，方便调试、显示、测试
    IReadOnlyDictionary<string, float> GetDrainSnapshot();
    // 设置是否冻结恢复
    void SetFrozen(bool frozen);
}
```

第一阶段：

- 必须真做

### 4. `IBdpFactorValue`

职责：

- 提供一个“当前因子值”

这里的“因子”按你刚纠正后的意思来定：

- 它不是一张修正表
- 它就是一个统一值
- 业务逻辑自己决定怎么解释和应用这个值
- 大概率主要和 Trion 天赋 / 资质 / 基因相关

可以先把它理解成：

- 一个统一“因子强度值”
- 平时默认是中性值
- 真正有天赋、状态、模式变化时，再让它偏移

也就是说，它更像：

- 一份统一输入值

而不是：

- 接口层预先替业务拆好一大堆专用字段

建议接口：

```csharp
public interface IBdpFactorValue
{
    // 当前统一因子值，默认 0
    float Value { get; }
}
```

读法约定：

- 默认值是 `0`
- 它本身不规定“+1%”还是“乘 2 倍”
- 具体怎么影响结果，由各业务按自己的规则解释

使用原则：

- 接口层只负责给出这个值
- 业务层负责解释这个值
- 不要在接口层提前替所有业务设计专用字段
- 真正需要统一换算规则时，再单独补一层规则，不提前臆造

使用示例：

- 伤害逻辑可以把它当倍率偏移量
- 子弹数量逻辑可以把它当额外加成值
- 判定逻辑可以把它当概率修正量
- 策略逻辑也可以只把它当阈值判断依据

关键点只有一个：

- 同一个因子值，可以被不同业务按不同方式解释
- 但“这个值从哪来”必须统一

第一阶段：

- 必须定义
- 默认实现为 `0`
- 暂时不要求立刻有具体天赋功能

## 十三、哪些对象应考虑参与“因子值”的组装

这里不再按“谁实现复杂因子接口”理解。

更准确的说法是：

- 未来哪些来源可能会共同决定这个统一因子值

我当前判断，优先是这些来源：

### 1. Trion 天赋 / 基因 / 相关资质

原因：

- 这就是当前最接近你真实需求的来源
- 很多修正大概率就从这里来
- 也最符合“平时默认中性，有时整体增强或削弱”的感觉

### 2. 芯片形态

原因：

- 它可能对动作、参数、表现带来额外修正
- 例如更偏范围、更偏数量、更偏耐久

### 3. FireMode

原因：

- 它已明确会影响伤害、连射、速度等结果
- 很适合通过统一因子值影响结果，而不是把判断散到各处

### 4. 战斗体状态

原因：

- 某些战斗体状态可能整体改变结果表现
- 例如异常态、强化态、崩解前态

### 5. 临时状态效果

例如：

- Hediff
- Buff
- Debuff

原因：

- 它们适合作为额外修正来源，而不是硬塞进每条业务判断
- 如果以后有“命中下降”“范围提升”之类状态，也更自然

### 6. 测试扩展内容

原因：

- 后置测试模组可以借此模拟极端修正情况
- 方便在游戏里验证主模组是否真的支持自然扩展

当前不建议把下面这些直接当作因子总入口 owner：

- `TrionState`
- `CombatBodyPhaseState`
- `TriggerLoadoutState`

因为它们是真值核心，
不应同时兼任“因子来源总入口”。

更直白地说：

- 真值系统负责“当前事实是什么”
- 因子值负责“这些事实综合起来给业务一个统一输入”
- 两者有关联，但不要混成同一个东西
