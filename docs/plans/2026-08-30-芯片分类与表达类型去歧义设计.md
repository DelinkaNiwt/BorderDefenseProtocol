# BDP 芯片分类与表达类型去歧义设计

## 1. 目标

整理 BDP（Border Defense Protocol，边境防御协议）中芯片分类、表达条目类型和运行时输出通道的边界，消除 `Category`（分类）、`Kind`（类型）以及“能力/被动/状态”等中文和技术标识之间的混淆。

本次同时调整芯片业务分类：

- 武装类保留。
- 防护类保留。
- 原状态类并入现能力类，现能力类改名为“通用技能类”。
- 原被动类改名为“配件类”。
- 配件类豁免默认的同侧激活控制冲突，但不豁免显式激活互斥组。

本次不考虑旧存档、旧 DefName（定义名）或旧技术 API（程序接口）的兼容。

## 2. 已确认的现状

### 2.1 `Category`（分类）

`ChipCategoryDef` 和 `Profile.Category` 表示芯片制造层的主分类，当前用于：

1. 制造窗口分组和筛选。
2. 芯片组合兼容性校验。
3. 制造成品和运行时快照保存芯片分类身份。
4. Content（内容层）向 Core（核心层）提供特殊激活控制分类。

因此 `Category` 语义本身准确，不改名为 `Classification`。只更新分类内容、分类 DefName、分类语言和相关说明。

### 2.2 当前芯片分类

当前芯片分类及目标分类如下：

| 当前芯片 | 当前分类 | 目标分类 |
| --- | --- | --- |
| 小行星、美特拉、毒蛇、猎犬、弧月、朱鹮 | 武装 | 武装类 |
| 光魂、护盾、常驻型自动能量护盾 | 防护 | 防护类 |
| 蚱蜢、铅弹 | 能力 | 通用技能类 |
| 变色龙 | 状态 | 通用技能类 |
| 旋空、紧急脱离、铅弹·改 | 被动 | 配件类 |

目标正式分类为四类：

```text
武装类
防护类
通用技能类
配件类
```

建议技术 DefName 为：

```text
BDP_ChipCategory_Weapon
BDP_ChipCategory_Defense
BDP_ChipCategory_GeneralSkill
BDP_ChipCategory_Accessory
```

`BDP_ChipCategory_Status` 退役，不再被正式内容引用。

### 2.3 芯片表达中的 `Kind`

配置层 `ChipExpressionEntryTypeConfig` 当前定义五种值；正式条目层有对应的 `ChipExpressionEntryType`：

| 当前值 | 机制用途 |
| --- | --- |
| `PrimaryVerb` | 生成主攻击入口，沿用原版 Verb（攻击动作）链；近战/远程由攻击模式和相关字段决定。 |
| `SecondaryVerb` | 生成副攻击入口；主副身份最终由 `VerbAttackRole`（攻击入口主副角色）承载。目前正式 XML 没有使用。 |
| `Ability` | 绑定原版 Ability（能力按钮），由表达系统同步到 Pawn 的 AbilityTracker（能力追踪器）。 |
| `Hediff` | 表达结果成立时维护 Hediff（健康状态）；可选择自动模式或由能力按钮控制。 |
| `Passive` | 不生成按钮或自动 Hediff，通过稳定的被动身份键向被动消费方发布行为或远程增强。 |

当前正式 XML 实际使用 `PrimaryVerb`、`Ability`、`Hediff`、`Passive`；`SecondaryVerb` 仅有代码支持。

表达条目 `Kind` 与芯片 `Category` 是正交关系。例如当前新“铅弹”是：

```text
Category = 通用技能类
Kind     = Passive
```

这表示它在制造层属于能力类，但在表达层通过被动远程增强声明发挥作用，二者不矛盾。

### 2.4 运行时结果类型

运行时的 `ExpressionOutputChannel` 不是配置层条目类型，而是结果输出通道：

```text
Verb
Ability
Hediff
Passive
```

`PrimaryVerb` 和 `SecondaryVerb` 在这里都会归入 `Verb`，主副身份另存为 `VerbAttackRole`。

为去掉 `Kind` 的泛化含义，已改为：

```text
ChipExpressionEntryKindConfig → ChipExpressionEntryTypeConfig
ChipExpressionEntryKind       → ChipExpressionEntryType
Kind                          → EntryType

ExpressionResultKind          → ExpressionOutputChannel
ResultKind                    → OutputChannel
```

`ExpressionPublishedChannelKind`（表达发布通道类型）保留其“发布观察快照通道”的语义；如实现时发现它与新的输出通道完全重复，再在同一批重命名中合并，不能只做机械替换。

## 3. Hediff 生命周期与持续消耗边界

当前实现中，Hediff 表达结果只要随芯片成立，`DefaultExpressionHediffHostSynchronizer`（默认 Hediff 宿主同步器）就会添加 Hediff；`ExpressionSustainDrainService`（表达持续消耗服务）也只按正式表达结果是否成立登记持续消耗。因此现状是“芯片/表达式驱动”，不是“实际 Hediff 驱动”。

本次引入通用的 Hediff 控制模式：

- `Automatic`（自动模式）：保持现有语义，正式 Hediff 结果成立时由通用同步器添加，结果失效时移除。
- `AbilityButton`（能力按钮模式）：正式结果只负责声明能力按钮和目标 Hediff；Hediff 的添加/移除由能力按钮组件切换，通用同步器不主动添加。
- 当来源芯片失效时，通用同步器仍会清理该表达宿主留下的按钮模式 Hediff。这是无来源状态的安全回收，不改变按钮模式在芯片激活期间由玩家控制的语义。

持续消耗的正式规则统一为：

- Hediff 表达必须先有实际的 BDP 表达宿主 Hediff，才进入持续消耗对账。
- 其它表达通道继续按正式结果可用性对账。
- 这样能力按钮尚未打开 Hediff 时不消耗；Hediff 被添加后才开始消耗；按钮关闭或来源芯片失效后停止消耗。

该机制放在 Core（核心层），通过 AbilityDef 组件配置目标 HediffDefName（定义名），不包含变色龙名称或隐身业务判断。

## 4. 变色龙行为调整

变色龙当前为：

```text
Category = Status
Kind     = Hediff
```

当前行为是芯片激活和关闭直接控制 Hediff 生命周期。

目标为：

```text
Category = GeneralSkill
Kind     = Hediff + Ability
```

激活芯片只负责让能力按钮出现；玩家通过能力按钮手动切换变色龙 Hediff。Hediff 表达本身仍保留为正式 Hediff 通道，但声明 `AbilityButton` 控制模式；另有一个 Ability 表达条目绑定配置化的通用 Hediff 切换效果。实现时继续复用现有 Ability 宿主同步、Trion（资源）扣费和表达结果绑定机制。

变色龙的 Hediff Def、隐身组件、隐身效果和攻击后自动关闭服务保持不变。攻击后自动关闭仍由现有 Hediff 组件触发来源芯片停用；来源芯片停用后的通用安全回收会移除变色龙 Hediff。

## 5. 配件类激活控制

当前“被动类”特殊规则由 Content 的分类提供器识别分类，再交给 Core 的触发器切换逻辑处理。目标行为为：

- 配件类之间可以绕过默认的同侧激活控制冲突。
- 配件类与普通芯片之间也不因同侧默认控制范围而互相阻塞。
- 显式声明相同 `ActivationExclusionGroup`（激活互斥组）的芯片仍然冲突，显式规则优先。
- 成对占用主副槽的芯片仍按其物理占用范围处理，不因普通配件规则改变。

Core 已使用 `HasIndependentActivationControl`（是否拥有独立激活控制范围）表达这一中性机制能力，由 Content 把 `BDP_ChipCategory_Accessory` 映射到该能力。这样业务分类名称变化不会再次污染 Core 的机制语义。

## 6. 其他术语统一原则

只处理真正产生跨层混淆的名称，不全局改写所有 `Kind`：

- `GunClass` 改为 `ArmamentForm`（武装构型），例如 `BDP_GunClass_Revolver` 改为 `BDP_ArmamentForm_Revolver`。
- 玩家可见“武装型”统一为“武装构型”。
- `WeaponMode` 保留现名；它表示近战/远程攻击模式，不表示武装构型。
- `ModeKey` 保留现名；它表示盾、大剑等芯片内部形态，不表示近战/远程。
- `PassiveKey` 已改为 `PassiveIdentityKey`（被动身份键），强调它是稳定查找身份，不是芯片分类。
- `RangedModuleAugmentations` 改为远程增强声明相关名称，和当前结果自身的 `RangedModules` 分开。
- `RoleKey` 改为表达角色键；`VerbAttackRole` 改为攻击入口主副角色相关名称。
- `TriggerCategoryDef`、投射物路径类型、预览绘制类型等语义已经明确的局部名称不因出现 `Category` 或 `Kind` 就强制改名。

所有玩家可见新文案和重写文案放入简体中文语言包，XML 默认值只保留必要回退文本；代码不新增硬编码玩家文案。

## 7. 实施边界和验证

实施顺序：

1. 先更新四类芯片分类 Def、语言包和全部内容引用。
2. 再更新 Core/Content 中表达条目类型与运行时输出通道名称。
3. 更新配件类独立激活控制接口、注册表和调用点。
4. 增加通用 AbilityButton Hediff 控制和实际 Hediff 持有态持续消耗。
5. 将变色龙接入通用能力按钮切换效果，同时保持原有 Hediff/隐身/攻击后关闭机制。
6. 清理旧标识、旧注释、旧测试名称和旧文档。

验证至少包括：

- XML/Def 引用完整性和旧 DefName 残留扫描。
- 四类芯片分类与制造窗口分组检查。
- `PrimaryVerb`、`Ability`、`Hediff`、`Passive` 的表达通道检查。
- 变色龙能力按钮出现、手动赋予 Hediff、再次操作关闭 Hediff，以及无 Hediff 时不产生持续消耗的逻辑测试。
- 配件类同侧并存、普通芯片同侧互斥、显式互斥组仍生效的边界测试。
- Core 隔离、Content 构建、Development 边界和发布检查。
- 最终进入游戏验证能力按钮与 Hediff 生命周期；仅编译通过不能代替该项验证。
