# BDP 芯片功能语义标准化落地实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 把已经确认的玩家功能语义、公共属性、信息组、子功能和来源读取规则落实为统一的开发者 XML（可扩展标记语言）契约，使芯片制造台、触发器装配台和第三方扩展读取同一份解析结果，同时保持现有游戏功能行为不变。

**Architecture:** `Features` 只显式声明“是什么功能”和结构关系；`Sources` 只定位权威业务数据并选择只读投影 Worker；`Groups` 保存同一功能内部的成组信息；功能本身与具体信息组都可声明一层 `Subgroups`，用于表达分别归属于整个功能或某个组的次级信息；`Children` 只保存完整子功能。子组不得继续嵌套。Core.dll 只提供中性契约、校验、解析和只读结果，Content.dll 提供 BDP 正式业务来源与标准语义 Def，Development.dll 提供扩展示例和诊断。游戏执行继续读取原版或 BDP 权威定义，不读取功能信息结果。

**Tech Stack:** RimWorld 1.6、C# 7.3、.NET Framework 4.8、Verse Def/XML、PowerShell 静态契约测试、MSBuild 编译验证。

**实施状态（2026-09-28）：** 用户已批准完整计划；Task 1–12 已完成实现与静态验证，37 项发布门禁通过。收到 RimWorld 1.6.4871 rev591 的实机日志后发现运行时 DLL 与新 Def/XML 不一致；现已按 Release 配置重建 Core、Content、Compatibility、Development 四个程序集到模组正式输出目录。重启游戏并确认 BDP 类型/字段错误消失仍待验证。最终实现说明与边界修正见文末“实施结果”。

## 二、最终开发者契约

```xml
<Features>
  <li>
    <Id>稳定功能实例Id</Id>
    <Feature>玩家语义FeatureDef</Feature>
    <LabelKey>可选实例名称语言键</LabelKey>
    <Sources>
      <!-- 只写来源定位和读取路线，不写展示值副本。 -->
    </Sources>
    <Groups>
      <!-- 同一功能内部的可重复成组信息；每组可按需包含组级 Subgroups。 -->
    </Groups>
    <Subgroups>
      <!-- 归属于整个功能的一层次级信息，不需要伪造中间父组。 -->
    </Subgroups>
    <Children>
      <!-- 完整、独立的玩家子功能。 -->
    </Children>
  </li>
</Features>
```

固定职责：

```text
Feature   = 这是什么玩家功能
Sources   = 去哪里读取权威信息、用哪种投影读取
Groups    = 同一功能内部的多套关联参数
Feature.Subgroups = 归属于整个功能的一层次级关联信息
Group.Subgroups   = 归属于某个具体信息组的一层次级关联信息
Children  = 当前功能包含的完整子功能
面板      = 从解析结果中选择展示内容、顺序、图标、图表和场景名称
```

### 信息树归属层次（本轮确认）

芯片信息有外层归属与功能内部结构两层，不得把两者混为一个树：

```text
芯片根节点
├─ 芯片本身的一般信息
├─ 根级功能语义树（可选）
├─ 根级扩展引用（可选）
└─ 形态上下文
   ├─ 该形态的功能语义树（可选）
   ├─ 该形态的扩展引用（可选）
   └─ 姿态上下文
      ├─ 该姿态的功能语义树（可选）
      └─ 该姿态的扩展引用（可选）
```

- 功能语义树与扩展引用在各自归属节点并列；组合技信息不能混进芯片功能树。
- `ComboDef`（组合技定义）本身拥有独立功能树；来源芯片只接收指向该定义或当前正式结果的中性引用，不复制组合技功能树，不回写芯片定义。
- 根级、形态级、姿态级引用通过稳定上下文键归属。当前上下文仍可用 `Contexts` 列表与 `ParentContextKey` 表示，不为本需求强制改成递归对象图。
- 静态 `ComboDef` 来源声明只证明“定义有关联”，不证明当前组合已经正式匹配；正式组合结果引用只能从既有已发布只读快照产生，绝不为展示触发表达重建。
- Core 只保存中性扩展引用（提供方键、引用类型键、引用目标键和可选上下文键）；组合技反向查找、引用的定义范围和运行时关联由 Content 适配。面板可自行决定是否展示这些引用。

额外效果始终是嵌套子组，不是与功能根部信息组并列的组。若效果由整个功能产生，放在 `Feature.Subgroups`；若只由某个攻击方式、防护规则或机动方式产生，放在该组的 `Group.Subgroups`。不得为了容纳效果伪造父组。远程与近战是不同玩家语义，必须保留各自功能实例和语义组；它们可以同时存在于同一芯片，不因使用相同子组 Def 而合并。

**Step 3：实现最小契约**

## 六、实施结果

### 6.1 已落地的标准结构

- Core 只提供中性语义 Def、属性 Def、信息组、受限子组、完整子功能、上下文归属、只读值合并和扩展引用模型；不按 BDP 功能名称分支，也不依赖 Content 或 Development。
- Content 的来源配置与 Worker 按已确认的玩家语义读取权威业务数据：能力生命周期、远程攻击、逐 Tool 近战方式、护盾规则、机动方式、能力中的近战攻击，以及额外效果专用扩展点。已淘汰按 `Verb`、`Hediff` 等底层承载类型猜测玩家语义的通用来源实现；表达条目来源基类仅作为标准来源的抽象定位基类保留。
- 芯片信息外层保留根级、形态、姿态三类归属上下文；功能内部只通过根属性、可重复 `Groups`、一层 `Subgroups` 和有界 `Children` 表达。功能级子组与信息组级子组分别归属其真实所有者；额外效果始终是子组，不与功能根部信息组并列。
- 上下文中的 `ActiveEntryIds=null` 表示未绑定具体条目范围，允许根级查看全部静态来源；显式空集合表示该形态/姿态没有活动条目，只保留无条目绑定的全局来源。无来源的父功能/信息组必须由其可达子组或子功能支撑，避免空形态捎带姿态专属结构。
- 姿态上下文稳定键采用 `ModeKey/StanceKey`；形态键、姿态键及组合来源范围均拒绝 `/`，以免路径分隔符与键自身冲突。请求式解析在原有上下文信息块上合并功能树，不覆盖旧有中性规则结果。
- 组合结果以正式已发布结果的稳定来源键关联 `ComboDef.Features`，在 Core 发布阶段通过统一解析器生成独立 `FeatureInformation`。适配不重新运行表达式、不暴露 Core 内部正式对象给 Content/UI、不更改组合匹配或执行。
- 组合对芯片的贡献使用独立扩展引用，能够处于芯片根级、形态级或姿态级；静态组合定义引用和已正式匹配后的运行时引用分开表达。芯片无需自行知道组合关系。
- 两个工作台从同一只读语义树和信息组结果组织显示；消费端仍可自行选择哪些信息、顺序与展示方式。选中一个没有功能的形态/姿态时，详情面板不再回退到根级聚合树。成品信息构建保留来访运行时形态/姿态状态。雷达图、精度图等恢复为可独立调用的中性静态图表工具，本轮没有接回业务面板。
- Development 扩展样例分别展示 XML 新建语义与把自定义 Worker 接入既有护盾语义；同时展示新属性、Patch 扩充护盾属性接收范围和自有权威业务 Def 来源，不污染正式执行链。

### 6.2 已确认的边界实例

- `Features` 只声明语义和结构，不填伤害、射程、半径、角度、概率、持续时间或消耗等实例值。
- 组合“战斧”的范围爆炸是远程攻击的主要攻击结果；按用户确认的复审记录，伤害与范围由远程攻击本体呈现，不再重复造一个“额外效果”子组。
- 扩展者可以把不同实现路线声明为相同玩家语义并提供权威值，也可以新增语义/属性/信息组及子组槽位；Core 不理解具体业务，通用回退展示未知扩展名称和属性。
