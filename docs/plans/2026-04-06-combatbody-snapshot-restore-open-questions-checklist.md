# CombatBody 快照/回滚系统未证实点清单

**日期：** 2026-04-06

## 1. 这份清单干什么

这份清单只记录一类东西：

> 目前还没有被旧 BDP 代码明确证实，所以现在不能下结论、也不能擅自写进“等价保证”里的点。

它的作用是防止后面再出现：

- 把“可能如此”说成“旧版就是这样”
- 把“设计偏好”说成“旧版事实”
- 把“没查到”误说成“没有”

---

## 2. 不属于未知点、已经证实的内容

下面这些已经有代码依据，不在本清单里反复讨论：

- 原始衣物/背包托管与恢复
- `ApparelState` / `ItemState` 两组恢复标记
- `HediffRecord` 13 个字段
- Need 只记录 `CurLevel`
- `Preset / MirrorOriginal` 两种模式
- `MirrorOriginal` 会复制 `Stuff` / 颜色 / `StyleDef` / 去品质
- `BDP_CombatBodyArmor` 这件预设装甲本体的显式 XML 字段
- `Hediff` 排除规则是动态 Def 配置，不是代码写死
- 托管防腐补丁只对快照容器生效

## 2.5 本轮已查实的新结论

### A. `BDP_CombatBodyActive` 不是“普通标记”

这轮已确认它至少还承担这些旧版语义：

- `preventsDeath`
- 自身 `stages` 里包含：
  - 疼痛免疫
  - 出血抑制
  - 精神崩溃阻止
  - 部分需求冻结
  - 环境抗性
  - 疾病免疫
- 自身 `comps` 里挂了 `HediffComp_TrionWoundDrain`
- `CombatBodyQuery.IsCombatBodyActive()` 直接拿它判断战斗体激活态
- `Patch_Pawn_PostApplyDamage` / `HediffComp_TrionDamageCost` 通过它接伤害后 Trion 消耗
- `Patch_HealthCardUtility_DrawHediffRow` 通过它切换 UI 图标

结论：

- 新版不能把它理解成“只是快照排除清单里的一项”
- 它是旧版战斗体运行态的正式业务承载点
- 但这恰恰说明：它不属于快照/回滚子系统本体应负责的内容

### B. `combatApparelContainer` 的写入路径不只一条

这轮已确认的写入路径包括：

- `Gene_TrionGland.InitializeCombatApparel()`：把 `defaultCombatApparel` 生成并放入容器
- `MirrorOriginal` 分支：先 `ClearAndDestroyContents()`，再把镜像副本 `TryAdd(copy)`
- `Preset` 退出时：把脱下来的战斗体衣物 `TryAdd(apparel)` 放回容器
- 调试动作：`CombatBodyDebugActions` 可手动向容器加衣物

结论：

- 如果说“旧版业务来源只有一条”，当前不能下这个结论
- 但若只说“旧版正式初始化来源已确认有 GeneExtension 这一条”，这个结论成立

### C. 普通退出后，目前没查到显式解除征召

这轮全仓只确认到：

- 激活时：`pawn.drafter.Drafted = true`
- 紧急退出时：显式 `Drafted = false`

当前未查到：

- 普通退出时在旧源码里还有别的显式 `Drafted = false`

结论：

- 目前不能声称“旧版普通退出一定会自动解除征召”
- 反过来也不能只靠一次搜索就说“绝对不会解除”
- 但就当前已查到的旧源码事实，**显式解除征召只在紧急退出路径里出现**
- 这同样属于外部战斗体流程待核项，不属于快照/回滚子系统责任边界

## 3. 当前未证实点

## 3.1 旧版是否还有其他战斗体前台装备 Def

### 当前状态

我已经确认：

- 旧版至少有 `BDP_CombatBodyArmor`

但在目前已核范围里，我还没有形成“旧版只有这一件、绝对没有别的前台装备 Def”的结论。

### 这意味着什么

- 现在可以说：第一版已确认预设事实是 `BDP_CombatBodyArmor`
- 不能说：旧版永远只有这一件、没有任何其他预设前台装备

### 对实现的影响

- 不阻塞第一版实现
- 但新的预设体系设计应允许以后继续追加，而不是写死成只支持一件

---

## 3.2 旧版前台预设来源是否只挂在 `Gene_TrionGland`

### 当前状态

已确认：

- `Gene_TrionGland` 会从 `GeneExtension_CombatBody.defaultCombatApparel` 初始化预设衣物
- `combatApparelContainer` 还有运行时写入与调试写入路径

未确认：

- 是否还有其他“正式业务初始化来源”也会向它注入预设衣物

### 对实现的影响

- 不阻塞新方案把来源迁入 `CombatBody` 正式设施
- 但如果要说“旧版正式预设来源只有这一条”，当前证据还不够

---

## 3.3 `BDP_CombatBodyActive` 在旧版是否只承担当前已见到的语义

### 当前状态

已确认：

- 激活时会加上它
- 退出前会单独移除它
- 它在快照排除清单里
- 旧注释提到它有 `preventsDeath`
- 它还被查询工具、伤害后 Trion 消耗链、健康卡 UI 图标逻辑直接依赖

未完全确认：

- 除已查明这些点之外，旧版是否还有更多模块继续依赖它

### 对实现的影响

- 这不会改变快照/回滚子系统“只做记录/恢复”的边界
- 它影响的是外部运行态设计是否需要继续保留同样的运行标记体系

---

## 3.4 `FinalCleanupResidualHediffs` 的判定精度是否足够复刻

### 当前状态

已确认：

- 旧版残留清理是通过：
  - `defName`
  - `bodyPartDefName`
 这两个维度去判断某个 `Hediff` 是否属于快照内容

未完全确认：

- 这种判定在旧版实际运行中是否存在误杀/漏杀
- 旧版是否有依赖这种“粗粒度判定缺陷”才能形成某种表象

### 对实现的影响

- 新版若完全照抄，可保证“更像旧版”
- 新版若试图“修正得更聪明”，反而可能偏离旧版表现

### 当前建议

- 第一版先按旧版判定粒度复刻
- 不擅自优化

---

## 3.5 旧版 `MirrorOriginal` 对“原件当前耐久”的业务意图

### 当前状态

已确认：

- 旧代码没有把原件当前耐久写回副本
- 注释写的是“耐久满”

未完全确认：

- 这是有意业务规则，还是实现顺手导致的结果

### 对实现的影响

- 如果目标是旧版表象等价，第一版应按“满耐久副本”实现
- 但若以后想改规则，这属于新设计决策，不是旧版事实

---

## 3.6 旧版 `Preset` 模式的颜色最终表现是否依赖额外来源

### 当前状态

已确认：

- `BDP_CombatBodyArmor` 继承了 `CompColorable`
- 但我当前没有看到旧版额外为这件预设装甲主动设色的代码

未完全确认：

- 游戏运行中它是否依赖默认材质/默认颜色/玩家染色结果形成最终外观

### 对实现的影响

- 新版第一版不应乱加“自动继承原衣颜色”给 `Preset`
- 因为这不是当前已证实的旧版事实

---

## 3.7 旧版退出后是否总要解除征召

### 当前状态

已确认：

- 旧版激活时会强制征召
- 旧版紧急退出时会解除征召
- 当前显式解除征召代码只查到紧急退出路径

未完全确认：

- 普通退出时是否还有“隐式”或间接路径会统一解除征召

### 对实现的影响

- 当前不能把“普通退出是否解除征召”写成快照子系统的职责
- 若后续继续查，也应归到外部战斗体退出流程，而不是快照子系统设计

---

## 3.8 旧版前台预设 Def 是否还有更多隐藏继承项影响表现

### 当前状态

已确认：

- `BDP_CombatBodyArmor` 继承 `ApparelNoQualityBase`
- 父类会带来一些通用服装属性和 `CompColorable`

未完全确认：

- 是否还有更深层继承链上的字段，实际影响旧版表现但尚未单独列出

### 对实现的影响

- 新版迁移时，最稳妥方式仍然是迁正式 Def，而不是在代码里“手抄效果”

## 4. 当前清单里的结论级别

为了避免以后又说满，这里明确分级：

### A 级：已被旧代码直接证实

- 可以写进“必须实现点”
- 可以拿来要求新版对齐

### B 级：高概率如此，但我还没把证据链补齐

- 可以列入待核项
- 不可以写成“旧版事实”

### C 级：纯推测

- 不进入计划
- 不进入等价性结论

这份清单里记录的都是 **B 级** 项，不是 A 级项。

---

## 5. 当前是否阻塞实现

### 不阻塞第一版实现的项

- 是否还有更多前台预设 Def
- `Preset` 最终颜色来源细节
- `MirrorOriginal` “满耐久”背后的业务意图
- 更深层继承项是否还有额外表现影响

### 可能影响严格等价结论的项

- `BDP_CombatBodyActive` 是否被其他旧模块额外依赖
- `FinalCleanupResidualHediffs` 的旧版粗粒度判定是否必须照抄
- 普通退出后征召状态是否在别处被处理

### 其中真正影响“快照/回滚子系统本体设计”的项

- `FinalCleanupResidualHediffs` 是否应被视为快照恢复的一部分，还是外部收尾的一部分

### 其中主要影响“外部战斗体流程设计”的项

- `BDP_CombatBodyActive` 的全部旧依赖面
- 普通退出后征召状态是否在别处被处理

## 6. 下一步建议

如果继续深挖旧版，我建议优先查这三项：

1. 全仓搜索 `BDP_CombatBodyActive`
2. 全仓搜索 `combatApparelContainer`
3. 全仓搜索普通退出后 `Drafted` 状态是否还有别处收尾

只有把这三项也钉死后，才更接近“旧版事实已经查到头”的状态。
