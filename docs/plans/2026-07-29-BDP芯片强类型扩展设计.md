# BDP 芯片强类型扩展设计

日期：2026-07-29  
范围：事项 07 `Extensions（扩展）`正式化  
状态：用户已确认

## 一、现状

当前芯片扩展由 `ChipExtensionBlockConfig` 表达，只有三段自由文本：

- `BlockName（块名）`
- `TargetSystem（目标系统）`
- `PayloadText（文本载荷）`

Core 会把这三段文本复制到芯片契约，再复制到每个表达来源的运行快照，但当前候选 XML 没有任何扩展声明，也没有任何业务系统读取这些数据。

因此，现状不是已经投入使用的扩展系统，而是一条没有消费者的文本复制管道。它不能检查字段拼写、不能保证读取方存在，也无法安全表达未来不同业务所需的不同参数。

## 二、目标

- 保留芯片定义内统一、工整的 `Extensions`分级。
- Core 只提供中性的强类型扩展父类和集合，不认识任何具体业务。
- Content 可以定义自己的扩展类型和明确字段，依赖继续保持 Content 单向引用 Core。
- 同一具体扩展类型，一枚芯片最多声明一个。
- 扩展只属于芯片静态定义，不自动复制到每次攻击、Ability（技能）、Hediff（状态）或被动表达的运行快照。

## 三、正式结构

Core 新增抽象父类型：

```csharp
public abstract class ChipExtensionConfig
{
}
```

`ChipDefinitionConfig.Extensions`正式改为：

```csharp
public List<ChipExtensionConfig> Extensions;
```

未来 Content 业务扩展按实际需求继承父类型，并通过 RimWorld 原生 XML `Class（具体类型）`写法声明：

```xml
<Extensions>
  <li Class="BDP.Content.某项业务.某个芯片扩展">
    <!-- 只填写该扩展真实需要的明确字段 -->
  </li>
</Extensions>
```

Core 不预设任何示例扩展，也不为了展示机制而创造没有实际消费者的字段。

## 四、读取和数据流

正式数据流为：

```text
ThingDef 芯片定义
    ↓
ChipDefinitionConfig.Extensions
    ↓
Core 契约浅复制静态扩展引用并做结构校验
    ↓
实际业务系统按自己的具体扩展类型读取
```

扩展是随 Def 加载后保持不变的静态配置，因此 Core 契约可以保留类型引用，不需要把它转写成通用文本，也不需要发明通用深复制规则。

表达运行快照中的 `ExpressionChipExtensionSnapshot`及其收集、克隆管道全部删除。表达系统只携带一次攻击或一次能力真正需要的运行数据；某个业务以后确实需要把扩展参数固化到运行会话时，应由该业务在自己的执行边界生成专用快照。

## 五、校验

Core 只做中性结构校验：

- 扩展集合可以为空。
- 空条目属于非法结构。
- 同一具体扩展类型重复声明属于非法结构。
- Core 不检查具体业务字段；具体扩展的合法性由拥有它的业务系统负责。

`ChipDefinitionDeclaredBlock.Extensions`继续保留：只要存在至少一个有效扩展条目，就把扩展块记为已声明。

## 六、删除内容

- 删除 `ChipExtensionBlockConfig`。
- 删除 `BlockName / TargetSystem / PayloadText`。
- 删除 `ChipExtensionBlockContract`。
- 删除表达运行快照中的 `ExpressionChipExtensionSnapshot`。
- 删除契约解释器、表达来源收集器和克隆函数里的旧文本复制链。
- 更新仍把“表达快照必须携带扩展”当成要求的过时测试。

不做旧 XML 兼容；当前候选内容没有扩展声明，因此不需要迁移候选业务配置。

## 七、验证标准

- 新测试先因正式父类型和新集合不存在而失败。
- 专项测试确认旧三段文本和表达快照复制链完全消失。
- Core、Content、DevHarness 三个程序集 Release（发布）构建成功。
- Core 不依赖其他任何本模组程序集。
- 两个模组全部 XML 可解析。
- 全量测试不增加新的失败项。

## 八、不在本项处理

- 不新增护盾、面板、追踪、形态或其他具体业务扩展。
- 不提前决定哪枚芯片需要什么扩展。
- 不建立扩展注册中心、事件总线或自动执行框架。
- 不把扩展改造成运行时状态容器或存档容器。
