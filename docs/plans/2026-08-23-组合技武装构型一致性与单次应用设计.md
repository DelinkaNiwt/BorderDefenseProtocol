# 组合技武装构型一致性与单次应用设计

## 1. 设计目标

让武装构型对组合技的作用保持确定、可解释，并同时满足以下要求：

1. 第一、第二来源项芯片的武装构型可以继续影响各自来源动作。
2. 组合技结果自己显式定义的字段也能接受构型修正。
3. 从第一、第二来源结果继承的字段不能再次重复应用构型修正。
4. 第一、第二来源项的武装构型不一致时，不生成含义不明确的组合技。
5. 构型判断不依赖运行时 Main/Sub 槽位顺序。

本文统一使用以下正式称谓：`ComboDef` 中按声明顺序定义的两个来源称为“第一来源项”和“第二来源项”；运行时解析出的对应动作结果称为“第一来源结果”和“第二来源结果”；组合表达产物称为“组合结果”；`SourceVariantKey` 所标识的武装构型称为“来源构型”。`Main`/`Sub` 仅表示运行时槽位，不表示来源项身份。

本设计只处理运行时组合表达阶段的来源构型一致性。若组合结果条目在制造阶段另有独立构型选择，属于后续单独设计，不在本方案中隐式叠加。

## 2. 当前问题

当前组合契约中的两个来源项，先分别经过各自实际生效武装构型的处理：

```text
组合契约第一来源项的动作 + 其实际生效构型 = 第一来源项的已修正结果
组合契约第二来源项的动作 + 其实际生效构型 = 第二来源项的已修正结果
```

组合表达再从已经处理后的来源结果读取字段，因此普通动作参数会得到第一、第二来源结果的值。但是组合结果重建时，组合结果自己显式定义的字段没有统一的构型作用阶段；如果直接对整个组合结果再套构型，又会使已经来自来源结果的字段重复修正。

此外，第一、第二来源项在运行时可能分别落入 Main 或 Sub 槽位，槽位不是稳定的来源项身份，不能用“当前 Main 构型”或“当前 Sub 构型”作为组合结果的构型来源。

## 3. 核心规则

### 3.1 构型一致性准入

在组合技来源准入阶段，读取 ComboDef 声明的第一、第二来源项的实际生效构型，按构型稳定身份比较：

| 组合契约第一来源项 | 组合契约第二来源项 | 结果 |
|---|---|---|
| 来源键为空 | 来源键为空 | 允许，组合结果无构型 |
| 来源键相同且非空 | 来源键相同且非空 | 允许，组合结果使用该来源构型 |
| 来源键不同且均非空 | 来源键不同且均非空 | 拒绝 |
| 来源键非空 | 来源键为空 | 拒绝 |
| 来源键为空 | 来源键非空 | 拒绝 |

构型比较使用稳定来源变体身份（当前为 `SourceVariantKey`，由 Content 以构型定义名提供），不比较显示名称，也不比较最终计算数值。若系统为来源芯片解析出了隐式默认构型，应以该实际生效构型参与比较。

准入失败应在表达组合生成前返回明确的 `SourceVariantMismatch` 类失败原因，不生成组合结果的正式表达。Core 只使用中性的来源变体概念；当前武装构型由 Content 映射为来源变体键。

### 3.2 槽位无关

准入比较绑定 ComboDef 的第一、第二来源项身份，而不是绑定当前 Main/Sub 槽位：

```text
Main = 组合契约第一来源项，Sub = 组合契约第二来源项  → 比较两个来源项的实际构型
Main = 组合契约第二来源项，Sub = 组合契约第一来源项  → 仍然比较两个来源项的实际构型
```

槽位只负责当前执行路径，不负责决定构型归属。

### 3.3 组合结果的组合级来源构型上下文

准入成功后，组合结果获得一个唯一的组合级来源构型上下文：

```text
第一、第二来源项使用同一构型  →  ComboSourceVariantKey = 该构型的来源变体键
第一、第二来源项均无构型      →  ComboSourceVariantKey = null
```

不再需要在 Main/Sub 之间选择构型，也不需要合并第一、第二来源项的不同构型。

## 4. 字段应用模型

组合结果必须区分“组合结果显式字段”和“来源继承字段”。

```text
组合结果[f] = Apply(ComboSourceVariantKey, 组合结果显式字段 f)
               如果 f 由组合结果显式定义

组合结果[f] = Resolve(第一、第二来源结果[f])
               如果 f 继承自第一、第二来源项
```

来源继承字段继续使用已经完成来源构型修正的第一、第二来源结果，不再追加 `ComboSourceVariantKey` 对应的修正。

组合结果显式字段则使用现有武装构型语义修正一次：

- 标量绝对覆盖按构型定义覆盖；
- 倍率字段作用于组合结果的自有基础值；
- 列表字段使用构型声明的 `Append` 或 `Replace` 策略；
- 视觉、近战工具、远程模块等同样按“字段归属”决定是否作用。

例如：

```text
组合契约第一来源项的射程 = 20，第一、第二来源项一致的来源构型修正 +5 → 第一来源项已修正结果的射程 = 25
组合契约第二来源项的射程 = 10，第一、第二来源项一致的来源构型修正 +5 → 第二来源项已修正结果的射程 = 15
组合结果显式射程字段 = 30，组合级来源构型 = 第一、第二来源项一致的来源构型
```

结果是：

```text
组合结果的射程 = Apply(第一、第二来源项一致的来源构型, 30)
```

而不是对第一、第二来源结果再套一次组合级来源构型。

## 5. ComboDef 契约调整

建议在组合来源准入契约增加明确的构型一致性条件，概念形式如下：

```xml
<SourceAdmission>
    <RequireSameSourceVariant>true</RequireSameSourceVariant>
</SourceAdmission>
```

该条件默认启用。后续如确实存在需要混合构型的特殊组合，应另行增加显式策略，而不是默默放宽当前规则。

ComboDef 的字段来源仍按字段处理：

- `FollowChipMain` / `FollowChipSub` 只决定动作字段从当前 Main/Sub 来源取值；
- 它们不再承担“为组合结果选择构型”的职责；
- 组合结果显式字段统一使用准入阶段确定的组合级来源构型。

## 6. 架构边界

Core.dll 不直接依赖 `ChipArmamentFormDef` 等 Content 业务类型。

建议由 Content 层解析实际构型并构造中性的来源构型上下文与字段修正计划，Core 层只消费：

- 来源项身份；
- 字段归属与显式性；
- 是否已应用来源修正；
- 组合级构型修正计划。

现有构型覆盖的绝对值、倍率和列表合并语义继续复用，不在组合系统中复制另一套构型计算规则。

## 7. 失败与边界处理

1. 第一、第二来源项缺少来源信息：按现有来源缺失流程处理。
2. 第一、第二来源项的构型定义名不同，即使最终数值碰巧相同，也拒绝组合。
3. 第一、第二来源项一方为无构型、另一方有构型，拒绝组合。
4. 构型已选择但对当前动作不实际生效时，比较实际生效构型，而不是单纯比较 UI 选择记录。
5. 组合结果若另有制造阶段构型，不能与组合级来源构型无声明地叠加；需要单独定义优先级或禁止该组合。

## 8. 验证矩阵

至少覆盖以下组合：

| 场景 | 预期 |
|---|---|
| 第一、第二来源项均无构型 | 允许，组合结果无构型 |
| 第一、第二来源项使用同一构型 | 允许，组合结果显式字段应用该构型一次 |
| 第一、第二来源项使用不同构型 | 准入拒绝 |
| 第一、第二来源项一方有构型、另一方无构型 | 准入拒绝 |
| Main/Sub 交换但第一、第二来源项构型不变 | 结果不变 |
| 组合结果继承 Main 字段 | 使用当前 Main 来源结果，不重复应用组合级来源构型 |
| 组合结果继承 Sub 字段 | 使用当前 Sub 来源结果，不重复应用组合级来源构型 |
| 组合结果显式定义射程/精度/执行字段 | 应用组合级来源构型一次 |
| 组合结果显式定义视觉/模块/近战工具 | 应用组合级来源构型一次 |

## 9. 非目标

本设计暂不实现：

- 两个不同构型的合并优先级；
- 第一、第二来源项构型的逐字段融合；
- 组合结果制造构型与运行时来源构型的多层叠加；
- 自动把不同构型强行折算成同一组数值。
