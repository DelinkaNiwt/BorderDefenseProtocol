# BDP 核心零模组程序集依赖检查设计

## 一、目的

自动保证 `BDP.Core.dll`（核心程序集）不依赖任何其他由 BDP 模组自身提供的 DLL（动态链接库）。

当前只有 `BDP.Content.dll`（内容程序集），但检查不得写死这个名字。以后新增本模组程序集工程时，应自动进入受检名单。

Core（核心）仍可依赖 RimWorld（边缘世界）、Unity（游戏引擎）、Harmony（补丁框架）和 .NET（运行环境）；这些不属于本模组自己的程序集。

## 二、采用方案

采用三层构建门禁：

1. 检查核心工程的 `ProjectReference`（工程引用）。
2. 检查编译后 `BDP.Core.dll` 的 `AssemblyRef`（程序集引用表）。
3. 检查核心源码和核心 XML（可扩展标记语言）是否明确写出其他本模组程序集的名称或专属命名空间。

三层中任意一层发现违规，检查脚本返回非零退出码，构建失败并显示具体位置。

## 三、未采用方案

### 只检查工程文件

实现最短，但无法发现手工加入的 DLL 引用，也无法发现编译产物与工程声明不一致。

### 只检查编译产物

能检查最真实的强类型依赖，但发现时间较晚，也无法发现 XML 中以字符串写入的内容类型。

### 常驻后台监控

对 RimWorld 小型模组没有必要，会增加进程、配置和维护成本。构建后立即检查已经能覆盖正常开发流程。

## 四、本模组程序集名单

检查器递归读取统一模组 `Source` 下的所有 `.csproj`（C# 工程），提取：

- `AssemblyName`（程序集名称）。
- `RootNamespace`（根命名空间）。
- 工程物理路径。

若工程没有显式声明 `AssemblyName`，才退回使用工程文件名。

因此未来新增工程后不需要手工修改“禁止名单”。

## 五、三层检查

### 1. 工程层

读取核心工程的全部 `ProjectReference`，解析其目标工程。

只要目标属于本模组程序集名单且不是核心自身，就判定失败。

### 2. DLL 层

以字节方式读取编译后的 Core DLL，再从 .NET 元数据中读取 `GetReferencedAssemblies()`（获取程序集引用）。

使用字节加载是为了避免锁住 `1.6/Assemblies/BDP.Core.dll`，确保同一终端后续仍可重新编译覆盖。

将 Core 的引用名称与“本模组程序集名单减去 Core 自身”求交集：

```text
交集为空：通过
交集非空：失败
```

### 3. 明确名称层

从其他本模组工程的 `RootNamespace` 和实际 C# `namespace`（命名空间）声明中收集专属名称。

扫描范围：

- `Source/BDP` 下的核心 C# 源码。
- 主模组 `1.6/Defs` 下的核心 XML。

明确写出其他本模组程序集名或专属命名空间时失败。

Core 已有的 `Type.GetType`（按类型名恢复）和 `Activator.CreateInstance`（按类型创建实例）属于中性扩展机制，不整体禁止；检查的是 Core 是否知道某个具体内容程序集或内容命名空间。

## 六、构建接线

检查脚本放在统一模组的构建工具目录中。

核心工程完成编译后自动调用检查脚本：

```text
编译 BDP.Core.dll
        ↓
执行零模组依赖检查
        ↓
通过：构建继续
失败：构建终止
```

检查脚本也可单独运行，便于诊断和自动测试。

## 七、错误输出

失败信息必须直接说明：

- 违规层级：工程、DLL 或明确名称。
- 违规程序集或命名空间。
- 对应工程或文件路径。

不自动修改依赖，不自动搬迁代码。若发现既有违规，应暂停并单独确认处理方式。

## 八、测试

自动测试至少覆盖：

1. 当前 Core 无其他本模组依赖时通过。
2. 模拟核心工程引用另一本模组工程时失败。
3. 使用现有 `BDP.Content.dll` 模拟被检查对象，确认 DLL 引用表中的 `BDP.Core` 能被发现。
4. 模拟核心源码明确写出内容命名空间时失败。
5. RimWorld、Unity、Harmony 和 .NET 依赖不会被误报。
6. 正常 Release（发布）构建会自动运行门禁。

## 九、本项不处理

- 不重命名现有 `DevHarness/Test/Sample`（开发框架/测试/示例）业务名称。
- 不整理内容程序集启动入口。
- 不调整任何具体芯片、武器、护盾或视觉参数。
- 不在本项划分正式内容与开发诊断工具；该边界由后续事项处理。
