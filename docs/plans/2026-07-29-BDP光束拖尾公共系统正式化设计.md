# BDP 光束拖尾公共系统正式化设计

**日期：** 2026-07-29  
**对应事项：** 04 正式化光束拖尾公共系统  
**状态：** 已实施并通过自动验证；亮薄荷绿色值等待游戏内实测

## 一、目标

把候选模组中已经被多个远程应用复用的光束拖尾整理为 `BDP.Content.dll`（内容程序集）中的正式公共视觉系统，同时严格保持：

- `BDP.Core.dll`（核心程序集）不依赖任何其他本模组 DLL（动态链接库）。
- Core（核心）只广播投射物位置和生命周期事实，不知道光束拖尾业务。
- Content（内容）单向使用 Core 已有的投射物视觉附加接口。
- 只迁入本事项已经确认的公共系统、通用贴图和两个正式预设，不提前迁入上层应用。

## 二、选择的方案

采用“选择性转正”，不采用以下两种方案：

1. 不原样整包搬运候选拖尾目录。原样搬运会保留重复配置入口、测试命名和多余开关。
2. 不只搬运行代码而把全部预设留在候选模组。公共系统需要两个已确认的正式预设作为主模组内容。

选择性转正只保留当前确有用途的六部分：

- 拖尾外观快照。
- 投射物拖尾附加件。
- 地图级拖尾管理器。
- 拖尾预设定义。
- 可存档的历史拖尾线段。
- 来源 Def（定义）使用的正式拖尾扩展。

无人使用的 `BeamTrailConfig（光束拖尾直接配置）`不迁移、不兼容并从候选源码中删除。

## 三、程序集与目录归属

### Core（核心程序集）

Core 保持不变，继续提供：

- 投射物视觉附加提供器接口。
- 投射物发射、飞行、读档恢复和终止通知。
- 单个视觉附加件异常隔离。

Core 不新增任何 `BeamTrail（光束拖尾）`名称、类型或配置引用。

### Content（内容程序集）

正式源码命名空间统一为：

```text
BDP.Content.Projectiles.BeamTrail
```

Content 负责拖尾预设解析、运行时线段生成、地图绘制、历史余痕存读档和资源使用。

拖尾通过 Def 扩展自动接入 Core 现有视觉宿主，不在 `ContentBootstrap（内容启动入口）`中添加具体业务注册。

### RimWorld（边缘世界）加载目录

采用“主版本根目录 + Content 补充层”，不把现有整个 `1.6`目录提前改名为 `Core`：

```text
1.6/
├─ Assemblies/                 Core 与 Content 两个 DLL
├─ Defs/                       现有 Core/尚待归属复查的主配置
├─ Textures/                   现有主模组资源
└─ Content/
   ├─ Defs/                    已确认属于 Content 的配置
   ├─ Patches/                 以后确认的 Content 补丁
   └─ Textures/                明确只属于 Content 的资源
```

`LoadFolders.xml`（加载目录配置）的 1.6 顺序固定为：

```text
/
1.6
1.6/Content
```

这样仍是一个模组，同时符合 RimWorld 以“加载根目录下面放 `Defs / Assemblies / Textures / Patches`”组织内容的方式。Core 依赖门禁只把 `1.6/Defs`视为核心 XML（配置文件）；`1.6/Content/Defs`中的合法 Content 类型不属于 Core 扫描范围。

不采用 `1.6/Core/Defs`作为当前结构，因为这会在事项 09 归属复查之前，把现有全部主配置提前定性为 Core，并引发大范围无必要搬迁。完成以后业务归属复查后，如仍需要完全对称的 Core/Content 物理目录，可再单独设计。

### 候选模组

候选模组移除已经转正的拖尾源码和通用贴图，避免同一系统存在两份实现。

候选模组继续保留：

- 炽红拖尾预设。
- 普通齐射对炽红预设的现有引用。
- 路线引导齐射对炽红预设的现有引用。

这些内容留到对应上层应用事项再审查。

## 四、正式配置

正式扩展类型为：

```text
BDP.Content.Projectiles.BeamTrail.BeamTrailExtension
```

扩展只保留一个预设引用：

```xml
<preset>BDP_TrailPreset_BrightMintLong</preset>
```

正式启用规则：

- 来源 Def 挂载扩展且 `preset（预设）`有效：生成拖尾。
- 未挂载扩展：不生成拖尾。
- 预设缺失或无效：不创建拖尾附加件，并给出可定位的配置警告。

删除以下旧结构：

- `ChipBeamTrailExtension（芯片拖尾扩展）`类名。
- `beamTrailPreset（光束拖尾预设）`字段名。
- `enabled（启用）`重复开关。
- `BeamTrailConfig（光束拖尾直接配置）`第二配置路线。

不保留旧类型、旧字段或旧 DefName（定义名称）兼容。

## 五、正式预设与候选引用

主模组正式加入两个预设：

| DefName（定义名称） | 中文名称 | 来源参数 |
|---|---|---|
| `BDP_TrailPreset_BrightMintLong` | 亮薄荷绿长拖尾 | 原冷蓝长拖尾除名称和颜色外的参数 |
| `BDP_TrailPreset_BrightMintShort` | 亮薄荷绿短拖尾 | 原追踪短蓝拖尾除名称和颜色外的参数 |

首版颜色为：

```text
#DAFDE5
(0.855, 0.992, 0.898, 1.0)
```

颜色是待游戏实测的首版，后续校色不改变系统结构。

候选配置只进行保持可加载所必需的机械更新：

- 旧冷蓝长版引用改为正式亮薄荷绿长版 DefName。
- 旧追踪短蓝版引用改为正式亮薄荷绿短版 DefName。
- 扩展类型和字段改为正式名称。
- 候选炽红预设改用正式预设类型，但 DefName、参数和两处现有引用不变。

上述更新只是同一长版或短版预设转正后的名称对接，不重新决定任何芯片应该选择哪个预设。

## 六、运行与存读档时序

### 发射与飞行

1. 投射物发射时，Core 视觉宿主从来源 Def 找到正式拖尾扩展。
2. 扩展根据预设生成一份不随 Def 继续变化的外观快照。
3. 拖尾附加件记录投射物当前锚点。
4. 每次收到新的飞行位置时，上一条活动头段固化为历史余痕，新的位置成为活动头段终点。

### 终止

投射物命中、销毁或以其他方式终止时：

- 停止生成新的活动头段。
- 清除仍跟随投射物的临时头段。
- 已经固化的历史余痕继续按自己的寿命淡出。

### 存读档

- 历史余痕保存起点、终点、外观和已经消耗的寿命进度。
- 读档后从保存时的进度继续淡出。
- 活动头段不作为独立历史线段保存。
- 活体投射物恢复后，由 Core 的恢复通知重新建立拖尾锚点。

本次不兼容改造前旧命名空间或旧 DefName 的存档；改造后的新存档必须稳定保存和恢复历史余痕。

## 七、绘制范围修正

现实现只按线段中点判断是否位于镜头范围，可能漏掉“线段穿过画面但中点在画面外”的长光束。

正式实现改为：

1. 根据线段起点和终点计算整条线段的平面覆盖矩形。
2. 按实际线宽向四周扩展覆盖矩形。
3. 覆盖矩形与镜头矩形相交时绘制。

该修正只决定是否需要绘制，不改变颜色、宽度、寿命、飞行路径、存读档或芯片预设选择。

## 八、资源与异常处理

- 通用白色半透明贴图进入主模组的 `1.6/Content/Textures/Things/Projectile/BDP_BeamTrail.png`，由预设颜色统一染色。
- 缺失贴图时给出一次明确警告，避免每帧重复刷日志。
- 无效预设不创建拖尾，不影响投射物本身继续运行。
- 拖尾附加件内部异常继续由 Core 现有视觉宿主隔离，不向投射物攻击流程扩散。
- 地图组件只管理本地图的拖尾，不建立跨地图共享状态。

## 九、验证范围

实施采用测试先行，至少覆盖：

- 正式源码只存在于 `BDP.Content.dll` 工程。
- Core 源码、工程引用和编译 DLL 中不存在 Content 或 BeamTrail 反向依赖。
- 旧 `DevHarness`、`Chip`、`BeamTrailConfig`、`enabled` 和 `beamTrailPreset` 语义不残留在正式系统。
- 主模组只包含亮薄荷绿长、短两个正式预设。
- 候选炽红预设和两处现有引用保持不变。
- 候选长、短引用只进行对应的机械改名。
- 历史余痕参与存读档，活动头段不重复保存。
- 投射物终止后不继续产生活动头段。
- 长线段穿过镜头时不会因为中点位于画面外而漏画。
- 主模组与候选模组 Release（发布）构建成功。
- XML（可扩展标记语言）可解析，Core 单向依赖门禁通过。
- 全量冒烟测试不得出现新的失败；既有十二项基线失败单独比对。

## 十、不在事项 04 处理

- 不修改任何芯片应该使用长版、短版或炽红预设的业务选择。
- 不调整候选炽红预设参数。
- 不重做远程、齐射、双持、追踪、路线引导或爆炸应用。
- 不处理触发器、触发体分类与命名。
- 不处理护盾补丁、诊断按钮或 Trion（触粒子）面板。
- 不修改 Core 的中性视觉接口，除非实施时发现当前接口无法支持已经确认的时序；如发生这种计划外情况，必须暂停并征询用户。
