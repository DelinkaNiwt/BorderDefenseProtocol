# BDP 自有 Verb 宿主层设计（第一版）

## 1. 文档目的

这份文档只做一件事：

- 正式定义 BDP 自有 Verb 宿主层

并基于当前真实代码状态，明确回答：

- 为什么现有方案必须整体拆掉
- 新宿主层的正式职责边界是什么
- 要删什么
- 要保留什么
- 要重建什么
- 为什么这次必须允许模组先进入“攻击失效但结构诚实”的缺陷状态

这不是实施计划。

这也不是“继续修现在这条线”的补丁设计。

这是一次大改造级别重构的正式设计稿。

---

## 2. 设计结论

本次重构采用下面的正式方案：

- 不再继续沿着“表达结果 -> 原版装备挂接点映射”这条路修补
- 不再保留任何 fallback、兼容桥、过渡宿主逻辑
- 先整体拆掉当前错误的 Verb 宿主映射链
- 允许模组暂时进入“攻击不可用但表达仍成立”的缺陷状态
- 在干净地基上建设 BDP 自有 Verb 宿主层
- 手动攻击、自动攻击、双武器、组合技都统一改为消费这套宿主层

一句话：

```text
先拆干净，再重建。
不在错误 ownership 上继续修。
```

---

## 3. 当前真实状态

### 3.1 当前已经有的东西

当前主模组已经有：

- 表达来源与表达合成链
- 正式表达结果 `FormalExpressionResult`
- 统一攻击执行入口 `AttackExecution`
- 手动攻击回接 BDP 执行入口
- 自动近战 / 自动远程回接 BDP 执行入口
- 远程 / 近战正式执行器

所以当前系统不是“没有架构”，而是已经建到一半。

### 3.2 当前真正卡住的地方

当前真正卡住的是：

- BDP 已经开始自己接攻击请求
- 但真正运行的 Verb 仍然依赖原版装备宿主环境

当前这条依赖具体表现为：

- 仍然从 `pawn.equipment.Primary` 往下取 `CompEquippable`
- 仍然把 `verb.verbTracker / tool / maneuver / caster` 绑回原版装备环境
- 仍然通过“先有正式结果，再解析出原版真实 Verb”的方式让系统运行

这说明当前系统的 ownership 是分裂的：

- 表达层以“正式结果”为中心
- 攻击执行以“正式请求和执行计划”为中心
- 运行时宿主却仍然以“原版装备挂点”为中心

### 3.3 这为什么一定会出问题

因为一旦 ownership 分裂，所有入口都会开始补桥：

- 手动攻击要补一层
- 自动远程要补一层
- 自动近战要补一层
- targeting 要补一层
- 双武器要补一层
- 组合技要补一层

最后得到的不是正式结构，而是：

- 一套看起来被统一了的外表
- 底下却仍然依赖旧宿主假设

这条路不能继续走。

## 4. 旧 BDP 留下的有效经验

旧 BDP 不是只有历史包袱。

它已经证明了几件关键事实，而且这些事实必须被新架构吸收。

### 4.1 芯片 Verb 不能回到 `VerbTracker.AllVerbs`

旧 BDP 已经证明：

- 只要芯片近战 Verb 进入 `AllVerbs`
- 原版近战池和默认路径就会误拾取

所以这次新宿主层的前提不是：

- “重新把自有宿主塞回原版池里”

而是：

- “自有宿主成立，但不回到原版 `AllVerbs`”

### 4.2 自有宿主方向本身是对的

旧 BDP 已经做过：

- 手动创建芯片 Verb
- 手动缓存
- 手动复用
- 自动攻击通过代理 Verb 桥接
- 双武器和组合技先组合，再落宿主

所以这次不是凭空发明一个方向。

这次是在承认：

- 旧 BDP 已经证明“自有宿主是对的”

### 4.3 旧 BDP 的错误不在“自有宿主”，而在“承载位置错了”

旧 BDP 最大的问题不是自造宿主，而是把下面这些东西全塞进了 `CompTriggerBody`：

- 宿主缓存
- 宿主创建
- 宿主复用
- 自动攻击桥
- 双武器组合
- 组合技创建
- VerbTick 驱动
- 读档复用

这会让 `CompTriggerBody` 重新膨胀成运行时总控。

这正是本次必须彻底避免的。

## 5. 本次正式裁定

### 裁定 1：当前宿主映射链整体作废

下面这条主线，正式裁定为错误路线：

```text
表达结果
    -> 解析原版装备挂点
    -> 绑定 CompEquippable / VerbTracker / Tool / Maneuver
    -> 借原版装备环境跑起来
```

这条线不再继续修。

### 裁定 2：本次不做温和迁移

本次不采用：

- 新旧逻辑并存
- 失败回退旧逻辑
- 保留兼容桥
- 先搭新的一半，再靠旧的一半兜底

理由很简单：

- 只要旧宿主映射链还在，它就会继续污染新架构

### 裁定 3：允许中间缺陷状态

本次重构明确允许：

- 模组在中间阶段失去攻击能力

前提是：

- 表达仍然成立
- Trigger 仍然正常
- 结构边界清楚
- 失败是诚实的

不允许：

- 为了保持“暂时能打”继续保留错误宿主线

### 裁定 4：宿主 ownership 统一归 BDP

自此之后，运行时 Verb 宿主的 owner 是：

- BDP 自有 Verb 宿主层

不是：

- 表达系统
- 攻击执行层
- Trigger
- 原版装备挂点

## 6. 新架构的正式边界

### 6.1 表达系统负责什么

表达系统只负责回答：

- 当前成立了哪些表达
- 每条表达的类型是什么
- 主副身份是什么
- 组合关系是什么
- 是否可投影
- 显示与语义信息是什么

表达系统不负责：

- 创建运行时 Verb
- 持有 Verb 宿主实例
- 给自动攻击直接提供真实宿主
- 给 JobDriver 维护宿主生命周期

### 6.2 Verb 宿主层负责什么

Verb 宿主层负责：

- 把表达结果翻译成宿主构造规格
- 创建和复用运行时 Verb 宿主
- 管理固定宿主入口
- 维护宿主实例表
- 对外提供手动 / 自动攻击可用的宿主读取口
- 维护宿主生命周期
- 维护宿主 tick / 运行状态
- 维护读档复用和运行时连续性

这层是本次重构新增的正式运行时层。

### 6.3 攻击执行层负责什么

攻击执行层负责：

- 接单
- 目标确认
- 执行计划生成
- 分发到近战 / 远程执行器
- 启动持续推进链

攻击执行层不负责：

- 决定有哪些宿主
- 创建宿主
- 回收宿主
- 解释双武器 / 组合技应该挂在哪个入口

### 6.4 Trigger 负责什么

Trigger 只负责：

- 芯片装载
- 激活与停用
- 槽位和侧别事实
- 触发表达重算
- 通知宿主层刷新

Trigger 不再负责：

- 持有 Verb 宿主缓存
- 创建组合技 Verb
- 直接回答自动攻击主入口
- 驱动芯片 VerbTick

### 6.5 RimWorld 侧保留什么

RimWorld 侧仍然保留：

- `Verb`
- `JobDriver`
- `Projectile`
- `Targeter`
- `Gizmo`
- 原版伤害链

也就是说：

- BDP 自有的是宿主 ownership
- 不是另造一套脱离 RimWorld 的战斗世界

## 7. 自有 Verb 宿主层的正式对象

下面这些对象不是建议，而是本次架构的最小正式对象集。

### 7.1 固定宿主入口

这是 BDP 宿主层的正式入口表。

第一版固定为：

- `MainPrimary`
- `MainSecondary`
- `SubPrimary`
- `SubSecondary`
- `DualPrimary`
- `DualSecondary`
- `ComboPrimary`
- `ComboSecondary`

作用：

- 明确当前哪些攻击宿主可以存在
- 让手动入口、自动入口、执行层都按同一入口表说话

这层不再依赖：

- `Tool`
- `Maneuver`
- 原版装备默认主武器概念

### 7.2 宿主构造规格

这是“要造什么宿主”的正式规格。

每条规格至少包含：

- 对应表达结果
- 对应固定宿主入口
- 近战 / 远程类型
- 主攻击 / 副攻击身份
- 单侧 / 双持 / 组合技类别
- 目标 `verbClass`
- 运行参数
- 是否允许手动入口
- 是否允许自动攻击

这层的作用是：

- 把表达结果整理成正式运行时规格

而不是：

- 一读到表达结果就直接 `new Verb`

### 7.3 宿主实例

宿主实例是正式运行对象。

它至少持有：

- 一个真实 `Verb`
- 自己所属的固定入口
- 自己对应的表达结果标识
- 自己当前是否可用
- 自己当前运行状态
- 自己的稳定运行时键

注意：

- 裸 `Verb` 不是正式宿主对象
- 正式宿主对象里持有一个真实 `Verb`

### 7.4 宿主持有器

宿主持有器是：

- 某个 Pawn 当前全部 Verb 宿主的正式 owner

它负责：

- 持有全部宿主实例
- 管理入口到宿主实例的映射
- 回答主远程是谁
- 回答主近战是谁
- 回答手动入口该显示谁
- 回答自动入口该取谁

这层要取代当前散落的：

- `PrimaryRanged`
- `PrimaryMelee`
- `VerbHostSlot`
- `VerbHostKey`
- 各类零散“主攻击猜测”

### 7.5 宿主工厂

宿主工厂负责：

- 按宿主构造规格创建宿主实例

它统一做：

- `Verb` 创建
- 最小运行态初始化
- BDP 上下文注入
- 近战 / 远程差异初始化
- 双持 / 组合技宿主初始化

它不再做：

- 扫描 `CompEquippable`
- 扫描 `Tool / Maneuver`
- 从原版装备环境反推宿主合法性

### 7.6 宿主读档复用器

这是正式对象，不是辅助工具。

它负责：

- 读档时按稳定键找到旧宿主实例
- 决定是复用还是替换
- 保持 Job / Stance / Warmup 等运行时引用不断链

### 7.7 宿主时钟 / 驱动器

这也是正式对象。

它负责：

- 驱动宿主 `VerbTick`
- 推进 burst / warmup / cooldown 计时
- 处理持续攻击期间的宿主运行状态

这层的存在是必须的，因为：

- 自有宿主不进入 `AllVerbs`
- 不能再默认依赖原版帮我们完整 tick

### 7.8 手动攻击接入口

手动攻击入口正式改为：

```text
按钮
    -> 宿主入口 / 宿主实例
    -> targeter
    -> AttackExecution
```

不再是：

```text
按钮
    -> ResultId
    -> 临时解析真实 Verb
    -> 再去攻击
```

### 7.9 自动攻击接入口

自动攻击入口正式改为：

- 自动远程先问宿主持有器：当前主远程宿主是谁
- 自动近战先问宿主持有器：当前主近战宿主是谁

然后再由桥接层决定：

- 返回给原版哪个 `Verb`
- 或直接向执行层下单

关键点：

- patch 可以保留
- 但 patch 只能读宿主层

### 7.10 双武器 / 组合技宿主

双武器和组合技不再是单独私有系统。

它们只是：

- 固定入口表中的特殊入口
- 宿主构造规格中的特殊类别

也就是说：

- 双武器 = `DualPrimary / DualSecondary`
- 组合技 = `ComboPrimary / ComboSecondary`

它们和单侧宿主共享同一套宿主层框架。

## 8. 要删什么

本次采取激进拆除策略。

下面这些东西，不是以后慢慢淡出，而是正式裁定为应整体删除。

### 8.1 当前错误宿主映射链

应整体删除：

- 当前 Verb 宿主同步器
- 当前 Verb 宿主解析器
- 当前 `ExpressionVerbBridge`
- 当前一切“按结果去借原版装备挂点”的宿主绑定逻辑

### 8.2 当前宿主绑定所依赖的错误核心假设

应彻底删除下面这些假设：

- 真实宿主来自 `equipment.Primary`
- 真实宿主必须绑定 `CompEquippable.VerbTracker`
- 近战合法性要靠 `Tool / Maneuver`
- 表达层可以顺手把 Verb 绑回原版装备环境

### 8.3 当前所有兼容 / fallback 语义

应全部删除：

- resolver 失败后临时创建 Verb
- 新逻辑失败回旧逻辑
- 临时代理继续承担真实执行职责
- 保留旧字段只为兜底

本次不允许保留任何过渡脏物。

### 8.4 当前应删除的旧概念

正式删除这些概念：

- “表达宿主同步器”继续充当运行时 Verb owner
- “真实宿主 = 已绑好的原版装备 Verb”
- “组合技创建属于 Trigger owner”
- “主攻击是从结果里猜出来的一个默认 Verb”

---

## 9. 要保留什么

下面这些不应误删。

### 9.1 表达主链

保留：

- 表达来源
- 表达合成
- 表达快照
- 正式结果模型

### 9.2 攻击执行主链

保留：

- `AttackExecution` 入口
- 执行计划层
- 近战 / 远程执行器
- JobDriver 运行时链

### 9.3 真实攻击宿主类

保留：

- `BdpVerb_Shoot`
- `BdpVerb_MeleeAttackDamage`

因为这次改的是：

- 宿主 ownership

不是：

- 真实攻击宿主类本身的语义职责

### 9.4 Trigger 的正确职责

保留 Trigger 作为：

- 装载 owner
- 激活 owner
- 来源事实 owner

但不再让它膨胀成运行时宿主总控。

### 9.5 语义攻击链

保留：

- 投射物语义传递
- 爆炸语义传递
- 伤害来源标注链

## 10. 新架构实施方式

### 10.1 第一阶段：先拆

先做的不是搭新层，而是先拆旧层。

阶段目标：

- 旧宿主映射链整体消失
- 手动攻击失效
- 自动攻击失效
- 表达仍能成立
- Trigger 仍能装载和激活
- 执行层代码还在，但拿不到宿主

这一步完成后，系统进入：

```text
表达成立
攻击失效
结构诚实
```

### 10.2 第二阶段：建立新宿主对象模型

建立：

- 固定宿主入口
- 宿主构造规格
- 宿主实例
- 宿主持有器
- 宿主工厂
- 宿主读档复用器
- 宿主时钟 / 驱动器

这一步结束后，宿主层作为正式运行时层存在，但入口还未恢复。

### 10.3 第三阶段：恢复手动入口

恢复顺序里手动入口先于自动入口。

原因：

- 手动入口更可控
- 更适合先验证宿主层是否成立

### 10.4 第四阶段：恢复自动入口

自动远程和自动近战统一改为读取宿主持有器。

这一步之后，自动攻击重新成立。

### 10.5 第五阶段：恢复双武器 / 组合技

双武器和组合技不单独补桥。

它们统一按：

- 宿主构造规格
- 固定入口
- 宿主实例

这条主线接回。

### 10.6 第六阶段：补完读档和长链稳定性

最后处理：

- 宿主读档复用
- 持续攻击不中断
- 宿主 tick 稳定性
- DevHarness 验证补齐

## 11. 风险判断

### 11.1 这是大改

这不是局部修复。

这是：

- 运行时 ownership 重构
- 主链重建
- 系统边界重划

所以它是大改造级工程。

### 11.2 最高风险点

最高风险点有 4 个：

- 宿主生命周期
- Job / stance / warmup 的运行时引用连续性
- 自动攻击接入口
- 双武器 / 组合技重新长成第二套系统

### 11.3 为什么仍然值得这么做

因为继续修现在这条路，风险不是更低，而是更隐蔽。

继续修的结果只会是：

- 错误 ownership 继续存在
- 桥接层继续增加
- 每个新功能都要重新补一条通路

这比一次性拆干净更危险。

---

## 12. DevHarness 对应要求

当前 DevHarness 已经有：

- 单远程测试芯片
- 单近战测试芯片
- 爆炸测试芯片
- Ability / Hediff / Passive 测试芯片
- 混合芯片
- 双持绑定测试芯片

但它还缺：

- 新宿主层下的固定入口验证
- 双武器宿主持有器验证
- 组合技宿主入口验证
- 宿主读档复用验证
- 宿主 tick / burst 连续性验证
- “攻击失效但表达仍成立”的中间缺陷阶段验证

本次重构完成后，DevHarness 必须围绕新宿主层补这些场景。

正式建议如下：

### 建议 1

先不写实现代码。

### 建议 2

先写拆除与重建实施计划。

### 建议 3

实施策略采用：

- 先拆错的系统
- 再搭对的系统

### 建议 4

- 攻击暂时不可用

- fallback
- 兼容桥
- 过渡宿主
- 旧映射兜底

## 14. 一句话定案

这次重构的正式方向不是：

- “继续修现成 Verb 宿主复用”

也不是：

- “回到旧 BDP 把宿主逻辑再塞回 Trigger”

而是：

```text
承认旧 BDP 已经证明自有宿主方向是对的，
然后把这条方向从 Trigger 中解放出来，
先拆干净当前错误宿主映射链，
再建设主模组正式的 BDP 自有 Verb 宿主层。
```
