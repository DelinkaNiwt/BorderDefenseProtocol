# 二次重构概念模型 v1

## 目的

这份文档不是实现计划。

它是二次重构正式设计前的“总模型”。

它要解决的问题是：

- BDP 这次到底要按哪些系统块来搭
- 每块系统的边界是什么
- 它们之间怎么流动
- 第一阶段最小闭环要覆盖哪些块
- 哪些外围功能从第一天就要留位置

## 一、总模型

二次重构建议按六块系统来理解 BDP：

1. 资源系统
2. 战斗体系统
3. 触发体装载系统
4. 表达系统
5. 入口与展示系统
6. 崩解与收尾系统

除此之外，再额外保留两类“支撑层”，但不把它们当业务核心：

- 工具收纳层
- 测试扩展层

其中：

- 前三块是核心真值块
- 第四块是核心业务块
- 第五块是对外投影块
- 第六块是跨块事务闭环块

事件总线不单独算第七块核心。

它只是：

- 状态变化广播工具
- 横切协作辅助层

工具收纳层和测试扩展层也不单独算业务核心。

它们是：

- 为主模组实现服务的支撑层
- 为验证和未来扩展服务的配套层

## 二、六块系统的边界

### 1. 资源系统

宿主建议继续是：

- `CompTrion`

它负责：

- 当前值
- 最大值
- 可用值
- 正式占用
- 预占用
- 持续消耗
- 冻结与恢复
- 资源不足检查

它不负责：

- 激活战斗体
- 激活芯片
- 组合判断
- 攻击表达

它对外提供的应该是明确资源语义，而不是业务结论。

### 2. 战斗体系统

宿主建议继续围绕：

- `CombatBodyState`
- 战斗体运行时门面
- 一个很薄的事务协调者

它负责：

- Inactive / Active / Collapsing / Cooldown
- 激活、主动解除、被动崩解的外层相位
- 战斗体期间的身体变化时机
- 冷却与崩解倒计时

它不负责：

- 槽位装载
- 芯片表达合成
- 按钮生成
- 自动攻击桥接

### 3. 触发体装载系统

宿主建议继续围绕收缩后的：

- `CompTriggerBody`

它负责：

- 槽位
- 装载
- 卸载
- 双手锁定
- 特殊槽
- 按侧切换状态机
- 槽位禁用
- 当前哪些芯片在“激活表达状态”

命名约束：

- 触发体内部稳定命名统一使用 `Main/Sub`
- 并固定约定：
  - `Main = 右`
  - `Sub = 左`
- 只有在和 RimWorld 身体部位事实直接对接时，才使用 `Left/Right`

它不该再负责：

- 资源真值
- 战斗体正式相位真值
- 自动入口桥接真值
- 全部 UI 生成

### 4. 表达系统

这是二次重构里最核心的业务层。

它负责：

- 芯片表达来源
- 左右表达合成
- 组合第三表达
- 主攻击投影
- 宿主类型投影
- 因子接口的应用点

这里建议再拆成四个内部概念：

- 表达来源
- 表达规则
- 表达结果
- 宿主投影

另外再预留一个“影响层”概念：

- 因子接口本身不直接生成表达
- 它只在表达参数、动作参数、资源参数、策略选择这些地方施加影响

其中按侧表达的内部稳定命名，也建议统一使用：

- `Main`
- `Sub`

### 5. 入口与展示系统

它负责把当前状态和表达结果投给外界。

至少分三条入口：

- 玩家手动入口
- 原版自动远程入口
- 原版自动近战入口

再加一类展示：

- 文本展示
- 信息卡展示
- 状态条展示
- 武器绘制与枪口展示

这一块只应该读取结果，不应该持有真值。

### 6. 崩解与收尾系统

这块单独列出来，是因为它不能再被当成“后面再补的细节”。

它负责：

- Trion 可用值耗尽后的被动崩解
- 受伤 / 手部损坏引发的功能收缩
- 卸下触发体后的两段式收尾
- 表达撤销
- 资源释放
- 快照恢复
- 组合失效后的撤销

这一块不是一个独立 owner，
而是一组必须从一开始就被设计进去的事务闭环。

## 三、两类支撑层

### 1. 工具收纳层

这层专门收纳那些会被多处复用、但本身不是模组需求的东西。

例如：

- 调试绘制
- 统一日志与诊断
- 通用 key / id 生成
- 宿主桥接辅助
- 小型数据转换
- 通用校验

这层的原则是：

- 可以通用
- 可以复用
- 但不承载具体业务规则

也就是说：

- 这里不能偷偷变成新的“业务垃圾堆”

### 2. 测试扩展层

这层建议以后做成独立后置测试模组。

它的定位不是给玩家发布内容，
而是：

- 用主模组暴露的接口和扩展点
- 挂入专门的测试内容
- 在游戏中验证主模组的真实运转情况

它适合承载：

- 测试芯片
- 测试组合
- 测试 Ability / Hediff
- 测试投射物
- 调试按钮
- 观察状态展示

这层的重要意义不只是“方便测试”，
还包括：

- 倒逼主模组接口做得足够清楚
- 倒逼扩展接入路径自然可用
- 倒逼重构结果具备真实内容扩展性

## 四、系统之间的数据流

### 1. 装载与资源流

大致顺序：

- 触发体装载系统决定当前装了什么
- 装载结果投给资源系统形成预占用需求
- 战斗体激活时再把预占用变成正式占用

这里最关键的边界是：

- 装载系统可以声明需求
- 资源系统才是真正记账者

### 2. 战斗体与装载流

大致顺序：

- 战斗体系统决定当前是否允许进入 Active
- 触发体系统决定当前哪些芯片可以转成激活表达
- 特殊槽和普通槽按各自规则进入激活状态

这里最关键的是：

- 战斗体决定“整体可用”
- 触发体决定“槽位与表达可用”

### 3. 装载与表达流

大致顺序：

- 激活中的槽位产出按侧表达来源
- 表达系统读取这些来源
- 根据左右关系与组合规则生成表达结果

这里最关键的是：

- 表达系统不直接改槽位
- 槽位系统也不直接决定最终主攻击结果

### 4. 表达与入口流

大致顺序：

- 表达系统生成当前表达结果
- 再分投到：
  - 玩家手动入口
  - 自动远程入口
  - 自动近战入口
  - 默认表面投影

这里最关键的边界是：

- 主攻击投影只是一种默认投影
- 不等于全部表达

### 5. 资源与表达执行流

大致顺序：

- 表达进入执行前先读资源系统
- 执行时用统一资源语义扣减 / 校验
- Ability / Verb / 组合表达都不自带另一套资源真值

### 6. 异常与收尾流

大致顺序：

- 任一异常源触发
  - Trion 可用值耗尽
  - 触发体卸下
  - 手部损坏
  - 战斗体解除
  - 组合失效
- 再进入统一收尾链：
  - 关表达
  - 撤组合
  - 释放资源
  - 恢复身体
  - 清入口投影

## 五、表达系统的内部模型

### 1. 表达来源

建议统一理解为：

- 不是“现成攻击对象”
- 而是“当前能被投影出去的表达候选”

来源至少分：

- 左手来源
- 右手来源
- 特殊槽来源
- 组合来源

### 2. 表达规则

这一层决定：

- 单侧怎么成立
- 双手怎么合成
- 混合时主攻击怎么投影
- 组合何时成立
- 组合是否额外生成第三表达

### 3. 表达结果

结果至少应包含：

- 当前所有可手动使用的表达
- 当前默认主攻击投影
- 当前对外默认表面投影
- 当前成立的第三表达

### 4. 宿主投影

建议按类型分流：

- `Verb` 投影
- `Ability` 投影
- `Hediff` 投影
- 特殊宿主投影

## 六、外围功能在总模型里的位置

### 1. FireMode

位置：

- 表达系统内部的局部规则模块
- 同时也是未来优先考虑实现“因子接口”的对象来源之一

原因：

- 它改变的是表达执行参数和默认表面
- 不是资源真值，也不是战斗体真值

第一阶段：

- 要留接口
- 不必一开始就做完整轴系

### 2. 多形态芯片

位置：

- 触发体装载系统与表达系统之间

原因：

- mode 会改变表达来源
- 也可能改变 Hediff / Stat / Ability
- 也很适合作为未来因子来源

第一阶段：

- 要留“表达来源可变”的口
- 不必先把全部 mode 业务做完

### 3. 特殊槽

位置：

- 触发体装载系统
- 战斗体系统的联动点

原因：

- 它不属于普通按侧切换
- 它和战斗体激活解除强关联

第一阶段：

- 必须留位置
- 可以先只支持最简单的全开全关

### 4. 双手锁定

位置：

- 触发体装载系统

原因：

- 这是装载与激活约束，不是表达层临时判断

第一阶段：

- 先留约束口
- 复杂细节第二阶段补齐

### 5. 视觉投影

位置：

- 入口与展示系统

原因：

- 它是表现投影，不是真值
- 但会反过来要求发射点与显示点一致

第一阶段：

- 只要先保留“展示宿主接口”位置
- 绘制细节可以稍后补

### 6. 手部损坏与槽位禁用

位置：

- 崩解与收尾系统
- 触发体装载系统

原因：

- 它影响槽位可用性
- 但来源是原版身体事实

第一阶段：

- 要先留“来自原版身体系统的约束输入”

### 7. 外部信息兼容表面

位置：

- 入口与展示系统

原因：

- 它本质上是“默认投影面”
- 不是攻击执行本身

第一阶段：

- 至少保留“当前默认表面投影”这个概念

### 8. 因子接口

位置：

- 表达系统与执行系统之间的影响层

原因：

- 它不直接负责主业务
- 它不是一份“修正表”
- 它更像一个统一因子值
- 平时默认是中性值
- 业务逻辑只是在原有逻辑上额外读一下这个值

当前最接近真实需求的理解是：

- 因子大概率主要和 Trion 天赋 / 基因 / 资质有关
- 未来可能被不同业务解释后影响：
  - 伤害
  - 子弹数量
  - 影响范围
  - 判定概率
  - 生成物耐久
  - 某些策略分支是否切换

这里最关键的约束是：

- 接口层只提供一个统一值
- 不在接口层提前拆成一堆“伤害因子 / 数量因子 / 范围因子”
- 由具体业务自己解释这个值怎么应用

第一阶段：

- 必须留“统一因子值”接口
- 必须留“因子提供者”接口
- 默认实现返回中性值
- 不要求立刻做具体天赋功能

## 七、第一阶段最小闭环的准确范围

第一阶段不是“只做攻击”。

第一阶段是做一个穿过六块系统的最小闭环。

建议范围如下：

### 必须打通

- 资源系统
  - 可用值
  - 正式占用
  - 预占用
  - 基本消耗
  - 释放
- 战斗体系统
  - Inactive
  - Active
  - Cooldown
  - 主动解除
- 触发体装载系统
  - 左右基本槽位
  - 装载
  - 激活
  - 关闭
  - 基本切换
- 表达系统
  - 单侧近战表达
  - 单侧远程表达
  - 主攻击投影
- 入口与展示系统
  - 1 个手动入口
  - 自动远程桥
  - 自动近战桥
  - 一个默认表面投影
- 崩解与收尾系统
  - 解除时表达撤销
  - 资源回收
  - 入口清理

### 先只留接口

- FireMode
- 多形态
- 特殊槽
- 双手锁定
- Ability
- Hediff
- 组合第三表达
- 视觉复杂投影
- 手部损坏细则
- 工具收纳层
- 测试扩展接口
- 因子接口

### 暂不展开细节

- 复杂双手节奏
- 复杂引导路径
- 复杂视觉补偿
- 复杂信息面板兼容

## 八、第二阶段重点扩展什么

当第一阶段最小闭环稳定后，
建议第二阶段重点补：

- 双手合成表达
- 混合主攻击投影
- FireMode 完整规则
- 特殊槽完整规则
- 多形态完整规则
- Ability / Hediff 正式接入
- 组合第三表达正式接入
- 基本视觉投影
- 工具收纳层整理
- 独立后置测试模组起步

## 九、第三阶段再补什么

建议第三阶段再补：

- 复杂视觉投影
- 枪口一致性完整补偿
- 外部信息面板兼容细节
- 调试与诊断工具
- 边界异常链补齐
- 如有必要，再评估是否把工具收纳层独立成前置工具库模组

## 十、后续实现阶段的硬规则

### 1. 每次实现前必须先回摘要，再回旧代码

顺序固定为：

1. 回看当前项目里对应的研究记录 / 决策记录 / 概念模型
2. 再回旧 BDP 中查相关代码，确认真实细节和时序
3. 最后再实现

不能只靠会话记忆或压缩后的印象直接开写。

### 2. 每次实现都先确认“这次做的是哪一块系统”

也就是先明确：

- 它属于六块业务系统中的哪一块
- 有没有同时碰到工具收纳层
- 需不需要为测试扩展层预留接口

### 3. 为测试模组暴露的接口，要按未来内容扩展接口来认真设计

虽然测试模组主要只给用户自己用，
但为了支持它而暴露的接口，
应视为未来内容扩展接口的第一批样板。

所以不能把它们做成临时小洞。

## 十一、当前我最建议你确认的三件事

基于现在这个模型，
最值得你先拍板的不是实现细节，
而是下面三件事：

### 1. 六块系统划分是否认可

也就是：

- 资源
- 战斗体
- 触发体装载
- 表达
- 入口与展示
- 崩解与收尾

### 2. 第一阶段最小闭环是否认可

也就是：

- 第一阶段要穿过六块系统
- 但很多外围功能只先留接口

### 3. 表达系统是否确认为上位骨架

也就是：

- “表达”高于“攻击”
- 组合技按第三表达处理
- 主攻击投影只是默认投影，不是唯一表达

## 十二、我当前的建议

我建议以这份 v1 作为接下来正式设计的基底。

下一步就不再继续铺大方向，
而是直接把它压成更可执行的东西：

- 核心对象图
- 第一阶段接口草案
- 第一阶段最小闭环的实现范围定义
