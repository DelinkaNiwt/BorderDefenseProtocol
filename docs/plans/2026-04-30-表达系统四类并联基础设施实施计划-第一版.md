# 表达系统四类并联基础设施实施计划（第一版）

> **For Codex:** 按本文任务顺序执行。每一阶段先补验证，再做最小实现；任何游戏内可见表现变化都视为失败，必须停下复查。

**Goal:** 让 `Verb`、`Ability`、`Hediff`、`Passive` 四类表达作为并联设施稳定接入，并为 `Combo` 建立统一的来源属性获取与计算机制。

**Architecture:** 保持 `FormalExpressionResult` 作为四类表达共同结果载体。新增类别中性的读取索引和 `Combo` 来源求值设施，让现有通道从同一份正式结果表读取，不改变现有游戏表现。`Dual` 继续只接收 `Verb`，`Combo` 才面向四类表达。

**Tech Stack:** RimWorld 1.6 Mod、C#、XML Def、PowerShell 烟测、现有 BDP 主模组与 DevHarness。

---

## 一、总验收红线

这是整理优化类工作，不是玩法改动。

修改前游戏中实测表现：

- `Verb` 芯片的手动攻击、自动攻击、远程、近战行为按现状运行。
- `Dual` 只作为双 `Verb` 攻击入口运行。
- 已有 `Combo` 型 `Verb` 行为按现状运行。
- `Ability` 表达按现状给 Pawn 增删 Ability。
- `Hediff` 表达按现状给 Pawn 增删 BDP 表达宿主 Hediff。
- `Passive` 表达按现状让紧急脱离等业务能读到许可。
- 玩家界面、Gizmo、攻击按钮、切换表现、Trion 消耗表现不应出现新增或消失。

修改后游戏中实测表现必须相同。

如果出现下列任一情况，本计划执行必须暂停：

- 已有芯片需要补 XML 字段才能继续工作。
- 已有攻击入口数量、图标、默认选择发生变化。
- 已有 Ability / Hediff 发布时机发生变化。
- 已有 Passive 许可判断结果发生变化。
- 已有 Combo / Dual 攻击表现发生变化。
- Trion 消耗、最低需求、容量占用在现有内容上发生变化。
- 新增日志刷屏、影响游戏运行或污染普通玩家体验。

## 二、本计划范围

本计划包含：

- 四类表达的并联结果索引。
- 四类表达的统一读取口。
- `Passive` 正式查询口。
- `Ability` / `Hediff` 继续通过现有宿主同步发布。
- `Combo` 来源属性获取与计算设施。
- `Combo` 生成四类正式结果的管线整理。
- 必要的烟测和游戏内回归检查。

本计划不包含：

- 新增第五类表达。
- 新增玩家可见 UI。
- 改变 `Dual` 的类别范围。
- 把 `Passive` 改成附属类别。
- 启用会改变现有表现的 Mode 玩法。
- 把 DevHarness 业务原型写入主模组。
- 修复需要改变游戏表现的历史行为问题。

说明：

- 如果整理过程中发现历史逻辑确实有错，但修复会改变游戏中表现，只记录为后续行为修复任务，不在本整理计划里直接启用。

### Step 2：新增 `ExpressionChannelIndex`

建议结构：

```csharp
using System.Collections.Generic;

namespace BDP.Core.Expressions
{
    /// <summary>
    /// 正式表达结果的四类并联索引。
    /// 它只服务读取，不改变结果生成与发布行为。
    /// </summary>
    internal sealed class ExpressionChannelIndex
    {
        public IReadOnlyList<FormalExpressionResult> AllResults { get; set; }
        public IReadOnlyList<FormalExpressionResult> VerbResults { get; set; }
        public IReadOnlyList<FormalExpressionResult> AbilityResults { get; set; }
        public IReadOnlyList<FormalExpressionResult> HediffResults { get; set; }
        public IReadOnlyList<FormalExpressionResult> PassiveResults { get; set; }
        public IReadOnlyDictionary<string, IReadOnlyList<FormalExpressionResult>> AbilityResultsByDefName { get; set; }
        public IReadOnlyDictionary<string, IReadOnlyList<FormalExpressionResult>> HediffResultsByDefName { get; set; }
        public IReadOnlyDictionary<string, IReadOnlyList<FormalExpressionResult>> PassiveResultsByKey { get; set; }

        internal static ExpressionChannelIndex Empty()
        {
            return new ExpressionChannelIndex
            {
                AllResults = new List<FormalExpressionResult>(),
                VerbResults = new List<FormalExpressionResult>(),
                AbilityResults = new List<FormalExpressionResult>(),
                HediffResults = new List<FormalExpressionResult>(),
                PassiveResults = new List<FormalExpressionResult>(),
                AbilityResultsByDefName = new Dictionary<string, IReadOnlyList<FormalExpressionResult>>(),
                HediffResultsByDefName = new Dictionary<string, IReadOnlyList<FormalExpressionResult>>(),
                PassiveResultsByKey = new Dictionary<string, IReadOnlyList<FormalExpressionResult>>()
            };
        }
    }
}
```

### Step 3：新增 `ExpressionChannelIndexBuilder`

- Ability 用 `AbilityDefName` 建索引。

- 返回集合用新列表，避免下游修改原始快照。
- 不在这里做条件判断、宿主发布或业务逻辑。

### Step 2：新增 `ComboSourceFieldResolver`

职责：

- 只负责字段级求值。
- 不知道 `Verb`、`Ability`、`Hediff`、`Passive` 的业务含义。
- 不生成正式结果。
- 不改写来源结果。

最小方法：

```csharp
internal static ComboResolvedFieldValue<float> ResolveFloat(float? explicitValue, ComboValueResolveMode? mode, float chipAValue, float chipBValue)
internal static ComboResolvedFieldValue<int> ResolveInt(int? explicitValue, ComboValueResolveMode? mode, int chipAValue, int chipBValue)
internal static string ResolveString(string explicitValue, ComboValueResolveMode? mode, string chipAValue, string chipBValue)
internal static IReadOnlyList<T> ResolveList<T>(IReadOnlyList<T> explicitValue, ComboValueResolveMode? mode, IReadOnlyList<T> chipAValue, IReadOnlyList<T> chipBValue)
```

规则：

```text
显式值存在 -> 显式值
显式值不存在且 mode 为空 -> 不求值
mode = FollowChipA -> 来源 A
mode = FollowChipB -> 来源 B
mode = Sum -> 两侧求和，仅数字
mode = Average -> 两侧平均，仅数字
mode = Max -> 两侧最大，仅数字
mode = Min -> 两侧最小，仅数字
```

兼容约束：

## 十二、风险与处理

### 1. Combo Trion 风险

风险：

- 统一求值后可能改变已有 Combo 的 Trion 表现。

处理：

- 先查现有 ComboDef 是否有 Trion 行为样本。
- 有样本就先锁基线。
- 会改变游戏表现的 Trion 修正不进入本整理计划。

### 2. Passive 读取风险

风险：

- 业务方从手扫结果改为正式读取口时，可能漏掉 `IsAvailable` 或 key 大小写规则。

处理：

- `ExpressionChannelIndexBuilder` 统一大小写规则。
- `HasPassiveKey` 只认可用结果。
- 紧急脱离烟测必须覆盖。

### 3. Ability / Hediff 发布风险

风险：

- 结果级追踪可能误改现有按 Def 聚合逻辑。

处理：

- 发布追踪只旁路记录。
- `GainAbility`、`RemoveAbility`、`AddHediff`、`RemoveHediff` 的调用条件保持现状。

### 4. Verb 回归风险

风险：

- 抽工厂时误动 `Verb` 的默认主攻击、手动入口或 formal host 槽位。

处理：

- `DefaultPrimaryExpressionSelector` 不因 Combo 改动而选择 Combo 为默认主攻击。
- `TriggerBodyVerbHostManager` 槽位规则不改。
- FormalHost 烟测必须跑。

### 5. Mode 风险

风险：

- 让 `Mode` 真正生效可能改变已有带 `Modes` 配置的芯片表现。

处理：

- 本计划不启用新的 Mode 玩法。
- 只保持 `ModeKey` 作为已有字段被稳定携带。
- 运行时 `GetChipModeKey` 的真实形态接入另开计划，除非能证明对现有内容零表现变化。
