# 战斗体切换闭环重建设计（第一版）

## 1. 目的

本文不是复述旧 BDP 的类名，也不是规定必须照抄旧实现。

本文只定义一件事：

- 新 BDP 应如何在不破坏三真值边界的前提下，重新建立战斗体的**进入 / 主动解除 / 被动崩解 / 收尾恢复**正式闭环。

本文把旧 BDP 当作**行为真相参考**，把当前新 BDP 当作**架构约束现实**。

---

## 2. 本文约束

### 2.1 三真值边界不变

战斗体不能长成第四个 owner。

正式真值仍然只有：

- `CompTrion`：资源账本真值
- `CombatBodyState`：整体相位真值
- `CompTriggerBody`：装载与局部激活真值

战斗体主链只负责：

- 编排进入事务
- 编排退出事务
- 裁定整体崩解
- 广播相位变化

它不能再持有：

- 一套额外资源账本
- 一套 Trigger 镜像真值
- 一套凌驾于三真值之上的总状态

### 2.2 退出主分类

退出只有两大类：

- 主动解除
- 被动崩解

`紧急脱离` 不与它们并列。

`紧急脱离` 的正确位置是：

- 被动崩解链中的一个**可选附加阶段**

也就是说：

- 主动解除 = 正常退出
- 被动崩解 = 失败退出
- 紧急脱离 = 失败退出过程中可能追加的一段特殊处理

### 2.3 Snapshot 必须是正式协作者

Snapshot 不是顺手补的工具，也不是分散在多处的临时逻辑。

它必须正式参与：

- 进入前建立回滚锚点
- 退出时恢复真身

但它不应升级成新的总控层。

---

## 3. 当前问题归纳

当前新 BDP 的主链骨架已经存在：

- 相位真值存在
- 激活/退出事务存在
- Trion 绑定存在
- Trigger 联动存在
- 崩解相位与 90 tick 收尾存在

但当前仍缺一块关键闭环：

- **还没有一个正式位置，负责把 Pawn 从真身切到战斗体前台，再从战斗体前台切回真身。**

因此当前缺口 1 和缺口 2 本质上应合并理解为：

- 宿主切换事务没有正式落点
- Snapshot / Cleanup / Restore 还没有作为宿主切换事务的一部分被正式接回

---

## 4. 最小结构设计

本文只保留最小必要结构，不做软件工程式过度拆分。

### 4.1 `CompCombatBodyHost`

职责：

- 继续作为 Pawn 上的战斗体宿主位
- 持有战斗体主链对象
- 额外持有一个最小宿主状态 `HostState`

它不负责：

- 亲自执行宿主变换细节
- 亲自实现 Snapshot 采集/恢复

### 4.2 `HostState`

这是一个很小的持久状态对象，只保存宿主切换需要记住的事实。

最小应包含：

- `HasSnapshot`
- `TransformationApplied`
- `SnapshotData`
- 真身托管内容
- 战斗体前台托管内容

它不持有：

- 资源总账
- Trigger 总状态
- 相位真值

### 4.3 `PawnCombatBodyBridge`

这是宿主事务桥，是本设计的核心。

它只负责两件事：

- `ApplyCombatBodyTransformation()`
- `RestoreFromCombatBody()`

含义分别是：

- 进入战斗体时，把 Pawn 正式切到战斗体前台
- 退出战斗体时，把 Pawn 正式恢复回真身

它不负责：

- 相位真值裁定
- Trigger 真值裁定
- Trion 真值裁定

### 4.4 `CombatBodySnapshotService`

这是桥的正式协作者。

它只提供两类能力：

- `Capture`
- `Restore`

它不负责编排进入链，也不负责编排退出链。

---

## 5. 相位模型

正式相位只保留：

- `Inactive`
- `Active`
- `Collapsing`
- `Cooldown`

### 5.1 `Inactive`

- 当前整体未进入战斗体
- 可以检查是否允许激活

### 5.2 `Active`

- 当前整体已正式进入战斗体
- Trigger 局部激活、表达运行、崩解检查，只有在此相位才有意义

### 5.3 `Collapsing`

- 当前已正式进入崩解态
- 但尚未完成整体退出和恢复

这不是装饰相位，而是正式相位。

### 5.4 `Cooldown`

- 当前整体退出已正式发生
- 但尚未回到允许再次激活的 `Inactive`

---

## 6. 正式闭环

## 6.1 进入闭环

### 前置检查

至少检查：

- 当前相位允许激活
- 资源层可正式锁定所需 Trion
- 宿主层允许应用战斗体变换

### 正式顺序

整体激活按以下顺序成立：

1. 资源锁定成功
2. 宿主应用战斗体变换
3. 相位进入 `Active`
4. 广播相位变化

这里的硬约束是：

- 宿主未切换前，不能先宣称 `Active`

### 宿主变换内部顺序

`PawnCombatBodyBridge.ApplyCombatBodyTransformation()` 内部最小顺序应为：

1. `SnapshotService.Capture`
2. 收起真身前台
3. 挂上战斗体前台
4. 做进入侧 cleanup
5. 标记 `TransformationApplied=true`

---

## 6.2 主动解除闭环

主动解除的定义：

- 玩家主动、正常、非失败语义地退出战斗体

### 正式顺序

1. 释放整体锁定资源
2. 关闭全部局部槽位
3. 恢复宿主
4. 进入 `Cooldown` 或 `Inactive`
5. 广播相位变化

### 宿主恢复内部顺序

`PawnCombatBodyBridge.RestoreFromCombatBody()` 内部最小顺序应为：

1. 清战斗态残留
2. `SnapshotService.Restore`
3. 最终 cleanup
4. 清空 `HostState`

### 恢复顺序

`SnapshotService.Restore` 的恢复顺序继续沿用旧 BDP 的事实：

1. 衣物
2. 背包/物品
3. Need
4. Hediff

---

## 6.3 被动崩解闭环

被动崩解的定义：

- 因失败条件成立而被迫退出战斗体

### 上游来源

允许有多条来源，例如：

- Trion 可用值耗尽
- 身体条件失败
- 倒地
- 关键部位摧毁
- 其他以后新增的失败源

### 统一入口

虽然来源可以多条，但正式进入崩解只能汇总到一个入口。

上游来源只能做：

- 提出崩解请求

它们不能做：

- 各自展开半套退出/恢复逻辑

### 正式顺序

1. 多来源汇总到单一崩解入口
2. `Active -> Collapsing`
3. 进入崩解表现期
4. 崩解表现结束后进入统一退出/恢复链

这里的关键是：

- `Collapsing` 必须被承认为正式相位
- 崩解不是“立即消失”

---

## 6.4 紧急脱离附加段

紧急脱离不是一级退出类型。

它的正确位置是：

- 被动崩解收尾链中的可选附加段

也就是说：

- 不是 “主动解除 / 紧急脱离 / 崩解” 三并列
- 而是 “主动解除 / 被动崩解” 两并列
- `紧急脱离` 挂在 `被动崩解` 之内

### 紧急脱离的作用

它允许在被动崩解链中追加特殊处理，例如：

- 位置转移
- 一次性逃生芯片消耗
- 额外日志与表现
- 额外宿主后果

但它不改变此次退出的本质：

- 这次退出仍然属于被动崩解

### 6.4.1 为什么需要一个中间协调点

紧急脱离依赖于芯片搭载事实。

如果没有中间协调点，最容易出现两种越位：

- CombatBody 退出链直接下钻 Trigger 槽位和芯片细节
- GUI 直接下钻 Trigger / 芯片细节自行判断是否存在紧急脱离

这两种做法都会把边界重新搅乱。

因此这里需要一个**很窄的能力协调点**，
专门回答一件事：

- 当前宿主在当前 Trigger 搭载事实下，是否存在可用的“紧急脱离附加段能力”

### 6.4.2 这个协调点的职责

这里建议增加一个很小的协调对象，概念上可命名为：

- `CombatBodyEmergencyEscapeResolver`

它不是新的主链 owner，也不是新的总协调器。

它只负责：

- 读取 Trigger 正式读取口
- 读取芯片正式能力声明
- 解析出一个**只读结论**

它不负责：

- 修改 `CombatBodyState`
- 修改 `CompTriggerBody`
- 直接消耗资源
- 直接执行退出链

### 6.4.3 它输出什么

这个协调点输出的结果应尽量小。

最小只需回答：

- 当前是否可用
- 来源芯片是谁
- 若执行该附加段，是否需要一次性消耗/销毁来源芯片
- 当前不可用时的原因键

它输出的是：

- **能力解析结果**

而不是：

- 新的业务真值

### 6.4.4 边界划分

#### 芯片侧

芯片只声明：

- 自己是否提供紧急脱离能力
- 这项能力的最小参数

芯片不负责：

- 判定整体是否崩解
- 判定现在是否进入退出链
- 直接调用 CombatBody 主链

#### Trigger 侧

Trigger 只负责提供：

- 当前装载事实
- 当前局部激活事实
- 当前可读的芯片声明来源

Trigger 不负责：

- 把紧急脱离能力升级成整体退出裁定
- 直接决定是否执行紧急脱离附加段

#### CombatBody 侧

CombatBody 只负责：

- 在被动崩解统一退出链中，决定是否消费该能力解析结果

CombatBody 不负责：

- 扫描 Trigger 内部槽位细节
- 直接硬编码某颗芯片或某个槽位

#### GUI 侧

GUI 只负责显示正式结果。

GUI 可以读取：

- CombatBody 正式读口
- Trion 状态扩展口
- 必要时读取“紧急脱离能力解析结果”的只读投影

GUI 不负责：

- 自己扫描 Trigger 搭载
- 自己裁定业务条件

### 6.4.5 它如何接入现有正式边界

这个协调点应只通过正式边界工作：

- Trigger 事实从 `TriggerSurfaceAccess` 获取
- CombatBody 收尾仍由 CombatBody 退出链统一执行
- Trion GUI 仍通过现有扩展口显示

因此它的正确位置是：

- 一个靠近 CombatBody 退出链的窄解析层

而不是：

- 嵌进 Trigger 真值层
- 嵌进 GUI 层
- 变成新的跨系统总控

### 6.4.6 它与紧急脱离附加段的关系

被动崩解链中，
CombatBody 退出链只做下面的判断：

- 当前是否存在可用的紧急脱离附加段能力

如果答案是：

- 否：继续普通崩解收尾
- 是：在统一退出链里追加“紧急脱离附加段”

这里的关键点是：

- **紧急脱离附加段是否存在，由协调点解析**
- **紧急脱离附加段是否执行，由 CombatBody 退出链裁定**

两者不能混成一个对象。

---

## 7. 局部失效与整体崩解的边界

手 / 臂 / 肩缺失这类情况，本质上首先属于：

- Trigger 局部能力失效

它们应导致：

- 对应侧槽位禁用

但它们不自动等于：

- 战斗体整体崩解

如果未来某条规则要求“局部失效足以升级为整体崩解”，
也必须通过：

- CombatBody 正式崩解入口裁定

而不能由 Trigger 自己越权判定。

---

## 8. 失败回滚规则

## 8.1 进入失败

### 资源未锁定

- 什么都不提交
- 不切相位
- 不切宿主

### 宿主变换失败

- 立刻回滚宿主侧已做步骤
- 释放刚刚锁定的资源
- 不允许提交 `Active`

原则：

- 只有当宿主切换完成后，才允许正式进入 `Active`

## 8.2 退出失败

退出链不允许留下“假 Active”。

即使部分恢复失败，也必须保证：

- 资源已释放
- 局部槽位已关闭
- 相位进入可解释状态

如果宿主恢复未完整成功：

- 可以留下明确残留信息
- 但不能让整体状态悬空

---

## 9. 本阶段明确不纳入

本设计当前不展开：

- Hediff 内部轮询细节
- HealthCard 图标
- 崩解括号文本
- 按钮具体摆放位置
- 运行态受击损耗细节

这些都不是本轮“主链闭环重建”的核心。

---

## 10. 本设计的最终落点

本设计最终要达成的不是“多做几个对象”，
而是把战斗体切换正式收成一句话：

- **战斗体的进入、主动解除、被动崩解与收尾恢复，都必须收口到一条不破坏三真值边界的正式闭环；其中 Pawn 宿主切换由宿主事务桥负责，Snapshot 作为正式协作者参与，但两者都不能膨胀成新的总控中心。**
