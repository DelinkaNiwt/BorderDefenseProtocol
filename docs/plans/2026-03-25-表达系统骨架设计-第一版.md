# 表达系统骨架设计（第一版）

## 目标

这份设计文档用于正式钉死主模组内部“表达系统”的第一版骨架。

它当前优先解决的不是：

- 测试模组怎么读取
- 哪个旧功能先补回
- 哪个按钮先重新出现

它优先解决的是：

- 主模组内部，表达系统到底是什么
- 它和 Trigger、CombatBody、Trion 的边界怎么切
- 它自己内部应该分成哪些层
- 这些层之间的数据应该怎样流动
- 特殊侧武器类表达与双手锁定视觉例外应落在哪一层

## 目录裁定

表达系统目录第一版固定拆成六层：

- `Core/Expressions/Access`
- `Core/Expressions/Config`
- `Core/Expressions/Contract`
- `Core/Expressions/Model`
- `Core/Expressions/Pipeline`
- `Core/Expressions/Projection`

其中：

- `Access` 只放模组内正式读取入口与表面
- `Config` 只放作者原始芯片表达配置
- `Contract` 只放主模组正式承认的芯片表达契约与契约解释器
- `Model` 只放结果对象与投影结果对象
- `Pipeline` 只放内部运算模块与接口
- `Projection` 只放默认主攻击、手动入口、视觉、说明四类投影模块与接口

这些目录当前统一视为：

- 主模组内部层

也就是说：

- 里面的对象
- 里面的接口
- 里面的实现

当前都不应直接对外开放。

后续如果表达系统需要正式对外读取面，
应单独建立新的 formal surface，
而不是把 `Config / Contract / Model / Pipeline / Projection` 直接公开给外部。

当前主模组内部其它系统如果需要访问表达系统，
应优先统一走 `Access` 层，
而不是直接 new `Pipeline / Projection` 实现类。

当前 `Access` 层第一版已收口为统一正式读取入口：

- `Snapshot`
- `ManualProjection`
- `VisualProjection`
- `InfoProjection`

也就是说：

- 其它系统如果只是要读表达系统当前正式答案
- 应先从 `Access` 层拿读取面
- 不应直接 new 手动入口投影器、视觉投影器、说明投影器

当前不允许把：

- 芯片声明契约
- 结果对象
- 内部运算模块
- 投影模块

重新混回同一目录。

当前已新增的上游约束是：

- 表达系统的正式芯片输入应优先来自 `Core/Chips`
- 表达系统不再把 `ThingDef.GetModExtension<ChipExpressionConfig>()` 当作长期正式总入口
- 芯片定义层只把表达块以正式句柄形式转交进来，不复制表达系统内部条目对象

## 一、先下总结论

### 1. 表达系统不是按钮系统，也不是攻击系统

表达系统更上位。

它先回答：

- 当前正式成立了哪些表达结果

然后才继续回答：

- 哪些结果变成按钮
- 哪些结果被选成默认主攻击
- 哪些结果用于视觉读取
- 哪些结果用于说明面板

### 2. 表达系统必须先有“真实结果总表”，再有各种投影

后续所有按钮、默认主攻击、视觉、说明面板，
都必须从同一份正式结果总表出发。

不能允许：

- 按钮层自己猜一套
- 视觉层自己猜一套
- 默认主攻击层再偷做一套“系统真相”

### 3. 特殊侧不是普通第三路并列武器输入

特殊侧芯片默认是整组同时激活。

因此在武器类表达上，特殊侧必须拥有更高优先级：

- 如果特殊侧当前存在武器类表达
- 则它拦截 Main / Sub 的武器类表达
- 当前武器类结果只保留特殊侧这一个单侧表达
- 特殊槽只允许正式表达出一个武器类结果，禁止多个武器类同时成立

这条裁定只作用于：

- 武器类表达

不自动吞掉：

- `Ability`
- `Hediff`
- `Passive`

### 4. 双手锁定武器允许“结果单侧、视觉双侧”

某些双手锁定类武器在结果层与控制层中仍然只是：

- 单侧表达

但在视觉层允许被伪装成：

- 双手持有
- 双侧占位
- 看起来像双侧表达

这条例外只能停留在视觉层：

- 不反向改写结果层身份
- 不反向改写按钮层
- 不把单侧表达偷换成双侧结果

## 二、表达系统与外围系统的边界

### 1. Trigger 提供什么

Trigger 向表达系统提供的是：

- 当前正式激活事实
- 当前芯片所属侧别
- 当前芯片形态

Trigger 不负责：

- 直接回答当前表达结果
- 直接回答默认主攻击
- 直接回答该画什么

这里补一条正式收口裁定：

- 表达系统不直接把“已装载”或“未禁用”当成自己的输入条件
- 这些条件应先由 Trigger 内部消化
- 对表达系统来说，真正进入表达链的 Trigger 上游事实应以“当前正式激活结果”为主

### 2. CombatBody 提供什么

CombatBody 向表达系统提供的是：

- 某些来源是否允许成立所需的前置状态

CombatBody 不负责：

- 生成表达结果
- 保管表达结果
- 选择默认主攻击

### 3. Trion 提供什么

Trion 向表达系统提供的是：

- 资源相关前置条件是否满足

Trion 不负责：

- 解释来源
- 保存表达结果
- 替表达系统做优先级裁定

### 4. 表达系统自己不持有什么

表达系统不能自己持有：

- Trigger 真值
- CombatBody 相位真值
- Trion 真值

它只能读取这些系统已经正式成立的事实，
然后生成：

- 表达结果
- 投影结果

## 三、表达系统内部九层骨架

## 0. 芯片契约解释层

### 作用

把作者写在芯片 Def 上的原始配置，
解释成主模组正式承认的芯片契约。

### 它回答什么

- 这枚芯片有哪些统一条目
- 每条条目属于哪一类
- 当前有哪些形态块
- 当前形态块如何对条目执行 `Append / Replace / Disable`
- 条目之间是否显式声明了轻量关系

### 它不回答什么

- 当前是否成立
- 当前按钮是谁
- 当前默认主攻击是谁

### 当前裁定

这层必须独立存在于：

- `Core/Expressions/Contract`

`Pipeline` 不再直接解释原始芯片配置。

### 不接受的旧路径

以下旧路径不再允许继续作为未来主结构：

- `Config -> Pipeline`
- `Config -> declaration provider -> Pipeline`

现在正式要求改为：

- `Config -> Contract -> Pipeline -> Projection`

这样做不是为了多加一层，
而是为了把“作者怎么写”和“主模组正式承认什么”明确切开。

## 1. 来源收集层

### 作用

把上游正式事实整理成当前可参与表达计算的“来源材料表”。

### 它回答什么

- 当前有哪些来源材料
- 每条来源来自哪枚芯片
- 来自 Main、Sub 还是 Special
- 属于哪一大类
- 当前是否启用
- 当前是否满足成立前提

### 它不回答什么

- 当前结果是什么
- 当前主攻击是谁
- 当前该显示什么按钮

## 2. 单侧结果层

### 作用

分别整理：

- Main 当前正式成立了什么
- Sub 当前正式成立了什么
- Special 当前正式成立了什么

### 它回答什么

- 每一侧当前有哪些正式结果
- 哪些是武器类
- 哪些是能力类
- 哪些是状态类
- 哪些是被动类
- 每个结果当前是否可用

### 特殊侧武器类裁定

在武器类表达上：

1. 先看 Special 是否存在武器类表达
2. 如果存在，则拦截 Main / Sub 的武器类表达
3. 当前武器类结果只保留 Special 这一份单侧表达
4. Special 当前只允许正式表达出一个武器类结果

## 3. 双侧关系重算层

### 作用

只处理 Main 与 Sub 已成立结果之间的高层关系。

### 它回答什么

- 是否形成双武器结果
- 是否形成组合技结果
- 是否形成非攻击联动结果
- 这些高层结果与原始左右结果的关系是什么

### 它不负责什么

- 不处理 Special 的武器类唯一化裁定
- 不直接做按钮和视觉

## 4. 完整结果总表层

### 作用

把这一刻真正正式成立的所有结果统一收口成一份总表。

### 它回答什么

- 当前正式成立了哪些结果
- 每个结果属于哪一类
- 每个结果属于哪种来源关系
- Main
- Sub

## 四、执行边界补充

### 1. 这次重构不做长期双轨

这次允许短暂迁移状态，
但不允许把旧四列表长期保留成并行主路径。

原因很简单：

- 会让内容作者不知道正式标准到底是哪套
- 会让 `Pipeline` 和 `Projection` 长期背着错误历史包袱
- 会让边界文档和代码事实长期冲突

### 2. `Access` 是模组内正式入口，`Contract` 不是

`Contract` 是表达系统内部正式层，
不是给表达系统外部随便读取的入口层。

表达系统外部如果只是要拿当前结果，
仍然应走：

- `Access`

而不是直接摸：

- `Contract`
- `Pipeline`
- `Projection`

这次新增 `Contract`，
解决的是主模组内部边界问题，
不是为了把内部对象直接开放出去。

### 3. 当前已落地的骨架事实

截至当前这轮实现，
以下骨架事实已经成立：

- `Access / Config / Contract / Model / Pipeline / Projection` 六层目录已成立
- 主读取入口仍统一收口在 `Access`
- `Config -> Contract -> Pipeline -> Projection` 已接通为主路径
- `Contract` 已拥有最小解释器、最小校验结果、最小契约对象
- 说明投影已能附带当前活跃芯片的契约诊断摘要

截至当前这轮实现，
以下内容仍属于后续扩展而非已完成事实：

- 完整模式生态
- 复杂从属关系驱动的按钮分组
- 更细的外部正式读取面

这样区分是为了防止文档先把未来能力写成既成事实。
  - Special
  - 双侧高层结果
- 每个结果当前是否可用
- 每个结果是否允许进入后续投影

### 它的重要性

这是表达系统真正的总账本。

后续所有投影层都必须只读它，
而不能自己重新拼业务。

## 5. 默认主攻击投影层

### 作用

在完整结果总表里选出：

- 默认主远程
- 默认主近战
- 场景默认主攻击决策

### 它回答什么

- 当系统分别需要默认主远程、默认主近战、场景默认主攻击决策时，应各自读取谁

### 这里必须额外钉死

- 默认主远程和默认主近战不是互斥二选一
- 它们是两条并列默认读取线
- 同一时刻可以同时存在默认主远程与默认主近战
- 后续实现时不能把它误做成“只能二选一留下一个默认主攻击”

当前还要补一条实现阶段约束：

- 在结果对象尚未正式携带“近战 / 远程武器类型”字段前
- 默认主远程与默认主近战宁可暂时留空
- 也不要为了先跑起来，错误地把同一个武器结果同时塞进两条默认线

### 它不等于什么

- 不等于全部真实结果
- 不等于按钮集合
- 不等于视觉当前对象

## 6. 手动入口投影层

### 作用

把完整结果总表中的一部分结果投影成玩家可操作入口。

### 它回答什么

- 当前有哪些手动入口组
- 每组入口对应哪个正式结果
- 每组内部有哪些直接操作入口
- 哪些结果虽然成立，但不生成手动入口

### 关键边界

- 按钮数量不等于真实结果数量
- 一个按钮可以不止一个操作入口

## 7. 视觉读取投影层

### 作用

给视觉层与执行跟随层提供当前应如何表现的正式答案。

### 它回答什么

- 当前常驻该画什么
- 当前执行时应跟随谁
- 当前枪口或发射基准应跟随谁
- 当前是否进入双武器视觉
- 当前是否进入组合技视觉
- 当前是否需要“结果单侧、视觉双侧”的双手锁定伪装

### 关键边界

- 视觉伪装不能反向污染结果层

这里要明确：

- 表达系统只给出正式视觉读取结果
- 如果视觉宿主系统自己还没成型，怎么处理是宿主层自己的事
- 这不应回写成表达系统内部字段或表达系统内部回退策略


## 8. 信息说明投影层

### 作用

给说明面板、调试面板、后续正式读取接口提供结构化说明结果。

### 它回答什么

- 当前有哪些正式结果
- 哪些是 Main / Sub / Special
- 哪些是高层新结果
- 默认主攻击是谁
- 当前执行表达是谁
- 哪些结果只是状态、能力、被动，不应被误看成武器

这里也要明确：

- 表达系统只给出正式信息读取结果
- 如果信息宿主系统自己还没成型，怎么兼容是宿主层自己的事
- 这不应写回表达系统内部结果对象


## 四、第一版最小字段要求

## 1. 来源材料最少字段

- 来源稳定编号
- 来源芯片身份
- 侧别
- 顶层大类
- 当前形态启用状态
- 成立条件
- 显示名
- 局部 Trion 参数声明

这里的“成立条件”指的是：

- 该来源进入表达链后，表达系统自己仍需要判断的业务前提

它不再包括：

- 是否已装载
- 是否已禁用

因为这两件事应先由 Trigger 处理，并折叠进“当前是否已经正式激活”

## 2. 单侧结果最少字段

- 结果稳定编号
- 所属侧
- 结果类别
- 显示名
- 当前是否可用
- 当前是否可进入后续投影

## 3. 双侧高层结果最少字段

- 结果稳定编号
- 高层关系类型
  - 双武器
  - 组合技
  - 非攻击联动
- 参与输入结果
- 当前是否成立
- 当前是否可用

## 4. 完整结果总表最少字段

- 全部正式结果集合
- 当前默认主远程
- 当前默认主近战
- 当前场景默认主攻击决策
- 当前执行表达
- 当前是否存在 Special 武器类拦截

## 5. 手动入口投影最少字段

- 入口组稳定编号
- 对应结果编号
- 入口组显示名
- 入口组内部操作入口列表

其中“入口组内部操作入口列表”当前已单独作为正式数据形状存在，
用于表达：

- 这一组入口属于哪个正式结果
- 这一组里实际有哪几个入口项

但这不等于：

- 现在已经正式确定哪些结果必定生成按钮
- 当前已经完成按钮宿主回接

## 6. 视觉读取投影最少字段

- 当前常驻显示对象集合
- 当前执行跟随对象
- 当前枪口 / 发射基准跟随对象
- 当前视觉关系类型
  - 普通单侧
  - 双武器
  - 组合技
  - 双手锁定视觉伪装

当前第一版已把这些字段中的“读取位”正式化为：

- 常驻显示结果标识集合
- 执行跟随结果标识
- 枪口 / 发射基准跟随结果标识

但当前仍未表示为：

- 视觉宿主已经正式接线完成
- 常驻显示规则已经全部落实

## 7. 信息说明投影最少字段

- 当前结果说明列表
- 结果层级关系
- 默认主攻击说明
- 执行表达说明

当前第一版已把说明层从“纯文本行”推进到：

- 文本说明列表
- 结构化说明条目列表
- 默认主远程结果标识
- 默认主近战结果标识
- 当前执行表达结果标识

这表示说明层现在已经开始具备：

- 给 UI 读取
- 给调试读取
- 给后续可视化读取

所需的正式数据形状，
但不表示最终 UI 已经完成。

## 五点五、模块拆分裁定

第一版表达系统内部运算与投影，适合拆且能拆的模块应直接拆开，不保留“大而全”中间件。

## 1. 内部运算模块

表达系统内部运算至少拆为：

- `来源收集器`
- `来源过滤器`
- `单侧结果生成器`
- `特殊侧武器裁定器`
- `双侧关系重算器`
- `完整结果装配器`

### 裁定说明

- `来源过滤器` 单独存在，不并回来源收集器
- `特殊侧武器裁定器` 单独存在，不并回单侧结果生成器
- `完整结果装配器` 单独存在，不让双侧关系重算器顺手兼任总表生成

## 2. 投影模块

表达系统投影至少拆为：

- `默认主攻击选择器`
- `Verb 宿主解析器`
- `手动入口投影器`
- `手动入口宿主解析桥`
- `视觉投影器`
- `说明投影器`

### 裁定说明

- 默认主攻击选择器不兼任按钮投影
- `Verb 宿主解析器` 不兼任默认主攻击选择
- `Verb 宿主解析器` 不反向决定哪条结果才是系统真相
- `手动入口宿主解析桥` 不反向决定哪些结果应生成入口
- 视觉投影器不兼任说明投影
- 说明投影器不兼任外部正式接口

## 2.5 结果到宿主实例的映射器裁定

当前表达系统继续往下落地时，
必须单独承认一类新模块：

- `结果到宿主实例的映射器`

它当前至少包括两条线：

- `FormalExpressionResult -> Verb 宿主实例`
- `ManualEntryProjection -> Gizmo 宿主实例`

### 这类模块最适合落在哪里

第一版最适合落在：

- `Core/Expressions/Projection`

而不是：

- `Trigger`
- patch
- `FormalExpressionResult`

### 原因

因为它本质上回答的是：

- 这条正式结果如果要落到某个宿主读取者
- 当前应怎样被翻译成宿主能消费的实例

这仍然属于投影问题，
不属于结果真相本身。

### 它应该回答什么

- 当前这条正式结果能不能解析到真实宿主实例
- 如果能，实例是谁
- 如果不能，诚实返回空

### 它不应该回答什么

- 当前谁才是主攻击
- 左右手 / 特殊侧谁优先
- 多表达规则如何成立
- 哪些结果应生成按钮
- 是否为了兼容而伪造宿主实例

### 为什么不能放进 Trigger

一旦放回 Trigger，
就很容易重新退化成旧 BDP 的模式：

- `CompTriggerBody` 一边持有运行时宿主
- 一边决定主攻击
- 一边决定自动入口
- 一边再把这些真相喂给原版

这会重新把表达真相和执行宿主绑死。

### 为什么不能放进 patch

patch 只该做：

- 调桥
- 有结果就接
- 没结果就不动

不该在 patch 里重新拼业务。

### 为什么不能放进结果对象

`FormalExpressionResult` 只回答：

- 这一刻正式成立了什么

不回答：

- 这一刻该如何实例化执行宿主

否则结果层会被运行时宿主污染。

### 第一版推荐拆法

第一版最适合先拆成：

- `IExpressionVerbHostResolver`
- `ExpressionVerbBridge`
- `IManualEntryGizmoResolver`
- `ExpressionManualGizmoBridge`

其中：

- `resolver` 只做解析
- `bridge` 只做接线

### 第一版输入输出裁定

`IExpressionVerbHostResolver`

输入：

- `Pawn`
- `FormalExpressionResult`

输出：

- `bool TryResolve(...)`
- `out Verb`

`IManualEntryGizmoResolver`

输入：

- `Pawn`
- `ManualEntryProjection`

输出：

- `IReadOnlyList<Gizmo>` 或枚举型输出

### 当前阶段最关键的边界

表达系统当前可以正式保留：

- 哪条结果是默认主远程
- 哪条结果是默认主近战
- 这条结果的 `verbProps`

因此真正剩下的缺口是：

- 如何把正式结果里携带的 `verbProps` 映射到当前 Pawn 身上的真实 `Verb` 宿主实例

这是一条“宿主解析缺口”，
不是“表达真相缺口”。

## 3. 当前不允许回退的错误拆分方式

不允许重新出现以下结构：

- 一个“表达运行时”同时收集来源、算结果、选默认主攻击、拼按钮、做视觉
- 一个“投影服务”同时决定系统真相和对外显示
- 一个“主攻击对象”同时代表默认远程、默认近战和全部真实结果
- 把视觉双侧伪装逻辑写回结果生成器
- 把 Special 武器类唯一化逻辑塞进按钮层或默认主攻击层

## 六、正式数据流顺序

表达系统第一版必须固定以下顺序：

1. 上游正式事实成立
2. 来源收集层收材料
3. 单侧结果层先分别成立 Main / Sub / Special
4. 在武器类表达上先完成 Special 唯一化裁定
5. 双侧关系重算层只处理 Main / Sub 高层关系
6. 完整结果总表层统一收口
7. 默认主攻击投影层读取总表
8. 手动入口投影层读取总表
9. 视觉读取投影层读取总表
10. 信息说明投影层读取总表

## 七、允许依赖与禁止依赖

## 1. 允许依赖

- 来源收集层读取 Trigger / CombatBody / Trion 的正式读取面
- 单侧结果层读取来源材料表
- 双侧关系重算层读取单侧结果
- 完整结果总表层读取单侧结果与双侧高层结果
- 各投影层统一读取完整结果总表

## 2. 禁止依赖

- 按钮层反向定义结果层
- 视觉层反向定义结果层
- 默认主攻击投影层吞掉完整结果总表
- 信息说明层自己重新拼一套业务
- 表达系统直接摸 Trigger 内部实现细节
- 表达系统自己持有 Trion / CombatBody / Trigger 真值

## 八、对象到接口映射裁定

第一版表达系统不应把所有东西都做成接口。

应区分：

- 哪些是稳定的数据形状
- 哪些是真正会变化的计算步骤

## 1. 先作为结果对象的数据层

以下内容第一版更适合先落为明确的数据对象，而不是空壳接口：

- `来源材料`
- `单侧结果包`
- `高层关系结果包`
- `完整结果总表`
- `默认主攻击投影结果`
- `手动入口投影结果`
- `视觉读取结果`
- `说明读取结果`

### 原因

这些内容的本质是：

- 当前这一刻正式成立的数据形状

它们首先要做到的是：

- 结构稳定
- 字段清楚
- 不顺手长出业务逻辑

## 2. 先作为计算接口的模块层

以下内容第一版更适合先以接口表达职责边界：

- `来源收集器`
- `来源过滤器`
- `单侧结果生成器`
- `特殊侧武器裁定器`
- `双侧关系重算器`
- `完整结果装配器`
- `默认主攻击选择器`
- `手动入口投影器`
- `视觉投影器`
- `说明投影器`

### 原因

这些内容的本质是：

- 计算步骤
- 规则步骤
- 翻译步骤

它们更可能在后续阶段：

- 改规则
- 换实现
- 增补变体

## 3. 第一版接口输入输出裁定

### `来源收集器`

输入：

- Trigger 正式激活读取面
- 芯片形态读取面
- CombatBody / Trion 前置读取面

输出：

- 来源材料列表

### `来源过滤器`

输入：

- 来源材料列表

输出：

- 有效来源列表

### `单侧结果生成器`

输入：

- 有效来源列表

输出：

- Main 结果包
- Sub 结果包
- Special 结果包

### `特殊侧武器裁定器`

输入：

- Main / Sub / Special 结果包

输出：

- 经裁定后的三侧武器类结果
- Special 武器类拦截标记

### `双侧关系重算器`

输入：

- 经 Special 裁定后的 Main / Sub 结果包

输出：

- 双武器结果包
- 组合技结果包
- 非攻击联动结果包

### `完整结果装配器`

输入：

- Main 结果包
- Sub 结果包
- Special 结果包
- 高层结果包
- Special 武器类拦截标记

输出：

- 完整结果总表

### `默认主攻击选择器`

输入：

- 完整结果总表

输出：

- 默认主远程
- 默认主近战
- 场景默认主攻击决策

### `手动入口投影器`

输入：

- 完整结果总表

输出：

- 手动入口投影结果

### `视觉投影器`

输入：

- 完整结果总表

输出：

- 视觉读取结果

### `说明投影器`

输入：

- 完整结果总表

输出：

- 说明读取结果

## 4. 当前不允许额外长出的壳层

第一版明确不允许再额外长出以下结构：

- `表达系统总协调器`
- `表达运行时总对象`
- `统一投影管理器`
- `万能表达服务`

### 原因

这些壳层极容易重新膨胀成：

- 上帝系统
- 假抽象
- 一把抓运行时

## 5. 当前最需要重点防膨胀的模块

### `完整结果总表`

风险：

- 顺手长出计算逻辑

裁定：

- 它只能做结果容器
- 不承担计算职责

### `默认主攻击选择器`

风险：

- 反向被误当成系统真相

裁定：

- 它只回答默认读取
- 不定义全部真实结果

### `视觉投影器`

风险：

- 偷偷反推业务

裁定：

- 它只能读总表
- 不能反向改写结果层

### `特殊侧武器裁定器`

风险：

- 后续被塞入不属于它的例外规则

裁定：

- 它只处理 Special 对武器类表达的唯一化裁定
- 不负责按钮
- 不负责默认主攻击
- 不负责视觉

## 九、第一版最需要避免的错误

### 1. 把 Special 当普通第三路并列武器输入

这会导致：

- 武器类结果堆积
- 后面再靠按钮层或主攻击层硬压

### 2. 把默认主攻击当成系统真相

这会让系统重新退化成：

- 只有一个主武器

还会进一步误做成：

- 默认主远程和默认主近战只能二选一

### 3. 让按钮层、视觉层、说明层各自猜业务

这会导致：

- 内部一套
- 按钮一套
- 视觉一套
- 说明一套

### 4. 把双手锁定视觉效果写回结果层

这会污染：

- 结果边界
- 控制边界
- 双侧关系判断

## 十、第一版文档结论

表达系统第一版骨架的核心，不是先把某个攻击做出来，
而是先建立一条稳定、诚实、可继续扩展的正式主链：

- 从来源材料
- 到单侧结果
- 到双侧高层关系
- 到完整结果总表
- 再到默认主攻击、手动入口、视觉读取、信息说明四类投影

其中：

- Special 在武器类表达上拥有唯一化优先级
- 双手锁定武器允许“结果单侧、视觉双侧”

只要这两条和整体主链一起钉死，
后续补功能时才不容易重新退化成“假多表达系统”。

## 十一、完整落地路线

这份文档不只定义“第一刀先做什么”，
还要把后面整条表达系统落地路线一起钉住，
避免做到一半后：

- 忘记后面还有哪些层
- 为了眼前能跑先把边界混回去
- 先做了局部样品后再误把样品当正式系统

因此下面按“整套表达系统最终要落成什么”来写完整路线。

## 1. 最终落地目标

表达系统最终应完整落地以下内容：

1. 来源收集层
2. 来源过滤层
3. 单侧结果层
4. Special 武器类唯一化裁定层
5. Main / Sub 双侧关系重算层
6. 完整结果总表层
7. 默认主远程投影层
8. 默认主近战投影层
9. 场景默认主攻击决策投影层
10. 手动入口投影层
11. 视觉读取投影层
12. 信息说明投影层

最终还要支持四个顶层表达大类：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

并允许未来继续扩展：

- 双武器
- 组合技
- 非攻击联动
- 视觉双侧伪装

## 2. 落地顺序总原则

完整路线虽然要一次写清，
但真正实现时仍应遵守以下顺序：

### 1. 先把内部运算链全部立住

也就是先保证：

- 来源怎么进来
- 单侧结果怎么成立
- Special 怎么裁定
- Main / Sub 怎么重算
- 总表怎么收口

### 2. 再把三个默认投影层立住

也就是：

- 默认主远程
- 默认主近战
- 场景默认主攻击决策

### 3. 再把手动入口、视觉、说明三层立住

因为这三层更容易被表面需求牵着跑。

### 4. 再逐步补齐四大类表达的完整落地

第一批先让结构支持全部四大类，
但不强求一开始就把每个细节玩法全部做满。

## 3. 完整阶段拆分

## 阶段 A：结果对象与计算链全立住

### 目标

把表达系统内部真正的“算结果主链”完整立住。

### 本阶段必须落地

- 来源材料对象
- 单侧结果包对象
- 高层关系结果包对象
- 完整结果总表对象
- 来源收集器
- 来源过滤器
- 单侧结果生成器
- Special 武器类裁定器
- 双侧关系重算器
- 完整结果装配器

### 本阶段完成标准

- 表达系统内部已经能回答“这一刻正式成立了什么”
- 不再依赖按钮层或主攻击层反推结果
- 已能容纳 Main / Sub / Special 三侧
- 已能容纳双武器、组合技、非攻击联动这些高层结果位

### 本阶段禁止事项

- 不准顺手生成按钮
- 不准顺手做视觉
- 不准顺手在结果对象里塞计算逻辑

## 阶段 B：默认投影三线同时成立

### 目标

让表达系统正式拥有三条并列默认读取线。

### 本阶段必须落地

- 默认主远程选择器
- 默认主近战选择器
- 场景默认主攻击决策选择逻辑

### 本阶段完成标准

- 默认主远程与默认主近战可同时存在
- 场景默认主攻击决策不再冒充系统真相
- 后续自动攻击、外部兼容、信息读取开始有稳定默认答案

### 本阶段禁止事项

- 不准把三条默认线重新压成一个“唯一主攻击对象”

## 阶段 C：手动入口层正式回接

### 目标

让玩家操作入口重新建立在正式结果总表之上。

### 本阶段必须落地

- 手动入口投影结果对象
- 手动入口投影器
- 手动入口到具体按钮宿主的接线

### 本阶段完成标准

- 按钮来源于正式结果总表
- 按钮数量不再冒充真实结果数量
- 一个按钮可承载多个操作入口

### 本阶段禁止事项

- 不准为了先把按钮做出来，又回去直接从 Trigger 拼按钮

## 阶段 D：视觉读取层正式回接

### 目标

让视觉层停止猜业务，改读正式视觉投影结果。

### 本阶段必须落地

- 视觉读取结果对象
- 视觉投影器
- 双手锁定视觉双侧伪装
- 双武器 / 组合技视觉关系读取口

### 本阶段完成标准

- 视觉层和结果层分层清楚
- 双手锁定武器的视觉例外正式化
- 视觉不再反向定义表达结果

### 本阶段禁止事项

- 不准把视觉伪装逻辑写回结果生成器

## 阶段 E：信息说明层正式回接

### 目标

让说明面板、调试说明和后续正式读取面建立在统一说明投影之上。

### 本阶段必须落地

- 说明读取结果对象
- 说明投影器
- 默认主攻击说明
- 结果层级关系说明

### 本阶段完成标准

- 说明层不再自己拼业务
- 可以清楚区分 Main / Sub / Special / 高层新结果
- 可以清楚说明默认主远程、默认主近战、当前执行表达

## 阶段 F：四大类表达逐步补齐

### 目标

让四个顶层表达大类都正式进入主链。

### 本阶段必须覆盖

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

### 裁定

第一版实现可以有先后顺序，
但完整路线必须从一开始就承认四大类都属于正式系统的一部分，
不能再把：

- `Verb`

偷当成“先做这个就等于表达系统成立”。

## 4. 完整路线中的固定停点

为了避免后续实现时迷路，
每个阶段都必须有固定停点。

### 停点 1：结果链已成立，但没有任何投影

说明：

- 这是内部运算链独立成立的验证点

### 停点 2：默认投影三线成立，但手动入口未接

说明：

- 用于确认默认主远程 / 默认主近战 / 默认兼容表面没有被重新压成一个对象

### 停点 3：手动入口回接，但视觉层仍未接

说明：

- 用于确认按钮开始正式读总表，而不是重新绕回 Trigger

### 停点 4：视觉层回接，但说明层仍未接

说明：

- 用于确认视觉双侧伪装只停留在视觉层

### 停点 5：说明层回接，完整主链收口

说明：

- 用于确认表达系统内部运算和多条投影已经全部闭环

## 5. 完整路线中的长期禁忌

不管走到哪一阶段，都不允许回退到以下做法：

- 把默认主攻击当成真实总表
- 把按钮层当成表达系统本体
- 把视觉层当成结果解释器
- 把 Special 武器类裁定丢给按钮层
- 把双手锁定视觉例外写回控制层
- 为了先跑一个功能，再重新造一个大而全表达运行时

## 6. 完整路线中的未来扩展预留

可以正式预留，但应保持克制的地方包括：

- 特殊侧武器类唯一化规则的未来扩展位
- Main / Sub 双侧关系规则的未来扩展位
- 默认主攻击选择规则的未来扩展位
- 视觉双侧伪装规则的未来扩展位

不需要现在就堆空系统的地方包括：

- 所有组合技词典
- 所有视觉特效词典
- 所有信息面板样式词典

## 7. 一句话总括

表达系统完整落地路线不是“先做一个能打的样品，再慢慢补层”，
而是：

从一开始就把整条最终路线写清楚，
按“内部结果链 -> 默认投影三线 -> 手动入口 -> 视觉 -> 说明 -> 四大类补齐”的顺序推进，
并在每一步都明确哪些是当前阶段目标、哪些是后续阶段目标、哪些永远不能为了赶功能重新混回去。

## 十二、当前落地停点

这一节只记录当前已经真实落下来的状态，
不拿计划目标冒充已完成事实。

## 1. 结果链停点

当前已经成立：

- 芯片表达声明配置层
