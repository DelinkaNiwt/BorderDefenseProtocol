# BDP 被动芯片手动控制设计

## 结论

被动芯片仍然属于普通 Main/Sub（主/副）槽位芯片，但“被动”只表示芯片的效果类别，不表示芯片采用自动激活方式。

被动芯片和普通芯片一样由玩家手动激活、手动关闭。战斗体状态、对应手部是否存在、槽位是否被禁用和芯片激活条件，继续作为芯片能否激活的前置条件；战斗体进入 Active（激活）状态本身不再自动打开被动芯片。

## 激活规则

- 被动芯片可通过现有槽位级 Activate/Deactivate（激活/关闭）入口操作。
- 被动芯片继续受对应主手/副手部位存在性和现有禁用同步约束。
- 被动芯片豁免默认的同侧激活互斥，因此同侧普通芯片与被动芯片可以同时激活；同侧多个被动芯片也可以同时激活。
- `ActivationExclusionGroups`（激活互斥组）不豁免。只要两枚芯片声明了相同互斥组，就不能同时处于正式激活状态。
- 被显式互斥组或其它实际阻挡关系关闭的被动芯片保持关闭，不自动重新激活，玩家需要再次手动操作。
- Special（特殊槽）仍与 Main/Sub 隔离，既不受本规则放宽，也不参与组合技。

## 状态真值

正式激活真值仍只有槽位上的 `IsActive`（是否激活）。本设计不增加“被动已激活”或“希望自动恢复”等第二套状态，也不保留被动自动过渡上下文。

“战斗体状态”从自动触发器调整为可用性边界：战斗体不在 Active 时，沿用现有逻辑禁止或清理 Main/Sub 激活；战斗体重新进入 Active 后，被动芯片仍保持玩家上次明确决定的关闭状态，直到再次收到玩家激活请求。

## 组合技

组合技继续只从正式激活的合法来源匹配：

- 一般激活 Main + 一般激活 Sub；
- 一般激活芯片 + 与它同侧的被动芯片；
- 被动芯片不是因为“自动激活”而获得资格，而是因为其当前 `IsActive` 且类别为被动；
- 被动 + 被动、跨侧一般 + 被动、Special + 任意来源均不匹配；
- 多个合法候选和多个匹配结果全部生成；
- 独立芯片表达继续保留。

## 交互与实现边界

被动芯片使用槽位级按钮，不通过“当前侧唯一激活芯片”推断目标，避免同侧多个被动同时激活时侧级按钮指向不明确。

Core（核心程序集）不再需要为被动芯片提供自动激活业务路径。Core 仍提供通用的槽位激活、关闭、互斥和条件检查；被动类别判断继续由 Content（内容程序集）按正式芯片类别读取，但该判断只用于同侧互斥和组合准入，不用于自动激活。

本设计不改变普通芯片、Special 芯片、芯片装卸、Trion（特里恩）费用、延迟切换和独立表达的既有语义。
