# BDP 芯片启停延迟规范化设计

日期：2026-07-30
状态：用户已完整确认并实施完成

## 一、要解决的问题

芯片 `Loadout（装载配置）`当前使用：

```xml
<WarmupTicks>60</WarmupTicks>
<WinddownTicks>30</WinddownTicks>
```

这两个字段实际控制的是：

1. 玩家发出启用命令后，芯片经过多久才正式生效。
2. 玩家发出停用命令后，芯片经过多久才正式失效。

它们不控制武器攻击前摇，也不控制未来的芯片形态切换。但是 `Warmup / Winddown（预热/收束）`容易被误解为攻击动作时序；Core（核心程序集）中也确实存在另一套真正用于远程攻击的 `WarmupTicks（攻击前摇游戏刻）`，继续沿用旧名会让两套机制难以区分。

## 二、现状复查结论

当前运行链完整使用旧字段：

```text
芯片 XML
  → ChipLoadoutConfig（装载配置）
  → ChipLoadoutContract（装载契约）
  → TriggerService（触发器服务）解析默认值
  → Trigger 切换状态机建立启用或停用阶段
  → 面板读取切换进度
```

当前候选库共有十枚芯片显式填写这组字段：

- 八枚使用 `60 / 30`。
- 一枚使用 `30 / 15`。
- 一枚使用 `15 / 15`。

未填写字段的芯片由运行时使用默认 `60 / 30`。

复查还发现，表达系统构建 `ExpressionChipSnapshot（表达芯片快照）`时会再次复制这两个值，但之后没有任何表达解释器、投影器或业务结果读取它们。它们只是被创建和克隆，没有实际消费者，属于无用副本。

## 三、采用方案

采用“不兼容正式改名，并删除表达快照无用副本”：

```xml
<ActivationDelayTicks>60</ActivationDelayTicks>
<DeactivationDelayTicks>30</DeactivationDelayTicks>
```

对应含义：

- `ActivationDelayTicks（启用延迟游戏刻）`：启用命令提交后，到芯片正式生效的等待时间。
- `DeactivationDelayTicks（停用延迟游戏刻）`：停用命令提交后，到芯片正式失效的等待时间。

不保留旧 XML 字段、旧 C# 字段或兼容读取入口。

## 四、取值规则

正式规则如下：

| 配置值 | 含义 |
|---|---|
| 未填写 | 使用系统默认值 |
| `0` | 立即启用或立即停用 |
| 正整数 | 等待对应数量的 tick（游戏刻） |
| `-1` | 只作为 C# 配置对象内部的“未填写”标记 |
| 小于 `-1` | 定义错误 |

默认值保持：

- 启用延迟：60 tick，约1秒。
- 停用延迟：30 tick，约0.5秒。

XML 作者不需要显式填写 `-1`。字段缺失时，C# 默认值自然保持为 `-1`，运行时再解析为系统默认值。

定义校验必须拒绝小于 `-1` 的数值，避免把任意负数悄悄解释为默认值。

## 五、归属边界

启停延迟只归 `Loadout + Trigger Switching（装载配置＋触发器切换）`管理：

```text
Loadout 声明延迟
  → Trigger 读取
  → Trigger 状态机执行
  → Trigger 状态快照供界面显示
```

表达系统只接收已经正式生效的芯片表达，不需要知道这枚芯片此前等待了多久。因此删除：

- `ExpressionChipSnapshot.WarmupTicks`
- `ExpressionChipSnapshot.WinddownTicks`
- `ExpressionSourceCollector`中的对应复制
- `Clone（克隆）`中的对应复制

不以新名称把这份副本重新加入表达快照。

## 六、代码命名范围

只要名称描述的是“芯片启用/停用延迟”，都同步改为正式语义：

- `WarmupTicks` → `ActivationDelayTicks`
- `WinddownTicks` → `DeactivationDelayTicks`
- `DefaultChipWarmupTicks` → `DefaultChipActivationDelayTicks`
- `DefaultChipWinddownTicks` → `DefaultChipDeactivationDelayTicks`
- `ResolveChipWarmupTicks` → `ResolveChipActivationDelayTicks`
- `ResolveChipWinddownTicks` → `ResolveChipDeactivationDelayTicks`
- `warmupDuration` → `activationDelayDuration`
- `winddownDuration` → `deactivationDelayDuration`
- `SwitchPhase.WarmingUp / WindingDown` → `SwitchPhase.Activating / Deactivating（切换阶段.启用中/停用中）`
- `windingDownSlotIndex / WindingDownSlotIndex` → `deactivatingSlotIndex / DeactivatingSlotIndex（正在停用的槽位序号）`
- 对应委托、参数、局部变量、阶段构造方法和到期结算方法使用同一语义

本项目已明确不做向后兼容，因此 `SwitchContext（切换上下文）`的存档键也随字段改名，不保留旧键双读。

## 七、明确不修改的同名系统

以下 `WarmupTicks（前摇游戏刻）`属于真实攻击系统，本次必须保留：

- `PrepareRecord.WarmupTicks`
- `FireStageContext.WarmupTicks`
- `RangedAttackProtocolService`中的攻击前摇合并
- `WarmupTicksCandidate（攻击前摇候选值）`
- 与远程攻击准备、瞄准和开火有关的其它同名字段

判断标准：

```text
点击芯片按钮到芯片生效？    → 本次改名
点击攻击命令到武器开火？    → 攻击系统，保持不动
芯片形态 A 切换到形态 B？   → 事项 07A，保持不动
```

## 八、候选内容迁移

候选库中现有十组配置只做等义改名，数值完全不变：

```xml
<WarmupTicks>60</WarmupTicks>
<WinddownTicks>30</WinddownTicks>
```

改为：

```xml
<ActivationDelayTicks>60</ActivationDelayTicks>
<DeactivationDelayTicks>30</DeactivationDelayTicks>
```

不改变任何芯片的攻击、表达、Trion（能量）、分类、槽位区域、槽位占用或互斥组。

## 九、玩家界面

芯片详情面板把旧的“切入/切出”改成清楚的“启用延迟/停用延迟”，单位显示为 `tick（游戏刻）`。

启用中、停用中、等待互斥解除的现有按钮行为、描边、进度和提示不改变。

## 十、本次不处理

- 不改变任何启停延迟数值。
- 不改变自动关闭冲突芯片、等待和自动开启目标的规则。
- 不修改攻击前摇。
- 不把启停延迟用于芯片形态切换。
- 不实施事项 07A 的形态运行态。
- 不实施事项 07B 的功率门槛。
- 不修改 Trion 消耗。
- 不处理触发器、触发体分类与命名。
- 不整理与本字段无关的旧文档或测试失败。
