# 攻击执行边界与运行时驱动实施计划（第一版） Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在主模组内建立“表达结果 -> 正式执行入口 -> 攻击编排层 -> 近战/远程运行时链”的清晰边界，让主模组拥有一套结果无关、可扩展的正式攻击运行时组织能力，手动按钮、自动远程、自动近战以及后续各种攻击表现都通过同一个正式执行入口进入各自正确的 RimWorld 运行时链。

**Architecture:** 本次不新增第四个真值 owner，不先新增新的攻击 Comp，不把执行重新塞回 `CompTriggerBody`。方案采用“Pawn 侧薄执行入口 + AttackExecution 内部攻击编排层 + Trigger/Expressions 保持原边界 + 远程/近战后续继续走 RimWorld 自然通道”的结构：`CompTriggerBody` 继续回答装载/激活事实，`Expressions` 继续回答当前成立结果，`AttackExecution` 负责接单、校验、生成通用攻击编排、分流到正式运行时，远程和近战分别进入各自正式执行器、`JobDriver`、`Verb`、`Projectile` 与原版伤害链。副攻击不是独立执行世界，只是另一条合法攻击身份，必须复用同一套正式执行边界与运行时链。

**Tech Stack:** C# 7.3, .NET Framework 4.8, RimWorld `Verb` / `JobDriver` / `Projectile` / `Pawn` patch / `ThingComp`, XML Def, `dotnet msbuild`

---

## 总执行原则

- 不新增第四个真值 owner。
- 不把攻击执行主责塞回 `CompTriggerBody`。
- 不让 `Expressions` 越权承担正式执行。
- 不让 UI、patch、自动攻击直接碰裸 `Verb` 再碰运气。
- 不把任何具体攻击表现硬编码成几条特例旁路。
- 所有入口统一先经过正式执行边界，再进入近战或远程链。
- 正式执行边界内部必须先形成通用攻击编排，再决定如何推进运行时。
- 副攻击与主攻击共享同一套执行边界、计划层和运行时，不得平行复制一套系统。
- 远程和近战尽量继续走 RimWorld 自然运行时，不再发明平行攻击世界。
- 每完成一个阶段都必须回写日志。

## 完成标准

本计划完成时，应同时满足：

- 主模组存在新的内部层：`Core/AttackExecution`
- 主模组存在明确的攻击编排层对象
- 手动按钮不再直接以裸 `Verb` 为正式执行边界
- 自动远程、自动近战都先经过统一执行入口
- 统一执行入口能清楚先生成攻击编排，再分流到近战执行器或远程执行器
- 远程执行器能正式启动远程运行时链
- 近战执行器能正式启动近战运行时链
- 主模组应天然支持多步、并列、连续推进、非连续推进等通用攻击组织能力
- 旧 BDP 的具体表现只作为架构验收样本，不作为架构形状本身
- 主模组能够清楚回答：
  - 谁负责执行
  - 谁负责推进
  - 谁负责结束
- BDP 主模组可编译
- 相关文档、计划、工作日志同步回写

## 当前已确认设计事实

- `CompTriggerBody` 的正式边界仍然是装载、局部激活、形态/槽位事实。
- `Expressions` 的正式边界仍然是“当前成立了什么”与“如何投影”，不是正式执行入口。
- 当前真正缺的不是某个按钮修补，而是把“表达结果”正式送入“RimWorld 运行时链”的统一入口。
- 当前确认还缺一层“攻击编排层”，用来回答“这次攻击如何组织推进”，而不把这种复杂度重新塞回 `Verb`、`JobDriver`、UI 或 patch。
- 副攻击在执行本质上不是另一套系统，只是另一条合法攻击身份；它必须复用主攻击那套正式执行边界、计划层和运行时。
- 攻击编排层必须是结果无关的通用结构；旧 BDP 的单侧齐射、双侧齐射、双侧混合、独立副攻击只能作为它自然承接出来的样本，不能反向塑造它的形状。
- 旧 BDP 的关键经验不是“到处都用 JobDriver”，而是：
  - UI 不是执行本体
  - 有些持续推进必须交给 `JobDriver`
  - `JobDriver` 也不能吞掉整条远程/近战链的全部复杂度
