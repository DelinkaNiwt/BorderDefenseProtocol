# 黑触发器定形方向与生命证据重设计

## 文档状态

- 日期：2026-09-19
- 状态：已确认，作为形成选择与生命印记展示的当前权威设计
- 适用范围：BDP 黑触发器形成、玩家选择、成品印记、开发者诊断
- 替代内容：旧设计中的倾向、最终意志、直接候选物品选择和普通检视文本堆叠
- 不改变内容：形成门槛、自然死亡与主动倾注生命入口、尸体销毁、世界唯一、绑定和二元适配

## 一、问题与目标

旧原型把形成过程拆成“侧重、倾向、最终意志”三层，但三者并非从同一逻辑推导：

- 侧重只是路线第一项生命轨迹；
- 倾向直接拼接成品物品上的标签；
- 最终意志只是路线语言文本；
- 人物快照已经采集的具体事实没有进入信件。

结果是玩家既不知道选项为什么来自这个角色，也不知道选择具体会把成品引向什么功能。

新设计只保留一项玩家决策：

```text
角色的真实经历
    ↓ 支撑
完整定形方向：经历来源 → 核心功能
    ↓ 筛选
具备相应固定功能的完整黑触发器
```

每张定形方向卡必须同时回答：

1. 为什么这个角色能够选择它；
2. 选择后会保证什么实际功能；
3. 该方向下存在多少种可能结果。

## 二、最终概念模型

### 2.1 玩家可选概念

玩家不再分别选择侧重、倾向和最终意志，而是一次选择一张完整的“定形方向”卡。

一张卡只有两个必要语义：

- **经历来源**：力量从角色哪一类真实人生经历中产生；
- **核心功能**：形成结果至少会具备哪一种主要游戏功能。

示例：

```text
承受经历 → 防护功能
营造经历 → 支援功能
战斗经历 → 杀伤功能
```

“倾向”和“最终意志”从配置、存档、界面和成品印记中删除，不以新名称保留。

### 2.2 人物称谓

玩家界面不使用“献祭者”“制造者”或“形成者”。它们分别存在自然死亡不适用、工业制造感过强或中文生硬的问题。

界面改用无角色名词的表达：

- `生命印记来源：Werner`
- `Werner留下的经历`
- `这件黑触发器由Werner的生命印记定形而成`

代码内部现有 `Maker` 命名可以保留，不直接暴露给玩家。

### 2.3 形成来源称谓

- 自然死亡：`死亡后自然形成`
- 主动入口：`主动倾注生命`

“献祭”只可作为开发内部历史命名，不再作为正式玩家称谓。

## 三、核心功能

第一版固定六种一级功能：

| 功能 | 判定含义 |
|---|---|
| 杀伤 | 直接造成伤害、突破防御或消灭目标 |
| 防护 | 护盾、拦截、减伤、伤害转移或保护目标 |
| 控制 | 限制行动、封锁区域、牵制或施加控制状态 |
| 机动 | 移动、传送、位移、撤离或快速接近 |
| 支援 | 治疗、强化、救援、补给、修复或提供持续辅助 |
| 侦察 | 探测、揭示、预警、预测或获取战场信息 |

### 3.1 构筑的归属

“构筑”是实现手段，不是与六种结果并列的一级功能：

- 构筑炮塔属于杀伤；
- 构筑屏障属于防护；
- 构筑封锁物属于控制；
- 构筑补给或修复设施属于支援。

黑触发器可以在具体功能摘要中明确写出构筑能力，但形成匹配按其实际结果分类。

### 3.2 成品功能配置

每件黑触发器先完成能力设计，再在自己的 `ThingDef` 扩展中声明一个或多个功能画像。每个画像包含：

- 一个 `BlackTriggerFunctionDef`；
- 一段语言包中的具体功能摘要；
- 可选显示顺序。

形成路线只能引用该物品已经声明的功能画像。加载校验拒绝：

- 路线引用未声明功能；
- 功能画像缺少具体摘要；
- 形成路线没有经历来源或核心功能；
- 同一物品内方向与路线编号重复。

系统不尝试从任意能力代码自动推断功能；作者负责分类，校验器负责保证声明完整且内部一致。

## 四、六类生命经历

生命经历不是玩家虚构的愿望，而是对角色实际记录的有限归纳。

### 4.1 证据来源原则

第一版只读取原版或已有 BDP 数据：

- `RecordDef` 长期记录；
- 技能等级和热情；
- 直接关系及双方好感；
- 死亡前的伤残、疾病和临终状态；
- 三离子容量潜力。

不为救援、保护某人或一般社交新增全局 Harmony 记录补丁。原版没有保存的历史，系统不伪造也不声称知道。

### 4.2 战斗

主要证据：

- `DamageDealt`；
- `Kills`；
- `PawnsDowned`；
- `TimeDrafted`；
- `ShotsFired`。

辅助证据：射击、格斗技能和热情；永久战斗伤残只作为文字旁证，不重复计入承受分。

`Kills` 与 `KillsHumanlikes` 等分类值不重复加分；分类只用于展示总数构成。

### 4.3 救护

主要证据：

- `TimesTendedOther`；
- `OperationsPerformed`；
- `TimeTreatingAndFeeding`；
- `FiresExtinguished` 作为低权重证据。

辅助证据：医疗技能和热情。

原版没有“救援殖民者次数”记录，第一版不显示也不参与计分。

### 4.4 营造

主要证据：

- `ThingsConstructed`、`TimeConstructing`；
- `ThingsCrafted`；
- `ThingsRepaired`、`TimeRepairing`；
- `ThingsInstalled`。

次要证据：播种、收获、烹饪和采矿的原版记录；清扫与搬运不进入第一版营造分。

辅助证据：建造、手工、种植、烹饪和采矿技能及热情。

### 4.5 求知

主要证据：

- `ResearchPointsResearched`；
- `TimeResearching`。

辅助证据：智识技能和热情；`ArtifactsActivated` 只作低权重特殊事实。

### 4.6 联结

主要证据：

- 配偶、恋人、子女、父母等明确直接关系；
- 关系双方好感；
- `PrisonersRecruited`；
- `PrisonersChatted`；
- `TimeWardening`。

辅助证据：社交技能和热情；相关社会角色只在具体路线要求时读取。

原版没有一般社交互动计数，不使用不存在的 `InteractionsInitiated` 或 `SocialInteractions`。

### 4.7 承受

主要证据：

- `DamageTaken`；
- `TimeDowned`；
- `TimeInBedForMedicalReasons`；
- `TimesTendedTo`；
- `OperationsReceived`；
- 死亡前仍存在的永久伤疤、缺失部位和长期病症。

辅助证据：临终伤势、失血与致死疾病。

精神崩溃次数不自动视为承受或坚韧。

### 4.8 当前错误名称

现有代码中的以下名称并不存在，实施时必须从根上移除：

- `HumanlikesKilled`
- `AnimalsHunted`
- `TimesTendedToOther`
- `RescuedColonist`
- `InteractionsInitiated`
- `SocialInteractions`
- `TimesDowned`
- `TotalTimeAsPatient`

## 五、经历强度和证据选择

### 5.1 计分方法

每类经历使用固定 Content 计算器，不实现通用规则语言，也不允许每件黑触发器重定义人物历史算法。

每项记录先通过独立饱和曲线归一化，再按证据组组合：

```text
实际行为或长期状态：最高占80%
技能与热情旁证：最高占20%
```

同一事实的总数与分类数只进入一个证据组。组内相互包含的数据取总记录或最大标准化值，不重复相加。

技能高但没有实际经历的角色可以获得少量支持，不能仅凭技能形成强生命经历。

### 5.2 玩家证据

内部保存归一化分数，玩家不看百分比和匹配分。每条成立路线从实际参与判断的事实中选取二至四条代表证据：

1. 优先显示核心经历的最强实际行为；
2. 再显示一条持续时间、关系或永久状态；
3. 技能和热情只有在确实影响路线时才显示；
4. 同义证据不重复；
5. 数值为零的项目不显示。

信件只冻结被至少一张方向卡实际采用的证据。完整原始数值留给 Development 调试界面。

## 六、形成路线配置

每条路线描述“这件已经设计完成的黑触发器，能够怎样从某种人生经历形成”。

必要字段：

- 稳定 `routeId`；
- 允许的形成来源；
- 一个明确的 `coreTrace`；
- 核心经历最低强度；
- 一个由成品已声明的核心功能；
- 结果权重；
- 作者排序优先级。

可选字段：

- 辅助经历要求；
- 最低技能；
- 必需或排斥特质；
- 关系或锚点规则；
- 临终情境要求；
- 极少数专用判定类。

限制：

- 一条路线只能有一个核心经历；
- 辅助条件不成为新的玩家选择层；
- 默认只提高匹配解释和排序；
- 只有黑触发器设定确实离不开某事实时，作者才能将其设为硬条件；
- 所有实际参与准入或排序的条件都必须能生成中文证据或中文开发诊断。

## 七、方向生成与稳定随机

### 7.1 路线评估

系统遍历所有未永久生成、未被其他事件预留的黑触发器，并评估它们自己的路线。

同一物品在不同方向中可以各保留一条最佳路线；同一物品在同一方向中只保留匹配分最高的一条路线。

路线匹配分只用于：

- 对方向卡排序；
- 同一方向内按作者权重稳定抽取结果；
- Development 诊断。

候选数量不提高自然形成概率，也不提高方向排序。

### 7.2 方向分组

方向键由以下内容组成：

```text
核心经历 Def + 核心功能 Def + 实际使用的锚点规则与对象
```

没有实际锚点机制时，关系人物不进入方向键。

相同方向下可以包含多个完整黑触发器。玩家不会看到具体候选名称，只看到功能保证和结果数量。

### 7.3 卡片数量

- 通常显示两张；
- 只有一个充分成立的方向时允许一张；
- 第三张必须匹配充分且语义与前两张不同；
- 最多三张；
- 不为凑数加入弱方向。

排序使用每个方向中最佳路线的匹配分、作者优先级和稳定键。方向下候选越多不会获得额外优势。

### 7.4 信件建立时暗选结果

为了同时满足延迟决定、世界唯一和“同一方向可随机对应多个黑触发器”，每张方向卡在信件建立时完成一次不可见的稳定抽取：

1. 使用世界标识、角色稳定 ID、事件 ID和方向键建立稳定种子；
2. 按路线 `resultWeight` 在该方向候选池中抽取一个结果；
3. 优先避免不同方向暗选出同一结果；没有替代项时允许重复；
4. 只预留各方向暗选出的结果，不预留整个候选池；
5. 信件保存完整候选池摘要、暗选结果和预留状态；
6. 读档或反复打开信件不重新抽取。

玩家选择方向后直接生成该方向已经冻结的结果，并释放其他方向的预留。

## 八、托付对象与关系锚点

托付对象不是通用第四步，也不是装饰文案。

只有当黑触发器实际能力、适配或绑定规则会读取特定人物时，路线才能声明锚点规则。此时：

- 系统从死亡前冻结的显著直接关系中选择合法对象；
- 不同合法对象可以形成不同完整方向卡；
- 卡片直接显示对象及其真实关系；
- 玩家通过选择整张卡决定对象，不再单独打开人物选择器；
- 没有实际机制用途的关系只作为联结经历证据，不保存为托付对象。

锚点对象必须满足路线声明的存活、关系类型和可解析条件；同分时使用关系强度、双方好感和 Pawn 稳定 ID 排序。

## 九、玩家选择窗口

### 9.1 顶部资料

顶部只显示会帮助玩家理解本次形成的内容：

- `生命印记来源：姓名`
- `形成经过：死亡后自然形成／主动倾注生命`
- 三离子容量潜力及已满足形成资格的说明；
- 临终原因或主要状态；
- 本次至少一张方向卡实际采用的人生资料。

不显示：

- 六项空白轨迹；
- 裸百分比；
- 内部匹配分；
- 技术键名；
- 没有参与任何方向的资料。

### 9.2 方向卡

每张卡固定包含：

```text
承受经历 → 防护功能

为什么能够选择
• 一生承受1276点伤害
• 因伤倒地累计1.8天
• 失去左眼后继续生活

选择后会保证
最终结果将以护盾、拦截、减伤、伤害转移
或防护性构筑为核心功能。

符合这一方向的结果：2种
```

如果方向使用锚点，追加“作用对象”及关系说明。

一次点击选择整张卡；再次点击可以改选。底部只有“确认定形”和“稍后决定”。确认前显示方向摘要，不显示暗选结果。

### 9.3 生成完成提示

最终物品成功放置并登记世界唯一后，追加一封原版蓝色正面事件信件：

- 标题说明黑触发器已经定形；
- 正文包含生命印记来源、玩家选择的完整方向和最终物品名称；
- 点击定位新物品；
- 事务失败时不发送成功信件。

## 十、成品生命印记

最终物品保存：

- 生命印记来源的稳定 ID 与姓名快照；
- 形成来源；
- 内部路线 ID；
- 经历来源 Def 与显示名回退；
- 核心功能 Def 与显示名回退；
- 成品实际功能摘要；
- 二至四条代表证据；
- 实际有机制用途时的锚点对象；
- 绑定信息仍由绑定组件保存。

不再保存倾向、最终意志或完整死亡快照。

### 10.1 普通检视面板

`CompInspectStringExtra` 不再把生命印记逐行堆入普通检视文本。

物品被直接选中时，由印记组件提供“查看生命印记”命令，打开独立只读窗口。窗口采用与原版艺术说明相近的结构：来源、形成经过、定形方向、实际功能、代表经历和可选作用对象。

### 10.2 信息面板

印记组件通过原版 `ThingComp.SpecialDisplayStats()` 增加“生命印记”条目。左侧只显示条目名和简短摘要，右侧详情显示与独立窗口一致的完整资料。

不新增全局 Harmony 信息面板补丁。

## 十一、适配关系

移除倾向与最终意志不会改变“二元适配、首次装备绑定、绑定者死亡后解绑”的共同规则。

适配系统可以按黑触发器自身配置读取：

- 选中的经历来源；
- 冻结的代表证据类型；
- 内部路线 ID；
- 实际存在的锚点对象；
- 使用者自身的技能、特质、经历和容量。

系统不根据核心功能自动提高适配，也不根据玩家派系或敌对派系自动调整。任何适配条件仍必须由具体黑触发器明确声明。

## 十二、保存与异常处理

### 12.1 待决信件

信件是待决事件单一真值，保存：

- 角色资料摘要；
- 被采用的结构化证据；
- 方向卡；
- 每张方向的候选池数量和稳定暗选结果；
- 预留结果；
- 当前选中方向。

遗物仍只保存事件关联和地图锚点。

### 12.2 失败行为

- 没有充分方向：不建立形成事件；自然死亡保留尸体，主动调试记录中文诊断。
- 建立遗物、信件或预留失败：回滚临时对象，不写耗尽标记，不销毁尸体。
- 形成事件成功建立：写耗尽标记并销毁尸体。
- 最终放置失败：保留遗物、信件、方向选择和预留，允许重试。
- 暗选 Def 在读档后缺失：取消对应方向；全部缺失时取消事件并释放预留。
- 地图被废弃：按既有设计取消事件、释放预留，生命印记耗尽不回滚。

### 12.3 原型旧存档

当前倾向／最终意志原型属于开发阶段数据，不提供字段迁移。新载入审计应安全取消旧结构的待决事件并释放预留，不得因缺少新字段持续报错。已经生成的旧测试物品可以显示“未记录生命印记”，不尝试推断新方向。

## 十三、Development 调试

### 13.1 系统总览

Development 总览继续罗列所有参与系统的黑触发器，并改为显示：

- 中文名称与 `DefName`；
- 世界唯一状态、实例数量和绑定状态；
- 声明的核心功能与具体功能摘要；
- 每条路线的核心经历、门槛、辅助条件、形成来源、锚点规则、权重和优先级；
- 配置校验结果；
- 当前待决事件中所属的方向池；
- 候选池全部成员、内部匹配分和权重；
- 每张方向暗选出的真实结果；
- 世界唯一预留和最终登记状态；
- 使用的原始证据、归一化值与玩家展示文本。

玩家界面不显示的技术信息在这里必须可见，但每项仍使用中文字段标题，不裸露无说明的键名。

### 13.2 强制测试

上帝模式“强制定形当前角色”继续绕过个人危机、自然概率和总体形成门槛，但仍走真实快照、方向分组、信件、遗物、尸体销毁、稳定暗选和最终事务。

Development 测试黑触发器使用零或极低核心经历门槛，保证新建角色也能进入界面；卡片仍显示该角色实际存在的技能或经历，不伪造战绩。

调试入口不得直接生成成品，也不得复制正式算法。

## 十四、程序集与原版落脚点

- `BDP.Content`：功能 Def、生命经历评估、路线、方向分组、信件、成品印记、成功信件和正式校验。
- `BDP.Development`：总览、强制测试、诊断和临时测试黑触发器。
- `BDP.Core`：不增加黑触发器专用概念。

复用原版：

- `RecordDef`、技能、关系和健康数据；
- `ChoiceLetter` 与 `Window`；
- `ThingComp.CompGetGizmosExtra()`；
- `ThingComp.SpecialDisplayStats()`；
- `StatDrawEntry`；
- `GameComponent` 世界唯一账本；
- 原版正面事件信件；
- 现有装备与绑定入口。

不新增逐 Tick 组件、通用条件 DSL、全局人物历史系统或无条件原版补丁。

## 十五、验收标准

1. 玩家只做一次完整定形方向选择。
2. 每张卡都显示二至四条来自该角色的真实依据。
3. 每张卡都明确承诺生成结果的核心游戏功能。
4. 同一方向可以包含多个黑触发器，玩家不直接选择具体物品。
5. 延迟决定、读档和反复打开信件不会改变暗选结果。
6. 一封待决信件最多预留每张方向一个结果，不占用整个候选池。
7. 成功建立事件后尸体必定销毁；失败建立时尸体保留。
8. 最终生成后发送蓝色正面事件信件。
9. 普通检视文本不堆叠印记详情；命令和信息面板均能查看完整印记。
10. 玩家界面没有技术键名、裸分数、倾向或最终意志。
11. Development 总览可以看到全部真实路线、证据、分数、候选池、暗选结果和唯一状态。
12. Core.dll 不受影响，Development.dll 卸载后正式流程仍完整可用。
