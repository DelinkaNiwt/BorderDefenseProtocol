# 自动攻击与原版攻击入口彻底分家设计

**目标**

在不重造表达系统与攻击执行系统的前提下，把 BDP 的自动攻击入口与原版武器入口彻底分家：

- 原版继续自然保留触发体本体攻击入口
- BDP 表达系统继续负责默认主攻击判定
- 自动攻击优先使用表达系统给出的默认主攻击
- BDP 入口不得再进入原版武器 `PrimaryVerb` / 原版装备 `VerbTracker` 候选链

**问题定义**

当前实现把 `CompTriggerBody` 的 `IVerbOwner.VerbProperties` / `IVerbOwner.Tools` 改接成了 formal host 壳声明面，导致原版 `VerbTracker` 初始化出来的主武器候选不再是触发体本体攻击，而是一组 BDP formal host 壳。原版自动攻击因此会在补丁之前先抓到 BDP 壳，绕过 BDP 自己的默认主攻击规则，并挤占本应由原版自然保留的本体攻击表面。

**适用范围**

- `Source/BDP/Core/Trigger/State/CompTriggerBody*`
- `Source/BDP/Core/VerbHosting/*`
- `Source/BDP/Core/Expressions/*`
- `Source/BDP/Core/AttackExecution/*`
- `Source/BDP/Patches/Patch_Pawn_TryGetAttackVerb.cs`
- `Source/BDP/Patches/Patch_Pawn_MeleeVerbs_TryMeleeAttack.cs`

**不做的事**

- 不重写表达系统默认主攻击选择器
- 不重写 AttackExecution 主边界
- 不人为补画触发体本体攻击按钮
- 不为了遮盖现状再发明一套平行宿主系统

---

## 一、需求本质

### 1. 触发体本体攻击面必须回归原版

原版武器入口应该继续来自触发体本体自己的 `VerbProperties` / `Tools`，而不是来自 BDP formal host 壳。

这意味着：

- 玩家看得到的本体攻击入口必须是原版自然生成的
- BDP 不能通过替换武器声明面的方式“画回去”
- 触发体本体近战入口能见、能点、能正常执行，属于基线，不属于 BDP 新增能力

### 2. 默认主攻击属于表达系统，不属于原版武器声明面

表达系统已经具备默认主攻击判定能力，且默认主攻击不是单一概念，而是两条并列默认读取口：

- `PrimaryRanged`
- `PrimaryMelee`

它们都是表达系统从当前正式结果总表中判定出来的，不允许再退回到“靠原版 `PrimaryVerb` 列表顺序猜主攻”。

### 3. 自动远程和自动近战都应受表达系统约束

自动攻击的正确语义不是“让原版去抓 BDP 宿主壳”，而是：

- 自动远程优先读表达系统给出的默认远程主攻击
- 自动近战优先读表达系统给出的默认近战主攻击
- 若某一类默认主攻击不存在，则该类自动攻击完全回退原版基线

这两条回退是分开的，不能互相污染。

### 4. 表达出的近战一旦存在，就必须独占自动近战

若表达系统当前给出了合法的默认近战主攻击，则自动近战必须由它全权接管。

此时禁止混入：

- 触发体本体近战
- pawn 拳头
- 其他装备近战池
- apparel / hediff 近战池

若表达系统没有给出合法默认近战主攻击，则自动近战完全回退原版 `Pawn_MeleeVerbs` 基线。

## 二、原版引擎验证结论

### 1. 原版远程默认攻击链只认主武器 `PrimaryVerb`

原版 `Pawn.TryGetAttackVerb` 会优先读取：

- `equipment.PrimaryEq.PrimaryVerb`

而 `PrimaryVerb` 又来自：

- `CompEquippable.verbTracker.PrimaryVerb`
- `VerbTracker.AllVerbs` 中第一个 `verbProps.isPrimary == true` 的 verb

因此，只要 BDP 的 formal host 壳进入主武器 `VerbTracker`，原版就会在补丁之前先抓到它。

### 2. 原版近战链本来就是独立池

原版自动近战与手动近战并不依赖主武器 `PrimaryVerb`，而是走：

- `pawn.meleeVerbs.TryGetMeleeVerb`

它会从多种近战来源聚合候选，包括：

- pawn 本体近战
- 装备近战
- apparel 近战
- hediff 近战

所以“原版保留本体近战入口”与“BDP 拥有独立默认自动攻击”在原理上完全可以同时成立，前提是模组不要把两套链条混成一套。

### 3. 当前 BDP 的根错不在选择规则，而在声明面越界

当前问题不是表达系统不会选主攻击，而是 BDP 让 formal host 壳直接进入了原版武器声明面。

结果变成：

- 原版武器表面被 BDP 宿主壳替代
- 原版自动攻击提前抓壳
- BDP 自己的自动攻击桥只能事后补漏
- 本体攻击入口不再是原版自然表面

这与“新增第三只眼”相反，属于“把原来的眼眶换掉了”。

## 三、现有设施复用裁决

本次整改禁止重复造轮子，必须直接复用以下已有设施。

### 1. 继续复用表达系统默认主攻击选择器

继续使用：

- `DefaultPrimaryExpressionSelector`
- `ExpressionService.BuildSelectedSnapshot`

它已经输出：

- `snapshot.PrimaryRanged`
- `snapshot.PrimaryMelee`

本次整改不再发明第二套“自动攻击专用选择器”。

### 2. 继续复用 AttackExecution 作为正式执行边界

继续使用：

- `AttackExecutionSurfaceAccess`
- `AttackExecutionService`

自动攻击仍然必须回到 AttackExecution 正式边界，不允许新增一个“自动攻击私有执行器”。

### 3. 继续复用现有手动入口与额外 gizmo 链

继续使用：

- `TriggerEquippedGizmoService`
- `ExpressionManualGizmoBridge`
- `DefaultManualEntryGizmoResolver`

这些设施负责 BDP 新增表达入口的可见性，不承担原版本体入口补画职责。

### 4. 继续复用现有补丁挂点，但重写其语义

继续使用原有补丁位置：

- `Patch_Pawn_TryGetAttackVerb`
- `Patch_Pawn_MeleeVerbs_TryMeleeAttack`

但要把它们从“回填 formal host 壳”改成“读取表达系统默认主攻击并桥接到 AttackExecution”。

### 5. 可复用现有 VerbHost 管理器，但必须降责

`TriggerBodyVerbHostManager` 可以保留，但职责必须收缩为：

- 结果标识到运行时宿主执行面的解析
- 当前表达结果可用性映射

它不再允许承担：

- 接管原版 `IVerbOwner` 声明面
- 成为原版 `PrimaryVerb` 候选链来源

## 四、三种可选方案

### 方案 A：只把 formal host 壳踢出 `PrimaryVerb`

做法：

- 保留 formal host 继续挂在主武器 `VerbTracker`
- 仅通过 `isPrimary = false` 等手段阻止其进入 `PrimaryVerb`

问题：

- 原版武器声明面仍然被 BDP 壳替代
- 只是少了一次最显眼的误抓
- 其它读取面仍可能看到错误表面

结论：

- 不采用

### 方案 B：原版声明面回归基线，自动攻击完全桥接表达系统

做法：

- `CompTriggerBody` 停止改写 `IVerbOwner.VerbProperties` / `IVerbOwner.Tools`
- 原版 `VerbTracker` 重新只持有触发体本体的基线攻击面
- 自动远程补丁读取 `ExpressionSnapshot.PrimaryRanged`
- 自动近战补丁读取 `ExpressionSnapshot.PrimaryMelee`
- 两条自动链都通过 AttackExecution 执行
- 若对应默认主攻击缺失，则各自完全回退原版

优点：

- 与第一性原理一致
- 不再污染原版武器表面
- 保留原版本体近战入口
- 不需要新造选择器和执行器

代价：

- 需要把当前 formal host 退出原版声明面的那部分彻底拆掉
- 自动远程持续攻击会话要重新确认不再依赖原版正式持有 BDP 宿主壳

结论：

- 推荐采用

### 方案 C：保留只读兼容投影层

做法：

- 在方案 B 基础上，另外保留一层“只读兼容投影”
- 给检查信息、展示面、某些兼容读取口提供默认主攻击信息
- 但这层信息不得回流成原版可执行武器入口

优点：

- 兼顾后续兼容需求

代价：

- 当前并非必需
- 容易被再次误接回执行链

结论：

- 只保留为后续演进空间，本次不落地成新层

## 五、最终设计裁决

本次采用方案 B。

### 1. 原版攻击面恢复为“触发体本体”

`CompTriggerBody` 必须停止把 formal host 壳暴露为原版 `IVerbOwner` 声明面。

整改后：

- 原版 `CompEquippable.VerbProperties` 回到 `parent.def.Verbs`
- 原版 `CompEquippable.Tools` 回到 `parent.def.tools`
- 原版 `VerbTracker` 只持有触发体本体基线攻击

这一步是整个整改的基线，不能妥协成“继续暴露壳，但少暴露一点”。

### 2. BDP 默认主攻击改为纯表达读取，不再借原版武器候选链

自动攻击读取统一改为：

- 先取 `ExpressionService.BuildSelectedSnapshot(pawn)`
- 远程只看 `PrimaryRanged`
- 近战只看 `PrimaryMelee`

表达系统没有结果时，视为“BDP 不接管该类自动攻击”。

### 3. 自动远程桥接规则

自动远程改为：

- 若 `PrimaryRanged` 合法，则由 BDP 桥接执行
- 若 `PrimaryRanged` 不存在或非法，则完全返回原版 `TryGetAttackVerb` 结果

关键点：

- BDP 远程自动攻击不再依赖原版主武器 `PrimaryVerb` 抓到 BDP 宿主壳
- 原版能抓到的始终只是触发体本体攻击

### 4. 自动近战桥接规则

自动近战改为：

- 若 `PrimaryMelee` 合法，则拦截原版 `Pawn_MeleeVerbs.TryMeleeAttack`
- 由 BDP 直接以该结果进入 AttackExecution
- 不再允许原版从自身近战池继续混选其它近战 verb

若 `PrimaryMelee` 不存在或非法：

- 完全放行原版 `Pawn_MeleeVerbs` 基线

这正好满足：

- “只有远程表达时，自动近战仍然是触发体本体肉搏或原版近战池”
- “存在表达近战时，自动近战完全由表达结果独占”

### 5. 手动入口与自动入口严格分层

手动入口层：

- 继续由 `ExpressionManualGizmoBridge` 投影 BDP 额外攻击入口
- 原版本体入口继续自然存在

自动入口层：

- 只由表达系统默认主攻击驱动
- 不借原版武器候选链表达 BDP 主攻击

两层互相协作，但不再共享同一宿主声明面。

## 六、模块职责调整

### 1. CompTriggerBody

保留：

- Trigger 真值 owner
- 原版武器本体宿主

删除：

- 用 formal host 覆盖原版 `IVerbOwner` 声明面的职责

### 2. TriggerBodyVerbHostManager

保留：

- 结果到执行宿主的最小解析
- 结果标识与可用态映射

删除：

- “formal host 是原版武器声明面”的定位

### 3. AttackExecutionSurfaceAccess

新增或改造语义：

- `TryGetAutoRangedVerb` 不再返回原版 `VerbTracker` 正式持有的 BDP 壳
- 改为从表达结果解析可执行宿主表面
- `TryExecuteAutoMelee` 继续作为自动近战正式桥，但其选择来源改为 `PrimaryMelee`

### 4. ExpressionService

继续作为唯一默认主攻击裁定来源。

本次不新增新的“AutoPrimarySelector”或类似平行类型。

---

## 七、验收标准

### 1. 原版表面

- 触发体本体近战入口在 UI 中自然存在
- 该入口来自原版武器基线，而非 BDP 补画

### 2. 自动远程

- 若表达系统存在合法 `PrimaryRanged`，自动远程走 BDP
- 若不存在，自动远程完全回退原版
- 原版 `TryGetAttackVerb` 不再直接抓到 BDP formal host 壳

### 3. 自动近战

- 若表达系统存在合法 `PrimaryMelee`，自动近战只走该结果
- 不得混入本体近战、拳头、hediff 近战等其它池
- 若不存在，自动近战完全回退原版 `Pawn_MeleeVerbs`

### 4. 架构边界

- BDP 不再通过接管主武器 `VerbTracker` 候选链来表达默认主攻击
- 不新增第二套主攻击选择器
- 不新增第二套攻击执行器

---

## 八、风险与护栏

### 1. 远程持续攻击会话风险

当前远程持续攻击部分逻辑仍假设能拿到某个宿主 `Verb`。整改时必须确认：

- 该宿主是否必须是原版主武器 `VerbTracker` 持有对象
- 若不是，应改成 BDP 自有运行时执行宿主或现有结果宿主解析面

这里允许做宿主解析整改，但不允许重新发明一整套新的战斗系统。

### 2. UI 误判风险

不得把“保留本体近战入口”理解成“由 BDP 手动再补一个本体近战按钮”。

正确做法是：

- 把原版武器声明面还给原版
- 让原版本体入口自然回来

### 3. 轮子膨胀风险

本次整改的高风险误区是：

- 再发明一个自动攻击专用选择器
- 再发明一个自动近战专用宿主层
- 再发明一个只为补现状的新门面服务

这些都属于重复造轮子，必须禁止。

---

## 九、结论

这次整改的本质不是“把补丁打得更准”，而是把三层东西重新分开：

- 原版武器本体攻击面
- BDP 表达系统默认主攻击裁定面
- BDP 自动攻击桥接执行面

当前实现的问题是把后两者塞进了第一层。整改后必须恢复为：

- 原版只看见触发体本体
- BDP 自己决定默认主攻击
- 自动攻击通过桥接使用 BDP 默认主攻击
- 没有对应表达时，按类别分别回退原版

这才符合“保留原来的两只眼，再额外长出第三只眼，并让第三只眼成为默认自动使用者”的需求本质。
