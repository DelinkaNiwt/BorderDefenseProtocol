# BDP 芯片功能语义契约重构设计

## 文档状态

- 状态：已确认总体设计；属性细目允许在实施中按现有业务校准
- 日期：2026-09-26
- 适用版本：RimWorld 1.6，新 BDP 主模组
- 适用程序集：`BDP.Core.dll`、`BDP.Content.dll`、`BDP.Development.dll`
- 取代文档：`docs/plans/2026-08-31-chip-information-model-design.md` 中“按 Verb、Ability、Hediff、Passive 技术结构自动发现玩家功能”的部分
- 不取代内容：旧文档中已经成立的只读值模型、来源链、上下文、诊断和统一消费者入口原则

## 一、决策摘要

本次重构建立一层显式的“芯片功能语义契约”，用于回答玩家和外部消费者真正关心的问题：

```text
这枚芯片具有什么功能？
这个功能公开哪些属性？
这些属性的当前有效值是什么？
它在哪个形态、姿态或组合中生效？
```

最终采用以下核心方案：

1. 现有表达与执行系统继续作为游戏行为的唯一事实来源。
2. 功能语义由 XML 显式声明，不再从 `Verb`、`Ability`、`Hediff`、`Passive` 等技术类型推测。
3. 功能声明只读，不参与攻击、能力、状态、护盾、资源、形态或组合的执行裁定。
4. 属性实际值从现有定义、有效表达结果或运行状态读取，不在语义声明中复制游戏数值。
5. 第三方实现主动声明自己属于哪个功能语义；功能语义不维护“所有已知实现”的全局名单。
6. XML 是主要扩展入口；只有全新的取值算法才需要小型 C# `Worker`（读取器）。
7. 通用展示器保证未知第三方功能与属性至少可以正常列出；专用展示器只能增强视觉，不能垄断信息。
8. 制造台、装配台、检查面板和第三方读取者消费同一个 `ChipInformationModel`。
9. 不保留旧字段、旧序列化或新旧双轨兼容；当前没有需要保护的正式存档。
10. 现有游戏行为必须保持不变，这是重构的硬门槛。

## 二、已经确认的现状

### 2.1 BDP 当前不是“定义文件直接交给原版执行”

现有主链大致为：

```text
ChipDefinitionConfig.Expression
        ↓
ChipExpressionEntryConfig
        ↓
ChipExpressionContract
        ↓
FormalExpressionResult / ResolvedVerbSpec
        ↓
BDP 宿主、同步与执行适配
        ↓
RimWorld 原版 Verb / Ability / Hediff 等机制
```

因此，作者在 XML 中写入与原版同名或相似的属性，并不等于原版直接读取该 XML 节点。BDP 会先把作者声明解释为自己的契约和正式结果，再把结果交给原版机制或 BDP 的原版适配宿主。

这一层转换本身不是错误。动态合并、形态姿态、组合技、武装构型和运行时有效值都需要稳定的中间结果。真正的问题是：现有信息系统又从这些技术结果反向推测“玩家功能”，造成了第二次不稳定翻译。

### 2.2 当前信息模型的主要问题

当前路径大致为：

```text
定义 / 表达结果
        ↓
技术事实提取
        ↓
Ranged / Melee / Ability / Hediff / Passive 规则
        ↓
ChipInformationBlock
        ↓
界面根据 Kind、BlockKey、FieldKey 再判断含义
```

已经确认的问题包括：

- `ChipInformationExpressionBlockBuilder` 大量投影 `VerbProperties`、`AbilityDef`、目标参数、投射物、Tool 和模块字段。
- `ChipInformationAbilityCompReflectionProvider` 会反射公开标量字段，不能保证玩家语义、有效值或长期稳定性。
- `ChipInformationExtensionRegistry` 以技术对象类型和 `CanProvide()` 逐个试探，存在顺序依赖、首个命中和异常静默问题。
- `ChipInformationDetailRenderer` 根据硬编码块种类、字段键和父子位置识别护盾等业务意义。
- 制造预览与装配预览虽然名义上消费同一个模型，但可用事实与展示路径并不真正对称。
- `ExpressionPublishedResultSnapshot.InformationBlocks` 让表达发布层承担信息结构构造，混合了执行事实和玩家解释。
- `RoleKey`、`Tags` 和运行时 `SemanticContext` 都不是静态功能语义契约，不能替代新结构。

### 2.3 现有结构与玩家功能不是一一对应

实际内容已经证明：

- `FujinRangedStrike` 技术入口是 `Ability`，玩家功能是远程攻击。
- 变色龙由一个 `Hediff` 条目和一个 `Ability` 条目共同构成一个隐蔽功能。
- 光魂同时包含两个护盾来源、盾击和重刃近战，并按形态与姿态选择。
- 推进器既提供机动，又参与光魂推进组合。
- 旋空主要作为组合支持来源，不能用 `Passive` 这个技术类型替代玩家说明。

因此，信息系统必须承认“功能语义”和“技术实现”是多对多关系。

## 三、需求目标与非目标

### 3.1 目标

- 作者显式声明芯片功能语义。
- 功能语义与技术实现路线解耦。
- 实际属性值来自正式定义、有效定义或运行状态。
- 制造台可以根据实时组合显示完整候选信息。
- 装配台可以显示成品配置和当前运行状态。
- 第三方可以通过 XML 新增功能、属性和声明。
- 第三方可以复用 BDP 标准语义，并使用自己的实现路线。
- 同一种功能可以存在多个实例、形态和姿态变体。
- 复杂攻击、爆炸、状态等结果可以结构化显示。
- 信息错误不能影响游戏执行。

### 3.2 非目标

- 不把 BDP 改造成通用插件平台或大型依赖注入框架。
- 不创造一套 XML 脚本语言。
- 不保证任意未知模组在没有任何声明时能被自动识别。
- 不让语义声明生成、修改或授权游戏行为。
- 不要求第一版定义所有未来可能出现的功能和属性。
- 不维护旧信息字段、旧序列化或旧存档兼容。
- 不以“编译通过”代替实际游戏行为验证。

## 四、方案复审与取舍

### 4.1 方案 A：在旧技术信息链上追加语义标签

做法：保留现有技术块、反射和界面判断，只给结果补“护盾”“远程攻击”等标签。

优点：短期改动小。

缺点：

- 技术结构和玩家语义继续混杂。
- 旧规则、标签和新声明形成双轨。
- 第三方仍需理解块键、字段键和注册顺序。
- 不能消除当前根因。

结论：拒绝作为最终方案。

### 4.2 方案 B：保留执行系统，重建只读功能语义层

做法：执行系统保持不变，在信息边界新增显式功能声明、来源读取和语义展示。

优点：

- 直接解决当前根因。
- 对现有玩法执行侵入最小。
- 支持制造预览、运行信息和第三方扩展。
- 可以在迁移完成后彻底删除旧技术信息链。

结论：采用。

### 4.3 方案 C：把表达系统和语义系统合并成一套统一图

优点：表面上只有一套模型。

缺点：

- 功能与实现天然多对多，强行合并反而产生更复杂的图。
- 为了信息展示触及攻击、护盾、能力和组合执行主链。
- 回归风险远大于收益。
- 不符合 RimWorld 模组的最小必要性。

结论：拒绝。

### 4.4 被否决的“功能语义维护所有实现列表”

以下方向技术上可行，但不作为正式主路径：

```text
护盾语义
├─ BDP 实现 A
├─ BDP 实现 B
└─ 第三方实现 C
```

原因：

- 护盾语义会变成实现注册中心。
- 制造预览仍要扫描技术结构并匹配列表。
- 通用技术类可能被多个功能复用，容易误判。
- 一个实现也可能同时承载多个功能，关系会迅速复杂化。

采用相反方向：

```text
BDP 实现 A   ─┐
BDP 实现 B   ─┼─> 显式声明：BDP_Feature_Shield
第三方实现 C ─┘
```

以后若确有兼容未声明旧模组的需求，可以另建受控兼容绑定，但不得成为制造台和正式信息系统的主事实来源。

## 五、核心边界：双契约、单向关联

### 5.1 执行契约

执行契约回答“游戏实际怎样工作”。它继续包括：

- 表达配置与表达契约；
- 正式表达结果；
- `ResolvedVerbSpec`；
- Ability、Hediff 和被动宿主；
- Trion 消耗；
- 形态、姿态和组合求值；
- 攻击、投射物、护盾、状态和视觉执行。

它是游戏行为的唯一事实来源。

### 5.2 功能语义契约

功能语义契约回答“它对玩家意味着什么”。它包括：

- 功能身份；
- 功能允许公开的属性；
- 当前芯片明确声明的功能实例；
- 属性值来源；
- 形态、姿态和组合中的归属；
- 通用或专用展示选择。

它是正式公开解释，但没有执行权。

### 5.3 单向关系

```text
执行定义 / 执行结果 ──只读──> 功能语义解析

功能语义声明 ──禁止──> 攻击、护盾、能力或资源执行
```

运行系统不得读取 `ChipFeatureDef` 或 `ResolvedChipFeature` 来决定武器是否存在、能否施放、是否格挡、如何扣除 Trion 或怎样切换形态。

## 六、术语与命名

### 6.1 制造预设重命名

当前 `ChipFunctionDef` 实际表示制造台可选的一整套芯片制造方案，不是功能语义。

重命名为：

```text
ChipManufacturingPresetDef
```

新功能语义类型命名为：

```text
ChipFeatureDef
```

由于不要求旧存档和旧 XML 兼容，可以一次性迁移，不保留别名。

### 6.2 主要对象

| 名称 | 职责 |
| --- | --- |
| `ChipFeatureDef` | 一个稳定的玩家功能语义，例如护盾 |
| `ChipFeaturePropertyDef` | 一个稳定的玩家属性语义，例如有效施放距离 |
| `ChipFeaturePropertySlot` | 某功能允许接收的一个属性及其顺序 |
| `ChipFeatureDeclaration` | 某枚芯片显式声明的一个功能实例 |
| `ChipFeatureSourceConfig` | 说明该功能从哪个实际来源读取值 |
| `IChipFeatureSourceWorker` | 对一种来源配置执行只读取值 |
| `ResolvedChipFeature` | 已解析、可公开读取的功能快照 |
| `ChipInformationRequest` | 制造、成品或运行信息的统一请求 |

## 七、程序集职责

### 7.1 Core.dll

Core 只提供中性基础设施：

- 上述 Def 类型的 C# 类定义；
- 功能声明、属性槽位和来源配置基类；
- 读取器接口与安全实例化；
- 解析请求、解析结果、来源链、上下文和诊断；
- 通用解析、合并与校验机制；
- 公开只读读取面。

Core 不定义“护盾”“远程攻击”等具体 Def 实例，也不包含它们的业务读取器和界面。

### 7.2 Content.dll

Content 承载正式业务：

- BDP 标准功能 Def；
- BDP 标准属性 Def；
- BDP 芯片与组合的功能声明；
- 标准 Verb、Ability、Hediff、被动和模块来源读取器；
- 制造台、装配台和检查面板接入；
- 通用功能展示器和必要的专用展示器。

### 7.3 Development.dll

Development 承载：

- 原始技术事实查看；
- 解析诊断与语义快照导出；
- XML-only（纯 XML）扩展示例；
- 自定义 Worker 扩展示例；
- 游戏内回归诊断入口。

正式信息模型不得依赖 Development。

## 八、功能与属性 Def

### 8.1 ChipFeatureDef

概念结构：

```csharp
public sealed class ChipFeatureDef : Def
{
    public int DisplayOrder;
    public List<ChipFeaturePropertySlot> Properties;
}
```

`label` 和 `description` 使用 RimWorld 原生 Def 语言包。功能 Def 不包含已知实现列表。

### 8.2 ChipFeaturePropertyDef

概念结构：

```csharp
public sealed class ChipFeaturePropertyDef : Def
{
    public ChipInformationValueKind ValueKind;
    public string UnitKey;
}
```

属性 Def 代表精确语义，不只代表单位。例如不定义一个含义模糊的 `Distance`，而分别定义：

- `CastRange`：使用者到施放目标的最大距离；
- `MinimumCastRange`：禁止施放的近距离范围；
- `EffectRadius`：目标点周围的作用半径；
- `MovementDistance`：位移实际跨越距离。

### 8.3 属性槽位可由 XML 扩展

护盾语义可以声明：

```xml
<Properties>
  <li><Property>BDP_Property_ShieldCapacity</Property><Order>100</Order></li>
  <li><Property>BDP_Property_ShieldRecovery</Property><Order>200</Order></li>
  <li><Property>BDP_Property_BlockArc</Property><Order>300</Order></li>
</Properties>
```

第三方可以通过 RimWorld 原生 `PatchOperationAdd` 增加新的属性槽位，例如反射比例。

属性槽位表示“该语义允许接收和展示该属性”，不表示所有实现必须提供该值。缺值的可选属性默认不显示，避免普通护盾出现大量“未知”。第一版不建立严格的必需属性体系；以后只有出现真实验证需求时再增加。

属性完整定义保持独立，一个属性可以被多个功能引用。

## 九、芯片功能声明

### 9.1 基本结构

`ChipDefinitionConfig` 增加：

```csharp
public List<ChipFeatureDeclaration> Features;
```

概念结构：

```csharp
public sealed class ChipFeatureDeclaration
{
    public string Id;
    public ChipFeatureDef Feature;
    public string LabelKey;
    public List<ChipFeatureSourceConfig> Sources;
    public List<ChipFeatureDeclaration> Children;
}
```

规则：

- `Id` 在当前配置范围内稳定且唯一。
- 同一种 `FeatureDef` 可以存在多个实例。
- 相同 `FeatureDef` 不自动合并。
- `LabelKey` 只用于区分姿态或变体，不覆盖语义身份。
- 复杂效果使用 `Children`，不另造第二套效果系统。

### 9.2 实现主动声明语义

第三方自定义护盾在自己的芯片配置中写入：

```xml
<Features>
  <li>
    <Id>custom_shield</Id>
    <Feature>BDP_Feature_Shield</Feature>
    <Sources>
      <li Class="OtherMod.Information.CustomShieldSourceConfig">
        <Id>shield_source</Id>
        <WorkerClass>OtherMod.Information.CustomShieldSourceWorker</WorkerClass>
      </li>
    </Sources>
  </li>
</Features>
```

信息系统无需判断这个实现“像不像护盾”，因为 XML 已明确声明功能身份。

### 9.3 给既有芯片追加声明

兼容补丁模组可以对目标芯片的 `config/Features` 使用 `PatchOperationAdd`。这仍是显式声明，不建立全局实现扫描器。

## 十、来源配置与 Worker

### 10.1 XML 优先

标准来源应支持纯 XML 使用，例如：

- 表达条目来源；
- Verb 条目来源；
- Tool 条目来源；
- Ability 条目来源；
- Hediff 条目来源；
- 被动条目来源；
- 远程模块来源；
- 组合最终表达来源。

扩展者使用已有来源配置时无需编写或注册 C#。

### 10.2 新取值算法才需要 C#

概念基类：

```csharp
public abstract class ChipFeatureSourceConfig
{
    public string Id;
    public Type WorkerClass;
}
```

概念接口：

```csharp
public interface IChipFeatureSourceWorker
{
    IReadOnlyList<ChipFeatureValueContribution> Resolve(
        ChipFeatureSourceConfig source,
        ChipFeatureReadContext context);
}
```

第三方全新实现通过 XML 的 `Class` 和 `WorkerClass` 挂接读取器，不要求启动代码调用全局 `Register()`。

Core 应校验 Worker 类型、缓存无状态 Worker 实例并隔离异常。不得以 `CanProvide()` 顺序试探和首个命中作为正式裁定。

### 10.3 Worker 的限制

Worker 只能：

- 定位来源；
- 读取或计算实际有效值；
- 返回以属性 Def 为键的类型化贡献。

Worker 不得：

- 决定功能身份；
- 创建信息块或界面控件；
- 修改游戏对象；
- 授予攻击、护盾或能力行为；
- 反射倾倒所有公开字段。

### 10.4 不支持任意 XML 字段路径

不提供类似以下接口：

```xml
<FieldPath>hediff.comps[0].props.maximumEnergy</FieldPath>
```

原因：字段路径会重新把玩家语义绑定到内部对象布局，不能表达有效值计算、优先级、条件和运行状态，并最终演化为脆弱的 XML 脚本语言。

### 10.5 多来源属性裁定

一个功能可以有多个来源，例如变色龙同时引用 Ability 和 Hediff。来源列表顺序不是覆盖优先级，也不能产生“最后一个写入者获胜”的隐式规则。

每个 Worker 返回带有属性 Def、值层级和来源记录的贡献。解析器按以下规则裁定：

- 不同属性：直接并入同一功能；
- 同一属性、相同值：合并来源链；
- 同一属性、不同值、层级不同：运行时值覆盖有效定义值，有效定义值覆盖作者声明值；
- 同一属性、不同值、层级相同：标记 `Conflict`，不按来源顺序猜测；
- 需要把多个底层数值组合成一个有效值时：由一个明确的来源 Worker 完成计算并返回最终贡献，不让通用合并器猜业务公式。

Worker 只能返回当前 `FeatureDef.Properties` 允许的属性。第三方要给已有语义增加新属性时，必须先用 XML 扩充属性槽位，然后由其来源提供该值。

## 十一、复杂功能与子功能

所有复杂结果复用同一 `ChipFeatureDeclaration` 结构。

例如美特拉：

```text
远程攻击
├─ 射程、准备时间、命中结果
└─ 范围伤害
   ├─ 半径
   ├─ 伤害
   └─ 伤害类型
```

例如铅弹：

```text
攻击增强
├─ 适用对象
├─ 直接伤害处理
├─ 护盾绕过规则
└─ 状态施加
   ├─ 状态
   ├─ 强度
   └─ 持续时间
```

首批候选子功能语义：

- 直接伤害；
- 范围伤害；
- 附加伤害；
- 状态施加；
- 属性修改；
- 身体能力修改；
- 资源变化；
- 对象生成。

作者侧通常控制在两层以内。数据结构可以递归，但解析和界面必须有深度保护；过深第三方结构产生诊断并停止继续展开。

## 十二、首批标准功能语义

首批只覆盖 BDP 当前真实内容：

| 功能语义 | 当前内容 |
| --- | --- |
| 远程攻击 | 小行星、美特拉、毒蛇、猎犬、卵之冠、朱鹮、Fujin 远程攻击 |
| 近战攻击 | 弧月、Fujin、蝎子、光魂盾击与重刃 |
| 护盾 | 能量护盾、自动能量护盾、光魂大盾 |
| 机动 | 蚱蜢、浮空、推进器、紧急脱离 |
| 隐蔽 | 变色龙 |
| 攻击增强 | 铅弹、铅弹·改 |
| 组合支持 | 旋空、推进器等组合来源 |

同一芯片可以声明多个功能。`Ability`、`Hediff`、`Passive` 不作为玩家功能语义。

未来出现治疗、召唤、部署、精神控制等真实内容时，可以新增功能 Def；第一版不提前建立完整功能百科。

## 十三、公共属性目录

属性细目允许在实现过程中按 BDP 真实数据继续校准，但分类和精确语义原则已经确定。

### 13.1 使用与触发

- 使用方式：主动、被动、开关、持续、自动；
- 触发条件：使用、受击、命中、攻击完成、濒危、战斗体崩解等；
- 目标类型：自身、地点、角色、物体、区域等；
- 是否要求视线；
- 使用概率；
- 使用次数与最大次数；
- 充能时间；
- 单次使用消耗；
- 持续维持消耗；
- 玩家可理解的使用要求。

### 13.2 空间

- 有效施放距离；
- 最小施放距离；
- 效果半径；
- 最大目标数；
- 移动距离；
- 作用角度；
- 路径和环境限制。

### 13.3 时间

- 准备时间；
- 冷却时间；
- 效果持续时间；
- 周期作用间隔；
- 恢复延迟；
- 结束条件。

原版与 DLC 的能力数据调查表明，距离、准备时间、视线、冷却、持续时间和效果半径具有高复用价值，应成为标准属性，而不是按能力逐个特判。

### 13.4 通用结果

- 伤害数值；
- 伤害类型；
- 护甲穿透；
- 治疗量；
- 施加状态；
- 状态强度；
- 属性变化；
- 身体能力变化；
- 叠加上限；
- 解除条件；
- 生成对象与数量。

复杂列表必须保持结构化，不压成不可解析的长文本。

### 13.5 BDP 专用重点

远程攻击、近战攻击和护盾的最终字段目录由后续业务校准，但至少需要覆盖：

- 远程：射程、精度、伤害、穿透、连发、投射物行为、追踪、引导、爆炸和附加状态；
- 近战：攻击方式、伤害、类型、穿透、冷却、权重、连击次数和间隔；
- 护盾：防护角度、格挡概率、可抵挡类型、容量或资源、抵挡消耗、恢复、破盾、绕过、反射和转化。

## 十四、形态、姿态与上下文

### 14.1 不重复声明生效关系

现有 `ChipExpressionModeConfig` 和 `ChipExpressionStanceConfig` 已通过 `ActiveEntryIds` 定义条目在哪些上下文生效。

功能声明只引用来源条目，信息解析器读取现有选择拓扑，将功能投影到上下文。它不根据技术类型推测功能，也不要求作者重复填写形态与姿态关系。

### 14.2 光魂示例

```text
大盾 / 灵活姿态
├─ 护盾
└─ 近战攻击：盾击

大盾 / 举盾姿态
├─ 护盾
└─ 近战攻击：盾击

重刃形态
└─ 近战攻击：重刃
```

一个逻辑功能声明可以引用多个来源条目，并在不同上下文解析出相应有效值。确实是两个独立功能时则使用不同功能实例 `Id`。

### 14.3 信息上下文与运行时语义上下文分离

- `ChipInformationContext`：用于玩家查看形态、姿态和组合。
- `SemanticContext`：用于攻击、爆炸、伤害和崩解等运行时来源追踪。

二者不复用、不互相转换。

## 十五、制造合并与组合技

### 15.1 制造配置合并

当前双预设制造会为表达条目增加 `mfg_0_`、`mfg_1_` 前缀并生成两个形态。功能声明必须在同一次复制中同步改写：

```text
shield                     → mfg_0_shield
energy_shield_primary      → mfg_0_energy_shield_primary
```

表达复制和功能复制不得各自重新计算映射。应由同一个复制上下文提供旧 `Id` 到新 `Id` 的映射，避免漂移。

### 15.2 相同语义不自动合并

两个功能都引用 `BDP_Feature_Shield`，不代表它们是一面护盾。默认按功能实例 `Id` 保持独立。第一版不实现隐式合并；未来若出现真实需求，只增加显式合并声明。

### 15.3 组合技显式声明功能

`ComboDef` 增加自己的 `Features`。组合结果不是来源芯片信息的简单拼接：

```text
ComboDef.Features
        +
最终组合 FormalExpressionResult
        ↓
组合功能信息
```

来源芯片功能仍可单独展示；组合功能位于独立组合上下文。组合功能属性读取最终组合结果，不从两侧原始数值猜测。

## 十六、统一请求与数据流

### 16.1 ChipInformationRequest

统一请求概念结构：

```text
Identity
DeclaredConfig
EffectiveConfig
RuntimeSnapshot（可选）
CurrentModeKey（可选）
CurrentStanceKey（可选）
ComboResults（可选）
Descriptions / 业务来源说明（可选）
```

### 16.2 最终数据流

```text
ChipInformationRequest
        ├─ GeneralInfoResolver
        ├─ ChipFeatureResolver
        ├─ ContextProjector
        └─ DiagnosticCollector
                    ↓
            ChipInformationModel
            ├─ Identity
            ├─ GeneralBlocks
            ├─ Features
            ├─ Contexts
            └─ Diagnostics
                    ↓
制造台 / 装配台 / 检查面板 / 第三方读取
```

### 16.3 值层级

```text
运行时值 > 有效定义值 > 作者声明值
```

最终值采用高层值，`ChipInformationProvenance` 保留来源链。功能身份不随数值层变化。

### 16.4 制造台与装配台差异

制造台：

- 使用玩家当前选择即时产生候选配置；
- 没有运行时对象；
- 展示全部形态与姿态并标记默认项；
- 当前方案与基准方案使用相同模型比较。

装配台：

- 读取成品芯片的有效配置；
- 可以附加当前形态、姿态和运行值；
- 当前上下文优先展示，其他上下文仍可查看。

二者只在请求内容上不同，不拥有不同的功能理解逻辑。

## 十七、输出模型与比较键

最终 `ChipInformationModel` 建议收敛为：

```text
Identity
GeneralBlocks
Features
Contexts
Diagnostics
```

`GeneralBlocks` 保留分类、装载、Trion、启用条件、描述和构型来源等非功能信息。

功能比较键：

```text
功能实例 Id + 属性 Def
```

子功能使用完整路径：

```text
meteora_attack / impact_explosion / DamageAmount
```

不再以技术块名和字段名作为玩家功能比较身份。

## 十八、展示契约

### 18.1 通用展示器

通用展示器按以下顺序输出：

- 功能 Def 默认顺序；
- 功能实例声明顺序；
- 属性槽位顺序；
- 子功能声明顺序。

新语义、新属性和新来源即使没有专用界面，也必须能通过通用展示器显示。

### 18.2 专用展示器

专用展示器按 `FeatureDef` 选择，只读取 `ResolvedChipFeature`，不得访问技术实现对象。

它必须返回已消费属性集合：

```text
专用展示器认识的属性 → 专用视觉
剩余属性             → 通用展示器追加显示
```

因此第三方为护盾增加反射比例时，即使 BDP 护盾图表不认识该属性，也不会丢失。

### 18.3 玩家文本

- 功能和属性名称优先使用 DefInjected 语言包；
- 动态提示和诊断摘要使用 Keyed 语言包；
- C# 不硬编码新增玩家可见文本。

## 十九、扩展场景

### 19.1 复用标准语义和标准来源

第三方新增普通 Ability 路线的远程攻击：

- XML 引用 `BDP_Feature_RangedAttack`；
- XML 使用标准 Ability 来源配置；
- 不需要 C#；
- 通用或远程攻击专用展示器自动工作。

### 19.2 复用标准语义，使用全新实现

第三方自定义组件实现护盾：

- XML 引用 `BDP_Feature_Shield`；
- 自定义 `ChipFeatureSourceConfig`；
- 提供一个只读 Worker；
- Worker 输出 BDP 标准护盾属性或第三方新增属性；
- 展示层仍只看护盾语义。

### 19.3 新功能语义

第三方定义自己的 `ChipFeatureDef` 和属性 Def，并在芯片 XML 中声明。没有专用展示器时走通用展示。

### 19.4 新属性扩充已有语义

第三方定义属性 Def，并用 XML Patch 向 BDP 功能 Def 的属性槽位追加引用。其实现来源提供该值；普通 BDP 实现不提供时不显示。

## 二十、诊断与失败处理

### 20.1 定义加载检查

- 功能实例 `Id` 重复；
- 功能 Def 缺失；
- 来源 `Id` 重复；
- 表达条目引用不存在；
- Worker 类型无效或无法实例化；
- 返回值类型与属性 Def 不一致；
- 子功能结构异常过深；
- 来源在任何上下文中都不可达；
- 来源声明了功能 Def 不允许的属性。

BDP 自有内容出现上述问题时，项目验证应失败。

### 20.2 运行解析处理

| 问题 | 行为 |
| --- | --- |
| 找不到来源 | 保留功能身份，相关属性未知 |
| Worker 异常 | 隔离异常并记录具体来源与 Worker |
| 类型错误 | 属性标记 Invalid |
| 多来源无法裁定 | 属性标记 Conflict |
| 运行对象不存在 | 回退有效定义值 |
| 专用展示器不认识属性 | 通用展示器显示 |

不得静默吞异常，不得用旧技术扫描作为回退。

正式界面只显示必要的“信息不可用”摘要；详细诊断进入 Development 或日志，并做去重以避免每帧刷屏。

## 二十二、行为保护边界

重构不得改变：

- 表达条目选择、解释和正式结果；
- Verb 创建、宿主和同步；
- 远程与近战攻击执行；
- Ability 释放与冷却；
- Hediff 添加、移除和生命周期；
- 护盾拦截和消耗；
- Trion 占用、消耗、崩解和恢复；
- 形态与姿态切换；
- 组合技准入、来源选择与求值；
- 武装构型的实际执行修改。

允许触及执行相关结构的范围只有：

- 暴露只读稳定标识或快照；
- 制造复制时同步复制功能声明；
- 删除经引用审计确认只供旧信息系统消费的字段。

## 二十三、迁移策略

1. 固化当前玩法行为基线和关键诊断。
2. 新增 Core 中性功能契约与解析结果。
3. 在 Content 中定义首批标准语义和属性。
4. 给 BDP 全部制造预设、芯片和组合补齐功能声明。
5. 让制造配置复制和双预设合并同步处理功能声明。
6. 在不切换 UI 的情况下生成新语义快照并验证。
7. 先切换制造台，再切换装配台和其它消费者。
8. 删除技术类型规则、反射读取、旧表达信息块和界面硬编码。
9. 全局搜索确认没有旧路径残留。
10. 完成编译、结构测试、扩展示例和游戏内行为回归。

实施中可以短暂并行产生新旧模型用于比对，但最终提交不得保留双轨。

## 二十五、允许后续校准但不得破坏的部分

以下细节可以在实施中根据真实内容调整，无需重新推翻架构：

- 首批属性 Def 的精确数量与命名；
- 某个复杂结果使用属性还是子功能；
- 专用展示器的具体视觉；
- 个别属性的排序和分组；
- 是否为极少数属性增加“必需”标记；
- 哪些标准来源 Worker 放入首批实现。

以下边界不得在实施中自行改变：

- 功能身份必须显式声明；
- 语义契约不参与执行；
- 实现主动声明语义，不建立全局实现猜测主链；
- XML 优先，C# 只补新取值算法；
- 实际值来自真实来源，不在语义声明中复制；
- 两个工作台消费同一模型；
- 专用展示不能吞掉未知属性；
- 最终不保留旧技术信息双轨；
- 现有玩法行为不得改变。

## 二十六、最终验收标准

- 所有 BDP 正式芯片都具有显式功能声明。
- 同一玩家语义可以由 Verb、Ability、Hediff、被动或第三方实现提供。
- 制造台和装配台使用同一个功能解析服务。
- 功能展示不依赖技术块类型、父子位置或反射字段。
- 第三方可纯 XML 新增语义、属性和标准来源声明。
- 第三方可用一个小型 Worker 接入全新实现路线。
- 新属性在专用展示器未知时仍由通用展示器显示。
- 复杂效果、形态、姿态和组合保持结构化。
- 信息解析失败不会改变任何游戏行为。
- 旧技术类型规则、反射倾倒和表达信息块已清除。
- Core 保持中性，Content 承载正式业务，Development 承载诊断与样例。
- 代表性芯片和组合通过结构验证与游戏内行为回归。
