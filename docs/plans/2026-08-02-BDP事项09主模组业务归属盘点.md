# BDP 事项09：主模组业务归属盘点

## 一、这份盘点要解决什么

事项09不是迁移实施，而是先回答一个问题：主模组当前已经存在的内容，哪些是真正的通用底层，哪些只是暂时放在主模组里的具体业务。

本轮只读取并整理主模组现有的：

- `Source/BDP/Core`（核心程序集源码）
- `Source/BDP.Content`（内容程序集源码）
- `1.6/Defs`（游戏定义文件）

本轮明确不做：搬文件、改命名、删内容、改 XML 参数、修改程序集引用关系。

## 二、判断规则

| 判断 | 含义 |
|---|---|
| Core 底层 | 不带某一款芯片或某一个具体玩法目标，负责通用状态、规则、运行时流程、原版接线或稳定契约。 |
| Content 公共支撑 | 仍然是可复用的内容侧能力，例如界面扩展、视觉表现、内容注册入口；它可以依赖 Core，但 Core 不反向寻找它。 |
| Content 具体业务 | 为某个明确玩家功能服务，例如紧急脱离、天赋检测、装配台等。以后可以逐项确认是否正式保留。 |
| 待复查 | 当前名字或目录不能直接说明归属，必须结合调用链和玩家用途再决定。 |

注意：文件放在 `Core` 目录，或 XML 放在主模组的 `Defs` 目录，并不自动证明它就是底层。归属要看它解决的是“通用问题”还是“某个具体玩法”。

### 4. 不能只凭目录定案的区域

| 当前区域 | 为什么不能直接定案 |
|---|---|
| `Core/CombatBody/Escape` 与普通战斗体退出流程的交界 | 紧急脱离调用了通用崩解主链，需确认哪些是通用退出步骤，哪些只是脱离业务分支。 |
| 装配台、芯片仓 | 未来可能是别的模组也能依赖的装载设施，也可能只是 BDP 的一个玩家业务；需要看扩展契约和玩家保留意图。 |
| `Core/Trion/Talent` 的结果计算部分 | “Trion 容量潜质/释放力”的数值生成可被 Core 使用，但“检测仪、检测工作、检测 UI”是具体业务，可能需要拆开。 |
| `CombatBodyConfigDefs`、`CombatBodyWoundPolicyDefs` | 配置本身偏中性，但当前默认值和视觉/业务用途可能带有 BDP 具体玩法假设。 |
| `TriggerCategoryDefs.xml` 中的边境/近界/黑类别实例 | 类别字段和校验是 Core 底层；具体类别实例是否继续由主模组提供，要结合最终触发体业务范围确认。 |

## 四、本轮结论

1. 主模组并不是“所有现有内容都已经是底层”。至少 `Trion/Talent`、`CombatBody/Escape`、装配设施属于明显的具体业务，虽然当前代码物理上仍在 Core。
2. 反过来，Content 也不等于“临时测试代码”。拖尾、正式界面和可插拔诊断入口已经是可复用的内容侧支撑。
3. 下一步不能按目录整体搬迁，必须按“通用运行时”和“具体玩家功能”的边界拆开确认。
4. 本事项到这里暂不改变游戏行为。只有用户确认归属后，才进入某一个小组的逐文件迁移或保留处理。

## 五、确认顺序进度

原先建议的 `Core/Trion/Talent`、`CombatBody/Escape`、装配设施和伤口视觉均已按事项09A—09D逐组处理。

其中，战斗日志不是必须保留的正式业务，而是一次临时兼容实验；用户已确认按事项09E完整退役，未来若重新处理，以原版日志显示为基线重新设计。

事项09剩余区域继续保持“先盘点、再确认、逐组处理”的顺序，不把未确认的候选内容批量搬入主模组。

## 六、全量归属建议（当前物理位置 → 建议目标）

### A. 可以明确判定为“现在放错在 Core，目标应为 Content”的整组

#### 1. 触发器装配业务

当前（事项09C完成后）：`Source/BDP.Content/Assembly/**`

包括装配台建筑、芯片仓组件、设施连接读取器、装配事务、搬运/装配 Job、WorkGiver、装配窗口和三个装配面板。

对应 Def 已移到 `1.6/Content/Defs/Buildings/Assembly`、`Jobs/Assembly`、`WorkGivers/Assembly`。

理由：这些内容直接创建玩家可摆放建筑、存放芯片、安排小人工作并打开玩家窗口，是完整的“装配台业务”。Core 已经有足够的 `Trigger` 正式读取面和命令面，不需要知道装配台、芯片仓或窗口。事项09C已按此边界完成迁移，Core只保留公开芯片定义快照读取面。

#### 2. Trion 天赋检测业务

当前：`Source/BDP/Core/Trion/Talent` 中的检测器、便携检测器、检测资格/浮动菜单、检测提交服务、结果对象、Job 和 WorkGiver。

建议：移到 `Source/BDP.Content/Trion/Talent/**`，对应 Def 移到 `1.6/Content/Defs/Buildings/Trion`、`Things/Trion`、`Jobs/Trion`、`WorkGivers/Trion`、`Trion/Talent`。

理由：这是一个可以整体启用或禁用的玩家功能“Trion 天赋检测”，不是 Trion 资源本身。Core 只需要提供容量潜质、释放力等角色事实和通用读写能力。

#### 3. 紧急脱离业务

当前：

- `Source/BDP/Core/CombatBody/Escape/**`
- `Source/BDP/Core/CombatBody/Flow/CombatBodyEmergencyEscape*`
- `Source/BDP/Core/CombatBody/External/CombatBodyEmergencyEscape*`
- `Source/BDP/Core/CombatBodySession` 中直接缓存和调用紧急脱离的部分
- `Source/BDP/Core/Buildings/PlaceWorker_OnlyOnePerMap.cs`（目前只被紧急脱离信标使用）

建议：业务执行、信标建筑、目的地寻找、传送表现、徽标状态和芯片消费逻辑移到 `Source/BDP.Content/CombatBody/Escape/**`；对应信标 Def 移到 `1.6/Content/Defs/Buildings/CombatBody`。

理由：紧急脱离是“某一枚芯片提供的具体能力”，不是所有战斗体都必须认识的生命周期规则。Core 应只保留“崩解时可让外部扩展参与”的中性事件/扩展口，由 Content 注册紧急脱离实现。不能把文件直接搬走后让 Core 继续直接调用它，否则会破坏严格单向依赖的设计意图。

#### 4. 伤口视觉表现

当前：`Source/BDP/Core/CombatBody/Wounds/Visuals/**`，以及 `1.6/Defs/Flecks/FleckDefs_WoundSpray.xml`。

建议：伤口喷溅发射和 Fleck 定义移到 Content；伤口严重度计算、Trion 泄露规则、持续扣费和伤口运行状态继续留在 Core。

理由：受伤如何改变 Trion 是通用规则；喷出什么视觉 Fleck 是玩家表现，应该可替换且不污染底层。

#### 5. 实验性战斗日志玩家文字表现（已退役）

原位置：`Core/CombatLog/**` 与 `Patches/Patch_LogEntry_ToGameStringFromPOV_BdpCombatLog.cs`。

处理结论：该功能只是临时验证原版日志兼容性的实验，不属于模组主线；已删除自定义快照、元数据仓库、中文格式化器、日志覆盖补丁，以及攻击协议中的表象传递。

保留内容：原版远程开火/命中日志写入和必要的 `weaponDef` 安全适配。未来若重新处理，以原版日志显示为基线重新设计。

### B. 不是整组搬迁，而是必须拆开的混合区域

#### 1. `CompTrion` 和 `ITrion*` 中混入了天赋检测状态

当前 Core 保留正确的底层事实：`TrionCapacityPotential`、`InnateTrionIntensity`、Trion 资源账本和扣费。

但以下内容是天赋检测业务状态，不应继续成为 Core 的正式资源契约：

- `TrionTalentAssessmentCompleted` 存档字段
- `ITrionReader.TrionTalentAssessmentCompleted`
- `ITrionCommands.TryMarkTrionTalentAssessmentCompleted()`
- 仅因“已检测”才显示结果的 `SpecialDisplayStats` 分支

建议：把“检测是否完成/检测结果是否已向玩家公开”放到 Content 自己的检测状态组件或扩展状态中；Core 继续提供原始容量潜质、释放力和通用资源读取。这样才能既保留“植入腺体后信息面板继续显示”，又不让 Core 认识某个检测仪业务。

#### 2. 战斗体会话流程混入了紧急脱离

当前 `CombatBodySessionService`、`CombatBodyExitTransaction`、`HostState` 直接持有 `CombatBodyEmergencyEscapeResolver/Service` 和 `CachedCollapseEmergencyEscape`。

建议：先在 Core 建立中性的“崩解/退出扩展通知”或结果扩展口，再由 Content 注册紧急脱离处理器；将缓存内容也改为通用扩展状态，不能让 Core 的宿主状态字段继续出现 `EmergencyEscape` 专名。

#### 3. 战斗体 Trion 徽标提供器混合了通用状态和紧急脱离

当前 `CombatBodyTrionGizmoExtensionProvider` 同时负责战斗体状态徽标和紧急脱离徽标。

建议：通用战斗体状态徽标留在 Core；紧急脱离徽标、贴图、颜色和提示文字拆为 Content provider，通过已有的 Trion 外部扩展注册口加入。

#### 4. 战斗体前台配置 Def 混合了底层快照与具体装备

当前 `1.6/Defs/Pawn/CombatBody/CombatBodyConfigDefs.xml` 同时定义：

- 通用快照排除策略（底层）
- 默认前台服装预设（具体表现）

处理结论（09F）：快照配置继续留在 `1.6/Defs`；未被生产运行时调用的默认前台预设和 `BDP_CombatBodyArmor` 示例服装直接退役，不迁入 Content。`CombatBodyFrontPresetDef` 类型本身继续留在 Core，Core 只提供通用配置契约；未来由 Content 或第三方模组按真实需求注册具体预设。

验证结果：默认宿主仍使用 `MirrorOriginal`（跟随原衣物），因此本次清理不改变玩家当前战斗体外观；前台外观专项和快照专项检查通过。

#### 5. 崩解原因文字与紧急冷却命名残留业务语义

处理前发现 `CombatBodyCollapseReasonPresenter` 是玩家文字格式化器，`CombatBodyService.EmergencyCooldownTicks` 则把战斗体通用冷却写成了“紧急冷却”。

处理结论（09G）：冷却字段已统一改为 `collapseCooldownTicks` / `CollapseCooldownTicks`，只改标识、不改数值与时序。原因文字映射暂留 Core，因为当前只处理通用的 `TrionAvailableDepleted`，不包含紧急脱离或其它具体业务；未来如果原因种类扩展到具体业务，再单独设计 Content 的文字提供器。

#### 6. Core 中性化巡检（09H）

处理结论：只读检查确认 Core 工程未反向引用 Content/DevHarness，Core Def 没有具体芯片或具体触发体，已完成内容化的业务没有回流。硬编码玩家文字、双武器入口显示名以及注释中的旧业务例子已记录为后续独立事项，本次不修改运行代码。

## 七、最后的目标结构（概念层）

```text
BDP.Core.dll
├─ 通用 Trion / 基因 / 芯片 / 表达 / Combo
├─ 通用 Trigger / CombatBody / 攻击 / 投射物
├─ 通用规则、契约、状态和原版接线
└─ 不认识装配台、天赋检测仪、紧急脱离或具体芯片

BDP.Content.dll
├─ 公共视觉与玩家界面
├─ 装配台与芯片仓
├─ Trion 天赋检测
├─ 紧急脱离
├─ 伤口视觉
└─ 以后逐项确认的具体芯片业务
```

这不是一次性迁移清单。每一组都要先确认，再建立中性扩展口，最后迁移和验证；否则直接搬文件会让 Core 继续通过隐式状态认识业务，表面上分成两个 DLL，实际仍然没有真正隔离。
