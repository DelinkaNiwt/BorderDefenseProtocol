# 表达系统主线重构与正式边界收口设计

**Goal（目标）:** 对 BDP 表达系统本体、正式结果层、复合来源层、已发布读取层与主要下游消费面做一次完整重审和收口，清理越界的 `ExpressionRuntimePayload（表达系统内部参数包）`，恢复正式边界，补齐复合来源消费缺口，并把代码、烟测、文档重新拉回同一套架构事实。

**Architecture（架构）:** 本轮继续保留“芯片条目解释器统一、combo 作为无实体第三芯片在表达系统内部成立”的总路线，不给 combo 另开第二套表达解释系统。重构重点不是推翻表达系统，而是把内部材料层、正式结果层、复合来源层和已发布读取层重新分清；内部信息只留在内部构建链，对外正式面统一收口到 `FormalExpressionResult（正式表达结果）`、`CompositeExpressionReference（复合来源引用）`、`TriggerCombatProjectionState（已发布战斗投影状态）`。

**Tech Stack（技术栈）:** RimWorld 1.6 Mod、C#、XML Def、PowerShell 烟测、BDP 主模组与 DevHarness

---

## 一、当前事实重审

### 1. 表达系统当前真实层级

当前系统不能只看成“FormalExpressionResult 一层”。

按实际代码，至少应分成下面 4 层：

```text
内部材料层：
ExpressionSourceMaterial

正式结果层：
FormalExpressionResult

复合来源层：
CompositeExpressionReference

已发布读取层：
TriggerCombatProjectionState
```

把它放回主链后，应理解为：

```text
激活芯片 / 来源声明
  -> ExpressionSourceMaterial                    // 内部材料
  -> 单侧 FormalExpressionResult                 // 正式单侧结果
  -> CompositeExpressionResolver                 // dual / combo 复合生成
  -> CompositeExpressionReference                // 复合来源映射
  -> ExpressionSnapshot
  -> TriggerCombatProjectionState                // 已发布正式读取面
  -> Ability / Hediff / Passive / Targeting / Host
```

### 2. 现在已经存在的 3 个正式读取面

这次重审确认，“下游正式读取面”并不只是一条：

1. `FormalExpressionResult`
   用来表达“系统正式承认了什么结果”。

2. `CompositeExpressionReference`
   用来表达“这条复合结果来自哪些单侧结果”。

3. `TriggerCombatProjectionState`
   用来把 `ResultIndex（结果索引）`、`CompositeReferenceIndex（复合引用索引）`、`ChannelIndex（类别索引）` 发布给运行时消费者。

所以当前问题不是“读取面太多”，而是：

- 各层职责没有守住。
- 内部参数包被塞进了正式层。
- 一部分下游已经读正式面，一部分老逻辑还停在旧单来源假设。

### 3. combo 当前真实实现状态

这次重审确认：

- combo 没有单独再写一套表达条目解释器。
- combo 当前确实复用了 `DefaultChipExpressionContractInterpreter（默认芯片表达契约解释器）`。
- 但 combo 仍然有自己的结果拼装与字段补值链。

也就是说，当前不是“完全统一”，而是：

```text
统一入口解释
  + combo 专用复合匹配
  + combo 专用结果拼装
```

这本身并不必然错误。

真正错误的是：

- combo 专用链在从正式结果反抠内部 payload。
- combo 的部分字段补值仍然只围绕 `mainPrimary / subPrimary` 组织，存在输入模型偏窄的问题。

## 二、确认存在的问题

### 1. `ExpressionRuntimePayload` 越权跨过了正式边界

当前它被挂到了：

- `FormalExpressionResult`
- `BdpFormalVerbBindingState`

这直接带来 3 个问题：

1. 内部材料对象越过了表达系统正式输出边界。
2. combo 内部构建开始依赖正式结果继续背内部材料。
3. formal host 宿主层开始携带自己本不该理解的表达系统内部对象。

### 2. combo 内部取材路径不诚实

当前 combo 工厂会从：

```text
sourceResult.RuntimePayload.SourceChip
```

回拿来源芯片快照。

这意味着：

- combo 不是直接从表达系统内部来源材料取值。
- 而是在要求“单侧正式结果替自己继续带内部数据”。

这条路必须切断。

### 3. 正式输出事实被误解成只有 `FormalExpressionResult`

用户对 `FormalExpressionResult` 的怀疑是合理的，但还不完整。

当前真正正式发布给下游的，不是一个对象，而是一组对象：

```text
FormalExpressionResult
+ CompositeExpressionReference
+ TriggerCombatProjectionState
```

所以本轮不应简单把所有缺口都硬补到 `FormalExpressionResult` 身上。

### 4. 下游主线大多已经在正确读正式面，但局部还停在旧假设

这次重审确认：

- Ability Trion 扣费已经读 `FormalExpressionResult.Trion`
- Hediff 持续耗蓝已经读 `FormalExpressionResult.Trion`
- dual targeting / formal host 已主要通过 `TriggerCombatProjectionState` 的索引回查正式真值

当前最明确的下游缺口，是：

- `CombatBodyEmergencyEscape` 仍只缓存单个 `SourceReference`
- 它没有复合来源消费能力

### 5. combo 输入模型仍有偏窄问题

目前 combo 的复合构建入口，仍主要从：

```text
mainPrimary / subPrimary
```

这两个单侧主结果出发。

这使它天然更偏向：

- 主副侧 Primary Verb

而不是一个更诚实的“来源芯片 + 该侧正式表达结果集合”的模型。

这不是说 combo 现在完全不能产出 `Ability / Hediff / Passive`。

而是说：

- 它的“输出类别”已扩展
- 但“内部来源输入模型”还没有完全跟上

### 6. 文档、烟测、代码已经漂移

当前至少有 3 套事实同时存在：

1. 旧计划中的 payload 外传路线
2. 后续内部化与复合来源收口的路线
3. 现在代码里的折中状态

这使得：

- 文档容易误导
- 烟测约束了旧边界
- 代码实际职责进一步变脏

## 三、这次重构的正式裁定

### 1. 保留统一表达解释器，不给 combo 再开第二套 parser

本轮明确保留：

- 芯片条目解释器统一
- combo 条目仍可转成普通 `ChipExpressionEntryConfig`
- combo 仍在表达系统内部复合阶段成立

本轮明确不做：

- combo 独立表达语法树
- combo 独立条目解释器
- combo 独立下游消费链

### 2. 对外正式面明确收口为 3 件东西

对外正式面裁定为：

1. `FormalExpressionResult`
2. `CompositeExpressionReference`
3. `TriggerCombatProjectionState`

其中职责分别是：

- `FormalExpressionResult`
  表达“这条结果是什么”

- `CompositeExpressionReference`
  表达“这条复合结果来自谁”

- `TriggerCombatProjectionState`
  表达“当前发布版本下，所有正式结果和复合来源映射怎样被稳定读取”

### 3. `ExpressionRuntimePayload` 只保留在表达系统内部

本轮明确裁定：

- `ExpressionRuntimePayload` 继续存在
- 但它只允许存在于 `ExpressionSourceMaterial`
- 不再出现在 `FormalExpressionResult`
- 不再出现在 `BdpFormalVerbBindingState`

这样做的含义不是“删掉内部信息”。

而是：

- 让内部信息回到它该待的层
- 不再污染正式输出边界

### 4. combo 的内部构建改为直接读内部来源材料

本轮不新增全局服务，也不把上下文做胖。

最小实现方向裁定为：

- 在复合构建阶段，为单侧正式结果建立到 `ExpressionSourceMaterial` 的内部映射
- combo 工厂通过这层内部映射直接拿来源芯片与内部快照
- 不再从 `FormalExpressionResult.RuntimePayload` 回拿

推荐的最小结构是：

```text
resultId -> ExpressionSourceMaterial
```

在实现层上，可以表现为：

- `CompositeExpressionResolver` 内部建立索引
- `ComboFormalExpressionResolution` 增加 `MainSourceMaterial / SubSourceMaterial`

这样既足够用，也不引入额外架构负担。

### 5. 下游继续只读正式面，不回头读 payload

本轮明确保留现有正确方向：

- Ability 继续从正式结果读 `Trion`
- Hediff 继续从正式结果读 `Trion`
- targeting / formal host 继续从已发布投影和正式结果读真值

本轮明确不做：

- Ability 改成读 payload
- Hediff 改成读 payload
- formal host 改成读 payload

### 6. `CombatBodyEmergencyEscape` 必须补成复合来源语义

本轮裁定：

- 单来源 passive：继续只消费 1 枚来源芯片
- 复合来源 passive：按已解析出的来源引用列表逐个消费

这条修正只属于：

- 已发布正式来源语义的正确消费

不属于“新增玩法”。

### 7. combo 输入模型要从“主副主攻结果中心”向“来源侧上下文中心”收口

本轮不打算把 combo 做成巨大的通用 DSL。

但必须做一个关键纠正：

- combo 的字段补值输入，不能再只在概念上等于 `mainPrimary / subPrimary`
- 它应当诚实地等于“来源侧上下文”

当前阶段推荐的最小收口方式是：

- 芯片级字段：从来源材料 / 芯片契约快照读取
- 表达级字段：优先从该侧正式结果读取
- 需要主副主攻的场景，只作为 `Verb` 相关字段的一个局部选择规则

这表示：

- `VerbPropsResolve / ExecutionResolve` 可以继续围绕该侧主 Verb 结果工作
- 但 combo 构建整体不再把“来源侧”误简化为“主 Verb 结果”

## 四、目标结构

### 1. 重构后的层次关系

```text
内部：
ExpressionSourceMaterial
  + ExpressionRuntimePayload
  -> SingleSide build
  -> Composite build (dual / combo)

正式：
FormalExpressionResult
CompositeExpressionReference
TriggerCombatProjectionState

下游：
Ability / Hediff / Passive / Targeting / FormalHost / CombatBody
```

### 2. 重构后的职责边界

#### 内部材料层

负责：

- 来源芯片身份
- 芯片契约快照
- 表达条目快照
- 内部构建期上下文

不负责：

- 作为对外正式输出

#### 正式结果层

负责：

- 结果类别
- 结果参数
- 单来源引用
- 结果显示与运行时正式字段

不负责：

- 继续充当内部材料包的外送壳

#### 复合来源层

负责：

- 记录复合结果来源结果 Id 列表
- 记录主副来源结果 Id

不负责：

- 重复存一套正式结果字段

#### 已发布读取层

负责：

- 稳定发布索引
- 统一给运行时消费者纯读访问

不负责：

- 承载内部材料对象

## 五、combo 在这次主线中的正确定位

### 1. combo 仍然是无实体第三芯片

这次重构后，combo 的定位不变：

- 不是实体芯片
- 不是第二套攻击系统
- 不是单独的新结果发布通道

它仍然是：

- 在表达系统内部由两枚芯片匹配出的、无实体第三芯片式结果

### 2. combo 仍然共享同一条表达总线

这次重构后，combo 仍然走：

```text
ComboDef
  -> 表达条目映射
  -> 统一条目解释器
  -> combo 复合结果工厂
  -> FormalExpressionResult
```

变化点只在于：

- combo 复合结果工厂不再反抠正式结果里的内部 payload
- 它改为从内部来源材料上下文取自己需要的内部信息

### 3. combo 作者侧写法不是本轮主阻塞点

当前 combo XML 写法确实还不够漂亮。

但这次主线重构的主阻塞点不是作者侧 XML 是否已经最优，而是：

- 正式边界脏了
- 内外层职责乱了
- 下游局部仍停在旧单来源假设

因此本轮以运行时和正式模型纠偏为主。

combo XML 作者侧若做收口，也只能在：

- 不打断这条主线
- 不再引入第二套解析规则

的前提下进行。

## 六、下游读取面重构结果

### 1. Ability

保持现状方向：

- 只从绑定的正式结果读取 `Trion`
- 不回头读芯片 Def
- 不读内部 payload

### 2. Hediff

保持现状方向：

- 只从宿主绑定的正式结果集合读取 `Trion`
- 不读内部 payload

### 3. targeting / formal host

保持现状方向：

- 只依赖 `TriggerCombatProjectionState`
- 用 `ResultIndex` 与 `CompositeReferenceIndex` 回到正式真值

同时做一处清理：

- `BdpFormalVerbBindingState` 不再携带 payload

### 4. CombatBodyEmergencyEscape

这条链需要从：

```text
单个 SourceReference
```

改成：

```text
SourceReferences 列表
```

它是当前确认存在的正式消费缺口，也是本轮唯一必须补齐的下游语义缺口。

## 七、文档与验证裁定

### 1. 烟测必须跟着新边界改

本轮烟测应改成约束下面这些事实：

- `FormalExpressionResult` 不再携带 `RuntimePayload`
- `BdpFormalVerbBindingState` 不再携带 `RuntimePayload`
- combo 工厂不再从 `sourceResult.RuntimePayload` 回读来源芯片
- `CombatBodyEmergencyEscape` 支持复合来源列表

### 2. DevHarness 必须补真实 combo 覆盖

当前 combo 的 `Ability / Hediff / Passive` 路径缺少真正业务样例。

本轮应补：

- combo Ability 样例
- combo Hediff 样例
- combo Passive 样例

并让烟测不再只停留在结构存在性。

### 3. 旧文档必须明确失效或被新文档取代

当前旧 payload 外传路线的设计与计划文档，不能再继续作为当前主线依据。

本轮应做到：

- 新文档明确给出当前主线裁定
- 旧文档要么标注过时，要么在新文档里被明确替代

---

## 八、不在本轮做的事

本轮明确不做：

- 重写整套芯片表达系统
- 发明新的全局表达运行时仓库
- 给 `FormalExpressionResult` 补一套多来源胖字段
- 为 combo 单开第二套 parser / 第二套下游通路
- 顺手改无关攻击执行业务

这次重构的目标是：

- 回到正确边界
- 让正式模型重新诚实
- 让下游重新只读正式面

不是借机做新的大工程。

---

## 九、验收标准

本轮完成后，应满足下面这些标准：

1. `FormalExpressionResult` 与 `BdpFormalVerbBindingState` 都不再携带 `RuntimePayload`
2. combo 构建不再依赖从正式结果反抠 payload
3. Ability / Hediff / targeting / formal host 继续正常工作
4. `CombatBodyEmergencyEscape` 能正确消费复合 passive 的多来源
5. 相关烟测、DevHarness 样例与文档全部和新边界一致
6. 不引入中间兼容垃圾来掩盖问题

如果重构后现有功能表现损坏，或者仍需要靠 payload 外传给下游“救火”，那就说明这次重构仍然没有做到位。
