# 表达系统参数包内部化与复合来源收口设计

> 本文已被 `2026-05-02-表达系统主线重构与正式边界收口设计-第一版.md` 与 `2026-05-02-表达系统主线重构与正式边界收口实施计划-第一版.md` 取代。当前主线以 2026-05-02 文档为准。

**Goal（目标）:** 把 `ExpressionRuntimePayload（表达系统内部参数包）` 收回表达系统内部，恢复 `FormalExpressionResult（正式表达结果）` 作为下游唯一正式结果；同时用现有正式复合引用结构收口 `combo（组合技）/ dual（双持复合）` 的来源追踪，不额外补胖结果结构。

**Architecture（架构）:** 本轮只改表达系统内部运算链与一个已确认越界的下游点 `CombatBodyEmergencyEscape（紧急脱离）`。参数包继续存在，但只允许留在 `ExpressionSourceMaterial（来源材料）` 这层内部材料对象中；`FormalExpressionResult`、`BdpFormalVerbBindingState（正式宿主绑定状态）` 等对外正式对象不再承载它。复合结果的来源追踪优先复用现有 `ExpressionSnapshot.CompositeReferences（复合来源引用表）`、`TriggerCombatProjectionState.ResultIndex（结果索引）`、`CompositeReferenceIndex（复合引用索引）`。

**Tech Stack（技术栈）:** RimWorld 1.6 Mod、C#、PowerShell 烟测、现有 BDP 表达系统主链

---

## 一、层级纠正

这次先把表达系统的层级说准。

当前应按下面 3 层看：

```text
来源侧：
Main / Sub / Special

复合层：
Single / DualWeapon / Combo

结果类别层：
Verb / Ability / Hediff / Passive
```

所以当前正式主链应理解为：

```text
chipA / chipB
  -> ExpressionSourceMaterial + RuntimePayload     // 内部材料层
  -> 单侧 FormalExpressionResult                   // 正式单侧结果
  -> 复合层
     - dual：只在两侧主结果都是 Verb 时成立，产物仍然只会是 Verb
     - combo：按 ComboDef 成立，产物可以是 Verb / Ability / Hediff / Passive
  -> ExpressionSnapshot
  -> 下游按正式结果类别消费
```

这也意味着：

- `dual / combo` 不是下游通道，它们是表达系统内部的复合生成层。
- `verb / ability / hediff / passive` 才是表达系统最终发布给下游的结果类别层。

## 二、当前问题

### 1. 内部参数包越过了边界

`ExpressionRuntimePayload` 当前被挂到了：

- `FormalExpressionResult`
- `BdpFormalVerbBindingState`

这让“内部材料”越过了表达系统正式输出边界。

后果不是“功能立刻错误”，而是职责变脏：

- 复合层开始从正式结果反抠内部材料。
- 宿主层开始携带本不该知道的表达系统内部对象。
- `dual` 是否有包、`combo` 是否带包，变成了错误的关注点。

### 2. `combo` 的内部取材路径不诚实

`ComboFormalExpressionResultFactory` 当前会从 `sourceResult.RuntimePayload.SourceChip` 回拿来源芯片快照。

这意味着：

- `combo` 的内部构建依赖“正式结果继续挂内部材料”。
- 一旦把参数包从正式结果上收回，`combo` 的这条路会断。

真正正确的关系应该是：

- `combo` 在表达系统内部直接从来源材料取内部参数。
- `combo` 不应要求单侧正式结果替自己背内部包。

### 3. `combo passive` 的来源追踪收口在了错误的位置

当前 `CombatBodyEmergencyEscape` 只认单个 `result.SourceReference`。

这对单芯片被动没问题，但对复合结果不够：

- 单侧结果来源在 `FormalExpressionResult.SourceReference`
- 复合结果来源在 `ExpressionSnapshot.CompositeReferences`

也就是说，复合来源信息其实已经有正式结构了，只是 `紧急脱离` 这条链还停在旧的单来源读法上。

---

## 三、重构裁定

### 1. 参数包只保留在表达系统内部

本轮明确裁定：

- `ExpressionRuntimePayload` 继续保留
- 但它只允许存在于 `ExpressionSourceMaterial`
- 不再挂到 `FormalExpressionResult`
- 不再挂到 `BdpFormalVerbBindingState`

这条裁定是本轮的核心边界。

### 2. `FormalExpressionResult` 继续做下游唯一正式结果

下游继续只读正式结果：

- `Trion`
- `PassiveKey`
- `AbilityDefName`
- `HediffDefName`
- `SourceReference`
- `CompositeKind`
- `ComboDefName`
- 其它已有正式字段

本轮不把下游改成“直接读参数包”。

也不额外给 `FormalExpressionResult` 补一套新的“大而全多来源结果字段”。

### 3. 复合来源追踪优先复用现有正式结构

本轮不新发明复合来源契约。

复合结果的来源一律优先用现有正式结构回查：

```text
复合结果 Id
  -> TriggerCombatProjectionState.CompositeReferenceIndex
  -> SourceResultIds
  -> TriggerCombatProjectionState.ResultIndex
  -> 单侧 FormalExpressionResult.SourceReference
```

现有正式结构已经足够：

- `ExpressionSnapshot.CompositeReferences`
- `TriggerCombatProjectionState.ResultIndex`
- `TriggerCombatProjectionState.CompositeReferenceIndex`

所以本轮不补新的正式“多来源字段”。

### 4. `dual` 不再以“漏传参数包”定义问题

在这次重构后，`dual` 没有 `RuntimePayload` 将不再是问题。

因为：

- `RuntimePayload` 本来就不应离开表达系统内部
- `dual` 真正要保证的是正式结果字段和复合来源引用完整
- 不是“给下游继续带一个内部包”

### 5. `Ability / Hediff / Ranged / Passive` 不改成读参数包

这几条下游链路继续读 `FormalExpressionResult` 正式字段。

因此本轮明确不做：

- 把 `Ability` 改成读内部参数包
- 把 `Hediff` 改成读内部参数包
- 把 `RangedPrepare` 改成读内部参数包
- 把 `Passive` 改成读内部参数包

按这次重审后的边界，这些都不应该发生。

## 四、最小实现形状

### 1. 表达系统内部只补一个“来源材料索引”

本轮不新增复杂上下文对象。

最小形状是：

```text
Dictionary<string, ExpressionSourceMaterial>
```

键使用单侧正式结果的稳定 `Id`。

用途只有一个：

- 在复合层内部，通过 `mainPrimary.Id / subPrimary.Id` 回查单侧来源材料

这让：

- `combo` 可以继续拿到来源芯片快照
- 但不再依赖 `FormalExpressionResult.RuntimePayload`

### 2. `combo` 只在内部用这个索引

`ComboFormalExpressionResultFactory` 只在内部构建时用来源材料索引：

- 读来源芯片快照
- 读来源参数包里的内部快照

构建完正式结果后，这些内部材料不再继续外传。

### 3. `紧急脱离` 只补自己真正需要的缓存结构

`CombatBodyEmergencyEscapeResolution` 当前只有一个：

```text
SourceReference
```

这不足以缓存复合来源。

本轮最小改法不是给 `FormalExpressionResult` 补字段，而是把 `Resolution` 自己改成：

```text
SourceReferences
```

原因很直接：

- 退出链开始后不能再回头重解析表达系统
- 但执行消费芯片时又必须已经拿到完整来源坐标

所以这条“多来源列表”只加在 `紧急脱离解析结果` 这个内部缓存对象上，属于最小必要，不属于对外正式契约膨胀。

### 4. 复合来源消费规则

当前唯一需要明确的复合来源消费点，是 `combo passive -> 紧急脱离`。

本轮裁定：

- 单来源结果：维持现状，只消费 1 枚来源芯片
- 复合来源结果：按已解析出的来源引用列表逐个消费

这不是“顺手加新玩法”，而是把复合来源语义补诚实。

在当前主模组内，这条语义只影响本来就缺失正确实现的复合被动链路；单芯片表现不变。

## 五、执行后结构

重构后应是下面这条关系：

```text
内部：
ExpressionSourceMaterial
  + RuntimePayload
    -> SingleSide build
    -> Composite build (dual / combo)
    -> 生成 FormalExpressionResult

对外：
FormalExpressionResult
  -> ExpressionSnapshot / CombatProjection
  -> Verb / Ability / Hediff / Passive / Host / CombatBody
```

而不再是：

```text
RuntimePayload
  -> FormalExpressionResult
  -> HostBindingState
  -> 下游继续顺手传
```

## 六、不做事项

本轮明确不做下面这些扩张：

- 不给 `FormalExpressionResult` 补新的多来源正式字段
- 不新增“统一复合来源 DTO（数据传输对象）”
- 不给 `IExpressionReader` 额外补新的大接口，只为携带内部材料
- 不改 `Ability / Hediff / Ranged / Passive` 的正式取值语义
- 不改 `Combo TrionResolve` 的正式求值规则
- 不顺手重写投影层、说明层、手动入口层

---

## 七、验收标准

### 1. 边界验收

- `FormalExpressionResult` 不再携带 `RuntimePayload`
- `BdpFormalVerbBindingState` 不再携带 `RuntimePayload`
- `combo` 构建不再从 `sourceResult.RuntimePayload` 反抠内部材料

### 2. 正式结果验收

- 单侧 `Verb / Ability / Hediff / Passive` 的正式字段不退化
- `dual` 仍只产出 `Verb`
- `combo` 仍可产出四类正式结果

### 3. 来源追踪验收

- 单侧结果仍使用 `SourceReference`
- 复合结果来源可通过 `CompositeReferenceIndex + ResultIndex` 追回
- `紧急脱离` 在复合被动下不再丢来源

### 4. 表现验收

- 单芯片现有游戏表现不变化
- `Ability / Hediff / Verb` 现有消耗与触发表现不变化
- 复合被动只修正当前缺失的来源消费语义，不引入计划外行为
