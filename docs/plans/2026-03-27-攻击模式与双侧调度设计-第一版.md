# 2026-03-27-攻击模式与双侧调度设计-第一版

## 1. 背景

当前新 BDP 已完成：

- 芯片定义正式化
- 表达系统正式化
- VerbHosting 与 AttackExecution 分层
- 默认主远程 / 默认主近战分离

但旧 BDP 中仍有一批实际存在的攻击策略逻辑尚未被新架构正式吸收：

- 远程逐发模式
- 远程齐射模式
- 近战连击机制
- 双侧攻击下不同模式组合的调度结果

本设计的目标不是复刻旧 BDP 的旧类结构，而是：

- 理解旧 BDP 的真实策略逻辑
- 在新 BDP 的分层原则下重新安放这些逻辑
- 明确哪些属于表达真相，哪些属于执行时序，哪些属于双侧调度

## 2. 旧 BDP 真实策略逻辑

### 2.1 单侧远程

旧 BDP 的单侧远程并不是两种武器类型，而是同一条远程攻击的两种执行节奏：

- `Sequential`
  - 由引擎 burst 逐发推进
  - 每次 `TryCastShot()` 只发一发
  - 发与发之间存在 `ticksBetweenBurstShots`
- `Simultaneous`
  - 一次 `TryCastShot()` 内循环发完整轮
  - 同一轮所有子弹瞬时打出
  - 可带齐射散布

因此旧 BDP 的“逐发 / 齐射”本质上是：

- 同一条表达结果的两种执行展开方式

不是：

- 两种不同表达类型

### 2.2 单侧近战

旧 BDP 的近战“连击”本质上是 burst 化的多段命中：

- `burstShotCount` 表示总击数
- `ticksBetweenBurstShots` 表示段间隔
- 每次 `TryCastShot()` 只打一击
- 后续击数由 burst 与自定义 JobDriver 继续推进

因此旧 BDP 的近战连击不是新的攻击类别，而是：

- 单条近战表达结果的一种时序展开

### 2.3 双侧远程

旧 BDP 的 `2远` 会进入双侧远程合成 Verb。

它支持三种实际调度结果：

- `逐发 + 逐发`
  - 左右交替逐发
- `齐射 + 齐射`
  - 左侧完整齐射 + 右侧完整齐射，在同一执行窗口内完成
- `逐发 + 齐射`
  - 混合调度
  - 逐发侧轮到时打一发
  - 齐射侧轮到时一次打完整轮

注意：

- 这里的“组合”不是表达系统额外发明出来的攻击类型
- 它本质上是双侧执行调度

### 2.4 双侧近战

旧 BDP 的 `2近` 会进入双侧近战合成 Verb。

但它不是左右交替连击，而是：

- 先执行左侧整段近战 burst
- 再执行右侧整段近战 burst

所以旧 BDP 双近战的真实策略不是“双侧交替”，而是：

- 左段后接右段

### 2.5 一远一近

旧 BDP 的 `1远 + 1近` 不会被合成为统一 Dual 攻击。

它的真实表现是：

- 远程入口走远程主攻击
- 近战入口走近战主攻击
- 两者并存
- 是否使用哪一个，由场景和引擎入口决定

因此：

- `1远 + 1近` 在旧 BDP 中不是“双侧组合攻击”
- 它只是双默认入口并存

## 3. 新 BDP 的架构原则

### 3.1 分层原则

在新 BDP 中必须维持以下分层：

- 表达系统负责声明“当前有哪些正式攻击结果”
- VerbHosting 负责把正式结果变成运行时可用 Verb
- AttackExecution 负责把一次攻击请求展开为真实执行时序

因此旧 BDP 中那些模式逻辑，不能再直接塞回：

- 特化 Verb 子类
- 运行时临时拼凑字段
- Patch 分流硬编码

### 3.2 真相与派生的边界

必须明确：

- 攻击身份属于表达真相
- 攻击节奏属于执行配置
- 双侧组合属于执行调度
- 场景默认主攻击属于运行时决策

不能混淆为一个字段或一个 Verb 类去同时承载。

## 4. 设计目标

本轮设计目标如下：

1. 保留新 BDP 的正式表达系统不变形。
2. 吸收旧 BDP 的逐发、齐射、连击和双侧调度能力。
3. 不把 `1远 + 1近` 强行合成为统一攻击结果。
4. 让执行策略可被表达系统正式声明，而不是执行层靠猜。
5. 为未来新增攻击模式预留稳定扩展位。

## 5. 正式方案

### 5.1 总体方案

采用方案 2：

- 表达系统输出稳定攻击结果
- 额外挂出正式执行配置
- AttackPlanner / AttackExecution 负责把配置展开成真实时序

不采用：

- 靠大量专门 Verb 子类承载模式差异
- 仅靠 `burstShotCount` 反推齐射/逐发/连击

### 5.2 新增正式概念：Attack Execution Style

建议在正式表达结果侧新增一个正式执行配置块，暂命名为：

- `AttackExecutionStyle`

它不描述“这是谁”，只描述“这次怎么打”。

### 5.3 执行配置的三层结构

#### A. 单条攻击的执行节奏

单条结果需要声明自己的基础展开方式。

远程：

- `RangedExecutionRhythm.Sequential`
- `RangedExecutionRhythm.Simultaneous`

近战：

- `MeleeExecutionRhythm.SingleHit`
- `MeleeExecutionRhythm.MultiHit`

同时需要最小配套参数：

- `shotCount`
- `shotIntervalTicks`
- `hitCount`
- `hitIntervalTicks`
- 远程可选 `volleySpreadRadius`

这里的含义是：

- 表达系统说明“它是一条远程/近战攻击”
- 执行配置说明“它一次施放内部怎么展开”

#### B. 双侧执行调度

当结果属于 `DualWeapon` 复合结果时，需要声明双侧如何调度。

建议引入：

- `DualExecutionSchedule`

第一版正式支持：

- `None`
- `Alternating`
- `Simultaneous`
- `MainThenSub`
- `MixedRhythm`

其含义：

- `Alternating`
  - 双侧逐发交替
- `Simultaneous`
  - 双侧整轮同时完成
- `MainThenSub`
  - 主侧完整执行后，再执行副侧
- `MixedRhythm`
  - 一侧逐发、一侧齐射的混合调度

#### C. 场景默认主攻击决策

场景默认主攻击不再是固定字段。

它应由运行时根据：

- `PrimaryRanged`
- `PrimaryMelee`
- 当前是否贴身
- 当前是否能用远程
- 当前是否能用近战

在决策层得出。

因此本设计不再引入新的固定 `PrimarySurface` 替代物。

### 5.4 本版命名与落地约束

为避免旧命名把执行层概念重新搅乱，本版正式约束如下：

- 近战一律使用 `hitCount` / `hitIntervalTicks`
- 远程一律使用 `shotCount` / `shotIntervalTicks`
- 双侧调度正式命名为 `DualExecutionSchedule`
- 不再把 `combo` 当作执行节奏术语
- `1远 + 1近` 只保留 `PrimaryRanged` 与 `PrimaryMelee` 并列，不生成统一双侧执行结果

## 6. 旧策略到新模型的正式映射

### 6.1 单侧映射

#### 单侧远程逐发

映射为：

- `WeaponMode = Ranged`
- `RangedExecutionRhythm = Sequential`
- `shotCount = burstShotCount`
- `shotIntervalTicks = ticksBetweenBurstShots`

#### 单侧远程齐射

映射为：

- `WeaponMode = Ranged`
- `RangedExecutionRhythm = Simultaneous`
- `shotCount = 实际齐射发数`
- `shotIntervalTicks = 0`
- 可附带 `volleySpreadRadius`

#### 单侧近战单击

映射为：

- `WeaponMode = Melee`
- `MeleeExecutionRhythm = SingleHit`
- `hitCount = 1`

#### 单侧近战连击

映射为：

- `WeaponMode = Melee`
- `MeleeExecutionRhythm = MultiHit`
- `hitCount = burstShotCount`
- `hitIntervalTicks = ticksBetweenBurstShots`

### 6.2 双侧远程映射

#### `逐发 + 逐发`

映射为：

- `CompositeKind = DualWeapon`
- `DualExecutionSchedule = Alternating`

#### `齐射 + 齐射`

映射为：

- `CompositeKind = DualWeapon`
- `DualExecutionSchedule = Simultaneous`

#### `逐发 + 齐射`

映射为：

- `CompositeKind = DualWeapon`
- `DualExecutionSchedule = MixedRhythm`

### 6.3 双侧近战映射

旧 BDP 的 `2近` 不是交替，而是左段再右段。

因此映射为：

- `CompositeKind = DualWeapon`
- `DualExecutionSchedule = MainThenSub`

### 6.4 一远一近映射

`1远 + 1近` 不应生成双侧复合攻击结果。

它应保持为：

- 一条正式远程结果
- 一条正式近战结果

并通过场景决策层在运行时做选择：

- 贴身优先近战
- 非贴身优先远程

这既符合旧 BDP 实际表现，也符合新 BDP 分层。

## 7. 新 BDP 中各层该承担的责任

### 7.1 Expression

负责：

- 声明正式攻击结果
- 声明结果的执行配置
- 声明是否属于双侧复合结果

不负责：

- 推进 burst
- 决定本 tick 先打左还是右
- 临时拼装齐射或连击循环

### 7.2 VerbHosting

负责：

- 创建运行时 Verb
- 绑定 `VerbProps`
- 绑定 `Tool`
- 绑定 `Maneuver`
- 绑定 `loadID`

不负责：

- 解释逐发/齐射/连击调度
- 决定双侧顺序

### 7.3 AttackPlanner / AttackExecution

负责：

- 读取 `AttackExecutionStyle`
- 把配置展开成真实执行计划
- 处理逐发、齐射、连击、多段和双侧调度
- 按场景选择默认主攻击

这是这些模式最合适的归宿层。

## 8. 第一版推荐的数据形状

以下为推荐方向，不是本轮必须立即一口气全落的最终类名：

```csharp
AttackExecutionStyle
{
    SingleAttackExecutionStyle Single;
    DualAttackExecutionStyle Dual;
}

SingleAttackExecutionStyle
{
    RangedExecutionRhythm? RangedRhythm;
    MeleeExecutionRhythm? MeleeRhythm;
    int shotCount;
    int shotIntervalTicks;
    int hitCount;
    int hitIntervalTicks;
    float volleySpreadRadius;
}

DualAttackExecutionStyle
{
    DualExecutionSchedule Schedule;
}
```

本设计推荐这种拆分，因为：

- 单条节奏和双侧调度语义不同
- 后续扩展更稳

## 9. 不做的事

本轮明确不做：

- 不把旧 BDP 的 `Verb_BDPSingle / Verb_BDPDual / Verb_BDPMelee` 类结构原样搬回
- 不把模式逻辑继续塞进 `VerbProps` 模糊字段里
- 不把 `1远 + 1近` 硬合成为一个 Dual 攻击结果
- 不恢复固定“默认主攻击”字段

## 10. 风险与约束

### 10.1 风险

如果继续只靠现有 `VerbProps` 猜执行方式，会立刻出现以下歧义：

- 同样 `burstShotCount = 4`
  - 可能是逐发 4 发
  - 也可能是齐射 4 发
  - 也可能是近战 4 连击

所以执行模式必须显式声明。

### 10.2 约束

双侧复合结果只应在“确实存在双侧同类联合执行语义”时生成。

因此：

- `2远` 可以生成 `DualWeapon`
- `2近` 可以生成 `DualWeapon`
- `1远 + 1近` 不应生成 `DualWeapon`

## 11. 最终结论

旧 BDP 的“逐发 / 齐射 / 连击 / 双侧组合”真正表达的，不是新的攻击种类，而是：

- 单条攻击的执行节奏
- 双侧攻击的执行调度

在新 BDP 中，最合适的落点不是 Verb 类层，而是：

- 表达系统正式声明执行配置
- AttackExecution 读取配置并展开时序

正式映射结论如下：

- 单侧远程逐发 -> `RangedExecutionRhythm.Sequential`
- 单侧远程齐射 -> `RangedExecutionRhythm.Simultaneous`
- 单侧近战连击 -> `MeleeExecutionRhythm.MultiHit`
- 双远逐发+逐发 -> `DualExecutionSchedule.Alternating`
- 双远齐射+齐射 -> `DualExecutionSchedule.Simultaneous`
- 双远逐发+齐射 -> `DualExecutionSchedule.MixedRhythm`
- 双近 -> `DualExecutionSchedule.MainThenSub`
- 一远一近 -> 不合成，只保留 `PrimaryRanged + PrimaryMelee` 并由场景决策层选择

这条方案同时满足：

- 理解旧 BDP 的真实策略逻辑
- 保持新 BDP 的架构边界
- 避免再次退回旧式专门 Verb 硬编码体系

## 12. 2026-03-28 落地裁定

为避免把“子弹数”误当成“开枪次数”，正式执行模型在落地时进一步明确为：

- `Plan -> Group -> Cast -> Emit`
- `Cast` 表示一次真实施放动作
- `Emit` 表示该次施放动作内部的单个效果实例

对应关系为：

- 单射：`1 Cast -> 1 Emit`
- 齐射：`1 Cast -> N Emit`
- 连击：`N Cast -> N Emit`
- 双持同步：`1 Group -> 多 Cast`

因此齐射不再表达为“一个 group 内多个 step”，而是：

- 一个 group 内一个 cast
- 该 cast 内多个 emit

这条裁定保证：

- 上层执行器只推进 cast，不再把 emit 数量误算成施放次数
- `Verb` 只负责一次 cast
- `Projectile / Damage` 只负责单个 emit 的实际落地
