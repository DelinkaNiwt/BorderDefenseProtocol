# BDP 殖民者战斗自动化设计

## 1. 目标

为玩家可控制的自由非奴隶殖民者提供四项彼此独立、默认关闭的可选自动化规则：

1. 从未征召切换为已征召时，若条件满足则尝试激活战斗体。
2. 从已征召切换为未征召时，若战斗体仍为激活状态则请求主动解除；不得触发崩解。
3. 战斗体完整激活事务完成后，若条件满足则尝试激活主手1号槽芯片。
4. 战斗体完整激活事务完成后，若条件满足则尝试激活副手1号槽芯片。

四项规则分别保存到每个殖民者，玩家可通过当前 Trion（资源）复合 Gizmo（游戏指令面板）的两个区域右键菜单修改。模组设置页另提供全局强制、加入殖民地时的默认值和一次性批量覆盖。

本功能只决定未来事件发生时是否提交一次正式请求。修改设置不得立即改变当前征召、战斗体或芯片状态。

## 2. 已确认行为

- 四项个人配置初始值全部关闭。
- 主手1号槽与副手1号槽分别配置，不使用一个总开关。
- 自动操作只响应下一次对应状态变化，不追溯当前状态。
- 每次事件只尝试一次；条件后来恢复时不轮询、不重试。
- 条件不满足、槽位不存在、槽位为空或正式请求不可用时静默跳过。
- 取消征召时，只要战斗体当前仍为 Active（激活）阶段就请求主动解除，不追踪战斗体最初由手动还是自动激活。
- 自动芯片激活顺序固定为 Main（主手）后 Sub（副手）；不新增互斥裁决。若两侧芯片互斥，由现有 Trigger（触发器）切换规则处理，后提交的副手请求按现有规则成为后请求。
- 全局强制只改变实际生效值，不改写小人的个人保存值。
- 一次性批量覆盖只改写当前处于“服从个人”策略的项目。
- 旧存档字段和旧配置键不兼容；本事项不建立迁移层。

## 3. 玩家范围

### 3.1 持久配置与批量覆盖范围

目标小人必须同时满足：

- 人形 Pawn（小人）。
- 玩家阵营。
- 自由殖民者。
- 非奴隶。
- 非任务借住者。
- 当前存活。

批量覆盖使用原版 `PawnsFinder.AllMapsCaravansAndTravellingTransporters_Alive_FreeColonists_NoLodgers`（所有地图、商队和运输中的存活自由非借住殖民者）作为候选集合，再显式排除奴隶与非人形小人。这样包含商队和旅行运输中的玩家殖民者，不会误扫全部世界小人，也不得只扫描当前地图。

不得修改：

- 奴隶。
- 囚犯。
- 任务借住者。
- 友军与敌对小人。
- 殖民地机甲。
- 亚人形或不可征召生物。

### 3.2 运行触发范围

征召自动化只处理原版当前允许玩家控制且拥有 `Pawn_DraftController`（征召控制器）的小人。战斗体激活完成后的芯片自动化还要再次确认小人仍符合玩家自由殖民者范围，避免阵营或身份在事务期间变化。

## 4. 玩家界面

### 4.1 Trion 能量条右键菜单

在 Trion 复合 Gizmo 左侧能量条区域右键，仅显示当前小人的战斗体自动化：

```text
✓ 征召时自动激活战斗体
○ 取消征召时自动解除战斗体
```

### 4.2 芯片控制面板右键菜单

在同一复合 Gizmo 右侧芯片控制面板区域右键，仅显示当前小人的芯片自动化：

```text
✓ 战斗体激活后自动激活主手1号槽
○ 战斗体激活后自动激活副手1号槽
```

没有右侧芯片控制面板时，不存在芯片区域右键入口。是否显示芯片面板继续由现有 `TriggerLoadoutPanelExtension`（触发器芯片面板许可扩展）决定。

菜单配置属于小人，不属于当前触发器或芯片。当前槽位为空、缺少1号槽或更换装备时仍可保留配置；下一次完整激活事件再按当时装备状态判断。

### 4.3 全局强制时的菜单表现

个人菜单仍显示该项，但不可修改，并明确说明实际状态来自全局设置：

```text
✓ 征召时自动激活战斗体（由全局设置强制开启）
○ 副手1号槽自动激活（由全局设置强制关闭）
```

恢复“服从个人”后，原个人保存值重新生效。

### 4.4 多选行为

右键菜单只修改被点击 Trion 卡片所属的小人，不扩散到同时选中的其他小人。统一修改必须通过模组设置页的批量覆盖入口完成。

## 5. 全局模组设置

### 5.1 四项独立策略

每项规则拥有一个三态全局策略：

- `Individual`（服从个人）。
- `ForceEnabled`（全员开启）。
- `ForceDisabled`（全员关闭）。

实际值统一由一个解析器计算：

```text
全员开启 → true
全员关闭 → false
服从个人 → 小人个人保存值
```

任何业务入口不得自行复制这段优先级判断。

### 5.2 “服从个人”展开项

某项选择“服从个人”时，设置页展开该项的“新殖民者默认值”。默认值初始为关闭。

被强制开启或关闭的项目隐藏默认值编辑，但已保存的默认值不得丢失；恢复“服从个人”后继续显示原值。

### 5.3 一次性批量覆盖

只要至少一项处于“服从个人”，游戏进行中显示：

```text
[按当前默认值覆盖所有现有自由殖民者]
```

执行前弹出原版确认窗口，列明：

- 受影响的存活殖民者数量。
- 将被覆盖的项目。
- 每项写入的开关值。
- 强制项目不会改写其个人保存值。

确认后只改写个人配置，不立即征召、激活、解除或切换芯片。主菜单没有活动游戏时禁用该按钮；全局策略和新殖民者默认值仍可正常编辑。

### 5.4 设置归属

全局策略和新殖民者默认值属于 `ModSettings`（模组设置），跨存档生效。个人配置属于 Pawn Comp（小人组件），随游戏存档保存。

`BDP.Core.dll`（核心程序集）现有 `BDPMod` 继续只负责核心 Harmony（方法补丁）初始化。`BDP.Content.dll`（内容程序集）新增自己的 `Mod`（模组入口）子类，独立持有内容侧设置并绘制唯一非空的 BDP 设置分类，避免 Core（核心）引用具体自动化字段。

## 6. 数据归属

### 6.1 Content 侧个人配置组件

新增 Content（内容）侧 `CompCombatAutomationPreferences`（战斗自动化偏好组件），注入所有人形 Pawn Def（小人定义），与现有 Content 侧天赋和紧急脱离组件采用同一注入模式。

组件保存：

```text
initialized
autoActivateCombatBodyOnDraft
autoReleaseCombatBodyOnUndraft
autoActivateMainSlotOneAfterCombatBody
autoActivateSubSlotOneAfterCombatBody
```

`initialized` 只表示个人值是否已经建立。首次成为符合范围的玩家自由殖民者时，从当时的四项“新殖民者默认值”复制一次；以后默认值变化不追改该小人。

初始化入口采用最小组合：

- 已是玩家自由殖民者时，在 `PostSpawnSetup`（生成后初始化）建立个人值。
- 后来招募的小人，在第一次读取或写入自动化配置时惰性初始化。
- 批量覆盖会先确保目标小人完成初始化，再写入处于“服从个人”的项目。

### 6.2 Content 侧全局设置

新增 `CombatAutomationModSettings`（战斗自动化模组设置），保存四个三态策略和四个新殖民者默认值。所有字段逐项序列化，默认值均为“服从个人 + 关闭”。

### 6.3 不新增真值的位置

不得把个人配置写入：

- `CompCombatBodyHost`（战斗体核心宿主）。
- `CompTriggerBody`（触发器核心宿主）。
- Trion 资源组件。
- 当前装备或芯片 Thing（物品）。
- 静态字典或按 ThingID（物品编号）保存的全局表。

## 7. 程序集与扩展边界

### 7.1 Core：分区右键菜单扩展

Core（核心）新增中性区域枚举：

```text
BaseCard（基础能量条区）
Panel（右侧扩展面板区）
```

新增中性提供器接口，输入现有 `TrionGizmoExtensionContext`（Trion 面板扩展上下文）和区域，返回原版 `FloatMenuOption`（悬浮菜单选项）集合。

现有 `TrionGizmoExtensionRegistry`（Trion 面板扩展注册表）增加注册、反注册和枚举菜单提供器的能力。Core 不认识战斗体自动化、芯片自动化或具体菜单文字。

`Gizmo_TrionStatus`（Trion 状态卡）负责：

1. 使用实际绘制出的 `baseRect`（基础矩形）和 `panelRect`（面板矩形）判断右键区域。
2. 在右键按下当帧收集菜单选项并保存为列表，避免原版重复读取属性时重复执行构建逻辑。
3. 只有列表非空时返回 `GizmoState.OpenedFloatMenu`（打开悬浮菜单状态）。
4. 继续保持现有左键槽位交互，不改变布局、宽度和绘制顺序。

### 7.2 Core：战斗体完整激活事件

现有 `PhaseChanged`（阶段变化事件）在 `CombatBodyActivationTransaction`（战斗体激活事务）尚未完成时广播，不能作为自动芯片入口。

在 `ICombatBodyEvents`（战斗体事件面）增加中性的 `ActivationCompleted`（激活完成）事件。`CombatBodySessionService.TryActivate`（战斗体会话激活请求）仅在完整激活事务返回成功后广播一次：

```text
完成宿主变换与 Active 阶段切换
→ 解除 Trigger 战斗体不可用状态
→ 自动处理既有 Special（特殊）槽
→ 绑定 Trion 持续消耗与伤口运行时
→ 冻结恢复并发布投影
→ 广播 ActivationCompleted
```

激活失败、重复激活请求、读档恢复和阶段查询不得广播该事件。

原始 `CombatBodyService`（战斗体阶段服务）只知道阶段切换，不知道完整事务是否结束，因此停止直接实现 `ICombatBodyEvents`；它继续保留内部阶段事件，由 `CombatBodySessionService` 对外转发。完整激活事件只由会话服务持有和广播，禁止在原始阶段服务中伪造。

### 7.3 Content：具体菜单与自动化

Content（内容）注册一个菜单提供器：

- `BaseCard` 返回两项战斗体自动化。
- `Panel` 返回主、副手1号槽两项芯片自动化。

Content 个人配置组件订阅自身 Pawn（小人）的 `ActivationCompleted` 事件。生成或重新生成时建立一次订阅，离图时解除订阅，避免重复处理。

### 7.4 依赖方向

```text
BDP.Content.dll → BDP.Core.dll
BDP.Core.dll    → 不依赖任何本模组其它程序集
```

Core 源码和 Core Def（定义）不得出现 `BDP.Content` 命名空间或自动化业务类型。

## 8. 原版征召接入

RimWorld 1.6（边缘世界1.6）的 `Pawn_DraftController.Drafted`（征召状态属性）没有公开变化事件，所有正常征召和取消征召最终都会经过其 setter（属性写入口）。因此采用一个最小 Harmony 后置补丁。

补丁只负责：

1. 前置记录原征召值。
2. 原版 setter 完整执行后比较新旧值。
3. 真正发生变化时，把 Pawn、旧值和新值交给 Content 自动化控制器。

补丁不得读取四项设置、判断战斗体条件或直接改战斗体状态。

原版 setter 执行在前，确保清理工作、工作中断、编队通知和原版自动取消征召逻辑全部保持原顺序。

## 9. 运行时序

### 9.1 征召时自动激活战斗体

```text
原版 Drafted: false → true
        ↓
薄补丁转发变化
        ↓
确认当前为玩家可控制自由殖民者
        ↓
解析“征召时自动激活战斗体”的实际生效值
        ↓
关闭：结束
开启：通过 CombatBody 正式 reader（读取口）确认当前未激活
        ↓
调用 ICombatBodyCommands.TryActivate
        ↓
正式事务自行检查阶段、Trigger、Trion 容量等条件
        ↓
成功或失败后结束；失败静默且不重试
```

不得在补丁或 Content 控制器中复制战斗体完整激活条件。

### 9.2 取消征召时主动解除战斗体

```text
原版 Drafted: true → false
        ↓
薄补丁转发变化
        ↓
解析“取消征召时自动解除战斗体”的实际生效值
        ↓
关闭：结束
开启：当前阶段不是 Active → 结束
        ↓
调用 ICombatBodyCommands.RequestRelease
```

必须调用主动解除命令，不得调用 `TriggerCollapse`（触发崩解）。崩解收尾中原版取消征召会再次经过 setter；此时阶段为 Collapsing（崩解中）且退出事务已有重入保护，自动化必须静默跳过。

### 9.3 战斗体完成后自动激活芯片

```text
完整激活事务成功
        ↓
ActivationCompleted
        ↓
依次处理 Main[0]、Sub[0]
        ↓
为当前侧重新读取 ITriggerSlotInteractionState（槽位交互状态）
        ↓
只在 Availability=Available 且动作为 Activate/SwitchTo 时提交
        ↓
调用 ITriggerLoadoutCommands.RequestActivate(side, 0)
        ↓
现有 Trigger 规则负责条件、延迟、绑定和互斥
```

底层索引固定为0，玩家文字固定显示“1号槽”。处理副手前必须重新读取交互状态，不能复用主手请求前的旧快照。

已激活、空槽、禁用、镜像、条件不满足、正在切换或命令口缺失均静默跳过。不得为失败建立待处理标记。

## 10. 错误处理与日志

以下属于正常业务结果，不显示消息、不写常规日志：

- 战斗体条件不满足。
- 芯片槽不存在或为空。
- 芯片激活条件不满足。
- 芯片被禁用、镜像控制或正在切换。
- 自动操作对应设置关闭。
- 全局设置使个人菜单只读。

只有以下非预期问题才允许写一次性或节流诊断日志：

- 已注入组件却无法解析自身 Pawn。
- 已成功订阅的事件调用中出现异常。
- 批量覆盖枚举到损坏或不可读组件。

诊断前缀统一为 `[BDP.Content.CombatAutomation]`，不得加入常驻逐 Tick 日志。若游戏内实测出现时序问题，再增加强可删除的临时诊断，不预埋大量日志。

## 11. 存读档

- 四项个人值和 `initialized` 由 Pawn Comp 逐字段保存。
- 四项全局策略和四项新殖民者默认值由 `ModSettings` 逐字段保存。
- 事件订阅、菜单选项和实际生效值均为可重建运行时状态，不序列化。
- 读档时不得因为战斗体已经为 Active 而补发 `ActivationCompleted`。
- 读档时不得根据当前已征召状态补做自动激活。
- 全局强制跨存档即时生效，但仍只影响下一次事件。

## 12. 不做范围

- 不改变战斗体、Trigger 或 Trion 真值结构。
- 不改变现有 Special（特殊）槽自动激活行为。
- 不改变芯片激活、关闭、互斥、延迟或条件规则。
- 不增加轮询、定时重试或待激活队列。
- 不因设置变化立即执行战斗动作。
- 不提供第三个独立个人设置面板。
- 不把芯片自动化扩展到2号及以后槽位。
- 不处理殖民地机甲、奴隶、囚犯、友军或敌人。
- 不修改旧版模组。
- 不修改 DevHarness（开发测试模组）业务；测试模组只在需要时作为游戏内验证载体使用现有内容。

## 13. 验证设计

### 13.1 Core 边界检查

- 分区菜单枚举、接口和注册表属于 Core 中性命名。
- `Gizmo_TrionStatus` 只按区域汇总原版悬浮菜单选项，不含自动化文字或 Content 类型。
- 右键基础区和面板区返回不同区域；无选项时不打开空菜单。
- 左键芯片槽交互路径保持不变。
- `ActivationCompleted` 只在完整激活事务成功后广播一次。
- Core 零本模组程序集依赖门禁继续通过。

### 13.2 Content 行为检查

- 个人组件只在 Content，注入范围为人形 Pawn。
- 四项个人值、四项策略和四项默认值均有独立存档键。
- 全局解析器是实际值的唯一入口。
- 征召补丁只捕获变化并转发，不承载业务判断。
- 自动战斗体只调用正式 CombatBody 命令口。
- 自动芯片先读取正式交互状态，再调用正式 Trigger 命令口。
- Main[0] 和 Sub[0] 独立配置、固定顺序且各只尝试一次。
- 预期失败不显示消息、不创建重试状态。

### 13.3 设置界面检查

- 四项策略可分别选择服从个人、全员开启、全员关闭。
- 只有服从个人时展开新殖民者默认值。
- 强制期间个人菜单只读，个人保存值不被覆盖。
- 批量按钮只在游戏中可用，并先显示确认窗口。
- 批量覆盖使用原版地图、商队和旅行运输候选集合，并排除奴隶与约定范围。
- 批量覆盖不立即触发任何战斗行为。

### 13.4 游戏内实测

1. 四项默认关闭时，征召、取消征召和手动激活行为与当前版本一致。
2. 仅开启征召自动激活：条件满足时激活；Trion 不足、无 Trigger 或冷却时静默跳过且不重试。
3. 仅开启取消征召自动解除：手动或自动激活的战斗体都主动解除；不得进入崩解。
4. 崩解收尾自动取消征召时，不产生第二次退出或异常消息。
5. 手动激活战斗体也会触发主、副手1号槽自动化。
6. 主手开启、副手关闭，以及主手关闭、副手开启，分别只操作对应侧。
7. 空槽、禁用、镜像、条件不足和正在切换时静默跳过。
8. 两侧均开启时按 Main[0] 后 Sub[0] 提交；互斥结果与现有 Trigger 后请求规则一致。
9. 能量条与芯片面板右键菜单严格分区，左键芯片操作不回归。
10. 全局强制生效但不改个人值；恢复服从个人后原值回归。
11. 新招募殖民者取得当前默认值；后续修改默认不追改。
12. 批量覆盖包含商队殖民者，排除奴隶、囚犯、借住者、友军和敌人。
13. 保存并读档后个人值正确恢复，且不会补触发自动动作。
