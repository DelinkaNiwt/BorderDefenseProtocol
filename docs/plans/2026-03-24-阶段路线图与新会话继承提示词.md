## 六、当前已经确认的长期原则

### 1. 根本任务与根本目标

- 基于旧 BDP 做二次重构
- 只重构内部原理
- 不沿用一次重构的总体架构
- 目标是 100% 重现旧 BDP 的外在本质表现
- 用户裁决高于文档，高于旧代码里不明确的地方

### 2. 宿主优先原则

- 必须从 RimWorld 出发，最后回到 RimWorld
- 优先使用原版 `Verb / Ability / Hediff / Projectile / Gizmo / ThingComp / JobDriver`
- 只有原版没有自然通道时才考虑 patch

### 3. 真值 owner 不能混

- `CompTrion` 只持有资源真值
- `CombatBodyState` 只持有战斗体阶段真值
- `CompTriggerBody` 只持有装载与局部激活真值
- 事件只通知，不持有真值

### 4. 多表达原则

- 芯片先产出表达来源，不等于直接产出固定武器
- 表达共存数量、按钮数量、可直接操作行为模式数量、主兼容表面，都不是一回事
- 组合技本质是左右满足条件后额外生成第三表达
- 攻击型组合技只是组合技的一种

### 5. 命名原则

- 内部稳定命名统一使用 `Main/Sub`
- 约定：`Main = 右`、`Sub = 左`
- 只有和原版身体部位直接对接时才使用 `Left/Right`

### 6. 文档与注释原则

- 中文优先
- 正文呈现结果，不写“原来怎样后来怎样”的过程口吻
- 过程痕迹留在日志和历史记录
- 代码与 XML 默认广覆盖注释，普通玩家和初级模组开发者应尽量能看懂

### 7. 实现前回查原则

- 每次要做一个功能前，先回到需求文档确认方向
- 再回到旧 BDP 代码确认细节
- 不能只凭压缩后的记忆继续写

## 七、已经踩过的坑与当前解决结论

### 1. 把“事件通信”误做成“依赖时间流动才成立”

踩坑表现：

- 玩家暂停时按钮或逻辑不立即成立
- 必须等时间流动才出结果

当前结论：

- 逻辑成立不能依赖 tick 推进
- tick 只允许用于资源自然过程、冷却倒计时、表现计时等时间过程
- 状态查询入口必须主动收掉已结束的冷却或表现期，不能等下一 tick

### 2. 把“第一阶段最小主链”误当成“整体需求基本完成”

踩坑表现：

- 类和接口一多，就容易误判已经做完了大半

当前结论：

- 新 BDP 当前只接通了最小主链
- 很多系统只是骨架，不是完整业务

### 3. 过度依赖 patch

踩坑表现：

- 容易把 patch 当主要实现手段

当前结论：

- patch 只能是最后手段
- 即使要 patch，也只能接线，不承载复杂业务

### 4. apply_patch 失败与中文编码问题

踩坑表现：

- 改文件时 `apply_patch` 偶发失败
- 终端直接读中文有时乱码

当前结论：

- 编辑文件必须优先用 `apply_patch`
- 读取中文文件时显式使用 `-Encoding utf8`
- 先读后改，避免 patch 上下文错位
- 一次 patch 不要太贪，必要时分小块改

### 5. 诊断日志过早调用导致空引用

踩坑表现：

- 模组初始化早期调用日志工具导致 `NullReferenceException`

当前结论：

- 不在过早阶段读取 `Prefs` 或其它未稳定对象
- 诊断工具必须容忍游戏早期初始化阶段

### 6. 测试内容和主模组物理耦合

踩坑表现：

- 测试按钮或测试内容混入主模组

当前结论：

- 测试应通过正式扩展口进入
- 删除测试模组后，主模组不应残留任何测试内容
- 不靠 Harmony 偷改主模组核心按钮链路
