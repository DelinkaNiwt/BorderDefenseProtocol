# BDP 架构二审与高风险修复设计（第一版）

**目标：** 基于第一性原理、旧 BDP 已知痛点、当前新 BDP 主模组真实代码现状，对上一轮架构审查结果做二次复核，重新评估哪些属于真实风险、哪些属于合理正式预留，并给出严重 / 高风险问题的正式修复设计与目标架构。

**范围：** 仅审查主模组 `Source/BDP` 当前真实代码；不把 DevHarness 测试层缺陷直接当作主模组架构结论，但会审查主模组是否为测试层保留了不合理依赖。

**前提裁定：**

- `外部按钮 / 外部扩展入口` 是正式长期需求，不因目前先由测试模组消费就被视为测试污染
- 但任何正式扩展口都必须面向“未来普通扩展模组作者”设计，不能在设计上围着测试模组场景长出来
- `CompTriggerBody / CompTrion / CombatBodyState` 三类真值 owner 仍必须严格分离
- 事件只通知，不持有真值
- patch 只接线，不承载复杂业务

---

## 一、二审后的总判断

二审后的结论是：

1. 上一轮指出的 `CompTriggerBody` 膨胀问题仍然成立，而且仍是当前头号风险
2. `CombatBody` 链路存在“骨架已存在，但主链未真正接通”的严重结构风险，这不是简单的“以后再做”
3. 表达 / 投影链已经出现“接口很多、具体耦合仍很强”的假解耦问题
4. `TriggerExternalGizmoRegistry` 不再被判定为“测试污染”，因为其存在已被用户裁定为正式需求
5. 但它目前仍然停留在“形式上开放扩展、实际上只有测试层在用”的早期状态，必须继续规范化，不可无限制扩生

---

## 二、二审后的分级调整

## 1. 严重风险

### S1. `CompTriggerBody` 再次向 Trigger 上帝模块方向膨胀

核心事实：

- 文件体量 `1455` 行，远高于当前其它核心对象
- 同时持有：
  - 槽位真值
  - 容器真值
  - 局部激活 / 关闭
  - 切换状态机
  - 双手绑定同步
  - 互斥检查
  - 身体禁用同步
  - 表达缓存桥
  - 外部按钮接线
  - 完整性诊断
  - `IThingHolder` 宿主职责
- 最近刚暴露出的“激活后闪退”问题，根因正是这个类内部的阶段推进与公开读取链重入耦合

为什么是严重风险：

- 这已经不是“有点大”，而是再次复现旧 BDP 的主要失败模式
- 只要继续沿当前方向加功能，后续任何新规则都会自然落入这个类
- 一旦继续膨胀，后续所有重构成本都会成倍上升

## 2. 高风险

### H1. `CombatBody` 存在双轨职责与主链未接通问题

核心事实：

- `CombatBodyCoordinator` 已承担激活 / 退出 / 崩解的流程协调
- `CombatBodyCleanupCoordinator` 又定义了一套收尾链，但当前主模组里没有正式接线
- `PawnCombatBodyHost` 仍是空桥位
- `CombatBodyState / CombatBodyCoordinator / CleanupCoordinator` 当前还没有形成已验证的正式闭环

为什么是高风险：

- 这会让“谁负责正式收尾”继续悬空
- 继续往后推进时，很容易再出现第二条、第三条收尾链
- 旧 BDP 后期一个典型痛点，就是收尾与恢复逻辑逐渐多点分叉、难以回溯

### H2. 表达 / 投影链存在假解耦与过度分层

核心事实：

- `TriggerProjectionFacade` 仍直接接具体 `CompTriggerBody`
- 两个自动攻击 patch 也直接依赖 `CompTriggerBody`
- `BdpProjectionRuntime` 内部仍直接 `new` 具体 collector / resolver / registry / projection
- 同时还定义了多组接口与 projection 层

为什么是高风险：

- 当前不是“真的可替换”，而是“看起来很多层”
- 复杂度已经上升，但依赖方向并未真正瘦下来
- 若继续沿这条路走，会出现旧 BDP 那种“概念越来越多，真正主链越来越难看清”的问题

### H3. 正式扩展口虽然合理存在，但其宿主位置和边界仍需规范化

核心事实：

- `TriggerExternalGizmoRegistry / Context / Provider` 已被正式裁定为长期需求
- 当前唯一消费者仍是测试模组
- 调用入口仍挂在 `CompTriggerBody.CompGetEquippedGizmosExtra()`

二审后的判断：

- 这不再被视为测试污染
- 但它仍是高风险设计点，因为目前它的存在形式仍紧贴 `CompTriggerBody`
- 若后续继续把各种“外部命令、外部观察、外部扩展”都顺手挂在 Trigger owner 上，仍会加速 owner 膨胀

---

## 三、不是高风险，但需要记录的中风险

### M1. 预留型抽象偏多，且部分没有真实实现或真实替换价值

典型对象：

- `IVisualProjection`
- `ISemanticDamageSource`
- `ICollapseCleanupCoordinator`
- 多组 `IAuto* / IManual* / ISurface*`

当前判断：

- 不是立刻必须删除所有接口
- 但后续应做一次清仓：没有真实调用、没有真实替换点、没有近期接线计划的，不继续留在主模组占认知预算

### M2. `PawnCombatBodyHost` 这种空桥位应尽快进入主链或移除

空桥位本身不是错误。

错误在于：

- 空桥位一旦长期存在，就会诱导其它系统围绕它做结构预留
- 这样后续会被“为了兼容已有桥位”倒逼实现，而不是由真实需求驱动实现

### M3. 诊断日志嵌入密度偏高

当前主模组中的诊断点总体仍符合“关键非高频点”原则。

但 `CompTriggerBody` 中诊断调用与业务逻辑混排过密，后续若继续增长，会进一步降低可读性并放大上帝化倾向。

## 四、修复总原则

## 1. 不新增新的真值 owner

本次修复不允许通过“再新建一个 TriggerManager / MasterCoordinator / RuntimeContext”来逃避问题。

必须坚持：

- `CompTriggerBody` 仍是 Trigger 真值 owner
- `CompTrion` 仍是 Trion 真值 owner
- `CombatBodyState` 仍是战斗体相位真值 owner

修复方向应是：

- 从 owner 身上剥离不必要的流程与规则吸附
- 而不是再增加一个更大的伪总控层

## 2. 允许拆模块，但模块不持有真值

本次修复允许引入局部模块，前提是它们只承担：

- 规则判断
- 阶段推进
- 外部接线
- 只读投影

不允许承担：

- 真值持有
- 总状态缓存
- 跨 owner 的替代协调中心

## 3. 优先接通主链，再裁剪空骨架

对于 `CombatBody` 这类“已进入正式架构，但尚未接通”的系统，优先策略不是全部删掉，而是先完成主链职责裁定并接回主链。

对于纯预留接口，则按真实需要决定保留或删去。

## 五、严重 / 高风险问题的修复设计

## R1. `CompTriggerBody` 瘦身设计

### 目标

让 `CompTriggerBody` 退回：

- Trigger 真值 owner
- Trigger 输入 / 读取门面
- Trigger 正式事件广播口

不再继续直接吸收大量局部规则细节与流程分支。

### 设计

保留在 `CompTriggerBody` 的内容：

- 槽位列表与正式容器真值
- 存读档
- 正式只读接口实现
- 正式请求接口实现
- 正式事件口实现

外移出 `CompTriggerBody` 的内容，按“局部模块，不持真值”处理：

1. `TriggerActivationRules`

职责：

- 激活前合法性判断
- 双手绑定与互斥冲突判断
- 目标槽位归一规则

边界：

- 输入是当前 Trigger 已有真值快照
- 输出是规则判断结果或目标解析结果
- 不直接改槽位真值

2. `TriggerSwitchEngine`

职责：

- 构造切换上下文
- 结算后摇 / 前摇
- 产出“应提交哪些正式动作”

边界：

- 不自己读公开懒结算口
- 只接收 owner 传入的原始状态
- 不直接碰表达运行时

3. `TriggerDisableSync`

职责：

- 根据 `PawnBodyConstraintSignalHub + TriggerBodyDisableEvaluator` 结果同步禁用真值

边界：

- 仍只处理 Trigger 局部禁用，不触碰战斗体整体相位

### 预期结果

- `CompTriggerBody` 仍是 owner，但不再直接容纳全部局部规则细节
- 后续新增 Trigger 规则时，不再默认“往 owner 里继续加方法”

## R2. `CombatBody` 单主链化设计

### 目标

明确：

- 谁是战斗体外层流程协调者
- 谁是收尾事务协调者
- 它们如何形成正式主链

### 设计裁定

采用：

- `CombatBodyCoordinator` 为唯一战斗体外层流程主协调者
- `CombatBodyCleanupCoordinator` 不再作为平行第二主协调者存在
- 它改为 `CombatBodyCoordinator` 的下游事务协作者，由主协调者在退出 / 崩解流程中显式调用

也就是：

- 主流程 owner：`CombatBodyCoordinator`
- 收尾事务协作模块：`CombatBodyCleanupCoordinator`
- 相位真值 owner：`CombatBodyState`

### 为什么这样定

- 这样可以保留“收尾职责集中化”的优点
- 又避免出现两个都像主协调者的平行链
- 也符合用户“倾向尽快接入主链”的判断

### 同时需要补的接线

1. `PawnCombatBodyHost` 必须进入真实行为接线
2. `CombatBodyCoordinator` 必须真的驱动 cleanup
3. `CompTrion / CombatBodyState / Trigger` 的退出顺序要正式化

### 预期结果

- `CombatBody` 不再是几块互不连通的骨架
- 战斗体退出 / 崩解 / 冷却的收尾责任回到单主链

## R3. 表达 / 投影链瘦身设计

### 目标

消除“接口很多但依赖仍很具体”的假解耦。

### 设计

1. `TriggerProjectionFacade` 的入参收窄为最小接口

建议改为：

- 吃 `ITriggerLoadoutReader`
- 如需要缓存与投影宿主能力，则由运行时内部判断是否实现了 `ITriggerProjectionHost`

这样 patch 仍可从 `equipment.Primary` 找到 `CompTriggerBody`，但 facade 边界不再把具体类写死。

2. 压平当前第一阶段没有真实替换价值的 projection 分层

建议保留：

- `BdpProjectionRuntime`
- `TriggerExpressionCollector`
- `BasicExpressionResolver`
- `VerbExpressionProjectionRegistry`

建议评估裁剪或内部化：

- `IAutoRangedProjection`
- `IAutoMeleeProjection`
- `IManualCommandProjection`
- `ISurfaceProjection`
- 对应当前只有单实现且无真实替换价值的类

### 预期结果

- 表达 / 投影链仍保持层次，但不再为了抽象而抽象
- 当前第一阶段的真实主链更清晰

## R4. 正式外部命令扩展口规范化设计

### 目标

保留它作为正式需求，同时避免它继续贴着 `CompTriggerBody` 生长。

### 设计

1. 扩展口定位正式化

把它明确定位为：

- `Trigger 外部命令扩展口`

而不是：

- `测试按钮扩展口`

2. 调用宿主从 `CompTriggerBody` 继续下沉一层

`CompTriggerBody` 仍必须保留 `CompGetEquippedGizmosExtra()`，但它只做：

- 把请求交给独立的 `TriggerCommandFacade` 或等价门面

真正负责拼接：

- 正式外部命令
- 正式手动表达命令

的，不再直接写在 owner 内。

### 预期结果

- 外部扩展仍是正式需求
- 但不再以继续膨胀 Trigger owner 为代价

---

## 六、建议的修复顺序

当前建议修复顺序如下：

1. 先做 `R1：CompTriggerBody 瘦身第一轮`
2. 再做 `R2：CombatBody 单主链化接通`
3. 然后做 `R3：表达 / 投影链瘦身`
4. 最后做 `R4：正式外部命令扩展口规范化`

原因：

- `R1` 是当前最大风险源
- `R2` 是当前主链未接通的结构风险
- `R3` 和 `R4` 都依赖前两者清理后的边界再稳定推进

## 七、当前架构与目标架构对比图

```text
  -> CompTriggerBody

     -> 切换状态机

     -> 禁用同步

     -> 外部gizmo接线

     -> 表达缓存桥

  -> BdpProjectionRuntime
     -> Collector
     -> Resolver
     -> ProjectionRegistry
     -> Auto/Manual/Surface Projection

CombatBodyState   CombatBodyCoordinator   CombatBodyCleanupCoordinator
   |                    |                         |
   |                    |                         |
   +------ 当前存在，但主链接线不完整 ----------+
```

```text

  -> CompTriggerBody
     -> Trigger 真值 owner

     -> 存读档

  -> TriggerActivationRules      (规则判断，不持真值)

  -> BdpProjectionRuntime

CombatBodyCoordinator  --->  CombatBodyCleanupCoordinator
        |                              |
        v                              v
   CombatBodyState                Trigger / Trion / Host 收尾

CompTrion
  -> 只持有资源真值
```

## 八、二审后的执行结论

当前不建议继续直接给现有主模组加功能。

正式建议是：

- 先按本文件完成高风险结构修复
- 修复完成后，再继续路线 B / C 的功能推进

否则后续每往前走一步，都会继续把历史债压进 `CompTriggerBody`，并让未接通的骨架继续扩大认知负担。
