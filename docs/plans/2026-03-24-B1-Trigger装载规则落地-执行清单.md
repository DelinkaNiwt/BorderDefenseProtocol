# B1 Trigger 装载规则落地执行清单

**目标：** 把 Trigger 从“最小槽位样板”推进为“边界稳定、真值清楚、可被后续多表达层安全读取的正式来源宿主”，并确保推进过程始终具备短阶段游戏内可测、可视、可反馈、易诊断的机会。

**范围：** 本清单只覆盖 Trigger 的装载、局部激活、局部禁用、局部切换协调、双手锁定与局部封锁、身体部位局部联动，不越级接入多表达主链、战斗体整体流程、FireMode 业务、远程链模块化和外围完整 GUI/绘制回收。

---

## 一、执行纪律

## 1. 不允许长时间闷头编码

从 B1 开始，推进节奏必须短阶段化。

每完成一个子块，都必须先具备：

- 游戏内可测机会
- 游戏内可视反馈
- 结果偏差可直接发现
- 诊断线索可直接指向修复入口

如果某个子块完成后仍然无法在游戏中验证它到底对不对，
就不进入下一个子块。

## 2. 禁止应试思维

设计与实现时必须视作：

- 不知晓测试存在

也就是说：

- 不能为了“过某个测试点”反向扭曲设计
- 不能为了让界面看上去通过而偷塞业务逻辑

但实现完成后的正式结果必须：

- 能通过测试
- 能被临时 GUI 清楚观察
- 能被诊断日志定位问题

## 3. 游戏内测试可视化必须与主模组隔离

本阶段如果需要游戏内可视化测试面，
优先方案必须是：

- 正式扩展口 + 测试模组

而不是：

- 直接把临时 GUI 塞进主模组

测试可视化层的要求是：

- 删除后主模组零残留
- 只调用正式 API
- 不持有真值
- 不承载业务裁定

## 4. 诊断日志只打关键点，不打高频循环

本阶段必须在重要但非高频、非循环的位置留下关键诊断日志。

重点是：

- 提供状态转移原因
- 提供拒绝激活/装载/切换的原因
- 提供容器与槽位不一致的修复线索

不能做成：

- 每 tick 刷日志
- 每帧刷日志
- 用海量日志掩盖边界不清

## 二、旧 BDP 参考入口

本阶段临时 GUI 和状态可视化可参考旧 BDP 的这些入口：

- `Source/BDP/Trigger/UI/Gizmo_TriggerBodyStatus.cs`
- `Source/BDP/Trigger/UI/Window_TriggerBodySlots.cs`
- `Source/BDP/Trigger/UI/TriggerBodyDisplayConfig.cs`

参考目的仅限于：

- 可视化测试与反馈方式
- 状态呈现信息颗粒度

不作为：

- 新实现的业务真标准

业务真标准仍然来自：

- 旧 BDP 代码事实
- 已冻结的需求文档边界

## 三、B1 子块顺序

固定按以下顺序推进：

1. B1-a 槽位与正式容器一致性
2. B1-b 局部正式激活/关闭成立
3. B1-c 局部切换态与表现期边界
4. B1-d 局部禁用规则
5. B1-e 双手锁定 / 局部封锁 / 身体部位联动

## 四、各子块执行清单

## B1-a 槽位与正式容器一致性

### 目标

- 槽位结构稳定
- 芯片必须进入正式 `ThingOwner`
- 装卸不会留下悬空引用
- 读档后槽位引用与正式容器重新对齐

### 禁止扩张项

- 不接入禁用规则
- 不接入切换表现期
- 不接入双手锁定
- 不接入多表达解析

### 最小游戏验证面

- 进游戏后可装入、卸下、再次装入
- 读档后无需重新装载
- 芯片不会只剩槽位字段引用却不在正式容器里

### 游戏内测试可视化面必须可见

- 每侧每槽当前 `LoadedChip`
- 正式容器中的芯片列表
- 槽位引用与容器是否一致

### 关键诊断日志点

- 装载成功
- 装载失败及失败原因
- 卸载成功
- 卸载失败及失败原因
- 读档后一致性修复发生时
- 修复失败导致槽位清空时

### 当前落地状态

- 已完成第一轮最小正式装载落地

当前正式已具备：

- 槽位与正式 `ThingOwner` 容器并存
- 装载、卸载、一致性修复关键日志
- 读档后最小一致性修复

当前明确不再允许作为阶段成果保留的内容：

- 主模组内置临时诊断窗口
- 主模组内置诊断按钮
- 主模组内置测试专用查询口

本子块后续若要形成游戏内可视化验证面，
必须改经：

- 正式扩展口
- 测试模组
- 可删除的外置测试层

## B1-b 局部正式激活/关闭成立

### 目标

- 明确某侧哪个槽位是正式激活槽位
- 激活与关闭立即成立
- 暂停下查询也立即得到正确结果

### 禁止扩张项

- 不做主攻击投影选择
- 不做表达结果集合重建
- 不做切换表现层业务

### 最小游戏验证面

- 进游戏后可明确切换某侧当前正式激活槽位
- 关闭后状态立即变化
- 暂停时点击或查询不需要等 tick 才成立

### 游戏内测试可视化面必须可见

- 当前侧正式激活槽位索引
- 当前是否存在激活槽位
- 最近一次激活或关闭动作结果

### 关键诊断日志点

- 激活请求进入
- 激活被拒绝及原因
- 激活正式提交
- 关闭请求进入
- 关闭被拒绝及原因
- 关闭正式提交

## B1-c 局部切换态与表现期边界

### 目标

- 把“逻辑已切换”和“表现仍在切换中”分开
- `Idle / WarmingUp / WindingDown` 语义清楚
- 切换表现只服务局部协调，不反向决定逻辑真值

### 禁止扩张项

- 不借表现期回写正式激活结果
- 不接入表达层真值
- 不接入视觉系统完整回收

### 最小游戏验证面

- 进游戏后可看出逻辑激活已成立，但表现期仍在持续
- 切换过程中可直接确认当前处于哪一态

### 游戏内测试可视化面必须可见

- `SwitchContext.phase`
- `targetSlotIndex`
- `windingDownSlotIndex`
- `phaseEndTick`

### 关键诊断日志点

- 切换表现上下文创建
- 切换表现上下文清理
- 表现期查询命中哪一态

## B1-d 局部禁用规则

### 目标

- 禁用成为正式局部状态
- 先接 Trigger 自身能正式判断的禁用来源
- 提供最小恢复入口

### 禁止扩张项

- 不把战斗体整体状态混进来
- 不把资源不足混成 Trigger 禁用真值
- 不做所有未来禁用来源一次补齐

### 最小游戏验证面

- 进游戏能区分“无芯片不可激活”和“有芯片但被禁用不可激活”
- 恢复后可重新激活
- 禁用态不会靠 tick 糊过去

### 游戏内测试可视化面必须可见

- `IsDisabled`
- 禁用来源标签或原因码
- 当前是否可激活

### 关键诊断日志点

- 禁用成立
- 禁用解除
- 因禁用拒绝激活

## B1-e 双手锁定 / 局部封锁 / 身体部位联动

### 目标

- 落地双手锁定与局部封锁的正式语义骨架
- 让手部缺失或损坏对 Trigger 的局部可用性产生正式影响
- 不越界接入战斗体整体流程

### 禁止扩张项

- 不接战斗体崩解
- 不接组合表达成立
- 不接完整身体恢复链
- 不把局部失效自动提升成整体相位变化

### 最小游戏验证面

- 进游戏后可直接观察某侧被锁、被封锁、或因部位失效而不可用
- 另一侧是否受联动影响可立即验证

### 游戏内测试可视化面必须可见

- 当前锁定源
- 当前封锁侧
- 当前部位状态映射到哪个槽位可用性判断

### 关键诊断日志点

- 双手锁定成立
- 双手锁定解除
- 局部封锁成立
- 部位失效导致槽位不可用

## 五、B1 游戏内测试可视化最小要求

本阶段测试可视化面至少要能显示：

1. 三侧槽位概览
2. 每槽芯片装载状态
3. 每侧正式激活槽位
4. 每侧切换态
5. 每槽禁用状态
6. 当前锁定或封锁状态
7. 正式容器与槽位引用一致性

同时应支持最小交互：

- 手动刷新显示
- 打开或关闭详细信息

但这些交互若需要进入实现，
也必须优先放在：

- 测试模组

不能直接先落进主模组。

## 六、B1 诊断日志最小要求

本阶段必须覆盖以下非高频关键点：

1. 装载
2. 卸载
3. 激活请求
4. 关闭请求
5. 切换表现上下文创建与失效
6. 禁用成立与解除
7. 双手锁定与封锁成立与解除
8. 读档后一致性修复

每条诊断日志至少应说明：

- 发生了什么
- 作用于哪一侧、哪一槽
- 成功还是失败
- 若失败，原因是什么

## 六点五、B1-a 切污后的正确补位要求

`B1-a` 已明确发生过一次“为了尽快可视化测试而把测试层能力塞进主模组”的污染。

从现在开始，
`B1-a` 后续若要恢复游戏内可视化验证能力，
必须同时满足：

1. 主模组只保留正式业务、关键诊断日志、正式最小读取口与正式扩展口
2. 游戏内窗口、测试按钮、显示面放在可删除的外置测试层
3. 外置测试层只通过正式接口读取，不直接依赖主模组内部私实现
4. 删除测试层后，主模组零残留、零分支、零额外责任

专项补位方案见：

- `docs/plans/2026-03-24-B1-a-切污后的正确补位方案-第一版.md`

## 七、B1 完成标准

当且仅当以下条件同时满足，B1 才算完成：

- Trigger 能稳定提供装载真值
- Trigger 能稳定提供局部激活真值
- Trigger 能稳定提供局部禁用真值
- Trigger 能稳定协调局部切换表现期
- Trigger 能表达双手锁定与局部封锁的最小正式语义
- 每个子块完成时都已获得至少一次游戏内可测反馈
- 若需要游戏内可视化验证面，必须通过隔离测试层提供，主模组本体不直接承载临时 GUI
- 关键诊断日志已足以支撑问题定位

## 八、一句话总括

B1 的真正交付物，不只是“把 Trigger 代码继续补厚”，而是“在不越级侵入多表达、战斗体、FireMode 和远程链的前提下，先把 Trigger 的装载、局部激活、局部禁用、局部切换协调、双手锁定与局部封锁做成一个边界稳定、游戏内可短周期验证、具备隔离测试可视化面和关键诊断日志的正式来源宿主”。
