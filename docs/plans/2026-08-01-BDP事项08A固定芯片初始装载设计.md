# BDP 事项08A固定芯片初始装载设计

## 一、目标

为触发体提供中性的“按定义文件预装真实芯片”能力，同时保持玩家配置权限、芯片业务规则和触发器类别彼此独立。

本设计只建立Core通用底层，不创建近界触发体、黑触发体或新的具体芯片装载方案。

## 二、核心语义

### 1. 玩家配置权限

`CompProperties_TriggerBody.loadoutControlMode`只判断玩家以后能否修改触发体内的芯片：

- `PlayerConfigurable`：玩家可配置。
- `PlayerNonConfigurable`：玩家不可配置。

两个值按同一主体和同一语法命名，避免旧名称`DefinitionFixed`把“玩家权限”和“初始装载来源”混为一谈。

两种控制模式都允许填写`fixedLoadout`。例如，玩家可配置的触发体可以出厂自带几枚芯片，玩家之后仍能拆换；玩家不可配置的触发体则保持定义给出的装载结果。

### 2. 初始固定装载表

`CompProperties_TriggerBody.fixedLoadout`是可空列表：

- 不写或写空：合法，表示新触发体初始不预装芯片。
- 填写条目：触发体首次生成时按表创建并装入真实芯片。
- `fixedLoadout`是否为空不参与玩家权限判断。

建议作者格式：

```xml
<loadoutControlMode>PlayerNonConfigurable</loadoutControlMode>

<mainSlotCount>0</mainSlotCount>
<subSlotCount>0</subSlotCount>
<specialSlotCount>3</specialSlotCount>

<fixedLoadout>
  <li>
    <side>Special</side>
    <slotNumber>1</slotNumber>
    <chipDef>第一枚芯片DefName</chipDef>
  </li>
  <li>
    <side>Special</side>
    <slotNumber>2</slotNumber>
    <chipDef>第二枚芯片DefName</chipDef>
  </li>
</fixedLoadout>
```

每条配置只包含三个必要字段：

- `side`：`Main`（主槽）、`Sub`（副槽）或`Special`（特殊槽）。
- `slotNumber`：面向作者的槽位编号，从1开始。
- `chipDef`：要生成的芯片ThingDef（物品定义）。

允许故意留空槽位；不增加数量、初始启用状态或初始形态字段。一个槽位对应一个真实芯片，芯片启用后仍从自己的默认形态开始。

## 三、实例与生命周期

固定装载生成的不是虚拟记录，而是真实的芯片Thing（物品实例）：

```text
新触发体首次生成
  -> 建立空槽位
  -> 读取 fixedLoadout
  -> 创建真实芯片
  -> 装入指定槽位及触发体隐藏容器

战斗体生成
  -> 继续使用现有流程自动启用特殊槽芯片

存档与读档
  -> 继续保存槽位和真实芯片实例
  -> 不再次应用 fixedLoadout
```

首次预装应接在RimWorld原版`PostPostMake`（物品首次制造完成回调）时机，不在读档初始化路径补装，不额外保存“是否初始化”标记，也不持续检查。

因此：

- 定义文件变更只影响以后新生成的触发体，不篡改存档中已有触发体。
- 预装芯片被消耗或销毁后保持缺失，不自动补充。
- 不新增特殊槽启用规则；现有战斗体生成流程已经会启用所有特殊槽芯片。

## 四、Core与业务边界

Core只提供通用装载能力，不写死“类别决定行为”：

- Core的固定装载条目仍支持主槽、副槽和特殊槽。
- 未来第一方近界、黑等不可配置触发体，由各自业务Def显式填写主槽0、副槽0及特殊槽固定芯片。
- 第三方开发者仍可按自己的触发体设计使用其它合法槽区。
- 类别Def不自动推导槽位数量、玩家权限或预装内容。

## 五、定义校验

`fixedLoadout`为空始终合法。非空时逐条检查：

1. `side`必须显式填写为已知槽区。
2. `slotNumber`必须从1开始，且不能超过对应槽区的实际槽位数。
3. `chipDef`必须填写，并且是通过现有芯片定义校验的有效芯片物品。
4. 两条配置不得指向同一实际槽位。
5. 芯片的`SlotRegion`（槽位区域）必须与目标槽区相容。
6. 复用现有`SlotOccupancy`（槽位占用方式）规则；例如`PairedHands`（成对主副槽）不能装入特殊槽。

`PlayerConfigurable`和`PlayerNonConfigurable`都可以拥有非空`fixedLoadout`，不因玩家权限产生定义错误。

## 六、运行失败处理

首次预装采用整批事务：

```text
全部检查并尝试装入
  -> 全部成功：保留全部芯片
  -> 任一失败：撤回本批创建和装入的全部芯片
```

发生未被定义校验提前发现的异常时：

- 只记录一条清楚的开发者日志，包含触发体、芯片、槽区和槽号。
- 不向普通玩家弹出消息，不抛出导致游戏中断的异常。
- 不保留半套预装结果。
- 不在之后反复重试或自动补装。

## 七、不在本次实现的内容

- 不创建近界、黑或边境特制触发体实例。
- 不给边境标准触发体添加预装芯片。
- 不改变特殊槽自动启用、芯片激活、形态、Trion费用或存读档规则。
- 不设计固定装载预设Def、跨触发体复用表或按类别自动套用配置。
