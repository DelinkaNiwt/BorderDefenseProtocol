# 临时攻击手武装构型退役设计

## 目标

从 BDP（Border Defense Protocol，边境防御协议）正式内容中移除仅用于验证的“临时”攻击手武装构型，并清理它专用的破墙斧视觉、语言键和测试入口。

## 已确认事实

- `BDP_ArmamentForm_Temporary` 位于 `1.6/Content/Defs/ChipArmamentFormDef/Presets.xml`，只兼容 `BDP_ChipProfession_Attacker`（攻击手职业）和 `BDP_ChipFunction_Kogetsu`（弧月芯片功能模板）。
- `BDP_Visual_Temporary_BreachAxe` 位于 `1.6/Content/Defs/ExpressionDef/Visual.xml`，只被该临时武装构型的 `visualGraphicOverrideDefName`（视觉贴图局部覆盖）引用。
- 两条 `BDP_ArmamentForm_Temporary*` Keyed（语言键）只为该构型提供名称和说明。
- 现有近战覆盖测试专门验证这个临时样本；武装构型边界测试和制造本地化测试也保留了它的存在断言。
- Trion 默认型的测试中有一段通用功能白名单行为验证，但测试提示语误称“临时型”；这段逻辑实际不依赖临时 Def，应改为中性表述并保留。

## 方案比较与决策

### 方案 A：退役正式内容并清理专属测试（采用）

删除临时武装 Def、破墙斧视觉 Def 和两条语言键；将原临时样本测试替换为“退役边界”检查，更新现有边界/本地化测试并修正通用白名单测试文案。

优点是正式内容、测试和语言包都没有悬空引用，且保留了通用机制的回归保护；改动范围仍局限于 Content XML、语言包和 Development 测试。缺点是旧临时样本的近战贴图覆盖行为不再由该样本验证，但该样本本来就是一次性验证入口。

### 方案 B：只隐藏临时武装型

保留 Def、视觉和语言键，只设置制造台与成品名称不可见。

改动最少，但临时测试样本仍进入 DefDatabase（定义数据库），正式工程继续携带已退役内容，不符合本次“清理”的目标。

### 方案 C：连同弧月近战视觉覆盖机制一起删除

删除临时样本并移除通用 `visualGraphicOverrideDefName` 支持。

范围过大，会影响正式的局部视觉覆盖机制；没有证据表明该通用机制已无其它用途，不采用。

## 设计边界

- 删除：临时攻击手武装 Def、临时破墙斧视觉 Def、两条临时语言键、临时样本专用测试。
- 更新：武装构型定义边界测试、制造本地化测试、Trion 测试中的通用白名单提示语。
- 保留：`ChipArmamentFormDef`（芯片武装构型定义）类型、视觉贴图局部覆盖字段、弧月正式视觉预设、Trion 默认型、其它正式攻击手/枪手/射手构型和历史文档。
- 不修改：Core.dll、正式运行时代码、制造解析逻辑、攻击执行链、贴图资源和存档字段。

## 验证标准

- 退役冒烟测试确认临时武装 Def、临时破墙斧视觉 Def 和两条语言键均不存在，同时 Trion 默认型仍存在。
- 武装构型定义边界、制造本地化、Trion 视觉/默认型和相关 XML 解析通过。
- 全局搜索确认正式 `1.6`、语言包和当前测试代码不再引用临时 DefName；历史设计/实施文档可保留历史事实，不作为运行时引用。
- 进入游戏后只需确认攻击手制造/装载列表不再显示“临时”；本次不改变正式攻击行为。
