# 二次重构核心对象图（第一版）

## 目的

这份文档把“概念模型 v1”进一步压到对象层。

它不写具体类名定稿，
但先明确：

- 需要哪些核心对象
- 每个对象大概管什么
- 对象之间怎么依赖
- 哪些对象属于第一阶段必须出现

## 一、对象分层

建议把对象分成五层：

1. 真值对象
2. 协调对象
3. 表达对象
4. 投影对象
5. 支撑对象

其中：

- 真值对象必须少
- 协调对象必须薄
- 表达对象必须清楚
- 投影对象必须只读
- 支撑对象不承载业务

## 二、第一层：真值对象

### 1. `TrionState`

对应现在的：

- `CompTrion`

职责：

- 持有资源真值
- 提供资源语义操作

建议持有的数据：

- `cur`
- `max`
- `allocated`
- `reserved`
- `drains`
- `frozen`

建议提供的操作：

- `CanAfford`
- `TryConsume`
- `ConsumeUntilDepleted`
- `Reserve`
- `Allocate`
- `Release`
- `RegisterDrain`
- `UnregisterDrain`
- `Freeze`

第一阶段：必须出现

### 2. `CombatBodyPhaseState`

对应现在的：

- `CombatBodyState`

职责：

- 持有战斗体外层相位
- 校验相位切换合法性

建议持有的数据：

- `phase`
- `activationTick`
- `cooldownEndTick`
- `collapseStartTick`
- `collapseReason`

建议提供的操作：

- `CanActivate`
- `EnterActive`
- `EnterCollapsing`
- `EnterCooldown`
- `EnterInactive`
- `GetCollapseRemaining`
- `GetCooldownRemaining`

第一阶段：必须出现

### 3. `TriggerLoadoutState`

对应现在收缩后的：

- `CompTriggerBody` 的装载真值部分

职责：

- 持有槽位与装载真值
- 持有切换状态机真值
- 持有当前激活表达状态

建议持有的数据：

- Main/Sub 普通槽
- 特殊槽
- 双手锁定
- 槽位禁用
- Main 切换上下文
- Sub 切换上下文

命名约束：

- 触发体内部稳定命名统一用 `Main/Sub`
- 并固定：
  - `Main = 右`
  - `Sub = 左`
- 只有与 RimWorld 身体部位直接关联的对象或字段，才继续使用 `Left/Right`

建议提供的操作：

- `LoadChip`
- `UnloadChip`
- `RequestActivateSlot`
- `RequestDeactivateSlot`
- `ResolveSwitching`
- `DisableSlot`
- `ClearDisabled`
- `GetActiveSlots`
- `GetActivatingSlots`

第一阶段：必须出现

## 三、第二层：协调对象

### 1. `CombatBodyCoordinator`

对应现在的：

- `CombatBodyOrchestrator`

职责：

- 激活战斗体事务
- 主动解除事务
- 被动崩解事务
- 异常收尾事务

它依赖：

- `TrionState`
- `CombatBodyPhaseState`
- `TriggerLoadoutState`
- 身体变换宿主
- 事件总线

它不持有新的真值。

第一阶段：必须出现

### 2. `TriggerActivationCoordinator`

这是现在旧 BDP 里分散在触发体内部的一块，
建议在新架构里单独提出来。

职责：

- 芯片激活 / 关闭的局部事务
- 激活成本、持续消耗注册
- 非 Verb 表达授予 / 撤销
- 组合状态刷新触发

它依赖：

- `TriggerLoadoutState`
- `TrionState`
- 表达系统
- 事件总线

第一阶段：必须出现，但可以很薄

### 3. `CollapseCleanupCoordinator`

职责：

- 各种崩解源汇总后进入统一收尾
- 确保表达撤销、资源回收、身体恢复、入口清理完整闭环

它可以一开始先并到 `CombatBodyCoordinator`，
但概念上必须留出来。

第一阶段：必须有职责，但不一定独立成类

## 四、第三层：表达对象

### 1. `ExpressionSource`

这不是最终宿主对象。

它表示：

- 当前某个芯片或组合提供了什么表达原料

建议至少区分：

- `VerbSource`
- `AbilitySource`
- `HediffSource`
- `SpecialSource`

每个来源至少应带：

- 来源 id
- 来源侧别
- 来源宿主槽位
- 类型
- 配置引用

第一阶段：必须出现概念和接口

### 2. `ExpressionSet`

职责：

- 收纳当前所有来源
- 提供按侧、按类型、按来源查询

它是表达系统内部的输入集合。

第一阶段：必须出现

### 3. `ExpressionResolver`

职责：

- 读取 `ExpressionSet`
- 应用双手规则、混合规则、组合规则
- 产出当前表达结果

它是表达系统的规则核心。

第一阶段：必须出现

### 4. `ResolvedExpressions`

职责：

- 收纳当前表达系统的最终结果

建议至少包含：

- `manualExpressions`
- `primaryAttackProjection`
- `primaryMeleeProjection`
- `surfaceProjection`
- `comboExpressions`

第一阶段：必须出现

## 五、第四层：投影对象

### 1. `ManualCommandProjection`

职责：

- 把 `ResolvedExpressions` 投影成玩家手动按钮

第一阶段：必须出现

### 2. `AutoAttackProjection`

职责：

- 产出给原版自动远程 / 近战入口用的默认投影

这层要明确分成两条：

- `AutoRangedProjection`
- `AutoMeleeProjection`

第一阶段：必须出现

### 3. `SurfaceProjection`

职责：

- 产出给外部只允许展示一个默认表面的投影结果

包括：

- 默认武器表面
- 信息面板默认表面

第一阶段：必须出现概念

### 4. `VisualProjection`

职责：

- 持武绘制
- 枪口位置
- 显示与发射点一致性

第一阶段：只留接口

## 六、第五层：支撑对象

### 1. `BdpTools`

这是主模组内部工具收纳层的总概念。

下面应只收：

- 诊断工具
- 日志工具
- 绘制调试工具
- 通用 key / id 生成
- 小型桥接辅助
- 通用校验

第一阶段：建议出现基本目录和约束

### 2. `BdpTestHooks`

这是为后置测试模组准备的一层公开接口概念。

职责：

- 暴露有限、稳定、可扩展的接入点
- 不暴露一堆内部脏细节

第一阶段：要先留概念，不必全实现

## 七、对象之间的依赖关系

建议遵守下面这些方向：

### 真值对象不依赖投影对象

也就是：

- `TrionState`
- `CombatBodyPhaseState`
- `TriggerLoadoutState`

都不该知道按钮、自动 AI、显示长什么样。

### 协调对象依赖真值对象，但不生成新真值

也就是：

- 协调可以写真值
- 但不能自己再偷偷持有另一套正式状态

### 表达对象读取真值，不直接改资源和相位

也就是：

- 表达系统主要读装载与状态
- 执行阶段才通过明确接口碰资源

### 投影对象只读取表达结果

也就是：

- 手动入口
- 自动入口
- 表面投影
- 视觉投影

都不该自己重新跑业务推导。

### 支撑对象谁都能用，但不拥有业务方向

## 八、第一阶段对象最小集

第一阶段最小闭环，建议至少落这些对象：

- `TrionState`
- `CombatBodyPhaseState`
- `TriggerLoadoutState`
- `CombatBodyCoordinator`
- `TriggerActivationCoordinator`
- `ExpressionSource`
- `ExpressionSet`
- `ExpressionResolver`
- `ResolvedExpressions`
- `ManualCommandProjection`
- `AutoRangedProjection`
- `AutoMeleeProjection`
- `SurfaceProjection`

可以暂缓完整实现的对象：

- `VisualProjection`
- `BdpTestHooks`
- 独立 `CollapseCleanupCoordinator`

## 九、当前不建议一开始就做成很多小对象的地方

### 1. 切换状态机

第一阶段可以先仍放在 `TriggerLoadoutState` 内部，
不急着再拆一层对象森林。

### 2. 崩解收尾

第一阶段可以先挂在 `CombatBodyCoordinator` 内，
等规则稳定后再细拆。

### 3. 非 Verb 投影执行器

第一阶段可以先做最简单的 Ability/Hediff 接入接口定义，
不必立即拆一堆策略类。

## 十、我当前的判断

如果你认可这份对象图方向，
下一步就该继续往下压成真正能开工的东西：

- 第一阶段接口草案
- 第一阶段最小闭环范围定义
- 第一阶段哪些对象只留接口、哪些必须真做
