# BDP 统一模组双程序集迁移实施计划

> **For future AI agents（给后续 AI 执行者）：** 开始任何迁移工作前，必须先完整读取本计划和同目录的 `2026-07-28-BDP统一模组双程序集设计.md`。严格按当前检查点工作，不得凭压缩后的对话记忆猜测。实施已确认任务时使用 `executing-plans（执行计划）` 工作方式，但不得创建 worktree（工作树）。

**Goal（目标）：** 把当前两个 BDP 模组统一为一个模组包和两个严格单向依赖的程序集，并优先正式化现测试模组中的偏底层系统；上层应用以后逐项确认。候选测试模组只是迁移期内容库，最终必须物理退役，只保留主模组。

**Architecture（架构）：** `BDP.Core.dll` 只保存中性核心骨架，`BDP.Content.dll` 单向引用核心并保存公共内容支撑、正式界面、开发工具和具体业务。物理合并与业务重做分开，避免一次改动过多。

**Tech Stack（技术环境）：** RimWorld 1.6（边缘世界1.6）、C# 7.3（C#语言7.3）、XML（可扩展标记语言）、Harmony（补丁框架）、PowerShell（命令行脚本）、Git（版本控制）。

## 一、每次继续工作时的固定动作

1. 完整读取本计划。
2. 读取设计文档中的长期边界。
3. 查看“当前检查点”。
4. 只处理当前已获用户确认的一项。
5. 实施前记录本项范围和不处理范围。
6. 实施后更新状态、验证结果、提交号和下一项。
7. 不提前处理后续上层应用。

## 二、状态说明

- `未介绍`：尚未向用户解释。
- `待确认`：已经介绍，等待用户决定。
- `已确认`：用户已经同意，但尚未实施。
- `进行中`：当前唯一正在处理的事项。
- `已暂停`：原事项已开始或完成部分审计，但因用户插入更高优先级事项暂时停下，既有结论保留。
- `已完成`：已经实施、验证并提交。
- `搁置`：用户决定以后再处理。
- `取消`：确认不再需要。

任何时刻最多只能有一个“进行中”事项。

### 01：统一模组外壳与两个程序集工程

目的：

- 让游戏只加载一个 BDP 模组。
- 让工程稳定输出 `BDP.Core.dll` 和 `BDP.Content.dll`。
- 暂时不重新设计上层应用。

建议处理：

- 将现 `BDP` 工程正式改为核心程序集工程。
- 将现 `BDP.DevHarness` 工程改为内容程序集工程。
- 统一输出到主模组的 `1.6/Assemblies`。
- 统一 About（模组说明）和 LoadFolders（加载目录）配置。
- 上层应用先机械随内容程序集保留，之后再逐项转正。

明确不处理：

- 不批量调整芯片参数。
- 不批量重命名具体应用。
- 不重做护盾、追踪、毒蛇或旋空弧月。
- 不顺手移动原主模组中的玩家业务内容。

### 02：程序集单向依赖自动检查

目的：

- 不依赖人工记忆，自动保证 `BDP.Core.dll` 不引用本模组的任何其他 DLL（动态链接库）。
- `BDP.Content.dll` 只是当前第一个受禁的本模组程序集；未来新增本模组程序集时自动纳入检查。

预期检查：

- 自动收集本模组各 C#（C#语言）工程声明的程序集名称，不手写只包含 `BDP.Content` 的固定名单。
- 核心工程文件不引用其他本模组工程。
- 核心程序集编译结果的依赖表不包含其他本模组程序集。
- 核心源码和 XML（可扩展标记语言）不直接引用其他本模组程序集所属的内容类型。
- 正式内容无开发工具反向依赖。

### 07：正式化芯片 Def（定义）公共基线

目的：

- 保留所有芯片真正共同需要的最小配置。

限制：

- 不把市场价值、伤害、科技等级等业务参数塞进公共基类。

已确认的分类边界：

- 每枚正式芯片必须引用统一登记的正式分类，不能继续自由填写分类字符串。
- 采用符合 RimWorld（边缘世界）习惯的 `ChipCategoryDef（芯片分类定义）`，由 Core 提供中性定义类型和引用规则，具体分类名单以后结合真实芯片逐项确认。
- 现有 `PrimaryCategory（主分类字符串）`及其临时内容不直接转正。
- 删除现有自由文本 `Tags（标签）`；装载位置、双侧绑定和表达方式由各自正式配置负责，不混入主分类。
- 正式作者入口统一为 `Profile.Category（画像.分类）`，必须引用已经登记的 `ChipCategoryDef`；Core 契约和运行快照只传递该正式引用，不再传递画像自由标签。
- Core 本轮只提供空业务语义的 `ChipCategoryDef` 类型，不预设攻击、防御、能力、状态、双持等具体分类。
- DevHarness（候选内容模组）单独定义一个“未审定芯片”分类；除故意缺失分类的非法校验样本外，现有候选芯片统一引用它，等待以后逐枚确认正式业务分类。

已确认的扩展边界：

- 保留 `Extensions（扩展）`作为芯片定义内统一、工整的可选能力分级。
- 删除旧的 `BlockName / TargetSystem / PayloadText（块名、目标系统、任意文本载荷）`方案；它只有文本搬运能力，没有可靠的类型、路由或调用保障。
- Core 提供中性的 `ChipExtensionConfig（芯片扩展配置）`共同父类型与扩展集合；Content 可按业务定义有明确字段的具体扩展类型，依赖仍严格为 Content 单向引用 Core。
- 同类扩展原则上一枚芯片只声明一个；需要多条内容时由该扩展内部持有自己的列表。
- 所有芯片共同需要的配置继续放在公共块中；只有部分芯片才拥有的可选能力进入 `Extensions`。
- 扩展只属于芯片静态 Def（定义）；Core 契约保留强类型静态引用并检查空条目和同类型重复，不把任意业务扩展自动复制进每个表达运行快照。
- 删除现有无消费者的 `ChipExtensionBlockContract`、`ExpressionChipExtensionSnapshot`及其文本复制链；某项业务确实需要运行快照时，由该业务在自己的执行边界建立专用快照。
- 当前候选 XML 没有任何扩展声明，本项不创造示例业务扩展，也不建立扩展注册中心或事件总线。
- 独立设计文档：`docs/plans/2026-07-29-BDP芯片强类型扩展设计.md`。

已确认的形态配置边界：

- 删除 `Loadout.InitialModeKey（装载配置.初始形态键）`，正式字段归入 `Expression.DefaultModeKey（表达配置.默认形态键）`。
- 形态采用“统一表达目录＋条目标识选择”：`Entries（表达条目）`声明芯片全部可能表达，`Modes（形态）`通过 `ActiveEntryIds（启用的表达条目标识）`选择本形态内容。
- 删除旧 `Append / Replace / Disable（追加/替换/禁用）`形态操作结构及全部配套类型，不兼容。
- 单形态芯片不声明 `Modes`和默认形态，全部合法 `Entries`生效；多形态芯片必须声明有效默认形态，并只发布当前形态所引用的条目。
- 事项07尚未建立当前形态状态，因此多形态芯片暂时固定使用默认形态；完整的当前形态、玩家切换、存读档和表达刷新仍拆为事项07A。
- 形态和表达标识必须非空且唯一；形态引用必须存在且不可重复；多形态条目不得完全无人引用；依附型子表达必须与父表达同形态且排在父表达之后。
- 任一结构错误使整枚芯片表达契约无效，不发布残缺结果。
- 现有齐射毒蛇、护盾、状态、能力和紧急脱离均为单形态配置，其 XML 不需要修改。
- “光魂”的默认大盾、巨刃和两形态共用冲刺技能只作为事项07A验收用例，不在底层阶段提前迁入具体业务。
- 独立设计文档：`docs/plans/2026-07-30-BDP芯片形态配置归位设计.md`。

已确认的功率配置边界：

- 芯片功率需求是独立于 Trion 存量与消耗的真实公共参数，不能删除。
- 使用者拥有“可输出功率”属性；只有其输出功率达到芯片需求时，该芯片提供的攻击、Ability（技能）、Hediff（状态）或被动效果才能真正使用。
- 功率不足不阻止芯片搭载，也不取代 Trion 容量和激活成本判断；具体失效表现与重新评估流程留到事项07B完整设计。
- 采用简单的单芯片门槛：每枚芯片分别与使用者输出功率比较，不累加所有已激活芯片的需求，也不建立第二套总额度。
- 使用者输出功率优先采用 RimWorld 原版 `StatDef（属性定义）`承载，以便基因、Hediff、装备等按原版方式修正；最终命名和比较细节留到事项07B确认。

已确认的装载互斥边界：

- 保留“芯片可以共同搭载，但部分芯片不能同时启用”的通用互斥机制。
- 删除自由文本 `ExclusionTags（排斥标签）`，改为受控的 `ActivationExclusionGroups / ChipExclusionGroupDef（启用互斥组/芯片互斥组定义）`引用。
- 两枚芯片共享任意一个互斥组时不得同时工作；具体互斥组由正式业务定义，Core 只提供中性规则。
- 发生冲突时不拒绝新目标：同侧让位芯片与全部跨侧冲突芯片同时执行正常关闭，目标进入 `WaitingForConflicts（等待冲突解除）`，全部阻挡者关闭后再执行正常开启。
- 同侧或互相冲突的后请求覆盖前请求；跨侧且互不冲突的请求并行保留。重复点击等待或开启中的同一目标无效，不提供主动取消。
- 等待阶段进入现有 `SwitchContext（切换状态）`存读档，不建立第二套队列；目标身份变化或失效时清理请求，不自动恢复旧芯片。
- Content 面板以亮琥珀黄色描边表示等待，图标不置灰；候选临时 `DualWieldTest`直接删除，不建立具体正式组。
- 独立设计文档：`docs/plans/2026-07-30-BDP芯片启用互斥组与自动切换设计.md`。

已确认的槽位区域边界：

- `Main（主槽）`与 `Sub（副槽）`共同组成主副槽区，`Special（特殊槽）`组成特殊槽区。
- 主副槽区与特殊槽区在设计上永久互斥，同一枚芯片只允许属于其中一类，不需要可组合的多选区域。
- 不建立只有配置认识、运行系统却无法理解的开放式槽位组 Def；不同触发体仍可通过各区域槽位数量表达不同布局。
- 现有 `SidePolicy（侧别策略）`正式改为必填的 `SlotRegion（槽位区域）`，枚举只允许 `MainSub（主副槽区）`与 `Special（特殊槽区）`。
- 底层保留 `Unspecified（未指定）`只用于识别漏填；漏填、显式写入未指定或未知值都属于定义错误，不得静默回退到主副槽区。

已确认的槽位占用边界：

- 保留一枚芯片同时占用主副两侧相同编号槽位的底层能力。
- 删除 `IsDualWieldBinding（是否双持绑定）`的具体业务命名，改为必填的 `SlotOccupancy（槽位占用方式）`；底层 `Unspecified（未指定）`只用于把漏填识别为定义错误。
- 正式值只提供 `Single（单槽）`与 `PairedHands（成对主副槽）`；`PairedHands`只允许搭配`MainSub（主副槽区）`，搭配特殊槽区属于定义错误。
- 成对占槽只计算一次容量、一次性激活费、持续费用、芯片定义和表达来源；当前双侧启用通知导致一次性激活费重复扣除的既有错误在本小项修正。
- 双持、双手重武器或其他具体效果由 `Expression（表达）`和上层应用决定，槽位占用配置不承诺攻击数量或视觉形式。

已确认的芯片启停时间边界：

- 保留芯片本体级启用与停用延迟；它们控制槽位表达何时正式生效或撤下。
- `WarmupTicks / WinddownTicks（前摇/后摇）`改名为 `ActivationDelayTicks / DeactivationDelayTicks（启用/停用延迟）`，避免与攻击动作时序混淆。
- 未填写时采用系统默认60/30 tick（游戏刻），0表示立即完成，正式配置不接受其它负数。
- 这两个字段不控制攻击前摇，也不借给事项07A的芯片形态切换使用。

已确认的持续 Trion 消耗边界：

- 正式持续消耗只有三类：战斗体启用后的固定维持消耗、部分芯片激活后的固定维持消耗、战斗体伤口泄漏消耗。
- 芯片本体只保留容量占用、一次性激活费用和功率要求，不再拥有持续消耗字段。
- 最终有效表达通过 `SustainCostBySourceCount（按有效来源数计费）`声明整组效果每秒总费用；旧标量 `SustainCost`、芯片 `ActiveDrainPerSecond`和 Hediff 专属扣费组件均不保留。
- 战斗体维持、伤口泄漏以及三类来源共同使用的中央 Trion 消耗账本保持不变。

已确认的芯片容量占用边界：

- `CapacityCost（容量占用）`保持现有机制与命名，不作改造。
- 容量占用不是实际消耗：开启战斗体时，按触发体中所有已装芯片合计锁定 Trion；解除战斗体后原量释放。
- 已装但暂时关闭的芯片仍占用容量，避免战斗中开关芯片造成可用量反复变化；成对占据主副槽的同一枚芯片只计算一次。
- 装配阶段的 `Reserved（预计占用）`继续用于显示和预览，真正的可用量在战斗体开启、完成正式锁定后减少。

已确认的激活与使用费用边界：

- 芯片每次从未激活转为激活时，由芯片本体的 `ChipTrionConfig.ActivationCost（芯片激活费用）`一次性扣费；现有运行机制保持不变。
- 表达结果实际执行武器攻击、Ability（技能）等动作时，继续由表达条目的 `UseCost（使用费用）`及其具体运行宿主负责扣费；`MinimumRequired（最低要求）`继续只作门槛检查。
- 表达条目的 `ActivationCost（表达激活费用）`没有运行消费者，正式 XML 也未使用，属于早期通用参数传递留下的无效空管道。
- 删除表达配置、表达运行快照、公开发布快照及组合表达继承中的该字段，不改动芯片激活扣费和现有表达使用扣费。
- 组合定义顶层自己的 `ComboTrionConfig.ActivationCost / CapacityCost（组合激活费用/容量占用）`不属于本次表达条目清理范围，另行审查。

本轮实施步骤：

1. 先新增边界测试，要求表达系统及组合表达继承不再声明或传递 `ActivationCost`，同时要求芯片激活服务仍按芯片本体费用调用 Trion 扣费。
2. 运行该测试并确认它因现有表达字段残留而失败。
3. 只删除 `ExpressionSourceTrionConfig`、`ExpressionSourceTrionSnapshot`、公开结果快照、收集/发布构建器及 `ComboExpressionTrionResolutionConfig`中的表达级激活费用链。
4. 运行边界测试、相关表达/组合/Trion 测试、三个程序集构建、Core 依赖门禁、XML 解析与全量脚本回归。
5. 更新计划、工作日志和提交号；如出现既有基线失败，必须与本次新增失败分开记录。

已确认的 Combo（组合结果）费用边界：

- Combo 不是实际装入触发体的第三枚芯片，不独立占用容量，也没有独立激活状态；两枚来源芯片继续各自承担容量占用和激活费用。
- 完整删除 Combo 顶层 `Trion`、`ComboTrionConfig`、`ComboTrionContract`、顶层容量/激活费用求值及两个候选样例中的无效数字。

### 07A：正式化芯片形态底层系统

目的：

- 让芯片定义中的多个形态成为真正可选择、可保存、可恢复的运行状态，而不是只存在于配置解释器中的未接线数据。

最低范围：

- 首次建立有效形态状态时选择 `Expression.DefaultModeKey（默认形态键）`。
- 保存并读取当前形态；无效形态安全回到默认形态。
- 提供中性的玩家形态切换入口，并在切换后重新发布该芯片的正式表达。
- 共享基础表达在切换前后保持稳定，避免共用 Ability（技能）的冷却等状态被无故重置。

已确认规则：

- 当前形态只属于芯片本次正式启用期间的运行状态，不属于未启用槽位或仓库中芯片物品的永久记忆。
- 当前形态保存在正式启用芯片的根 `TriggerSlotState（触发体槽位状态）`中；成对主副槽只由根槽保存一份，镜像槽统一读取根槽，不建立触发体额外字典。
- 未启用芯片没有当前形态，也不允许预先选择形态；启用正式完成时才建立 `Expression.DefaultModeKey（默认形态键）`。
- 停用过程中旧形态继续随正式激活态有效，停用正式完成后清除；无论关闭前处于什么形态，下次启用都重新从默认形态开始。
- 芯片卸下时同样不保留形态；以后重新装入同一把或另一把触发体时，不恢复历史形态。
- 不为芯片物品增加跨装载、跨触发体保存形态的额外组件或状态。
- 形态切换立即完成；不新增切换耗时字段、过渡阶段、进度条或独立切换状态机，也不借用芯片启用/停用延迟。
- Core 负责当前形态真值、可选形态读取、指定/下一形态切换命令、有效性检查、存读档、无效回退和表达重新发布，不认识具体芯片业务。
- Content 在启动时只注册一个通用形态 `Gizmo Provider（按钮提供器）`，不为每枚芯片编写 C# 注册代码；具体芯片通过 XML 形态定义自动接入。
- 玩家形态切换入口采用装备状态下新增的独立 `Gizmo（游戏操作按钮）`，不使用 Trion 面板槽位作为唯一入口；每枚正式启用的多形态芯片显示一个按钮，左键切换到定义顺序中的下一形态，右键打开完整形态列表。
- 左键和右键菜单都严格采用 XML `Modes（形态列表）`顺序，最后一项继续左键时循环回第一项；右键菜单明确标出当前形态。
- 每枚物理上真实存在的启用中多形态芯片只生成一个按钮，成对主副槽的镜像不重复生成；多枚按钮按主槽、副槽、特殊槽及槽位编号稳定排列。
- Gizmo 展示芯片当前形态的名称和专用图标，缺少专用图标时回退芯片图标；提示文字说明左键将切换到的下一形态，切换完成后按钮立即更新。
- Content 形态按钮复用现有 `TriggerLoadoutPanelExtension（触发体玩家芯片控制许可）`；没有该许可的触发体不显示通用玩家形态按钮，但具体内容仍可通过 Core 正式命令实现自己的受控入口。
- 每个形态在 XML 中声明必填的稳定 `ModeKey（形态键）`、必填的 `DisplayLabel（玩家显示名称）`和选填的 `GizmoIconTexPath（按钮图标路径）`；缺少显示名称使多形态定义无效，不把内部键暴露给玩家；没有专用图标时回退芯片物品图标。
- 形态切换动作本身不消耗 Trion，也不新增形态切换费用字段；切换后生效的武器、Ability、Hediff、被动和持续消耗继续遵循各自已有费用规则。

- 暂定允许形态即时切换并中断旧形态尚未完成的攻击；已经实际扣除的费用不返还。该规则必须保留为后续实测复查点，连续射击或连段若显得突兀，再单独设计“已开始动作自然收尾后切换”，本项不提前加入等待队列。
- 形态切换采用原子提交：先校验启用状态、多形态契约和目标形态，再暂时写入并重建正式投影；成功才提交，失败或异常恢复旧形态并保留旧投影。

### 07B：正式化使用者 Trion 释放力门槛

目的：

- 把当前只被保存和显示的芯片临时功率需求改名并接成真正生效的 Trion 释放力门槛，同时与 Trion 总量、容量占用和具体动作消耗保持清楚分工。

最低范围：

- 使用者拥有一个原版 `StatDef（属性定义）`形式的 `TrionIntensity（Trion释放力）`。
- 芯片临时字段 `PowerRequirement（功率要求）`不兼容改名为 `TrionIntensityRequirement（释放力要求）`。
- 每枚芯片独立比较自己的释放力要求，不累加为总释放力预算。
- 释放力不足不影响芯片装载、战斗体生成或其它已满足条件的芯片；玩家请求启用该芯片时直接拒绝激活并说明原因，芯片保持未启用。
- Trion释放力与永久潜在容量数值独立；现有检测显示名“Trion潜质”修正为“Trion容量潜质”，不把容量直接换算成释放力。
- 每个角色拥有生成一次并永久保存的先天释放力底数；Trion腺体只让角色实际使用该底数，不负责重新生成。
- 芯片比较原版 `BDP_TrionIntensity`最终属性值；未来后天成长、状态削弱或临时增强只通过原版属性修正最终值，不覆盖先天底数。
- 未完成检测时不向玩家揭示容量潜质和释放力；现有一次 Trion 潜质检测同时揭示两项相互独立的先天结果，不增加第二套检测流程。
- 植入有效Trion腺体后，“Trion容量潜质”仍永久保留在角色面板，不因精确容量已经可读而隐藏；“Trion释放力”转由正式原版属性显示和参与芯片判断。
- “Trion容量潜质”继续显示模糊档位；检测后的“Trion释放力”和芯片“释放力要求”显示可直接比较的精确整数，不使用小数，也不另建释放力模糊档位系统。
- 检测总流程正式命名为 `TrionTalentAssessment（Trion天赋检测）`；它只作为容量潜质和释放力两项先天条件的总概念，不建立名为“Trion天赋”的总数值。
- 容量分支统一使用 `TrionCapacityPotential（Trion容量潜质）`，释放力分支统一使用 `TrionIntensity（Trion释放力）`；菜单、工作、完成提示、内部状态、服务、结果、容量档位和分布类型同步改名。
- 检测完成提示固定同时显示“Trion容量潜质：档位”和“Trion释放力：整数”；旧含糊`TrionAssessment / TrionPotential / PotentialAssessed`命名及相关旧存档键、旧DefName不兼容删除。
- 正式准入比较采用 `TrionIntensity >= TrionIntensityRequirement`；达到要求即可使用，只有低于要求时判定释放力不足。
- Core建立中性的芯片激活条件检查边界，不把启用准入硬编码成只有Trion释放力；后续可以按正式配置加入角色技能等级等其它条件。
- 所有激活条件都在芯片真正进入启用流程前检查；任一条件失败就拒绝本次激活并返回对应玩家提示，不建立“已激活但效果为空”的中间状态。
- 激活请求当下立即完整检查条件；芯片正式启用后，每60 tick按角色错峰复查一次，仅遍历启用中、具有条件的真实根芯片，遇到失败立即进入关闭流程。
- 不做每tick全量扫描，也不为属性、技能、伤势、基因或其它模组修正到处增加变化补丁；条件恢复后不自动重开芯片。
- 芯片配置新增统一的 `ActivationRequirements（激活条件）`有序列表；释放力、技能等级和未来条件都通过同一入口检查，不把条件散落为芯片主配置固定字段。
- Core现在实现通用条件父类型、统一检查结果、统一有序检查服务和Content只读快照，并提供`TrionIntensityRequirement`与`SkillLevelRequirement`两种内置中性条件；Content以后可以继承共同父类型增加业务条件，依赖仍严格保持Content单向指向Core。
- `TrionIntensityRequirement（释放力要求）`从旧`Trion`费用区移入激活条件列表；`Trion`区只保留容量占用、激活费用等资源参数。
- `SkillLevelRequirement`要求有效原版SkillDef和1～20整数最低等级，采用当前等级大于或等于要求；同一芯片允许多个不同技能但禁止重复同一技能，只比较等级，不承担工作禁用或暴力能力等其它语义。
- 当前没有任何真实芯片配置技能条件，不虚构业务芯片或占位XML；未被XML使用的标准条件不实例化、不参与持续复查。首个真实用例出现时只需增加配置。
- 激活条件检查位于互斥关闭、启用延迟和激活费用之前，并且检查本身只读、无副作用；任一条件失败时不扣费、不进入延迟、不关闭互斥芯片、不改变槽位状态，只提示原因。
- 手动激活失败时一次列出当前全部未满足条件，严格采用XML条件顺序，不采用修复一项后才逐次暴露下一项的提示方式。
- 启用中条件失效触发关闭时同样只提示一次；芯片进入关闭流程后不再作为启用中目标重复检查，禁止每60tick重复刷消息。
- 启用中持续条件失效后复用芯片原有正常关闭流程和 `DeactivationDelayTicks（停用延迟）`，不建立立即强制撤下的第二路径。
- 条件在正常关闭途中恢复也不取消关闭、不自动重新启用；停用正式完成前的表达存续沿用现有停用语义。
- 玩家点击启用时通过的条件结果作为本次启用事务的准入许可；后续互斥让位等待和芯片启用延迟期间不重复否决本次事务，也不建立旧芯片自动回滚。
- 芯片正式启用后才进入每60tick持续复查；若条件在启用等待期间已经失效，正式启用后由正常持续检查发现并关闭。
- 芯片静态详情增加唯一“激活条件”分区，按XML顺序显示声明要求；没有条件时不显示该分区。
- 角色芯片面板在同一“激活条件”分区实时显示当前值与要求，满足项正常或绿色、不满足项红色；不在槽位周围继续堆叠零散状态图标。
- 任一条件不足时启用入口保持可见但不可用，悬停列出全部失败原因；Core正式启用命令仍即时复查，防止其它界面或业务入口绕过。
- 每张正式芯片必须且只能声明一项 `TrionIntensityRequirement（释放力要求）`；最低值必须是正整数，缺失、重复、零、负数或小数都使芯片定义无效。
- 技能等级等其它激活条件保持选填；现有候选芯片的临时 `PowerRequirement=1`等义迁移为最低释放力1，不保留旧字段兼容。

- 原版StatDef修正后的原始释放力统一向下取整并钳制到不低于0；界面、失败提示和准入比较全部读取同一个有效整数，不允许显示值与判断值分裂。
