# BDP玩家日志设计稿

日期：2026-10-03。

状态：讨论形成的设计稿；尚未实施。实现入口与最小改动清单留待实施计划确认。

## 1. 用途与范围

帮助玩家回看角色参与的战斗：谁使用什么进行了什么行动，对谁产生了什么直接结果，以及哪些重要战斗节点已经发生。

保留原版角色日志界面、人物关联、时间顺序、战斗分组、存档和简略/全部显示机制。敌我遵循同一规则，同一事件可关联双方角色；当前角色的日志只展示与其有关的事件。

记录范围为攻击行动、直接交互结果和明确声明的重要事件。普通效果持续、数值或层数变化、自然到期不自动记录。日志不承担持续状态追踪职责。

## 2. 方案选择

采用“原版攻击记录＋少量共用句式＋明确声明的重要事件”。

- 全部逐项定制：每新增一件武器或一种能力都要维护专属整句，难以自然复用。
- 自动记录所有变化：容易形成状态流水，增加噪声和不必要的设施。
- 推荐方案：普通内容继承原版规则；只为原版不能准确表达的动作、直接结果和重要事件补充文法。

## 3. 一条记录的边界

### 攻击行动

- 沿用原版一次开火或近战行动的粒度。连发不额外逐弹生成开火条目。
- 玩家点击、预备瞄准、条件不足和未进入实际行动的尝试，默认不增加BDP日志。
- 攻击已经实际开始后发生的重要中断，可以由具体内容明确声明记录；不记录每次自动重试或失败检查。
- 原版已有的行动条目优先复用，不为同一行动再添加BDP重复条目。

### 直接交互结果

- 按原版实际命中记录的粒度记录。行动与命中发生在不同时间，可以分别存在。
- 同一次交互的伤害与必要特殊结果优先在对应结果条目内表达，不把同一事实再拆一条。
- 飞行转弯、追踪修正、穿过路径节点等中间过程不记日志。
- 多目标攻击按实际受影响的对象分别关联结果，不因同源或同一时刻而合并成一个目标，也不据此去重真实多次命中。
- 后续独立伤害沿用其实际发生时的原版记录；普通效果后续变化不追加条目。

### 重要事件

- 由内容明确声明事件及确认发生的时机；不会因为出现某个状态变化就自动生成。
- 保留战斗体启动成功、主动解除完成、开始崩解、紧急脱离成功。
- 和平时期的启动与主动解除也记录。使用原版战斗日志容器时，这些事件仍受原版战斗分组管理；不为此另建历史系统。
- 崩解与紧急脱离是两个实际阶段，可以各记一次；不额外重复记录崩解结束。
- 强制解除不表述为主动解除；战斗体崩解不表述为人物死亡，也不使用死亡图标。

## 4. 共用文案规则

### 句子成分

行动句使用“行动者＋动作＋来源＋目标”；结果句使用“来源或攻击者＋交互结果＋目标＋必要部位或直接后果”。没有的成分省略，保留完整句式。

来源分清三种用途：行动使用的武器或能力名称、命中的弹体或攻击名称、实际抵挡的防护来源。只在对应事实已知时使用，不把弹体名强行当武器名，也不把装备中的能力当作已发生结果。

正式武装、组合技等来源按行动发生时确定；延迟命中沿用当时来源，不能读取命中时新选中的芯片替换。必要本地化身份使用定义引用或语言键与参数保存，不只保存已翻译的整句。

### 句式示意

以下是文法族的示意，正式玩家文案必须放入语言包。实施时沿用适用的原版随机措辞，不要求逐字替换原版文本。

| 用途 | 示意 |
| --- | --- |
| 开火 | 甲用〔来源〕向乙开火。 |
| 近战 | 甲用〔来源〕挥砍乙。 |
| 能力使用 | 甲对乙使用了〔能力〕。 |
| 命中 | 甲的〔攻击〕击中了乙的〔部位〕。 |
| 未命中 | 甲的〔攻击〕未击中乙。 |
| 抵挡 | 乙的〔防护来源〕挡住了甲的〔攻击〕。 |
| 特殊直接结果 | 甲的〔攻击〕击中了乙，〔实际结果〕。 |
| 重要事件 | 甲〔动作〕了〔对象〕。 |

近战可以采用挥砍、刺击、打击等少量共用动作。实际内容不适合现有动作时再补充，避免为每个武器扩展一种动作类别。

普通伤害、偏转、部位破坏和死亡等结果优先沿用原版。非伤害攻击可以采用简短的直接结果句；结果相同的不同能力共用文法。

### 事实与措辞

- 第三人称事实短句，敌我标准一致。打开不同角色的日志不增加情绪或推测。
- 不使用未经游戏结果确认的精准、猛烈、压制成功等评价。
- 零伤害不等于未命中。接触、伤害处理、伤害抵挡和特殊效果是否实际生效分别判断。
- 部分伤害被挡住不写成整次攻击无效；只确认伤害被挡住时，文案明确限定为伤害。
- 效果执行成功或存在某项能力不等于目标已经发生相应变化；只使用对应交互已有的确认结果。
- 特殊结果只补玩家理解此次交互所需的简短事实，不列效果清单、逐项数值或内部参数。
- 紧急脱离只在实际移动成功后记录，不推断落点安全，也不在未确认时写返回信标。
- 已确认原因可以用于关键事件句。未知原因使用通用句，不显示内部原因码。

### 缺失信息

来源未知可写“甲向乙开火”；目标未知可写“甲用〔来源〕开火”；二者都未知可写“甲开火”。只在相应成分确实缺失时使用。

实际抵挡已经确认但防护来源未知时，可以省略防护名称；不得猜测是哪种护盾。必要文本缺失必须有完整的通用句式，不能仅捕获语法异常后返回空白。

## 5. 新内容如何自然适用

| 新内容 | 默认接入方式 | 何时需要补充 |
| --- | --- | --- |
| 普通枪械或弹体 | 原版开火、命中和伤害记录 | 原版来源名称不能代表正式武装时 |
| 普通近战武器 | 原版近战与伤害记录 | 需要选择不同共用动作时 |
| 新能力 | 适用的原版能力或攻击条目 | 原版无法表达实际行动时 |
| 非伤害攻击 | 原版行动记录，适用的交互结果句 | 需要表达已确认的直接后果时 |
| 多目标攻击 | 每个实际目标的已有结果记录 | 不额外建立全体效果汇总 |
| 新重要机制 | 内容声明事件和实际完成点 | 确有独立回看价值时 |

默认不必为每项内容写专属句子。内容只在必要时提供正式来源身份、共用动作选择、直接结果文法或重要事件声明。只有出现不能准确表达的新交互方式，才扩展共用规则。

日志中不按芯片、武器或能力名称写逐项判断。接入优先落在既有的共用攻击/交互完成点，新机制增加必要适配，不强迫所有业务经过新的通用事件框架。

## 6. 原版兼容与职责

- 继续使用原版记录容器和显示界面，不建立独立历史仓库，不恢复全局整句覆盖。
- 优先原版条目与文法；确有缺口时，使用仅限BDP的条目扩展或文法适配。
- 普通攻击沿用原版简略显示规则。重要事件默认保留在简略视图；“显示全部”不产生新记录。
- 一条结果关联其实际参与人物，不按阵营复制两份。重复回调不能重复提交同一事实；同源、同目标或同一时刻不足以证明两次结果重复。
- Core.dll（基础程序集）只提供已经需要的中性共性事实与必要接入支持，不承担战斗体事件、芯片名称判断或玩家文案政策。
- Content.dll（正式内容程序集）承载BDP文法、重要事件以及必要内容适配。Development.dll（开发程序集）不参与正式玩家日志运行。
- 不为日志增加全量效果状态观察、通用反应引擎或持续变化缓冲。

## 7. 设计覆盖检查

以下是规则推演，不代表已运行游戏验证。

- 普通枪械：沿用开火、实际命中与伤害部位，无专属整句需求。
- 非伤害附着：描述该次确认的附着或直接负重结果，不跟踪后续维持与消退。
- 护盾交互：按实际阻挡范围表述，不能把伤害被吸收等同于所有附带效果被阻挡。
- 多目标攻击：不同目标保留自己的结果，不用单一行动标识去重。
- 延迟命中期间切换武装：来源仍是发起该次攻击时的武装。
- 战斗体崩解后脱离：两条独立重要事件，不误写人物死亡。
- 目标或来源缺失：进入对应完整通用句式。
- 尚未实装的新武器：只要沿用既有攻击机制，默认获得原版日志覆盖。

## 8. 实施计划需要解决的最小事项

1. 对照当前共用攻击入口与原版文法输入，确定正式来源和动作词的最小适配方式。原版开火读取武器定义的首个动作配置，不能假定动态动作配置自动进入日志。
2. 修正BDP动态武器缺少原版武器文法输入时的生成问题，保证缺失信息有完整句式；不以捕获异常替代正确输入。
3. 确认特殊直接结果可以在哪个既有完成点取得。仅需要记录的机制提供必要结果，不升级为全部效果状态协议。
4. 为战斗体关键节点接入原版事件条目与语言文法，避免默认死亡图标。
5. 列出语言键、存档所需最小事实和仅限BDP的接入范围，实施前确认清单。

实际实现及游戏验证尚未执行。此前错误分析作为原版文法输入问题的依据，不把其他启动警告混入本次日志设计。
