# BDP 角色条件共享与 Combo 使用门槛设计

## 一、背景与目标

事项 07B 已经让芯片通过 `ActivationRequirements（激活条件）`检查 Trion 释放力和技能等级。本次在游戏实测阶段补正四项需求：

1. 完成 Trion 天赋检测后，角色信息页中的“Trion释放力”条目始终保留；植入有效腺体后不再退出。
2. 所有玩家可见的 Trion 释放力数值统一增加“级”单位，例如 `4级`。
3. 候选库“测试旋空芯片”的启用门槛改为：Trion释放力4级、格斗10级、射击6级，三项必须同时满足。
4. Combo（组合技）可以声明自己的使用条件；条件不足时整个 Combo 暂时不可用，但按钮保留并置灰，自动状态和被动效果不生效，并向玩家给出一次性黄色提示。

本次不为任何现有 Combo 擅自填写具体门槛。Combo 通用能力先完整建立，首个具体 Combo 门槛数值以后再单独确认。

## 二、设计原则

- Core（核心程序集）只保留一套“角色是否满足一组条件”的中性底层。
- 芯片和 Combo 不共用业务时机：
  - 芯片在激活前检查，激活后每60 tick（游戏刻）持续复查。
  - Combo 在成立、显示按钮和实际使用时检查，不满足时不关闭来源芯片。
- 条件求值只读、无副作用；失败不扣 Trion、不进入冷却、不开始动作。
- Content（内容程序集）只消费 Core 的只读快照，不重新实现释放力或技能判断。
- 不兼容旧的芯片专属条件底层内部类型名；本次直接整理为中性名称。
- 不增加每 tick（游戏刻）全量检查。自动效果的变化最多延迟60 tick刷新。

## 三、中性角色条件底层

### 3.1 通用结构

把现有芯片专属类型提升到 `BDP.Core.Requirements（BDP核心.条件）`：

```text
PawnRequirement
├─ TrionIntensityRequirement
└─ SkillLevelRequirement

PawnRequirementSnapshot
PawnRequirementCheckResult
PawnRequirementEvaluator
PawnRequirementListValidator
```

职责：

- `PawnRequirement（角色条件）`：具体条件的共同父类型。
- `PawnRequirementSnapshot（角色条件快照）`：显示名称、当前值、要求值、是否满足、失败原因。
- `PawnRequirementCheckResult（角色条件检查结果）`：按 XML（可扩展标记语言）顺序保存全部条件和全部失败项。
- `PawnRequirementEvaluator（角色条件求值器）`：统一执行静态说明和角色实时检查。
- `PawnRequirementListValidator（角色条件列表校验器）`：统一拒绝空项、非法条件、重复释放力条件和重复技能条件。

芯片仍由薄适配器解析自己的配置：

```text
ChipActivationRequirementService
    └─ 读取 ChipDefinitionConfig.ActivationRequirements
       再交给 PawnRequirementEvaluator
```

Combo 使用另一层薄适配器：

```text
ComboUseRequirementService
    └─ 读取 ComboDef.UseRequirements
       再交给 PawnRequirementEvaluator
```

两层适配器只负责“从哪里取得条件”，不复制条件判断。

### 3.2 两种配置入口

芯片继续使用激活语义：

```xml
<ActivationRequirements>
  <li Class="BDP.Core.Requirements.TrionIntensityRequirement">
    <Minimum>4</Minimum>
  </li>
</ActivationRequirements>
```

Combo 使用使用语义：

```xml
<UseRequirements>
  <li Class="BDP.Core.Requirements.TrionIntensityRequirement">
    <Minimum>6</Minimum>
  </li>
  <li Class="BDP.Core.Requirements.SkillLevelRequirement">
    <Skill>Melee</Skill>
    <MinimumLevel>12</MinimumLevel>
  </li>
</UseRequirements>
```

`UseRequirements（使用条件）`属于 Combo 顶层，与 `chipA / chipB / Expression`同级。列表可选；不填写时保持现有 Combo 行为。

## 四、Trion 释放力显示补正

### 4.1 角色信息页

只有完成 Trion 天赋检测后才显示容量潜质与释放力，这一保密边界不变。

- 未植入有效腺体：显示永久先天释放力。
- 已植入有效腺体：显示经过原版 `StatDef（属性定义）`修正并统一向下取整后的当前有效释放力。
- 植入腺体不再移除“Trion释放力”信息条目。

### 4.2 “级”单位

Core 提供唯一 `TrionIntensityUtility.FormatLevel`格式化入口。以下玩家可见位置统一使用它：

- 角色信息页。
- Trion 天赋检测完成提示。
- 芯片和 Combo 静态条件说明。
- 槽位实时条件。
- 芯片激活失败提示。
- Combo 按钮置灰原因和一次性黄色消息。
- 原版 `BDP_TrionIntensity`属性显示使用 `<formatString>{0}级</formatString>`。

内部比较和存档仍保存整数，不把“级”写进数值字段。

## 五、测试旋空芯片配置

只修改候选库 `BDP_TestChipSenku（测试旋空芯片）`，不修改弧月芯片：

```xml
<ActivationRequirements>
  <!-- 旋空需要至少4级 Trion释放力。 -->
  <li Class="BDP.Core.Requirements.TrionIntensityRequirement">
    <Minimum>4</Minimum>
  </li>
  <!-- 旋空需要至少10级格斗。 -->
  <li Class="BDP.Core.Requirements.SkillLevelRequirement">
    <Skill>Melee</Skill>
    <MinimumLevel>10</MinimumLevel>
  </li>
  <!-- 旋空需要至少6级射击。 -->
  <li Class="BDP.Core.Requirements.SkillLevelRequirement">
    <Skill>Shooting</Skill>
    <MinimumLevel>6</MinimumLevel>
  </li>
</ActivationRequirements>
```

三项采用 XML 顺序检查和显示，必须全部满足才能激活旋空芯片。

## 六、Combo 使用条件运行语义

### 6.1 成立与可用分离

两枚来源芯片正常启用且匹配 `ComboDef（组合技定义）`时，Combo 仍然成立。随后独立检查 `UseRequirements`：

- 满足：Combo 结果正常使用。
- 不满足：Combo 结果保留，但标记为“使用受阻”。

不能复用 `FormalExpressionResult.IsAvailable（表达结果是否存在）`表示门槛失败，因为现有投影器会据此删除按钮。正式结果新增独立的角色条件检查结果，使“结果存在”和“当前能否使用”保持分离。

### 6.2 按钮型结果

Ability（能力）和手动 Verb（动作）按钮：

- 条件不足时仍生成。
- 按钮置灰。
- 悬停按 XML 顺序列出全部未满足条件。
- 点击、快捷键或其它入口绕过按钮时，在正式执行前重新检查。
- 失败时不扣 Trion、不进入冷却、不开始瞄准或攻击。

### 6.3 自动结果

Combo 产生 Hediff（状态）、Passive（被动）或其它自动结果时：

- 条件不足期间不应用或不发布自动效果。
- 条件恢复后最多60 tick内重新发布。
- 条件再次跌破后最多60 tick内撤下自动效果。
- 来源芯片保持启用，不触发芯片关闭。

### 6.4 低频刷新

复用 Trigger（触发体）运行协调器的60 tick错峰节奏：

- 非到期 tick 立即返回。
- 只检查当前已成立且声明了 `UseRequirements`的 Combo。
- 新结果与当前已发布结果的满足状态一致时不重建投影。
- 满足状态发生变化时只把现有投影标为 dirty（待重建），复用原发布链。

不建立第二套表达发布状态机。

## 七、一次性黄色提示

Trigger 运行协调器为每个角色和 Combo 维护当前受阻集合：

- Combo 第一次进入受阻状态时，发送一次 `CautionInput（黄色注意消息）`。
- 消息格式：

```text
组合技「旋空弧月」暂时无法使用：
Trion释放力：当前3级，需要4级
格斗：当前8，需要10
```

- 所有失败项一次列全，顺序与 XML 一致。
- 条件持续不足时不重复提示。
- 条件恢复或 Combo 来源组合消失时清除受阻记录。
- 以后再次进入受阻状态时允许再次提示一次。
- 条件恢复时不发送成功消息。
- 受阻集合只属于运行时提示状态，不写入存档；读档后重新形成受阻 Combo 时允许重新提示一次。

## 八、程序集与数据边界

- `PawnRequirement`及内置条件全部属于 Core。
- Content 不新增条件判断。
- DevHarness（候选测试模组）只修改旋空芯片 XML 和对应回归测试。
- Core 继续不依赖 Content、DevHarness 或未来其它本模组 DLL（动态链接库）。
- 当前候选 Combo 不填写 `UseRequirements`，避免擅自决定具体业务门槛。

## 九、验证范围

自动验证至少覆盖：

1. 检测前不显示释放力，检测后无论是否有腺体都显示。
2. 腺体前显示先天值，腺体后显示当前有效值。
3. 所有 Trion 释放力玩家文本带“级”。
4. 旋空芯片恰好配置释放力4、格斗10、射击6三项条件。
5. 芯片与 Combo 使用同一 `PawnRequirement`底层。
6. Combo 条件不足时结果存在、按钮置灰、自动效果不发布。
7. 正式执行入口重新检查，失败不扣费、不进入冷却。
8. 一次受阻只提示一次；恢复或来源消失后再次受阻可再次提示。
9. 60 tick错峰复查只在满足状态改变时刷新投影。
10. 三个程序集0警告0错误，Core依赖门禁通过。
11. 主模组和候选模组当前XML全部可解析。
12. 全量自动测试新增失败为0。

游戏内实测重点：

- 植入腺体后角色信息页仍显示“Trion释放力：N级”。
- 旋空芯片三项门槛分别正确显示和拒绝。
- 未来给具体 Combo 配置门槛后，按钮置灰、悬停原因与一次性黄色提示符合设计。
