# BDP Trion 天赋与芯片激活条件设计

日期：2026-07-30

所属事项：07B“正式化使用者 Trion 释放力门槛”

前置事项：07“正式化芯片 Def（定义）公共基线”、07A“正式化芯片形态底层系统”

## 一、目标

建立两项彼此独立、可长期保存的角色 Trion 天赋：

- `TrionCapacityPotential（Trion容量潜质）`：在精确容量未知时，给玩家一个模糊容量档位。
- `TrionIntensity（Trion释放力）`：表示角色能够驱动多高门槛芯片的能力，以精确整数显示。

同时把芯片原有临时 `PowerRequirement（功率要求）`改造成统一激活条件系统中的正式 `TrionIntensityRequirement（释放力要求）`，并补齐可复用的技能等级条件。

本项只建立单枚芯片各自的准入门槛，不建立多芯片共享的释放力总额、分摊、优先级或自动断电系统。

## 二、概念与正式命名

### 2.1 总检测流程

一次检测正式命名为：

- 中文：`Trion天赋检测`
- 英文标识：`TrionTalentAssessment`

它是检测行为和结果容器，不是一项名为“Trion天赋”的总数值。检测下分两项结果：

- `TrionCapacityPotential（Trion容量潜质）`
- `TrionIntensity（Trion释放力）`

玩家结果示例：

```text
Trion天赋检测完成
Trion容量潜质：优秀
Trion释放力：4
```

内部状态、服务、结果、资格判断、容量档位和容量分布同步采用对应名称，例如：

- `TrionTalentAssessmentService`
- `TrionTalentAssessmentResult`
- `TrionTalentAssessmentEligibility`
- `TrionTalentAssessmentCompleted`
- `TrionCapacityPotentialBandDef`
- `TrionCapacityPotentialBandResolver`
- `TrionCapacityPotentialDistributionDef`

旧的 `TrionAssessment`、`TrionPotential`、`PotentialAssessed`、旧存档键和旧 DefName（定义名称）不做兼容，直接删除。

### 2.2 释放力

角色属性：

- 中文：`Trion释放力`
- 英文标识：`TrionIntensity`
- 原版属性定义：`BDP_TrionIntensity`

芯片条件：

- 中文：`释放力要求`
- 英文标识：`TrionIntensityRequirement`

旧 `PowerRequirement`不保留兼容。

容量潜质与释放力都可视为先天 Trion 天赋，但数值彼此独立；本项不通过容量换算释放力，也不预设概率关联。

## 三、角色数据与生成

### 3.1 先天底数和最终属性

每名人形 Pawn（角色）在 `CompTrion`中保存一个永久的先天释放力底数。有效 Trion 腺体只让该数值可被正式使用，不重新生成它。

实际判断统一读取原版 `StatDef（属性定义）` `BDP_TrionIntensity`的最终值：

```text
先天释放力底数
    + 原版属性修正
    = 原始最终值
    → 向下取整
    → 钳制到不低于 0
    = 游戏实际使用的释放力整数
```

界面显示、失败提示和准入判断必须读取同一个有效整数。BDP 正式内容原则上只使用整数加减；其它模组提供小数修正时，必须完整达到下一整数才提升一级。

未来的后天成长、Hediff（状态）、基因或临时增强只修正最终属性，不覆盖先天底数。常规先天生成上限是 10，但系统最终值和特殊芯片要求允许超过 10。

### 3.2 生成对象

- 所有人形角色无论阵营、年龄或是否已经具有 Trion 腺体，都具有独立先天释放力。
- 其它模组的人形种族自动适用。
- 动物和机械体不生成先天释放力，有效值按 0 处理，不显示也不参加天赋检测。

### 3.3 惰性初始化

不在开档时扫描全部世界角色。检测、腺体属性读取或芯片条件检查第一次正式需要数据时：

1. 统一入口判断是否已经初始化。
2. 未初始化时独立随机生成一次。
3. 立即保存初始化标记和值。
4. 此后永久复用，任何消费者都不得自行重抽。

容量潜质和释放力即使在同一次检测中初始化，也分别按各自分布独立抽取。

### 3.4 独立权重

释放力先天底数为 1～10 的整数，权重由独立 Def（定义）配置：

| 释放力 | 权重 |
|---:|---:|
| 1 | 5% |
| 2 | 10% |
| 3 | 20% |
| 4 | 25% |
| 5 | 20% |
| 6 | 10% |
| 7 | 5% |
| 8 | 3% |
| 9 | 1.5% |
| 10 | 0.5% |

该分布使 3～5 合计占 65%，8～10 合计占 5%。对应最低要求的自然达标率约为：

| 最低要求 | 达标率 |
|---:|---:|
| 1 | 100% |
| 4 | 65% |
| 5 | 40% |
| 6 | 20% |
| 7 | 10% |
| 8 | 5% |
| 9 | 2% |
| 10 | 0.5% |

## 四、检测与角色面板

检测前，玩家看不到容量潜质和释放力。

同一次 `TrionTalentAssessment（Trion天赋检测）`完成后：

- 容量潜质显示模糊档位。
- 释放力显示精确整数。

有效 Trion 腺体植入后：

- 精确 Trion 容量继续按现有规则可读。
- “Trion容量潜质”仍永久保留在角色面板，不因精确容量已经可读而隐藏。
- “Trion释放力”通过正式原版属性显示当前有效整数。

因此实施时必须修正 `CompTrion.SpecialDisplayStats`当前在腺体生效后隐藏容量潜质的行为。

## 五、统一激活条件配置

### 5.1 XML 结构

芯片新增唯一有序入口：

```xml
<ActivationRequirements>
  <li Class="BDP.Core.Chips.Requirements.TrionIntensityRequirement">
    <Minimum>5</Minimum>
  </li>
  <li Class="BDP.Core.Chips.Requirements.SkillLevelRequirement">
    <Skill>Shooting</Skill>
    <MinimumLevel>8</MinimumLevel>
  </li>
</ActivationRequirements>
```

`TrionIntensityRequirement`从 `<Trion>`费用区移出。`<Trion>`只保留容量占用、激活费用等资源参数。

### 5.2 必填与校验

每张正式芯片必须且只能声明一项 `TrionIntensityRequirement`：

- `Minimum`必须是正整数。
- 缺失、重复、0、负数或小数都使芯片定义无效。
- 现有候选芯片的 `PowerRequirement=1`等义迁移为最低释放力 1。

其它条件保持选填。

`SkillLevelRequirement（技能等级要求）`规则：

- `Skill`必须引用有效原版 `SkillDef（技能定义）`。
- `MinimumLevel`必须是 1～20 的整数。
- 当前技能等级大于或等于最低等级时满足。
- 同一芯片可以要求多个不同技能，不得重复要求同一技能。
- 角色缺少技能追踪器或对应技能记录时不满足。
- 只比较数值等级，不承担工作禁用或暴力能力等额外语义。

当前没有真实芯片需要技能门槛，因此只实现中性底层，不虚构业务芯片或占位 XML。

## 六、Core 与 Content 职责

### 6.1 Core

Core（核心程序集）负责：

- 抽象共同父类型 `ChipActivationRequirement（芯片激活条件）`。
- 标准条件 `TrionIntensityRequirement`与 `SkillLevelRequirement`。
- 统一结果模型：是否满足、条件名称、当前值文本、要求值文本、失败原因。
- 按 XML 顺序执行的统一检查服务。
- 提供给 Content 的公开只读快照。
- 芯片定义校验。
- 激活命令的最终复查。
- 启用后低频持续复查和正常关闭。
- 先天数据、原版属性和天赋检测。

Core 不依赖 Content，也不认识具体业务芯片。

### 6.2 Content

Content（内容程序集）只负责玩家界面：

- 读取 Core 的条件快照。
- 在现有玩家芯片面板展示实时比较结果。
- 根据 Core 结果禁用激活入口并显示失败原因。

未来具体业务条件可以在 Content 中继承 Core 共同父类型，但不得反向污染 Core。当前不增加注册表、反射扫描、公式脚本或任意字符串条件系统。

## 七、激活时序

### 7.1 玩家请求激活

在芯片已装载、当前未启用等基本有效性成立后，条件检查是第一个只读、无副作用的门：

```text
基本有效性
  → 检查全部激活条件
      ├─ 失败：拒绝，列出全部失败项
      └─ 通过：进入原有互斥让位、启用延迟和激活费用流程
```

条件失败时：

- 不进入启用延迟。
- 不扣除 Trion。
- 不关闭任何互斥芯片。
- 不改变槽位状态。
- 一次按 XML 顺序列出全部失败条件。

玩家点击时通过的检查结果，作为这一次激活事务的准入许可。后续互斥等待与启用延迟期间不重新否决，不建立复杂回滚。

若条件在等待期间失效，芯片可以按事务正常完成启用；正式启用后由持续检查发现并进入正常关闭。

### 7.2 启用后持续满足

正式启用后，条件必须继续满足：

- 每 60 tick（游戏刻）复查一次。
- 按角色或物件标识错峰。
- 只遍历启用中、具有条件的真实根芯片。
- 镜像槽不重复检查。
- 不做每 tick 全量扫描。
- 不在属性、技能、伤势、基因等变化处铺设大量补丁。
- 不产生无意义分配、日志或重复提示。

发现任一条件不满足时：

1. 一次按 XML 顺序提示全部失败项。
2. 复用芯片既有正常关闭流程。
3. 使用芯片已有 `DeactivationDelayTicks（停用延迟）`。
4. 关闭途中即使条件恢复，也不取消关闭、不自动重开。
5. 完成关闭后，玩家必须在条件重新满足时手动激活。

停用延迟内表达是否继续存在，完全沿用现有关闭语义，不建立第二条强制撤下路径。

## 八、玩家界面

条件只放在两个固定位置，避免零散堆叠。

### 8.1 芯片静态详情

增加“激活条件”分区：

- 按 XML 顺序显示声明要求。
- 没有条件时不显示分区。
- 这里只显示芯片本身的固定要求，不依赖当前角色。

### 8.2 角色芯片面板

在同名“激活条件”分区显示：

- 当前值与要求值的比较。
- 满足项使用正常色或绿色。
- 不满足项使用红色。
- 任一条件不足时，激活入口仍可见但不可用。
- 悬停一次列出全部失败原因。

界面只消费 Core 的只读快照，不自行复制判断。Core 正式命令仍会即时复查，防止其它界面或业务入口绕过。

## 九、验证边界

### 9.1 自动验证

自动测试必须覆盖：

- 释放力不足拒绝激活。
- 拒绝时不扣费、不进入延迟、不关闭冲突芯片、不改变槽位状态。
- 多项失败按 XML 顺序一次返回。
- 技能等级条件的满足、不满足和非法定义。
- 必填释放力条件、重复条件及非法数值校验。
- 启用后每 60 tick 错峰复查。
- 条件失效进入原有正常关闭流程。
- 先天释放力惰性生成、永久保存和存读档。
- Trion 天赋检测一次揭示两项结果。
- Core 与 Content 的严格单向依赖。

### 9.2 游戏内验证

本项只用真实内容验证：

- Trion 天赋检测同时显示容量潜质和释放力。
- 植入腺体后容量潜质仍保留。
- 释放力以整数属性显示。
- 现有最低要求 1 的芯片仍能正常激活。
- 两个“激活条件”界面分区排版清楚。

不增加假的高门槛芯片，也不擅自提高现有芯片门槛。第一个真实最低要求大于 1 或真实技能条件的芯片出现时，再补充游戏内拒绝和持续失效验证。

## 十、明确不做

- 不兼容旧字段、旧存档键、旧 DefName 或旧内部命名。
- 不建立 Trion 天赋总数值。
- 不把容量潜质换算为释放力。
- 不建立容量与释放力的概率关联。
- 不建立多芯片释放力总预算或分摊。
- 不添加自动重启芯片。
- 不添加假芯片、占位技能条件或测试性高门槛配置。
- 不提前调整任何具体芯片的正式门槛。
