# BDP 开发辅助程序集设计

## 1. 背景

`BorderDefenseProtocol.DevHarness` 已基本退役，但主模组仍需要承载以下开发期能力：

- 详细诊断日志与数据导出；
- 地图标记、诊断按钮和现场观察面板；
- 临时 Harmony 补丁；
- 功能原型；
- 只能在游戏内验证的测试入口。

这些能力不应继续混入 Core 或 Content，也不应成为正式业务的依赖。为此，在主模组工程内增加一个仅供开发环境加载的叶子程序集 `BDP.Development.dll`。

## 2. 目标

1. 为日志输出、临时原型和游戏内功能测试提供统一落点。
2. 保证 Core 和 Content 不依赖 Development。
3. 删除 Development 后，正式业务行为、XML 加载和存档读取完全不受影响。
4. 本地开发时随主模组自动加载，不再要求额外启用测试后置模组。
5. 正式发布前允许人工删除开发产物，并由自动检查防止遗漏。

## 3. 非目标

- Development 不是第三个正式业务层。
- Development 不承载正式内容、正式配置或正式存档状态。
- Development 不替代 PowerShell 自动测试。
- Development 不成为 Core 或 Content 的服务提供方。
- 本次不整体迁移旧 DevHarness；其中内容只在有明确价值时逐项重建。

## 4. 程序集关系

依赖方向固定为：

```text
BDP.Development.dll
        ├────→ BDP.Content.dll
        └────→ BDP.Core.dll

BDP.Content.dll ─────→ BDP.Core.dll
```

约束：

- Core 工程不得引用 Development。
- Content 工程不得引用 Development。
- Core 和 Content 源码不得写出 Development 的程序集名、命名空间或具体类型名。
- Development 可以引用 Core 和 Content，并主动注册、监听或补丁正式系统。
- 正式 XML、语言包和存档字段不得引用 Development 类型。

## 5. 职责边界

### 5.1 Core

Core 只保留中性、通用的诊断基础设施：

- 诊断事件提交入口；
- 可选诊断接收器注册口；
- 必要的一次性与节流语义；
- 业务中立的只读快照或观察面。

现有 `BdpDiagnostics` 不直接迁出 Core，而是收缩为中性发射器。没有注册接收器时，开发追踪日志应安全静默。

### 5.2 Content

Content 保留业务事实的产生位置：

- 在发生重要业务节点时提交诊断事件；
- 对真实配置错误、恢复失败和可能影响玩家结果的问题，继续在所属业务内输出必要的 `Log.Error` 或 `Log.Warning`；
- 不实现诊断 UI、日志导出或测试入口。

### 5.3 Development

Development 承载：

- 诊断日志的实际输出、分类、节流展示和可选导出；
- 开发者地图标记、诊断 Gizmo 和现场观察面板；
- 临时 Harmony 补丁；
- 临时功能原型；
- 玩家主动触发的游戏内功能测试和故障注入。

Development 不得：

- 被正式程序集调用；
- 向正式系统提供运行所必需的服务；
- 自动修改地图、角色或正式存档；
- 把自身类型写入正式存档；
- 在未开启开发者模式时注册测试按钮或临时补丁。

## 6. 诊断数据流

```text
Core / Content 产生业务事实
              ↓
Core 中性 BdpDiagnostics 发射口
              ↓（可选接收器）
BDP.Development 日志接收器
              ↓
RimWorld 日志 / 开发面板 / 临时导出文件
```

边界原则：

- 正式代码只知道诊断通道、键、消息和节流要求，不知道 Development。
- Development 缺失时，诊断调用不得抛异常或改变业务结果。
- 诊断接收器自身异常必须被隔离，不能反向破坏正式调用链。
- 若 Development 需要观察的事实尚不可读，优先增加最小只读事件或快照；不得为了测试开放正式写入权限。

## 7. 本地加载布局

工程与输出位置：

```text
BorderDefenseProtocol
├─ Source
│  ├─ BDP
│  ├─ BDP.Content
│  └─ BDP.Development
└─ 1.6
   ├─ Assemblies
   │  ├─ BDP.Core.dll
   │  └─ BDP.Content.dll
   ├─ Content
   └─ Development
      ├─ .keep
      ├─ Assemblies
      │  └─ BDP.Development.dll
      └─ Defs
```

`LoadFolders.xml` 增加 `1.6/Development`。原版会报告不存在的 LoadFolder，因此正式发布即使排除开发 DLL，也保留空的 `1.6/Development` 目录标记。

Development 工程构建后必须删除误复制到开发目录的 `BDP.Core.dll`、`BDP.Content.dll` 及其调试符号，开发目录只保留 Development 自身产物。

## 8. 启动与运行

```text
RimWorld 加载 BDP.Development.dll
              ↓
安全检查开发者模式
              ↓
注册诊断接收器
              ↓
注册开发 UI、提供器和临时补丁
              ↓
等待玩家主动触发测试功能
```

- `DevelopmentBootstrap` 是唯一启动入口。
- 启动入口捕获自身异常，避免诊断设施阻断 Core 或 Content。
- 未开启 RimWorld 开发者模式时，不注册测试按钮、诊断 UI 或临时补丁。
- 测试与故障注入必须由玩家主动触发。
- Development 状态只保存在内存中。
- 使用开发 Def 的存档视为一次性测试存档，不作为正式兼容目标。

## 9. 发布边界

正式发布前由用户手动删除：

- `1.6/Development/Assemblies/BDP.Development.dll`；
- `1.6/Development/Assemblies/BDP.Development.pdb`；
- `1.6/Development/Defs` 下的开发 Def；
- 其它明确标记为 Development 的运行产物。

新增发布前检查脚本，但脚本只检查、不自动删除。发现任何开发运行产物时立即失败并列出路径。

正式发布验证必须在 Development DLL 不存在的状态下完成：

1. Core 构建与隔离检查通过；
2. Content 构建通过；
3. 正式 XML 不引用 Development；
4. 正式程序集不引用 Development；
5. 游戏中主模组可独立加载并运行。

## 10. 开发工作流

```text
在 Development 中复现和观察问题
              ↓
定位正式代码根因
              ↓
在 Core / Content 做最小正式修复
              ↓
删除一次性日志、补丁和原型
              ↓
移除 Development 产物
              ↓
验证正式模组独立运行
```

可以长期保留的内容仅包括：

- 通用诊断接收器；
- 多次任务都会复用的诊断面板；
- 稳定的游戏内测试入口；
- 明确可插拔且不写正式状态的观察工具。

一次性问题日志、临时补丁和原型完成任务后必须删除。

## 11. 自动门禁

至少建立以下检查：

1. Core 仍无任何本模组程序集依赖。
2. Content 只引用 Core。
3. Development 只单向引用 Core 和 Content。
4. Core/Content 源码与正式 XML 不出现 Development 具体名称。
5. Development 输出目录不包含 Core/Content 副本。
6. 发布前检查在开发 DLL、PDB 或开发 Def 存在时失败。
7. 删除 Development 后，Core/Content 构建和正式专项测试仍通过。

## 12. 与芯片制造台工作的关系

开发辅助程序集属于架构前置，建议先完成最小骨架和发布门禁，再开始芯片制造台业务实现。后续芯片制造台的游戏内诊断日志、临时原型和功能测试入口优先放在 Development；正式制造规则、UI 和原版工作台适配仍全部属于 Content。
