# 武装构型泛化重构设计

## 一、设计状态

- 日期：2026-08-22
- 状态：已实施并完成收口验证
- 范围：芯片制造业务、成品组合解析、运行时来源身份、制造窗口和 Core（核心程序集）组合准入中残留的枪壳专名
- 非范围：本轮不新增射手立方体、攻击手长枪或狙击手构型的正式数值；不改变现有枪械平衡值；不把武装构型做成多构型叠加系统；不把 Trion 立方体做成玩家可选的制造台条目。临时攻击手型仅作为可删除的游戏内测试样本保留。

本设计以当前工作区源码为准。已有的“枪壳”系统是本次重构对象，不以旧版模组作为设计依据。

## 二、设计结论

把现有 `ChipGunShellDef`（枪壳定义）泛化为 `ChipArmamentFormDef`（武装构型定义）。中文业务名称统一使用“武装构型”；“外壳”可以继续作为玩家理解用的比喻，但不再作为代码和正式架构名称。

一枚武装类芯片的正式结构是：

```text
动作内芯
  ├─ 默认一个动作预设
  └─ 仅当当前有效构型声明允许时，才可为两个动作预设的合并结果
          ↓
有效武装构型
  ├─ 玩家显式选择的可见构型
  └─ 或系统按职业/动作条件补入的不可见默认构型
          ↓
一个统一覆盖块
          ↓
最终芯片配置
```

武装构型不是另一枚芯片，也不是多个独立特征模块的集合。它是动作内芯合并完成后，按需覆盖最终表达条目的一个统一外层配置。玩家可见构型和不可见默认构型共用同一套定义和覆盖逻辑，但只有前者进入制造台和成品名称。

动作数量规则也属于构型能力，而不是职业名称特判：默认最大动作数为 1；当前枪械构型数据声明最大动作数为 2，因此保留现有枪械路径的单动作或双动作选择，并把双动作合并为一个动作的多形态。其它构型默认只能选择一个动作。

## 三、当前实现的事实与保留项

### 3.1 当前枪壳已经承担的职责

现有枪壳同时参与：

- 制造窗口的可选项；
- 职业兼容判断；
- 附加材料和附加工作量；
- 远程 `Verb`（动作）属性覆盖；
- `Execution`（执行）部分覆盖；
- `ProjectileOverrides`（投射物覆盖）；
- 单侧和复合视觉预设；
- 远程模块追加或替换；
- 近战 `tools`（工具）追加或替换；
- 成品标签和运行时来源变体身份。

因此，本次不是从“枪械参数”重新设计一个新系统，而是将已有的外层覆盖语义改成武装构型语义。

### 3.2 当前实现中需要保留的正确主干

以下结构继续作为正式真值链：

1. `ChipCombinationRecord`（芯片组合记录）只保存玩家选择，不保存完整计算结果。
2. `ChipCombinationResolver`（芯片组合解析器）是组合解析的唯一入口。
3. 按当前有效构型的动作数量能力选择一个或两个动作；双动作先合并为一个最终多形态配置副本。
4. 武装构型在动作合并完成后只应用一次。
5. 任何应用过程都不得修改原始动作或构型 Def（定义）对象。
6. 成品运行时通过 `IChipInstanceDefinitionProvider`（芯片实例定义提供器）取得最终配置。
7. Core 运行时继续使用中性的 `SourceVariantKey`（来源变体键）和 `SourceVariantLabel`（来源变体标签）。

其中“先合并动作、再一次性应用构型”是本次重构必须锁定的时序，不得改成对动作 A、动作 B 分别应用构型。两个动作不是两个并列运行时动作，而是现有规则下合并出的一个动作多形态。

## 四、目标领域模型

### 4.1 `ChipArmamentFormDef`

建议字段：

```text
ChipArmamentFormDef
  compatibleProfessions
  compatibleActionPresetDefNames
  maxActionCount = 1
  showInManufacturing = true
  includeInProductLabel = true
  implicitDefault = false
  overrides
  additionalCost
  additionalWorkAmount
```

字段含义：

- `compatibleProfessions`：允许选择该构型的制造职业。
- `compatibleActionPresetDefNames`：可选动作白名单。为空表示不限制动作；非空时，组合中的每个动作都必须在白名单内。它只限制构型适用范围，不改变动作内芯内容。
- `maxActionCount`：该构型允许的动作数量上限，默认值为 1；现有枪械构型声明为 2。它只表达组合能力，不按职业 DefName（定义名）硬编码。
- `showInManufacturing`：是否作为玩家可见的制造台选项，默认显示；Trion 立方体默认关闭。
- `includeInProductLabel`：是否参与成品动态名称和玩家可见来源标签，默认参与；不可见默认构型关闭。
- `implicitDefault`：是否可以在没有玩家显式选择时由解析器按兼容条件自动采用；定义校验必须保证同一条件下最多一个有效默认构型。
- `overrides`：唯一的武装构型覆盖块；未声明字段保持动作内芯的原值。
- `additionalCost`：每枚成品追加的具体材料。
- `additionalWorkAmount`：每枚成品追加的工作量。

构型暂时不增加独立的 `compatibleCategories` 字段。当前它只服务 `BDP_ChipCategory_Weapon`（武装主分类）；如果将来确实需要非武装主分类使用同一机制，再单独扩大适用范围。

### 4.1.1 显式构型与隐式默认构型

解析时先得到有效构型：

```text
玩家选择了可见构型？
  ├─ 是：使用该显式构型
  └─ 否：查找当前职业、分类和动作条件下唯一的隐式默认构型
             └─ 没有默认构型：不使用构型覆盖
```

动作数量能力按同一份数据规则解析：

```text
显式构型已选？
  ├─ 是：使用显式构型的 maxActionCount
  └─ 否：使用当前制造路径可用构型声明的默认能力
             └─ 没有声明：回落到 1
```

因此当前枪械路径即使暂时不选具体枪械型，也仍可保留 2 个动作的现况；攻击手、射手等其它路径默认回落到 1。若显式选择了只允许 1 个动作的构型，则已有两个动作的草稿必须被判为不兼容，不能继续入队。

隐式默认构型仍然可以参与最终配置覆盖，但必须同时满足：

- 不进入制造台构型列表；
- 不显示为预览分组或构型名称；
- 不加入成品动态名称；
- 不产生玩家可见的来源变体标签；
- 不改变芯片图标、队列标题、半成品名称、成品名称或装配台名称。

如果需要让成品跨 Def 更新稳定复现，账单/成品记录可以在入队或制造开始时物化有效默认构型的内部 DefName；这只是内部身份，不代表玩家做过显式选择。

Trion 立方体默认构型的内容约束是：射手职业、武装主分类、最终表达中存在远程武装条目时自动适用；`maxActionCount` 为 1，`showInManufacturing` 和 `includeInProductLabel` 均为 false。当前已把原射手远程动作中的单侧/双侧贴图预设转移到该隐藏构型，动作条目的贴图字段留空但运行时表现保持一致。

### 4.2 `ChipArmamentFormOverrides`

`ChipArmamentFormOverrides`（武装构型覆盖块）是一个统一对象，不拆成远程模块、近战模块、视觉模块或投射物模块。

它可以按需包含以下字段区域：

- 远程 `VerbProps`（动作属性）字段；
- 近战 `Tool`、`tools` 和 `Maneuver`（动作机动定义）字段；
- `Execution` 执行字段；
- `Presentation`（表现）字段；
- `ProjectileOverrides` 投射物字段；
- `RangedModules`（远程模块）字段；
- 对应列表的 `MergeStrategy`（合并策略）。

所有可覆盖标量字段继续使用可空字段表达“未声明”：

```text
null       = 不覆盖，保留动作内芯
显式数值   = 覆盖动作内芯
显式列表   = 按声明的 Append / Replace 合并
```

不使用反射把整个 `VerbProperties`（原版动作属性）对象无条件替换，也不使用字符串键值表。这样可以保持 XML 可读、字段可检查、覆盖行为可追踪。

### 4.3 不属于构型覆盖的字段

武装构型修改的是动作条目的属性和表现，不修改表达结构身份。以下字段默认不开放给构型覆盖：

- 条目 `Id`（标识）；
- `Kind`（表达条目类型）；
- `RelationKind`（条目关系）；
- `ParentEntryId`（父条目标识）；
- 条目条件列表；
- `AbilityDefName`、`HediffDefName`、`PassiveKey` 等通道身份；
- 表达条目 Trion 的来源关系；
- 通过构型新增、删除表达条目。

如果未来需要构型新增一条 Ability（能力）、Hediff（健康状态）或 Passive（被动）表达，那是“表达组合”能力，不是本设计中的外层特征覆盖。

## 五、覆盖适用规则

### 5.1 条目资格

武装构型应用服务遍历最终配置中的表达条目：

- `PrimaryVerb` 或 `SecondaryVerb` 才能接受武装动作属性覆盖；
- `WeaponMode=Ranged` 时，允许远程字段、投射物字段和远程模块字段；
- `WeaponMode=Melee` 时，允许近战工具、动作机动和近战执行字段；
- 表现字段作用于符合武装表达资格的动作条目；
- `Ability`、`Hediff`、`Passive` 等非武装动作条目不接受武装属性覆盖。

当前代码的关键缺口是：旧武装型表达入口只允许远程 Verb，因此虽然覆盖对象已经有 `tools` 字段，近战路径实际上没有被接通。本次已修正应用资格判断，而不是额外建立近战模块系统。

### 5.2 未声明与不适用

- 构型没有声明某字段：保持动作内芯原值。
- 构型声明远程字段，但最终没有适用的远程条目：定义校验或组合解析必须给出稳定错误，不得静默伪装成成功。
- 构型只声明表现字段：只要存在可表现的武装动作条目即可，不要求它必须声明远程或近战数值。
- 显式构型与职业不兼容：组合无效，不能进入制造队列。
- 隐式默认构型不满足条件：不应用默认构型，不把它伪装成玩家可选项。

### 5.3 动作适用范围

动作适用范围由 `ChipCombinationSelectionRules`（组合选择规则）集中判断，制造台和最终解析器复用同一谓词：

- 白名单为空：构型对所有动作开放；
- 白名单非空：每一个已选动作都必须命中白名单；
- 双动作只要有一个动作不匹配，整个构型组合无效；不允许只对其中一个形态局部覆盖；
- 选择动作时会提前过滤不适用的动作，读档或外部数据造成不匹配时仍由最终兼容性校验拒绝；
- 默认构型查找同样检查动作范围，避免未来多个隐藏默认型因 Def 加载顺序产生不稳定结果。

具体字段是否需要增加，以第一个真实业务用例为依据。当前不为了假设中的长枪、狙击手或未来模块提前复制全部原版属性。

## 六、解析和制造数据流

```text
制造草稿
  └─ CategoryDefName + ProfessionDefName
  └─ OrderedActionPresetDefNames
  └─ ArmamentFormDefName（显式选择，可空）
          ↓
ChipCombinationResolver
  1. 读取分类、职业、动作、构型
  2. 解析显式构型或唯一隐式默认构型
  3. 检查来源缺失、动作数量能力和兼容条件
  4. 合并动作内芯；只有有效构型允许时才合并两个动作
  5. 深复制并应用有效构型覆盖一次
  6. 只把可见构型纳入玩家名称和来源标签
  7. 返回最终配置、成本所需来源和成品身份
          ↓
账单 / 半成品 / 成品组件 / Core 运行时
```

成本计算和配置解析继续共同读取同一份组合记录：

- 基础配方材料；
- 动作预设材料；
- 武装构型材料；
- 动作工作量；
- 武装构型工作量。

武装构型成本和覆盖都只能计算一次。

## 七、制造窗口和预览

制造窗口不再判断“当前是不是枪手”来决定是否显示外层区域，而是根据当前分类、职业和动作选择查询可用的可见武装构型。隐式默认构型不进入列表；射手远程武装芯片因此不会出现 Trion 立方体构型选项。

目标语义：

```text
GetArmamentForms(category, profession, selectedActions)
```

UI（用户界面）和 `ChipCombinationResolver` 必须使用同一套兼容判断，避免“界面能选、提交时才失败”的分裂规则。

预览模型使用 `ArmamentFormAdjustments`、`ArmamentFormMetrics` 等中性构型名称。预览仍然只读取统一解析结果，不直接读取草稿中的 Def。

预览规则：

- 构型修正只显示一次；
- 动作形态显示最终结果；
- 显式构型只修改视觉时也能显示构型名称和说明；
- 隐式默认构型不显示构型名称、构型分组或额外 UI 标识；
- 远程、近战字段根据最终条目是否存在决定显示，不预留空的枪械指标区域；
- 射手隐式默认构型导致的最终属性变化可以反映在已有属性字段中，但整个制造、队列、半成品、成品和装配过程不出现明显额外身份提示；
- 所有新增玩家可见文案写入语言包。

## 八、运行时身份与 Core 边界

Content（内容程序集）中的 `CompManufacturedChip` 将有效武装构型的中性来源身份公开为：

```text
SourceVariantKey        # 供逻辑使用的中性键，可包含内部默认构型身份
SourceVariantLabel      # 仅对 includeInProductLabel=true 的可见构型返回玩家标签
```

Core 不读取 `ChipArmamentFormDef`，也不依赖 Content 的制造类型。

重构前 Core 组合技准入曾存在枪壳专名：

- `AllowedGunShells`；
- `DeniedGunShells`；
- `GunShellKey`。

这些字段现已改成 `AllowedSourceVariants`、`DeniedSourceVariants` 和 `SourceVariantKey`，只表达“来源变体身份”，不解释其业务含义。

Core 表达管线中的旧专名注释、格式说明和特定后缀描述现已改为中性来源变体语义。玩家可见的具体构型名称按内容语言包写成“左轮手枪型”“长枪型”等；Core 不强制后缀，也不把隐式默认构型格式化为玩家标签。

## 九、存档边界

当前账单、半成品和成品组件都持有 `ChipCombinationRecord`，因此字段重命名必须明确新的存档边界。

新字段使用：

```text
ArmamentFormDefName
```

新格式只保存 `ArmamentFormDefName`。不读取 `gunShellDefName`，不提供旧字段别名，不执行旧存档迁移。

旧存档若仍携带旧字段，必须直接暴露为不兼容或来源缺失问题，由测试和日志暴露，而不是被自动整理成当前格式。账单、半成品匹配和成品身份比较全部使用新的构型字段。

## 十、验证与安全性

必须验证：

- 默认动作数量为 1；现有枪械构型允许 1~2 个动作，双动作合并为一个动作的多形态；
- 其它构型只能选择 1 个动作；该规则由构型数据能力声明，不按职业或 DefName 硬编码；
- 单动作不选显式构型时行为保持不变；
- 现有三种枪械构型改名后数值和视觉结果保持不变；
- 双动作只应用一次构型；
- 射手远程武装芯片自动使用不可见 Trion 立方体默认构型，但不进入构型列表、动态名称、来源标签或过程 UI；
- 近战条目可以真正接受 `tools` 和执行属性覆盖；
- 只写视觉字段的构型不会要求远程数值；
- 构型不能修改表达条目类型和身份；
- 动作白名单为空时不限制动作，非空时双动作必须全量匹配；
- 原始动作 Def 不被修改；
- 材料槽全集包含所有武装构型材料；
- 缺失构型来源不会静默替换；
- Core 不出现制造业务类型依赖；
- Core 组合准入只使用中性来源变体字段；
- 所有新文案都来自语言包。

## 十一、明确不做的事情

- 不建立远程、近战、视觉、投射物特征模块注册表；
- 不把构型放进 `ChipDefinitionConfig.Extensions`（芯片静态扩展）；
- 不把构型放入 Core；
- 不支持一枚芯片同时叠加多个构型；
- 不用字符串键值表替代强类型覆盖字段；
- 不为尚无实际业务的原版字段提前做完整反射覆盖；
- 不在本次重构中改变枪械、动作或制造成本平衡值；
- 临时攻击手型只用于验证弧月动作和破墙斧贴图，不视为正式平衡内容；
- 不顺手修改与芯片制造无关的战斗系统。
- 不把隐式默认构型变成玩家可选项或动态名称后缀。

## 十二、验收标准

本设计实施完成后，代码应能用同一套武装构型机制表达：

1. 现有枪手枪械外观和远程参数，且继续允许 1~2 个动作合并为多形态；
2. 射手远程武装芯片自动获得不可见的 Trion 立方体默认修正，制造到装配的玩家可视身份不发生明显变化；
3. 攻击手体系刀或长枪的显式“型”构型，且只能选择一个动作；
4. 未来狙击手构型的远程特征，而不再新增枪壳专用流程。

这些具体构型不要求在本次架构重构中全部落地，但系统不能再因名称、职业特判或远程入口限制而阻止它们接入。
