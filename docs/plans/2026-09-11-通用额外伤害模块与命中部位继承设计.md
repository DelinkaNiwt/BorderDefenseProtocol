# 通用额外伤害模块与命中部位继承设计

## 1. 目标

为 BDP 增加一个可被多个远程攻击复用的通用额外伤害模块。模块可以在远程投射物命中后追加独立伤害，并支持“当前存在身体部件的最大血量总和 × 百分比”的计算方式。

风刃作为第一个使用者：每枚风刃有效命中 Pawn（人形单位）后，追加实际命中部件最大生命值的 10% 伤害。

额外伤害模块不得引用或识别 `VitalHitModule`（要害命中模块）。命中部位共享必须通过 Core（核心基础设施）定义的中性 Impact（命中结算）协议完成。

## 2. 已确认的当前事实

1. 风刃使用 `BDP_Projectile_Fujin` 和 `BDP.Core.Projectiles.BdpProjectile`。
2. 风刃投射物主伤害为原版 `Cut`（切割）伤害，基础伤害为 30，当前一轮发射 10 枚投射物。
3. BDP 已有 `ImpactStageService`（命中阶段服务）、`ImpactContribution`（命中贡献）和 `DamagePlan`（伤害计划）机制。
4. `VitalHitModule` 只负责解析 `BodyPartRecord`（身体部件记录），并把结果提交为 `ImpactPlan.HitPartOverride`（命中部位覆盖）。它不负责放大伤害。
5. 当前主伤害会消费 `HitPartOverride`，但额外伤害执行路径传入空命中部位，因此额外伤害会重新走原版随机部位选择。
6. 原版 `HediffSet.GetNotMissingParts()`（获取未缺失部件）可以取得目标当前存在的身体部件；`BodyPartDef.GetMaxHealth(pawn)`（获取部件最大血量）会按 Pawn 的健康倍率计算部件最大血量。

## 3. 设计原则

### 3.1 模块互不认识

业务模块之间不建立直接引用：

```text
VitalHitModule
    └─ 提交 Impact 的命中部位事实

ExtraDamageModule
    └─ 提交额外 DamagePlan，并声明通用命中部位策略

Core Impact 汇总层
    └─ 合并事实与策略

BdpProjectile
    └─ 按最终计划执行主伤害和额外伤害
```

额外伤害模块不得出现 `VitalHitModule`、`VitalHitConfig` 或 `HitPartPolicyResolver` 的引用。

### 3.2 Core 只提供中性能力

Core 不解释“要害”的业务含义，只提供通用的命中部位绑定能力。Core 只知道：

- 当前 Impact 是否解析出了一个命中部位；
- 某条伤害计划是否要求继承该命中部位；
- 没有可继承部位时是否回退原版随机选择。

### 3.3 原版伤害链优先

额外伤害继续通过原版 `Thing.TakeDamage`（目标承伤入口）执行，保留：

- 原版伤害类型；
- 原版护甲处理；
- BDP 已有伤害护盾和投射物交互策略；
- 原版伤害结果与战斗日志路径。

额外伤害与主伤害仍是两次独立伤害调用，因此护甲会分别计算。这不等价于把两者合并成一次总伤害。

## 4. Core 中性协议

### 4.1 伤害计划增加命中部位解析策略

在 Core 的伤害计划模型中增加中性策略，建议命名为 `HitPartResolutionMode`（命中部位解析模式）：

- `Independent`：不继承 Impact 命中部位，交给原版重新选择；
- `InheritImpactHitPart`：如果当前 Impact 存在已解析命中部位，则使用该部位；不存在时回退原版选择。

该策略属于伤害计划的执行语义，不属于任何具体业务模块。

### 4.2 额外伤害执行

`BdpProjectile.ExecuteImpact`（投射物命中执行）执行 `ExtraDamages`（额外伤害）时：

1. 读取额外 `DamagePlan` 的命中部位解析策略；
2. 当策略为 `InheritImpactHitPart` 时，传入当前 `ImpactPlan.HitPartOverride`；
3. 当策略为 `Independent` 时传入空部位；
4. 其余伤害信息继续按现有 `BuildDamageInfo`（伤害信息构造）流程生成。

这样 `VitalHitModule` 只提供部位，`ExtraDamageModule` 只声明继承策略，两者由 Core 在执行阶段自然组合。

## 5. 通用额外伤害模块

### 5.1 模块职责

新增 Content（正式业务内容）模块，建议命名为 `RangedExtraDamageModule`。它只负责：

1. 判断当前命中是否满足模块配置；
2. 根据配置计算额外伤害量；
3. 创建并追加 `DamagePlan`；
4. 设置伤害类型、护甲穿透和命中部位解析策略。

模块不负责直接调用 `TakeDamage`，不负责查找其它模块，也不负责解析要害。

### 5.2 初始配置能力

第一版保留满足当前需求所需的最小通用能力：

- 直接命中目标范围；
- 固定额外伤害；
- 目标 Pawn 当前存在身体部件最大血量总和百分比；
- 可配置额外伤害 `DamageDef`（伤害定义）；
- 可配置或继承投射物的护甲穿透；
- 可配置命中部位策略，风刃使用 `InheritImpactHitPart`。

不在第一版加入范围爆炸逐目标额外伤害、按当前剩余生命计算、攻击会话去重或多目标分摊，避免扩大当前需求。

### 5.3 身体部件总和公式

对直接命中的 Pawn：

```text
bodyPartMaxHealthSum =
    Σ part.def.GetMaxHealth(target)
    for part in target.health.hediffSet.GetNotMissingParts()

extraDamage = bodyPartMaxHealthSum × configuredRatio
```

该模式由通用模块按挂载配置的 `configuredRatio` 计算，供需要全身部件总和的挂载使用。

如果命中目标不是 Pawn，或目标没有可用身体部件，则不追加这类百分比伤害。

### 5.4 风刃挂载

风刃在自身 `RangedModules`（远程模块）列表中追加通用额外伤害模块配置。风刃只配置参数，不新增风刃专用运行时类型。

风刃继续单独挂载现有 `BDP_VitalHitModule`。两个模块的组合结果为：

- 主伤害使用要害模块解析的部位；
- 额外伤害使用同一个部位；
- 两次伤害分别经过原版伤害入口和护甲处理。

风刃当前选择 `HitPartMaxHealthPercent`，每次额外伤害按“实际命中部件最大生命值 × 0.10”计算。

当前风刃一轮发射 10 枚投射物，因此倍率按每枚有效命中分别计算；10 枚全部命中时，每枚额外伤害仍按当次实际命中部件的最大生命值计算。

## 6. 不做的方案

### 6.1 额外伤害模块直接调用要害模块

禁止。会破坏模块独立性，并把通用模块绑定到某一项业务模块。

### 6.2 Harmony（运行时补丁）全局拦截 `TakeDamage`

不采用。来源识别、递归防护、护盾重复处理和第三方模组兼容成本都高于当前需求。

### 6.3 把主伤害和额外伤害直接合并

第一版不采用。合并会改变伤害日志、护甲计算次数和现有模块的独立语义。

## 7. 计划涉及的文件范围

预计修改范围如下，实际实施前以当前源码为准：

- Core 伤害计划模型：增加命中部位解析策略；
- Core Impact 执行：让额外伤害消费该策略；
- Content 远程模块：新增通用额外伤害模块及配置；
- `1.6/Content/Defs/RangedModuleDef`：新增通用模块 Def；
- 风刃 `ChipFunctionDef`：挂载通用模块，并在挂载配置中声明 10% 命中部件公式、伤害类型和命中部位继承；
- 简体中文语言包：新增模块名称、说明和必要字段文案；
- BDP 测试脚本：增加模块装配边界、命中部位继承和风刃参数验证。

明确不修改：

- `VitalHitModule` 的业务逻辑；
- Core 对“要害”的解释；
- 风刃投射物飞行和追踪逻辑；
- 现有护盾模块的业务规则。

## 8. 验证要求

### 8.1 静态验证

- Core、Content 编译通过；
- 模块 Def 可以加载；
- 风刃挂载的是通用模块，而不是风刃专用运行时类型；
- 额外伤害模块源码不引用 `VitalHitModule`；
- `VitalHitModule` 源码保持不变。

### 8.2 运行时验证

至少验证以下情况：

1. 只有通用额外伤害模块：额外伤害随机部位；
2. 只有要害模块：主伤害命中要害；
3. 两个模块同时存在：主伤害和额外伤害命中同一部位；
4. 没有可继承命中部位时：额外伤害回退原版随机部位；
5. 目标缺失身体部件后：总和只计算剩余部件；
6. 命中建筑或其它非 Pawn 目标：不执行身体部件百分比额外伤害；
7. 有护甲和伤害护盾时：两条伤害仍遵守现有防御策略；
8. 风刃多枚投射物分别命中时：每枚命中只结算一次额外伤害。

## 9. 设计结论

采用“模块独立提交，Core 统一组合”的方案。`VitalHitModule` 和 `RangedExtraDamageModule` 不互相认识，通过 Core 的 `HitPartResolutionMode` 共享一次 Impact 已解析的命中部位事实。该方案保持当前 BDP 的模块边界、原版伤害入口和最小改动原则。
