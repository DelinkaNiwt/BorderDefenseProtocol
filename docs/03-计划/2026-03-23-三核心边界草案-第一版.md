# 三核心边界草案（第一版）

## 目的

这份草案只做一件事：

先把旧 BDP 里最缠在一起的三块切开：

- `Trion`
- `战斗体`
- `触发体/装载`

它不是最终架构图，只是二次重构起步时必须先定清的 owner 边界。

## 总原则

- 每块核心只维护自己的正式状态
- 跨核心只能提请求、收结果，不能直接改对方真值
- 触发体不再做总装配中心

## 1. Trion 核心

### 它负责什么

- 容量
- 当前值
- 正式占用
- 预留值
- 持续消耗登记
- 自动恢复
- 资源不足判定

### 它不负责什么

- 不负责判断战斗体是否允许激活
- 不负责决定触发体当前激活哪枚芯片
- 不负责决定攻击怎么发射
- 不直接执行战斗体崩解流程

### 它对外只应提供什么

- 当前资源状态查询
- 扣费请求
- 占用/释放请求
- 持续消耗注册与注销
- 资源不足事件

## 2. 战斗体核心

### 它负责什么

- 当前相位：未激活 / 激活 / 崩解中 / 冷却中
- 激活条件检查
- 进入战斗体后的身体状态表达
- 解除与崩解的正式流程状态
- 与快照恢复相关的正式规则

### 它不负责什么

- 不拥有 Trion 真值
- 不自己管理芯片槽和装载数据
- 不自己生成攻击动作
- 不直接支配 projectile 细节

### 它对外只应提供什么

- 是否可激活
- 当前相位查询
- 激活请求
- 正常解除请求
- 被动崩解请求
- 相位变化事件

## 3. 触发体 / 装载核心

### 它负责什么

- 槽位结构
- 左右手 / 特殊槽的装载语义
- 芯片装载与卸载
- 当前哪些能力可用
- 装载切换流程
- 装备侧的原版桥接

### 它不负责什么

- 不拥有 Trion 真值
- 不拥有战斗体正式相位真值
- 不直接决定战斗体是否崩解
- 不做全局业务总协调

### 它对外只应提供什么

- 当前装载状态查询
- 切换请求
- 能力清单
- 给原版 Verb / Gizmo / Inspect 的桥接数据

## 三者关系草案

### Trion -> 战斗体

允许：

- 战斗体请求 Trion 扣费或占用
- Trion 返回成功或失败
- Trion 发出“资源不足”结果

不允许：

- Trion 直接改战斗体相位

### 战斗体 -> 触发体

允许：

- 战斗体激活后通知触发体“现在允许进入战斗体专用能力状态”
- 战斗体解除后通知触发体“恢复非战斗体限制”

不允许：

- 战斗体直接改触发体槽位真值

### 触发体 -> Trion

允许：

- 触发体根据装载情况申请预留值
- 触发体在具体行动时发起扣费请求

不允许：

- 触发体直接写资源字段

## 当前最重要的切割目标

### 第一刀

把“战斗体是否崩解”从 `CompTriggerBody` 手里拿走。

### 第二刀

把“资源正式真值”牢牢固定在 Trion 核心，别再让触发体和战斗体共同持有。

### 第三刀

把触发体降级成装备侧宿主和装载 owner，不再兼任系统总协调者。

## 为什么先只切这三块

因为旧 BDP 最大的问题正是它们互相缠死了。

如果这三块边界不先稳定，后面不管你怎么设计行动、投递、效果，最后都会重新长回一个超级触发体。

## 这份草案的用途

下一步研究时，所有旧版代码都要继续拿这份草案对照：

- 哪些行为其实应该归 Trion
- 哪些其实应该归战斗体
- 哪些只是触发体历史上顺手扛了下来

这会成为后续第一版正式核心设计的前置材料。
