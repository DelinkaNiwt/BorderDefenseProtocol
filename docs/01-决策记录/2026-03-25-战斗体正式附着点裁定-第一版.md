# 战斗体正式附着点裁定（第一版）

## 裁定目的

在继续推进战斗体主链前，
先把一个不能含糊的问题定死：

- 战斗体这条主链，正式附着到 RimWorld 的哪个自然宿主上

这个问题如果不先定，
后面很容易为了“先接通”而临时造新载体，
最终重新偏离：

- `Verb / Ability / Hediff / Projectile / Gizmo / ThingComp / JobDriver`

这些原版自然通道。

## 结论

战斗体正式附着点，
当前裁定为：

- `Hediff / HediffComp` 优先

不是：

- `CompTriggerBody`
- `CompTrion`
- 额外新建平行生命周期容器
- 纯静态全局管理器

## 理由

## 1. 旧 BDP 与现有研究记录都指向 `Hediff/HediffComp`

现有研究文档已经明确：

- 战斗体相位整体更贴 `Hediff/HediffComp`
- 它天然贴近 Pawn 身体状态、持续状态存在、序列化附着点

这与旧 BDP 的实际落点也是一致的：

- `Hediff_CombatBodyActive`
- `Hediff_CombatBodyCollapsing`

虽然旧 BDP 的具体实现并不理想，
但“战斗体附着在 Pawn 身体状态宿主上”这个方向本身没有错。

## 2. `Hediff` 更适合作为附着点，不适合作为总协调者

这次裁定不是说：

- 战斗体 = Hediff

而是说：

- `Hediff/HediffComp` 负责正式附着与宿主存在
- `CombatBodyCoordinator` 负责主链事务编排
- `CombatBodyState` 负责相位真值

也就是说：

- `Hediff` 是附着点
- 不是总流程 owner

## 3. 继续悬空或临时塞进别的地方都会带来更差结果

如果不接 `Hediff/HediffComp`，
当前看似还有几个“方便”方案：

- 继续只保留 `PawnCombatBodyHost`
- 临时挂到 `CompTriggerBody`
- 临时挂到 `CompTrion`
- 新建一个平行 `ThingComp`

这些方案的问题分别是：

- 继续悬空：主链对象永远没有正式宿主，后续任何行为都只能靠绕接
- 挂到 `CompTriggerBody`：Trigger 越权吞战斗体
- 挂到 `CompTrion`：资源 owner 越权吞相位与身体状态
- 新建平行 `ThingComp`：脱离原版身体状态体系，再造一层平行生命周期

## 当前阶段的具体结论

当前正式结论只到这里：

- 战斗体主链下一步应围绕 `Hediff/HediffComp` 接回 Pawn
- `PawnCombatBodyHost` 继续保留为宿主桥，但不再被视作最终附着点
- `CombatBodyCoordinator / CombatBodyState / EnterPipeline / ExitPipeline`
  这些对象继续保持“主链事务 + 相位真值 + 局部步骤簇”的位置

当前还没有在代码里继续推进以下内容：

- 新增具体 `HediffDef`
- 新增具体 `HediffComp`
- 接回快照、恢复、崩解 90 tick 收尾等完整闭环

原因不是这些不重要，
而是这份裁定先只冻结“正式附着点方向”，
避免后续实现再次迷失在宿主选择上。

## 一句话裁定

战斗体在新 BDP 中应继续以 `CombatBodyCoordinator + CombatBodyState` 维持主链与真值边界，但其正式附着点必须优先回到 RimWorld 的 `Hediff/HediffComp` 宿主语义上；`Hediff` 是战斗体附着点，不是战斗体总协调者。
