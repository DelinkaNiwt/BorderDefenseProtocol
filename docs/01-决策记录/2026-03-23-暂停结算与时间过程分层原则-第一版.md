# 暂停结算与时间过程分层原则（第一版）

## 目的

这份记录用于纠正当前二次重构里已经暴露出的一个方向性错误：

- 把“时间过程”误当成“逻辑成立条件”
- 把“RimWorld 的驱动方式”误当成“需求本体”

这会直接导致：

- 玩家已经做出操作，但系统结果还不成立
- 游戏暂停时，控制与界面状态看起来像卡住
- 查询入口被迫承担“补结算”的脏活
- 事件名看起来像事件，实际核心仍是时间状态机

## 硬原则

### 1. 玩家控制操作不得以时间流动为前提

以下内容必须在暂停下也能正确成立：

- 装载芯片
- 卸载芯片
- 激活目标选择
- 关闭目标选择
- 当前按钮可见性
- 当前表达结果
- 当前主 / 副槽位逻辑状态
- 当前是否允许某个控制动作

### 2. 只有时间表现才允许依赖时间推进

以下内容允许依赖时间流动：

- 持续消耗
- 自然恢复
- 动作前摇 / 后摇
- 连发间隔
- 切换视觉表现
- 明确属于表现层的冷却过程

### 3. 逻辑层与表现层必须分开

今后任何涉及切换、冷却、收尾、攻击动作、资源过程的功能，都必须先分成两层：

- 逻辑层：现在到底应当算什么结果
- 表现层：这个结果在游戏里如何随时间表现出来

禁止再把“表现尚未结束”写成“逻辑尚未成立”。

### 4. 事件用于表达变化，不用于偷藏真值 owner

事件层只负责：

- 广播发生了什么
- 通知哪些快照失效
- 触发跨模块协作

事件层不负责：

- 持有唯一真值
- 代替资源 owner
- 代替战斗体 owner
- 代替触发体 owner

### 5. 查询入口只能读取结果，不应承担补救式结算

理想状态下：

- 按钮查询读到的是已成立的逻辑结果
- 自动攻击查询读到的是已成立的逻辑结果
- 表达查询读到的是已成立的逻辑结果

如果查询入口必须“顺手补一次结算”才能正常工作，通常说明上游建模已经偏了，应优先回头修 owner 与事件链。

## 当前已确认违反本原则的地方

### 1. Trigger 切换

当前问题最明确。

- `RequestActivate()` 不是立即提交逻辑状态
- 而是先写入 `SwitchContext + phaseEndTick`
- 后续再等时间或入口查询去推进

这与“暂停下必须正确成立”直接冲突。

### 2. CombatBody 冷却

当前 `CombatBodyState` 仍以 `TicksGame >= cooldownEndTick` 作为可再次激活判断。

这说明战斗体启闭与冷却目前也仍是时间状态机优先，后续必须重构。

### 3. 事件通信尚未真正落地

当前工程里：

- `Trion` 有边界事件
- 但 `Trigger / CombatBody / Expressions / Projections` 还没有真正统一的事件通信链

因此“事件总线 + 多核心骨架”目前仍停留在目标层，不是现状。

## 后续执行要求

后续修正时，必须按下列顺序推进：

1. 先修 Trigger，让逻辑激活结果立即成立
2. 再让 Expressions / Buttons / AutoAttack 统一读取同一份逻辑结果
3. 再重构 CombatBody 的冷却与收尾分层
4. 最后补齐最小事件通信骨架

## 一句话结论

二次重构后续必须坚持：

- 逻辑成立优先于时间表现
- 需求本质优先于引擎驱动方式
- 事件表达变化，owner 持有真值
