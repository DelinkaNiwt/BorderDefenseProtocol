# 避免架构退化与测试污染（第一版）

## 目的

这份记录用于冻结一组新的硬约束，
专门防止二次重构在推进过程中再次退化成：

- owner 宿主不断膨胀
- 为了短期可测把临时能力塞进正式业务
- 测试与正式代码混层
- 局部便利压倒整体架构
- 不必要的跨模块直接耦合不断增加

这些问题一旦不立刻钉死，
就会直接削弱二次重构的意义。

## 一、这次暴露出的核心问题

### 1. 为了尽快获得可测反馈，开始用“往现有宿主里继续塞功能”的方式推进

这说明当前推进里出现了一个危险倾向：

- 把“尽快形成可测试环节”
- 误执行成“尽快往当前类里加入口、加窗口、加调试口”

这不是正确的工程节奏，
而是架构意识开始变弱的信号。

### 2. 开始把 owner 宿主当成最方便的落点，而不是最严格的真值边界

`CompTriggerBody` 的正式定位已经被明确冻结为：

- 装载真值 owner
- 局部激活真值 owner
- 局部禁用真值 owner
- 局部切换协调者

如果继续把以下内容顺手塞进它：

- 临时 GUI
- 测试入口
- 调试窗口
- 与验证节奏直接绑定的辅助能力

那么它就会重新走回旧 BDP 那种：

- 上帝模块化

### 3. 把“测试可视化需求”直接落入主模组，是测试污染正式业务的开端

测试与正式必须隔离。

任何测试用、临时用、验证用的东西，
都必须做到：

- 直接删除后，对主模组项目无影响

如果删除一个测试面、临时窗口、验证入口后，
主模组就残留：

- 无用 API
- 无用按钮
- 无用窗口
- 无用状态字段
- 无用逻辑分支

那就说明测试污染已经发生。

## 二、从现在开始冻结的硬约束

## 0. 架构重审重点新增“不必要耦合”

从现在开始，每次代码交付前的架构重审，
都不能只看：

- 架构污染
- 上帝膨胀
- 过度抽象

还必须同时看：

- 不必要耦合是否增加

这里的“不必要耦合”重点包括：

- patch 直接驱动具体业务 owner
- 上游系统直接写下游真值
- 某个 owner 为了方便而直接读取过多外部细节
- 模块之间绕开中性事件或正式读取口互相直连

后续默认架构指导方向统一加上这条：

- 多核心骨架
- 局部模块化
- 事件通信

## 1. owner 宿主禁止继续膨胀

从现在开始，任何人对一个正式 owner 类动手前，
都必须先回答：

- 这个改动是在增加它的真值责任
- 还是只是因为它现在最方便下手

如果答案是后者，
就不能继续往这个 owner 里塞。

## 2. “可测试”不能成为“可乱塞”的理由

短阶段可测、可视、可反馈、易诊断仍然必须坚持。

但这条要求只能推动：

- 更好的测试接入口设计
- 更好的正式读取口设计
- 更好的诊断面设计

不能推动：

- 更随意地把临时能力并入正式宿主

## 3. 测试与正式必须物理隔离

任何测试用、临时用、验证用的东西，
都必须优先通过：

- 正式扩展口
- 测试模组
- 可删除的外置调试层

进入系统。

主模组不应直接承载：

- 临时测试窗口
- 临时测试按钮
- 临时验证逻辑
- 只服务测试节奏的界面对象

## 4. 删除测试层后，主模组必须零残留

这条必须作为硬判定：

如果某个测试能力删除后，
主模组还残留与它强绑定的：

- 类型
- API
- 调用路径
- 逻辑分支
- 配置项

那么它就不算隔离成功。

## 5. 诊断能力可以进入主模组，但必须满足最小正式性

主模组允许保留的只有：

- 关键状态转移日志
- 关键拒绝原因日志
- 正式读取口上可复用的最小查询能力

这些内容之所以允许进入主模组，
是因为它们服务的是：

- 正式问题定位

不是：

- 临时测试交互

## 6. 临时 GUI 不得先落入主模组再说

如果需要游戏内可视化测试面，
必须先设计：

- 它是否能通过正式扩展口挂入
- 它是否应放在测试模组
- 它删掉后主模组是否完全不受影响

只有这三件事先成立，
才允许进入实现。

不能再走：

- 先在主模组里做一个临时窗口
- 后面再说怎么清理

## 7. 每次准备实现时，先做“责任归属检查”

实现前必须先回答：

1. 这是 owner 真值责任吗
2. 这是正式结果责任吗
3. 这是读取层责任吗
4. 这是测试层责任吗
5. 这是诊断层责任吗

如果一个东西既像测试层，
又想放进 owner，
就必须立即停下。

## 三、对当前 B 路线的直接影响

从路线 B 开始，以下要求立即生效：

### 1. `CompTriggerBody` 只能继续承载正式 Trigger 边界内的东西

允许：

- 装载
- 局部激活
- 局部禁用
- 局部切换协调
- 关键诊断日志
- 正式只读查询口

不允许：

- 临时测试窗口
- 临时测试按钮
- 测试专用交互流程

### 2. 游戏内测试面必须优先走测试隔离方案

后续如果仍需要游戏内可视化测试，
优先方案应是：

- 正式扩展口 + 测试模组

而不是：

- 继续往主模组塞临时 GUI

### 3. 后续推进中，一旦发现“为了快测开始往正式宿主里塞测试能力”，立即停下

这条应作为当前路线的硬停点之一。

## 四、一句话总括

二次重构不能一边批判旧 BDP 的上帝模块化，一边在新 BDP 里因为想更快看到测试结果，就继续把临时 GUI、测试入口和辅助能力往正式 owner 宿主里塞；从现在开始，短反馈回路必须坚持，但测试与正式必须严格隔离，任何测试用、临时用、验证用的东西都必须做到直接删除后对主模组项目零影响，否则就视为架构退化与测试污染。
