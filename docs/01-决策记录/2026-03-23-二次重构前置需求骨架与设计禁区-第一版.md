# 二次重构前置需求骨架与设计禁区（第一版）

## 目的

这不是实现设计稿。

这份文档只做二次重构正式起步前最重要的一步：

- 把“旧 BDP 里必须保留的本质需求”写清楚
- 把“二次重构绝不能再犯的错误”写清楚
- 把“允许的实现方向”和“暂时不要碰的东西”写清楚

它的用途是：

- 以后开始设计和实现时，先拿这份文档对照
- 避免又滑回“架构漂亮，但游戏里表现不对”的路

## 一、最高原则

### 1. 旧 BDP 的外部表现是当前唯一真标准

二次重构是：

- 只重构内部原理
- 不允许丢失旧 BDP 的外部表现本质

这里强调的是：

- 本质功能
- 宿主行为
- 真实规则

不是表面案例名字。

### 2. 二次重构必须从 RimWorld 出发，最后回到 RimWorld

必须优先回到这些原版宿主：

- `Verb`
- `Ability`
- `Hediff`
- `JobDriver`
- `Projectile`
- `Gizmo`
- `ThingComp`

不能把 BDP 做成一个脱离 RimWorld 自己转的“平行游戏”。

### 3. 表达系统比攻击系统更上位

旧代码已经证明：

- 不只有攻击 Verb
- 还有 Ability
- 还有 Hediff
- 还有组合成立后额外生成的第三表达

所以二次重构时，
“攻击系统”不应再被当作最高中心。

更上位的应是：

- 表达来源
- 表达投影
- 宿主承载

## 二、当前已经明确的真实需求骨架

### 1. 表达来源层

芯片激活后，产生的是“按侧的表达来源”，而不是固定写死的最终攻击对象。

来源至少包括：

- 单侧近战表达
- 单侧远程表达
- Ability 表达
- Hediff 表达
- 组合条件成立后的第三表达

### 2. 表达合成层

左右两侧表达会根据组合关系，合成出：

- 左手独立表达
- 右手独立表达
- 双手合成表达
- 混合表达下的默认主攻击
- 组合第三表达

这一步是规则层，不是执行层。

### 3. 表达执行层

执行层必须继续按宿主类型分流：

- 标准近战 → 真原版近战链
- 标准远程 → 真原版远程链
- Ability → 原版 Ability 宿主
- Hediff → 原版 Hediff 宿主
- 非标准飞行 / 特殊攻击 → 自己的投射或效果宿主，但最终仍要回到 RimWorld 可理解的入口

### 4. 表达投影层

对外投影至少分三条口：

- 玩家手动入口
- 原版自动攻击入口
- 外部默认表面入口

这三条口不能再混成一个总入口。

### 5. 资源与战斗体层

必须继续保留三类不同真值：

- `CompTrion`：资源真值
- `CombatBodyState`：战斗体外层相位真值
- `CompTriggerBody`：装载与局部激活表达真值

不能再把它们糊成一个全能核心。

## 三、已经明确的设计禁区

### 1. 禁止把事件总线当成真值 owner

事件可以做：

- 通知
- 广播
- 协调触发

但不能做：

- 资源真值中心
- 战斗体真值中心
- 弹道底层唯一写入口

否则一定会重新失控。

### 2. 禁止把所有真实表达重新塞回原版 `VerbTracker.AllVerbs`

旧代码已经证明：

- 这会导致原版近战池和默认路径误拾取

所以“全部统一回原版池里”虽然看起来干净，
实际上是错的。

### 3. 禁止把手动入口和自动入口合流

必须继续分层：

- 手动入口是玩家操作层
- 自动入口是原版 AI 发现层

旧版已经明确走的是两套路。

### 4. 禁止把组合技继续理解成“攻击子系统”

组合技本质是：

- 满足组合条件后，额外生成第三表达

攻击型组合技只是它的一种。

### 5. 禁止继续让 `CompTriggerBody` 无限膨胀

触发体必须收缩回：

- 装载 owner
- 局部激活表达 owner
- 局部协调者

而不是继续兼任：

- 资源 owner
- 战斗体相位 owner
- 全局表达中心

### 6. 禁止为了“架构统一”牺牲 RimWorld 宿主现实

包括但不限于：

- 自动近战和自动远程本来就不是同一入口
- 真实绘制点和发射点必须共基准
- Ability / Hediff 应继续优先借原版宿主

## 四、允许的实现方向

### 1. 允许用事件总线做协调层

但前提是它只做：

- 状态变化通知
- 横切协作
- 非 owner 之间的解耦

### 2. 允许用多核心骨架

目前最自然的方向是至少分出：

- 表达与装载核心
- 资源核心
- 战斗体相位核心

必要时再加一个很薄的协调层。

### 3. 允许局部模块化

例如：

- 远程发射编排模块
- Ability 投影模块
- Hediff 投影模块
- 组合表达模块
- 手动入口投影模块
- 自动入口桥接模块

但这些模块都必须有统一接入协议。

### 4. 允许重写 Def 与内部组织

用户已明确：

- Def 不需要迁移
- 旧数据兼容不是当前目标

所以可以优先追求干净、可理解、可扩展。

### 5. 允许用 `Main/Sub` 作为触发体内部稳定命名

为避免旧版 `LeftHand/RightHand` 在玩家视角、角色朝向、身体部位三者之间长期冲突，
二次重构从起步开始统一采用：

- `Main = 右`
- `Sub = 左`

约束如下：

- 触发体内部稳定命名优先使用 `Main/Sub`
- 只有在和 RimWorld 身体部位事实直接对接时，才保留 `Left/Right`
  - 如缺手检查
  - 身体部位损坏
  - 与原版 body part 直接映射的桥接逻辑

## 五、二次重构时必须优先验证的验收口

### 1. 主攻击投影仍然正确

必须确认：

- 自动攻击默认读到的还是正确主攻击
- 外部只能展示一个武器表面时，回退仍合理

### 2. 手动入口和自动入口仍分层

必须确认：

- 玩家按钮逻辑不污染自动 AI
- 自动 AI 也不绕过真实攻击宿主

### 3. 标准近战 / 远程仍是真原版链

必须确认：

- 不是表演式假近战 / 假射击

### 4. 非 Verb 表达仍回到正确宿主

必须确认：

- Ability 走 Ability
- Hediff 走 Hediff
- 组合第三表达按其类型投影

### 5. 真值边界不再互相打架

必须确认：

- 资源真值只有一处
- 战斗体相位真值只有一处
- 触发体只有镜像或局部状态，不再和正式相位并列双真值

### 6. 扩展接口必须真实可用

必须确认：

- 主模组暴露出来的扩展接口，足以支撑后续内容扩展
- 新内容不需要到处 patch 主业务内部才能接入
- 测试模组可以只通过公开接口和扩展点，就把测试内容挂进去

这里虽然属于后续标准，
但它本质上也是重构是否成功的重要标志。

## 六、当前阶段的停止条件

在正式开始二次重构设计前，
只要满足下面几条，就不再继续扩读旧代码：

- 已能完整描述“表达来源 -> 合成 -> 执行 -> 投影”的主链
- 已明确普通表达与组合第三表达的宿主落点
- 已明确 `CompTrion / CombatBodyState / CompTriggerBody` 的真值边界
- 已形成这份“需求骨架 + 禁区清单”

我认为截至当前，这几个条件已经满足。

## 七、接下来该做什么

下一步不该继续考古。

应进入：

- 二次重构的概念骨架设计
- 模块与核心边界初稿
- 最小起步方案

并且始终以上面这些约束为前提。

## 八、后续落实代码时的工作原则

### 1. 先查摘要，再查旧代码，再实现

后续每次准备落实某个具体功能时，都必须先做下面三步：

1. 先回看当前项目中已沉淀的研究记录和决策记录，确认该功能所属系统、边界和大方向
2. 再回到旧 BDP 中，针对性查相关代码，确认真实细节、时序和宿主行为
3. 最后才开始写新代码

禁止直接靠会话记忆、印象或压缩后的模糊认识硬写。

### 2. 先确认“外在表现需求”，再确认“内部实现方向”

每次实现前都要先回答：

- 这个功能在旧 BDP 中对外到底表现成什么
- 哪些是本质规则
- 哪些只是旧实现或临时表现

确认后，才能决定新架构里怎么落。

### 3. 主模组接口要按“未来可扩展”认真设计

虽然后置测试模组主要只给用户自己用，
但为了支持它而暴露的接口，
应视为未来内容扩展接口的雏形。

所以这些接口不能随便应付，
而要尽量做到：

- 宿主清楚
- 责任清楚
- 接入方式自然
- 不要求扩展方硬改主业务内部
