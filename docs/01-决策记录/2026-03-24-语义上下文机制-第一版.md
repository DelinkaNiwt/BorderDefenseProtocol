# 语义上下文机制（第一版）

## 目的

为 BDP 增加一层统一的“语义上下文”机制，让跨链路传递的不只是结果，还能保留来源语义。

当前最明确的需求包括：

- 攻击行为造成伤害后，伤口等下游结果能够知道“这次攻击行为本身是谁”
- 战斗体崩裂等状态变化发生后，下游能够知道“为什么发生”

## 名称

本项目当前正式使用：

- `语义上下文`

英文内部名可使用：

- `SemanticContext`

## 它是什么

它是一种轻量、统一、可传递的信息载荷。

它用于表达：

- 这次过程是谁
- 它对外应叫什么
- 它属于什么来源种类
- 它为什么发生
- 它由谁发起
- 它还带着哪些额外语义

## 它不是什么

它不是：

- 业务逻辑协调者
- 事件总线
- 真值 owner
- 大而全的全局状态容器

它更像“跟着过程流动的一封信”，而不是“指挥整个系统的大脑”。

## 当前推荐最小字段

第一版建议固定这些共通字段：

- `Id`
- `DisplayLabel`
- `SourceKind`
- `ReasonKey`
- `Instigator`
- `Tags`
- `ExtraData`

其中：

- 固定字段负责承接高频共通语义
- `ExtraData` 负责承接少量特例，不把未来所有需求提前写死

## 第一批正式接入范围

当前只接两条链：

### 1. 攻击行为链

范围：

- 表达来源
- 攻击行为生成
- 伤害落地接口预留

目标：

- 下游伤害结果能够知道“这次攻击行为的身份语义”

### 2. 崩裂原因链

范围：

- `CombatBodyCoordinator.TriggerCollapse(reason)`
- 崩裂相关事件参数与后续处理预留

目标：

- 下游处理能够知道“这次崩裂的触发原因”

## 当前不接入的范围

第一版先不接：

- 全部资源变化
- 全部 UI 展示
- 全部组合技
- 全部日志系统
- 全部 XML 配置层

原因：

- 先验证这层机制是否自然、清晰、好维护
- 避免一上来扩散成新的大层级

## 一句话结论

语义上下文机制的任务是：

- 让结果在跨链路传递时，不丢掉来源语义

而不是：

- 再造一个看起来很漂亮、实际上吞一切的总架构
