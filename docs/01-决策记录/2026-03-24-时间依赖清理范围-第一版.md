# 时间依赖清理范围（第一版）

## 目的

明确本轮“清理错误使用 tick 方案”之后，当前工程里哪些时间依赖已经去掉，哪些仍然保留且属于合法时间过程。

## 已清理

以下内容不再依赖 `CompTick()` 或查询入口顺手补结算：

- Trigger 槽位激活结果成立
- Trigger 槽位关闭结果成立
- 表达来源是否有效
- 手动按钮是否出现
- 自动远程入口是否读到当前主远程表达
- 自动近战入口是否读到当前主近战表达

同时：

- `CompTriggerBody` 已去掉 `CompTick()`
- `ResolveSwitching()` 已从查询口和接口中移除
- 切换表现不再通过 tick 或查询去主动清空，只在读取时按时间判断“现在是否仍在表现期”
- 查询热路径上的大部分诊断日志已移除

## 当前仍保留的时间依赖

以下内容当前仍然使用时间点，但属于允许保留的时间过程：

### 1. Trigger 切换表现

涉及：

- `SwitchContext.phaseEndTick`
- `CompTriggerBody.GetCurrentTick()`

用途：

- 只回答“这段预热 / 退场表现现在是否还在持续”
- 不再决定逻辑激活是否成立

### 2. Trion 持续消耗与自然恢复

涉及：

- `CompTrion.CompTick()`
- `drainSettleTick`
- `recoveryTick`

用途：

- 聚合消耗结算
- 自然恢复结算

这属于资源时间过程，本来就允许依赖时间推进。

### 3. CombatBody 冷却与崩解剩余时间

涉及：

- `CombatBodyState.cooldownEndTick`
- `CombatBodyState.collapseStartTick`

用途：

- 回答剩余冷却时间
- 回答崩解表现剩余时间

当前它已经不会再要求外部 tick 先跑过一遍才能再次激活，但这部分系统仍未正式装配到主模组主线。

## 当前结论

本轮之后，当前工程里“错误的时间依赖”主要已经从 Trigger 主链上清掉。

剩余时间依赖主要集中在两类：

- 合法的时间过程
- 还未正式接入主线、后续要继续重构的 CombatBody 预备骨架

## 一句话结论

现在不能再把“看见时间字段存在”直接等同于“还在拿 tick 当逻辑前提”。

真正需要警惕的是：

- 逻辑结果是否要等时间流动才成立
- 查询入口是否顺手在偷偷补结算
