# 攻击执行边界与运行时驱动裁定（第一版）

## 当前有效裁定

主模组当前正式采用：

- Pawn 侧薄执行入口
- AttackExecution 内部攻击编排层
- Trigger / Expressions 保持原边界
- 近战 / 远程继续回到 RimWorld 自然运行时链

## 一句话裁定

攻击执行边界当前正式收口为：先由 Pawn 侧薄执行入口承接“执行哪条正式表达”的请求，再在 `AttackExecution` 内部形成一份通用攻击编排，最后才分流到近战或远程正式运行时链；`CompTriggerBody` 不再承担正式攻击执行入口职责，`Expressions` 不再承担正式攻击执行职责。

## 直接排除

下列方向当前不采用：

- 把执行主责重新塞回 `CompTriggerBody`
- 让手动按钮直接把裸 `Verb` 当正式执行边界
- 让自动远程 / 自动近战 patch 直接临时决定谁来打
- 先新增新的攻击 `Comp` 作为默认承载位

## 为什么不把执行挂回 Trigger

`CompTriggerBody` 当前正式职责是：

- 装载
- 局部激活
- 侧别 / 槽位 / 当前形态事实

如果再让它承担：

- 攻击正式起手
- 持续推进总入口
- 执行结束收尾

就会重新长回旧 BDP 那种“装载、表达、执行、运行时全往 Trigger 里堆”的对象膨胀。

## 为什么不用“各走各的原版对象”直接散接

如果不先收一个统一入口，而让：

- 手动按钮自己找 verb
- 自动远程自己找 verb
- 自动近战自己找 verb
- 近战 / 远程各自进入自己的原版链

那最后仍然回答不清：

- 谁负责正式执行
- 谁负责把表达结果送进正确运行时链

这会把当前卡点继续保留为“很多地方都沾一点执行，但没人正式总负责起手”。

## Pawn 侧薄执行入口的正式含义

这里的“Pawn 侧薄执行入口”不是新真值 owner，也不是新总控系统。

它只正式负责：

1. 接收一次执行请求
2. 校验该表达当前是否仍然成立
3. 生成一份通用攻击编排
4. 判断该编排属于近战还是远程主链
5. 把请求分流到对应正式执行器

它不负责：

- 保存 Trigger 真值
- 保存 Expressions 真值
- 持有长期执行中状态镜像
- 吞掉 `JobDriver` / `Verb` / `Projectile` 的原本职责

## JobDriver 的正式位置

`JobDriver` 当前正式定位为：

- Pawn 级持续推进器之一

不是：

- 整个攻击运行时本体
- 表达结果 owner
- 统一执行边界本体

也就是说：

- 需要持续追击、持续射击、burst 推进时，可以由 `JobDriver` 推进
- 但攻击运行时不能被重新压回“一个大 JobDriver 包办全部”

进一步明确：

- `JobDriver` 只回答“这次已经确认好的步骤怎样跨 tick 往前走”
- 它不重新选择表达结果
- 它不拥有攻击编排
- 它不替代 `Verb` 承担真正发射或真正伤害落地

## 攻击编排层的正式位置

攻击编排层当前正式定位为：

- AttackExecution 的内部组织层

它只负责回答：

- 这次攻击是否由一到多步组成
- 这些步骤是顺序关系还是并列关系
- 每一步由哪条正式结果、哪一侧去执行
- 每一步是单发还是多发
- 整体是否需要持续推进

它不负责：

- 保存 Trigger 真值
- 重新计算 Expressions 真值
- 替代 `Verb` / `JobDriver` / `Projectile` 成为运行时本体

这层的存在目的，是把“如何组织执行”从 UI、patch、`CompTriggerBody`、零散特殊 verb 中收回来，形成主模组内部唯一正式编排口。

## 副攻击的正式定位

副攻击当前正式裁定为：

- 与主攻击共享同一套执行边界
- 与主攻击共享同一套攻击编排层
- 与主攻击共享同一套运行时链

它不是：

- 平行于主攻击的另一套执行系统
- 特殊 UI 旁路
- 专门为了旧 BDP 兼容而保留的历史例外

副攻击只允许体现在：

- 正式结果身份差异
- 默认选择权差异
- 攻击编排内容差异

不能体现在“再造一套执行架构”。

## 对旧 BDP 需求的正式承诺

旧 BDP 的具体现象当前只作为架构验收样本，不能反向决定架构形状。

当前架构必须天然支持这些样本，但不能只为它们定制：

- 单侧齐射
- 双侧顺序攻击
- 双侧同时攻击
- 双侧混合攻击
- 独立副攻击

如果后续实现这些需求时必须新增大量平行入口、平行宿主或平行运行时，说明架构走错，应优先回看攻击计划层设计，而不是继续堆特判。

## 远程链的正式责任划分

- 统一执行入口：负责接单与分流
- 攻击编排层：负责先把这次请求整理成通用执行步骤
- 远程执行器：负责把请求送进正式远程链
- `JobDriver`：负责持续驱动远程攻击过程（如需要）
- `BdpVerb_Shoot`：负责正式发射
- `Projectile`：负责飞行后半段
- 原版伤害链：负责命中、爆炸、伤害、效果落地

## 近战链的正式责任划分

- 统一执行入口：负责接单与分流
- 攻击编排层：负责先把这次请求整理成通用执行步骤
- 近战执行器：负责把请求送进正式近战链
- `JobDriver`：负责持续追击、连击、burst 推进（如需要）
- `BdpVerb_MeleeAttackDamage`：负责近战正式伤害落地
- 原版近战伤害链：负责最终伤害结算

## 为什么不新增新的攻击 Comp

当前不新增新的攻击 `Comp`，原因不是“以后永远不能有”，而是现阶段它只会把责任再打散一次：

- Trigger 已经拥有装载、槽位、启停真值
- Expressions 已经拥有“当前成立了什么”的正式结果
- AttackExecution 已经承担正式执行边界与编排

如果此时再加一个新的攻击 `Comp`：

- 它要么重复保存上面某一层已经拥有的事实
- 要么又变成一个“什么都沾一点”的旁路总控

这会让主模组重新回答不清：到底谁负责执行、谁负责推进、谁负责结束。

## 为什么采用 Pawn 侧薄执行入口

采用 Pawn 侧薄执行入口，是因为这次攻击真正发生在“这个 Pawn 此刻准备打谁”的时刻。

把入口放在这里，才能自然承接：

- 手动按钮点选目标后的执行请求
- 自动远程的攻击起手
- 自动近战的攻击起手

同时又不把 Trigger、Expressions、Verb、JobDriver 的职责吞进去。

所以它“薄”的含义就是：

- 只接单
- 只校验
- 只编排
- 只分流

而不是成为新的真值 owner 或新的大总控。

## 对当前主模组的直接要求

后续实现必须满足：

- 手动按钮先走统一执行入口
- 自动远程先走统一执行入口
- 自动近战先走统一执行入口
- `ExpressionVerbBridge` 降级为辅助桥，不再承担正式执行边界角色
- `CompTriggerBody` 继续只回答 Trigger 事实，不越权承担正式执行入口

进一步明确：

- 自动远程 / 自动近战的 patch 只允许承担“桥接原版自动起手事件”的薄职责
- 不允许继续把“给原版补一个 Verb，让原版自己继续打”当成自动攻击的正式边界
- 自动攻击也必须先翻译成正式攻击订单，再进入 `AttackExecution`

## Targeting 适配层的正式裁定

本轮新增正式裁定：

- BDP 不把裸 `Verb` 重新扶正为正式执行边界
- 但 BDP 必须正式接入原版 `ITargetingSource` / `Targeter` 语义链
- 因此新增一层通用 `AttackExecutionTargetingSource`（攻击执行目标选择适配源）

这层的正式职责只有一件事：

- 把 `formal result`（正式表达结果）翻译成原版 `ITargetingSource`

它不负责：

- 保存表达真值
- 重新决定该执行哪条表达
- 直接替代 `AttackExecution` 成为正式执行边界

所以这层的正式位置是：

```text
formal result
    -> AttackExecutionTargetingSource
        -> ITargetingSource
            -> Targeter
```

而不是：

```text
formal result
    -> targeting UI
        -> callback
            -> 裸 Verb
```

## 为什么适配层必须做成通用层

这层当前虽然先由手动入口使用，但它不是“手动按钮特供件”。

正式原因有三点：

1. 它解决的是“BDP formal result 怎样进入原版 targetingSource 体系”这个共性问题，不是“手动按钮怎样点目标”这个局部问题。
2. 如果把它做成手动专属件，后续别的入口要接 `Targeter` 时，还会再长出第二份近似逻辑。
3. 一旦适配层持有“只有手动入口才有的固定真值”，它就会从翻译层滑成业务层。

因此正式裁定是：

- 手动入口只是第一批调用方
- 不是适配层的拥有者

## 为什么采用会话型轻量缓存

`AttackExecutionTargetingSource` 当前正式采用：

- 会话型轻量缓存

而不采用：

- 永久缓存 formal 真值
- 每次 UI 查询都重新全量解析

原因是：

- `OnGUI(...)`
- `ValidateTarget(...)`
- `DrawHighlight(...)`
- `GetVerb`
- `targetParams`

这些成员在一次 targeting 会话中会被高频读取。

如果完全不缓存，就会在同一帧或同一 tick 中重复做：

- 读表达快照
- 按 `ResultId` 找结果
- 解析真实 `Verb`

这对单机模组也没必要。

但如果做永久缓存，又会把适配层错误地推成“结果真值 owner”。

因此正式裁定是：

- 只缓存“当前 targeting 会话里这一个 tick 的解析结果”
- 一旦 `Pawn / 地图 / 主武器 / ResultId / DispatchIntent` 显著变化，就允许失效重建

## 为什么 OrderForceTarget(...) 必须回到 AttackExecution

原版 `Targeter` 的 `OrderForceTarget(...)` 语义，本质上是在说：

- 玩家已经确认目标
- 现在要正式下单

在 BDP 里，这个“正式下单”不能直接变成：

- `verb.TryStartCastOn(...)`

因为那样只是在 UI 层临时打一手，根本没有进入正式执行边界。

所以当前正式裁定是：

```text
Targeter
    -> AttackExecutionTargetingSource.OrderForceTarget(...)
        -> AttackExecution.TryExecute(...)
            -> DispatchIntent = ForceTargetOrder
                -> 执行器
                    -> BDP JobDriver 持续推进链
```

这样才能同时满足两件事：

- BDP 先经过自己的正式执行边界
- 原版 `Targeter / OnGUI / ValidateTarget` 交互语义继续保留在前段
- 正式持续攻击真值继续留在 BDP 自己的执行链里，而不是偷偷交回裸 `Verb`
