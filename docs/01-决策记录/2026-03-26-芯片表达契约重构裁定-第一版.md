# 芯片表达契约重构裁定（第一版）

## 目的

这份裁定用于正式推翻“芯片表达按四类来源列表平铺组织”的未来标准地位，
并把新 BDP 的芯片正式输入收口为：

- 一枚芯片
- 一组统一表达条目
- 一组形态操作

它不是实现草稿，
而是主模组公开契约边界的重定。

## 一、先下总结论

### 1. 芯片的正式输入单位不是四类来源列表，而是一组统一条目

旧思路更像：

- `verbSources`
- `abilitySources`
- `hediffSources`
- `passiveSources`

这对简单芯片能用，
但不适合作为长期标准。

新标准改为：

- 芯片先声明一组统一条目
- 每条条目再声明自己属于哪一类

对玩家更好理解的话说就是：

- 一枚芯片有几种本事
- 每种本事是一条条目
- 每条条目自己说明是攻击、能力、状态还是被动

### 2. 形态切换不是“命中就追加”，而是“对条目做操作”

旧思路里的形态块更像：

- 当前形态命中后，再往系统里额外塞一堆来源

这会让形态慢慢退化成隐藏堆叠器。

新标准改为：

- 基础条目集始终存在
- 形态块只对基础条目做显式操作

第一版只承认三种操作：

- `Append`
- `Replace`
- `Disable`

### 3. 混合芯片默认允许，且默认并列

一枚芯片允许同时声明：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

第一版默认解释为：

- 并列条目

系统不自动猜：

- 哪条是主，哪条是附属
- 哪条是某条攻击的副作用

只有在契约中显式声明关系时，
系统才承认关系语义。

### 4. 从属关系纳入结构预留，但不抢第一优先级

第一版正式预留：

- `RelationKind`
- `ParentEntryId`

但第一版只轻量承认两种关系：

- `Independent`
- `Attached`

第一版不允许从属关系直接改写：

- 默认主攻击选择
- 自动攻击选择
- 当前结果成立判定

它先只作为：

- 芯片解释语义
- 未来按钮分组依据
- 未来说明排序依据

### 5. 主模组内部必须新增 `Contract` 层

当前表达系统目录不应继续只有：

- `Access`
- `Config`
- `Model`
- `Pipeline`
- `Projection`

必须新增：

- `Contract`

其职责是：

- 把作者写的原始芯片配置解释成主模组正式承认的芯片契约

正式切分为：

- `Config`：作者原始写法
- `Contract`：系统正式承认的芯片契约
- `Pipeline`：根据当前真值计算当前成立结果
- `Projection`：把结果投影到按钮、自动攻击、视觉、说明、宿主

## 二、为什么旧标准不再适合作为未来主结构

### 1. 对玩家不直观

玩家理解芯片时，
会理解成：

- 这枚芯片会什么
- 切形态后它会什么

不会理解成：

- 这里一组 `Verb`
- 那里一组 `Hediff`

### 2. 对内容作者不够好写

当芯片开始混合时，
四列表结构会越来越难写清：

- 一个攻击和一个状态是并列还是主从
- 一个形态是在替换旧攻击还是加一个新攻击
- 一个被动是整枚芯片被动还是某个主动条目的附带效果

### 3. 对内部系统不够好解释

主模组真正想知道的是：

- 这枚芯片当前有哪些正式条目
- 当前形态下这些条目怎样展开
- 当前时刻哪些条目进入结果链

统一条目结构比四列表更贴近这个问题本身。

## 三、前后变更总表

## 1. 作者写法的前后变化

旧写法：

- 芯片先按四类列表分组
- 形态块里再按四类列表分组
- 当前形态命中后追加来源

新写法：

- 芯片先声明统一 `Entries`
- 每条条目自己声明 `Kind`
- 形态块通过 `Operations` 修改条目集

## 2. 主模组解释路径的前后变化

旧路径：

- `Config`
- declaration provider 直接解释原始来源
- `Pipeline`

新路径：

- `Config`
- `Contract`
- `Pipeline`

也就是说：

- `Pipeline` 不再直接吞原始芯片配置

## 3. 名词层面的前后变化

旧主名词：

- 来源
- 四类来源列表
- 形态来源追加

新主名词：

- 条目
- 统一条目集
- 形态操作

## 4. 结构保留项

以下内容保留：

- 四大顶层类型：
- `Verb`
- `Ability`
- `Hediff`
- `Passive`
- Trigger / Expression / Projection 分层
- 默认主远程 / 默认主近战并列
- Special 武器拦截

## 5. 结构删除项

以下内容不再作为未来标准保留：

- 芯片表达按四类列表平铺作为主设计
- 形态命中后无脑追加来源
- `Pipeline` 兼做芯片契约解释器

## 6. 不做长期双轨

这次不是：

- 先偷偷保留旧四列表主路径
- 再慢慢说以后有空再删

而是明确裁定：

- 旧四列表可以只在迁移过程里短暂停留
- 但不能继续作为主模组未来标准

原因不是“代码洁癖”，而是很实际：

- 双轨会让内容作者不知道到底哪套才算正式写法
- 双轨会让 `Pipeline` 和 `Projection` 被迫继续兼容错误结构
- 双轨会把后续 bug 解释成本抬高
- 双轨会让主模组边界长期不干净

所以这次重构的目标不是“兼容旧中心”，
而是把旧中心彻底降级为迁移残留，
并在本轮任务内尽量切干净。

## 四、正式新标准

## 1. 芯片整体配置

建议正式改为：

- `ChipExpressionContractConfig`

它至少包含：

- `Entries`
- `Modes`

它回答的是：

- 这枚芯片整体声明了哪些表达条目
- 它有哪些形态块

## 2. 统一条目

建议正式改为：

- `ChipExpressionEntryConfig`

每条条目最少字段：

- `Id`
- `Label`
- `Kind`

## 五、主模组分层边界裁定

### 1. `Config`

`Config` 只回答：

- 作者在芯片 Def 上原始写了什么

它不回答：

- 系统最终承认了什么
- 当前时刻哪些条目成立

### 2. `Contract`

`Contract` 只回答：

- 主模组正式接受哪些条目
- 当前形态如何把条目展开成正式契约
- 哪些配置错误会被判为无效、警告或拒收

它不回答：

- 当前按钮是什么
- 当前默认主攻击是什么
- 当前视觉该怎么画

### 3. `Pipeline`

`Pipeline` 只回答：

- 在当前 Trigger / CombatBody / Trion 正式事实下
- 契约条目里哪些当前成立
- 最终正式结果总表是什么

它不再负责：

- 直接读取原始四列表配置
- 猜测作者本意

### 4. `Projection`

`Projection` 只回答：

- 结果怎样投影成按钮、主攻击、视觉、说明、宿主同步

它不再负责：

- 解释芯片原始写法
- 重做一套成立裁定

### 5. Trigger 的边界

Trigger 继续是：

- 装载 owner
- 局部激活事实 owner
- 形态事实 owner

Trigger 不是：

- 芯片条目解释器
- 表达结果 owner
- 投影规则 owner
- `RoleKey`
- `Tags`
- `Conditions`
- `Trion`
- `RelationKind`
- `ParentEntryId`

其中：

- `Kind` 统一承认四类：
- `Verb`
- `Ability`
- `Hediff`
- `Passive`

## 3. 条目专属字段

### `Verb`

至少包括：

- `WeaponMode`
- `VerbProps`

### `Ability`

至少包括：

- `AbilityDefName`

### `Hediff`

至少包括：

- `HediffDefName`
- `ApplyMode`

### `Passive`

至少包括：

- `PassiveKey`
- `ExposedData`

## 4. 形态块

建议正式改为：

- `ChipExpressionModeConfig`

每个形态块至少包含：

- `ModeKey`
- `Operations`

## 5. 形态操作

建议正式改为：

- `ChipExpressionModeOperationConfig`

每条操作至少包含：

- `Action`
- `TargetEntryId`
- `Entry`

第一版动作枚举固定为：

- `Append`
- `Replace`
- `Disable`

## 五、当前旧结构的处理裁定

### 1. 旧四列表结构不再作为未来标准继续维护

也就是说：

- `VerbSources`
- `AbilitySources`
- `HediffSources`
- `PassiveSources`

不再是未来芯片契约的正式推荐写法。

### 2. 主模组实现应直接转向新结构

这里不建议长期保留“双轨并存、慢慢过渡”的策略。

原因是：

- 芯片契约是主模组的最上游输入
- 如果这里长期双轨并存，后面 `Contract / Pipeline / Projection` 都会被双轨污染

因此应采用：

- 一次任务内完成结构切换
- 旧结构直接退出主设计舞台

### 3. 若短期需要兼容，只能视为迁移脚手架

即便实现阶段临时保留旧读法，
也只能视为：

- 迁移期脚手架

而不能再把它写进正式需求说明或未来标准。

## 六、从属关系的正式边界

### 1. 第一版只轻量预留

第一版承认：

- 某条条目可以附着到另一条条目

但第一版不承认：

- 复杂多级树
- 关系驱动的自动攻击规则
- 关系驱动的结果成立裁定

### 2. 第一版的作用范围

第一版只允许从属关系影响：

- 芯片解释语义
- 将来按钮分组
- 将来说明排序

### 3. 第一版不允许关系越位

从属关系不能越位去替代：

- Trigger 真值
- 表达结果成立条件
- 默认主攻击选择器

## 七、对全模组边界的影响

### 1. Trigger 不受污染

Trigger 仍然只负责：

- 装载
- 激活
- 局部规则
- 形态键

不负责解释芯片条目。

### 2. 表达系统的职责更清楚

表达系统内部正式分三段：

1. 芯片契约解释
2. 当前成立结果计算
3. 结果投影与宿主回接

### 3. 外部内容作者的学习成本下降

外部作者不需要先理解四套来源列表怎么配合，
而只需要理解：

- 一枚芯片有哪些条目
- 每个形态怎样修改这些条目

## 八、代码落地切口

本次重定不接受长期双轨。

代码落地建议按以下切口直接推进：

1. 新增 `Core/Expressions/Contract`
2. 将当前 `ChipExpressionConfig` 改写为统一条目结构
3. 将当前 `ChipExpressionModeConfig` 改写为 `Operations`
4. 删除旧四列表在主代码中的直接读取逻辑
5. 新增芯片契约解释器
6. 让 `Pipeline` 改为只消费契约对象
7. 再回收 `Projection` 与宿主回接

## 九、当前后续落地任务

这份裁定落地后，后续任务应按以下顺序推进：

1. 改写芯片标准结构说明
2. 改写表达系统骨架文档，新增 `Contract` 层
3. 直接调整主模组代码结构：
- 新增 `Contract`
- 芯片配置改为统一条目
- 形态改为操作模式
4. 删除旧四列表在主设计中的地位
5. 再回接 `Pipeline / Projection`

## 十、一句话总括

这次裁定的核心不是“给芯片换个写法”，
而是正式承认：

- 芯片对 BDP 的真正输入单位是“统一条目契约”

而不是：

- 四类来源列表的拼装容器
