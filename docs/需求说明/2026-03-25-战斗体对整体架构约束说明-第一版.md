# 战斗体对整体架构约束说明（第一版）

## 目的

这份说明不重复讲战斗体有哪些表现，
也不重复讲旧 BDP 里每个类怎么写。

它只回答一件事：

- 战斗体这个领域真相，如何反向约束整个 BDP 的架构

也就是说，这份文档的重点不是：

- 战斗体局部怎么实现

而是：

- `CompTrion`
- `CombatBodyState`
- `CompTriggerBody`
- `Snapshot`
- `Hediff`
- `Host`
- `事件通信`

这些对象和层，在战斗体存在的前提下必须怎样分责，
否则模组整体结构会再次失真。

## 一、先下总结论

### 1. 战斗体不是局部功能，而是全模组的域切换主轴

战斗体不是：

- 某个 Trigger 的附属功能
- 某个 Hediff 的局部效果
- 某个 Trion 扣费动作的外包装

战斗体的本质是：

- `真身域 -> 战斗域 -> 真身域`

的一次正式域切换。

因此它天然会同时约束：

- 资源系统
- Trigger 装载系统
- Pawn 身体状态表达
- 快照与恢复
- 阶段事件通信

### 2. 战斗体不能成为第四个真值核心

战斗体很重要，
但它不能因为重要就膨胀成“第四个 owner 中心”。

当前正式边界仍必须保持：

- `CompTrion`：资源真值
- `CombatBodyState`：战斗体外层相位真值
- `CompTriggerBody`：装载与局部激活真值

战斗体协调层只能做：

- 编排进入事务
- 编排离开事务
- 汇总原因
- 触发事件通知

它不能做：

- 再持一份资源账本
- 再持一份 Trigger 装载镜像
- 再持一份快照总状态

### 3. 战斗体对整体架构的最大要求，不是多写功能，而是强制全模组承认三核心边界

只要战斗体这条主轴成立，
模组里其它系统就必须一起接受：

- 资源真值不许分叉
- Trigger 不能越位成战斗体 owner
- Snapshot 不能散落到多个对象顺手恢复
- 事件只能通知，不能变相持真值

## 二、战斗体对三核心骨架的正式约束

## 1. 对 `CompTrion` 的约束

### 1.1 战斗体只能请求资源动作，不能持资源镜像真值

战斗体需要正式依赖资源结算，
但它不应自己持有：

- 当前总量
- 当前可用量
- 当前占用明细
- drain 注册表

战斗体可以正式请求：

- 锁定进入战斗体所需占用
- 主动解除时释放占用
- 被动破裂时执行耗尽或强制结算
- 注册或注销战斗体维持消耗

### 1.2 资源不足只能是战斗体事务的失败结果，不能倒逼资源 owner 越权改相位

`CompTrion` 可以返回：

- 可支付
- 不可支付
- 当前可用值耗尽

但它不能直接做：

- 把 `CombatBodyState` 改成崩解
- 把 Trigger 关闭

它只能通过：

- 正式返回结果
- 正式广播事件

让上层协调者决定接下来怎么走。

## 2. 对 `CombatBodyState` 的约束

### 2.1 它只持有战斗体外层相位真值

它应正式持有：

- 当前相位
- 相位剩余时间
- 崩解原因
- 当前战斗体阶段锁定的总 Trion 量

它不应持有：

- 槽位数据
- 芯片激活集合
- Ability / Hediff / Verb 结果
- 快照内容

### 2.2 相位必须在事务成立后提交

`Active`、`Collapsing`、`Cooldown`
都不能只是意图标志。

它们必须是：

- 进入事务已经成立后的正式结果
- 离开事务已经提交后的正式结果

否则外部会读到“名义上已进入，但底层还没成立”的伪状态。

## 3. 对 `CompTriggerBody` 的约束

### 3.1 Trigger 只能提供装载事实与局部能力事实

Trigger 在战斗体上下文中正式负责的是：

- 当前装了什么芯片
- 当前局部激活什么
- 当前哪些芯片声明了多少战斗体占用

它不正式负责的是：

- 决定整体是否进入战斗体
- 决定整体何时崩解
- 决定整体何时退出并冷却

### 3.2 Trigger 不得继续保留战斗体镜像真值

像旧 BDP 中的：

- `IsCombatBodyActive`

这类镜像标志，
在二次重构里不应再作为正式真值存在。

因为它会造成：

- Trigger 和 CombatBody 双方都像 owner
- 外部代码不知道该信谁

### 3.3 Trigger 可以声明资源需求，但不能执行战斗体资源事务

更合理的边界是：

- Trigger 负责汇总已装载芯片的占用声明
- CombatBody 协调层拿这个声明去请求 `CompTrion`

而不是：

- Trigger 自己 `Allocate`
- Trigger 自己 `Release`

## 三、战斗体对局部模块化结构的约束

## 1. 战斗体需要的是“局部事务模块”，不是超级子系统

战斗体周边最适合的不是一个超大 runtime，
而是一组围绕单一切面的局部模块。

建议的局部模块化方向是：

- `CombatBodyActivationRules`
- `CombatBodyEnterPipeline`
- `CombatBodyExitPipeline`
- `CombatBodySnapshotService`
- `CombatBodyMaintenanceBridge`
- `CombatBodyEmergencyEscape`

这些模块都可以存在，
但它们都不能持有三核心真值。

## 2. 进入链与离开链必须分为两个局部事务模块

因为它们虽然对称，
但不属于同一个局部切面。

更合理的分法是：

- 进入链：只回答如何从真身域正式进入战斗域
- 离开链：只回答如何从战斗域正式退出到真身域

而不是：

- 一个大模块既处理进入又处理所有清理又处理所有资源又处理所有恢复

## 3. Snapshot 必须成为正式局部模块，不能继续散装

战斗体文档已经说明：

- 进入时要建立回滚锚点
- 离开时要恢复真身状态

这意味着 Snapshot 不是补丁性质的小工具，
而是战斗体主链里的正式事务协作者。

因此它应收束成明确模块，
而不能继续分散到：

- Host
- Cleanup
- Trigger
- 某些 Hediff 侧效果

## 四、战斗体对事件通信的正式约束

## 1. 事件只能通知事实变化，不能承载阶段真值

战斗体相关事件应只表达：

- 进入成功
- 离开成功
- 崩解开始
- 冷却开始
- 相位变化

它们不能替代：

- `CombatBodyState`

也不能要求外部通过“最近收到什么事件”来倒推出当前相位。

## 2. 资源事件与战斗体事件不能混成一条总线

更合理的关系是：

- `CompTrion` 广播资源侧事件
- CombatBody 协调层监听并裁定是否进入崩解
- CombatBody 自己广播相位事件

而不是：

- 一条总线同时假装自己在持有资源事实和相位事实

## 3. Trigger 事件与 CombatBody 事件应保持平行，而不是从属

因为二者 owner 不同。

更自然的结构是：

- Trigger 广播装载与局部激活变化
- CombatBody 广播整体相位变化
- 两边通过协调层或观察者联动

而不是：

- 把 Trigger 事件当成 CombatBody 事件的子集
- 或把 CombatBody 事件回灌给 Trigger 作为正式真值

## 五、战斗体对 RimWorld 原版宿主映射的约束

## 1. 战斗体必须优先贴 Pawn 身体与状态语义

旧研究已经确认：

- 战斗体整体更贴 `Hediff/HediffComp`

这不等于“战斗体 = Hediff”，
而是说：

- 它的身体域表达、持续状态存在、序列化附着点
- 天然更接近 Pawn 身体状态语义

## 2. 但不能把 `Hediff` 误当总协调者

`Hediff` 更适合作为：

- 正式附着点
- 身体状态表达点

而不是：

- 进入/离开总流程控制器

真正的总流程仍应由 CombatBody 协调层编排。

## 3. Trigger 继续贴装备语义，不回退到“平行身体系统”

战斗体再重要，
也不能把 Trigger 从装备侧扯走。

Trigger 仍应继续贴：

- `CompEquippable`
- 装备装载
- 装备局部命令
- 装备侧桥接

否则整个模组会重新滑向“脱离 RimWorld 的平行游戏”。

## 六、战斗体对 Snapshot / 恢复 / Cleanup 的约束

## 1. 恢复链必须是主链的一部分，不是离场补丁

只要战斗体允许进入，
就必须从一开始同步定义：

- 何时快照
- 何时应用变换
- 何时恢复
- 何时清理残留

否则“进入”会被正式化，
而“回去”仍然是散装后补。

## 2. Cleanup 更适合作为离开侧事务协作者

从整体架构看，
Cleanup 的自然位置是：

- 离开事务里的收尾协作者

而不是：

- 第二个平行主协调者

它可以负责：

- 关闭局部能力
- 清理残留状态
- 调用恢复动作
- 提交冷却后的收尾步骤

但它不应自己决定：

- 是否进入离开链
- 是否进入崩解链
- 何时提交相位变化

## 七、战斗体对 Host 的约束

## 1. Host 只能做正式挂接点

`PawnCombatBodyHost` 一类对象，
更适合承担：

- 把 Pawn 与 CombatBody 主链接起来
- 暴露最小正式入口
- 承担宿主发现与桥接责任

它不适合承担：

- 新的总流程
- 新的真值
- 快照与恢复细节

## 2. 空桥位长期存在会诱导错误实现

如果 Host 长期只是空壳，
后续代码会很容易为了“先用起来”而绕开它，
最终重新回到：

- Trigger 直连
- Cleanup 直连
- 资源事件直连

这会破坏整体优雅性。

## 八、战斗体对现有代码调整方向的约束

## 1. 现阶段允许先调结构，不急着补完整行为

只要调整目标明确是：

- 让三核心边界更清楚
- 让 CombatBody 主链更单一
- 让 Snapshot / Cleanup / Host 回到正确位置

那么即使暂时不新增完整战斗体功能，
这类调整也是正式推进的一部分。

## 2. 当前最合理的优先调整对象

从整体角度看，
当前最合理的先手调整是：

- 让 `CombatBodyCoordinator` 成为唯一主链协调者
- 让 `CombatBodyCleanupCoordinator` 退回离开侧事务协作者
- 让 `PawnCombatBodyHost` 从空桥位变成正式挂接点
- 让 Trigger 侧彻底停止继续保留战斗体镜像真值或事务职责

## 九、一句话总括

战斗体对 BDP 整体架构提出的根本要求不是“再做一个强系统”，而是“在 `CompTrion / CombatBodyState / CompTriggerBody` 三核心边界不被打破的前提下，用一条克制的战斗体主链去编排 `真身域 <-> 战斗域` 的进入与离开事务，并让 Snapshot、Cleanup、Host、Hediff 与事件通信都只回到各自自然的位置，而不重新长成新的总控层”。
