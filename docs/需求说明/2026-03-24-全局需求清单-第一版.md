它不是实现计划。

它回答的是：

- BDP 现在已经确认要做什么
- 各项功能机制各自受什么规则约束
- 哪些属于当前必须做
- 哪些属于现在只留口
- 哪些应放到后续阶段

这份说明专门补足以下容易混淆、但对 BDP 极关键的知识点：

- 芯片先产出表达来源，不等于直接产出固定攻击对象
- 同时成立多少表达，不等于同时显示多少按钮
- 按钮数量，不等于可直接操作的攻击行为模式数量
- 主攻击投影，不等于玩家能操作的全部表达
- 对外兼容表面、自动攻击读取、视觉绘制跟随，也不等于手动按钮层
- 芯片形态切换会沿整条链连锁影响表达、按钮、组合、主攻击投影与外部表面

另一份说明专门补足：

- 旧 BDP 的复杂视觉表现是既有需求，不是重构新增玩法
- 信息面板与信息类模组兼容，是这次重构要新增强化的需求
- 多表达真实状态、视觉渲染、信息暴露、兼容回退、定点补丁边界，不是同一层

## 一、根本任务、根本目标、最终检验

### 1. 根本任务

- 基于旧 BDP 做第二次重构
- 只重构内部原理
- 不沿用第一次失败重构的总体架构

### 2. 根本目标

- 保留旧 BDP 的外在本质表现
- 把内部改成贴 RimWorld、边界清楚、可继续扩展维护的版本

### 3. 最终检验

- 第一层：100% 重现旧 BDP 的外在本质表现
- 第二层：这种重现来自更清楚的边界、统一规则、自然扩展能力，而不是把旧混乱原样抄一遍

### 4. 真标准

- `BorderDefenseProtocol.Legacy` 是唯一行为真标准
- 一次重构归档与文档只能辅助理解，不能替代旧代码事实
- 关键不明确处，以用户当前裁决为最高标准

## 二、全局硬约束

### 1. 必须从 RimWorld 出发，最后回到 RimWorld

优先贴这些原版宿主：

- `Verb`
- `Ability`
- `Hediff`
- `JobDriver`
- `Projectile`
- `Gizmo`
- `ThingComp`

### 2. 三类真值 owner 不能混

- `CompTrion` 只持有资源真值
- `CombatBodyState` 只持有战斗体相位真值
- `CompTriggerBody` 只持有装载与局部激活表达真值

### 3. 事件总线不是 owner

事件只能做：

- 通知
- 广播
- 协调

事件不能做：

- 资源真值中心
- 战斗体真值中心
- 底层唯一事实来源

### 4. patch 不是优先方案

- 只有确认原版没有合适、自然、可维护的通道时，才允许评估 patch
- patch 只负责接线，不负责承载复杂业务
- 使用 patch 前必须先记录边界、前置条件、影响范围、兼容风险

### 5. 正文只呈现结果

- 正文不保留“从旧改到新”的过程描述
- 过程痕迹留在日志和历史记录

### 6. 中文优先

- 中文优先
- 必须保留英文名词时，旁边给简短中文说明
- 文档、接口草案、代码、XML 都默认广覆盖注释

## 三、六块业务系统

当前统一按六块业务系统理解 BDP：

1. 资源系统
2. 战斗体系统
3. 触发体装载系统
4. 表达系统
5. 入口与展示系统
6. 崩解与收尾系统

另有两类支撑层：

- 工具收纳层
- 测试扩展层

其中：

- 前三块是核心真值块
- 第四块是核心业务块
- 第五块是对外投影块
- 第六块是跨块事务闭环块

## 四、资源系统需求与约束

### 1. 必须具备的资源语义

- `Cur / Max / Available`
- 正式占用 `Allocated`
- 预占用 `Reserved`
- 一次性消耗
- 持续消耗聚合
- 自然恢复
- 冻结与恢复
- 资源不足检查
- 可用值耗尽边界通知

### 2. 它负责什么

- 记账
- 状态查询
- 扣费请求
- 占用与释放
- 持续消耗注册与注销

### 3. 它不负责什么

- 不负责决定战斗体是否允许激活
- 不负责决定触发体激活哪枚芯片
- 不负责决定表达如何形成
- 不负责直接执行崩解流程

### 4. 特别约束

- 资源真值必须集中
- 资源系统可以被其它系统读取和请求，但不能被外部系统直接改字段
- 持续消耗与自然恢复允许依赖 tick
- 资源时间过程合法，但不能把它误写成“逻辑是否成立”的前提

## 五、战斗体系统需求与约束

### 1. 必须具备的相位

- `Inactive`
- `Active`
- `Cooldown`

完整目标中还包括：

- `Collapsing`

### 2. 必须支持的流程

- 手动激活
- 手动解除
- 被动崩解
- 冷却
- 快照恢复
- 身体变化恢复

### 3. 它负责什么

- 当前相位
- 激活条件检查
- 主动解除与被动崩解的外层流程
- 战斗体期间身体状态变化的时机

### 4. 它不负责什么

- 不负责槽位装载
- 不负责芯片表达合成
- 不负责按钮生成
- 不负责自动攻击桥接

### 5. 特别约束

- 主动解除与被动崩解不能混为一谈
- 崩解应保留“多来源 -> 单崩解入口 -> 延时解除”的整体结构
- 事件只广播阶段变化，不能替代相位真值

## 六、触发体装载系统需求与约束

### 1. 必须具备的基础能力

- Main / Sub 基本槽位
- 芯片装入
- 芯片卸下
- 槽位激活
- 槽位关闭
- 基本切换
- 当前装载状态可查询
- 当前哪些芯片处于激活表达状态可查询

### 2. 必须预留的外围规则

- 特殊槽
- 双手锁定
- 槽位禁用
- 手部状态联动
- 多形态芯片导致的来源可变

### 3. 它负责什么

- 槽位结构
- 装载与卸载
- 局部激活状态
- 装载切换流程
- 特殊槽与普通槽的装载语义

### 4. 它不负责什么

- 不负责资源真值
- 不负责战斗体正式相位真值
- 不负责全局业务总协调

### 5. 命名约束

- 内部稳定命名统一使用 `Main/Sub`
- 固定约定：`Main = 右`、`Sub = 左`
- 只有在与原版身体部位事实直接对接时，才使用 `Left/Right`

### 6. 特别约束

- 双手锁定属于装载约束，不是表达层临时判断
- 手部损坏导致的是局部能力失效，不等于整体崩解
- `CompTriggerBody` 必须收缩回装载 owner、局部激活表达 owner、局部协调者

## 七、表达系统需求与约束

### 1. 表达系统的地位

- 表达系统高于攻击系统
- 攻击只是表达的一种投影

### 2. 表达来源至少包括

- 单侧近战表达
- 单侧远程表达
- `Ability` 表达
- `Hediff` 表达
- 组合成立后的第三表达

### 3. 表达系统内部至少要分清

- 表达来源
- 表达规则
- 表达结果
- 宿主投影

### 4. 表达结果至少应包含

- 当前所有可手动使用的表达
- 当前默认主近战投影
- 当前默认主远程投影
- 当前默认外部表面投影
- 当前成立的第三表达

### 5. 特别约束

- 主攻击投影只是默认投影，不等于全部表达
- 统一的是规则层，不是把所有表现强压成同一种宿主
- 表达系统不能自己持有资源真值或战斗体相位真值

## 八、攻击入口、主攻击模式、宿主投影需求

### 1. 手动入口

- 必须保留玩家手动入口
- 手动入口是玩家操作层
- 按钮只负责入口控制，不应吞掉完整业务

### 2. 自动入口

- 必须保留自动远程入口
- 必须保留自动近战入口
- 自动入口继续贴原版 AI 发现链

### 3. 入口分层

- 手动入口和自动入口必须分层
- 不能强行合流成一条总入口
- 但底层应尽量共享真实表达规则

### 4. 主攻击模式

- 主攻击模式是规则层结果，不是 UI 标签
- 它至少服务于：
  - 自动攻击默认入口
  - 外部主要兼容表面
  - 外部只能读取一个主要武器表面时的回退投影

### 5. 手动层与主攻击模式的关系

- 玩家手动层应允许并列看到多个表达
- 主攻击模式不应吞掉全部手动表达

### 6. 宿主投影约束

- 标准近战必须走真原版近战链
- 标准远程必须走真原版远程链
- `Ability` 必须优先走原版 `Ability`
- `Hediff` 必须优先走原版 `Hediff`
- 非标准表达可以自建宿主，但最终仍要回到 RimWorld 可理解通道

## 九、双武器、组合、未来扩展表达需求

### 1. 双武器表达

- 双武器不是“多一个按钮”
- 它本质上是两个输入表达合成出更高层的新表达
- 近战 + 近战、远程 + 远程、近战 + 远程都要有规则层结果

### 2. 组合技表达

- 组合技本质不是攻击
- 本质定义是：左右芯片满足组合定义后，额外生成第三表达
- 这个第三表达可以是攻击，也可以不是
- 攻击型组合技只是组合技的一种

### 3. 未来扩展表达

未来必须能容纳：

- 近战类
- 射击类
- 飞行实体类
- 范围类
- 状态施加类
- 生成建筑 / 生成物类

### 4. 特别约束

- 不能把“攻击系统”狭义理解成“射击系统”
- 不能只枚举旧版已出现种类
- 重点是建立一条贯穿“入口 -> 行动生成 -> 投递 -> 效果落地 -> 外部信息投影”的总规则

## 十、执行、投递、命中、伤害需求

### 1. 执行层要求

- 表达执行前要走统一资源语义检查
- 不同宿主类型按各自原版链或自定义宿主分流执行

### 2. 投射物与模块化要求

射击全过程要支持模块化叠加，例如：

- 路径引导
- 追踪
- 抛物线
- 穿透
- 爆炸
- 附加状态
- 对原始属性修正

### 3. 统一要求

- 各模块彼此不需要互相认识
- 但要能组合共存、不冲突
- 不能每种类型单独发明一套完全分裂的协议

## 十一、语义上下文需求

### 1. 语义上下文的作用

- 让跨链路传递的不只是结果
- 还要保留来源语义、显示名、来源种类、触发原因等信息

### 2. 当前已明确的正式用途

- 攻击行为造成伤害后，伤口等下游结果能知道“这次攻击行为是谁”
- 战斗体崩裂等状态变化后，下游能知道“为什么发生”

### 3. 当前推荐最小字段

- `Id`
- `DisplayLabel`
- `SourceKind`
- `ReasonKey`
- `Instigator`
- `Tags`
- `ExtraData`

### 4. 特别约束

- 它是轻量、可传递的信息载荷
- 它不是事件总线
- 它不是真值 owner
- 它不是全局状态容器

## 十二、崩解、伤害联动、收尾需求

### 1. 崩解来源至少包括

- Trion 可用值耗尽
- 战斗体身体条件失败
- 手动紧急脱离

### 2. 伤害联动要求

- 伤害不一定直接等于崩解
- 伤害可能先转成 Trion 消耗，再由资源或身体条件决定是否崩解
- 手部损坏处理的是局部能力失效，不是整体崩解

### 3. 收尾必须做到

- 撤销表达
- 释放资源
- 恢复宿主状态
- 清理入口投影
- 清理装载残留脏数据

### 4. 特别约束

- 收尾不是“后面补的细节”
- 它是一条必须从一开始就设计进去的事务闭环
- 后续应补统一收尾入口与结构化原因上下文

## 十三、展示、GUI、视觉、信息兼容需求

### 1. GUI 约束

- GUI 不是当前验收目标
- 但 GUI 暴露的状态模型与规则要保留

### 2. 视觉投影需求

包括但不限于：

- 手持武器绘制
- 左右手绘制规则
- 枪口位置
- 绘制与发射点共基准
- 发光层
- 特殊图标
- 组合图标

特别补充：

- 复杂视觉表现属于旧 BDP 已有的既有需求
- 重构必须先理解并保留旧 BDP 真实视觉表现的本质
- 不能把“原版默认只显一把武器”误当成 BDP 也必须退化成单武器表现
- 视觉层应视为“真实多表达状态的游戏内投影”，而不是简化后的唯一武器假象

### 3. 信息展示需求

包括但不限于：

- `Label`
- `InspectString`
- `Tooltip`
- `SpecialDisplayStats`
- 对外默认武器表面

特别补充：

- 信息对外兼容属于这次重构要新增强化的需求
- 目标不是否认多表达真实状态，而是在不压扁真实系统的前提下，补出更成熟的对外信息暴露能力
- 必须分清：
  - 内部真实表达集合
  - 场景默认主攻击决策
  - BDP 自己可见的多表达明细
  - 给外部扩展读取的正式接口

### 4. 外部兼容原则

- 兼容首先不能反过来扭曲内部真实多表达系统
- 原版已有属性应优先通过正式投影暴露给外部读取
- 原版与普通信息类模组天然只能理解单主表面时，允许回退到“自动攻击主攻击模式”
- 这个单主表面回退是最后退路，不是系统本体
- 后续可为高价值对象补少量定点桥接，但不能把 patch 变成主兼容策略

## 十四、工具收纳层需求

### 1. 作用

收纳会被多处复用、但本身不是业务需求的东西。

### 2. 典型内容

- 统一日志与诊断
- 调试绘制
- 通用 key / id
- 宿主桥接辅助
- 小型数据转换
- 通用校验

### 3. 特别约束

- 可以通用
- 可以复用
- 但不能偷偷变成新的业务垃圾堆

## 十五、测试扩展层需求

### 1. 定位

- 建议作为独立后置测试模组
- 通过主模组暴露的正式接口挂入测试内容

### 2. 可承载内容

- 测试芯片
- 测试组合
- 测试 `Ability / Hediff`
- 测试投射物
- 调试按钮
- 状态观察展示

### 3. 特别约束

- 删除测试模组后，主模组不应残留任何测试内容
- 测试模组不能靠 Harmony 偷改主模组核心按钮链路
- 测试模组应通过正式扩展口注册
- 暴露给测试模组的接口，也应视作未来正式扩展接口样板

## 十六、时间、暂停、事件通信约束

### 1. 暂停下必须立即成立的东西

以下内容不得以时间流动为前提：

- 装载芯片
- 卸载芯片
- 激活目标选择
- 关闭目标选择
- 当前按钮可见性
- 当前表达结果
- 当前 Main / Sub 逻辑状态
- 当前是否允许某个控制动作

### 2. 允许依赖时间推进的东西

- 持续消耗
- 自然恢复
- 动作前摇 / 后摇
- 连发间隔
- 明确属于表现层的切换与冷却

### 3. 查询口约束

- 查询入口只能读取已成立结果
- 不应承担补救式结算

### 4. 当前事件通信方向

- 事件用于表达变化
- owner 继续持有真值
- 当前最小正式事件链主要落实在 Trigger 变化驱动表达缓存失效

## 十七、第一阶段必须打通

### 1. 资源系统

- `Cur / Max / Available`
- `Allocated / Reserved`
- 基本消耗
- 持续消耗聚合
- 释放

### 2. 战斗体系统

## 二十一、实现阶段固定自查问题

每次继续推进前，至少先回问：

2. 这次设计是否贴着 RimWorld 原版宿主在走
3. 资源、战斗体、触发体三类真值是否又被混起来
4. 手动入口、自动远程、自动近战是否被错误合流
5. 新增抽象是否让代码更容易理解，而不只是更漂亮
6. 这次内容是否属于当前阶段，而不是抢跑后续范围
7. 是否同时回看了当前文档摘要与旧代码事实
