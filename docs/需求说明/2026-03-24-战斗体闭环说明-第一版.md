# 战斗体闭环说明（第一版）

## 目的

这份说明专门用于把 BDP 中“战斗体”这条链压成一份正式需求文档。

它回答的不是：

- 旧 BDP 里有哪些战斗体特效
- 旧 BDP 里现在用了哪些具体 Hediff 名
- 当前代码里哪个类名看起来像做了什么

它回答的是：

- 战斗体的整体相位真值到底是什么
- 激活、手动解除、被动崩解、冷却、恢复分别怎样成立
- Trigger、Trion、CombatBody、Cleanup 这几层怎样分责
- 多来源触发崩解后，为什么必须汇合到单一崩解入口
- 收尾为什么不是后面再补的小细节，而是一开始就要存在的事务闭环

这份文档的任务，是把战斗体从“旧 BDP 里一大团跨层逻辑”收束成：

- `CombatBodyState`：相位真值 owner
- `CombatBodyCoordinator`：外层流程协调者
- `CombatBodyCleanupCoordinator`：收尾事务协调者

## 一、先下总结论

### 1. 战斗体系统的本体是“整体相位闭环”

战斗体系统不是：

- Trigger 的附属开关
- 资源系统的一个显示标签
- 某个 Hediff 的局部效果

它的本体是：

- 战斗体整体相位
- 整体进入条件
- 整体退出条件
- 多来源崩解汇合
- 整体收尾与恢复

### 2. `CombatBodyState` 只持有整体相位真值

`CombatBodyState` 正式持有的是：

- 当前相位
- 相位允许性
- 冷却剩余
- 崩解表现剩余
- 崩解原因
- 当前整体锁定的 Trion 量

它不应持有的是：

- Trigger 槽位真值
- 表达结果真值
- 资源账本细节
- 收尾执行细节

### 3. 战斗体闭环必须保持“多来源 -> 单崩解入口 -> 收尾”

旧 BDP 的重要经验之一是：

- 崩解来源不止一条
- 但正式进入崩解态的入口必须收束

这条结构必须保留。

### 4. 局部失效不等于整体崩解

像手部损坏、单侧槽位禁用这类情况，本质上是：

- Trigger 层局部能力失效

它不自动等于：

- 战斗体整体崩解

### 5. 收尾不是“后面再补”，而是战斗体本体的一部分

只要战斗体允许进入：

- Active
- Collapsing
- Cooldown

就必须从一开始同时定义：

- 何时释放资源
- 何时关闭槽位
- 何时恢复宿主
- 何时清理残留

## 二、适用范围与行为真标准

### 1. 行为真标准

这份文档的行为真标准有两层：

第一层：

- 旧 BDP 战斗体激活、崩解、延时解除、伤害联动、收尾恢复相关代码事实

第二层：

- 当前二次重构已经明确的 owner 边界与时间原则

也就是说：

- 旧 BDP 用于确认“整体行为真相”
- 当前需求体系用于校正“这些行为该由谁正式持有”

### 2. 适用范围

本文适用于：

- `CombatBodyState`
- `CombatBodyCoordinator`
- `CombatBodyCleanupCoordinator`
- 战斗体激活 / 手动解除 / 崩解 / 冷却 / 恢复 / 收尾

本文不单独展开：

- Trigger 装载细节
- 多表达解析细节
- 远程攻击链
- 视觉与信息兼容

## 三、名词释义与辨析

### 1. 战斗体

本文中的“战斗体”指的是：

- Pawn 当前是否进入 BDP 战斗体整体状态

它不是：

- 某一侧槽位是否激活
- 某枚芯片是否激活

### 2. 相位

“相位”指的是：

- 战斗体整体所处的外层阶段真值

它至少包括：

- `Inactive`
- `Active`
- `Collapsing`
- `Cooldown`

### 3. 激活

“激活”在本文默认指：

- 战斗体整体进入 `Active`

如果说的是槽位激活，会明确写成：

- 局部激活
- 槽位激活

### 4. 崩解

“崩解”指的是：

- 战斗体整体因某种正式原因进入整体失败 / 退出流程

它不是：

- 单侧槽位失效
- 某按钮暂时不可用

### 5. 收尾

“收尾”指的是：

- 战斗体退出后必须做完的一整组正式恢复动作

至少包括：

- 资源释放
- 槽位关闭
- 宿主恢复
- 残留清理

## 四、战斗体系统的正式真值面

## 1. 相位真值

战斗体系统最核心的真值是：

- 当前整体相位

只有这层成立，外部系统才能稳定回答：

- 当前能否再次激活
- 当前能否手动解除
- 当前是否处于崩解表现期
- 当前是否还在冷却中

## 2. 整体锁定资源量

战斗体系统还必须知道：

- 当前战斗体阶段正式锁定了多少 Trion

但这里要强调：

- “当前锁定了多少”可以挂在战斗体相位状态上
- “Trion 当前总账怎么记”仍然属于资源系统

## 3. 崩解原因

战斗体系统应正式记录：

- 当前崩解原因

因为这会影响：

- 语义上下文
- 下游显示
- 收尾解释

## 4. 冷却 / 崩解剩余时间

这些属于允许依赖时间推进的过程真值：

- 冷却剩余
- 崩解表现剩余

但“是否可再次激活”不能要求外部先跑 tick 才成立。

## 五、战斗体相位模型

## 1. `Inactive`

它表示：

- 当前整体未进入战斗体

此时：

- 可以检查是否允许激活
- 不应视为战斗体运行中

## 2. `Active`

它表示：

- 当前整体已正式进入战斗体

此时：

- Trigger 层局部激活才有意义
- 表达层才有正式运行基础
- 崩解来源检查才有正式对象

## 3. `Collapsing`

它表示：

- 当前已正式进入崩解态
- 但尚未完成整体退出和收尾

这一相位必须被明确承认，因为旧 BDP 的崩解不是“立即消失”，而是：

- 先进入延时崩解态
- 再统一走正式解除链

## 4. `Cooldown`

它表示：

- 当前整体退出已正式发生
- 但还未回到允许再次激活的 `Inactive`

## 六、激活闭环规则

## 1. 激活前检查

战斗体整体激活前，至少要检查：

- 当前相位允许激活
- 资源层可正式锁定所需 Trion
- 宿主层允许应用战斗体变换

这里必须坚持：

- Trigger 装载与局部激活检查不能替代整体激活检查

## 2. 激活事务顺序

整体激活应至少按这条正式顺序成立：

1. 资源锁定成功
2. 宿主应用战斗体变换
3. 相位进入 `Active`
4. 广播阶段变化

这样写的原因是：

- 资源失败时不能半激活
- 宿主未切换前不能谎称已经 `Active`

## 3. 整体激活与局部激活的关系

必须长期保持：

- 战斗体整体 `Active` 是 Trigger 局部激活的前置条件

但也必须区分：

- 整体 `Active` 不等于所有槽位都已经局部激活

## 七、手动解除闭环规则

## 1. 手动解除只能从 `Active` 发起

手动解除是战斗体整体主动退出流程。

它不应从：

- `Inactive`
- `Cooldown`

误发起。

## 2. 手动解除的最小事务链

当前正式方向应是：

1. 释放当前整体锁定资源
2. 恢复宿主
3. 进入 `Cooldown` 或直接回 `Inactive`
4. 广播阶段变化

## 3. 紧急脱离与普通手动解除不能完全混为一谈

二者都可能是“玩家主动发起”，
但语义上仍应允许区分：

- 普通手动解除
- 紧急脱离

因为它们可能影响：

- 冷却时长
- 崩解语义
- 显示与日志

## 八、被动崩解闭环规则

## 1. 崩解来源至少有多条

旧 BDP 已确认至少存在这些上游来源：

- Trion 可用值耗尽
- 身体条件失败
- 倒地
- 关键部位摧毁
- 手动紧急脱离

这说明崩解不是单点事件。

## 2. 多来源必须汇合到单崩解入口

虽然来源有多条，但正式进入崩解态时必须汇合到：

- 单一崩解入口

原因是：

- 防止多处各自半展开崩解逻辑
- 保持崩解原因、阶段切换、语义广播统一

## 3. 崩解进入后先切相位，不立即完成解除

这是旧 BDP 非常关键的结构事实：

- 先 `Active -> Collapsing`
- 再进入延时表现与正式解除链

因此新文档也必须坚持：

- `Collapsing` 不是装饰性相位，而是正式相位

## 九、崩解表现期与延时解除

## 1. 崩解表现期的意义

崩解表现期存在的意义不是单纯做特效，
而是正式承认：

- “崩解已成立”
- “但整体尚未解除完毕”

## 2. 崩解期内的整体语义

崩解期内至少应允许成立这些外层语义：

- 当前不再允许视为正常 `Active`
- 当前正在走整体失败流程
- 某些表现或保护语义可依附在这个相位上

## 3. 崩解结束后必须进入正式收尾链

崩解表现一旦结束，就必须进入：

- 统一解除 / 收尾 / 恢复

不能让崩解期结束后状态悬空。

## 十、冷却闭环规则

## 1. 冷却属于允许依赖时间的过程

冷却本身允许依赖时间推进。

这类时间过程是合法的。

## 2. 但“冷却是否结束”必须在查询口主动结算

这一点已经是当前二次重构明确踩坑后的硬约束。

也就是说：

- 玩家暂停时只要冷却已经到点
- 查询口就必须立即把相位收回 `Inactive`

不能要求：

- 先等下一 tick

## 十一、局部失效与整体崩解的边界

## 1. 手部损坏属于 Trigger 局部失效

旧 BDP 已确认：

- 手部 / 手臂 / 肩部缺失会导致对应侧槽位禁用

这条链处理的是：

- 局部能力失效

## 2. 局部失效不自动等于整体崩解

这必须作为正式边界固定下来。

否则后面很容易把：

- 缺一只手

粗暴做成：

- 战斗体立刻崩掉

## 3. 何时由局部失效升级成整体崩解，要由战斗体层统一裁定

如果以后某些规则要求：

- 局部失效足以触发整体崩解

也必须通过：

- 战斗体层正式入口

而不能由 Trigger 自己越权判定。

## 十二、收尾事务规则

## 1. 收尾的本体是事务闭环

收尾不是一堆零散“清理一下”的代码。

它的本体是：

- 退出战斗体后所有必须完成的正式后果

## 2. 当前最小正式收尾链

当前第一版至少应承认这条最小收尾链：

1. 释放战斗体锁定资源
2. 关闭全部局部槽位
3. 恢复宿主

## 3. 后续完整收尾链必须继续容纳

后续还必须继续容纳：

- 快照恢复
- Hediff 清理
- 身体变化恢复
- 入口与表达残留清理
- 视觉残留清理

## 十三、对外正式输出面

战斗体系统后续至少应稳定提供：

- 当前整体相位
- 是否允许激活
- 是否允许手动解除
- 当前冷却剩余
- 当前崩解剩余
- 当前锁定 Trion 量
- 当前崩解原因
- 阶段变化事件

## 十四、事件、语义与 owner 边界

## 1. 事件只广播变化

阶段事件只能做：

- 通知当前从哪一相位进入哪一相位
- 携带原因与语义上下文

它不能替代：

- `CombatBodyState` 的正式相位真值

## 2. 崩解语义上下文要跟着崩解入口走

因为崩解来源有多条，
所以崩解语义上下文应在统一崩解入口形成。

这样下游才能知道：

- 为什么发生
- 由谁触发

## 3. owner 边界必须保持清楚

- `CombatBodyState` 只持有相位真值
- `CompTrion` 只持有资源真值
- `CompTriggerBody` 只持有装载与局部激活真值

任何把这三类真值重新揉成一锅的写法，都应视为走偏。

## 十五、存读档与恢复边界

## 1. 战斗体必须正式保存的状态

至少包括：

- 当前相位
- 当前锁定 Trion 量
- 激活时刻
- 冷却结束时刻
- 崩解开始时刻
- 崩解原因

## 2. 读档后必须保证什么

读档后至少必须保证：

- 相位合法
- 冷却到点时立即收回 `Inactive`
- 崩解期仍能继续正确续接

## 3. 战斗体恢复不等于全系统恢复

即使战斗体相位恢复了，
仍不等于：

- Trigger 已完全对齐
- 表达已完全重算
- 宿主已完全恢复

所以后续还要有单独的存读档与恢复说明去覆盖全局。

## 十六、当前阶段必须落地与只留口

## 1. 第一阶段必须正式落地

当前阶段至少必须正式落地：

- `Inactive / Active / Cooldown`
- 手动激活
- 手动解除
- 冷却立即结算查询
- 最小阶段事件广播

## 2. 当前阶段只留口但必须明确

当前阶段可以不完整落地，但必须明确预留：

- `Collapsing` 完整表现链
- 多来源崩解统一汇合
- 紧急脱离细则
- 完整收尾恢复链
- 快照恢复
- 身体变化恢复

## 十七、对后续实现的直接要求

### 1. 不能把战斗体写成 Trigger 大附庸

Trigger 只能告诉战斗体：

- 当前局部装载和局部激活是什么

不能替战斗体持有：

- 整体相位真值

### 2. 不能把战斗体写成资源系统外壳

资源是资源，
战斗体是战斗体。

战斗体可以锁定 / 释放资源，
但不能把资源系统直接吞进来。

### 3. 不能把崩解写成多处半展开

后续任何来源触发崩解时，都应先问：

- 最终是不是汇合到同一个正式崩解入口

### 4. 不能把收尾继续当作后补细节

只要允许进入相位变化，
就必须同步定义退出后的正式收尾路径。

## 十八、一句话总括

战斗体闭环的本体，不是“某个按钮把 Pawn 切成另一种状态”，而是“以 `CombatBodyState` 持有整体相位真值，以协调层串联资源锁定、宿主变换、崩解汇合、冷却收束与统一收尾，并且始终把局部 Trigger 失效和整体战斗体崩解区分开来”的正式流程系统。
