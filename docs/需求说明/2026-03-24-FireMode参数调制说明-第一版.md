# FireMode 参数调制说明（第一版）

## 目的

这份说明不把 `FireMode` 理解成“一个特权功能，专门插进攻击系统里四处改参数”。

这份说明要定义的是：

- 攻击系统应先暴露出哪些正式调制通道
- 调制功能应怎样以低耦合方式接入这些通道
- `FireMode` 在其中处于什么地位
- 为什么这类东西不能再被做成“中心功能到处强改”

因此这里的重心不是：

- 旧 BDP 里有哪些预设名
- 当前窗口里有哪些滑条
- 当前具体调了哪些倍率

而是：

- 参数调制协议
- 调制挂点
- 调制对象
- 读写边界
- 合并规则
- 扩展兼容性

## 一、先下总结论

### 1. `FireMode` 不是攻击系统的 owner

`FireMode` 不应正式持有：

- 攻击系统主参数真值
- 发射计划真值
- 投射物真值
- 表达结果真值

它的正式地位应是：

- 参数调制参与者

### 2. 攻击系统必须先公开“调制通道”，调制功能才能低耦合接入

正确方向不是：

- 先有一个 FireMode，再让它去 patch / 注入 / 直改各段参数

正确方向应是：

- 先由攻击系统公开正式调制口
- 再由 FireMode 或其它调制功能通过同一套协议参与

### 3. `FireMode` 只是参数调制功能的一种，不应绑死协议

如果协议写成：

- “FireMode 怎么改这个、怎么改那个”

那么未来任何其它调制功能都只能：

- 再复制一套私协议

这正是应该避免的。

### 4. 真正要统一的是“调制对象 + 调制语义 + 合并规则”

统一协议不等于：

- 所有调制功能共用同一组 UI

真正要统一的是：

- 它调的是什么对象
- 它怎样表达调制意图
- 宿主怎样合并多个调制参与者

## 二、适用范围与行为真标准

### 1. 行为真标准

这份文档的行为真标准有两层：

第一层：

- 旧 BDP 已证明这类调制会跨越攻击链多个位置，并且会影响显示面板与行为结果

第二层：

- 当前二次重构要求的是“统一调制协议”，不是继续让某个调制功能越权控制攻击系统

因此旧 BDP 在这里的作用只是：

- 证明“参数调制是跨层真实需求”

而不是：

- 规定未来仍应沿用旧 BDP 的接入方式

### 2. 适用范围

本文适用于：

- 攻击系统开放给调制功能的正式通道
- 调制功能如何参与表达 / 发射 / 投送 / 显示等结果形成

本文不直接定义：

- 具体 UI 形态
- 具体预设名
- 具体倍率值

## 三、名词释义与辨析

### 1. 参数调制

“参数调制”指的是：

- 在不改写系统真值 owner 的前提下，对某些正式结果的形成过程施加规则性影响

它不是：

- 直接改 owner 真值
- 直接篡改最终宿主内部私有状态

### 2. 调制通道

“调制通道”指的是：

- 攻击系统明确公开给外部调制参与者的正式挂点

它回答的是：

- 允许在哪个阶段参与
- 允许调哪些对象
- 允许提交什么类型的调制意图

### 3. 调制对象

“调制对象”指的是：

- 可被调制协议作用的一类正式结果对象

例如：

- 表达层参数面
- 发射计划
- 投送宿主初始化面
- 显示值

### 4. 调制参与者

“调制参与者”指的是：

- 通过正式调制通道提交调制意图的扩展单元

`FireMode` 只是调制参与者的一种。

### 5. 显示值

“显示值”指的是：

- 给信息层、界面层看的解释值

它不等于：

- 行为执行的最终正式值

但它必须和行为结果保持可解释的一致性。

## 四、总原则

## 1. 攻击系统先开放通道，再允许调制参与者接入

攻击系统必须先定义：

- 哪些阶段开放调制
- 哪些对象允许调制
- 哪些字段允许调制

然后 `FireMode` 才能接入。

不能反过来写成：

- 攻击系统为了 FireMode 到处开洞

更不能写成：

- 某个调制功能先决定自己想改哪里
- 再逼攻击系统为它补专用后门

正式依赖方向只能是：

- 攻击系统先给出标准调制接口
- 外部调制参与者自行声明接入

这条方向约束的意义是：

- 不让调制功能反向绑架攻击系统设计
- 不让系统因为当前一个功能而失去对未来未知功能的开放性

## 2. 调制参与者不能直接越权写宿主内部状态

调制参与者可以：

- 读取允许读取的正式结果
- 提交调制意图

调制参与者不能：

- 直接写某个 `Verb` 私有字段
- 直接改某个 `Projectile` 私有内部状态
- 直接改表达系统真值

## 3. 多个调制参与者必须能共存

协议必须从一开始就支持：

- 不止一个调制参与者

这意味着：

- 不能把 FireMode 写成唯一调制中心

## 4. 调制协议要对未知功能开放

未来可能会出现：

- 不是 FireMode 的其它调制功能

因此协议不能写成：

- 只为当前 FireMode 服务的私协议

## 五、正式调制层次

建议长期承认至少这几类正式调制层次：

1. 表达参数调制
2. 发射计划调制
3. 投送宿主初始化调制
4. 在途参数调制
5. 落地参数调制
6. 显示值调制

这些层次的意义不是“都必须现在实现”，而是：

- 以后任何调制功能都只能在这些层次中声明自己参与哪里

## 六、各调制层次的正式对象

## 1. 表达参数调制

### 调制对象

- 表达层公开的参数面

### 可调制内容类型

- 表达行为档位
- 默认行为倾向
- 可供后续阶段读取的参数标签

这里说的“表达参数面”，应严格限定为：

- 已经成立的表达结果对后续攻击阶段公开的参数面

不能把它理解成：

- 反向参与表达是否成立
- 反向改写表达解析结果集合
- 反向夺取主攻击投影选择权

### 不应做什么

- 不直接改表达真值是否成立

## 2. 发射计划调制

### 调制对象

- 发射计划正式结果

### 可调制内容类型

- 节奏
- 批次
- 次数
- 资源消耗倍率
- 某些行为参数

### 这一层为什么重要

因为很多“模式差异”本质上不是换一种攻击，
而是同一表达在发射计划层被重新调制。

## 3. 投送宿主初始化调制

### 调制对象

- 投送宿主建立时允许注入的参数面

### 可调制内容类型

- 宿主初始化参数
- 初始在途参数
- 初始语义标签

### 不应做什么

- 不直接 patch 原版宿主内部计算作为主方案

## 4. 在途参数调制

### 调制对象

- 在途阶段允许公开调制的参数面

### 说明

这一层不是专属于 FireMode，
但协议应允许未来某些调制功能在此层参与。

## 5. 落地参数调制

### 调制对象

- 落地结果正式参数面

### 可调制内容类型

- 伤害倍率
- 状态强度
- 其它落地参数

### 边界

- 这里调的是落地结果参数
- 不是直接改写伤害系统 owner 真值

## 6. 显示值调制

### 调制对象

- 信息层读取的显示值结果

### 可调制内容类型

- 玩家可见说明值
- UI 展示值

### 必须注意

- 显示值调制不能与行为值完全脱节

## 七、调制协议应公开的正式通道

攻击系统后续至少应公开这些类型的正式调制通道：

## 1. 只读上下文输入

调制参与者至少应能读取：

- 来源表达标识
- 当前阶段正式结果
- 当前执行宿主信息
- 当前语义上下文

## 2. 阶段调制意图提交口

调制参与者应通过正式提交口表达：

- 想调哪些字段
- 用什么调制语义调

而不是直接改结果对象。

## 3. 宿主合并器

每个调制层次都应由宿主统一合并：

- 多个调制参与者的意图

## 4. 显示值解释口

攻击系统应允许调制结果产生：

- 给信息层读取的解释值

而不是让显示层自己重新猜一套调制结果。

## 八、标准调制语义

调制协议至少要长期支持以下标准语义：

## 1. `Scale`

用于：

- 倍率放缩

## 2. `Offset`

用于：

- 固定增减

## 3. `Clamp`

用于：

- 上下界裁剪

## 4. `Override`

用于：

- 有明确权限时替换默认值

## 5. `Tag`

用于：

- 给后续阶段或显示层附加解释标签

这些语义的意义是：

- 让调制参与者表达自己怎么影响结果
- 而不是让每个调制功能各自发明一套私有表述

## 九、合并与冲突规则

## 1. 多个调制参与者必须可叠加

协议必须允许：

- 不止一个参与者作用于同一调制对象

## 2. 合并不能按“谁先执行就算谁”处理

正式裁定必须来自：

- 宿主合并规则
- 明确优先级
- 明确字段级语义

不能依赖：

- 注册顺序巧合

## 3. 不同字段可以有不同合并规则

例如：

- 某字段允许 `Scale` 叠乘
- 某字段只允许 `Clamp`
- 某字段只允许单一 `Override`

因此调制协议必须是：

- 字段级

不是：

- 功能级粗暴覆盖

## 十、`FireMode` 在协议中的正式地位

## 1. `FireMode` 只是调制参与者的一种

它的正式地位应是：

- 一个通过调制通道接入的参与者

而不是：

- 特殊中心
- 统一控制器
- 攻击系统内部不可绕开的核心

## 2. 为什么要这样定义

因为如果 `FireMode` 被写成特权中心，
后面任何其它调制功能都会被迫：

- 模仿它再侵入一次系统

这样系统一定继续耦合。

## 3. `FireMode` 可以影响多层，但必须通过多层正式通道

如果它确实要影响：

- 发射计划
- 投送宿主
- 显示值

也必须分别通过：

- 对应层次的正式调制口

而不是一条旁路把多层全改了。

## 4. `FireMode` 不拥有“要求攻击系统配合自己”的设计特权

如果某种调制需求无法通过正式调制通道表达，
正确动作应是：

- 评估攻击系统是否真的缺正式调制层
- 如确实缺失，则补“通用可复用的正式通道”

而不是：

- 为 FireMode 单独塞一个私入口

这条规则要长期成立，
因为未来可能出现：

- FireMode 之外的其它调制功能
- 不同来源同时参与同一阶段调制
- 某些只读解释型调制
- 某些只改显示、不改行为的调制

只要攻击系统一旦接受“某个功能可以先提出自己要改哪里，再把系统切开一个入口给它”，
整个协议就会重新退化成：

- 一组彼此不兼容的功能特权口

## 十一、显示层与调制协议的关系

## 1. 显示层不负责重新计算调制结果

显示层只应读取：

- 正式显示值结果

## 2. 调制协议应允许“行为值”和“显示值”分层

这不是为了造两套真值，
而是为了允许：

- 同一调制结果有一套执行解释
- 同时有一套展示解释

但两者必须可解释一致。

## 十二、第一阶段必须落地与只留口

## 1. 当前阶段必须明确的东西

即使暂时不完整实现，也必须先明确：

- 调制不是 owner
- 攻击系统先开放通道
- 多参与者可共存
- 宿主统一合并

## 2. 当前阶段可以只留口的东西

可以先不完整实现，但必须预留：

- 各层正式调制对象
- 标准调制语义
- 合并规则
- 显示值解释口

## 十三、对后续实现的直接要求

### 1. 不能把 `FireMode` 做成攻击系统里的特权中心

### 2. 不能让调制参与者直接 patch 宿主内部状态作为主方案

### 3. 不能让显示层自己重新猜调制结果

### 4. 不能把“当前已有 FireMode 功能”当成协议边界

## 十四、一句话总括

`FireMode` 参数调制真正要定义的，不是“一个模式功能怎样去四处改攻击参数”，而是“攻击系统先公开统一调制通道，让 `FireMode` 以及未来任何其它调制功能都只能以低耦合参与者身份接入，对正式调制对象提交标准语义的调制意图，再由宿主统一合并成行为结果与显示结果”的扩展协议标准。
