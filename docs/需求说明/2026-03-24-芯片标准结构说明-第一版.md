# 芯片标准结构说明（第一版）

## 目的

这份说明专门用于把新 BDP 中“芯片到底是什么、应如何组织、应向各系统提供什么信息”压成一份正式标准说明。

但从当前版本开始，
它不再单独承担“什么叫正式芯片”的上位裁定职责。

关于芯片上位总结构，
应以上位文档
`2026-03-26-正式芯片定义契约说明-第一版.md`
为准。

当前上位总结构已明确固定为：

- `profile`
- `loadout`
- `expression`
- `trion`
- `extensions`

其中：

- 形态留在 `expression`
- 本文中的 Trion 细化规则继续有效
- 本文不再支持旧 `Identity / Resource` 总块说法

它不是：

- 某几枚旧芯片的功能介绍
- 某个类的实现草稿
- 某一轮重构过程记录

它回答的是：

- 芯片在新 BDP 中的正式定位是什么
- 芯片标准结构应由哪些部分组成
- 哪些信息属于芯片本体，哪些不属于
- 表达来源、Trion 参数、形态、远程模块化各自应落在哪一层
- 后续为模组新增一枚芯片时，应优先按什么思路组织定义

## 一、先下总结论

### 1. 芯片对玩家来说首先是物品实体

芯片必须是 RimWorld 里自然成立的实体物品。

它应支持：

- 生成
- 制造
- 持有
- 选中
- 装载
- 转移
- 存读档恢复

也就是说，玩家接触到的不是抽象配置块，而是一枚真实存在的物品。

### 2. 芯片对 BDP 来说本质上是信息载体

芯片在系统中的关键，不是“它自己做了多少事”，而是“它声明了什么信息”。

这些信息会被不同系统分别读取：

- `CompTriggerBody` 读取装载与局部规则
- 表达系统读取表达来源
- Trion 相关系统读取资源参数
- 视觉与兼容层读取显示和投影信息
- 其它扩展系统读取自己需要的附加声明

因此，芯片是多系统共同读取的上游声明源。

### 3. 芯片不是新的总 owner

芯片虽然是很多系统的共同入口，但它不是新的总真值中心。

芯片不能替代：

- `CompTrion`
- `CombatBodyState`
- `CompTriggerBody`

芯片只提供声明信息，不持有这些系统的正式真值。

### 4. 芯片标准必须优先追求统一、扩展、复用、易学

芯片标准的设计目标不是“先把旧芯片一个个照抄回来”。

更准确地说，它必须同时满足：

- 统一标准约定
- 高扩展性
- 高可配置性
- 对已有机制的复用组合能力
- 面向模组开发者的易学易用性

## 二、芯片的五类基础信息

芯片标准当前统一按五类基础信息理解。

### 1. 基本信息

用于回答：

- 这是什么芯片
- 玩家看到它叫什么
- 它的基础说明是什么

典型内容包括：

- `defName`
- `label`
- `description`
- 基础分类
- 图标
- 基础信息面板内容

### 2. 装载信息

用于回答：

- 这枚芯片能装在哪
- 装载时受什么 Trigger 规则约束

典型内容包括：

- 槽位限制
- 双手属性
- 互斥标签
- 形态入口

### 3. 表达信息

用于回答：

- 这枚芯片能提供哪些表达来源
- 各来源在什么前提下成立

这是芯片的核心信息区。

### 4. Trion 参数

用于回答：

- 这枚芯片和 Trion 资源系统如何发生关系

包括芯片整体级参数和局部来源级参数两种。

### 5. 显示与扩展信息

用于回答：

- 这枚芯片如何被说明、被显示、被附加扩展系统读取

这部分不等于表达来源本体，也不等于攻击链模块本体。

## 三、芯片表达契约的新总结构

当前正式改为：

- 一枚芯片
- 一组统一表达条目
- 一组形态操作

不再把四类来源列表视为未来标准主结构。

### 1. 芯片整体先声明条目，而不是先分四堆列表

旧思路是：

- `verbSources`
- `abilitySources`
- `hediffSources`
- `passiveSources`

新思路改为：

- `entries`

也就是说：

- 一枚芯片先声明“自己有哪几条本事”
- 每条条目再声明自己属于哪一类

这样更符合：

- 玩家理解
- 内容作者写法
- 主模组内部解释路径

### 2. 形态切换改为“对条目做操作”

旧思路里的形态更像：

- 命中某个形态块后，再额外追加一批来源

这会让形态慢慢长成隐藏堆叠器。

当前正式改为：

- 基础条目集始终存在
- 形态块只对条目做显式操作

第一版固定只承认三种操作：

- `Append`
- `Replace`
- `Disable`

### 3. 混合芯片正式允许，且默认并列

一枚芯片允许同时声明：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

第一版默认解释为：

- 并列条目

系统不自动猜：

- 哪条是主条目
- 哪条是副作用
- 哪条附属于哪条

只有条目显式声明关系时，
系统才承认关系语义。

### 4. 从属关系纳入结构预留，但不抢第一优先级

第一版允许条目可选填写：

- `relationKind`
- `parentEntryId`

第一版只轻量承认：

- `Independent`
- `Attached`

第一版只把它用于：

- 解释语义
- 未来按钮分组
- 未来说明排序

不允许它直接改写：

- 默认主攻击选择
- 自动攻击选择
- 当前结果成立判定

### 5. 不做长期双轨

从这一版开始，
正式标准只承认：

- `Entries`
- `Modes`
- `Modes.Operations`

不再把以下旧结构视为未来正式模板：

- `verbSources`
- `abilitySources`
- `hediffSources`
- `passiveSources`

如果迁移期代码里还短暂残留这些名字，
它们也只是迁移残留，
不是内容作者未来继续写芯片时该跟随的标准。

### 6. 当前已落地到什么程度

截至当前这轮重构，
主模组已经正式落地：

- `ChipExpressionConfig` 以 `Entries + Modes` 作为主结构
- 每条 `Entry` 用 `Kind` 区分 `Verb / Ability / Hediff / Passive`
- `Contract` 层已成立，主路径已改为先解释契约，再进入结果链
- DevHarness 示例芯片已迁到 `Entries` 写法

截至当前这轮重构，
主模组尚未正式落地：

- 完整的正式形态来源系统
- 复杂从属关系对按钮分组和排序的深度参与
- 为了“展示完整性”而伪造的模式样例

也就是说，
现在已经可以正式写统一条目芯片，
但还不应假装“整套模式生态也已完整定稿”。

## 四、表达信息的顶层分类

当前芯片表达来源先统一承认四个顶层大类：

- `Verb`
- `Ability`
- `Hediff`
- `Passive`

这四类是顶层分类，不是最终粒度。

后续每一大类内部都允许继续向下细化子结构。

### 1. `Verb`

适用于：

- 近战攻击
- 远程攻击
- 爆炸攻击
- 其它通过原版 `Verb` 通道成立的动作来源

### 2. `Ability`

适用于：

- 需要原版 `Ability` 入口的能力
- 需要点选、选目标或主动施放的战术能力

### 3. `Hediff`

适用于：

- 持续状态
- 防御状态
- 模式状态
- 通过原版 `Hediff` 通道成立的附加效果

### 4. `Passive`

适用于：

- 不直接生成主动入口
- 但需要向其它系统声明“这个来源已成立”的被动内容

## 五、统一条目的一般规则

### 1. 一枚芯片天然允许多个表达来源

芯片不应被限制成“一枚芯片只能有一个表达来源”。

正确方向是：

- 简单芯片可以只有一个来源
- 复杂芯片可以有多个来源
- 复合芯片允许同时声明多类来源

### 2. 条目必须统一平铺，再由类型字段区分

表达条目不再按四类来源列表分组组织。

未来正式写法应是：

- 一组统一 `entries`

每条 `entry` 自己说明：

- 它是 `Verb`
- `Ability`
- `Hediff`
- 还是 `Passive`

### 3. 每条来源必须有稳定 `id`

每条来源都应有自己的稳定标识。

它用于：

- 形态覆盖
- 诊断
- 配置引用
- 后续扩展

### 4. 芯片提供的是条目声明，不是最终结果

芯片应声明：

- 它有哪些条目

芯片不应直接声明：

- 最终主攻击投影是谁
- 最终组合技结果是谁
- 最终默认兼容表面是谁

这些是更高层解析与投影结果。

## 六、四类表达的最小结构

## 1. `Verb`

`Verb` 条目第一版最小字段应至少包括：

- `id`
- `label`
- `role`
- `conditions`
- `tags`
- `trion`
- `verbProps`

这里的 `Verb` 条目首先是：

- 一个可被系统解释并投到原版 `Verb` 通道的动作来源声明

不是：

- 一整把完整武器定义
- 一整个远程系统定义

## 2. `Ability`

`Ability` 条目第一版最小字段应至少包括：

- `id`
- `label`
- `role`
- `conditions`
- `tags`
- `trion`
- `abilityDef`

它首先是：

- 一个可被系统解释并投到原版 `Ability` 通道的能力来源声明

## 3. `Hediff`

`Hediff` 条目第一版最小字段应至少包括：

- `id`
- `label`
- `role`
- `conditions`
- `tags`
- `trion`
- `hediffDef`
- `applyMode`

这里的 `applyMode` 用于区分最小应用方式差异，例如：

- 独占覆盖
- 叠加
- 按形态切换

## 4. `Passive`

`Passive` 条目第一版最小字段应至少包括：

- `id`
- `label`
- `role`
- `conditions`
- `tags`
- `trion`
- `passiveKey`
- `exposedData`

它首先是：

- 一个向其它系统声明“该被动来源已成立”的来源声明

## 七、形态规则

### 1. 形态不是第二套来源列表

形态块不应再被理解成：

- “命中后再额外塞一套来源”

更准确的理解应是：

- 当前形态如何修改这枚芯片原本的条目集

### 2. 第一版形态操作固定为三种

- `Append`
- `Replace`
- `Disable`

这三种足以覆盖第一版正式需求。

### 3. 所有形态操作都必须基于稳定条目 `id`

形态切换不能靠：

- 顺序覆盖
- 第几个来源
- 第几个数组项

必须明确指向：

- `targetEntryId`

## 八、Trion 参数规则

### 1. 芯片只声明 Trion 参数，不持有 Trion 真值

芯片不能持有：

- 当前剩余多少 Trion
- 当前是否扣费成功
- 当前已锁定多少
- 当前是否耗尽

这些真值只能在 `CompTrion`。

### 2. 占用值属于芯片整体级参数

占用值不是局部激活时才读取的参数。

占用值的正式语义是：

- 这枚芯片在“已装载集合”中时，对战斗体总锁定量贡献多少

### 3. 占用值由战斗体进入/离开流程统一处理

占用值应在：

- 战斗体进入时统一汇总并锁定
- 战斗体离开时统一释放

它不属于：

- 局部激活流程
- 单槽位切换流程

### 4. 局部使用类参数属于来源级参数

以下参数更接近局部来源成立或使用时才读取的参数：

- 激活消耗
- 使用消耗
- 持续消耗
- 最低要求

它们应挂在具体来源自己的 `trion` 区，而不是一律平铺到芯片总层。

## 七、形态规则

### 1. 形态是同一芯片内部的工作状态

形态不是另一枚芯片。

形态的本质是：

- 同一枚芯片在不同工作状态下，当前有效配置发生变化

### 2. 形态不应重写整枚芯片

更合理的方向是：

- 芯片先声明基础结构
- 形态只声明相对于基础结构的覆盖项

### 3. 形态主要覆盖这些内容

- 当前启用哪些来源
- 来源参数
- 局部使用类 Trion 参数
- 显示信息

### 4. 形态默认不覆盖这些内容

- 芯片身份
- 装载本体约束
- 战斗体占用值

除非后续有明确旧 BDP 事实支撑，否则不应把这些内容轻易做成形态可变项。

## 八、远程 `Verb` 的模块化规则

### 1. 远程模块化是基础需求，不是额外需求

对于远程武器类芯片而言，支持多种附加模块的任意插拔，是基础需求的一部分。

### 2. 模块化属于远程 `Verb` 内部结构

它的落点不是：

- 芯片总层
- 表达总层

而是：

- 某条远程 `Verb` 来源内部的攻击链配置层

### 3. 模块必须按攻击链阶段分组

当前第一版正式承认的分组为：

- `aimModules`
- `fireModules`
- `flightModules`
- `impactModules`
- `visualModules`

### 4. 模块是作用点模块，不是玩法名模块

模块的分类依据应是：

- 它改攻击链的哪一段

而不是：

- 它表面上看起来像什么玩法名

### 5. 宿主统一合并，模块不跨段乱改

正确方向是：

- 模块只改自己所属阶段
- 阶段宿主统一读取、合并、产出结果
- 模块不应跨段直接修改不属于自己的结果

## 九、模块的一般结构

每个模块配置项当前建议至少包含：

- `id`
- `moduleType`
- `enabled`
- `order`
- `tags`
- `parameters`

其中：

- `moduleType` 用于说明模块类型
- `order` 用于控制同段模块顺序
- `parameters` 用于承载模块自己的专属参数

## 十、哪些不是模块

以下内容不应塞进远程链模块区：

- `FireMode`
- `WeaponDraw`
- 默认主攻击投影
- 对外兼容表面
- 整个 `Verb` 来源本身
- 组合技结果
- 双武器结果

其中：

- `FireMode` 更接近参数调制层
- `WeaponDraw` 更接近显示投影层

## 十一、XML 结构草案

当前芯片总结构建议至少包含这些区块：

- `identity`
- `loadout`
- `resource`
- `expression`
- `modes`
- `extensions`

其中：

- 芯片总层放共享信息
- 单来源层放各来源自己的信息
- 形态层放覆盖项
- `extensions` 放未来附加扩展位

这里故意不再把 `display` 单独列成芯片总块，
不是否认未来会有显示声明，
而是为了避免把“显示结果”和“芯片原始声明”重新混回一层。

## 十二、旧 BDP 芯片实例按需求本质归类

### 1. 纯 `Verb` 型

典型包括：

- `BDP_Chip_Asteroid`
- `BDP_Chip_Viper`
- `BDP_Chip_Meteora`
- `BDP_Chip_Kogetsu`
- `BDP_Chip_RifleAsteroid`

### 2. 纯 `Ability` 型

典型包括：

- `BDP_Chip_Grasshopper`

### 3. 纯 `Hediff` 型

典型包括：

- `BDP_Chip_Shield`
- `BDP_Chip_ShieldFront`

### 4. 纯 `Passive` 型

典型包括：

- `BDP_Chip_EmergencyEscape`

### 5. 复合多来源型

典型包括：

- `BDP_Chip_Raygust`

它不是新的顶层表达大类，而是：

- 多来源复合芯片

### 6. 多形态型

典型包括：

- `BDP_Chip_Raygust`

### 7. 远程模块化 `Verb` 型

典型包括：

- `BDP_Chip_Asteroid`
- `BDP_Chip_Viper`
- `BDP_Chip_Meteora`
- `BDP_Chip_RifleAsteroid`

它们说明的是：

- 远程 `Verb` 内部必须支持攻击链模块化

而不是：

- 需要额外再发明一个新的顶层表达大类

## 十三、第一版边界

当前第一版正式优先钉死的是：

- 芯片总定位
- 五类基础信息
- 四个表达顶层大类
- 多来源能力
- Trion 参数的层级边界
