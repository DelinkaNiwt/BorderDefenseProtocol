# Trigger 装载规则说明（第一版）

## 目的

这份说明专门用于把 BDP 中 `Trigger` 的装载、槽位、局部激活、局部失效、局部切换规则压成一份正式需求文档。

它回答的是：

- `CompTriggerBody` 这一层到底持有什么正式真值
- 芯片装载、卸下、局部激活、局部关闭、切换、禁用、形态切换分别如何成立
- Trigger 对表达层、入口层、战斗体层、存读档层到底提供什么正式输出
- 哪些规则属于 Trigger 自己，哪些不属于

它不回答的是：

- 当前到底形成了哪些表达结果
- 双武器表达和组合第三表达如何解析
- 战斗体整体相位如何流转
- 资源系统如何记账
- 视觉最终如何渲染

也就是说，这份文档的目标不是重新描述“攻击系统”，而是把 Trigger 收缩回：

- 装载 owner
- 局部激活 owner
- 局部禁用 owner
- 局部切换协调者

## 一、名词释义与辨析

这一节专门用于消除 Trigger 文档里最容易混淆的基础名词。

后续正文里如无特别说明，默认按本节定义理解。

### 1. 芯片

本文中的“芯片”指的是：

- 可被装入 Trigger 槽位的单个 `Thing`
- 它作为一个独立物品存在
- 它可以被 Trigger 正式容器持有

它不是：

- 一个槽位
- 一整侧的统称
- 一个表达结果

### 2. 槽位

本文中的“槽位”指的是：

- Trigger 内部的单个装载格
- 它有自己的侧别
- 它有自己的索引
- 它记录自己的装载芯片、激活态、禁用态、形态索引

它不是：

- 一整侧
- 一个按钮
- 一个表达

### 3. 侧

本文中的“侧”指的是：

- 一组槽位的归属类别

当前统一承认三侧：

- `Main`
- `Sub`
- `Special`

其中：

- `Main = 右`
- `Sub = 左`

侧是“槽位分组单位”，不是“单个槽位”。

### 4. 单槽位与单侧不是一回事

这是最容易混淆的地方。

- “单槽位”指一格槽位
- “单侧”指这一侧下的整组槽位

因此：

- “每个槽位同一时刻最多装载一枚芯片”

不等于：

- “每一侧同一时刻最多只能装一枚芯片”

旧 BDP 的当前槽位模型是：

- 一个槽位只记录一个 `loadedChip`

但一整侧可以有多个槽位，每个槽位都可以各自装一枚芯片。

### 5. 装载

本文中的“装载”指的是：

- 某枚芯片正式进入 Trigger 槽位体系
- 芯片进入 Trigger 正式容器
- 某个槽位记录这枚芯片为当前装载对象

它不是：

- 单纯 UI 上显示“这个槽里有东西”
- 单纯缓存里存了一个引用

### 6. 卸载

本文中的“卸载”指的是：

- 某枚芯片正式离开当前槽位
- 芯片正式离开 Trigger 的持有体系

它不是：

- 仅把按钮隐藏
- 仅把某个派生结果清空

### 7. 局部激活

本文中的“局部激活”指的是：

- 某个槽位当前正式成立为可用来源

它不等于：

- 战斗体整体激活
- 表达结果已经完全解析完毕
- 玩家当前已经看到对应按钮

### 8. 正式激活槽位

“正式激活槽位”指的是：

- Trigger 真值层认定当前已经成立的激活槽位

它不包括：

- 仍在 `WarmingUp` 的目标槽位

它在旧 BDP 的切换语义里可以包括：

- 仍在 `WindingDown` 的旧槽位

### 9. 切换中目标槽位

“切换中目标槽位”指的是：

- 当前局部切换过程正在尝试进入的目标

它不等于：

- 已正式激活

因此后续文档里如果写“目标槽位”，默认只是：

- 切换过程目标

不是：

- 正式来源已经切过去

### 10. 禁用

“禁用”指的是：

- 某槽位当前因局部规则失去可用资格

它不是：

- 空槽
- 已卸载
- 整个 Trigger 失效

### 11. 形态

“形态”指的是：

- 某枚芯片在当前槽位上采用的当前模式

它不是：

- 一个单纯显示皮肤
- 一个独立槽位
- 一个独立芯片实例

### 12. 事件、缓存、真值 owner

后续文档里这三个词也必须强行拆开：

- 真值 owner：正式持有某类事实的对象
- 事件：只通知变化的广播
- 缓存：为了读取效率保留的派生结果

事件和缓存都不能替代真值 owner。

## 二、先下总结论

### 1. Trigger 的本体不是攻击系统

`CompTriggerBody` 的本体不是：

- 一组按钮
- 一组固定武器
- 一组固定 `Verb`
- 一个总攻击协调中心

更准确地说，它的本体是：

- 槽位结构
- 芯片装载事实
- 局部激活事实
- 局部禁用事实
- 局部切换过程

### 2. Trigger 只持有“装载与局部激活”这类真值

它正式持有的是：

- 某一侧有哪些槽位
- 某个槽位当前装了什么
- 某个槽位当前是否正式激活
- 某个槽位当前是否被禁用
- 某个槽位当前处于哪个形态索引

它不正式持有的是：

- 表达结果真值
- 主攻击投影真值
- 战斗体整体相位真值
- Trion 资源真值

### 3. `Special` 也是槽位侧，不是“额外表达层”

`Special` 的本质仍然是 Trigger 槽位侧。

它不是：

- 第三只手
- 表达层独立宿主
- 一个临时补丁口

它和普通手槽的关键差异只是：

- 不参与左右普通切换状态机
- 走整体激活 / 整体关闭语义

### 4. 切换上下文不是正式真值 owner

切换中的 `WindingDown / WarmingUp` 上下文只能回答：

- 当前这一侧是否处于局部切换过程
- 当前局部切换过程处于哪个阶段
- 当前阶段大致何时结束

它不能替代：

- 当前哪一个槽位是正式激活槽位
- 当前哪一个槽位已经正式成立为表达来源

### 5. Trigger 是上游来源层，不是下游投影层

Trigger 的职责是给下游提供：

- 哪些芯片当前可作为正式来源
- 哪些来源因为局部规则而失效
- 哪些切换正在进行

它不直接回答：

- 当前应该生成几个按钮
- 当前默认主攻击是谁
- 当前视觉层该画什么

## 三、适用范围与行为真标准

### 1. 行为真标准

- 旧 BDP 中 `CompTriggerBody` 与其相关槽位、切换、手部联动、特殊槽、读档恢复代码事实，是这份文档的行为真标准
- 一次重构归档与其它设计稿只能辅助理解，不能替代旧代码事实
- 旧代码事实不明确处，以用户当前裁决为最高标准

### 2. 适用范围

本文适用于这些主题：

- `CompTriggerBody`
- `ChipSlot`
- `SwitchContext`
- Trigger 槽位结构
- Trigger 芯片正式容器
- Trigger 局部激活 / 关闭 / 切换 / 禁用 / 形态切换

本文不直接定义这些主题的完整业务：

- 表达解析
- 多表达共存
- 双武器表达
- 组合第三表达
- 战斗体闭环
- 远程攻击链
- 视觉渲染
- FireMode 参数调制

## 四、Trigger 的正式真值面

## 1. 槽位结构真值

Trigger 正式持有：

- 哪些侧存在
- 每侧有多少槽位
- 每个槽位的索引

这是 Trigger 的基础真值。

如果这层不成立，后续：

- 装载
- 激活
- 切换
- 形态切换
- 表达来源收集

都无从谈起。

## 2. 芯片装载真值

Trigger 正式持有：

- 某槽位是否装有芯片
- 该芯片是否真的被 Trigger 正式持有

这里必须特别强调：

- “槽位字段里记了一个引用”还不够
- 芯片必须真的进入 Trigger 的正式容器

否则：

- 存读档不可靠
- 装备转移不可靠
- 删除或掉落后状态容易悬空

## 3. 局部激活真值

Trigger 正式持有：

- 某槽位当前是否正式激活

这里的“正式激活”指的是：

- 该槽位当前可以作为正式表达来源
- 下游读取 Trigger 激活槽位时，应把它视为当前成立结果

它不等于：

- 正在切换到它
- 按钮上显示了它
- 视觉层已经切到它

## 4. 槽位禁用真值

Trigger 正式持有：

- 某槽位当前是否被局部规则禁用

禁用属于正式真值，不属于临时 UI 灰显。

被禁用的后果至少包括：

- 不允许激活
- 如已激活，则立即失去正式激活资格

## 5. 当前形态索引真值

Trigger 正式持有：

- 某槽位当前芯片的当前形态索引

这点很重要，因为形态索引不是显示参数。

它直接决定：

- 当前芯片按哪组效果配置成立
- 当前来源语义是什么
- 后续表达链应从哪种来源出发

## 6. 运行时辅助上下文不是正式真值

以下对象只属于运行时辅助，不属于正式真值 owner：

- 切换表现上下文
- 表达缓存
- 事件广播对象
- UI 灰显推导结果

特别是切换上下文，只是：

- 局部过程辅助上下文

不是：

- 当前正式激活唯一事实来源

## 五、三侧槽位模型

## 1. 内部稳定命名统一使用 `Main / Sub / Special`

二次重构内部稳定命名应统一使用：

- `Main`
- `Sub`
- `Special`

固定约定：

- `Main = 右`
- `Sub = 左`

这样做是为了：

- 和本轮重构的全局命名约束一致
- 避免系统内部各处来回混用 `Left/Right` 与 `Main/Sub`

## 2. `Left / Right` 只在和原版身体事实对接时使用

只有在这些场景下，才应直接使用 `Left / Right`：

- 身体部位判断
- 缺手 / 缺臂 / 左右身体部位映射
- 原版 `BodyPartRecord` 或类似宿主接口

其余 Trigger 内部规则描述，默认使用：

- `Main / Sub`

## 3. 三侧的共同点

三侧共同拥有这些基础属性：

- 槽位集合
- 每槽最多一枚芯片
- 芯片装载事实
- 槽位激活事实
- 槽位禁用事实
- 模式索引事实

也就是说，`Special` 不是“假的槽位”，而是真正式式槽位侧。

## 4. `Main / Sub` 与 `Special` 的关键差异

普通手槽：

- 参与普通侧局部切换
- 同侧同一时刻最多一个正式激活槽位
- 受双手锁定与跨侧规则影响

特殊槽：

- 不参与普通手槽切换状态机
- 走整体激活 / 整体关闭语义
- 不应被误当成“额外副手”

## 5. `Special` 的地位

`Special` 的地位应被明确承认：

- 它是 Trigger 结构的一部分
- 它属于当前就要保留的正式槽位模型
- 即使第一阶段只先保留骨架，也不能假装它不存在

因为后续这些内容都会依赖它：

- 特殊芯片
- 近界 / 黑触发器结构
- 战斗体生成时的整体激活

## 六、基础不变量

后续文档、代码、测试都应长期遵守以下基础不变量。

### 1. 槽位与装载

1. 每个槽位同一时刻最多装载一枚芯片
2. 一个装载中的芯片必须有明确所属槽位
3. 芯片要么在 Trigger 正式容器里，要么已正式离开 Trigger
4. 不允许“槽位引用还在，但容器里没有”的长期稳定状态

### 2. 激活

1. 已正式激活的槽位必须有已装载芯片
2. 被禁用槽位不能保持正式激活
3. 普通手槽每侧同一时刻最多一个正式激活槽位
4. `Special` 不按“每侧一个”的规则处理，而按整体语义处理

### 3. 切换

1. 切换上下文存在，不自动等于正式激活已改变
2. `WindingDown` 时旧槽位仍然属于正式激活槽位
3. `WarmingUp` 时目标槽位还不是正式激活槽位
4. 查询口只能读取已成立事实，不承担补救式结算

### 4. 禁用

1. 槽位禁用是正式状态，不是临时视觉态
2. 槽位禁用后，芯片可以保留在槽位
3. 槽位禁用导致局部能力失效，但不自动等于整体崩解

### 5. 形态

1. 模式索引属于槽位真值的一部分
2. 形态切换会改变来源语义
3. 形态切换应被视为表达链重算触发点之一

## 七、装载与卸载规则

## 1. 装载的本质

芯片装载不是：

- 点一下 UI 就算完成
- 某个缓存里记一下就算完成

芯片装载的正式成立至少包括：

1. 芯片通过 Trigger 允许的入口进入
2. 芯片进入 Trigger 正式容器
3. 槽位记录该芯片为当前装载芯片
4. 装载变化对外广播

## 2. 装载成立条件

某芯片装入某槽位时，至少应检查：

- 槽位存在
- 槽位当前为空
- 芯片对象存在且合法
- 芯片满足该槽位类型约束
- 当前管理权限允许装载

后续还应长期容纳这些外围规则：

- 特殊槽限定
- 普通手槽限定
- 双手锁定期间是否允许改装
- 战斗体激活中是否允许改装
- 某些触发器是否根本不允许玩家管理

## 3. 槽位限制属于装载层规则

像 `HandsOnly`、`SpecialOnly` 这种限制，本质上是：

- 该芯片可否进入该槽位的正式规则

它不是：

- 仅供 UI 提示的文字
- 表达层的过滤条件

一旦装载层没有拦住，后面就会把错误状态扩散到：

- 激活
- 表达来源
- 主攻击投影
- 视觉与信息投影

## 4. 卸载的本质

卸载的本质是：

- 芯片正式离开当前槽位
- 芯片正式离开 Trigger 持有容器
- Trigger 对该芯片的装载事实结束

它不是：

- 仅把槽位字段清空
- 仅把图标隐藏

## 5. 卸载成立条件

某槽位芯片卸下时，至少应检查：

- 槽位存在
- 当前确实有芯片
- 当前不处于不允许卸载的正式状态

这类“不允许卸载”的正式状态，后续至少应包含：

- 当前正式激活中
- 当前切换处理中
- 当前受更高层战斗体约束

第一阶段允许先采取保守语义：

- 正式激活中槽位不可直接卸载

## 6. 装载变化的下游影响

装载变化会改变的，不是按钮本身，而是：

- 正式来源候选集合
- 后续局部激活可能性
- 表达层重算输入

因此装载变化至少应触发：

- Trigger 自身装载事件
- 表达缓存失效

但它不应直接在 Trigger 内部完成：

- 表达最终解析
- 主攻击投影最终选定
- 视觉最终切换

## 八、局部激活与局部关闭规则

## 1. 局部激活不是战斗体整体激活

Trigger 的局部激活只回答：

- 某槽位当前能否正式进入局部激活

它不回答：

- Pawn 当前是否已整体进入战斗体 `Active`
- 整个战斗体是否允许维持

换句话说：

- 战斗体层裁定“整体能否成立”
- Trigger 裁定“局部哪一个槽位成立”

## 2. 局部激活前置条件

局部激活前至少要通过这些正式检查：

- 战斗体层允许当前进行局部激活
- 槽位存在
- 槽位有芯片
- 槽位未禁用
- 资源层允许支付激活成本
- 输出功率等外围条件满足
- 双手锁定与跨侧约束满足
- 互斥规则满足
- 芯片效果自身允许激活

这里要特别注意：

- Trigger 可以发起这些检查
- 但资源真值仍然属于资源层
- 战斗体整体相位真值仍然属于战斗体层

## 3. 普通手槽的局部激活语义

普通手槽至少应遵守：

- 同侧同一时刻最多一个正式激活槽位
- 激活新槽位时，如同侧已有旧槽位激活，应按切换语义处理
- 没有旧槽位时，可直接进入新槽位激活路径

## 4. `Special` 的局部激活语义

`Special` 不应按普通手槽的“一侧切一格”理解。

它的正式语义应是：

- 特殊槽是同一组整体
- 激活时按整体批量激活
- 关闭时按整体批量关闭

它不应被误设计成：

- 用户逐格点开 / 逐格点关的普通副槽

## 5. 局部关闭语义

局部关闭回答的是：

- 某一侧当前正式激活槽位如何结束局部激活

它至少要区分：

- 纯关闭
- 切换关闭
- 强制关闭

这里的“强制关闭”后续会包括：

- 手部损坏
- 更高层解除流程要求
- 其它正式中断来源

## 6. 局部关闭不等于整体解除

关闭某个槽位不自动等于：

- 所有槽位都关闭
- 战斗体整体退出
- Trion 已全部释放

这些后果是否成立，应交给：

- 战斗体层
- 资源层
- 统一收尾层

而不是在 Trigger 自己这里偷做成一锅端。

## 九、切换状态机规则

## 1. 为什么 Trigger 需要切换状态机

普通手槽的激活不是永远都能瞬时完成。

旧 BDP 的真实需求里已经存在：

- 关闭后摇
- 激活前摇
- 切换空窗期

所以 Trigger 需要一层正式切换语义来回答：

- 当前这一侧是不是正在局部切换
- 当前旧槽位是否仍算正式激活
- 当前目标槽位是否已经正式成立

## 2. 正式阶段

Trigger 局部切换至少应长期承认三种阶段：

1. `Idle`
2. `WindingDown`
3. `WarmingUp`

它们分别回答：

- `Idle`：当前这侧没有局部切换过程
- `WindingDown`：旧槽位正在结束，但尚未正式关闭
- `WarmingUp`：目标槽位正在进入，但尚未正式激活

## 3. `WindingDown` 的正式语义

`WindingDown` 时：

- 旧槽位仍然是正式激活槽位
- 旧来源仍然是当前侧正式来源
- 新槽位还没有正式成立

这点必须钉死。

否则后面很容易出现：

- 旧来源被过早移除
- 新来源被过早加入
- 按钮、投影、视觉一起提前切换

## 4. `WarmingUp` 的正式语义

`WarmingUp` 时：

- 旧槽位已经正式结束
- 目标槽位仍未正式激活
- 目标槽位最多只能算“正在进入”

所以 `WarmingUp` 期间：

- 不应把目标槽位当成已正式成立来源
- 不应让表达层把它视为已生效来源

## 5. 纯关闭与切换的区别

纯关闭路径：

- 有旧槽位
- 没有目标槽位
- 只需把旧槽位走完关闭过程

切换路径：

- 有旧槽位
- 也有目标槽位
- 先旧槽位结束，再目标槽位进入

这两者不能混成一个模糊“切换中”。

## 6. 查询口必须读取已成立结果

切换状态机的查询口只能回答：

- 当前切换阶段是什么
- 当前进度大概多少
- 当前目标槽位是谁

它不能在查询时偷偷改写：

- 正式激活真值
- 资源真值
- 战斗体相位真值

## 7. 暂停下必须立即成立的规则

以下内容不得依赖游戏继续走 tick 才“逻辑上成立”：

- 发起装载
- 发起卸载
- 发起局部激活
- 发起局部关闭
- 当前是否允许该操作
- 当前正式激活槽位是谁
- 当前按钮可见性依据的正式结果

tick 在 Trigger 这层只允许用于：

- 前摇 / 后摇 / 切换空窗期这类表现计时

不允许用于：

- 让本该立即成立的逻辑结果延后成立

## 十、双手锁定与跨侧约束

## 1. 双手锁定的本质

双手锁定的本质不是：

- 某个表达层临时判断
- 某个按钮层特殊限制

它的本质是：

- Trigger 装载与局部激活层的跨侧约束

也就是说，它回答的是：

- 当某个槽位激活后，另一侧还能不能再正式成立新的局部激活

## 2. 双手锁定何时生效

至少应在这类芯片激活后生效：

- 被定义为双手芯片的芯片

其正式后果应是：

- 锁定另一侧新的局部激活成立
- 必要时先关闭另一侧已存在的局部激活

## 3. 双手锁定何时解除

双手锁定应在锁定来源槽位正式关闭后解除。

它不应：

- 依赖某个按钮自己清理
- 依赖视觉层切换成功后再清理

## 4. 为什么这条规则必须写在 Trigger 文档里

因为它决定的是：

- 哪些局部来源可以同时成立

这正是 Trigger 的职责范围。

如果把它拖到表达层再判断，就会导致：

- Trigger 允许了错误的局部激活
- 表达层再被迫补救式过滤
- 真值 owner 混乱

## 十一、槽位禁用与身体部位联动

## 1. 槽位禁用的本质

槽位禁用回答的是：

- 这一侧或这一格当前是否因局部身体条件而不能继续使用

它是：

- Trigger 真值的一部分

它不是：

- 仅供 UI 显示的灰显态
- 整体崩解判定结果

## 2. 手部损坏与局部失效

旧 BDP 的事实已经说明：

- 手部 / 手臂 / 肩部破坏可以导致对应侧槽位禁用
- 禁用后该侧当前局部能力立即失效

但这不自动等于：

- 战斗体整体崩解

因此后续必须长期坚持：

- 局部失效和整体崩解分层处理

## 3. 禁用后的芯片去留

槽位禁用后，芯片应允许：

- 继续保留在槽位中

这说明禁用的语义是：

- “不能用”

而不是：

- “自动卸下”

## 4. 禁用后的局部激活状态

槽位一旦禁用：

- 该槽位不能继续保持正式激活
- 该槽位也不能重新激活

这条规则必须立即成立，不得等待时间流动。

## 5. 禁用的恢复时机

禁用的恢复不应由 Trigger 自己随意猜测。

它应当由更高层正式流程驱动，例如：

- 战斗体解除
- 身体恢复
- 统一恢复链路

也就是说：

- Trigger 负责持有当前禁用真值
- 但是否恢复、何时恢复，应由正式上游流程裁定

## 十二、多形态芯片与 Trigger 层责任

## 1. 形态索引属于 Trigger 槽位真值

某槽位当前芯片处于哪一个模式，不是纯显示问题。

它应属于：

- 该槽位的正式状态

因为它直接影响：

- 当前激活时调用哪一组效果
- 当前来源语义是什么

## 2. 形态切换的 Trigger 层直接后果

形态切换至少会直接改变：

- 当前槽位模式索引
- 当前槽位激活效果集合
- 当前槽位来源语义

如果该槽位当前已激活，则形态切换本质上是：

- 关闭旧形态
- 切到新索引
- 重新按新形态成立

## 3. 形态切换是整条链的重算触发点

形态切换不是芯片自己的私事。

它至少应触发这些下游重算：

- 表达来源重算
- 表达结果重算
- 手动入口重算
- 默认主近战 / 主远程投影重算
- 外部兼容表面重算
- 视觉与执行跟随重算

但这些重算结果本身：

- 不由 Trigger 自己持有为真值

## 十三、Trigger 对外正式输出面

Trigger 后续应向其它系统稳定提供这些正式读取面。

## 1. 给表达层的输出

- 当前全部槽位快照
- 当前正式激活槽位集合
- 当前槽位模式索引
- 当前槽位禁用态

## 2. 给入口与投影层的输出

- 当前正式激活来源
- 当前切换表现上下文
- 当前哪些侧处于局部切换中

## 3. 给战斗体层的输出

- 当前局部激活情况
- 当前禁用情况
- 当前装载总览

但 Trigger 不应把这些输出伪装成：

- 战斗体整体相位

## 4. 给存读档层的输出

- 正式槽位结构
- 正式容器内容
- 正式激活态
- 正式禁用态
- 正式模式索引
- 切换上下文

## 5. 给测试扩展层的输出

后续正式扩展接口至少应允许测试模组读取：

- 当前装载状态
- 当前激活状态
- 当前禁用状态
- 当前切换上下文

但不应鼓励测试模组：

- 直接偷读内部缓存
- 直接改写 Trigger 私有字段

## 十四、事件、缓存与 owner 边界

## 1. 事件只通知，不持有真值

Trigger 发出的装载、激活、关闭变化事件，只能用于：

- 通知
- 失效缓存
- 广播变化

不能用于：

- 充当唯一真值来源
- 让其它系统靠“错过没收到事件”来丢状态

## 2. 缓存只服务读取效率

表达缓存、投影缓存这类对象，只能：

- 从 Trigger 正式真值推导
- 在 Trigger 真值变化后失效

它们不能：

- 比 Trigger 真值更权威

## 3. Trigger 的 owner 边界

Trigger 负责：

- 槽位结构
- 装载与卸载
- 局部激活与局部关闭
- 槽位禁用
- 模式索引
- 局部切换过程

Trigger 不负责：

- Trion 数值真值
- 战斗体整体相位真值
- 表达结果最终真值
- 主攻击模式最终真值

## 十五、存读档与恢复责任边界

## 1. Trigger 必须正式保存的状态

至少包括：

- 各侧槽位结构
- 每槽装载芯片
- 每槽是否激活
- 每槽是否禁用
- 每槽当前形态索引
- 必要的切换上下文
- 正式芯片容器

## 2. Trigger 不应把哪些东西当真值存起来

不应把这些当正式真值直接保存：

- 表达结果缓存
- 按钮集合
- 默认主攻击投影结果
- 视觉投影结果

因为这些都应当：

- 在读档后从正式真值重算

## 3. 读档后 Trigger 至少要完成什么

读档后 Trigger 至少要做：

- 槽位结构补齐
- 容器与槽位对齐校正
- 丢失或非法芯片清理
- 激活态合法性校正
- 形态索引延续
- 必要运行态重建

## 4. Trigger 不单独承担完整恢复闭环

即使 Trigger 自己恢复完成，也不等于整个系统恢复完成。

后续完整恢复还要涉及：

- 战斗体层
- 表达层
- 投影层
- 资源层

因此 Trigger 在恢复方面的正式定位应是：

- 先保证装载与局部激活真值恢复
- 再把重算机会交给下游系统

## 十六、当前阶段必须落地与只留口

## 1. 第一阶段必须正式落地

Trigger 这块当前阶段至少必须正式落地：

- `Main / Sub` 基本槽位结构
- 正式芯片容器
- 装载
- 卸载
- 局部激活
- 局部关闭
- 当前状态查询
- 基本切换表现上下文
- 变化事件广播

## 2. 第一阶段应先留口但不能忘记

以下内容当前阶段可以不完整落地，但必须在文档中预留明确边界：

- `Special` 完整业务语义
- 双手锁定完整细则
- 槽位禁用完整规则
- 手部损坏细化等级
- 多形态完整规则
- 战斗体联动完整恢复
- 更完整的存读档续接

## 3. 为什么现在就要把这些写出来

因为这些内容虽然可以后补实现，
但它们会反过来影响当前是否要预留：

- 槽位字段
- 正式接口
- 事件边界
- 恢复口
- 下游读取面

不能等后期再发现：

- 基础结构早期没有预留
- 真值面不够
- 结果只好再返工 Trigger 本体

## 十七、对后续实现的直接要求

### 1. 不能把 Trigger 再写回“大总管”

后续实现中，凡是出现 Trigger 直接持有：

- 主攻击模式
- 全局表达结果
- 战斗体整体阶段
- Trion 数值

都应视为越界。

### 2. 不能把切换表现做成逻辑真值来源

切换上下文只能辅助解释：

- 当前正在切换什么

不能反过来代替：

- 当前正式激活结果

### 3. 不能把局部禁用做成整体崩解

局部禁用只回答：

- 某槽位或某侧当前不可用

整体是否崩解，应留给：

- 战斗体层

### 4. 不能把多形态切换当成 UI 小功能

形态切换必须被实现成：

- Trigger 真值变化点
- 表达链重算触发点

### 5. 不能把存读档恢复做成缓存复活

读档恢复必须从：

- 正式槽位
- 正式容器
- 正式激活态

出发。

不能把：

- 缓存
- 按钮
- 临时投影结果

当成唯一恢复基础。

## 十八、一句话总括

Trigger 装载系统的本体，不是“一组按钮背后的攻击逻辑”，而是“正式持有芯片、维护槽位装载事实、裁定局部激活与局部失效、并向上游表达系统提供稳定来源面”的系统；它必须保持 owner 边界清楚，既不越权持有资源与战斗体真值，也不把事件、缓存、切换表现误当成正式事实。
