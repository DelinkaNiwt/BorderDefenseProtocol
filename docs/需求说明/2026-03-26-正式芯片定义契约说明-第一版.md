# 正式芯片定义契约说明（第一版）

## 目的

这份说明不是表达系统子文档，
也不是给测试模组补入口的说明。

它要先回答一件更上位的事：

- 在 BDP 里，一枚正式芯片到底需要向主模组声明什么

这份说明不再沿用上一轮偏抽象的旧说法。

以下旧骨架从本版开始明确作废：

- `Identity`
- `Resource`
- `IsFormalChip`
- `ContractVersion`
- `ChipKindKey`
- 泛 `Namespace / Key / Value` 扩展结构

如果需要看“芯片内部条目、形态、Trion 层级”的细化说明，
应配合：

- `2026-03-24-芯片标准结构说明-第一版.md`

一起看。

## 一、先用玩家能懂的话说结论

### 1. 芯片首先是一枚真实芯片

对玩家来说，
芯片首先不是一段契约声明，
而是一枚真实存在的 Trigger 芯片。

它应能：

- 生成
- 持有
- 装载
- 切换
- 随存档恢复

### 2. 芯片要说清楚五件事

一枚正式芯片最少要向主模组说清楚：

- 我是什么类型的芯片
- 我能装到哪里
- 我能表达出哪些能力
- 装上和启动我自己要多少 `Trion`
- 我还有没有少量额外正式说明要交给别的系统

### 3. 芯片不是运行时结果 owner

芯片不能替代：

- Trigger 的装载真值
- 表达系统的结果真值
- Trion 系统的运行真值
- CombatBody 的运行真值

芯片只负责上游静态声明，
不负责保存战斗现场结果。

### 4. 形态属于表达，不属于芯片本体

形态改变的是：

- 这枚芯片当前哪些表达成立
- 这些表达怎样被追加、替换、禁用

形态不改变：

- 芯片本体身份
- 装载本体规则
- 芯片本体级 Trion 语义

所以形态留在 `expression` 内部，
不单列成芯片总块。

## 二、芯片总结构正式固定为五块

当前正式固定为：

- `profile`
- `loadout`
- `expression`
- `trion`
- `extensions`

### 1. `profile`

回答：

- 这是什么芯片
- 它的主分类是什么
- 它有哪些补充标签

这一块首先服务：

- 玩家理解
- 信息模板选择
- 排序
- 诊断

它不负责：

- 自证自己是不是正式芯片
- 直接决定装载结果
- 直接决定表达结果

### 2. `loadout`

回答：

- 能装到哪些侧、哪些槽
- 是否双持绑定
- 有哪些装载互斥语义
- Trigger 装载时需要知道的正式约束

这一块只回答“怎么装”，
不回答“装完最后表达出什么”。

### 3. `expression`

回答：

- 这枚芯片有哪些表达条目
- 条目属于哪一类
- 条目之间有什么正式关系
- 形态如何对条目做操作

这块继续由表达系统作为主要下游消费者。

### 4. `trion`

回答：

- 这枚芯片本体级 Trion 占用是多少
- 激活这枚芯片本身要付什么成本
- 这枚芯片本身有什么功率要求或其它本体门槛

这一块只放芯片本体级 Trion 参数，
不放条目使用级成本。

### 5. `extensions`

回答：

- 这枚芯片还有哪些正式附加声明需要交给其它系统

扩展区保留，
但只能有一个总入口。

它不是垃圾桶，
也不是为了跳过正式结构而开的偷渡口。

## 三、哪些东西属于芯片自己，哪些不属于

### 1. 属于芯片自己的

- 芯片画像和分类
- 装载约束
- 表达条目声明
- 芯片本体级 Trion 参数
- 少量正式扩展声明

### 2. 不属于芯片自己的

- 当前是否激活
- 当前哪条表达结果成立
- 当前默认主攻击是谁
- 当前按钮该不该出现
- 当前自动攻击拿哪条 `Verb`
- 当前剩余多少 Trion

这些都属于运行结果，
不能塞回芯片定义层冒充声明。

## 四、外部内容作者最少该声明什么

### 1. 最低合法芯片至少要有

- `profile`
- `loadout`
- `expression`
- `trion`

否则它只是普通物品，
还谈不上 BDP 芯片。

### 2. `profile` 至少要说明

- `primaryCategory`
- `tags`

当前基础分类固定为：

- 单主类
- 可选标签

主分类可参与：

- 信息模板选择
- 排序
- 说明分组
- 诊断

### 3. `expression` 至少要说明

- 条目 `id`
- 条目类型
- 条目最低必要参数

例如：

- `Verb` 条目声明 `VerbProps`
- `Ability` 条目声明 `AbilityDef`
- `Hediff` 条目声明 `HediffDef`
- `Passive` 条目声明稳定被动键和暴露数据

### 4. `trion` 至少要说明

- 占用
- 激活成本
- 功率要求

而使用消耗、持续消耗这类，
继续留在具体表达条目的 `trion` 区。

## 五、各系统应该从芯片读取什么

### 1. Trigger 应读取

- `loadout`
- 必要时少量 `profile`

Trigger 不应读取：

- 表达内部条目细节
- 最终表达结果

### 2. Expressions 应读取

- `expression`

必要时可读少量 `loadout` 语义，
但不应依赖 Trigger 私有实现。

### 3. Trion 系统应读取

- `trion`
- 必要时少量 `profile`

它不应读取：

- 表达系统内部对象
- Trigger 私有槽位实现

### 4. 说明、信息、兼容系统应读取

- `profile`
- 正式结果面
- 必要时芯片本体级 `trion`

它们不应直接摸：

- 表达内部管线
- Trigger 私有上下文

## 六、主模组当前要正式承认什么，不承认什么

### 1. 当前正式承认

- 芯片定义层独立成立
- 主模组内部统一走芯片读取口
- 芯片总结构按 `profile / loadout / expression / trion / extensions`
- 形态归入 `expression`

### 2. 当前明确不承认

- 自我宣誓式正式芯片标记
- 契约版本号
- 稳定类型键
- 泛资源块命名
- 通用三元组扩展结构

## 七、当前结论

这层要解决的不是“先让某个测试功能跑起来”，
而是先把主模组真正承认的芯片输入边界封干净。

从这一版开始，
后续代码与文档都应以这套新骨架为准：

- `profile`
- `loadout`
- `expression`
- `trion`
- `extensions`
