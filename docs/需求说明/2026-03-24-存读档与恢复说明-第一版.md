# 存读档与恢复说明（第一版）

## 目的

这份说明不写成“当前有哪些字段要 `Scribe` 一遍”的字段清单。

这份说明要定义的是：

- 哪些对象有资格作为正式恢复基础
- 哪些状态必须持久化
- 哪些状态必须在读档后重算
- 哪些状态必须在读档后清空
- 哪些流程允许续接
- 哪些缓存、投影、桥接结果绝不能被当成真值恢复

因此本文的重点不是：

- 某个旧类里具体保存了几个字段
- 某个当前实现里暂时序列化了什么

而是：

- 恢复责任协议
- owner 边界
- 正式容器
- 正式结果与临时结果的区分
- 读档后重建顺序
- 对未知扩展的兼容性

## 一、先下总结论

### 1. 存读档恢复必须服从 owner 边界

恢复时真正允许作为真基础的，
只能是正式 owner 所持有的正式真值。

当前至少包括：

- `CompTrion` 的资源真值
- `CombatBodyState` 的战斗体相位真值
- `CompTriggerBody` 的装载与局部激活真值
- 正式在途宿主自己的在途真值

不能把以下东西当成恢复真基础：

- 事件广播记录
- 投影缓存
- 显示结果
- 临时按钮
- 临时桥接对象
- 为兼容外部系统而生成的映射结果

### 2. 读档恢复不是“把所有运行时对象复活”

正确恢复不是：

- 把上一次运行期里所有临时对象都序列化下来
- 读档后尽量原样塞回去

正确恢复应是：

- 保留正式 owner 真值
- 让运行时缓存、投影、桥接结果从正式真值重新生成

### 3. 存读档必须承认“持久化 / 重算 / 清空 / 续接”四种不同责任

不是所有状态都应该进入同一类处理。

系统至少要区分：

1. 必须持久化的正式真值
2. 读档后必须重算的正式投影结果
3. 读档后必须清空的临时运行态
4. 读档后允许续接的时间过程或在途宿主状态

### 4. 恢复顺序必须从 owner 到投影，不能反过来

正确顺序应是：

1. 恢复正式 owner
2. 恢复正式容器关系
3. 续接允许续接的宿主状态
4. 重算表达结果、投影结果、显示结果
5. 最后才让外部兼容面重新读取

不能写成：

1. 先恢复按钮
2. 先恢复 `Verb`
3. 先恢复显示入口
4. 再倒推 owner 是什么

### 5. 读档后立即应成立的逻辑仍必须立即成立

恢复流程不能依赖：

- “等下一 tick 再慢慢修正”

如果某个状态在读档完成当下已经满足成立条件，
它就必须在读档后立即可查询成立。

tick 只允许用于：

- 自然恢复
- 冷却倒计时
- 在途过程推进
- 表现计时

不允许用于：

- 读档后补齐本该已经成立的正式逻辑

## 二、行为真标准与适用范围

### 1. 行为真标准

本文行为真标准来自两层：

第一层：

- 旧 BDP 已经证明 Trigger 装载、战斗体阶段、在途宿主、快照恢复都属于真实需求

第二层：

- 二次重构要求的是“在 owner 边界下建立统一恢复协议”，不是继续堆叠旧代码里的恢复补丁

因此旧 BDP 在这里的作用是：

- 证明哪些主题必须被覆盖
- 提醒哪些东西跨存档确实会断

而不是：

- 规定未来必须照搬旧实现的数据形状

### 2. 适用范围

本文适用于：

- 触发体
- 战斗体
- 资源系统
- 表达结果重建
- 主攻击投影重建
- 在途宿主续接
- 显示与兼容读取重建

本文不直接规定：

- 具体 `Scribe` API 写法
- 具体字段命名
- 具体类拆分方式

## 三、名词释义与辨析

### 1. 正式真值

“正式真值”指的是：

- 某个正式 owner 对外负责的、可作为恢复基础的状态

例如：

- 当前 Trion 量
- 当前战斗体相位
- 当前槽位装载与局部激活状态

### 2. 正式结果

“正式结果”指的是：

- 从正式真值经过正式规则计算出的、可被外部读取的结果

例如：

- 当前表达结果集合
- 当前默认主攻击投影
- 当前允许显示的信息结果

它与“正式真值”不同：

- 它可以不直接存档
- 但必须能从正式真值稳定重建

### 3. 临时运行态

“临时运行态”指的是：

- 只为当前运行期方便而存在的缓存、桥接、上下文、查询结果

例如：

- 表达缓存
- Gizmo 临时载体
- 外部兼容桥接结果
- 查询时的组合中间表

### 4. 正式容器

“正式容器”指的是：

- RimWorld 原生持有体系中真正承载 Thing / Hediff / 其它正式对象所有权的容器

只有进入正式容器，
这些对象才有可靠的存读档基础。

### 5. 续接

“续接”指的是：

- 读档后继续承认某个时间过程或在途宿主仍处于进行中

它不同于“重算”：

- 重算是根据真值重新得出结果
- 续接是承认某个过程本身没有结束

## 四、恢复责任总原则

## 1. 谁持有真值，谁负责最小恢复基础

恢复责任首先是 owner 责任。

例如：

- `CompTrion` 负责资源值
- `CombatBodyState` 负责阶段值
- `CompTriggerBody` 负责装载与局部激活值

不能写成：

- 外层事件协调器替 owner 保存真值
- 显示层替 owner 反向恢复真值

## 2. 事件只通知，不构成恢复基础

任何事件系统都只能：

- 通知“发生了什么”

不能承担：

- 跨存档记住“真相是什么”

### 3. 投影、显示、兼容结果必须可重建

表达投影、显示投影、兼容表面都应被视为：

- 从 owner 真值与正式结果派生出来的读取面

因此它们原则上应：

- 读档后重算

而不是：

- 当成独立真值持久化

## 4. patch 不承担恢复业务主体

即使某些外部兼容读取最终需要 patch 接线，
patch 也只能：

- 重新把读取流量接回正式结果

不能承担：

- 自己持有恢复真值
- 自己推断恢复顺序
- 自己补做复杂恢复业务

## 五、哪些状态必须持久化

建议长期承认以下类别必须进入持久化范围。

## 1. 正式 owner 真值

至少包括：

- `CompTrion` 的 `cur / max / allocated / reserved / frozen`
- `CombatBodyState` 的 `phase / allocatedTrion / activationTick / cooldownEndTick / collapseStartTick / collapseReason`
- `CompTriggerBody` 的槽位结构、槽位装载芯片引用、局部激活状态、局部禁用状态

这里持久化的意义是：

- 读档后仍能回答“当前真实处于什么状态”

## 2. 正式容器关系

只要某个正式对象跨存档后仍应存在，
它就必须进入正式容器体系。

例如：

- Trigger 芯片必须真正进入 `ThingOwner`
- 在途宿主如果仍存在，就必须由其正式宿主类自己序列化

## 3. 允许续接的在途过程真值

某些过程本身不是缓存，
而是“读档后仍应继续存在”的正式过程。

例如：

- 投射物已生成且仍在飞行
- 某些 `PawnFlyer` 仍在进行中
- 某些 Hediff 自己带有正式倒计时
- Trigger 局部切换表现仍处于正式表现计时中

这一类必须由它自己的正式宿主承担序列化。

## 4. 不可从当前世界直接反推的恢复上下文

如果某个恢复过程所需信息：

- 既不是临时缓存
- 也不能从当前世界状态直接反推
- 但又是恢复闭环所必需

那么它应被承认为正式恢复数据。

例如旧 BDP 中：

- 战斗体快照

这类数据不能因为“看起来像辅助对象”就直接降级为缓存。

## 六、哪些状态必须重算

## 1. 表达结果集合

表达结果本身可以是正式结果，
但不应依赖旧缓存复活。

读档后应从：

- Trigger 装载真值
- 局部激活真值
- 当前宿主上下文

重新解析出：

- 当前可用表达结果集合

## 2. 主攻击投影与外部兼容表面

这些结果应在读档后根据：

- 当前表达结果
- 当前攻击链协议

重新建立。

不能因为某个旧 `Verb` 引用还在，
就把它当成唯一恢复基础。

## 3. 显示值与信息兼容结果

显示层读取结果应从正式结果重新生成，
不能把旧 UI 缓存或旧说明文本当成恢复基础。

## 4. 调制参与结果

参数调制参与者的影响应通过：

- 正式调制协议
- 正式上下文

重新合并得出。

不能把某次运行期已经合并好的临时数值快照当成唯一真值继续使用。

## 七、哪些状态必须清空

## 1. 临时缓存

例如：

- 表达缓存
- 查询缓存
- 视觉缓存
- 兼容桥缓存

## 2. 临时按钮与直接操作载体

例如：

- 运行期构建出的 Gizmo 列表
- 临时命令对象

这些对象应在读档后按正式结果重新生成，
而不是从存档直接复活。

## 3. 事件订阅与临时回调关系

例如：

- 某个运行期临时注册的事件监听
- 某个协调器内部的短生命周期回调

这些应在读档后重新挂接，
不能把旧委托图当作持久化对象。

## 4. 只服务于当前一次动作的上下文

例如：

- 某次攻击提交中的临时上下文
- 某次解析中的中间合并表
- 某次手动操作的现场参数

读档后应视为已经结束。

## 八、哪些状态允许续接

## 1. 合法在途宿主

如果一个正式宿主对象本身仍存在，
并且它的正式语义就是“过程尚未结束”，
那么它允许续接。

例如：

- Projectile
- `PawnFlyer`
- 某些正式 Hediff

但前提是：

- 它们有自己的正式宿主类
- 它们由自己的正式宿主承担存读档

## 2. 时间过程

时间过程允许续接，
但要明确它们只是“过程续接”，不是“逻辑补算补丁”。

例如：

- 冷却剩余时间
- 崩解表现剩余时间
- 在途飞行剩余时间

## 3. 续接后的结果仍要走正式查询口

即使某个过程允许续接，
外部系统也不能直接去读它的私字段推业务。

续接后对外仍应通过：

- 正式状态查询口
- 正式结果读取口

## 九、三类核心 owner 的恢复边界

## 1. `CompTrion`

### 必须持久化

- 当前总量
- 最大量
- 已占用量
- 预占用量
- 冻结状态
- 持续消耗注册表

### 读档后必须做

- 状态裁剪
- 重建运行时字典
- 重新安排自然恢复与持续消耗结算时点

### 不应持久化为真值的东西

- 下次查询缓存
- 读数显示文本

## 2. `CombatBodyState`

### 必须持久化

- 当前阶段
- 锁定资源量
- 激活时间
- 冷却结束时间
- 崩解开始时间
- 崩解原因

### 读档后必须做

- 立刻收掉已经结束的冷却
- 保证暂停下查询也能得到已成立结果

### 不应越权承担

- Trigger 装载恢复
- 资源系统恢复
- 显示层恢复

## 3. `CompTriggerBody`

### 必须持久化

- 槽位集合
- 芯片正式容器
- 槽位对芯片的正式引用
- 局部激活状态
- 局部禁用状态

### 读档后必须做

- 保证槽位结构完整
- 保证芯片回到正式容器
- 保证槽位引用与容器对齐
- 让局部激活真值可直接被读取

### 若需要续接的局部表现过程

- 切换表现上下文

它的正式定位应是：

- 局部表现过程续接信息

而不是：

- Trigger 装载与局部激活真值本身

### 不应越权承担

- 战斗体整体相位恢复
- 资源真值恢复
- 复杂显示层恢复

## 十、表达、投影、显示的恢复边界

## 1. 表达层

表达层应从正式 owner 真值重新解析。

它恢复的不是：

- 旧缓存对象本身

而是：

- 旧缓存对应的正式表达结果

## 2. 投影层

默认主攻击投影、手动按钮载体、外部兼容表面都应：

- 从当前表达结果重建

不能把某个旧 `Verb` / `Command` 实例是否还在当成正式依据。

## 3. 显示层

显示层只负责读取恢复后的正式结果，
不负责自己补推恢复逻辑。

## 十一、远程攻击链与在途宿主恢复边界

## 1. 远程链应区分“链前结果重建”和“链中宿主续接”

链前结果重建包括：

- 当前哪些表达可用于远程攻击
- 默认主远程入口是什么
- 当前调制协议会生成什么正式攻击参数面

链中宿主续接包括：

- 已生成的 Projectile
- 已进入世界的飞行宿主

两者不能混成一个“全都序列化”的做法。

## 2. 在途宿主必须自己承担正式恢复

如果一个在途宿主需要跨存档继续存在，
它必须由自己的正式类承担：

- 位置
- 目标
- 阶段
- 在途参数

而不是依赖外部攻击系统去替它补回全部运行态。

## 3. 攻击系统只负责重新提供正式读取面

读档后攻击系统需要做的是：

- 让新的攻击请求仍能走正式链路
- 让外部读取能重新拿到正式入口

不是：

- 替已经存在的在途宿主重演一遍发射

## 十二、调制参与者的恢复边界

## 1. 调制参与者不是攻击系统真值 owner

因此它们的恢复边界应是：

- 恢复自身正式配置或正式档位
- 重新通过正式调制通道参与合并

而不是：

- 直接恢复一次已经被它改过的攻击结果快照

## 2. 调制结果必须重新合并

原因是：

- 读档后的宿主状态可能已变化
- 多个调制参与者可能共存
- 未来未知调制功能也要遵守同一协议

所以恢复后正确做法应是：

- 重新读取参与者状态
- 重新走正式调制合并口

## 十三、恢复顺序建议

建议长期遵守以下顺序：

1. 恢复 RimWorld 原生正式容器与正式宿主
2. 恢复 `CompTrion`
3. 恢复 `CombatBodyState`
4. 恢复 `CompTriggerBody`
5. 续接合法在途宿主
6. 重算表达结果
7. 重建攻击投影与兼容表面
8. 重建显示读取结果
9. 最后重新挂接事件与扩展口

这个顺序的核心是：

- 先恢复真值
- 再恢复结果
- 最后恢复读取与通知

## 十四、对后续实现的直接要求

### 1. 不能把缓存复活当成恢复方案

### 2. 不能把显示结果当成真值存档

### 3. 不能让 patch 自己承担恢复主体

### 4. 不能依赖下一 tick 才把读档后应成立的逻辑补齐

### 5. 不能让某个外部功能私自定义一套自己的恢复协议

### 6. 任何新功能在实现前都必须先判定自己属于：

- 必须持久化
- 必须重算
- 必须清空
- 允许续接

否则它就还没有被正式纳入系统恢复协议

## 十五、一句话总括

BDP 的存读档与恢复，真正要建立的不是“一份把运行期所有对象都序列化下来的保命清单”，而是“一套严格服从 owner 边界的恢复责任协议：正式真值进入持久化，正式结果在读档后重建，临时缓存与桥接结果在读档后清空，合法在途宿主按自身正式语义续接，并且所有读档后立即应成立的逻辑都必须立即成立”的统一标准。
