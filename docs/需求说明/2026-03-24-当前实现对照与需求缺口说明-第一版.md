# 当前实现对照与需求缺口说明（第一版）

## 目的

这份说明专门回答两个问题：

- 基于新 BDP 现在已经写出的代码事实，它实际已经做到哪里
- 对照旧 BDP 既有功能和当前需求目录，它还遗漏了哪些需求，哪些需求现在必须继续细化

这里不按“类名看起来像做了什么”来判断。

这里按三类事实来判断：

1. 新 BDP 当前真正已经落地并接通的链路
2. 旧 BDP 已经存在、但新 BDP 还没有承接回来的功能与机制
3. 需求文档虽然已经提到，但颗粒度还不够，后续如果不继续钉死，实施时仍然容易走偏的部分

## 一、先下结论

### 1. 新 BDP 当前落地的是“第一阶段最小主链”

它现在真正已经接通的重点只有：

- Trigger 槽位装载、激活、关闭、存读档容器
- 激活槽位到表达来源的最小收集
- 表达到默认主远程 / 主近战的最小解析
- 默认主远程 / 主近战到原版自动攻击入口的桥接
- 两个手动按钮到原版 `Verb` 目标选择入口的桥接
- 远程 / 近战 / 爆炸伤害链中的攻击语义传递
- 伤口括号来源名改成“攻击行为名”

这条链已经证明：

- “贴原版宿主”这条方向是能跑通的
- “语义上下文”这条机制是能稳定进入伤害下游的

但它还远远不是完整 BDP。

### 2. 新 BDP 当前最大的问题，不是“有些功能没写”，而是“很多系统只立了骨架”

典型表现是：

- 类和接口已经存在，但还没有真正接进主链
- 文档里已经承认目标很复杂，但代码里目前只落了最小回路
- 有些需求已经被知道了，但规则边界还没细到能直接指导实现

因此当前不能误判成：

- “主体已经差不多，只剩补点外围”

更准确地说是：

- “已经打通一条正确方向的最小样板链”
- “离旧 BDP 的完整需求覆盖还差多个大块”

### 3. 当前最该继续深化的，不是随便挑功能加，而是先把几组高风险规则写实

最危险的不是“暂时没做 Shield / Glow / FireMode”。

最危险的是下面这些如果不先写实，后面一做就容易再次返工：

- 多表达如何正式共存、重算、投影
- Trigger 装载约束如何正式成立
- 战斗体激活 / 崩裂 / 收尾 / 快照恢复如何闭环
- 远程攻击链每一段的正式输入输出和模块插点
- 视觉渲染 / 外部信息兼容 / 正式接口之间如何分层

## 二、新 BDP 当前已经真正落地的部分

## 1. 触发体基础装载主链已经成立

当前 `CompTriggerBody` 已经真正承担了这些正式事实：

- Main / Sub / Special 三侧槽位结构
- 芯片装入与卸下
- 正式激活与关闭
- 芯片 `ThingOwner` 容器持有
- 存读档恢复后槽位与容器重新对齐

这说明新 BDP 已经不再像旧 BDP 那样把太多状态散在多个临时字段和 UI 行为里。

但它现在仍然只做到：

- “最小槽位事实成立”

还没做到：

- 特殊槽正式规则
- 双手锁定
- 槽位禁用完整语义
- 手部损坏联动
- 多形态切换引发的正式重算

## 2. 表达系统只落地了“单侧来源 -> 默认主近战 / 主远程”的最小回路

当前 `TriggerExpressionCollector` + `BasicExpressionResolver` 真正做的是：

- 从当前正式激活槽位读取来源
- 读取芯片 Def 上的表达声明配置
- 只处理 `Verb` 宿主
- 从全部来源里挑一个默认主远程、一个默认主近战

这条链现在没有真正实现：

- 双武器表达
- 组合第三表达
- `Ability` 表达
- `Hediff` 表达
- `Passive` 表达
- 多来源之间的正式合成规则
- 形态切换后的整链重算

所以目前代码虽然已经有“表达系统”这个名字，但本质上还只是：

- “默认主近战 / 主远程选择器”

不是完整表达系统。

## 3. 自动攻击桥和手动按钮桥已经接通，但仍是最小投影

当前投影层真正接通了：

- 自动远程读取口
- 自动近战读取口
- 两个手动按钮入口
- 一个默认表层来源读取口

但它仍然只是：

- 主远程一个按钮
- 主近战一个按钮

它还没有正式落地：

- 单侧独立按钮并存
- 双武器按钮
- 组合技按钮
- 副攻击入口
- 手动层与自动层分开但共享底层规则的完整投影
- 多表达明细展示
- 对外正式读取接口

因此当前按钮链能证明“方向对”，但不能证明“多表达投影问题已解决”。

## 4. 伤害来源语义链已经接通，而且是当前最完整的一块

当前最扎实的一块其实是“攻击行为语义下传”：

- `Verb` 能携带语义
- `Projectile` 能接语义
- 爆炸链能继续带语义
- 伤口来源名能显示表达名而不是触发体名
- 崩裂事件参数也已经预留语义上下文

这块已经证明：

- “通信不只调逻辑，还能带信息”这条需求可以做成正式架构的一部分

但它还只是第一步。

还没继续扩到：

- 更广的行为上下游链
- 非伤害型表达的语义记录
- 更多下游对象对语义的消费规则

## 5. Trion 和战斗体目前是“真值骨架已写，主链还没正式接回”

`CompTrion` 已经有正式资源真值语义：

- `Cur / Max / Allocated / Reserved / Available`
- 一次性消耗
- 聚合持续消耗
- 自然恢复
- 冻结
- 边界事件

`CombatBodyState` / `CombatBodyCoordinator` / `CombatBodyCleanupCoordinator` 已经有：

- `Inactive / Active / Collapsing / Cooldown`
- 激活
- 手动解除
- 崩裂
- 冷却收束
- 最小收尾接口

但从当前代码事实看，这一组还没有真正接到新 BDP 的正式游戏主链里。

也就是说：

- 它们现在更像“正确边界的独立骨架”
- 还不是“已经在模组里真正驱动战斗体行为的正式系统”

## 三、对照旧 BDP，当前明确遗漏的需求

下面这些不是“也许以后再说”。

它们要么是旧 BDP 已经真实存在的功能，要么是当前需求清单已经明确列为必须回收的部分。

## 1. 触发体装载规则还缺大半

当前还没有正式承接回来的至少包括：

- 特殊槽完整语义
- 双手锁定与另一侧封锁
- 槽位禁用规则
- 手部缺失 / 手部损坏联动
- 多形态芯片切换
- 当前激活槽位与切换中槽位的完整规则
- 装载管理 GUI
- 状态显示 Gizmo

这些不是纯 UI 细节。

它们决定的是：

- 哪些表达来源可以成立
- 哪些表达必须失效
- 哪些切换会触发整条链重算

## 2. 表达系统仍缺最关键的“多表达真实体”

旧 BDP 里已经存在、但新 BDP 还没接回的包括：

- 左右侧独立表达并存
- 双武器表达
- 组合第三表达
- `Ability` 型表达
- `Hediff` 型表达
- `Passive` 型表达
- 主攻击与副攻击并存
- 一个按钮承载多个可直接操作行为模式

这部分当前如果不继续深化规则，后续很容易再次退化成：

- “两个默认按钮 + 一个默认主攻击”的假多表达系统

## 3. 远程攻击链的模块化目前只落到最外层宿主，没有落到链内

旧 BDP 已经真实存在的链内模块，包括但不限于：

- 瞄准侧模块
- 发射侧模块
- 路径引导
- 锚点瞄准
- LOS 检查
- 范围指示
- 齐射 / 扩散
- Trion 消耗模块
- 飞行数据模块
- 自动路由
- 追踪
- 引导
- 轨迹
- 爆炸模块

新 BDP 现在虽然已经有：

- 自定义 `Verb`
- 自定义 `Projectile`
- 爆炸语义桥

但它还没有正式落地：

- “攻击链按作用点拆模块”的架构本体

也就是说：

- 现在只是宿主换成了正确方向
- 链内统一模块协议还没有真正建起来

## 4. 战斗体主业务目前还没有真正回收

旧 BDP 已经存在、当前需求也明确要求的，包括：

- 战斗体进入时的正式宿主变化
- 快照保存
- 退出恢复
- 崩裂表现
- 紧急脱离
- 多来源触发崩裂
- 崩裂后的统一收尾
- 身体变化恢复
- 与伤害 / hediff 的联动

新 BDP 现在只有：

- 阶段真值类
- 协调器类
- 收尾接口类
- 空的宿主桥

所以这部分仍然属于：

- “方向明确，但业务尚未真正落地”

## 5. 展示、绘制、枪口、发光系统基本还没回收

旧 BDP 已经存在而新 BDP 几乎还没开始的，包括：

- 左右手武器绘制
- 绘制遮罩 / 抑制原版武器绘制
- 枪口基准位置
- 发射点与绘制共基准
- 执行侧与绘制跟随一致
- 发光层与控制器
- 护盾显示
- 视觉特效联动

这块不能被误判成“后面做点美术就行”。

因为它实际承载的是：

- 多表达在游戏里的真实可见状态

## 6. 外部信息兼容目前只做了伤害来源名，没有做正式兼容层

当前已经做了：

- 伤口括号来源名

但还没正式做：

- 场景默认主攻击决策
- 多表达明细展示
- 原版信息卡 / 信息类模组的稳定读取面
- 对愿意接入 BDP 的外部扩展开放的正式接口
- 兼容回退策略

而这是这次重构里明确属于：

- 旧 BDP 没做好，但新 BDP 必须新增强化的需求

## 7. 火力模式系统还没有重新进入主线

旧 BDP 里，`FireMode` 不只是一个小窗口。

它实际影响了：

- 子弹数量
- 伤害
- 飞行速度
- 展示面板
- 双侧相同芯片也可能因为模式不同而行为不同

新 BDP 当前完全还没有把这块写回主链。

所以它不是“单纯少一个设置页面”，而是：

- 一整组会影响攻击链多个环节的参数调制系统尚未回收

## 8. Shield / 特殊 Hediff / 伤口扩展链还没有回收

旧 BDP 已有的外围但真实影响战斗闭环的部分，包括：

- 护盾伤害拦截
- 护盾绘制与特效
- 自定义伤口 Hediff
- 自定义伤口显示与愈合规则
- 伤口附带 Trion 相关效果

这些不一定都属于第一优先级核心主线。

但它们绝对不能被视作“和主需求无关”。

因为它们决定的是：

- 旧 BDP 战斗结果如何落地到 Pawn 身上

## 9. 快照、存读档恢复、身体恢复类需求还缺正式方案

当前新 BDP 只在 Trigger 这边认真处理了芯片容器和槽位存读档。

但对照旧 BDP 与需求清单，后面还必须正式覆盖：

- 战斗体阶段存读档
- 激活中 / 崩裂中状态恢复
- 快照恢复
- 装备 / 背包 / apparel / hediff / need 等恢复
- 身体变化后的重建

如果这组规则不单独写实，后面很容易出现：

- 表面能用
- 一读档或一恢复就全乱

## 10. 测试扩展层和工具收纳层只开了口，还没形成正式规范

当前已经有：

- `TriggerExternalGizmoRegistry`

它证明“后置测试模组通过正式接口挂入”这条方向是对的。

但还没形成完整正式规范：

- 测试模组可读取哪些正式状态
- 测试模组可注册哪些入口
- 外部扩展读多表达应该走什么接口
- 工具类应该沉到哪个统一位置

## 四、当前最需要继续提高颗粒度的需求主题

下面这些不是“可以一边写代码一边再想”。

它们如果现在不继续细化，后面最容易再次让实现偏掉。

## 1. Trigger 装载规则说明

需要继续单独写实的至少包括：

- 特殊槽到底承担什么
- 双手锁定什么时候生效、锁谁、何时解除
- 手部缺失和手部损坏分别影响什么
- 槽位禁用是短时状态还是正式规则
- 切换中、激活中、正式激活三者边界
- 多形态切换如何沿整条表达链重算

这块现在在总需求清单里已经出现，但颗粒度还不足以直接指导实现。

## 2. 多表达解析规则说明

需要继续钉死的包括：

- 单侧表达如何成立
- 双武器表达如何成立
- 组合第三表达如何成立
- 同时成立多少表达
- 同时暴露多少手动入口
- 当前默认主近战 / 主远程 / 主兼容表面分别怎么选
- 形态切换时哪些投影必须一起重算

当前文档已经讲清“不能混着理解”，但还没把正式判定规则完全写死。

## 3. 远程攻击链正式 I/O 说明

现在最需要继续细的是：

- 表达层输入什么
- 瞄准层输入输出什么
- 发射层输入输出什么
- 投射物层输入输出什么
- 命中层输入输出什么
- 爆炸 / 落地层输入输出什么
- 下游伤害 / hediff / 语义记录如何接
- 每一类模块应该挂在哪一段，而不是按玩法名乱挂

当前专项说明已经指出方向，但要继续写到“能直接指导实现”的粒度。

## 4. 战斗体闭环说明

这是当前最缺细节、又最容易误做成“自造小游戏系统”的一块。

必须继续写实：

- 激活前检查
- 激活时到底对 Pawn 做什么
- 快照何时创建
- 崩裂由哪些来源触发
- 是否有紧急脱离分支
- 崩裂表现期与无敌期关系
- 何时收尾
- 何时恢复
- 恢复顺序
- 读档时如何复位或续接

## 5. 视觉渲染与信息兼容的正式读取模型

当前已有专项说明，但还需要继续细到：

- 绘制层读取哪一份正式结果
- 枪口 / 发射点读取哪一份正式结果
- 当前执行表达与场景默认主攻击决策的关系
- 外部只认一个武器表面时如何回退
- 外部若愿意接完整数据，应通过什么正式接口读取
- 哪些对象值得做定点补丁，哪些不做

## 6. 火力模式与参数调制说明

当前文档里几乎还没有把这块单独钉死。

但对照旧 BDP 事实，它值得独立写一份说明，因为它会影响：

- 单侧攻击
- 双武器攻击
- 表示层数值
- 攻击链参数
- 相同芯片不同实例的行为差异

## 7. 伤害结果落地说明

当前“语义下传”已经起步，但后面还需要继续细：

- 伤口是否要自定义 Hediff
- 哪些伤害继续用原版伤口
- 哪些结果要带额外 BDP 信息
- 护盾、爆炸、状态施加等落地层各自怎样回到原版可理解对象

## 8. 存读档与恢复说明

这块建议单独成文。

因为它不是实现细枝末节，而是：

- 哪些状态必须存
- 哪些状态应在读档后重算
- 哪些状态应在读档后清空
- 哪些对象必须真的进入 `ThingOwner`
- 哪些缓存绝不能当真值

## 五、当前可直接指导后续排期的判断

## 1. 可以视为“已经有正确最小样板”的部分

- Trigger 正式槽位装载
- 表达最小收集
- 默认主近战 / 主远程投影
- 自动攻击桥
- 手动按钮桥
- 攻击语义进入伤害下游

这些部分适合：

- 作为后续扩展的“正确最小样板”

而不是推倒重来。

## 2. 不能误判为“已经完成”的部分

- 表达系统整体
- 战斗体系统整体
- Trion 与战斗体联动
- 视觉渲染层
- 外部信息兼容层
- 远程模块化攻击链
- 测试扩展接口层

它们现在最多只能算：

- 已开头
- 或已立边界
- 或已落一个最小样板点

## 3. 接下来文档深化的优先顺序建议

优先顺序建议如下：

1. Trigger 装载规则说明
2. 多表达解析规则说明
3. 战斗体闭环说明
4. 远程攻击链正式 I/O 说明
5. 火力模式与参数调制说明
6. 伤害结果落地说明
7. 存读档与恢复说明

## 六、总收束

新 BDP 当前并不是“已经接近完整，只剩补外围”。

它真正达到的状态是：

- 已经用正确方向接通了一条最小主链
- 已经证明“贴原版宿主 + 多层投影 + 语义下传”这条路线可行
- 但旧 BDP 的大部分复杂真实需求还没有正式承接回来

因此下一步最重要的不是盲目加功能。

而是继续把那些会决定整条链怎么长的高风险规则，先写到足够细、足够硬、足够不容易误解。
