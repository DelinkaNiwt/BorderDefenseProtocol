# 项目起步约束

## 目标

本项目是旧 BDP 的二次重构。

当前阶段目标不是赶快重写功能，而是先把起步基础打稳：

- 新项目目录独立建立
- 旧版只读参考
- 关键结论持续落文档
- 中文文件与编辑方式先固定

## 当前范围

当前只做这些事：

- 建立最小模组骨架
- 建立最小文档记录区
- 研究旧 BDP
- 研究 RimWorld 原版引擎通道
- 定义起步约束、边界、原则

当前不做这些事：

- 不开始正式业务重构
- 不引入复杂架构层
- 不以一次重构产物为基础继续演化

## 工作边界

- 旧项目 `BorderDefenseProtocol.Legacy` 是唯一行为参考源
- 一次重构的项目和文档只作为失败经验，不作为当前设计基础
- 任何新设计都要先回答“它贴 RimWorld 的哪个原版通道”
- 如果某个抽象不能让代码更容易理解、验证、维护，就不引入

## 文档规则

- 中文优先
- 必须保留英文名词时，旁边给出简短中文说明
- 正式结论必须写入 `docs`
- 每次重要决定都写一条决策记录
- 每次会话结束前补一条简短交接记录，避免上下文丢失
- 每次阶段性工作交回给用户前，补一条简短工作日志，留下本次做了什么、结论是什么
- 工作日志不再每次单开新文件，改为每 10 次记录合并到同一卷里；满 10 次后再开下一卷
- 从当前阶段开始，文档、接口草案、代码草案都默认增加广覆盖注释
- 注释目标读者不只是假定熟练开发者，也包括普通玩家和初级模组开发者
- 注释要简单明了，先说明“它是什么、干什么、为什么在这里”

## 中文与编码规则

- 新项目文本文件统一使用 UTF-8
- 编辑中文文件时，优先在新项目里新增 UTF-8 文件，不直接批量改旧版历史文件
- 在终端读取中文文件前，先把 PowerShell 输入输出编码切到 UTF-8

建议命令：

```powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::InputEncoding = [System.Text.UTF8Encoding]::new($false)
```

- 如果终端输出仍乱码，先怀疑终端编码，不先怀疑文件内容
- 修改含中文的正式文件时，优先小步修改并立即回读验证
- 后续所有手工编辑统一走 ASCII 映射路径 `C:\NiwtDatas\Projects\RimworldModStudio\bdp_ascii`

## 起步阶段的硬原则

- 务实有效优先，不搞空转的大工程仪式
- 正文只呈现最终结果，不在正文里保留“从旧改到新”的过程表述
- 先研究旧 BDP 的本质，再决定新骨架
- 先贴 RimWorld，再谈抽象
- 优先使用 RimWorld 原版已有宿主、接口、数据通道与生命周期；只有确认不存在合适、自然、可维护的原版实现通道时，才允许进入 patch 方案评估
- 如果某个原版宿主适合被 BDP 继承成轻量自定义子类，且风险不高、不会明显破坏兼容性，这是一种优先级较高的实现策略
- patch 只能作为引擎接线的后备手段，不能作为默认优先方案
- 使用 patch 前必须先明确记录：为什么原版通道不够用、patch 具体接在哪个边界、它的前置条件是什么、如何限制影响范围、有哪些兼容风险
- 使用 patch 时必须把侵入面压到最小，避免把业务规则写进 patch 本身；patch 只负责接线，不负责承载复杂业务
- 先定 owner，再谈事件和模块
- 先分清“逻辑立即成立”和“时间表现推进”，再决定是否引入 tick
- 先做短链路闭环，再扩展
- 后续默认“实现与配置要有注释”，字段、方法、接口、XML 配置都尽量覆盖
- 每次设计和实现后，都要主动回看当前文档与旧代码，自查是否遗漏了资源、战斗体、装载、表达、入口、收尾这些系统块
- 不能等用户指出问题后才补，要默认自己多反省、多回顾、多交叉检查
