# 长期硬约束与工作方法总纲（第一版）

## 这份文件的定位

这份文件不是某个局部功能的需求文档。

它负责长期约束整个二次重构过程中的：

- 架构判断
- 工作方法
- 风险识别
- 沟通方式
- 文档与日志义务

它比单次计划更稳定，
比单次会话记录更长期。

以后只要继续推进这个项目，
无论是在写文档、做设计、改代码、做测试，还是做复审，
都应先回看这份文件，
确认没有偏离根本方向。

## 一、根本目标

这个项目的根本目标是：

- 对旧 BDP 做真正的架构重构

不是：

- 机械搬运旧功能
- 赶进度式堆出可玩结果
- 先做功能再回头补结构
- 做一个脱离 RimWorld 的平行系统

这里的“重构”必须满足：

- 外在本质表现不偏离旧 BDP
- 内部原理重新整理
- 架构更清楚
- 边界更诚实
- 扩展更自然
- 维护更稳定

项目的最高事项是：

- 架构的正确
- 架构的干净
- 架构的优雅

功能表现是验卷方式，
不是主导设计的唯一中心。

应该让功能从架构中自然生长，而不是写好功能硬塞入架构
如果为了实现功能而污染架构，
就等于偏离了项目的根本动机。

项目体量：单人游玩的单机游戏的一个模组

## 二、事实来源等级

本项目中，事实来源的优先级固定如下：

### 第一优先级

- 用户裁定

当关键问题不明确、文档互相冲突、旧代码无法直接定论时，
以用户裁定为最高标准。

### 第二优先级

- 旧 BDP 代码事实

旧 BDP 的代码事实是唯一行为真标准。

这里强调的是：

- 代码实际行为和本质需求

不是：
- 旧代码的表象
- 对旧设计的印象
- 对旧文档的二手概括

### 第三优先级

- 现有需求文档

需求文档是设计约束来源，
用于明确方向、边界、阶段路线与风险点。

但如果需求文档与旧 BDP 行为事实存在冲突，
必须显式识别，
不能偷换。

### 第四优先级

- 一次重构归档与其它辅助材料

一次重构已归档，
不作为当前设计基础，
只能辅助参考。

## 三、长期总原则

二次重构期间，
必须长期挂住这些原则：

### 1. 架构高于赶功能

- 功能不是第一目标
- 可用不是第一目标
- “先通再说”不是合理借口

真正优先的是：

- 边界是否正确
- 结构是否干净
- 系统是否自然

### 2. 必须始终保持全局视角

不能只盯：

- 当前报错
- 当前按钮
- 当前某个类
- 当前某段业务

必须始终问：

- 这会不会破坏全局边界
- 这会不会为后期埋耦合
- 这会不会重新制造上帝系统
- 这会不会把系统拉回旧 BDP 的痛点

### 3. 从 RimWorld 出发，最后回到 RimWorld

所有正式实现，
都应优先落回 RimWorld 的自然通道与自然宿主。

### 4. 不凭印象，不凭记忆硬做

每次推进前，
都必须基于现有文档、旧 BDP、当前代码事实建立上下文。

### 5. 关键裁定必须写下来

重要的边界、原则、禁忌、阶段路线，
不能只留在对话里，
必须写入：

- 项目宪章
- 决策记录
- 计划文件
- 源码旁注释
- 会话日志
  
对于绝不允许遗忘的信息，以最简方式以注释形式写在代码文件内。LLM模型的特性注定了如果不在代码里早晚会忘记

## 四、全局架构主旋律

本项目的总体架构主旋律固定为：

- 多核心骨架
- 局部模块化
- 事件通信

这三个词不是宣传语，
而是长期判断任何代码是否健康的标准。

### 1. 多核心骨架

模组不是单核心总控架构。

必须承认有多个稳定核心，
并让它们长期保持各自的真实边界。

### 2. 局部模块化

局部模块可以存在，
但只能处理局部切面，
不能借机长成新的总系统。

### 3. 事件通信

事件用于：

- 通知
- 同步
- 解耦

事件不用于：

- 持有真值
- 替代 owner
- 倒推出系统当前状态

## 五、真值边界硬约束

这是本项目最重要的长期硬约束之一。

### 1. 三类真值 owner 不能混

当前长期固定的三类真值 owner 为：

- `CompTrion`：只持资源真值
- `CombatBodyState`：只持战斗体相位真值
- `CompTriggerBody`：只持装载与局部激活真值

这三者的边界不能混，
不能借协调之名模糊，
不能借便利之名复制镜像。

### 2. 不允许新增第四个方便 owner

任何对象都不能因为“用起来顺手”而再持一份：

- 资源状态
- 相位状态
- 装载状态

尤其警惕：

- Host
- Coordinator
- Runtime
- EventBus
- Debug 结构
- GUI 状态模型

### 3. 事件只通知，不持真值

事件可以广播：

- 已发生了什么
- 刚刚发生了什么

事件不能变成：

- 当前事实来源
- 最近真值缓存
- “收到事件就等于状态已经改变”的替代品

### 4. 不允许镜像真值长期并存

如果两个对象都开始回答同一类核心事实，
就已经进入高风险区。

例如：

- Trigger 和 CombatBody 同时像战斗体 owner
- 表现层和主链同时像阶段 owner
- 测试层与正式层分别保存自己的状态

这种情况必须尽快整顿。

## 六、对象职责判断准绳

任何对象的设计与改造，
都要遵守以下职责判断准绳。

### 1. owner 只持自己的真值

owner 的职责是：

- 持有真值
- 对外暴露正式读写面

owner 不应吞掉其它核心的职责。

### 2. 协调者只编排，不吞 owner

协调者可以：

- 编排事务
- 收集结果
- 判断流程走向
- 触发通知

协调者不可以：

- 再持一份资源状态
- 再持一份装载状态
- 再持一份相位真值

### 3. Host 只是宿主位，不是新核心

Host 的职责应收束为：

- 正式挂接点
- 外部面的承接位
- 宿主桥

Host 不应成为：

- 新 owner
- 新总控
- 新的快照容器

### 4. 局部模块只做局部切面

局部模块可以承担：

- 进入步骤
- 离开步骤
- 某类恢复
- 某类解析
- 某类投影

但不能顺势演化成：

- 平行主链
- 平行 runtime
- 平行生命周期中心

### 5. 表现层只负责表现

表现层可以承担：

- Hediff 表现
- 绘制
- UI 呈现
- 反馈文本

但不应承担：

- 主链宿主
- 真值中心
- 越权流程控制

## 七、长期高危问题清单

以后每次推进或复审，
都要重点盯这些问题。

### 1. 上帝系统膨胀

判断信号包括：

- 一个对象越来越大
- 横跨多类职责
- 同时理解太多上下文
- 外部越来越依赖它

### 2. 不必要耦合

判断信号包括：

- 直接跨核心取内部状态
- 测试层依赖实现类
- GUI 直插业务内部
- 表现层反向控制主链

### 3. 过度抽象

判断信号包括：

- 新增很多接口但没有稳定边界收益
- facade/bridge/adapter/runtime 壳层增多
- 真实行为没简化，理解成本却更高

### 4. 假解耦

判断信号包括：

- 表面走接口，实质还是硬耦合
- 抽象层并未隔离真实变化点
- 代码绕了一圈，职责反而更模糊

### 5. 临时实现污染正式架构

判断信号包括：

- 为了测试先加的东西被正式依赖
- 为了过渡先写的逻辑长期存活
- debug 逻辑被正式行为默认依赖

### 6. 构建与接线污染判断

不仅源码会污染架构，
构建方式、引用方式、加载时机也会污染实际判断。

例如：

- 吃旧 DLL
- 在错误阶段做注入
- 测试层拿到的不是当前主工程产物

这些都必须纳入排查。

## 八、对抽象和接口的长期要求

### 1. 抽象必须有真实收益

只有在以下情况下，
抽象才值得长期保留：

- 隔离稳定边界
- 暴露正式外部面
- 降低必要耦合
- 提高长期可维护性

### 2. 不要为“看起来模块化”而抽象

如果新增抽象只是让结构看起来更整齐，
但没有减少复杂度，
那它就是负担。

### 3. 空壳接口应谨慎

空壳接口、空骨架、空 facade 如果没有明确长期记忆价值，
就容易变成过度抽象。

### 4. 未来预留要克制而诚实

可以为未来留最小锚点，
但不能把大量未来设想提前做成现在的空系统。

判断标准是：

- 这个锚点是否真的会反复影响后续结构判断
- 它是否足够薄
- 它是否不会挤占当前正式职责

## 九、对耦合的长期判断标准

不是所有耦合都错，
但每条耦合都要问是否合理。

### 1. 可接受耦合

通常更可接受的是：

- owner 到自己真值的耦合
- 协调者到正式外部面的耦合
- 自然宿主到自己局部行为的耦合

### 2. 高风险耦合

应优先警惕：

- 跨核心直接取内部对象
- 越权调用对方内部细节
- 临时调试口被正式逻辑依赖
- 测试按钮依赖内部实现类

### 3. 耦合要诚实

如果必须耦合，
也应耦合到：

- 正式外部面
- 自然宿主
- 稳定边界

而不是耦合到某个现在刚好能用的内部类。

## 十、RimWorld 导向与 patch 原则

### 1. 必须优先回到原版自然通道

优先考虑的正式通道包括但不限于：

- `Verb`
- `Ability`
- `Hediff`
- `Projectile`
- `Gizmo`
- `ThingComp`
- `JobDriver`

### 2. 不轻易发明平行系统

只要 RimWorld 已有自然通道，
就不应优先自建平行机制顶替它。

### 3. patch 不是优先方案

只有当：

- 原版没有自然接入点
- 自然通道确实不足以承接需求

时才评估 patch。

### 4. patch 只负责接线

patch 可以做：

- 最小挂接
- 最小转发
- 最小捕获

patch 不应做：

- 复杂业务
- 真值承载
- 多阶段流程中心

## 十一、时间与状态成立原则

### 1. 不能让状态成立依赖 tick 流动

凡是本应立即成立的逻辑，
都必须在暂停下也立即成立。

### 2. tick 只用于真正时间过程

tick 可以用于：

- 自然恢复
- 冷却
- 表现计时
- 持续过程结算

tick 不应用于：

- 本应同步成立的禁用判断
- 本应立刻切换的状态提交
- 本应即时成立的边界逻辑

### 3. 暂停是正式状态，不是例外

暂停下能否正确成立，
是验证逻辑是否真正独立于时间流的关键标准之一。

## 十二、测试与正式隔离原则

### 1. 测试必须通过正式扩展口接入

测试层只能：

- 调用正式外部面
- 观察正式状态
- 提供测试 UI/按钮/诊断

测试层不能：

- 直接改正式内部状态
- 依赖内部实现类才能工作
- 要求主模组知道测试模组存在

### 2. 测试代码必须可整块删除

测试层删掉后，
主模组不应有任何残留影响。

### 3. 必须持续提供短周期可测机会

不能闷头编码太久，
等很久后才第一次进游戏验证。

必须让阶段推进始终具备：

- 可测
- 可视
- 可反馈
- 易诊断

### 4. 但不能为了测试污染正式架构

测试需要不能反过来支配正式结构设计。

规划上要为测试做准备，
实现上不能变成应试思维。

## 十三、文档、注释与日志义务

### 1. 中文优先

默认使用中文表达。

必要英文可以保留，
但应在旁边给出简短中文说明。

### 2. 文档、代码、XML 默认广覆盖注释

注释不能只停留在粗粒度概述。

重要对象、字段、方法、参数、配置项，
应尽量有逐成员注释。

### 3. 注释要解释职责与边界

注释不应只是重复代码字面意思。

更应解释：

- 这是做什么的
- 为什么放在这里
- 不该做什么
- 与谁边界相邻

### 4. 正文只呈现结果

正式文档正文不写“从旧改到新”的过程口吻。

过程留给：

- 历史
- 日志
- 版本记录

### 5. 每次行动结束都要留简要日志

工作日志必须持续维护，
便于以后回溯与交接。

## 十四、沟通与推进方式

### 1. 不能闷头做

推进过程中应持续说明：

- 准备做什么
- 怎么做
- 为什么
- 当前理解是什么

### 2. 不能只讲抽象空话

要给具体判断，
而不是只给口号与套话。

### 3. 要边做边确认

在高风险架构点上，
不能长时间脱离讨论独自推进。

### 4. 要有计划，不要迷失在细节里

必须有：

- 局部清单
- 阶段路线
- 停点
- 回查点

避免无限“下一步”与局部钻牛角尖。

## 十五、实现前的强制流程

每次准备实现功能前，
都应遵循以下基本顺序：

1. 回查需求文档确认方向
2. 回查旧 BDP 代码确认细节
3. 回查当前新 BDP 现状
4. 判断边界与风险
5. 再决定如何下手

禁止：

- 凭记忆直接实现
- 凭印象复述需求
- 看到相似结构就机械套用

## 十六、实现后的强制复审

每次改完代码准备交付前，
都应至少做一次架构重审。

复审重点包括：

- 旧 BDP 的痛点是否在重演
- 当前结构是否出现显而易见错误
- 谁在膨胀成上帝系统
- 哪里存在耦合，是否必要
- 哪里有不必要的过度抽象
- 哪里有临时/测试代码进入正式依赖链

如果发现污染，
应敢于整套回切，
而不是只补表面。

## 十七、阶段推进原则

### 1. 可以分阶段推迟次要内容

不是所有需求都要立刻完整实现。

### 2. 但必须提前考虑长期结构支持

不能等到后期才发现：

- 当前结构没有预留自然通道
- 当前实现堵死了未来扩展
- 当前命名和职责让后期必须返工

### 3. 预留不是提前堆空系统

必须区分：

- 合理最小锚点
- 不必要空骨架

## 十八、长期自查问题

以后每次继续推进前，
至少应先问自己这些问题：

1. 这次工作是否仍服务于“旧 BDP 外在本质表现不变”
2. 这次设计是否贴着 RimWorld 原版自然通道在走
3. 三类真值 owner 是否仍清楚分离
4. 这次是否新增了不必要耦合
5. 这次是否新增了过度抽象
6. 这次是否把测试或临时实现带进正式架构
7. 这次是否只顾当前局部而忽略全局结构
8. 这次是否会让某个对象继续膨胀成上帝系统
9. 这次是否把应立即成立的逻辑做成依赖 tick
10. 这次是否把关键裁定落进了文档或源码旁锚点

## 十九、长期禁忌事项

以下行为应视为项目中的长期禁忌：

- 为了实现功能而忽视架构
- 凭记忆硬做
- 把事件当真值
- 混 owner
- 让测试污染正式
- 用 patch 承载复杂业务
- 为了方便当前而制造平行系统
- 用 tick 偷渡本应即时成立的逻辑
- 让对象无意识膨胀
- 长时间闷头推进而不复审

## 二十、一句话总括

二次重构期间，
所有设计、实现、测试、文档与复审，
都必须服从同一个核心目标：

- 在旧 BDP 外在本质表现不变的前提下，
  以 RimWorld 自然通道为基础，
  维持诚实的多核心边界，
  用克制的局部模块和事件通信去构建一个真正干净、正确、优雅、可持续演化的新 BDP。
