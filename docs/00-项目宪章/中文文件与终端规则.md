# 中文文件与终端规则

## 目的

避免出现以下问题：

- 中文文件被写坏
- 终端读出来是乱码
- 编辑工具把中文变成 `?`
- `apply_patch` 因编码或目录状态异常反复失败
- 为了修文本问题反复打断主任务

## 核心结论

- 项目正式文本统一使用 `UTF-8`
- 中文文件读取必须显式带 `-Encoding utf8`
- 手工改文件优先用 `apply_patch`
- `apply_patch` 前先读，改完后再回读
- 一次补丁不要贪大，宁可拆小块
- 如果是乱码上下文，优先换“稳定锚点 + 小块替换”或“按行重建”，不要死磕原乱码上下文
- 如果 `apply_patch` 报 `windows sandbox: setup refresh failed`，优先怀疑目录权限或目录状态，不要先怪中文路径

## 终端基础设置

需要在读取或检查中文文件前先切到 UTF-8 输入输出：

```powershell
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
[Console]::InputEncoding = [System.Text.UTF8Encoding]::new($false)
```

读取中文文件时统一写法：

```powershell
Get-Content -Path '某文件' -Encoding utf8
```

读取整个文件做完整检查时优先：

```powershell
Get-Content -Path '某文件' -Raw -Encoding utf8
```

## 标准处理顺序

每次动中文文本都按这个顺序执行：

1. 先用 `Get-Content -Encoding utf8` 读取目标文件。
2. 确认文件是否已经有乱码、重复注释、异常空行、异常替换痕迹。
3. 再决定用 `apply_patch` 小块修改，还是按稳定锚点重写局部。
4. 改完立刻回读刚修改的区域。
5. 如果是代码文件，再做一次最小编译或最小验证。

## 正确编辑方法

### 1. 常规改动

适用情况：

- 注释正常
- 上下文文本正常
- 只是加减几行

做法：

- 直接用 `apply_patch`
- 补丁上下文尽量选稳定英文、稳定签名、稳定结构，不要依赖容易变的中文长段

### 2. 中文内容改动

适用情况：

- 中文注释
- 中文文档
- 中文字符串

做法：

- 先 `Get-Content -Encoding utf8`
- 再 `apply_patch`
- 改完再次 `Get-Content -Encoding utf8`

不要省掉回读验证。

### 3. 乱码块改动

适用情况：

- 原文件里已经有乱码
- `apply_patch` 总是匹配不到
- 同一段文本里有异常字符或被截断字符

做法：

- 不要继续拿乱码行本身当补丁上下文
- 改用方法签名、类名、固定结构块当锚点
- 必要时整段重写，而不是一行一行修
- 如果整段也不稳，改用“按行扫描重建指定注释块”的方式处理

结论：

- 乱码文本不适合做补丁上下文
- 稳定结构比原始乱码内容更可靠

### 4. 大块文件改动

适用情况：

- 一次要改很多处注释
- 同一文件中后段有连续脏内容

做法：

- 先分段读取
- 按块修改
- 每改一块就回读一块

不要上来就打一整个超大补丁，失败后会浪费更多时间。

## 已确认的坑

### 1. 终端乱码不等于文件已坏

表现：

- 编辑器里正常
- 终端里乱码

判断：

- 先看是不是读取时没带 `-Encoding utf8`
- 再看控制台是不是没切 UTF-8

处理：

- 先修终端显示链
- 不要因为终端乱码就立刻重写文件

### 2. `apply_patch` 不一定是编码问题

表现：

- `apply_patch` 失败
- 报上下文找不到
- 报 `windows sandbox: setup refresh failed`

判断：

- 如果是“上下文找不到”，通常是文本上下文不稳，常见于乱码、重复块、前面已改过
- 如果是 `setup refresh failed`，优先怀疑目录 ACL 或目录状态异常

处理：

- 上下文找不到：先读文件，再换小块补丁或换稳定锚点
- `setup refresh failed`：先查目录，不要继续在坏根目录硬堆修改

### 3. 中文路径不是默认元凶

已确认：

- 中文路径本身不是这次 `apply_patch` 失败的根因
- `bdp_ascii` 结点路径本身也不是这次 `apply_patch` 失败的根因

真正问题：

- 项目根目录 ACL 异常，导致 `apply_patch` 使用的沙箱刷新阶段进不去目录

处理：

- 同级新建干净目录
- 做最小 `apply_patch` 验证
- 验证通过后再迁移内容

结论：

- 遇到这种情况时，“重建干净根目录”通常比“死磕坏权限目录”更稳

### 4. 先改后读很容易把问题放大

表现：

- 补丁匹配错位
- 同一段注释重复出现
- 改完才发现原文件早就有脏内容

处理：

- 先读再改是硬规则
- 不读原文直接补丁，失败概率明显更高

### 5. 一次补丁过大很容易把自己卡住

表现：

- 补丁失败后难定位
- 不知道是哪一段出错
- 回滚思路混乱

处理：

- 一次只处理一个逻辑块
- 一个方法组一个方法组地改
- 大文件优先按区段推进

## 推荐命令模板

读取单文件：

```powershell
Get-Content -Path '文件路径' -Encoding utf8
```

读取局部区域：

```powershell
Get-Content -Path '文件路径' -Encoding utf8 | Select-Object -Skip 200 -First 80
```

读取完整原文：

```powershell
Get-Content -Path '文件路径' -Raw -Encoding utf8
```

搜索乱码特征：

```powershell
Select-String -Path '文件路径' -Pattern '闁|閻|缁|鍨|妤' -Encoding utf8
```

## 禁止事项

- 不要在中文文件上省略 `-Encoding utf8`
- 不要直接拿乱码文本当补丁上下文
- 不要一上来就打超大补丁
- 不要把“终端乱码”直接等同于“文件损坏”
- 不要在 `apply_patch` 已明显受目录状态影响时继续硬改
- 不要为了修编码问题顺手扩大到无关架构改动

## 遇到卡顿时的分流规则

如果 5 到 10 分钟还卡在文本工具问题上，按下面分流：

1. 先判断是显示问题、上下文问题，还是目录问题。
2. 显示问题就修读取方式，不动文件。
3. 上下文问题就缩小补丁，换锚点，必要时改按行重建。
4. 目录问题就停下，不再往坏目录里堆修改，优先迁移到干净根目录验证。

## 本项目长期执行要求

- 每次新会话只要涉及中文文件，默认先按本规则执行
- 每次遇到新的文本编辑坑，都要补记到本文件
- 文本工具问题不能长期阻塞主任务，超过阈值必须切换到更稳的方法

## 暂不做的事

- 暂不批量转码旧版历史文档
- 暂不引入复杂脚本链
- 暂不为了编码问题改动旧项目结构
