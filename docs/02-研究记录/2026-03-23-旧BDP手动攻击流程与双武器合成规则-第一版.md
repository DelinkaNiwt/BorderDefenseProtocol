# 旧 BDP 手动攻击流程与双武器合成规则（第一版）

## 目的

这份记录专门梳理两件事：

- 玩家点下自定义攻击按钮后，旧 BDP 实际上是怎样进入持续攻击流程的
- 双武器 / 混合武器的“主攻击模式”到底按什么规则形成

## 一、手动攻击按钮不是终点，只是入口

### 1. `Command_BDPChipAttack` 的职责只是入口控制

代码事实：

- 它继承 `Command_VerbTarget`
- 通过 `attackId` 控制 Gizmo 是否合并
- 左键走主攻击 `verb`
- 右键如果有 `secondaryVerb`，则走副攻击
- 如果是支持引导的远程 Verb，则直接启动多步锚点瞄准
- 普通副攻击则回到原版 `Targeter.BeginTargeting(secondaryVerb)`

结论：

- 按钮本身不是完整攻击系统
- 它只负责把玩家送进正确的瞄准 / 发射入口
- 这符合“手动入口可自定义，但点击后的攻击体验应接近原版”的方向

### 2. 手动远程攻击后续靠专用 `JobDriver_BDPChipRangedAttack`

代码事实：

- 这个 JobDriver 明确是为了替代原版 `AttackStatic` 里的不适配行为
- 原版 `AttackStatic` 会重新 `TryGetAttackVerb()`，这样会把芯片远程攻击找丢
- 所以旧版这里直接使用 `job.verbToUse`
- Job 结束时会清理射击会话，避免引导锚点残留污染后续自动攻击
- `tickIntervalAction` 中会反复检查：
  - 目标是否还有效
  - 是否达到最大攻击次数
  - 当前是否仍在 stance 忙碌
  - 最终目标是否超出真实射程
- 真正发射靠 `verb.TryStartCastOn(castTarget)`

结论：

- 旧版手动远程攻击并不是点一下就完，而是进入一个“原版感的持续攻击 Job”
- 这说明旧版确实在努力贴原版战斗节奏，而不是只做一次性脚本效果

### 3. 手动近战攻击后续靠专用 `JobDriver_BDPChipMeleeAttack`

代码事实：

- 这个 JobDriver 负责跟随目标、进入近战范围、持续攻击
- `tickAction` 每 tick 手动推进 `verb.VerbTick()` 和 `ApplyPendingInterval()`
- `tickIntervalAction` 负责：
  - burst 中不重新开新攻击
  - 跟随目标重新寻路
  - 到近战范围后调用 `pawn.meleeVerbs.TryMeleeAttack(thing, job.verbToUse)`
- 这里也是直接使用 `job.verbToUse`，而不是让原版自己重新找一把武器

结论：

- 旧版手动近战同样是“自定义入口 + 原版感持续攻击流程”
- 不是表面做个挥刀效果就算结束

## 二、旧版为什么需要专门的 JobDriver

### 1. 原版会重新查攻击 Verb，导致芯片 Verb 被找丢

这在远程 JobDriver 注释里说得很明确：

- 原版 `AttackStatic` 会重新查 verb
- 重新查时可能回到触发体本身的“柄”近战，而不是芯片远程攻击

### 2. 芯片 Verb 不在 `VerbTracker.AllVerbs` 里，原版不会自动 tick 它们

这会带来两个实际问题：

- burst 连射卡在第一发后面
- 自定义发射间隔推进不了

旧版的解决方式是两层：

- 自动攻击链由 `Patch_VerbTracker_VerbsTick -> TickChipVerbs()` 统一补 tick
- 手动近战 Job 里还额外自己推进 `VerbTick()`，并套专门的防错处理

### 结论

- 这些 JobDriver 不是附加花活，而是为了让“脱离 VerbTracker 的真实芯片 Verb”还能像原版攻击一样持续运作
- 这再次说明旧版很多绕法，根源都在适配 RimWorld 引擎，而不是作者单纯乱写

## 三、双武器 / 混合武器的主攻击合成规则已经很明确

### 1. `VerbChipConfig` 已经把每个芯片的攻击定义抽成配置

代码事实：

- 每个芯片至少有 `primaryVerbProps`
- 可选 `secondaryVerbProps`
- 主副攻击各自可以设置 `FiringPattern`
- 还可附带：
  - melee 配置
  - ranged 配置
  - aimModules
  - fireModules

结论：

- 旧版已经在往“以配置声明攻击表达”这个方向走了
- 只是最后没有形成贯穿的统一规则层

### 2. `DualVerbCompositor` 不是表面工具，而是主攻击形成规则机

它会根据左右两侧当前激活芯片的 Verb 配置，合成最终结果。

当前确认的规则：

- 单侧有攻击：生成该侧独立 Verb，并标记为主攻击
- 近战 + 近战：生成左独立、右独立、双近战主攻击 Verb
- 远程 + 远程：生成左独立、右独立、双远程主攻击 Verb
- 近战 + 远程：生成两个独立 Verb，远程那侧设为主攻击

结论：

- 旧版的“主攻击模式”不是 later 投影，而是在这里就已经被计算出来了

### 3. 双侧齐射 / 逐发不是表面特效，而是直接影响 burst 规则

代码事实：

- `FiringPattern.Simultaneous` 会强制把某些 `burstShotCount` 修正为 1
- 因为齐射是在一次 `TryCastShot()` 内部完成全部发射
- 如果还保留引擎层 burst 次数，会被重复发射
- 双武器合成时，`ticksBetweenBurstShots` 也会根据两侧的 firing pattern 重新计算

结论：

- 旧版这里已经不是“把两把武器拼一起”那么简单
- 而是在合成一个真正新的攻击表达规则

## 四、现在能更清楚地看出旧版里哪些东西是本质

### 1. 手动入口和持续攻击执行是分层的

- 按钮只负责入口
- JobDriver 负责攻击过程
- Verb 负责具体暖机、射击、burst、特殊投递逻辑

这是一条应该保留的结构事实。

### 2. “主攻击模式”是规则层结果，不是 UI 标签

它会决定：

- 自动攻击桥接给谁
- 外部主要攻击投影读谁
- 双武器时哪个表达算默认主表达

这也是应该保留的本质。

### 3. 双武器 / 组合不是“多一个按钮”而已

它本质上是：

- 从两个输入表达合成一个更高层表达
- 这个高层表达有自己的 burst、间隔、投射物、主从关系

这对二次重构很重要，因为它说明以后不能把“组合技”和“攻击合成”继续当作 UI 层拼接。

## 五、旧版这里暴露出的主要问题

### 1. 规则虽然存在，但散在太多层里

相关规则分散在：

- `Command_BDPChipAttack`
- `JobDriver_BDPChipRangedAttack`
- `JobDriver_BDPChipMeleeAttack`
- `CompTriggerBody`
- `DualVerbCompositor`
- 各种 Verb 子类
- patch

### 2. `CompTriggerBody` 仍是承压中心

即使现在读到 `DualVerbCompositor` 和 `JobDriver`，也还是会回到：

- verb 缓存放在触发体
- 主攻击查询放在触发体
- 按钮生成放在触发体
- ProxyVerb 同步放在触发体

### 3. “规则配置”与“规则执行”之间还没有清楚总协议

`VerbChipConfig` 已经有了一些很好的方向：

- 主攻击配置
- 副攻击配置
- 发射模式
- aimModules / fireModules

但它仍然主要服务于 Verb 系统这一段，尚未成为一条贯穿整个攻击表达链的总规则声明。

## 六、对二次重构的直接启发

### 1. 手动入口应继续自定义，但不要把完整业务塞进按钮类

按钮只负责入口控制，这是对的。

### 2. 攻击过程需要一个清楚的“执行层”概念

从旧版看，这一层真实存在，只是现在由 JobDriver、Verb、patch 共同拼起来。

### 3. 主攻击模式应从 `CompTriggerBody` 的隐式缓存规则，升级成明确可查询的规则结果

以后它至少应服务：

- 自动攻击默认入口
- 外部主要投影
- 双武器 / 组合表达默认主表达

### 4. `VerbChipConfig` 这一类“表达声明”很值得保留思路，但要纳入更高层统一协议

它已经很接近“表达定义”，只是现在还不够贯穿。
