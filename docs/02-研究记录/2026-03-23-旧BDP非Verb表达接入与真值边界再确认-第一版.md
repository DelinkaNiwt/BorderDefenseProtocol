# 旧 BDP 非 Verb 表达接入与真值边界再确认（第一版）

## 目的

这一轮只补两件事：

- 非 Verb 表达是怎么接入 RimWorld 宿主的
- `CompTrion`、`CombatBodyState`、`CompTriggerBody` 三者的真值边界，现在还能再确认到什么程度

这两件事补上后，
围绕二次重构起步所需的“需求骨架”就基本够了。

## 一、先下结论

### 1. 旧 BDP 的“表达”本来就不只 Verb

目前代码已经可以明确分出三类：

- 普通芯片 Verb 表达
- 普通芯片 Ability / Hediff 表达
- 组合匹配后额外生成的第三表达

其中后两类说明得很清楚：

- 旧 BDP 并不是把所有能力都硬塞进攻击 Verb
- 它确实已经在用 RimWorld 原生 Ability / Hediff 宿主

这和你前面强调的方向是一致的。

### 2. 普通芯片 Ability / Hediff 的接入方式，是“芯片激活时直接投影到原版宿主”

普通芯片 Ability：

- `AbilityChipEffect.Activate()` → `pawn.abilities.GainAbility(cfg.abilityDef)`
- `Deactivate()` → `RemoveAbility(cfg.abilityDef)`

普通芯片 Hediff：

- `HediffChipEffectBase.Activate()` → 直接对 `pawn.health.hediffSet` 操作
- `Deactivate()` → 更新或移除 Hediff

这说明普通非 Verb 表达不是再包一层大系统，
而是：

- 芯片激活
- 立即投影进 RimWorld 自己的 Ability / Hediff 宿主

### 3. 组合第三表达已经被统一到了 `ComboEffectDef`

这点非常关键。

当前统一层是：

- `ComboEffectDef`
  - `ComboVerbDef`
  - `ComboAbilityDef`
  - 设计上还预留了 `ComboHediffDef`

并且 `CompTriggerBody.UpdateComboEffects(...)` 会：

- 统一扫描所有 `ComboEffectDef`
- 判断当前左右手是否匹配
- 匹配则 `ActivateEffect(...)`
- 失配则 `DeactivateEffect(...)`

这已经非常接近你要的那句：

- 组合技本质不是攻击，而是左右芯片满足后，额外生成第三表达

因为在这里：

- 攻击型组合技只是 `ComboVerbDef`
- 能力型组合技是 `ComboAbilityDef`
- 将来被动型也可以接到同一抽象层

### 4. 三大真值边界现在可以再压实一层

当前更准确的说法是：

- `CompTrion`
  - 是资源真值 owner
  - 持有 `cur / max / allocated / reservedAllocation / drainRegistry / frozen`
- `CombatBodyState`
  - 是战斗体外层相位 owner
  - 持有 `Inactive / Active / Collapsing / Cooldown` 与相位时间数据
- `CompTriggerBody`
  - 是装载与激活表达的 owner
  - 但越界持有了战斗体镜像标志 `IsCombatBodyActive`
  - 并直接参与资源占用和释放

所以用户前面指出的“触发体职责过重”不是感觉问题，
而是代码事实。

## 二、普通非 Verb 表达是怎样接回 RimWorld 的

### 1. Ability 芯片：直接借用 RimWorld 的 Ability 宿主

`AbilityChipEffect` 非常直白：

- 激活时 `GainAbility`
- 关闭时 `RemoveAbility`

这说明对于“点击 -> 选目标 -> 执行”的能力，
旧 BDP 的真实路线不是自己再造一套技能系统，
而是：

- 芯片负责决定有没有这个能力
- Ability 本身仍交给 RimWorld 机制托管

### 2. Hediff 芯片：直接借用 RimWorld 的 Hediff 宿主

`HediffChipEffectBase` 及其子类也很直白：

- 直接读取/添加/更新/移除 `Hediff`

并且旧版已经出现了两种不同业务模型：

- `ModeBasedHediffChipEffect`
  - 同一个芯片按形态切换 Severity
- `StackableHediffChipEffect`
  - 多个相同效果芯片叠加 Severity

这说明 Hediff 表达也不是单一模板，
但它们仍然共享一个很清楚的宿主事实：

- 表达最终落在原版 Hediff

### 3. 这里再次证明“不要脱离 RimWorld 造新游戏”是硬约束

旧 BDP 自己其实已经在做这件事：

- 不是所有东西都做成 BDP 自己的运行时对象
- 合适的表达会直接投回 Ability / Hediff / Verb

所以二次重构时，
不能因为想统一架构，
就把原本已经很好接回 RimWorld 的东西重新抽离出去。

## 三、组合第三表达的真实落点

### 1. `ComboEffectDef` 是组合第三表达的统一抽象层

它负责：

- 芯片匹配规则
- 效果类型标识
- 激活 / 撤销统一接口

不负责具体表现内容。

这点很重要，
因为它说明旧版已经开始摆脱“组合技 = 攻击”的狭窄理解。

### 2. `CompTriggerBody.UpdateComboEffects()` 是统一匹配与开关入口

它做的事很明确：

- 左右任一缺失 → 撤销全部组合效果
- 否则遍历所有 `ComboEffectDef`
- 逐个做匹配和激活状态比对

这说明组合系统的真正触发条件是：

- 左右芯片当前组合事实

而不是：

- 某个按钮按没按
- 某个攻击入口有没有走到

### 3. `ComboVerbDef` 目前还是旧式独立结构，但已在统一抽象层外显出位置

当前 `ComboVerbDef` 仍是单独的 `Def`，
没有直接继承 `ComboEffectDef`。

这说明旧版这里还有过渡痕迹。

但从 `ComboSystem` 的注释和统一方向看，
它明显已经在朝：

- 组合 Verb / Ability / Hediff 统一管理

这个方向走。

这点对二次重构很有价值：

- 不是把旧版照搬
- 而是抓住它已经露出来的正确抽象方向

### 4. 组合 Ability 已经完全证明“第三表达可以不是攻击”

`ComboAbilityDef.ActivateEffect()` 做的只是：

- `pawn.abilities.GainAbility(abilityDef)`

这已经把用户前面说的那句话直接坐实了：

- 组合第三表达可以是 Ability，而不是攻击 Verb

## 四、Ability 表达和组合 Ability 的一个重要细节：消耗来源不一定一样

`CompAbilityEffect_TrionCost` 很值得注意。

它说明 Ability 的资源消耗有两条路：

- 普通 Ability 芯片：
  - 通过 `AbilityChipConfig.abilityDef` 找到当前激活芯片，再读统一层 `usageCost`
- 组合 Ability：
  - 可以直接用 `costSourceChipDef` 指定消耗来源芯片

这说明旧版对 Ability 的理解不是：

- Ability 自己持有消耗真值

而是：

- Ability 只是表现入口
- 消耗真值仍应回到芯片 / Trion 统一层

这点对二次重构非常重要。

## 五、三大真值边界的再确认

### 1. `CompTrion` 的资源 owner 地位更明确了

现在可以更精确地说：

- `cur`
- `max`
- `allocated`
- `reservedAllocation`
- `drainRegistry`
- `frozen`

都在 `CompTrion` 内部。

而且它区分了两种很重要的资源行为：

- `TryConsume()`：全额或不扣
- `Consume()`：尽力消耗，允许压到 `Available = 0`

这说明资源语义在旧版里其实已经很细。

### 2. `CombatBodyState` 只管战斗体外层相位，不直接管芯片和表达

它负责的是：

- 当前是 `Inactive / Active / Collapsing / Cooldown`
- 以及这些相位的时间数据、原因数据

它不直接负责：

- 槽位
- 芯片
- Ability
- Hediff
- Verb

这说明它的 owner 边界相对是干净的。

### 3. `CompTriggerBody` 仍然是最容易越界的那层

它现在同时承担：

- 装载 owner
- 激活表达 owner
- 特殊槽激活关闭
- 组合效果更新入口
- 战斗体支援接口实现
- `IsCombatBodyActive` 镜像状态

并且它还直接：

- `TryAllocateTrionForCombatBody()`
- `DismissCombatBody()`

去写资源状态。

所以用户最初指出的：

- 触发体承担过多职责

现在已经被代码反复证实了。

## 六、`IsCombatBodyActive` 的地位现在可以更准确地描述

它不是战斗体正式相位 owner。

更像是：

- 触发体这一侧的“战斗体可用镜像标志”

因为它影响的主要是：

- 芯片能不能激活
- 自动攻击入口要不要对外开放
- UI 状态怎么显示

但真正的战斗体外层相位仍在：

- `CombatBodyState`

所以二次重构时，
这类状态最好降成：

- 明确派生镜像
- 或局部宿主只读镜像

不能再让它和正式相位并列当双真值。

## 七、`CompTriggerBody.CombatBodySupport` 说明触发体为什么会显得“像第二核心”

`TryAllocateTrionForCombatBody()` 和 `DismissCombatBody()` 这两段很说明问题：

- 激活战斗体时它先算所有芯片占用，再逐个 `Allocate`
- 解除时它又 `DeactivateAll()`，再 `Release(trion.Allocated)`

这说明旧版触发体不仅是装载 owner，
还被拉进了战斗体事务执行。

也就是说：

- 触发体现在并不只是“装备上的芯片盒子”
- 它实际上已经在担当战斗体支援核心的一部分

这正是后面二次重构必须拆边界的重点。

## 八、这一轮对二次重构最重要的启发

### 1. “表达系统”必须明确分成至少两层

更合适的理解是：

- 表达来源层
  - 芯片提供 Verb / Ability / Hediff / 组合候选
- 宿主投影层
  - 最终分别投到 RimWorld 的 Verb / Ability / Hediff 宿主

而不是用一个统一大对象把所有表现都自己托管。

### 2. 组合第三表达应以统一抽象层管理，而不是默认归入攻击系统

旧版已经用 `ComboEffectDef` 证明了这个方向是对的。

所以二次重构时，
“组合表达系统”应比“攻击系统”更上位。

### 3. 资源消耗真值必须继续留在 `CompTrion`

不管表达是：

- Verb
- Ability
- Hediff
- 组合第三表达

它们都不该自己拥有另一套资源真值。

### 4. `CombatBodyState` 应继续只做外层相位 owner

不要再往它里面塞：

- 芯片表达
- 攻击实现
- UI 投影

它的职责应继续很薄、很清楚。

### 5. `CompTriggerBody` 必须从“超级对象”往“装载 owner + 局部协调”收缩

旧版最需要拆的不是把它彻底打碎，
而是把那些不该由它持有的真值和流程从它身上拿掉。

## 九、接下来是否还要继续深读

我认为这一轮之后，
已经不需要再继续细读具体 Ability 技能或具体 Hediff 业务。

因为对二次重构来说，
最关键的需求事实已经够了：

- 非 Verb 表达如何接回 RimWorld
- 组合第三表达为何比攻击更上位
- 三大真值边界分别落在哪里

下一步就该把这些已读事实收束成：

- 二次重构前置需求骨架
- 设计禁区清单
- 可接受的实现方向

而不是继续做代码考古。
