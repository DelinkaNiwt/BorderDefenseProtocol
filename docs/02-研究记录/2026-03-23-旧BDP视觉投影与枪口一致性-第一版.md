# 旧 BDP 视觉投影与枪口一致性（第一版）

## 目的

这一轮不是研究 GUI 长什么样。

这一轮只回答：

- 旧 BDP 怎样把内部激活状态继续投影成 RimWorld 里的“持武显示”
- 旧 BDP 怎样保证“看见的枪”和“子弹发出的点”尽量来自同一套基准

这对二次重构非常关键，因为用户已经明确要求：

- 不要做一个脱离 RimWorld 的“新游戏”
- 必须从 RimWorld 原版宿主出发，最后也回到 RimWorld

## 一、先下结论

### 1. 旧 BDP 的视觉层，本质上也是“宿主投影层”

它不是单独做一套自定义渲染世界。

它做的是：

- 借用 RimWorld 原版 `PawnRenderUtility.DrawEquipmentAiming`
- 截获原版装备绘制时机
- 把触发体内部激活芯片，投影成“此刻该绘什么武器、画在什么位置、朝什么角度、在前景还是背景”

也就是说：

- 内部还是芯片状态
- 对外仍然尽量表现成 RimWorld 的持武与开火

### 2. 旧 BDP 很在意“绘制位置”和“发射原点”一致

这不是只把贴图画对就完了。

旧版还专门做了：

- `Patch_DrawEquipmentAiming_Weapon` 每帧缓存 `lastDrawLoc`
- `Verb_BDPRangedBase.GetMuzzlePosition()` 使用 `lastDrawLoc + WeaponDrawEntry.drawOffset`

这说明旧版已经明确意识到：

- `Pawn.DrawPos`
- 和原版武器真实绘制使用的 `drawLoc`

不是同一个点。

如果子弹还从 `DrawPos` 算，会出现：

- 枪画在一处
- 子弹从另一处飞出

所以旧 BDP 的真实要求是：

- 视觉投影
- 和发射投影

必须共用同一绘制基准。

### 3. 武器绘制配置不是“美术参数”，而是领域投影协议的一部分

`WeaponDrawChipConfig` 看起来像贴图参数表，
但它实际承担的是：

- 定义该芯片投影成手持武器时的图形
- 定义不同朝向、左右手、前景背景的偏移规则
- 定义枪口局部坐标
- 定义这是不是远程武器

因此它不是纯表现层装饰。
它是“表达如何投影到 RimWorld 持武宿主”的协议一部分。

## 二、视觉层的数据流

当前代码能看出的主链是：

- 芯片 `ThingDef`
- `WeaponDrawChipConfig`
- `CompTriggerBody.GetActiveWeaponDrawEntries(facing)`
- `WeaponDrawEntry`
- `Patch_DrawEquipmentAiming_Weapon.DrawEntry(...)`

其中分工很清楚：

- `WeaponDrawChipConfig`
  - 提供静态配置
- `CompTriggerBody`
  - 读取当前激活槽位
  - 决定这一帧有哪些武器该显示
  - 生成统一的绘制描述符
- `Patch_DrawEquipmentAiming_Weapon`
  - 借原版绘制时机消费描述符
  - 真正把武器贴图画出来

这套关系很像前面已经确认过的其它地方：

- 模块给配置或意图
- 宿主统一聚合
- 最后投影到 RimWorld 原版入口

## 三、旧 BDP 不是自己造渲染系统，而是精准挂接原版绘制入口

Patch 挂在：

- `PawnRenderUtility.DrawEquipmentAiming`

这很关键。

因为这个原版入口天然带着：

- `aimAngle`
- `drawLoc`
- 原版持武姿态与动画偏移
- “只有当前真的在持武时才会走到这里”的宿主时机

所以旧 BDP 选择的不是：

- 自己每 tick 找 pawn 画贴图

而是：

- 等 RimWorld 自己进入“画装备”这一刻
- 再决定是否替换原来的触发体贴图

这完全符合“从游戏出发，最终回归游戏”的方向。

## 四、`WeaponDrawEntry` 说明视觉层也在走“统一描述符”路线

`WeaponDrawEntry` 把单帧绘制所需的关键信息统一装进一个结构里：

- `graphic`
- `glowGraphic`
- `drawOffset`
- `altitudeOffset`
- `angle`
- `flipHorizontal`

这说明旧版不是在 Patch 里散着直接算所有东西。

它先把“要怎么画”收敛成统一描述符，
再交给绘制入口消费。

这一点很有价值：

- 它比“每个芯片自己改原版绘制”更清楚
- 也比“所有细节直接堆在 Patch 里”更容易维持一致

## 五、左右手和四朝向，并不是两三条 if，而是一套明确投影规则

`CompTriggerBody.BuildEntry(...)` 已经把规则写得很清楚：

- South / North 一套
- East / West 一套
- 左右手前后景关系会变
- 图形镜像和高度层级会变

这说明旧 BDP 真正在意的不是“画两把武器”这么简单，
而是：

- 左右手在不同朝向下的相对关系
- 谁在前景、谁在背景
- 哪一只手该翻转贴图

所以二次重构如果以后重做视觉层，
不能只保留“能显示两个武器”这种表面效果。
必须保留这些更底层的投影规则。

## 六、`ShouldSuppressWeaponDraw()` 暴露了一个很重要的宿主决定

只要存在激活的非 `Special` 芯片，
就可能抑制触发体本体绘制。

这说明旧版视觉上的核心动作不是“叠加一个额外武器”，
而是：

- 原触发体贴图让位
- 激活芯片成为当前真正对外可见的武器表面

也就是说，触发体在视觉上更像一个承载器，
激活芯片才是被投影成武器身份的东西。

这和前面已经确认过的：

- 标签投影
- 检视投影
- 主攻击投影

其实是同一方向。

## 七、枪口系统进一步证明“视觉投影”和“攻击投影”必须共基准

`Verb_BDPRangedBase.GetMuzzlePosition()` 的关键做法有三步：

### 1. 先复用视觉层同一套 `BuildEntry(...)`

它不会自己重写一套“武器在哪”的算法。

而是：

- 同样调用 `CompTriggerBody.BuildEntry(config, chipThing, CasterPawn.Rotation, isLeft)`

这说明枪口系统已经在主动依赖视觉层规则。

### 2. 再用 `lastDrawLoc + entry.drawOffset` 还原武器世界位置

这一步极关键。

因为武器真正画在哪里，
不是简单等于 pawn 中心点。

旧版明确用：

- 原版绘制时传入的 `drawLoc`
- 加上武器描述符里的 `drawOffset`

来得到武器世界位置。

### 3. 最后才把 `muzzleOffset` 按 `aimAngle` 旋到世界空间

枪口偏移是局部坐标。

旧版没有拿图形旋转角 `drawAngle` 来算枪口，
而是拿：

- `aimAngle`

因为它想保证的是：

- 枪口沿真实瞄准方向出射

而不是沿贴图装饰角度出射。

这说明旧版在“视觉正确”和“射击正确”冲突时，
明显更优先射击逻辑一致性。

## 八、这里已经能看到一个重要边界

### 1. 视觉层可以有表现偏移

例如：

- `defaultAngle`
- `leftHandAngleOffset`
- 发光层
- 前景背景高度差

这些主要服务于看起来合理。

### 2. 但发射层不能脱离宿主投影基准

旧版允许图形有姿态表现，
但不允许发射原点完全跟图形脱钩。

因此更准确的说法是：

- 发射层不直接等于贴图角度
- 但必须和武器世界位置共用同一宿主基准

这是二次重构时必须守住的线。

## 九、这轮对二次重构最重要的启发

### 1. 视觉层仍应被视为“表达投影到宿主”的一环

不要把视觉系统理解成附属皮肤。

在 BDP 里，它承担的是：

- 让内部芯片表达重新取得 RimWorld 中“装备外观”的位置

### 2. 应继续保留“统一描述符 -> 宿主消费”的做法

至少从旧版经验看，
下面这种结构是有价值的：

- 表达来源提供配置
- 触发体或其它宿主做统一聚合
- 最后交给原版入口消费

### 3. 必须保证绘制基准与发射基准一致

如果以后新架构把：

- 武器显示
- 枪口发射

拆到不同地方做，
那也必须共享同一个“宿主实际绘制基准”。

否则视觉和战斗表现会飘。

### 4. GUI 样式可以丢，但显示投影口不能忘

用户已经明确：

- 旧 GUI 只是临时设计，不是目标

但这轮再次证明：

- 旧 BDP 一直在把内部状态投影回原版宿主口

不只是 UI 文本口，
也包括持武绘制口。

## 十、目前还不能下死结论的地方

### 1. `WeaponDrawChipConfig` 是否应在二次重构里继续保留为独立 Def 扩展形态

当前只能确定：

- 它承载的“投影信息”必须保留

但它未来是：

- 继续单独扩展
- 还是并入更统一的表达投影配置

现在还不该拍板。

### 2. 枪口计算目前仍和远程 Verb 实现绑得比较近

这可能意味着：

- 旧版已经有“共基准”的正确意识
- 但组织位置还不够理想

这一点要等后面更系统地读完表达来源和投影层，再决定怎么抽。
