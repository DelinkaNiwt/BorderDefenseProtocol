# 小行星反击旧会话与修复风险分析

日期：2026-10-17。用户确认调查目标为 RimWorld 1.7（边缘世界1.7）。本轮只分析与离线验证，没有修改业务代码、构建或部署。

## 结论与确定程度

1. **已确认实现错误**：正式远程宿主把“仍有待发计划”误用为“当前攻击不可被换目标”，即使原版已经取消瞄准、人物没有实际动作占用，也会永久拒绝新目标。对应代码在 `BdpVerb_FormalHostShoot.TryPrepareCastSession`。
2. **已确认形成路径**：原版取消瞄准只移除姿态，不清理 BDP 自有计划；空闲的原版 `VerbTick`（攻击对象逐刻更新）不会消费计划。已用当前项目1.7真实程序集独立验证这个组合。
3. **已确认历史关联，但不能简单认定最近一次改动从无到有制造全部问题**：10月13日提交 `4f51a0032` 加入当前阻断分支；此前已有“旧会话目标不同时清空武器候选”的做法，同样没有正确结束失去动作承接的会话。最近的 Trion 兵（能量兵）新增不是该分支来源。
4. **待确认现场最初触发**：所贴日志从旧 Per 会话已经存在时开始，无法证明它是取消瞄准、失去射线、任务中断还是其他途径留下。代码可证明形成机制，不等于证明本次现场的第一事件。
5. 本问题没有证据属于1.7独有差异。有关代码是共享源码；本轮真实程序集行为验证仅针对1.7，未运行1.6验证。

## 从日志到代码的完整链路

所贴日志中，Lorenzo（角色名，Human344）使用小行星，对轻型试作兵01发出137次自动起手请求；其内部会话、当前目标及待发计划仍指向 Per（另一角色，Human350），计划保持发射0/4。

`canHitTarget=True`（目标可命中）、`canHitFromCurrentPos=True`（当前位置可命中）、`hasShootLineToRequested=True`（请求目标射线存在）均通过。调用栈来自原版 `JobDriver_AttackStatic`（定点攻击任务驱动）与 `Pawn.TryStartAttack`（人物尝试起手）。原版进入攻击对象前已经检查全身忙碌，因此不能把这137次解释为普通冷却等待。

```text
原版任务选择新敌人
  → Pawn.TryStartAttack 已通过忙碌门槛
  → BDP 可命中检查通过
  → 正式宿主检查“需要继续逐刻更新”
       = 正在瞄准 或 正在连发 或 尚有待发计划
  → 旧计划仍在，因此必须匹配旧目标
  → 新敌人不匹配，立即返回失败
  → 后面的 Reset（重置）与计划重建永远走不到
```

其中“需要逐刻更新”原本是宿主管理器的调度依据，并不证明攻击仍有动作承接者。把这两个含义混用，才是当前阻断的核心。

手动强制入口先绑定新目标及正式攻击任务，而 `TryPrepareCastSession` 对该任务走既有专用入口，所以能越过上述自动换目标判断。现场随后出现起手成功、瞄准以及 tick=27801、27810（游戏刻）的发射窗口记录，与用户观察一致。不是手动点击修复了芯片，而是走了另一条合法的会话绑定路径。

## 旧计划为什么能够留下，又为什么不会自己恢复

核对1.7真实原版程序集：

- `Pawn_StanceTracker.CancelBusyStanceSoft`（软取消忙碌姿态）发现瞄准姿态后，只调用 `SetStance(new Stance_Mobile())`（切换可移动姿态），没有重置攻击对象。
- `CancelBusyStanceHard`（硬取消忙碌姿态）同样只切换姿态。不能据名称推断它会关闭 BDP 会话。
- `Stance_Warmup.StanceTick`（瞄准姿态更新）发现目标倒地、离图或当前不能命中时，也会直接换成可移动姿态。
- `Pawn_JobTracker.CleanupCurrentJob`（任务结束清理）默认调用上述软取消。原版任务没有 BDP 手动任务驱动的会话归属清理。
- `Verb.VerbTick` 仅在 `Bursting`（连发中）推进出手；空闲状态不会处理 BDP 自有待发计划。

因此，正常的任务中断或视线变化已经足以产生“没有瞄准／连发，但仍有待发计划”的合法中间状态。BDP 必须能够在下次真实自动起手时处理它，不能要求它先自行完成。

现有目标倒地／死亡通知也不能保证救回：`NotifyTargetLifecycleChanged`（目标生命周期通知）及 `ShouldResetAfterTargetLifecycleChange`（是否可以收尾）仍以“不需要逐刻更新”为清理条件。旧计划会继续使该条件不成立。这是同一判断混用造成的收尾缺口，不应再用更多目标事件补丁绕开它。

另一条代码可达路径是：BDP 已准备计划，后续原版起手返回失败；返回处没有统一撤销该计划。原版连发因可用性或出手失败结束时，也不保证所有 BDP 余下计划都已经消费。这些路径说明应按实际动作状态判断，不应只针对“小行星”或“反击策略”写特殊处理；但日志不足以认定本次由其中某条触发。

## 历史改动是否有关

`4f51a0032`（2026-10-13，自动远近战边界修复）做了正确的职责调整：武器查询只读、原版管理自动任务，BDP 只在真正起手时准备会话。其新增判断为：

```csharp
if (RequiresFormalHostRuntimeTick()) return MatchesAutomaticCastTarget(target);
```

该判断意图保留已经准备好但尚未瞄准的正式有限攻击及其确认输入；意图合理，保护范围却过大，把失去动作承接的旧计划也保住了。文件历史追踪确认该行来自此提交，并非近期试作兵业务改动。

但其父提交已有“不能暂存新自动会话且目标不同，就清空原版候选”的分支。旧版本可能表现成选不到远程攻击或退到其他行为，新版本则表现为已请求攻击却不能起手。因此准确归类是：**原有会话结束边界不完整，后续职责调整保留了这项缺口，并改变了外部表现。**仅回退10月13日改动，不能证明修复问题，反而会重新引入查询改状态及候选被清空的问题。

当时的真实程序集边界样本覆盖了查询不改令牌／上下文、实体及格子精确匹配、连发／忙碌保护。没有覆盖“原版瞄准取消 → 待发计划残留 → 自动换目标”。其他目标生命周期检查主要匹配源码中方法和分支是否存在，不能证明该状态真的能退出。这解释了为何先前检查通过仍遗漏此问题。

## 修复应当怎样收紧，哪些做法容易制造新问题

建议只在**正式远程宿主的真实起手边界**纠正判断：

1. 原版已经判定可命中后再处理会话；武器能力查询继续保持只读。
2. 正在瞄准、正在连发或全身忙碌时，继续拒绝覆盖。
3. 同一语义目标的已准备有限攻击，继续保留确认输入和既有通路。
4. 不同语义目标、且没有实际动作占用时，先验证当前绑定、结果和新模块会话可用，再经既有完整重置关闭旧会话，准备新目标。
5. 手动正式任务维持原专用路径；不改任务归属清理，不强制取消正常姿态。

这里的“语义目标”是实际想攻击的对象，不是路线中的第一个发射目标。应复用既有 `MatchesAutomaticCastTarget`（自动起手目标匹配），不能依据诊断日志里的首段目标差异直接重置。

| 必须保留的边界 | 粗暴清理可能出现的新问题 | 建议限制 |
|---|---|---|
| 正常瞄准与连发 | 每次自动检查都重启瞄准、打断连发，甚至重复扣费 | 保留真实动作及忙碌门槛 |
| 已确认的手动路径与有限攻击 | 毒蛇路径、双侧合成或其他输入丢失 | 手动入口不改；同语义目标继续保留 |
| 资源按轮结算 | 旧轮次已扣费状态泄漏到新目标，或重置活动连发导致重复扣费 | 使用完整旧会话重置；不修改资源结算实现，不补退费 |
| 新目标仍不合法 | 仅仅查询另一个敌人就丢掉原会话 | 仍在可命中检查之后处理，先确认新绑定／模块会话可用 |
| 任务清理归属 | 旧手动任务结束时误清掉后来的新会话 | 保留既有攻击令牌代际检查 |
| 读档与绑定换版 | 破坏连发游标、投影版本或已恢复瞄准 | 不改恢复、同步与调度判定的公共含义 |
| 非BDP攻击 | 无条件姿态／任务补丁干扰原版或其他模组 | 修改限于BDP正式远程宿主，不增加全局清理补丁 |

不建议删除全部保护、在武器查询中重置、每隔几刻强制刷新，或全局修改原版取消姿态方法。也不建议直接缩减 `RequiresFormalHostRuntimeTick` 的含义：它同时服务活跃队列、目标生命周期及读档后的调度，改动影响比本次起手边界更大。

上述方案能使原版选定的新目标正常取代失去动作承接的旧计划；不承诺顺带清理所有没有后续攻击请求的空闲残留。起手失败回滚、完全无人承接时立即收尾可作为额外生命周期改动评估，不能借本次修复无边界扩展。

## 本轮实际验证及后续验收

在独立 PowerShell（命令解释器）进程中，加载当前项目1.7的真实核心与对应原版程序集。核心程序集模块版本标识为 `5078c313-0736-4e45-b838-177b70ef8f74`；另通过反编译确认产物包含同一阻断判断。

临时样本使用真实游标绑定待发计划，构造旧目标、空任务跟踪器和瞄准姿态，实际调用原版软取消与 BDP 起手判断、原版空闲逐刻更新。只替代“未被眩晕”这一依赖，以避免离线进程启动完整模组配置；没有运行地图、投射物、伤害或资源系统，未声称复现完整战斗。

- 软取消之后，原版姿态不再忙碌，待发计划仍存在。
- 对新目标连续调用137次，全部被现有正式宿主判断拒绝，旧计划引用不变。
- 再调用1000次空闲更新，计划仍在，新目标仍被拒绝。
- 同目标待发计划能通过当前判断；连发状态以及预热姿态的忙碌保护均仍能拒绝覆盖。
- 临时样本在取证后删除；不把断言当前错误行为的调查样本长期当作正常回归测试。

正式修复时，可在无需玩家复现的独立验证中构造“取消瞄准后换目标、同目标重试、连发保护、忙碌保护、无效新绑定、手动已确认输入”等状态，并实际调用修改后的入口。资源扣费、双侧路径及读档恢复按涉及风险选择真实行为检查，不能只靠源码关键字匹配。

最终仍需标明游戏内未验证，但不应要求用户反复提供随机复现来证明已能由代码与真实程序集确认的门槛错误。1.6应按共享实现错误检查受影响范围、独立构建与验证，不能用1.7结果替代。
