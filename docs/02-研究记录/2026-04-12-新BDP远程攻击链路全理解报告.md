# 新 BDP 远程攻击链路全理解报告

## 一句话结论

- 新 BDP 把远程攻击拆成了 5 段：**声明**、**表达成立**、**攻击下单**、**远程发射**、**投射物后半段**。
- 芯片在新 BDP 里**不是运行时 owner（拥有者）**，它只负责上游声明“我想提供什么攻击”。
- 业务功能必须作为 `RangedModules`（远程模块）挂在**表达条目**上，而不是把业务逻辑塞进主模组或投射物定义里。
- 最终落地仍然回原版：`Verb`（武器动作）、`Projectile`（投射物）、`Damage`（伤害）、`Explosion`（爆炸）。

## 总图

```text
芯片 Def / XML（定义）
        |
        v
表达契约解释
`ChipExpressionEntryConfig` -> `ChipExpressionEntryContract`
        |
        v
表达来源收集 / 条件过滤 / 单侧结果 / 复合结果
        |
        v
`ExpressionSnapshot`（表达总表快照）
        |
        +--> 选出 `PrimaryRanged`（默认主远程）
        |
        v
`TriggerRuntimeCoordinator`（触发体运行时协调器）发布投影
        |
        +--> 自动攻击：`Pawn.TryGetAttackVerb` 补丁接管
        |
        +--> 手动攻击：按钮 -> `AttackExecutionTargetingSource`
        |
        v
`AttackExecution`（攻击执行）正式下单
        |
        v
`RangedAttackProtocolService`（远程协议）
Aim -> Prepare -> Fire -> ProjectileInit
        |
        v
`BdpVerb_Shoot`（远程宿主动作）只负责把计划发出去
        |
        v
`BdpProjectile`（统一投射物宿主）
Flight -> Arrival -> Hit -> Impact
        |
        v
原版伤害 / 原版爆炸 / 原版战斗日志
```

## 1. 芯片定义层到底负责什么

- 作者在 XML 里写的是 `ChipExpressionEntryConfig`（芯片表达条目配置）。这里面可以写：
  - 这是主攻击还是副攻击。
  - 近战还是远程。
  - `VerbProps`（原版动作参数）。
  - `Execution` / `ExecutionStyle`（攻击节奏）。
  - `RangedModules`（远程模块挂载列表）。
- `DefaultChipExpressionContractInterpreter`（默认芯片表达契约解释器）会把作者写法正规化成 `ChipExpressionEntryContract`（正式承认的条目）。
- 这一步的重点不是“直接发射”，而是把作者的写法整理成**后面所有系统都能稳定读取的正式真值**。
- 这里已经冻结了一个很关键的事实：**模块顺序就是 XML 书写顺序**。

## 2. 表达系统怎么把“定义”变成“这一刻成立的攻击”

- `ExpressionRuntimeRepository`（表达运行时仓库）串起整条表达链。
- `DefaultExpressionSourceDeclarationProvider`（表达来源声明提供器）把芯片定义翻成来源声明。
- `ExpressionSourceCollector`（来源收集器）读取 Pawn（角色）当前实际装了什么芯片、哪些条件成立。
- `SingleSideExpressionBuilder`（单侧表达构建器）分别生成 `Main`（主侧）、`Sub`（副侧）、`Special`（特殊侧）结果。
- `CompositeExpressionResolver`（复合表达解析器）再往上合成双持、组合技这类复合结果。
- 最后得到 `ExpressionSnapshot`（表达总表快照）。

这一层的真实产物，不是“我猜这个人能不能开枪”，而是：

- 这一刻正式承认了哪些结果。
- 每条结果的 `ResolvedVerbSpec`（正式动作规格）是什么。
- 这条结果有没有 `RangedModules`（远程模块）。
- 哪条是默认主远程 `PrimaryRanged`（默认主远程）。

## 3. 攻击系统怎么分发到“自动攻击”和“手动攻击”

### 自动攻击

- `Patch_Pawn_TryGetAttackVerb`（自动远程入口补丁）会优先看表达系统已经选出的 `PrimaryRanged`（默认主远程）。
- 只要这条正式结果合法，就把它对应的 `BdpVerb_Shoot`（远程宿主动作）交给原版持续攻击会话。
- 这意味着：**自动攻击入口已经不再靠原版自己猜哪把武器该用，而是先信表达系统。**

### 手动攻击

- `DefaultManualEntryGizmoResolver`（默认手动入口按钮解析器）给玩家造按钮。
- 点按钮时，不是直接发射，而是创建 `AttackExecutionTargetingSource`（攻击执行目标适配源）。
- 这个对象负责接入原版 `Targeter`（目标选择器），把玩家选目标的过程翻译成正式下单。

这里最关键的一点：

- **模块会话 `RangedAttackModuleSession`（远程模块会话）是在按钮点下去时先冻结一份。**
- 后面从选目标到确认，再到开火和投射物飞行，都会沿用这一份会话或它的冻结快照。
- 这能避免“玩家点按钮时是一套状态，子弹飞出去时又偷偷重新解释成另一套状态”。

## 4. 远程会话和编排是怎么串起来的

玩家手动攻击实际走的是这条链：

```text
点按钮
  -> ManualEntry（手动入口阶段）
  -> Targeting（目标选择阶段）
  -> Preview（预览阶段）
  -> Confirm（确认冻结阶段）
  -> AttackExecutionRequest（正式请求）
  -> BuildPlan / BuildSteps（建计划 / 建动作步）
  -> 远程协议
```

### 上游 4 个交互阶段各干什么

- `ManualEntry`（手动入口）只管按钮本身：名字、说明、图标、隐藏与否。
- `Targeting`（目标选择）只管目标选择表面：能不能选、是否多选、当前输入状态。
- `Preview`（预览）只管给玩家看什么：线、圈、格子群、鼠标附着图标等。
- `Confirm`（确认）是最后下单前的裁定点：允许还是拒绝、拒绝原因是什么、要冻结哪些中性输入事实。

### 为什么说它是“中性系统骨架”

因为主模组只提供中性事实，不理解业务名字：

- `TargetingInputState`（目标输入状态）只知道当前是否激活、在第几步、是否完成、有哪些标签。
- `ConfirmedInputSnapshot`（确认输入快照）只冻结步骤号、完成状态、标签。
- `TargetingInteractionSession`（目标交互会话）只知道当前交互是不是还活着。

主模组的态度非常明确：

- **我只负责让业务模块有地方挂事实。**
- **我不替“毒蛇”“战斧”这种业务名词做专用字段。**

## 5. 新 BDP 的模块化远程射击管线

`AttackExecutionService`（攻击执行服务）先把高层攻击拆成 `Cast`（施放）和 `Step`（动作步），然后远程部分交给：

- `RangedAttackProtocolService`（远程攻击协议服务）

它的前半段固定是 4 个正式阶段：

```text
Aim（瞄准）
 -> Prepare（准备）
 -> Fire（发射展开）
 -> ProjectileInit（投射物初始化）
```

每一段都遵守同一个原则：

- **基线先给出一个默认结果。**
- **模块只提交 contribution（贡献）去改这个默认结果。**
- **宿主最后只消费已经裁定好的正式计划。**

所以主模组没有让业务模块直接“接管整把枪”，而是只给它们改有限维度的机会。

## 6. 投射物后半段怎么落回原版

真正发射时，`BdpVerb_Shoot`（远程宿主动作）只消费 `ProjectileInitPlan`（投射物初始化计划）。

它会吃这些关键真值：

- `LaunchTarget`（真正发射朝向）
- `AimTarget`（瞄准目标）
- `CurrentTarget`（当前目标）
- `InitialSpeedFactor`（初始速度倍率）
- `InitialDamageFactor`（初始伤害倍率）
- `ForcedMissRadius`（强制失准半径）
- `ModuleContextSnapshot`（模块私有上下文冻结快照）

然后把计划交给 `BdpProjectile`（统一投射物宿主）。

`BdpProjectile` 的后半段固定走：

```text
Flight（飞行）
 -> Arrival（到达）
 -> Hit（命中解释）
 -> Impact（落地效果）
```

最后仍然回原版：

- 直接伤害 -> 原版 `DamageInfo`（伤害信息）
- 爆炸 -> 原版 `GenExplosion.DoExplosion`（原版爆炸）
- 战斗日志 -> 原版 `BattleLog`（战斗日志）

这就是新 BDP 的根：

- **中间可以很模块化。**
- **终点必须尽量回原版基线。**

## 7. 模块设计规则，哪些能做，哪些不能做

### 能做什么

- 挂在表达条目的 `RangedModules`（远程模块）里。
- 在 `ManualEntry / Targeting / Preview / Confirm` 里控制玩家操作表面。
- 在 `Aim / Prepare / Fire / ProjectileInit` 里控制开火前半段。
- 在 `Flight / Arrival / Hit / Impact` 里控制投射物后半段。
- 用私有上下文 `IRangedModulePrivateContext`（模块私有上下文）保存业务自己的状态。
- 用 `SharedState`（共享状态表）做跨阶段轻量共享。

### 明确不能做什么

- 不能让芯片自己变成运行时 owner（拥有者）。
- 不能在主模组里写“毒蛇专用 if / 战斧专用 if”。
- 不能绕开 `AttackExecution`（攻击执行）和 `BdpVerb_Shoot`（远程宿主动作）另起一套独立射击系统。
- 不能在模块里直接乱写投射物宿主私有字段，必须通过贡献对象或正式计划说话。
- 不能把模块挂到投射物 Def（定义）上来承担业务入口；模块入口应在表达条目上。

### 合并规则

- 普通覆盖：**后写模块优先**。
- 倍率：**连乘**。
- 标签 / 额外伤害：**追加**。
- `Flight`（飞行）阶段的独占维度：谁最后声明独占，谁赢。

## 8. 现在这套骨架已经到哪一步了

下半身已经很成熟：

- 5 发齐射能做。
- 第一段朝向和后续折线飞行能做。
- 中途续飞 / 中途终止 / 最终命中 / 最终爆炸都能做。
- 模块私有上下文也能被冻结进 `ProjectileInitPlan`（投射物初始化计划）继续往后传。

真正偏紧的是上半身输入层：

- `TargetingInputFrame`（目标输入帧）目前只有：悬停目标、选中目标、确认请求、取消请求。
- 它**没有**键盘修饰键（比如 `Shift`）、鼠标按钮种类、多次点击明细、锚点坐标列表。

所以现在主模组已经能很好承接“远程模块化飞行”，但还**没有完全中性地暴露复杂多步输入事实**。

这点会直接影响旧 BDP 那种“Shift + 左键 连续设锚点”的 1:1 复现。
