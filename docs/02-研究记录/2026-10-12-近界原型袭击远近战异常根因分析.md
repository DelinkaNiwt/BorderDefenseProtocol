# 近界原型袭击远近战异常根因分析

研究日期：2026-10-12。对象：近界原型触发体，小兵短剑＋小兵弹丸。任务范围：定位异常、划清原版与 BDP 管理边界；本轮不修改游戏逻辑。

## 结论与证据等级

**已确认两个 BDP 接入缺陷：自动远程查询被旧目标会话污染；自动近战起手被扩成持续追击任务。** 两者都超出了“只替换原版决定使用的攻击”的边界。

“贴脸不打，受反击才挥刀”不能直接判为“短剑攻击拒绝无威胁目标”。原版和 BDP 的实际近战执行代码均没有“目标必须反击”这一前提。更吻合代码的路径是：战斗决策被远程查询阻断，随后执行的是靠近目标任务；受攻击后，另一条原版反击分支才启动短剑。**这条现场路径尚缺当时的任务及查询结果记录，不能冒充已复现。**

“进入近战后绝不恢复射击”则已被现有日志中的反例排除；真正的问题是返回远程的时机被 BDP 的任务接管改变，且换目标又可能被旧远程会话阻断。

依据：本机 RimWorld（边缘世界）1.6.4871 rev591 真实程序集、当前主模组源码、当前安装版核心程序集和 Player.log（游戏日志）。核心程序集的工作区／安装目录 SHA256（文件校验值）一致。本轮没有操作游戏复测；磁盘文件一致也不单独证明运行中的进程已重载该文件。原版职责采用 RimSearcher（运行时定义查询工具）导出的 AssaultColony（进攻殖民地）；数据库缺少最新 BDP 定义，自研部分以工作区为准。

## 1. 原版究竟在管理什么

| 管理内容 | 原版承担的工作 | BDP 应提供的最小内容 |
|---|---|---|
| 索敌 | 选目标、判断敌对、视线、可达性及威胁状态 | 稳定、可查询的默认攻击能力 |
| 战斗方式及站位 | 根据攻击行为是远程还是近战，安排射击位置或近战任务 | 远程查询得到默认弹丸，近战出手使用默认短剑 |
| 远程攻击 | 战斗等待任务中反复选可射目标，等待暖机及冷却 | 执行当前这次弹丸攻击，正确结束自己的会话 |
| 邻格近战 | 战斗等待内遇到可攻击的邻格敌人，尝试一次近战 | 完成这次短剑攻击，保留原版等待任务 |
| 近身反击 | 高优先级反击任务，最多攻击一次、200 游戏刻期限 | 替换这一刀，保留攻击次数、任务期限及反击语义 |
| 破坏／点火／开路 | 正常作战不给任务时，按职责树继续尝试 | 仅在原版真正请求近战时提供短剑 |
| 重新决策 | 任务结束、到期复查、高优先级事件时重新选行为 | 不额外延长原版任务，不用执行残留改变可用能力 |

这里的“原版选择远程／近战”依赖它查询到的攻击行为。若 BDP 在查询环节返回错误结果，虽然最后任务仍由原版创建，决策输入已经被 BDP 改坏，不能把结果都归因于原版。

## 2. 缺陷一：旧射击会话阻止新目标进入原版战斗分支

调用链：

```text
原版 JobGiver_AIFightEnemy（敌人战斗决策）
  → Pawn.TryGetAttackVerb（查询攻击行为）
  → BDP 自动远程后置补丁
  → TryGetAutoRangedVerb（取得默认远程行为）
  → 旧宿主仍有正式会话／快照／攻击实例身份？
      ├─ 查询目标为空，或与旧目标相同：返回弹丸
      └─ 查询另一个实体目标：suppressOriginalResult=true（清空原版候选）
          → 原版收到 null（无攻击行为）
          → 正常战斗分支直接不给任务
```

主要位置：

- [自动远程入口判断](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/AttackExecution/AttackExecutionSurfaceAccess.cs:143)。冲突分支在第 191 行设置清空标志。
- [查询后置补丁](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Patches/Patch_Pawn_TryGetAttackVerb.cs:24)。该标志使查询结果变成空值，包括清掉原版已经取得的可用弹丸。
- [宿主能否接受自动起手](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/Verbs/BdpVerb_Shoot.cs:93)。会话、快照或带攻击实例的令牌任一存在，都视为不能接受新起手，**并非只在实际暖机／连射期间拒绝**。
- [同目标判断](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/Verbs/BdpVerb_Shoot.cs:115)。空目标被直接允许；另一个实体被拒绝。

### 为什么等冷却结束也不一定恢复

成功发射完成后，BDP 在 [发射计划收尾](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/Verbs/BdpVerb_Shoot.cs:939) 清掉待发计划。该清理函数仅清发射游标和当轮资源状态，不清正式会话、冻结快照、攻击实例令牌和会话目标。

原版 `Verb.TryCastNextBurstShot`（推进下一次连射）在最后一发后把状态置为空闲、安排冷却；**不会自动调用 BDP 的 Reset（重置）**。原版冷却到期也只是恢复移动姿态；任务清理的软取消同样不会重置这个远程宿主。BDP 的 [宿主刻更新](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/VerbHosting/TriggerBodyVerbHostManager.cs:115) 也没有“普通自动攻击任务结束／自动目标更换后释放旧会话”的对应收尾。

因此可以得到确定的代码结果：

| 已向 A 射击，发射与冷却已经结束，旧会话未重置 | 查询结果 |
|---|---|
| 查询总体攻击能力，目标为空 | 弹丸可用 |
| 再查询 A | 弹丸可用，可以续射 |
| 改查询 B，包括另一个殖民者或炮塔 | 无攻击行为，正常战斗分支失败 |

这是**能力查询与一次攻击会话的所有权混在一起**的问题。原版本来在问“可以用哪种攻击”，BDP 却按“是否与上一轮目标相同”回答。

旧会话并非永不清理：[重置入口](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/Verbs/BdpVerb_Shoot.cs:1772)、装备／投影变化、目标倒地／死亡等生命周期事件可以清掉它。但目标仍活着、只是失去视线或原版改选另一个目标，不属于可靠的普通收尾路径。原目标重新可射时，同目标分支也可能恢复射击。

本轮确认的是这项代码缺陷及其确定后果；现有日志没有直接记录“某次原版查询因冲突被清空”，所以还不能锁定用户现场中哪一次查询触发了它。

## 3. 为什么有炮塔时更容易出现异常链

```text
〔原版管理〕先前向殖民者 A 射击，随后失去视线／更换候选
  → 选择另一个殖民者或炮塔 B
〔BDP 管理，缺陷一〕弹丸仍绑定 A，针对 B 的攻击查询被清空
〔原版管理〕正常战斗分支没有任务，继续职责树
  ├─ 就近破坏建筑
  ├─ 破坏较远建筑
  │   ├─ 可能点火
  │   └─ 可能创建 AttackMelee（近战攻击）
  └─ 上述都无任务：Goto（走向）最近敌对目标
〔BDP 管理〕原版真正请求近战出手时，再进入短剑接入
```

炮塔并不是 BDP 写死的“切换近战开关”。它增加了新的攻击候选和原版破坏目标，容易暴露换目标与会话冲突。原版战斗索敌要求对人物有视线，当前进攻职责没有强制对所有非人物目标也采用同样的索敌视线门槛；可达炮塔可能在人物失去视线后仍成为候选。

必须保留另一个正常原因：**即使没有缺陷一，原版找不到有效射击位置，也可能转去破坏建筑。** 不能凭“冲炮塔”这一画面单独判断故障。实际进入哪一条，需要记录决策来源。

无炮塔时若主要一直围绕同一个殖民者，旧会话的同目标放行会使问题不明显。这解释的是“为什么两种场景可能表现不同”，不是断言没有炮塔就绝不会触发；其他换目标同样可以触发。

## 4. “贴着不打、受反击才出刀”应如何定位

原版 `JobGiver_AIGotoNearestHostile`（走向最近敌人）创建的是走路任务，**不会把到达目标身旁自动翻译成一次近战请求**。它发现已经可以接触目标时直接不给新走路任务。原版 `JobDriver_Goto`（走路任务执行器）也没有到达后挥刀的动作。

若缺陷一使正常战斗分支持续失败，后续走路／破坏／开路等分支就可能接管。受击后，原版 `JobGiver_ReactToCloseMeleeThreat`（应对近身近战威胁）可以越过普通进攻职责，直接安排反击近战；这条入口不依赖正常战斗分支针对新目标取得弹丸，因此仍可能正常启动短剑。

需要纠正“无威胁”的含义：

- 玩家说的“不反击／没拿武器”，不等于原版 `ThreatDisabled`（威胁已失效）。该函数主要检查离图、倒地、休眠、隐形、职责禁用等状态，没有“普通殖民者不反击即失效”的规则。
- 原版战斗等待内的邻格近战要求目标属于活跃敌方威胁，但普通清醒殖民者可以满足；它不要求目标先挥刀。
- 原版真正的近战跟随执行，以及 [BDP 短剑任务执行](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/AttackExecution/JobDriver_BdpMeleeAttackExecution.cs:77)，都没有“目标必须反击才允许出刀”的判断。
- [BDP 短剑实际出刀](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/Verbs/BdpVerb_MeleeAttackDamage.cs:244) 检查命中范围和攻击者状态，再交原版处理，不检查目标是否反击。

因此，**“已经进入近战任务，但因为目标无威胁而不出刀”目前没有代码证据**。若现场任务确实是 BDP 持续近战，则应改查会话有效性、身体忙碌、接触可达性和起手失败，不能继续沿“不反击禁止挥刀”这个不存在的条件查。

## 5. 缺陷二：一次自动近战变成持续追击

目前 BDP 在 [自动近战前置接入](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Patches/Patch_Pawn_MeleeVerbs_TryMeleeAttack.cs:26) 截住原版的一次近战请求，成功后跳过原版实现。

[近战执行上下文](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/AttackExecution/MeleeAttackExecutionContext.cs:352) 把自动攻击和玩家强制攻击都归为持续攻击：动作计划结束后回到步骤零，上限变成整型最大值。

[近战执行器](C:/NiwtDatas/Projects/RimworldModStudio/模组工程/BorderDefenseProtocol/Source/BDP/Core/AttackExecution/DefaultMeleeAttackExecutor.cs:81) 因此启动新 BDP 近战任务，替换原任务。它保留剩余期限、部分到期条件、来源节点和倒地处置，却没有保留原版攻击次数上限、反击标记等完整任务语义。

| 原版原本要做的事 | 当前 BDP 实际做的事 | 问题归属 |
|---|---|---|
| 战斗等待里顺手砍一次，仍由等待任务管理后续射击 | 替换为持续近战，目标离开后可继续追砍 | BDP 扩大了任务接管范围 |
| 近身反击最多一刀，200 游戏刻期限 | 继承期限但丢掉一刀上限及反击标记，持续计划可重复出刀 | BDP 丢失原版任务语义 |
| 真正的近战攻击任务负责追击和重新决策 | 改由 BDP 驱动追击和续刀，仅继承部分规则 | BDP 接管了原版本应保留的职责 |

新任务执行时只续接短剑计划，不主动重新比较弹丸；重新回到射击依赖上层复查／任务结束等条件。这会改变什么时候结束近战，但**并非存在一个永久把武器标记成近战的开关**。

## 7. 最小修正方向与现场验证

依照用户要求，应恢复以下边界，不增加 BDP 专属远近战策略：

```text
原版：索敌 → 判断攻击方式 → 安排站位／追击／破坏 → 决定再次攻击或结束
                      ↓ 只在攻击能力及实际出手处接入
BDP：提供默认弹丸／默认短剑 → 完成本次攻击及必要内部步骤 → 收好本次状态
                      ↓
原版：继续管理原来的任务、次数、期限和下一轮决策
```

修正主线：

1. 让攻击能力查询稳定地回答能力，不因旧会话绑定另一个目标而清空原版决策候选；实际执行期间的并发／所有权保护应留在出手入口。
2. 补齐自动远程在正常结束、取消、改目标时的会话收尾，区分正在暖机／连射和仅残留旧上下文；不能只删保护判断后继续误用旧目标模块状态。
3. 自动近战只替换该次出手，不将战斗等待和一刀反击自动升级成持续追击；原版真正的近战任务继续由原版控制追击、次数及终止。BDP 若需完成一轮内部动作，也不应因此改变外层任务语义。
4. 保留玩家主动下达的 BDP 持续攻击命令和需要内部推进的正式攻击计划；不能把自动入口与手动入口一并粗暴删除。

本轮只形成修正边界，没有实现修复。要闭合用户现场，应先通过 Development.dll（开发诊断程序集）或原版任务调试记录，获取一名异常人物的：当前任务及来源节点、目标、身体姿态、远程旧目标及会话状态、查询原始／最终结果、近战入口是否被调用。不在业务层新增“贴脸强制挥刀”或“每几秒强制切回远程”的补丁。

最小对照场景：同一近界人物先打 A，再让原版改选 B；分别放置／移除炮塔；让 B 被动站立／近身反击。随后验证普通近战一次、反击一次、持续射击换目标、正常破坏建筑，以及玩家手动持续攻击。这里首先需要验证任务与状态转移，不适合用只匹配源码字符串的脚本宣布游戏行为正确。
