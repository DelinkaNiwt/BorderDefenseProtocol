# 旧 BDP 领域地图（第一版）

## 目的

这份记录不按旧项目文件夹名理解系统，而是按“它本质上在做什么”重新归类。

目标不是马上设计新架构，而是先搞清楚旧 BDP 的真实领域边界、真正 owner、以及主要耦合点。

## 总体判断

旧 BDP 可以重排成 6 个主要领域：

1. `资源域`
2. `战斗体域`
3. `装载与触发域`
4. `行动域`
5. `投递与命中域`
6. `显示与桥接域`

旧项目目录里的 `Core / Combat / Trigger / Projectiles` 只是历史分工，不等于真实领域边界。

## 1. 资源域

### 主要职责

- Trion 容量、当前值、占用、预占用
- 持续消耗登记
- 自动恢复
- 可用量耗尽、总量耗尽事件

### 主要文件

- `Source/BDP/Core/Comps/CompTrion.cs`
- `Source/BDP/Core/Comps/CompProperties_Trion.cs`
- `Source/BDP/Core/DrainKeys.cs`

### 当前 owner 判断

`CompTrion` 是旧 BDP 最接近单一真值源的对象。

它明确负责：

- 当前量 `cur`
- 容量 `max`
- 正式占用 `allocated`
- 预占用 `reservedAllocation`
- 持续消耗登记表 `drainRegistry`
- 恢复与定时结算
- 资源耗尽事件

### 主要问题

- 虽然资源真值比较集中，但它又通过事件反向牵动战斗体
- `预占用` 又被触发体系统写入，说明资源域和装载域没有清晰边界
- `冻结恢复` 这种战斗体相关状态直接进入资源对象，边界已经开始互相侵入

## 2. 战斗体域

### 主要职责

- 战斗体是否可激活
- 激活、解除、崩解、冷却
- 快照、恢复、伤害清理
- 战斗体专属 Hediff 与状态转换

### 主要文件

- `Source/BDP/Combat/CombatBodyOrchestrator.cs`
- `Source/BDP/Combat/CombatBodyRuntime.cs`
- `Source/BDP/Combat/CombatBodyState.cs`
- `Source/BDP/Combat/Hediff_CombatBodyActive.cs`
- `Source/BDP/Combat/Hediff_CombatBodyCollapsing.cs`
- `Source/BDP/Combat/Snapshot/CombatBodySnapshot.cs`

### 当前 owner 判断

这里没有单一 owner。

真实控制权分散在：

- `CombatBodyOrchestrator`：负责编排流程
- `CombatBodyRuntime/State`：持有部分战斗体状态
- Hediff：承载部分 Pawn 身体状态
- `CompTriggerBody`：又承担了战斗体支持接口
- `CompTrion`：通过资源耗尽事件倒逼战斗体崩解

### 主要问题

- 这是旧 BDP 最大的耦合中心之一
- 战斗体既像 Pawn 身体状态，又像外部流程状态机，又像装备触发状态
- `激活/解除` 流程很长，说明它已经不是一个清晰对象，而是一个跨系统事务

## 3. 装载与触发域

### 主要职责

- 芯片槽位
- 左右手 / 特殊槽语义
- 芯片装载、切换、激活、停用
- 组合、双持、主副手逻辑
- 触发体 UI 与武器表现

### 主要文件

- `Source/BDP/Trigger/Comps/CompTriggerBody*.cs`
- `Source/BDP/Trigger/Comps/CompTriggerChip.cs`
- `Source/BDP/Trigger/Data/*.cs`
- `Source/BDP/Trigger/UI/*.cs`
- `Source/BDP/Trigger/WeaponDraw/*.cs`

### 当前 owner 判断

`CompTriggerBody` 是旧 BDP 的超级对象。

它至少同时承担：

- 装载数据 owner
- 切换状态机 owner
- 芯片激活入口
- verb 缓存与桥接
- UI/Gizmo 入口
- 战斗体支持接口的一部分
- 与 Trion 预占用同步

### 主要问题

- 职责明显过载
- 很多行为正确性藏在触发体内部状态耦合里
- 一旦要重构，几乎所有领域都要碰它

## 4. 行动域

### 主要职责

- 瞄准
- 开火
- Trion 消耗
- 发射时数据注入
- 手动攻击与自动攻击接入

### 主要文件

- `Source/BDP/Trigger/ShotPipeline/*.cs`
- `Source/BDP/Trigger/DualWeapon/*.cs`
- `Source/BDP/Trigger/Patches/Patch_Pawn_TryGetAttackVerb.cs`
- `Source/BDP/Trigger/Patches/Patch_Pawn_MeleeVerbs_TryMeleeAttack.cs`
- `Source/BDP/Trigger/Patches/Patch_VerbTracker_VerbsTick.cs`

### 当前 owner 判断

这里也没有统一 owner。

实际由三层共同构成：

- `Verb` 和 `JobDriver` 接 RimWorld 原版行动入口
- `ShotPipeline` 处理“单次射击”的规划与结果合并
- `CompTriggerBody` 决定当前有哪些可用 verb、如何切换与补 tick

### 主要问题

- 已经开始出现统一管线思想，但只覆盖“单次射击”
- 自动攻击、近战、双持、手动攻击等入口仍然分散
- 行动域没有成为贯穿 trigger 到 projectile 的总规则层

## 5. 投递与命中域

### 主要职责

- 投射物飞行
- 轨迹修正
- 命中解析
- 到达策略
- 视觉尾迹和地图特效

### 主要文件

- `Source/BDP/Projectiles/Bullet_BDP.cs`
- `Source/BDP/Projectiles/IBDPProjectileModule.cs`
- `Source/BDP/Projectiles/Pipeline/*.cs`
- `Source/BDP/Projectiles/Modules/*.cs`
- `Source/BDP/Projectiles/BDPEffectMapComponent.cs`

### 当前 owner 判断

`Bullet_BDP` 是这里的宿主 owner，投射物模块围绕它运作。

这一块比旧 BDP 其他区域更接近“宿主统一执行、模块只产出意图”的健康结构。

### 主要问题

- 这套模块协议只在投射物域内部成立
- 没有和上游的芯片能力协议、射击行动协议统一起来
- 因此“引导、追踪、爆炸”能模块化，但整条攻击链仍然没有统一规则层

## 6. 显示与桥接域

### 主要职责

- Gizmo
- UI 窗口
- Inspect/展示
- 武器绘制
- 与 RimWorld 原版入口的补丁桥接

### 主要文件

- `Source/BDP/Core/Gizmos/*.cs`
- `Source/BDP/Trigger/UI/*.cs`
- `Source/BDP/Trigger/WeaponDraw/*.cs`
- 各种 `Patch_*`

### 当前 owner 判断

这一域本应是只读投影与桥接，但旧版里它常常反向影响业务层。

### 主要问题

- 显示层和业务层没有完全分离
- 一些 patch 既是桥接，也是业务补丁

## 旧 BDP 最明显的三类根问题

### 1. 资源域和战斗体域互相拿着对方的脖子

- `CompTrion` 负责真值
- 战斗体激活要分配 Trion
- 战斗体维持要注册消耗
- 资源耗尽又要触发战斗体崩解

这说明两者关系极深，但边界没有被设计清楚。

### 2. `CompTriggerBody` 是超级对象

它不是单纯装备宿主，而是混合了：

- 装载
- 切换
- verb
- UI
- 战斗体支持
- 资源预占用同步

这就是旧 BDP 最重的维护负担来源。

### 3. 扩展协议是分裂的，不是贯穿的

旧版不是没有协议，而是有多套平行协议：

- 芯片效果协议：`IChipEffect`
- 射击管线协议：`IShotAimModule / IShotFireModule` 等
- 投射物模块协议：`IBDPProjectileModule` 与一组 pipeline 接口

问题不是“没有接口”，而是这些接口各自为政，没有形成一条从“能力声明 -> 行动生成 -> 投递 -> 效果落地”的统一规则链。

## 对二次重构的直接启发

当前最值得保留的旧经验：

- `CompTrion` 的单一真值思路
- `Bullet_BDP` 这种宿主统一执行、模块只参与的思路
- 贴 RimWorld 原版 verb / projectile / hediff 通道的做法

当前最应该拆掉的旧结构：

- `CompTriggerBody` 的超级对象地位
- 战斗体状态跨多处共同拥有的状态分布
- 三套平行扩展协议各管一段、互不统领
