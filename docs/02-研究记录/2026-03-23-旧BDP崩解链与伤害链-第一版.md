# 旧 BDP 崩解链与伤害链（第一版）

## 目的

这份记录专门梳理旧 BDP 里“战斗体为什么会崩解、崩解后怎样进入正式解除”的代码事实。

这里不能只看一个入口，因为旧版崩解不是单点触发，而是多条链汇合到同一个崩解流程。

## 一、目前确认的崩解总入口

### `CombatBodyOrchestrator.TriggerCollapse(pawn, runtime, reason)`

当前确认的统一动作：

- 把 `CombatBodyState` 从 `Active` 切到 `Collapsing`
- 打断 Pawn 当前动作
- 给 Pawn 加上 `BDP_CombatBodyCollapsing`

结论：

- 旧 BDP 的“正式进入崩解态”入口已经被统一到这里
- 这是一条可以保留的旧经验
- 但触发这个入口的上游来源不止一条

## 二、已确认的三条上游崩解来源

### 1. `Trion Available` 耗尽链

代码事实：

- 战斗体激活后，`CombatBodyOrchestrator.RegisterMaintenance()` 订阅 `CompTrion.OnAvailableDepleted`
- `CompTrion.Consume()` 或定时消耗结算后，只要 `Available <= 0` 就会触发这个事件
- 订阅回调里如果 `runtime.State.IsActive`，就调用 `TriggerCollapse(..., "Trion可用值耗尽")`

意义：

- 这是“资源可用值耗尽导致崩解”的快速链
- 它不依赖 Hediff 轮询

### 2. `Hediff_CombatBodyActive` 轮询崩解链

代码事实：

- `Hediff_CombatBodyActive.Tick()` 每 tick 检查三类条件
- 优先顺序是：关键部位摧毁 -> 倒地 -> `CompTrion.Cur <= 0`
- 任一条件满足后调用内部 `TriggerRupture(reason)`
- `TriggerRupture()` 再转到 `CombatBodyOrchestrator.TriggerCollapse()`

意义：

- 这是“战斗体身体状态侧”的崩解监视器
- 它处理的不是单纯 Trion，还处理关键部位和倒地

### 3. 手动紧急脱离链

代码事实：

- `Gene_TrionGland` 的 gizmo 按钮会直接调用 `CombatBodyOrchestrator.TriggerCollapse(pawn, runtime, "手动紧急脱离")`

意义：

- 这说明旧版已经把“手动紧急脱离”和“被动崩解”统一到了同一条延时崩解管线
- 这不是表面 UI 细节，而是旧版流程设计上的统一点

## 三、崩解后的延时执行链

### `Hediff_CombatBodyCollapsing`

代码事实：

- `PostAdd()` 时记录 `collapseAtTick = now + 90`
- 原因从 `runtime.State.CollapseReason` 读取
- `Tick()` 到时后执行 `ExecuteCollapse()`
- `ExecuteCollapse()` 会：
  - 再次打断当前动作
  - 移除自己
  - 移除全部 `BDP_CombatBodyPartPending`
  - 调用 `runtime.Deactivate(isEmergency: true)`

意义：

- 崩解不是立即解除，而是先进入一个 90 ticks 的过渡态
- 正式解除还是走 `Runtime -> Orchestrator.Deactivate(true)` 这一整套流程
- 旧版这里明显在强调“崩解也是一种正式相位”，不是简单的即时失败

## 四、伤害进入后的事件链

### `Patch_Pawn_PostApplyDamage`

代码事实：

- 这是 `Pawn.PostApplyDamage` 的 postfix
- 只在目标 Pawn 身上存在 `BDP_CombatBodyActive` 时才继续
- 它本身不做具体业务，只发布 `BDPEvents.OnDamageReceived`

意义：

- 这里是比较健康的一层：patch 只做桥接，不直接改业务真值

### 伤害事件的两个已确认订阅者

#### 1. `HediffComp_TrionDamageCost`

代码事实：

- 订阅 `BDPEvents.OnDamageReceived`
- 找到 `BDP_CombatBodyActive` 上的 `HediffComp_TrionDamageCost`
- 根据伤害量计算 Trion 消耗
- 调用 `compTrion.Consume(cost)`

意义：

- 伤害并不直接导致崩解，而是先转成 Trion 消耗
- 再由 `CompTrion` / `Hediff_CombatBodyActive` 的崩解条件去决定是否进入崩解

#### 2. `CompTriggerBody` 静态订阅者

代码事实：

- `CompTriggerBody.Fields.cs` 静态构造函数订阅 `BDPEvents.OnDamageReceived`
- 收到事件后，从 `args.Pawn.equipment.Primary` 找 `CompTriggerBody`
- 调用 `CheckHandIntegrity(args.Pawn)`

意义：

- 触发体对伤害事件的关心点不是战斗体相位，而是“手部是否被打坏，需要禁用对应槽位”
- 这条链仍然强绑定主武器

## 五、当前发现的关键细节与风险点

### 1. 旧版同时存在 `Available<=0` 和 `Cur<=0` 两套 Trion 相关崩解条件

代码事实：

- `Orchestrator` 订阅的是 `OnAvailableDepleted`
- `Hediff_CombatBodyActive` 轮询的是 `compTrion.Cur <= 0`

当前理解：

- `Available<=0` 更像“战斗体已经没有可支配战斗资源”
- `Cur<=0` 更像“总 Trion 真正见底”
- 两者不是同一个阈值

需要警惕：

- 二次重构不能偷懒把两者并成一个字段判断
- 也不能简单删掉其中一条链，除非确认另一条已经完整覆盖旧行为

### 2. `ruptureTriggered` 只防 `Hediff_CombatBodyActive` 自己重复触发，不能替代全局去重

代码事实：

- `Hediff_CombatBodyActive.TriggerRupture()` 里有 `ruptureTriggered`
- 但 `OnAvailableDepleted` 那条链不经过这个字段
- `CombatBodyState.TransitionToCollapsing()` 自己要求只能从 `Active` 进入

当前理解：

- 真正兜底重复触发的其实是战斗体外层状态机
- 这再次证明 `CombatBodyState` 是关键相位真值 owner

### 3. 手部损坏链没有直接触发崩解，而是禁用触发体对应侧槽位

代码事实：

- `CheckHandIntegrity()` 发现 `Hand / Arm / Shoulder` 缺失时
- 只调用 `OnHandDestroyed()` -> `ForceDeactivateSideSlots()`
- 它会停用该侧激活芯片、标记 slot disabled、清理该侧 verb、重建 verbs

意义：

- 这条链处理的是“战斗能力残损”，不是“战斗体整体崩解”
- 二次重构时不能把“手部损坏”粗暴归类成统一崩解条件

## 六、对二次重构的直接约束

### 1. 必须保留“多来源 -> 单崩解入口 -> 延时解除”的整体结构

这是旧版现在最清楚的一条主线之一。

### 2. 伤害 patch 适合继续只做桥接，不适合直接写核心状态

这是旧版里少数已经比较健康的结构，应该保留这种方向。

### 3. 手部残损、资源枯竭、倒地、关键部位摧毁，不是同一种事件

它们最后可能都影响战斗体，但中间语义不同：

- 有的是局部能力失效
- 有的是资源用尽
- 有的是身体彻底失去继续维持战斗体的条件

新架构应该先把这些事件语义分清，再决定它们如何汇合。
