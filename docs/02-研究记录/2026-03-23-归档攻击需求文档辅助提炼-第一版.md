# 归档攻击需求文档对旧 BDP 理解的辅助提炼（第一版）

## 来源与地位

来源文件：

- `归档/20260323/BorderDefenseProtocol/docs/plans/2026-03-22-attack-requirements-understanding.md`

使用原则：

- 这份文档不是二次重构的直接需求来源
- 它不能覆盖旧 BDP 代码事实
- 它更不能覆盖你当前的明确决定
- 它只用于辅助理解：旧 BDP 当时哪些设计意图是有意识的，哪些方向值得保留

当前优先级：

1. 你的当前决定
2. 旧 BDP 代码事实
3. 这份归档文档的解释价值

## 一、这份文档对“攻击”本质的定义是有价值的

归档文档的核心意思：

- 攻击不只是原版武器攻击
- 本质上是“触发体 / 芯片 / 组合表达，对外产生战斗性作用的入口与执行”
- 组合技不天然等于攻击，攻击只是组合表达的一种可能
- 未来扩展不应只局限于近战、远程、子弹

这和我当前对旧 BDP 的代码理解是相容的：

- 旧版已经存在原版近战/远程
- 也存在 Ability 型、飞行实体型、投射物模块型表达
- 旧版的问题不是“攻击太少”，而是这些表达缺少一条贯穿式统一规则层

结论：

- 二次重构时，“攻击系统”不该被理解成“射击系统”
- 更准确的说法应该接近“战斗表达系统”或“攻击表达系统”

## 二、“标准原版链”和“非标准表达”必须分开对待

归档文档里最重要的一条，不是具体攻击种类，而是这组边界：

- 本质上属于原版近战 / 原版远程的，必须尽量走原版主链
- 不能只做出看起来像近战/射击的旁路
- 非原版标准武器型表达，则可以通过 Ability、飞行实体、范围效果等协议化实现

这和旧 BDP 代码现实高度一致：

- 旧版触发体已经深度接入 `Verb`、自动攻击、双武器主攻击模式
- 旧版投射物系统又支持大量非标准模块化效果
- 说明旧版本来就在同时做两件事：
  - 接原版链
  - 容纳非原版表达

结论：

- 二次重构不能企图“统一到只剩一种攻击实现”
- 真正该统一的是规则层，不是把所有表现强压成同一种宿主

## 三、手动入口和自动攻击入口分层，是明确设计意图，不是偶然实现

归档文档强调：

- 手动入口可自定义按钮
- 自动攻击应让原版 AI 自然发现入口
- 这两条路不能混

这和旧 BDP 目前能看到的结构是吻合的：

- 旧版确实有自定义按钮入口
- 旧版也确实试图走 `Verb` / `VerbTracker` / 自动攻击链
- 这不是历史遗留噪音，而是有意识的双入口分层

结论：

- 二次重构里必须保留“双入口，单规则”的方向
- 不该把“手动按钮”粗暴并回原版装备按钮，也不该把自动攻击改成全自制旁路

## 四、你最关心的“统一协议”在这份文档里表达得更清楚了

你之前说：

- 引导弹、追踪弹、炸裂弹不重要
- 重要的是贯穿整个攻击系统的统一规则
- 现在有哪些芯片类型不重要，重要的是想有什么类型就能有什么类型

这份归档文档里与之最一致的部分是：

- “未来扩展攻击”必须能容纳近战类、射击类、飞行实体类、范围类、状态施加类、生成建筑/生成物类
- “射击全过程要支持模块化叠加”
- “还要能容纳其它类型”
- “至少要有行为投递层、投递/飞行层、效果层”

这正好补强了我前面从旧代码里得到的判断：

- 旧版不是没有协议
- 旧版的问题是协议分裂，没贯穿
- 投射物域已经比较接近健康结构
- 但上游的动作生成、能力表达、组合表达还没有统一规则层

结论：

- 二次重构的重点不应是“枚举旧攻击种类”
- 而应是先建立一条能贯穿“入口 -> 行动生成 -> 投递 -> 效果落地 -> 外部信息投影”的总规则

## 五、对外兼容的原则也被这份文档说得更透了

归档文档强调：

- 原版已有属性，优先伪装成原版表面
- 让原版和其它模组自然拾取
- 多武器多表现时，如果外部系统只能读一个，就回退到“自动攻击主攻击模式”作为唯一投影

这和旧 BDP 触发体上的一些脏实现方向是对应得上的，但归档文档把“为什么要这样做”讲清楚了：

- 不是为了伪装而伪装
- 而是为了把兼容负担压在投影层，而不是让外部系统学习 BDP 内部语义

结论：

- 二次重构应该明确分开：
  - 内部真实规则
  - 对外兼容投影
- “主攻击模式”很可能应该成为一个重要的外部投影概念

## 六、目前我认为最值得吸收的几条辅助结论

### 1. “攻击”不是单一宿主概念，而是统一规则下的多种表达

这有助于避免把整个系统误做成“只是另一把武器”。

### 2. “标准原版链”与“非标准表达”必须同时成立

这有助于避免以后走两个极端：

- 要么全都强行原版化
- 要么全都自制旁路化

### 3. “手动入口”和“自动入口”必须分层

这有助于避免 UI、AI、Verb 三者重新缠死。

### 4. 统一协议应覆盖未知未来类型，而不是只覆盖旧版已经出现的攻击

这和你的最高目标完全一致。

### 5. 对外兼容优先投影成原版表面，而不是把外部兼容写进核心业务

这有助于控制后续架构膨胀。

## 七、这份文档不能直接当真需求的地方

### 1. 它不是旧 BDP 的代码事实

如果它和旧代码冲突，先信旧代码，再回来判断旧代码是不是历史错误或未完成实现。

### 2. 它来自一次重构阶段的理解整理

所以它天然带有“总结过、抽象过、筛选过”的视角，不适合反过来压代码。

### 3. 它没有资格替代你的当前裁决

以后遇到关键选择，仍然要以你现在的决定为最高标准。

## 八、对接下来阅读工作的直接帮助

结合这份归档文档，下一步看旧代码时要重点盯住这几件事：

- 旧版里“手动按钮入口”和“自动攻击入口”到底各自接到哪里
- “主攻击模式”在旧版里是怎么形成、怎么投影给外部的
- 旧版哪些表达是真原版链，哪些是非标准表达
- 旧版的 ShotPipeline、ProjectilePipeline、IChipEffect 之间到底缺哪一层统一协议

## 九、当前结论

这份归档文档最有价值的地方，不是它列了哪些攻击类型，而是它把二次重构真正该抓的本质说得更清楚了：

- 攻击不是若干具体业务清单
- 而是一套要同时容纳原版标准链与非标准表达的统一规则系统

这点与旧 BDP 代码事实、与你当前给出的最高目标，是一致的。
