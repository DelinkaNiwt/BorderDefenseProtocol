# 旧 BDP 外围功能与纳入时机清单（第一版）

## 目的

这份清单不是说这些功能不重要。

它只是把“核心骨架之外，旧 BDP 还真实存在的功能”先登记清楚，
并标明：

- 什么时候该纳入设计
- 什么时候暂时只记账，不深入

避免二次重构只盯着核心，
后面突然漏掉一堆真实功能。

## 一、我目前明确知道的旧 BDP 其它功能

### 1. 手动操作与目标选择相关

包括：

- 自定义攻击按钮
- 右键副攻击
- 引导弹多步锚点瞄准
- 自动绕行路径准备
- 手动攻击 JobDriver

这些不只是“按钮样式”，而是实际交互功能。

### 2. 自动攻击桥接相关

包括：

- 自动远程桥接
- 自动近战桥接
- 主攻击默认投影
- 芯片 Verb 脱离 `AllVerbs` 后的 `VerbTick` 补桥

这些已经算核心附近，但仍属于“入口桥接层”。

### 3. FireMode / 发射模式相关

包括：

- 伤害倍率
- 连射数变化
- 速度轴变化
- 单侧和双手独立 FireMode
- FireMode Gizmo

这块不是最底层核心真值，
但它是真实功能，不是装饰。

### 4. 多形态芯片相关

包括：

- 芯片 mode 切换
- mode 切换成本
- mode 切换后效果变化
- mode 对 Hediff / Stat / 表达的影响

这块明显是旧 BDP 已经存在的扩展能力。

### 5. 特殊槽与双手锁定相关

包括：

- 特殊槽全开全关
- 特殊槽不参与普通切换状态机
- 双手芯片锁定另一侧
- 槽位禁用与手部状态联动

这块是触发体装载系统的重要外围规则。

### 6. 视觉投影相关

包括：

- 手持武器绘制
- 左右手绘制规则
- 枪口位置
- 绘制与发射点共基准
- 发光层
- 特殊图标 / 组合图标

这块不是“美术附属”，而是实际表现层。

### 7. 信息展示与兼容表面相关

包括：

- Label
- InspectString
- Tooltip
- SpecialDisplayStats
- 对外默认武器表面

这块和外部模组兼容、玩家理解都相关。

### 8. Trion 展示与资源体验相关

包括：

- Trion 条
- 可用值 / 占用值 / 持续消耗显示
- 资源不足时按钮灰显
- Ability / 攻击前置资源检查

这块虽然建立在资源核心上，
但用户体验层面是独立功能。

### 9. 战斗体表现与收尾相关

包括：

- 主动解除
- 被动崩解
- 冷却
- 快照回滚
- 身体变化恢复
- 特殊槽联动
- 装备卸下时的两段式收尾

这块和战斗体核心强相关，但有不少外围规则。

### 10. 伤害 / 手部 / 部位联动相关

包括：

- 手部损坏导致槽位禁用
- 手部完整性检查
- 与 MissingPart / Hediff 的原版身体系统联动

这块不属于攻击系统，
但会直接影响装载和表达可用性。

### 11. 调试与诊断功能

包括：

- 枪口位置调试
- 位置标记
- 组合残留诊断日志
- 资源消耗注册日志

这些不是正式业务需求，
但重构期间很可能还需要某种替代物。

### 12. 外部兼容与信息面板兼容相关

包括：

- InventoryTab / DPS 类信息读取
- 原版 AI 可发现攻击
- 原版近战/远程识别
- 原版 Ability / Hediff 面板兼容

这块是“对外表面”需求的一部分。

## 二、这些功能应该什么时候纳入

### 第一批：从概念模型阶段就必须记住

这批不一定马上实现，
但从现在开始必须在骨架里留位置：

- FireMode
- 多形态芯片
- 特殊槽
- 双手锁定
- 视觉投影
- 信息展示投影
- 手部损坏联动
- 外部兼容表面

原因：

- 它们会反过来影响核心对象边界
- 不能等架构定死后才想起它们

### 第二批：在第一阶段最小闭环里只留接口，不做完整实现

建议先只留接口或占位规则的有：

- FireMode
- 多形态芯片
- 特殊槽
- 组合图标与复杂显示
- 复杂视觉补偿

原因：

- 第一阶段的任务是证明骨架正确
- 不是一次把所有玩法还原

### 第三批：在第二阶段系统扩展时重点补齐

建议在骨架稳定后重点补齐：

- 双手锁定完整规则
- 特殊槽完整规则
- 多形态完整规则
- FireMode 完整规则
- 视觉投影完整规则
- 外部信息兼容表面

### 第四批：实现接近完成时统一回头补验证

这时要系统检查：

- 调试替代能力够不够
- 各类按钮灰显和提示是否正确
- 信息面板表现是否合理
- 自动攻击和手动攻击是否都没回归错误

## 三、当前不该怎么做

### 1. 不能因为它们不是最核心，就完全忘掉

否则架构很容易在核心上看着对，
一接外围就崩。

### 2. 也不能现在就把每个外围功能都细读到底

否则又会回到无止境代码考古，
拖慢正式起步。

### 3. 正确做法是：先记账、分批、留口

也就是：

- 先知道它们存在
- 先知道它们大致属于哪一层
- 先在骨架里给它们留位置
- 以后按批次补齐

## 四、我当前的判断

我现在不是不知道旧 BDP 还有什么。

相反，我已经能明确知道旧 BDP 至少还有上面这些外围功能块。

只是我当前故意没有把它们全部细读到底，
因为现在更重要的是：

- 先把全系统骨架立对
- 同时确保这些外围功能未来有位置可接

下一步在“概念模型 v1”里，
我会把这些外围功能按层挂到骨架上，
明确哪些从第一阶段就必须留接口，
哪些可以第二阶段再补。
