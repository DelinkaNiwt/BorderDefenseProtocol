# 刀光剑影：功能、构型、形态、姿态配置适配评估

日期：2026-10-09。性质：按最新要求补充的可行性评估，尚未实施，不作为已批准的实施设计。

## 当前目标

刀光剑影武器配置列表应包含 BDP 定义的有效近战配置条目。基础身份为芯片功能或武装构型，构型优先于功能；在基础身份内，形态与姿态也参与识别和配置。

同一功能、构型与状态制造出的不同芯片实例共用设置，不按芯片实例、角色或左右手另建条目。只列实际包含近战攻击的有效状态。条目名注明实际存在的形态、姿态，没有对应层级则省略。

本记录承接《2026-10-09-刀光剑影识别机制与BDP适配可行性》，将原先“先只做攻击类型”的建议更新为“完整的配置条目与攻击归属桥接”。原机制调查仍适用。

## 已确认的支撑条件

### BDP 来源与状态

- `ChipInstanceSurfaceAccess.ReadSourceReference`（芯片来源读取）公开功能来源键与生效构型键。制造组件的 `SourceVariantKey`（来源变体键）也考虑隐式生效的默认构型，不能只检查制造记录有没有手选构型。
- `ExpressionSurfaceAccess.TryGetPublishedResult`（公开表达结果读取）可按实际攻击的结果标识读取来源芯片、形态及复合来源关系。
- `ITriggerLoadoutReader.GetChipModeKey / GetChipStanceKey`（读取当前形态、姿态）已有正式读取口。配置枚举使用定义，实际攻击路由使用当前正式来源与状态，两者不能混用。
- `ChipExpressionModeConfig`（形态配置）从统一表达目录中选取公共条目；`ChipExpressionStanceConfig`（姿态配置）再追加姿态条目。
- `ChipExpressionContractInterpreter.SelectActiveEntryConfigs`（选择实际有效表达条目）已经明确：无形态时使用统一目录；有形态时先选形态公共条目，再追加所属姿态条目。兼容判断应遵循这套规则。
- `ChipArmamentFormExpressionService`（构型表达覆盖）只对正式武装攻击条目施加覆盖，并遵循声明字段覆盖、未声明保留的规则。不能以构型名称判断是否近战。

### 刀光剑影列表与保存

本轮继续读取当前安装程序集，模块标识仍为 `041d3159622747b98cb68730c4ada103`。

- `DGJY_MeleeWeaponEntry`（武器目录项）有物品定义引用、字符串身份键、名称及所属模组字段。
- `DGJY_Window_WeaponReachOverrides.DrawWeaponRow`（配置页武器行）依赖真实物品定义计算自动类别和距离，但菜单通过字符串身份键修改配置。因此新条目需要展示适配，不能只把文字插进列表。
- `DGJY_WeaponVfxOverrideDatabase`（刀光覆盖数据库）提供按字符串设置、读取、清除的入口。加载覆盖记录时不要求这个键对应真实物品定义，支持复用其原有保存机制。
- `DGJY_MeleeVfxService.TryPlay`（播放服务）目前仍按真实装备物品定义查覆盖，必须额外把实际 BDP 攻击路由到相应配置键。
- 现有手动刀光配置的语义是替换效果纹理、保留自动选择的基础效果配置；本适配不应未经说明将其变成另一套效果行为。

## 建议的条目识别规则

### 只展开实际存在的状态

| 定义结构 | 建议生成的配置单位 |
|---|---|
| 无形态、无姿态 | 功能或构型本身 |
| 有形态，该形态无姿态 | 功能或构型＋该形态 |
| 有形态，该形态有姿态 | 功能或构型＋该形态＋各有效姿态 |

每项都必须通过有效近战检查。不把没有姿态的形态与其它形态的姿态交叉相乘；不为有姿态的形态再自动增设一个运行中不存在的“无姿态”条目。

建议第一版采用这种完整状态条目，不额外增加“全部形态通用设置、形态默认设置、姿态单独设置”的多层继承。这能让每次攻击明确对应一项设置，避免优先级膨胀。

### 判断有效近战

```text
功能声明的表达目录
  → 施加有效构型覆盖
  → 选择该形态公共条目
  → 追加该姿态条目
  → 判断所得结果是否包含有效近战攻击
```

基础候选应来自真实武装攻击配置及有效近战工具，不能仅凭“剑、刀、盾”等名称、职业或标签判断。远程攻击、护盾和纯防御效果本身不构成近战条目。

若某姿态只声明防御效果，但继承了形态公共近战攻击，仍应入列。反过来，整个功能在另一形态有近战，不代表当前形态也入列。

目录表达的是定义允许的潜在近战状态，不随当前角色是否装载、是否缺资源、是否受伤等临时条件反复增删。真正播放时仍遵守实际攻击的合法性和外部播放开关。

特殊能力或范围攻击是否也算本适配的近战，需要按其实际执行入口判断。第一版可完整覆盖当前正式近战武装；不能宣称所有外观像近战的能力自动纳入原版近战刀光入口。

### 当前名称实例

| 条目名称示例 | 原因 |
|---|---|
| 弧月 | 没有形态、姿态层级 |
| 蝎子 | 没有形态、姿态层级 |
| 光魂【形态：光魂大盾；姿态：灵活姿态】 | 大盾公共条目包含盾击，姿态追加防御效果 |
| 光魂【形态：光魂大盾；姿态：举盾姿态】 | 同样继承公共盾击，可以单独配置刀光 |
| 光魂【形态：光魂重刃】 | 重刃有近战工具，没有姿态层级 |

基础默认效果可按该有效状态的工具自动识别：弧月、蝎子是切割；大盾是钝击；重刃含钝击与切割工具。重刃默认类别的具体规则仍须在实施设计中明确，可复用外部整套工具评分，或按本次实际招式作为自动回退。玩家手动覆盖则归属于完整状态条目。

名称读取现有功能、构型、形态和姿态语言键；新增“形态、姿态”等组合格式放入语言包。保存键使用定义标识、形态键和姿态键，不使用可翻译的显示名称。

## 构型优先与攻击归属

建议每次攻击先确定实际来源芯片与功能，再确定生效的近战构型，最后匹配该来源的有效形态、姿态：

```text
有对应有效近战构型条目 → 使用构型的完整状态配置
否则                 → 使用功能的完整状态配置
```

构型设为“自动”仍使用构型条目的自动效果，不因没有手动覆盖就偷偷使用功能的手动效果。此处是建议的优先语义，尚待实施前定稿。

构型当前是覆盖层，并没有独立的形态、姿态目录。未来将一个构型叠加到多形态功能时，状态往往来自功能。构型配置键必须保留这些状态的来源范围，不能只把裸形态键拼到构型名后。

例如两个功能都存在 `shield`（盾）形态、`guard`（举盾）姿态，若它们叠加同一构型，必须防止误合并。建议形态、姿态使用所属功能范围内的稳定身份；必要时在条目名称中再注明来源功能。同一构型叠加到多个无状态功能时，仍可共用构型基础条目，避免无必要拆分。

当前双功能制造会用功能定义键建立制造形态，但这只是来源路由；单功能芯片与双功能芯片中的同一无状态功能应继续共用配置，不能因为制造包装多出一个形态就重复列项。当前原生多形态功能也被制造选择规则限制为独立组合，减少了现阶段复杂性。

攻击来源应使用正式结果和芯片来源记录，不能通过当前装备名猜测。对于连击或未来复合近战，还需核对当前攻击实际采用的来源，防止借用另一只手或切换后的新来源配置。记录用于本次播放的身份应与实际攻击一致，不能在每次绘制时重新猜状态。

## 实现方向与复杂度

推荐在 BDP.Compatibility（兼容程序集）做可选适配：为刀光剑影配置页加入虚拟配置条目，复用其字符串设置和保存入口；为实际播放补身份查询。虚拟条目是界面和配置身份，不向原版全局定义库注册虚构武器，不改变真实装备归属。

配置页的搜索、所属模组筛选、自动类别展示、重置及保存均须完整支持这些条目。是否加入全局目录，必须先核对其它目录使用者；只要求配置页条目时，应优先限定在该页面，避免排除页等其它功能受到意外影响。

备选方案：生成代理武器定义以迁就外部所有接口，但会引入定义、缓存与装备语义的额外维护，不推荐作为默认路线。若能协作修改刀光剑影，增加通用配置来源扩展口会更稳，但本项目不能把外部作者配合作为当前可行性的前提。

| 工作块 | 复杂度 |
|---|---|
| 功能来源与生效构型识别 | 低至中：已有中性公开读口 |
| 形态、姿态有效近战枚举 | 中：需继承公共条目，并应用构型覆盖 |
| 配置页条目、名称、筛选与原有设置保存 | 中：保存可复用，自动数据展示须适配 |
| 实际攻击路由、连击与切换边界 | 中：来源必须与本次攻击一致 |
| 构型跨不同功能的状态命名与身份 | 中至高：当前没有近战构型实物可验证 |
| 外部升级后的成员检查与适配失效处理 | 中：依赖外部具体方法，需独立停用 |

综合判断：当前功能与状态的完整刀光适配为中等复杂度；包含未来构型跨功能状态的可靠通用支持，为中至高。增加形态姿态本身不是主要障碍，难点是列表中的配置身份与每次实际攻击的身份始终一致。

真实攻击距离仍是独立范围。外部同页存在距离控件，纯刀光版本应对 BDP 虚拟条目明确禁用或标明不支持战斗距离，不能让玩家修改后产生“配置可改但实际无效”的误解，也不能暗中改变 BDP 接触寻路和攻击判定。
