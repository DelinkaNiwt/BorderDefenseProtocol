# 清洗执行记录-第八刀

日期：2026-03-25

## 本刀目标

在三核心都补齐正式表面对象之后，继续压缩 owner / host 的公开成员面。

这一步解决的问题是：

- 虽然外部已经有 `SurfaceAccess + FormalSurfaces`
- 但 `CompTriggerBody / CompTrion / CompCombatBodyHost` 仍保留太多 `public` 成员
- 这会让“外部绕开正式表面直接摸 owner”继续成为默认诱惑

## 实际改动

### 1. `Trigger` owner 公开面收口

处理结果：

- `CompTriggerBody` 上供正式表面转发使用的成员，改为 `internal`
- 包括：
  - 事件
  - 读取方法
  - 请求方法
  - 诊断方法
  - `OwnerPawn`

保留 `public`：

- RimWorld 框架必须公开的入口
  - `IThingHolder` 相关
  - `CompGetEquippedGizmosExtra`

裁定：

- `Trigger` owner 继续可被程序集内部正式表面访问
- 但不再鼓励程序集外或后续开发者直接把它当正式接口面使用

### 2. `Trion` owner 公开面收口

处理结果：

- `CompTrion` 上供正式表面转发使用的成员，改为 `internal`
- 包括：
  - 资源读取属性
  - 请求方法
  - 事件

保留 `public`：

- RimWorld 生命周期入口
  - `Initialize`
  - `PostSpawnSetup`
  - `CompTick`
  - `PostExposeData`

裁定：

- `CompTrion` 现在更明确地只作为资源真值 owner
- 正式外部能力应从表面对象拿

### 3. `CombatBody` host 公开面收口

处理结果：

- `CompCombatBodyHost` 上供正式表面转发使用的成员，改为 `internal`
- 包括：
  - 读取属性
  - 请求方法
  - 事件

保留 `public`：

- RimWorld 生命周期入口
  - `PostExposeData`

裁定：

- `CompCombatBodyHost` 现在更明确地只是主链宿主位
- 正式对外读写事件都应走 `CombatBodySurfaceAccess`

## 结构结果

本刀前：

- 三核心已经具备正式表面对象
- 但 owner / host 自身仍然暴露大量 public 转发成员

本刀后：

- 三核心不仅“有正式表面”
- 而且 owner / host 的公开面也开始被压窄

也就是说，边界不再只是“建议你走表面”，而是“结构上更不方便绕开表面”。

## 当前裁定

这刀之后，三核心边界统一度进一步提高：

- `Trigger`：owner + 正式表面 + 压窄 owner public 面
- `Trion`：owner + 正式表面 + 压窄 owner public 面
- `CombatBody`：host + 正式表面 + 压窄 host public 面

下一步重点应转向：

1. 复审兼容接口是否仍有空壳或命名误导
2. 复审 `SurfaceAccess / FormalSurfaces / owner` 三层之间是否还有多余转发
3. 对目录归属、命名、残留假中间层做综合清洗清单第二版
