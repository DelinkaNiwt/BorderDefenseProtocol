# 清洗执行记录-第十七刀

日期：2026-03-25

## 本刀目标

处理“一级分组后，组内还是太平铺”的问题。

这一步只给已经再次拥挤的组补二级抓手，不把所有目录都拆成多层模板。

## 本刀判断

### 1. `Trigger/Access`

问题：

- 接口文件
- formal surface 实现
- surface access 入口

三类东西还堆在一层。

裁定：

- 增加：
  - `Contracts`
  - `Surfaces`

理由：

- 先看协议，再看表面实现
- 读目录时更符合“外部先拿什么，再由谁实现”

### 2. `Trigger/Switching`

问题：

- 状态模型
- 规则
- 推进流程
- 协调件

混在一层，读起来还是挤。

裁定：

- 增加：
  - `Model`
  - `Flow`

理由：

- `SwitchContext / SwitchPhase / TriggerDisableReason` 属于切换状态模型
- 其余启停推进、规则与切换流程属于过程层

### 3. `CombatBody/Access`

问题：

- 接口
- formal surface
- access 入口

仍然混在一层。

裁定：

- 增加：
  - `Contracts`
  - `Surfaces`

### 4. `CombatBody/Flow`

问题：

- 协调口
- 总协调器
- enter / exit pipeline

虽然不多，但继续增长时会再次打平。

裁定：

- 增加：
  - `Contracts`
  - `Pipelines`

并保留：

- `CombatBodyCoordinator` 在 `Flow` 根层

理由：

- 它是这一组的中心件
- 不该再埋进更深目录

## 本刀后的分层原则

### 允许二级分层的情况

- 一级目录下再次出现明显混类
- 文件阅读顺序已经需要靠记忆
- 二级目录名能直接说明职责

### 不允许二级分层的情况

- 只是为了看起来更工整
- 文件数量不多
- 目录名只能表达技术抽象，不能表达玩法职责

## 当前结果

现在目录阅读路径变成：

- 先看大职责
- 再看协议 / 表面 / 模型 / 流程
- 最后才看具体文件

这比单层平铺更适合长期维护，也没有重新长成“企业式层级展示图”。
