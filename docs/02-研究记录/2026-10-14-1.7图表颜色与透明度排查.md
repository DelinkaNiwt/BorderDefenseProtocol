# 1.7 图表颜色与透明度排查（场景 02 / S04）

## 结论与范围

**根因已确认：1.7 的 GL（即时几何绘制）兼容层使用顶点颜色，未沿用 BDP 原先依赖的纯色材质颜色路径。BDP 没有显式设置顶点颜色，初始顶点色为完全不透明的白色，因此雷达图、护盾扇区和折线一起变白。属于版本差异，应只适配 1.7。**

首次排查完成截图对照、真实程序集调用链核实、独立进程颜色传递验证和替代接口调查；当时没有修改模组。用户后续已授权实施推荐方案，执行结果见文末“实施记录”。

用户确认三张异常截图都来自 1.7，主要异常是变白、不透明，未指出明显的其他问题。随后补充一张 1.6 对照图，预期为青色当前线、较淡的网格/基准线和半透明填充。两张图的界面布局与文案并非完全一致，故不能仅凭截图差异判定新增的布局或数据错误；本轮只确认颜色和透明度。

## BDP 实际绘制链

当前不是第三方图表库，而是 BDP 的中性图表工具：

```text
Content：芯片信息详情渲染器（提供数据和样式）
  → Core：雷达图 / 折线图 / ChartCanvas（图表画布）
    → ChartDrawingContext（绘图上下文）
      → ChartGeometryRenderer（裁切和三角形提交）
        → 纯色材质.SetPass(0) → GL.Begin → GL.Vertex3 → GL.End
```

关键位置为 `Source/BDP/Core/UI/Charts/ChartGeometryRenderer.cs:161`。它将所需颜色交给 `SolidColorMaterials.SimpleSolidColorMaterial(color)`，但整个文件没有 `GL.Color(...)`（设置顶点颜色）调用。

业务层的颜色及透明度仍正确存在：`ChipInformationDetailRenderer.cs:2997` 附近配置当前线青色、填充色 `(0.18, 0.55, 0.56)`，雷达当前填充实际使用 0.18 透明度；护盾扇区在第 3072 行附近传入 0.22 透明度。`RadarChartRenderer.cs:119` 附近也确实将填充透明度写入颜色后再传到底层。不是数值模型把颜色变成白色。

影响范围按共同入口归并：四轴/六轴雷达图、精度折线、虚线、数据点、护盾参考圆和扇区、机动示意，以及 Development（开发辅助）的图表预览。文本通过 `GUI.color`（界面着色）和原版文字控件绘制，走另一条颜色路径，故截图中文字仍能正常显示青色。

## 真实程序集证据

对应本机 1.7.4977 rev1248 与 1.6.4871；游戏查询明确使用分版本上下文。关键证据：

| 对象 | 证据 |
|---|---|
| 两版 `SolidColorMaterials.SimpleSolidColorMaterial` | 方法反编译内容相同，哈希 `31295a564548a6554e41b548292a873862821bd1e85b8325f8c7e593d8f6a814`；仍按传入颜色选取纯色材质 |
| 1.7 `UnityStubs.dll` | MVID（模块标识）`725037033ce749c4abad87b980bc0cc3` |
| `UnityEngine.Material.SetPass` | 只记录即时材质/来源并返回成功，不设置 GL 顶点色；方法哈希 `778a43b7951b05ba27a3cbc338b807fc0aa3f5382a71e045e5e7d607dc9b5c2b` |
| `UnityEngine.GL` | `_color` 初始为四通道 255；`Color(c)` 更新它，`Vertex` 把它写进每个顶点；`End` 只从即时材质取得纹理并把顶点交给界面后端；类型哈希 `78608e1a6743367d358481491585f124da13e2ccb7fa8c43e841420c232c2e50` |
| 1.7 `RimWorld.dll` | MVID `5ed5a13416674869b0769856f94ea84d`；`ImGuiGuiBackend.DrawPrimitives` 将三角形送入原生绘制列表 |
| 后端 `PrimVertex` | 明确使用 `v.color.r/g/b/a` 写入绘制顶点，不乘上述纯色材质颜色；方法哈希 `8f7cedab3121fa691059de07f6ebfc465f0d490b4a11e740c7d69c86c38cdf5c` |

因此这条路径的材质颜色及透明度没有到达最终绘制顶点。接口调用本身成功，几何也被提交，不必产生错误日志。若其他调用曾改过 GL 全局颜色，未显式设色的图表还可能受到遗留状态影响；本次独立进程与用户截图均为初始白色的表现。

不能将 `GL.Color` 无条件复制进 1.6，并假设所有材质都会以相同方式处理顶点颜色。1.6 的纯色材质显示已有用户对照证据；版本适配应集中在中性绘制底层，保留其现有路径。

## 可选替代方案

官方公告只笼统提到新引擎更便于大型视觉改动和复杂效果，没有给出可直接替换这些图表的组件说明：[Ludeon 1.7 公告](https://ludeon.com/blog/2026/10/announcing-the-waylith-engine-and-update-1-7/)。以下接口的存在与行为主要依据本机真实程序集，而非旧版教程。

| 方案 | 已确认的能力 | 对 BDP 的适用性 |
|---|---|---|
| 保留图表工具，在 1.7 显式传递顶点色 | 上述真实接口实验已通过 | **优先建议**：集中修改几何提交入口，可同时覆盖截图中的多种图形；保留数据、布局、裁切和 1.6 路径 |
| 原版 `Widgets.DrawLine`（绘制线段） | 两版本实现相同；使用带明确颜色的纹理绘制路径，并采用抗锯齿线纹理 | 可作为线条绘制候选；不能单独替换雷达或护盾填充，线宽、端点及裁切效果仍需对照 |
| 原版 `SimpleCurveDrawer`（曲线绘制器） | 可绘制多条曲线、坐标刻度和图例；抗锯齿线分支复用 `Widgets.DrawLine` | 适合常规曲线；不是雷达图或扇区平替，迁移现有虚线、比较值标记和布局并非必要修正 |
| 随游戏提供的 `Brutal.ImGui` 原生绘制列表 | 已找到折线、圆、圆弧、凸/凹多边形填充，以及线条/填充抗锯齿标记 | 可作为未来画质改进候选，但不是现成的雷达图表库；需接入当前绘制帧/列表并处理坐标、缩放、裁切、颜色及依赖，不适合仅为当前颜色问题整体迁移 |

原生接口的具体证据来自 `Brutal.ImGui.dll`，MVID `ec6876d57ebb4615a47f29576959dba5`：`AddPolyline`（折线）、`AddTriangleFilled`（三角形填充）、`AddCircleFilled`（圆填充）、`PathArcTo`（圆弧路径）、`AddConvexPolyFilled`（凸多边形填充）、`AddConcavePolyFilled`（凹多边形填充）。`ImDrawListFlags` 含 `AntiAliasedLines` 和 `AntiAliasedFill`（线条/填充抗锯齿）标记；本轮未做这些原生接口的游戏内画质或性能测量。

注意雷达数据轮廓可能是凹多边形，不能将所有雷达轮廓直接交给凸多边形接口。现有 GL 兼容层本身就把几何送入同一个 ImGui 后端；直接改为原生调用并不自动意味着更快、更清晰或更稳定。原生高级绘制函数有画质改进空间，但要单独验证。

## 建议的最小处理与验收

1. 仅在 `ChartGeometryRenderer` 的 1.7 路径中，于顶点提交前显式设置颜色；绘制结束恢复白色状态，不向无关业务散布版本判断。已按后续授权实施。
2. 1.7 通过现有开发菜单“BDP：打开中性图表工具预览”验证固定数据，再验证用户截图的远程/近战雷达、护盾 180°扇区、精度实虚线及机动示意。
3. 检查颜色、不同透明度叠加、透明度 0、滚动上下边界裁切，以及不同界面缩放；对照用户提供的 1.6 风格。
4. 1.6 保留原路径，分别编译并复查对应图表，不使用 1.7 结果替代。暂不引入新依赖或整体迁移工具。
