RimWorld（边缘世界）1.7 即时界面绘制能力与 BDP 现状

**研究基线。** 2026-10-14，用户明确研究 1.7。读取本机 `Version.txt` 为 `1.7.4977 rev1248`；原版行为以真实程序集反编译为依据，BDP 以当前工作区源码为依据。本次没有修改游戏或模组功能，没有构建、部署或进行游戏内点击、画质和性能测试。官网资料只补充发布背景与库的一般原理，不代替实际游戏接口。

**核心结论。** 新引擎叫 Waylith（引擎名称）；它集成的界面库确实是 Dear ImGui（即时界面库），游戏通过 `Brutal.ImGui.dll` 提供 C#（C#语言）绑定。旧版 Unity 的 IMGUI（即时模式界面系统）与 Dear ImGui 采用相近的界面编程方式，但不是同一套实现。BDP 的正式界面主要沿用原版控件与 Unity 风格接口，在 1.7 中经过兼容层最终进入 ImGui 绘制后端；开发程序集中的独立展示则直接调用原生 ImGui。

**名称与层级。**

| 名称 | 指的是什么 | 与 BDP 的关系 |
|---|---|---|
| Waylith（引擎名称） | RimWorld 1.7 使用的新游戏引擎 | 负责运行、渲染、输入等底层能力 |
| IMGUI（即时模式图形界面） | 一种界面编程方式 | 每轮界面更新用代码描述当前应显示的内容 |
| Unity IMGUI（Unity 即时界面系统） | Unity 对这种方式的实现 | 1.6 主要界面基础，常见入口为 `OnGUI`（界面事件回调） |
| Dear ImGui（即时界面库） | 独立的原生界面库 | 1.7 实际使用，支持控件和二维绘制列表 |
| `Brutal.ImGuiApi`（界面绑定命名空间） | 游戏随附的托管调用接口 | BDP 展示通过它调用原生库 |
| `Verse.Widgets`（原版控件工具） | RimWorld 自己的按钮、标签、滚动等封装 | BDP 正式界面的主要调用入口 |
| `UnityStubs`（Unity 接口兼容程序集） | 在新引擎上实现 Unity 风格接口 | 允许大量旧界面源码继续工作，不代表仍在运行 Unity 引擎 |

官方在 2026-10-12 公告中说明从 Unity 转到 Waylith，当时通过不稳定测试分支提供 1.7。公告中整体性能提升不能归因于某一个界面库，也不能作为 BDP 改用原生接口后必然提速的依据。

**即时模式怎样工作。** 每次界面更新，代码读取当前数据，按顺序调用标签、按钮、滑条或绘制函数；控件调用也返回是否发生点击、数值是否变化等信息。显示条件改变时，下次提交的界面自然改变，不必另建和维护整棵长期存在的控件对象树。

即时模式不等于没有状态。选中的芯片、输入文字和业务数据由应用持有；库内部仍保存焦点、正在拖动的控件、滚动位置、窗口状态等。控件靠稳定的 ID（标识）跨帧关联，不能把每帧变化的显示文字直接当作唯一稳定身份。`PushID`（压入标识）和 `##`（隐藏标识后缀）用于解决重复或变化标签的问题。本地化仍由 BDP 语言键和 `Translate`（翻译调用）负责。

“每次重新描述界面”也不意味着每次重新读取资源、上传所有贴图、重建字体，或逐个控件马上向显卡发命令。库会生成顶点、索引和绘制命令，后端再集中提交。

**RimWorld 1.7 的真实绘制链路。**

```text
正式界面：窗口、状态卡、原版控件、自定义图表
    ↓
Verse.Widgets / UnityEngine.GUI / UnityEngine.GL
（原版封装 / Unity 风格界面接口 / 即时几何接口）
    ↓
UnityStubs.Gui.IGuiBackend（兼容后端约定）
    ↓
RimWorldWaylith.Imgui.ImGuiGuiBackend（实际兼容后端）
    ↓
Dear ImGui 绘制列表
    ↓
绘制快照 → 顶点及索引缓冲 → Vulkan（图形接口）→ 屏幕

原生展示：Brutal.ImGuiApi.ImGui（原生控件）
          / ImDrawList（原生绘制列表）
    └────────────────────→ 同一 ImGui 帧与渲染后端
```

`Bootstrap.ConfigureFrameRenderer`（引擎绘制初始化）建立宿主、兼容后端和界面渲染阶段。`ImGuiRenderFeature.CaptureFrame`（捕获界面帧）依次执行宿主开始帧、构建界面、宿主结束帧。宿主开始帧调用 `ImGui.NewFrame`（开始原生帧）；结束帧调用 `ImGui.Render`（生成绘制数据）、处理纹理更新并复制绘制快照。

`ImGuiVulkanRenderer.RecordDraws`（记录显卡绘制命令）把顶点和索引写入缓冲，设置裁切矩形，绑定纹理并调用索引绘制。每个顶点主要带位置、纹理坐标和颜色；文字也是字体纹理上的图形。颜色透明度、纹理、裁切和命令顺序共同决定最终结果。

这里必须分清“使用同一绘制后端”和“使用同一控件”。`Widgets.ButtonTextWorker`（原版文字按钮实现）仍使用原版绘制和不可见按钮判断；兼容层 `GUI.ButtonImpl`（按钮实现）仍处理 Unity 风格事件。它们不会仅因后端使用 ImGui 就变成 `ImGui.Button`（原生按钮），也不会自动获得原生控件的所有布局和交互能力。

**两类接口。** 一类是现成控件，如按钮、输入框、滑条、表格；它们负责布局和常见交互。另一类是 `ImDrawList`（绘制列表），用于画线、圆、多边形、图片等。后者只负责画图；画一个圆不等于产生一个能点击和拖动的圆形控件。可通过 `InvisibleButton`（不可见按钮）和鼠标位置给自定义画布补上交互，具体命中形状与业务规则仍由调用者决定。

**本机绑定已确认的能力范围。** 下表“有接口”表示真实程序集包含对应入口，不表示本次已经逐项在游戏内验收。

| 能力 | 可以做什么 | 已确认的代表接口与边界 |
|---|---|---|
| 基础控件 | 按钮、复选、单选、选择项、进度条、滑条、数值拖动和颜色编辑 | `Button / Checkbox / SliderFloat / ColorEdit4`（按钮／复选／滑条／颜色编辑）等；操作如何修改游戏仍由模组决定 |

| 窗口与布局 | 子窗口、滚动、同排排版、菜单、弹出框、提示、折叠树和标签页 | `BeginChild / SameLine / BeginTabBar`（子窗口／同排／标签栏）；不是自动适应所有屏幕的网页排版系统 |
| 数据表格 | 列宽调整、列隐藏、重排、冻结表头、排序交互 | `BeginTable`（开始表格）和表格标记；排序后的业务数据由调用方处理 |

| 拖放 | 拖动源、目标和载荷传递 | `BeginDragDropSource / BeginDragDropTarget`（拖放源／目标）；不能代替 BDP 装配准入、容量校验与事务提交 |
| 基本几何 | 直线、折线、圆角矩形、三角形、圆、椭圆及填充 | 绘制列表有相应接口；轮廓和填充可分别控制 |
| 路径与曲线 | 圆弧、二次和三次贝塞尔曲线、路径描边与填充 | `PathArcTo / AddBezierCubic`（圆弧路径／三次贝塞尔）；采样和曲线细分由库提供基础支持 |
| 多边形 | 凸多边形、简单凹多边形填充 | `AddConvexPolyFilled / AddConcavePolyFilled`（凸／凹多边形填充）；凹轮廓不能用凸接口替代，不代表支持任意自交、孔洞和布尔运算 |
| 颜色与边缘 | 每顶点颜色、透明叠加、四角颜色渐变、线条和填充抗锯齿 | `AddRectFilledMultiColor`（四角渐变矩形），`AntiAliasedLines / AntiAliasedFill`（线条／填充抗锯齿）；直接提交裸三角形不会自动补出高级轮廓抗锯齿 |
| 图片与文字 | 图片、四边形图片、圆角图片、纹理坐标、字体与文字 | `AddImage / AddImageQuad / AddImageRounded`（图片／四边形图片／圆角图片）；游戏纹理要通过后端正确解析成纹理引用 |
| 裁切与层次 | 窗口／子区域裁切、绘制顺序、不同绘制列表 | `PushClipRect`（压入矩形裁切）；矩形裁切不是任意多边形遮罩，绘制裁切也不自动处理全部鼠标命中规则 |
| 简单图表 | 数值折线与直方显示 | `PlotLines / PlotHistogram`（折线绘图／直方显示）；没有替 BDP 定义雷达轴、缺失值、对比语义和领域标注 |
| 自定义图形工具 | 雷达图、仪表、时间轴、节点连接线、动画和可拖画布 | 用几何、文字与交互组合实现；这类成品通常仍需模组代码，不能把可组合能力当作内置完整编辑器 |
| 调试检查 | 示例窗口、样式编辑、绘制指标、标识检查 | `ShowDemoWindow / ShowMetricsWindow`（示例／指标窗口）等；适合 Development（开发辅助程序集） |
| 停靠与多视口 | 可停靠窗口以及跨系统窗口的潜在能力 | 绑定包含 `DockSpace`（停靠区域）及视口接口；本次未证实游戏启用停靠配置或完整多系统窗口后端，不能承诺直接可用 |

**为什么曲线能更方便、更平滑。** 使用原生高级几何接口时，库把路径细分成三角形，并可沿轮廓增加透明边缘，使斜线和曲线边缘过渡更平滑。现有 BDP 图表自己把线段扩成四边形，再拆成三角形；圆点使用固定 16 段扇形；没有显式建立原生高级描边的边缘抗锯齿。因此直接使用高级接口有减少手工几何代码、改善轮廓的潜力。

这不是无限精度矢量绘图。最终仍是像素和三角形；线宽、位置是否落在合适像素、缩放、细分密度、透明叠加和原生标记均会影响效果。更多细分也会增加顶点数量。不能仅因换了调用入口就声称一定更清晰或更快。

**图表与生态的边界。** Dear ImGui 的核心包含简单曲线显示，但不是完整专业绘图库。ImPlot（图表扩展库）、节点编辑器、时间轴编辑器等属于额外生态；未从当前游戏目录发现可以直接视为内置的 ImPlot 程序集，不能把网上扩展展示算作 RimWorld 现成能力。雷达图和高级折线比较图可以用绘制列表搭建，数据到坐标、刻度、图例、缺失数据、领域提示、缩放和点选逻辑仍需实现。

**动画与效果的边界。** 每帧改变点位置、颜色、透明度、线宽和进度，就能做扫描、波动、旋转和闪烁。库没有自动的业务动画状态机；界面动画用真实帧间时间还是游戏刻时间由作者决定。地图暂停后界面仍可继续动画。任意模糊、光晕、复杂滤镜、三维模型和地图特效不属于仅调用基础 ImGui 图元就自动得到的功能，通常还需贴图、材质或引擎其他渲染能力。

**字体与中文。** 游戏宿主管理字体及语言后备字体，并尝试使用 FreeType（字体栅格化库），失败时回退到另一字体实现。原生展示复用游戏上下文和字体。能显示中文与中文输入法能正常输入是两项不同验证；本地化、文本布局和输入桥也不能彼此替代。普通原生 `Text`（文字接口）不应直接当作原版富文本标签解析器。

**性能应如何理解。** 即时界面库可合并相容的绘制命令，适合快速变化的数据界面。收益取决于调用数量、顶点数量、纹理和裁切切换、列表可见项裁剪、布局计算及每帧数据准备。每帧重新查询全部芯片、重复构建详情模型或生成大量临时集合，仍会消耗处理时间。因为现有兼容路径也进入 ImGui 后端，不能假定“直接调用”会带来一个独立的新渲染器或官方公告中的整体倍率提升。

**BDP 当前技术对照。**

| 能力领域 | 当前 BDP 使用的方法 | 原生能力可能减少什么工作 |
|---|---|---|
| 正式窗口 | 继承 `Verse.Window`（原版窗口），重写 `DoWindowContents`（窗口内容回调），使用窗口栈管理打开关闭、暂停和输入遮挡 | 原生窗口能提供布局与控件，但不会自动纳入原版窗口栈；保留原版窗口壳有实际价值 |
| 页面布局 | 手算 `Rect`（矩形）和固定宽度／间距，装配台明确为三栏布局 | 自动流式布局、子窗口或表格可减少部分位置计算；不能保证完全复现当前外观 |
| 搜索与库存列表 | 原版输入框、按钮、滚动区域，自行筛选数据、画卡片并记录命中矩形 | 原生控件和可见项裁剪可提供工具；筛选和芯片状态规则继续保留 |
| 文字与图标 | `Widgets.Label`（原版标签）、原版字体状态、`GUI.DrawTexture`（绘制纹理）和语言键 | 原生文字和图片可直接绘制，但需处理现有纹理与字体衔接 |
| 操作卡与状态条 | 原版 `Gizmo`（操作卡）入口；Trion（触力能）状态卡和通用状态卡自行组合色块、标签、数值及提示 | 原生进度条能表达一般比例，未必适合替换原版操作卡位置与专门版式 |
| 装配拖拽 | 独立拖拽状态、原版鼠标事件、槽位／库存命中判断、释放和拖拽图标；实际装配交给业务事务 | 原生拖放可管理交互载荷，不能接管业务事务 |
| 雷达图与折线图 | Core（基础设施程序集）保存中性图表模型、范围、坐标映射和样式，Content（内容程序集）提供业务值；通过图表画布集中绘制 | 可只替换部分几何提交而继续复用模型和业务调用 |
| 图表线条与填充 | 自算线段四边形、虚线切段、圆弧采样、扇形填充，裁切后经 `GL.TRIANGLES`（即时三角形模式）提交 | 折线、圆弧、凹多边形和抗锯齿可改由原生高级函数处理 |
| 图表裁切 | 自算矩形与凸多边形交集，文字通过原版分组裁切 | 原生矩形裁切能减少部分工作；雷达边界等多边形裁切仍不能无条件删除 |
| 人物肖像 | 调用原版人物缓存渲染器生成 `RenderTexture`（渲染纹理），在界面显示 | ImGui 能显示结果图片，不能生成 RimWorld 人物外观或代替人物渲染树 |
| 原生能力探索 | 1.7 的 Development 独立展示直接调用原生控件与绘制列表，仅用示例数据 | 已有可拔除样例，可用于视觉与交互验收；尚未成为正式界面通用设施 |

正式图表调用链已从源码确认：芯片详情渲染器 → 雷达／折线渲染器 → 图表画布与绘制上下文 → 几何绘制器 → Unity 风格 GL 接口 → 1.7 兼容后端 → ImGui 绘制列表。

**现有图表颜色适配说明了什么。** `GL.End`（结束即时提交）从当前材质读取纹理，再把已收集的带色顶点交给后端；后端三角形路径使用顶点颜色，没有把纯色材质颜色自动乘进去。BDP 现有 1.7 分支已经在三角形提交开始时显式调用 `GL.Color(color)`（设置顶点颜色），结束时恢复白色；1.6 保留原来路径。这是具体接口语义差异，不能笼统归结为“旧界面不能用”。本轮只核查现有代码，没有再次修改此修正。

**现有原生展示的实际边界。** `Source/BDP.Development/UI/ImGuiShowcase`（源码目录）包含原版窗口外壳、原生控件、六类绘制分区和窗口局部鼠标输入桥。展示支持颜色、透明叠加、渐变、形状、凹多边形、曲线、抗锯齿对照、假数据图表、裁切、拖点和动画；独立引用仅对 1.7 生效。它复用游戏帧，不自行建立或切换上下文，不额外调用开始／提交帧。

兼容事件派发器处理的是 Unity 风格输入事件，并未在该路径自动向原生 ImGui 鼠标队列投递输入。当前展示在窗口输入阶段转交鼠标位置、按键、滚轮，并消费已接管事件，防止原版窗口再次拖动；失去输入权或关闭时释放接管的按键。展示没有通用键盘输入桥。既有研究记录记载用户曾看到真实游戏绘制但发现鼠标无响应，随后已做局部修正；本轮没有重新完成游戏内复测，不能把源码存在等同于当前实测通过。

**将来直接使用时的必要约束。**

1. 复用游戏上下文和帧生命周期，在适当绘制阶段提交；原版同一帧可能多次回调，不能每次都重复创建原生控件。
2. 原版逻辑坐标、窗口局部坐标与原生物理像素必须明确转换，界面缩放只应用一次。
3. 窗口栈决定谁获得输入；鼠标、键盘、文字和输入法要按实际阶段衔接，避免点穿、重复处理和拖出窗口后无法释放。
4. 原生控件焦点和原版焦点不自动相同；更换整个控件系统需单独验证键盘和输入法。
5. 窗口绘制列表、背景列表和前景列表的层次不同。绘制裁切、视觉覆盖与输入命中是分别需要检查的事项。
6. 成对恢复字体、样式、裁切、纹理与绘制标记，避免污染游戏共享上下文。
7. 使用游戏自带绑定及原生库，不自行替换原生动态库或随意混入另一套绑定；原生结构布局和库版本必须匹配。
8. 按 1.6／1.7 独立编译引用，不能把 1.7 库复制到 1.6。若仅优化 1.7 几何，应保持差异局限于绘制入口。
