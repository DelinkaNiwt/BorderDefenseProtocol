# 旧 BDP 主攻击投影与触发体时序补偿（第一版）

## 目的

这份记录专门回答四个问题：

- 旧 BDP 的“主攻击”到底是谁决定的
- `CompTriggerBody` 在攻击投影里承担什么角色
- `Verb_BDPProxy` 到底是不是一层真业务
- 为什么 `TickChipVerbs()` 是旧 BDP 自动攻击稳定性的关键点

## 一、先下结论

### 1. 旧 BDP 的“主攻击投影”是明确规则结果，不是临时猜测

它不是：

- UI 上哪个按钮排前面
- 当前刚好哪个 Verb 不为空
- 自动攻击时再临时现算

它的真实形成链是：

1. 每侧芯片先产生本侧攻击表达
2. `DualVerbCompositor` 按组合规则合成结果
3. `CompTriggerBody` 手动创建并缓存这些 Verb
4. `GetPrimaryChipVerb()` / `GetPrimaryMeleeChipVerb()` 对外提供默认投影

所以“主攻击”在旧版里已经是规则层产物。

### 2. `CompTriggerBody` 在这里是缓存 owner + 对外投影入口

它不是主攻击规则本身的定义者，
但它是：

- 主攻击缓存的持有者
- 自动攻击桥接的对外查询口
- 芯片 Verb 时序补偿的执行者

也就是说：

- 规则形成在合成器
- 对外暴露和运行时补偿在触发体

### 3. `Verb_BDPProxy` 不是业务 owner，只是原版自动攻击桥

它做的事很克制：

- 同步主远程攻击的 `verbProps`
- 让原版 AI 射程判断成立
- 把 `TryStartCastOn()` 委托给真正的主芯片远程 Verb

它不负责：

- 决定谁是主攻击
- 自己开火
- 自己维护 warmup / burst / cooldown

### 4. `TickChipVerbs()` 是“脱离 VerbTracker 之后必须补回来的时序链”

这是旧 BDP 自动攻击能稳定工作的关键点之一。

因为芯片 Verb 不进 `AllVerbs` 之后，
如果不手动补 tick：

- warmup / cooldown 不会正常推进
- burst 第 2 发以后会卡住

## 二、`DualVerbCompositor` 的真实地位

### 1. 它是纯规则合成器，不持有运行时状态

代码注释和实现都很明确：

- 它是纯静态工具
- 不保存运行时数据
- 输入是左右两侧已有的 `VerbProperties`
- 输出是合成后的完整 `VerbProperties` 列表

这点很重要，因为它说明旧版已经有一点“规则层”和“运行时层”分离的意识。

### 2. 它输出的不只是一个主攻击，而是整套攻击表达

根据已读代码，它会产出：

- 左手独立攻击 Verb
- 右手独立攻击 Verb
- 双手合成主攻击 Verb
- 混合模式下的近战 / 远程分配结果

也就是说它的任务不是：

- “挑一个默认”

而是：

- “先把当前这套可用攻击表达完整构出来”
- “其中某个再被标记为默认主表达”

### 3. `isPrimary=true` 是这里的核心标记

它在这里被明确写到合成结果里。

这就解释了为什么后面的 `CompTriggerBody` 可以靠缓存直接提供默认投影：

- 因为规则在合成时就已经定下来了

### 4. 组合规则再次得到代码确认

当前已确认：

- 单侧有值：
  - 该侧 Verb 直接设为主攻击
- 近战 + 近战：
  - 左、右独立近战 Verb
  - 再加一个双近战主攻击 Verb
- 远程 + 远程：
  - 左、右独立远程 Verb
  - 再加一个双远程主攻击 Verb
- 近战 + 远程：
  - 两个独立 Verb
  - 远程那侧为主攻击

这再次说明：

- “主攻击投影”不是 UI 层行为
- 它是组合规则产物

## 三、`CompTriggerBody` 在这条链里的真实作用

### 1. 它负责把“规则结果”变成“运行时可用的真实 Verb 实例”

`RebuildVerbs()` 的实际流程是：

1. 先重建只包含占位内容的 `VerbTracker`
2. 给占位 Verb 重新绑定 `caster`
3. 调 `CreateAndCacheChipVerbs()`
4. 手动创建芯片 Verb
5. 把芯片 Verb 缓存到各字段
6. 再同步 `ProxyVerb`

关键点：

- 芯片 Verb 不进 `VerbTracker.AllVerbs`
- 而是手动创建后缓存在 `CompTriggerBody`

这就让触发体变成了：

- 芯片 Verb 的运行时缓存 owner

### 2. 它对外提供了两个很关键的默认查询口

一个是：

- `GetPrimaryChipVerb()`

规则是：

- 双手合成攻击优先
- 再看左右手中 `isPrimary=true` 的那一侧
- 最后右手优先兜底

另一个是：

- `GetPrimaryMeleeChipVerb()`

规则是：

- 双近战时优先双近战 Verb
- 否则优先带 `isPrimary=true` 的近战侧
- 再退到任意一侧近战

这两个接口非常重要，因为它们说明：

- 旧版已经把“对外默认投影”收口成明确 API

### 3. `CompTriggerBody` 也是 `ProxyVerb` 的同步入口

`SyncProxyVerb()` 逻辑很克制：

- 先看当前主攻击
- 如果没有主远程，或主攻击是近战
  - 就把 `proxyVerb` 清空
- 如果当前主攻击是远程
  - 就创建或复用一个 `Verb_BDPProxy`
  - 再从主远程 Verb 同步关键 `verbProps`

这说明：

- `ProxyVerb` 并不是独立长期存在的系统核心
- 它只是当前“主远程投影”的一个外接桥

## 四、`Verb_BDPProxy` 的真实边界

### 1. 它只负责让 RimWorld 原版自动攻击系统“看见”远程芯片攻击

它会同步：

- `range`
- `minRange`
- `burstShotCount`
- `ticksBetweenBurstShots`
- `warmupTime`
- `defaultCooldownTime`
- `defaultProjectile`
- `soundCast`
- `muzzleFlashScale`

这说明它做的核心事只有一件：

- 把真正主远程攻击的“对外表面参数”复制出来给原版 AI 看

### 2. 它故意不是主 Verb

这里有两个关键标志：

- `verbProps.isPrimary = false`
- `verbProps.hasStandardCommand = false`

这非常重要，说明旧版明确在防止：

- 被原版 PrimaryVerb 路径误拾取
- 被原版命令生成路径误拾取

### 3. 它自己不执行开火

`TryStartCastOn()` 里它只是：

- 重新拿一次 `ownerTriggerComp.GetPrimaryChipVerb()`
- 确认还是远程主攻击
- 然后直接委托给那个真正的芯片 Verb

所以：

- `ProxyVerb` 只是桥
- 真正进入 warmup / burst / TryCastShot 的仍是主芯片远程 Verb

## 五、`TickChipVerbs()` 为什么这么关键

### 1. 芯片 Verb 脱离 `AllVerbs` 后，原版 tick 链天然断掉

旧版这里已经明说：

- 引擎只会自动 tick `VerbTracker.AllVerbs`
- 芯片 Verb 不在里面

所以如果不额外处理：

- `VerbTick()` 根本不会跑

### 2. `TickChipVerbs()` 实际补回了整套芯片 Verb 的时序推进

它会统一 tick：

- 左手主攻击
- 右手主攻击
- 双手主攻击
- 左右双手副攻击
- 组合技主副攻击

这点很关键，因为旧版不是只补“当前正在自动攻击的那个 Verb”。

它补的是：

- 触发体上所有可能处于 warmup / cooldown / burst 过程中的芯片 Verb

### 3. 它还做了同 tick 去重

字段：

- `lastChipVerbTickedTick`

逻辑：

- 同一 tick 已经推进过，就直接 return

这很重要，因为旧版同时存在两种 tick 来源：

- `Patch_VerbTracker_VerbsTick`
- 某些 JobDriver 自己手动 `VerbTick()`

没有这个去重，时序就会炸。

## 六、从这条链可以看到旧版一个很真实的设计取舍

### 1. 为什么旧版不让芯片 Verb 直接留在 `AllVerbs`

因为那会带来两个实际副作用：

- 被原版近战选择池乱选
- 被原版默认命令路径乱捡

所以旧版选择：

- 先把它们彻底脱出去

### 2. 一旦脱出去，就必须自己补回三样东西

- 默认攻击投影
- 自动攻击桥接
- per-tick 时序推进

旧版在这三件事上都给了明确做法：

- 默认攻击投影：
  - `DualVerbCompositor` + `GetPrimaryChipVerb()`
- 自动攻击桥接：
  - `ProxyVerb` + melee 注入 patch
- 时序推进：
  - `TickChipVerbs()`

这条因果链非常重要，二次重构不能丢。

## 七、这一层暴露出的结构问题

### 1. 规则层和运行时层虽然已经有分离意识，但仍旧深度汇聚到触发体

现在能看到：

- 合成规则在 `DualVerbCompositor`
- 运行时缓存在 `CompTriggerBody`
- 自动桥接也在 `CompTriggerBody`
- tick 补偿也在 `CompTriggerBody`

这说明触发体在这里仍然很重。

### 2. `GetPrimaryChipVerb()` 仍然带有运行时兜底逻辑

比如：

- 右手优先兜底

这说明旧版虽然已有主攻击规则，
但“规则层结果”和“运行时安全回退”还没有完全拆干净。

### 3. `TriggerBodyQueries` 更像局部减重复工具，不是统一协议层

它做的主要是：

- 减少长查询链重复
- 提供双侧配置和槽位查询

它有用，但不能把它误认为“已经形成统一业务层”。

## 八、对二次重构的直接启发

### 1. 主攻击投影必须单独成为一个明确概念

因为它会同时服务：

- 自动远程桥接
- 自动近战桥接
- 主按钮默认入口
- 外部系统默认攻击识别

这说明它不是某个字段顺便算出来就行，而是必须被清楚建模。

### 2. 代理桥和真实攻击 owner 必须严格分开

`Verb_BDPProxy` 这个边界其实是对的：

- 桥只负责被原版识别
- 真业务仍在真实芯片 Verb

这个边界应该保留。

### 3. 一旦选择不把表达直接挂进原版集合，就必须设计完整补偿链

也就是：

- 入口补偿
- 时序补偿
- 默认投影补偿

不能只切断原版链，不补全。

### 4. 触发体不该继续做这么多层职责 owner

旧版这里说明：

- 它已经成为
  - 缓存 owner
  - 对外查询口
  - 自动桥接组织者
  - tick 补偿执行者

二次重构时，这几件事应尽量拆出更清晰的边界。

但注意：

- 不能因此脱离 RimWorld 宿主现实
- 这些拆分出来的东西最终仍要能挂回 `CompTriggerBody` 这个宿主入口
