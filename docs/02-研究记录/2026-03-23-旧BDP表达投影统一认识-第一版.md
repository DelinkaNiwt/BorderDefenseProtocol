# 旧 BDP 表达投影统一认识（第一版）

## 目的

这份记录要把前几轮分散读到的东西统一起来，回答一个更上位的问题：

- 旧 BDP 里，“普通芯片表达”和“组合第三表达”是不是其实遵循同一类思路

结论要基于代码事实，而不是表面业务名词。

## 一、先下结论

### 1. 旧 BDP 的一个重要真实结构是：先生成表达，再投影到 RimWorld 宿主通道

当前已确认的宿主通道至少有：

- `Verb`
- `Ability`
- `Hediff`
- `Passive` 外部检测通道

这里最重要的不是“有哪些芯片名”或“有哪些技能名”。

更重要的是：

- 旧 BDP 已经在很多地方自然形成了“表达 -> 宿主投影”的思路

### 2. 普通芯片表达和组合第三表达，本质上只是两个不同来源

普通芯片表达来自：

- `ChipMode.effectClasses`
- `IChipEffect`

组合第三表达来自：

- `ComboEffectDef`

二者共同点是：

- 都不是先假设自己属于某个固定系统
- 而是在成立后再投影到具体宿主通道

### 3. 这比“攻击系统/技能系统/状态系统各管各的”更接近旧 BDP 真实内核

因为代码里能看到：

- 同一个触发体激活流程里，会统一调用 effect 激活
- 同一个组合效果更新流程里，会统一激活不同类型组合表达

这说明旧 BDP 后期的一个真实方向已经是：

- “表达类型统一入口，宿主投影后置决定”

## 二、普通芯片表达：`IChipEffect`

### 1. 普通芯片的统一协议是 `IChipEffect`

接口只有四件事：

- `Activate`
- `Deactivate`
- `Tick`
- `CanActivate`

而且注释明确约定：

- 无状态
- 幂等
- 无参构造

这很重要，因为它说明普通芯片表达的核心不是某个具体业务，而是：

- 一个统一激活协议

### 2. 普通芯片表达的来源是 `ChipMode.effectClasses`

`CompTriggerChip.GetModeEffects(modeIndex)` 会：

- 读取当前形态 `ChipMode`
- 遍历 `effectClasses`
- 用 `Activator.CreateInstance(effectType)` 实例化
- 缓存到 `modeEffectCache`

这说明普通芯片表达的形成过程是：

- 芯片当前形态先声明有哪些表达类型
- 运行时再实例化出对应表达对象

也就是说，普通芯片在这里不是“我是武器芯片，所以走武器系统”。

而是：

- “我这个形态当前携带哪些表达”

### 3. 普通芯片表达已经明确投影到多种宿主通道

当前已确认：

#### `VerbChipEffect`

投影到：

- `Verb`

做法：

- 往 `CompTriggerBody` 的按侧 Verb 存储里写数据
- 再触发 `RebuildVerbs()`

#### `AbilityChipEffect`

投影到：

- 原版 `Ability`

做法：

- `GainAbility`
- `RemoveAbility`

#### `HediffChipEffectBase`

投影到：

- `Hediff`

做法：

- 添加 / 更新 / 移除 Hediff
- 通过 Severity 表达形态或叠加层数

#### `PassiveChipEffect`

投影到：

- 外部检测通道

做法：

- 自己激活时不直接干预
- 由其他系统检测“芯片是否激活”后再触发实际行为

这说明普通芯片表达本身已经不是单一攻击模型。

## 三、普通芯片表达的统一激活入口

### 1. 入口在 `CompTriggerBody.Activation`

当某芯片被激活时：

- 先结算激活成本
- 注册持续消耗
- 取当前形态所有 `effects`
- 在 `WithActivatingContext` 里逐个 `effect.Activate(...)`
- 再把 `slot.isActive = true`
- 最后 `UpdateComboEffects(pawn)`

关闭时则对称地：

- 注销持续消耗
- 逐个 `effect.Deactivate(...)`
- `slot.isActive = false`
- 最后 `UpdateComboEffects(pawn)`

这条链很关键，因为它说明：

- 普通芯片表达不管最后投影到哪条宿主通道
- 它们先共享一个统一激活流程

### 2. 组合第三表达是在普通表达之后更新的

顺序上很明确：

- 先完成本次芯片表达激活 / 关闭
- 再更新组合第三表达

这再次说明组合技不是普通表达的子步骤，
而是：

- 由当前普通表达状态变化所派生出的额外表达层

## 四、组合第三表达：`ComboEffectDef`

### 1. 它和普通 `IChipEffect` 不是一套接口，但思路相同

普通芯片：

- 来源是 `ChipMode.effectClasses`
- 协议是 `IChipEffect`

组合第三表达：

- 来源是 `DefDatabase<ComboEffectDef>`
- 协议是 `ActivateEffect / DeactivateEffect`

虽然接口不同，
但真正的结构相似点在于：

- 都先形成表达
- 再投影到宿主通道

### 2. 当前组合第三表达也已明确投影到多种通道

当前已确认：

#### `ComboVerbDef`

投影到：

- `Verb`

做法：

- 创建 `comboAttackVerb / comboSecondaryVerb`
- 再通过自定义攻击按钮显示

#### `ComboAbilityDef`

投影到：

- 原版 `Ability`

做法：

- `GainAbility`
- `RemoveAbility`

#### `ComboEffectType.Hediff`

当前状态：

- 枚举已预留
- 说明设计方向已经明确承认该通道

### 3. 组合第三表达的统一入口是 `UpdateComboEffects()`

它会：

- 看当前左右手激活芯片
- 遍历所有 `ComboEffectDef`
- 匹配则激活，不匹配则撤销

这和普通芯片激活流程在结构上非常像：

- 都是统一入口
- 都是逐个表达激活 / 撤销
- 都允许不同表达投影到不同宿主通道

## 五、这两套东西的本质关系

### 1. 普通芯片表达是第一层

来源：

- 单个芯片当前形态

### 2. 组合第三表达是第二层

来源：

- 左右芯片当前组合关系

### 3. 二者共享的是“表达投影思想”

不共享的是：

- 来源
- 触发条件
- 具体接口

所以更准确的理解应该是：

- 旧 BDP 不是只有一个统一协议已经完全做成
- 但它已经自然长出了一个统一方向：
  - “表达来源不同，但都要投影回 RimWorld 宿主通道”

## 六、读档恢复也证明这些表达不是临时 UI 产物

`CompTriggerBody.Lifecycle` 里读档后会：

- 对所有激活槽位重新取 `effects`
- 再逐个 `effect.Activate(...)`
- 之后再 `UpdateComboEffects(pawn)`

这意味着：

- 普通表达和组合第三表达都被当成真实运行状态的一部分
- 不是只在按钮生成时临时算一下

这很关键，因为它说明这些表达是：

- 真运行时表达
- 不是单纯表现层数据

## 七、当前旧 BDP 这里的成熟点和不成熟点

### 1. 成熟点

- 已经有统一“表达激活/撤销”思路
- 已经有多宿主通道投影
- 已经有普通表达和组合表达两层
- 已经贴 RimWorld 宿主现实

### 2. 不成熟点

- 普通表达和组合表达还不是同一个抽象协议
- `Passive` 仍是“外部系统自己检测”的空壳通道
- 组合表达的旧攻击逻辑和新统一入口仍并存
- 很多最终 owner 仍堆在 `CompTriggerBody`

所以这里不能直接说旧版已经完成了“完美统一层”。

更准确地说是：

- 它已经摸到了正确方向
- 但没有把它收束到一条真正干净的统一骨架

## 八、对二次重构的直接启发

### 1. “攻击系统”不该再被当成唯一中心

更上位的概念应当是：

- 表达系统

攻击只是其中一种投影。

### 2. 组合技应该和普通芯片表达放进同一理解框架

也就是：

- 普通芯片表达：来自单芯片形态
- 组合第三表达：来自双芯片组合
- 二者最后都投影到 RimWorld 宿主通道

### 3. 宿主通道必须继续贴 RimWorld

当前代码事实支持的通道已经很明确：

- `Verb`
- `Ability`
- `Hediff`
- 外部被动检测

二次重构不该发明一个脱离 RimWorld 的新宿主世界。

### 4. 统一层应该统一“表达来源与投影规则”，而不是统一成一个抽象过头的大执行器

因为：

- `Verb`、`Ability`、`Hediff` 的宿主规律本来就不同
- 真正该统一的是：
  - 表达何时成立
  - 表达投影到哪条宿主通道
  - 生命周期何时激活、撤销、恢复
