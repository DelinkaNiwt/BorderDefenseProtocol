# BDP 现有能力的原版接口使用核查

日期：2026-10-15。沿用本次持续研究已确认的 1.6、1.7 范围。对象为当前工作区主模组；没有把已部署程序集或旧运行时快照视为最新工程真相。本轮仅调查和记录，未修改功能、构建或部署。

## 结论

**常规能力授予、施放和触力能扣费已有共同体系；特殊施放的基础记账、冷却跨卸载规则和中断收尾尚未完全收口。** 不能说没有利用原版，也不能说全部能力已能通过同一组接口安全操纵状态。

当前公共正式定义有八个 Ability（能力）：弹射砍击、变色龙、战斗体短距跳跃、风刃远程斩击、蚱蜢、光魂推进、皇室契约、旋空弧月。七个配置了独立能力冷却，五个配置了表达触力能成本组件；八个都未声明原版次数、逐次恢复或能力冷却分组。

没有使用次数和装填接口本身不是缺陷：当前需求以施放冷却、触力能和人物永久资格为主。皇室契约的一次性资格保存为人物契约状态，比“能力剩一次”更能表达基因移除／重建后仍不能重新缔约的业务含义。

## 已形成体系的部分

| 环节 | 当前实现 | 判断 |
|---|---|---|
| 动态能力授予／移除 | 表达同步器调用原版获得、查找、移除能力入口，并读取角色全部能力汇总表 | 已接入原版管理器，不另建按钮假装技能 |
| 普通施放 | 通用 BDP 施放动作在扣费后继续原版实际施放，再进入能力激活和效果组件 | 主干复用正确 |
| 触力能使用条件 | 同一成本组件接入可施放、按钮禁用、目标确认、人工智能检查，实际扣费前再检查 | 已有较完整的共同入口 |
| 触力能扣除 | `BdpAbilityTrionCostCommitter.TryCommit`（能力成本提交）调用成本组件，后者使用 `ITrionCommands`（触力能命令接口） | 没有直接在每个效果里随意改资源字段 |
| 组合技使用条件 | 通用条件组件从绑定表达结果解析组合技条件 | 与扣费和冷却分责 |
| 常规冷却及动作恢复 | 能力定义配置原版能力冷却；旋空弧月和光魂推进还使用原版动作恢复时间 | 分清角色动作停顿和技能冷却 |
| 特殊跳跃 | 战斗体短跳继承原版能力跳跃；蚱蜢和光魂推进继续使用原版作业、能力和飞行对象扩展点 | 特殊业务有扩展，不等于重写整套能力 |
| 变色龙跨卸载冷却 | 记录原版实际冷却的剩余及总时长，重新挂载时通过原版启动冷却恢复，并存入游戏组件 | 解决了临时能力对象被移除后冷却丢失的具体问题 |

- `Source/BDP/Core/Abilities/BdpVerb_CastAbility.cs`：普通实际施放复用原版。
- `Source/BDP/Core/Abilities/CompAbilityEffect_BdpTrionCost.cs`：64、82、112、152、183 行分别接入可用性、按钮、目标、人工智能与实际扣费。

## 缺口一：远程能力宿主只复用部分原版生命周期

位置：`Source/BDP/Core/Abilities/BdpVerb_AbilityShoot.cs:105`。

当前风刃远程斩击使用的射击宿主流程为：

```text
原版选择目标与前摇
  → 构建 BDP 远程发射计划
  → 共同触力能扣费
  → 发射投射物
  → 直接启动能力冷却
```

它没有调用基础实际施放或 `Ability.Activate`（能力激活）。直接启动冷却发生在 138 行。因此原版激活前处理中的扣次数、按次数决定冷却、共享组通知、装备能力使用通知，以及常规效果组件执行，不会由该流程自动完成。

这是一项**已确认的原版接口覆盖缺口**，不是证据充分的“当前风刃已经坏了”：当前风刃没有次数、共享冷却组和普通业务效果组件。自有远程协议有实际用途，不能为了形式统一直接叠加第二次发射或第二次扣费。

攻击成功通知已经专门处理：`Source/BDP/Patches/Patch_Verb_TryCastNextBurstShot_BdpAttackActionSuccess.cs:33` 明确解释该宿主不走能力激活，并在原版动作成功收尾后发布能力成功通知。不能误报为完全没有成功通知。

实际影响是：给这个共用射击宿主新增原版次数、分组或普通效果组件，不能仅配置定义就认定它们会按原版生效。

## 缺口二：冷却恢复和重置尚未形成共同规则

位置：`Common/Content/Defs/AbilityDef/Chameleon.xml:52`；同步器 254、387 行；`AbilityReleaseCooldownService.cs:66`。

只有变色龙配置了来源级冷却组件和冷却键。表达能力不再成立时，同步器移除原版能力对象；重新成立后通过原版获得能力入口创建新对象。没有来源级冷却配置的表达能力，这条路径没有恢复旧对象剩余冷却的记录。

```text
变色龙：移除能力 → 账本仍保存冷却 → 重建后恢复剩余时间
其它未配置者：移除能力 → 旧对象不再保存 → 重建为新的能力对象
```

**已确认的是状态保留行为不同；是否应统一，是待确认的业务规则。** 不能在本次只读核查里擅自认定所有能力都必须使用同一账本。具体玩家操作是否触发此流程，还应通过芯片切换、组合条件变化等游戏内情形验证。

另外，来源级冷却组件的可用性检查还会读取账本。原版 `ResetCooldown`（解除能力冷却）不会清除这个额外记录；现有账本提供查询、启动／延长、保存和到期移除，没有统一主动清除或缩短入口。因此若其他地方需要“立即恢复变色龙”，仅调用原版解除冷却还不够。

来源级账本也不是所有次数模式都能直接套用：其组件在账本有剩余等待时统一禁止施放，不能未经设计就用于“有剩余次数仍能施放”的逐次恢复能力。

## 缺口三：链式弹射的失败出口漏累计冷却收尾

位置：`Source/BDP.Content/Grasshopper/CompAbilityEffect_GrasshopperJump.cs:122`、167、217 行。弹射砍击的效果继承这个组件，因此同样受影响。

首段施放经过正常能力激活，会先启动一次基础冷却。后续段在前一段落地回调中独立扣触力能；扣除失败直接退出。累计冷却只在没有后续路径点的成功分支中调用。

```text
已完成首段和第二段
  → 准备第三段
  → 触力能不足
  → 直接退出
  → 没有累计冷却结算
```

这是**实现错误（代码控制流已确认，游戏内现象待复现）**：中途资源不足退出不会走正常完成分支，保留的是首段基础冷却状态，不是按多段使用收束的累计冷却。它来自共享业务代码，不能归为纯 1.7 版本差异。

另一个已确认的时序差异：注释写“最终段落地后累计冷却”，但调用在最终段飞行器生成并放入地图之前，实际是最终段起跳时。该落点究竟应以起跳还是落地为准仍需确认需求，不能仅按注释擅改。

后续段资源入口同样比首段更薄：它直接消耗单段成本，没有复用首段完整的最低门槛检查；触力能命令对象缺失时还返回成功。这里只记录规则差异，不推断当前常规游戏一定能触发这些异常状态。

## 最小下一步

1. 优先复现并收束蚱蜢／弹射砍击中断时的累计冷却结算，明确按已执行段数还是计划段数计费计时，以及起跳／落地时点。
2. 明确能力被移除重建后冷却是否应继续，再决定哪些定义需要保留记录；不要直接给全部能力加账本。
3. 收紧远程射击宿主的能力支持约定：哪些原版能力机制应支持，哪些暂未使用。实际有需求时再最小补齐基础记账，不新建全游戏能力框架。

## 验证边界

- 自研模组以当前工作区源码与公共正式定义为准；逐一解析八个能力定义，检查次数／冷却／动作／组件配置，并追踪共同入口和特殊出口。
- 读取 1.6、1.7 真实程序集的原版能力激活前处理，扣次数、冷却分支和通知逻辑一致。原版获得／移除能力确实创建／移除实例，不自行为已删除对象保留状态。
- 本次涉及的 BDP 能力主体、同步器和链式弹射使用共享源码，没有相应版本条件分支。以上缺口不以“只在新版本报错”推断版本归因。
- 1.6：未编译、未实测。1.7：未编译、未实测。没有把静态控制流结论写成已完成的游戏内复现，也没有验证已部署程序集与工作区完全一致。
- 本轮没有修改功能或运行测试脚本；不以历史源码字符串断言代替实际生命周期验证。
