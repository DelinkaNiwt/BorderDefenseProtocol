# 旧 BDP 远程发射编排与原版主链关系（第一版）

## 目的

这一轮要澄清的不是“旧 BDP 有没有很多自定义远程逻辑”。

真正要澄清的是：

- 它到底改了原版远程链的哪一层
- 哪些地方是在做宿主兼容修正
- 哪些地方是在做双手 / 齐射 / 引导的业务编排
- 哪些地方仍然坚持走原版的命中、掩体、LOS、投射物发射主链

用户前面已经明确要求：

- 标准远程必须是真原版链，不是假模仿

所以这一轮很关键。

## 一、先下结论

### 1. 旧 BDP 的远程核心，不是重写原版射击规则，而是“在原版射击链外面包一层发射编排”

从 `Verb_BDPRangedBase` 和 `Verb_BDPDual` 现在能确认：

- 原版真正负责的那部分仍尽量保留
  - LOS 检查
  - forced miss
  - wild miss
  - cover miss
  - 投射物 `Launch`
  - `ShotsFired` 记录
- BDP 主要改的是外层：
  - 当前到底是哪一侧发
  - 一次发一颗还是一批
  - 用哪一侧的 projectileDef
  - 用哪一侧的音效 / 芯片身份 / 资源消耗
  - 发射原点是否矫正到武器枪口

所以更准确的说法是：

- 旧 BDP 在“编排层”自定义很强
- 但在“标准远程命中主链”上，仍然尽量贴原版

### 2. `TryCastShotCore()` 的本质，是“复制原版远程主链并替换少数关键输入”

它做的最关键替换有三个：

- `equipmentSource` 尽量换成芯片 `Thing`
- `drawPos` 尽量换成枪口位置
- `Projectile` / `target` / 引导路径由外层编排提前准备好

除此之外，后面的：

- miss
- cover
- intended hit
- `Projectile.Launch(...)`

大体都还是原版风格。

### 3. 双手 / 齐射 / 引导这些复杂性，主要发生在“TryCastShotCore 之前”

`Verb_BDPDual` 真正做的是：

- 初始化左右剩余发射数
- 选择当前是哪一侧出手
- 判断这一侧是逐发还是齐射
- 临时切换当前 projectileDef
- 必要时恢复 `Thing` 目标
- 决定这一次是否带路径数据

最后每一发真正落地时，
仍然是回到：

- `TryCastShotCore(...)`

也就是说：

- 双侧复杂性被压在发射调度层
- 没直接把原版命中逻辑撕碎重写

## 二、`Verb_BDPRangedBase` 的真正职责

### 1. 它是 BDP 远程的“宿主兼容基类”

这个类最重要的价值不是“实现了某个具体武器效果”，
而是给所有 BDP 远程表达提供了一层共同宿主：

- 统一的上下文快照
- 统一的 ShotPipeline 初始化
- 统一的锚点 / 自动绕行准备
- 统一的发射原点修正
- 统一的原版远程链调用

所以它更像：

- BDP 远程表达进入 RimWorld 原版远程系统的桥

### 2. `ExecuteFire()` 只是外层入口，真正发射落点还是 `TryCastShotCore()` / `LaunchProjectile()`

当前代码里同时存在：

- `LaunchProjectile(...)`
- `TryCastShotCore(...)`

两者本质都在做同一类事情：

- 复制原版 `Verb_LaunchProjectile.TryCastShot()` 的核心逻辑

其中 `TryCastShotCore()` 明显是当前主用版本，
因为双手发射、齐射循环都是回到它。

这说明旧版的关键思路是：

- 不让子类各自散着复制原版发射逻辑
- 而是尽量汇到一个共享发射核心

### 3. `equipmentSource` 替换成芯片，不是小修饰，而是重要兼容点

旧代码里明确写了：

- `Thing equipmentSource = chipEquipment`

这很关键。

因为这样可以让：

- 战斗日志
- 原版或其它系统读取装备来源

更接近“真正攻击的是当前芯片”，
而不是永远显示触发体。

这和前面已经确认过的“主攻击投影”“显示投影”是同一路数：

- 触发体是承载器
- 当前激活芯片才是对外表达主体

## 三、原版远程主链，哪些被保留了

### 1. LOS 仍然是硬门槛，只是引导模式下目标换成了首锚点

代码不是取消 LOS，
而是做了更符合引导弹本质的重定向：

- 普通模式：检查 caster 到目标
- 引导模式：检查 caster 到第一锚点

这点非常重要。

因为它说明旧 BDP 不是为了实现复杂功能就放弃原版基本战斗约束，
而是重新解释“这次真正需要直视的对象是谁”。

### 2. forced miss / wild miss / cover miss / intended hit 这条链基本保留

`TryCastShotCore()` 里可以清楚看到：

- `ForcedMissRadius`
- `ShotReport.HitReportFor(...)`
- `GetRandomCoverToMissInto()`
- `PassCoverChance`
- `ProjectileHitFlags`
- `proj.Launch(...)`

这些全都还是原版远程攻击的核心语言。

因此旧 BDP 对标准远程的处理，并不是：

- 自己先算好“命中没有”
- 然后只播一个表演

而是：

- 仍把结果交给原版投射物命中链

### 3. 记录、原版装备组件通知也被保留

例如：

- `CompChangeableProjectile.Notify_ProjectileLaunched()`
- `CompApparelVerbOwner_Charged.UsedOnce()`
- `ShotsFired`

这进一步证明：

- 旧版虽然替换了表达主体
- 但没有忘记原版宿主周边的副作用链

## 四、旧 BDP 真正改动最大的地方：发射编排层

### 1. `TryCastShot()` 被重写，不是为了重写原版命中，而是为了把发射调度权拿回来

原版 `Verb_Shoot.TryCastShot()` 只知道：

- 发一颗

但 BDP 需要支持：

- 单侧逐发
- 单侧齐射
- 双侧交替
- 双侧同时齐射
- 一侧逐发一侧齐射
- 引导路径只对部分侧生效

这些都不是原版一个标准 `Verb_Shoot` 能直接表达的。

所以 BDP 重写这个入口是有必要的。

但它重写后做的是：

- 先调度
- 再落回共享发射核心

这点必须分清。

### 2. `Verb_BDPDual` 是“编排器”，不是“命中系统”

它负责的关键事情有：

- `InitDualBurst()` 初始化双侧状态
- `GetCurrentShotSide()` 决定当前轮到哪侧
- `FireBothSimultaneous()`
- `FireSideSimultaneous()`
- `FireSideSequential()`
- `WithProjectileSwap(...)` 临时切换当前侧投射物
- `WithTargetRestore(...)` 在非路径侧恢复 `Thing` 目标

这说明双手系统真正复杂的地方是：

- 调度
- 状态保存
- 输入切换

而不是：

- 每颗子弹重新发明命中规则

### 3. 齐射的本质，是“单次逻辑里循环发多颗”

`FireVolleyLoop(...)` 明确说明：

- 在一次 `TryCastShot` 里
- 循环调用 `TryCastShotCore(...)`
- 每次只改 `shotOriginOffset`

这说明旧版对齐射的理解是：

- 外层是一次攻击表达
- 内部是多颗标准发射

而不是另做一套“散弹专用命中系统”。

## 五、`shotOriginOffset` 的意义：只改视觉与发射起点，不改标准命中世界

### 1. 齐射散布不是拿来改命中判定的

代码里已经写得很清楚：

- `shotOriginOffset` 只影响弹道视觉起点
- LOS / cover 仍用 `caster.Position`

这非常关键。

因为它说明旧版在这里做了一个明确边界：

- 可以让多发子弹从略微不同的位置飞出
- 但不能因此破坏原版对掩体、视线的主体判断

### 2. 枪口位置和齐射散布是分层叠加的

当前代码有两种写法痕迹：

- 一处是枪口位置后不再叠加 `originOffset`
- 一处是枪口位置后再叠加 `shotOriginOffset`

这说明旧版这里可能经历过演化。

但无论哪种写法，核心认识都很清楚：

- 枪口位置是“武器真实发射基准”
- 齐射散布是“围绕该基准的小范围偏移”

后面如果继续深入测试代码或实际表现，
要特别留意这里最后哪条路径才是实际生效路径。

## 六、引导路径与目标锁定，说明旧版很在意“看起来打谁”和“实际算谁”一致

### 1. 有锚点时会锁定 `currentTarget` 为 Cell，避免 Thing 追踪导致幽灵命中

这不是表现补丁，而是很实在的规则修正。

说明旧版已经意识到：

- 如果目标是 `Thing`
- 引导路径又是按一组锚点飞
- 那中途继续跟踪活动目标可能会让结果变味

所以它主动把目标锁到格子。

### 2. 双侧模式下，路径并不是默认同时作用于两边

`Verb_BDPDual` 里很明确：

- `currentShotHasPath`
- `leftHasPath`
- `rightHasPath`

都按当前发射侧来区分。

这说明旧版对双手路径系统的真实理解是：

- 路径是“当前这一次发射是否带路径”的属性
- 不是“只要本次双手攻击里有路径，所有子弹都强制套路径”

这点是很细但很重要的业务事实。

### 3. `WithTargetRestore()` 暴露了一个很关键的边界补偿

有手动锚点时：

- 引导侧要用锚点 / Cell 目标
- 非引导侧仍应尽量对真实 `Thing` 目标开火

所以旧版做了：

- 临时恢复 `savedThingTarget`
- 发完后再回到最终锁定的 Cell

这不是优雅结构，
但它说明旧业务里很明确存在这条混合要求。

## 七、Trion 消耗也被纳入了“统一层”，不是散在每种子弹行为里

从 `Verb_BDPDual` 可见：

- 发射前用 `ChipUsageCostHelper.GetUsageCost(...)` 计算成本
- 发不出就不进入发射
- 成功发出后再扣除

双侧同时齐射时还会：

- 先合并总成本
- 再统一校验是否能承担

这说明旧版至少在这一块已经有“统一消耗层”的意识，
而不是每个武器效果自己乱扣。

## 八、这一轮对二次重构最重要的启发

### 1. 不要把“标准远程主链”和“BDP 发射编排层”混成一团

更合适的理解应该是：

- 标准远程主链：尽量复用原版
- BDP 编排层：决定谁发、从哪发、发几次、带不带路径、用什么身份投影出去

### 2. 双手复杂性主要在调度，不在命中公式

二次重构时最容易犯的错就是：

- 因为双手和组合很复杂
- 就把所有东西都塞进一个“万能攻击执行器”

旧版代码事实告诉我们，
真正复杂的是：

- 选择当前表达
- 切换当前侧上下文
- 协调路径与目标恢复

而不是把 `ShotReport`、掩体、miss 整套推翻。

### 3. “从枪口发射”必须继续被视为宿主校正，不是可有可无的视觉增强

它不是锦上添花。

它关系到：

- 玩家看到的武器位置
- 子弹起飞位置
- 双手不同武器表面

三者是否一致。

### 4. `TryCastShotCore()` 这种“共享原版主链桥接层”在新架构里应保留同等职责

名字可以变，组织方式可以更清楚，
但至少需要保留一个统一位置去负责：

- 标准远程链入口
- equipmentSource 投影
- 发射点修正
- 原版副作用通知
- projectile launch

否则子系统很快会再次分散。

## 九、当前还需继续确认的地方

- 它们高度相似
- `TryCastShotCore()` 更像现主用路径

后面要继续查谁还在直接调用 `LaunchProjectile(...)`，
避免误判。

### 2. 齐射散布在枪口之后是否始终叠加，当前文件里存在两种痕迹

这需要后面结合调用路径和实际游戏表现继续核实。
