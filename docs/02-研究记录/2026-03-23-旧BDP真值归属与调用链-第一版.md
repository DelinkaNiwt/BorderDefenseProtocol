# 旧 BDP 真值归属与调用链（第一版）

## 目的

这份记录只回答三个问题：

- 谁真正持有状态
- 谁只是协调者
- 哪些跨层改动是旧 BDP 里真实存在、而且不能靠想当然忽略的

它是给二次重构定边界用的，不是最终设计稿。

## 一、目前确认的真值 owner

### 1. `CompTrion` 是资源真值 owner

代码事实：

- `cur / max / allocated / reservedAllocation / drainRegistry / frozen` 都在 `CompTrion` 内部
- 正式占用通过 `Allocate()` / `Release()` 改
- 预占用通过 `UpdateReservedAllocation()` 改
- 持续消耗通过 `RegisterDrain()` / `UnregisterDrain()` 改
- 可用值耗尽通过 `OnAvailableDepleted` 往外发信号

结论：

- 资源真值确实集中在 `CompTrion`
- 但它不是完全孤立的资源盒子，而是被战斗体和触发体同时写入不同侧面的资源状态

### 2. `CombatBodyState` 是战斗体外层相位 owner

代码事实：

- `Inactive / Active / Collapsing / Cooldown` 都在 `CombatBodyState` 中
- `allocatedTrion / activationTick / cooldownEndTick / collapseStartTick / collapseReason` 也在这里
- 相位切换必须走 `TransitionToActive/Collapsing/Cooldown/Inactive`
- 非法切换会直接抛异常

结论：

- 旧 BDP 的战斗体“外层状态机”其实是清楚的
- 问题不是没有状态 owner，而是这个 owner 之外还有很多流程代码在同时处理战斗体相关事实

### 3. `CompTriggerBody` 是装载真值 owner，但同时越界持有战斗体相关状态

代码事实：

- 槽位、已装载芯片、激活标记、切换上下文都在 `CompTriggerBody`
- 它还维护 `IsCombatBodyActive`
- 它还负责把全部已装载芯片的 allocation cost 汇总后写入 `CompTrion.ReservedAllocation`
- 它实现 `ICombatBodySupport`，直接参与战斗体激活和解除

结论：

- 触发体确实是装载真值 owner
- 但它已经越界到“战斗体支援 owner”，这正是超级对象问题的一部分

## 二、目前确认的协调者与宿主

### 1. `Gene_TrionGland` 不是战斗体 owner，更像宿主与入口

代码事实：

- `PostAdd()` 创建 `snapshot / state / orchestrator / runtime`
- 负责序列化 `snapshot` 和 `state`
- 提供 Gizmo 按钮入口
- 激活和解除最终都委托给 `Runtime`
- 还订阅 `BDPEvents.RequestDeactivateCombatBody`

结论：

- Gene 更像“Pawn 侧长期宿主 + 初始化入口 + UI 入口”
- 它不适合在二次重构里继续承担复杂业务判断
- 但它作为 RimWorld `Gene` 宿主的身份是重要事实，不能随便抛掉

### 2. `CombatBodyRuntime` 不是 owner，只是统一访问门面

代码事实：

- 它只持有 `State`、`Snapshot`、`orchestrator`、`pawn`、`gene`
- `TryActivate()` 直接转给 `orchestrator.TryActivate()`
- `Deactivate()` 直接转给 `orchestrator.Deactivate()`
- `Of(pawn)` 只是统一查找入口

结论：

- `Runtime` 是运行时访问门面，不应被误解成核心 owner
- 二次重构时可以保留“统一访问门面”的思路，但不要把业务塞回门面里

### 3. `CombatBodyOrchestrator` 是流程协调者，不是真值 owner

代码事实：

- 负责激活和解除的完整编排
- 会操作 `Snapshot`、`State`、`CompTrion`、`ICombatBodySupport`
- 负责订阅和取消 `CompTrion.OnAvailableDepleted`
- 负责触发崩解 `TriggerCollapse()`

结论：

- 它的本质是事务编排者
- 旧 BDP 里很多跨域行为被集中到它这里，说明“协调层”确实有必要
- 但它现在直接伸手改太多对象，边界还不够干净

## 三、必须记住的几条真实调用链

### 1. 触发体卸下时，不是只发事件

真实链路：

1. `CompTriggerBody.Notify_Unequipped(pawn)` 发现战斗体仍激活
2. 先直接 `DismissCombatBody(pawn)`
3. `DismissCombatBody()` 内部 `DeactivateAll()`，清禁用标记，`trion.Release(trion.Allocated)`，并把 `IsCombatBodyActive = false`
4. 然后才 `BDPEvents.TriggerDeactivateRequest(pawn)`
5. `Gene_TrionGland.OnRequestDeactivate()` 再去调 `runtime.Deactivate(false)` 做快照恢复、状态收尾等后续

结论：

- “卸下触发体导致战斗体解除”这件事，旧版里是两段式事实链
- 事件不是唯一真相来源
- 第一段真状态处理发生在触发体仍然存在的时候
- 二次重构如果把这里改成“只发一个总事件，其他都等监听方慢慢处理”，很容易丢掉旧行为细节

### 2. 战斗体激活依赖主武器查询触发体支援

真实链路：

- `CombatBodyQuery.FindCombatBodySupport(Pawn)` 只看 `pawn.equipment.Primary`
- 找到其 `AllComps` 里实现 `ICombatBodySupport` 的 comp
- `CombatBodyOrchestrator.TryActivate()` 通过这个接口去申请 allocation 和激活 special 槽

结论：

- 旧 BDP 的“战斗体支援体”在事实层上绑定主武器
- 这是很强的 RimWorld 宿主约束，不是随便可替换的抽象关系

### 3. Trion 触发崩解靠的是 `Available` 而不是 `cur`

真实链路：

- `CombatBodyOrchestrator.RegisterMaintenance()` 订阅 `CompTrion.OnAvailableDepleted`
- `CompTrion.CheckAvailableDepleted()` 在 `Available <= 0` 时触发
- `OnAvailableDepleted` 触发后，若当前 `State.IsActive`，则 `TriggerCollapse()`

为什么不是 `OnTrionDepleted`：

- 战斗体激活时会有 `allocated > 0`
- 很多消耗只会把 `cur` 压到 `allocated`
- 这时 `Available` 会到 0，但 `cur` 不一定到 0

结论：

- 这里不是实现细节，而是旧版资源规则的关键本质
- 二次重构绝不能把“可用值耗尽”和“总量耗尽”混成一件事

## 四、现在能明确指出的越界点

### 1. 触发体直接写资源域的预占用和正式占用释放

代码事实：

- `SyncReservedAllocationToTrion()` 直接写 `CompTrion.UpdateReservedAllocation()`
- `DismissCombatBody()` 直接 `trion.Release(trion.Allocated)`

含义：

- 装载域不是只“声明需求”，而是直接改资源真值
- 这是旧版耦合最硬的一段之一

### 2. 协调层直接推动 Pawn 身体事实

代码事实：

- `ApplyTransformation()` 里做快照、换装、删 Hediff、加 `BDP_CombatBodyActive`、强制征召
- `Deactivate()` 里清战斗期 Hediff、移除 Active Hediff、恢复快照、最终清理残留

含义：

- 战斗体不是纯逻辑状态，而是深度落在 RimWorld 原生身体系统上
- 二次重构必须继续把“身体变化”走原版 Hediff / Apparel / Draft 这些宿主通道

### 3. 触发体仍然保存了一份 `IsCombatBodyActive`

代码事实：

- `TryAllocateTrionForCombatBody()` 里会先把 `IsCombatBodyActive = true`
- `DismissCombatBody()` 里再改回 `false`
- 但外层真正的战斗体相位又在 `CombatBodyState`

含义：

- 这是一份明显的跨核心重复状态
- 二次重构里必须小心处理：要么降成派生态，要么明确它只是装备侧只读镜像，不能再让它和正式相位并列当真值

## 五、对二次重构的直接约束

### 1. 事件总线不能冒充真值 owner

旧版已经证明：

- 事件适合通知
- 但很多关键收尾必须发生在特定宿主仍然存在时
- 所以事件总线更适合作为“协调信号层”，不该变成“所有状态都靠广播凑出来”的中心

### 2. “三核心”之外还需要一个很薄的协调层

理由：

- 旧版 `CombatBodyOrchestrator` 虽然越界，但它存在本身说明跨核心事务是真实需要
- 激活、解除、崩解都不是单对象内部动作，而是跨资源、身体、装备的多步事务

### 3. 新架构必须继续服从 RimWorld 宿主事实

当前确认的宿主事实：

- 资源长期挂在 Pawn 的 `ThingComp`
- 战斗体相位与身体变化落在 `Gene + Hediff + Apparel + Draft`
- 触发体支援入口依附装备，且当前实际上绑定主武器

## 六、下一步细读重点

接下来要继续确认：

- `Hediff_CombatBodyActive` 是如何决定崩解条件的
- `Hediff_CombatBodyCollapsing` 的 90 ticks 延时结束后到底怎么回到解除流程
- 旧版里手部损坏、受伤、Trion 可用值耗尽三条崩解链各自怎么汇合
- `CompTriggerBody` 的手部禁用、特殊槽、Verb 侧数据与战斗体相位之间还有哪些隐式耦合
