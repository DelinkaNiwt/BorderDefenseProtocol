# 旧 BDP 交互投影视角下的状态真约束（第一版）

## 目的

这份记录不把旧 GUI 当目标。

它只回答一件事：

- 如果把旧 GUI 只当成“内部状态投影窗口”，那它暴露了哪些真实约束

用户已经明确说过：

- 旧 BDP 的芯片控制 GUI 只是临时设计
- 注定会被重新设计

所以这里不研究布局、按钮风格、窗口形式。
只研究它背后依赖了哪些不可随便丢的状态事实。

## 一、先下结论

### 1. 旧 GUI 不是需求目标，但它确实暴露了很多内部真约束

当前最重要的有四类：

- 按侧独立切换状态机
- 槽位状态不止“开/关”两态
- 表达投影给玩家时需要“最佳显示槽位”规则
- 触发体的展示层会把内部表达重新投影回原版 UI 通道

这些东西不是 GUI 样式问题，
而是交互层必须依赖的真实状态。

### 2. 旧 BDP 的交互层，本质上是在做“状态投影”，不是在做业务 owner

不管是：

- `Window_TriggerBodySlots`
- `Gizmo_TriggerBodyStatus`
- `CompTriggerBody.Display`

它们都没有自己决定业务。

它们只是把以下状态投影出来：

- 槽位是否有芯片
- 战斗体是否激活
- 某侧是否切换中
- 该侧处于前摇还是后摇
- 当前最该显示哪一个芯片
- 当前有哪些表达已经形成

所以二次重构时，UI 可以重做，
但这些“被 UI 读的真状态”必须保留或重新明确建模。

## 二、按侧独立切换状态机是硬约束，不是 UI 偶然需求

### 1. `CompTriggerBody.SwitchStateMachine` 明确是左右手独立状态机

已有接口：

- `IsSwitching`
- `IsSideSwitching(side)`
- `GetSideSwitchProgress(side)`
- `GetSideSwitchPhase(side)`

并且有明确阶段：

- `Idle`
- `WindingDown`
- `WarmingUp`

这说明切换不是“全触发体只有一个总状态”。

而是：

- 左手一套状态机
- 右手一套状态机

### 2. 这不是为了 UI 好看，而是旧业务本来就要求左右手能独立推进

从实现看：

- 访问状态时才懒求值结算
- 一侧切换不应把另一侧一起锁死

这点甚至在窗口代码里都有明确修正注释：

- 旧代码用全局 `IsSwitching`
- 会导致一侧切换时另一侧也被禁用
- 后来改成按侧检查

所以这里的本质约束是：

- 切换锁定粒度必须至少精确到“侧”

## 三、槽位状态至少是五态，不是二态

### 1. `Window_TriggerBodySlots` 已经把槽位投影成五态

当前可读出的状态有：

- 空
- 挂载未注册
- 注册未激活
- 激活
- 禁用

这些颜色本身不重要，
重要的是背后的状态分类已经被写出来了。

### 2. 这五态的真实来源

#### 空

- `slot.loadedChip == null`

#### 挂载未注册

- `slot.loadedChip != null`
- `!triggerBody.IsCombatBodyActive`

#### 注册未激活

- `slot.loadedChip != null`
- `triggerBody.IsCombatBodyActive == true`
- `slot.isActive == false`

#### 激活

- `slot.isActive == true`

#### 禁用

- `slot.isDisabled == true`

这很重要，因为它说明旧版交互层依赖的不是一个“是否激活”布尔值，
而是一组更细的领域状态组合。

### 3. 这组五态很可能应被单独抽成正式状态投影

旧版目前还是在 UI 里临时拼条件。

但对二次重构来说，这更像应该独立成一个：

- 槽位显示状态
- 或槽位交互状态

而不是继续散在 UI 判断里。

## 四、“最佳显示槽位”也是一个真实投影规则

### 1. `Gizmo_TriggerBodyStatus` 不直接问“当前激活槽位”

它有一条更完整的规则：

- 先取激活槽位
- 没有激活槽位时，再取第一个有芯片的槽位

这说明旧版已经意识到：

- 玩家看到的“该侧当前代表芯片”
- 不一定总是激活芯片

### 2. 这个规则本质上是“交互投影默认代表值”

它和主攻击投影不是同一个概念，
但同样属于：

- 从多个内部状态中，选一个最适合对外显示的代表项

所以后续二次重构里，
最好不要把“攻击默认投影”和“显示默认投影”混在一起。

## 五、展示层会把内部表达重新投影回原版 UI 通道

### 1. `CompTriggerBody.Display` 说明旧版非常在意“回到 RimWorld 原版展示口”

它重写了：

- `TransformLabel`
- `CompInspectStringExtra`
- `CompTipStringExtra`
- `SpecialDisplayStats`

这说明旧版不是只想自己做一个自定义窗口。

它还在努力把内部状态投影回原版这些通道：

- 装备栏标题
- 左下检视面板
- 悬停提示
- Info Card

### 2. 这再次说明用户前面要求的“回归 RimWorld”是对的

旧版虽然 GUI 临时，
但它背后的方向其实已经表明：

- 内部再复杂
- 对外仍应尽量投影回游戏本身的通道

## 六、切换状态机与交互层之间的真实依赖

### 1. 旧 GUI 显示进度条，不是为了动画，而是因为前摇/后摇本来就是真业务状态

`Gizmo_TriggerBodyStatus` 会根据：

- `GetSideSwitchPhase(side)`
- `GetSideSwitchProgress(side)`

决定：

- 是否显示进度条
- 进度条颜色是前摇还是后摇

这说明：

- 前摇和后摇不只是实现细节
- 它们是对玩家可见、可感知、可影响交互的真实状态

### 2. `TryResolveSideSwitch()` 还是懒求值

这意味着：

- UI 读取状态，不只是“展示”
- 还顺带触发了状态推进

这不是理想结构，
但它暴露出一个很重要的宿主事实：

- 因为装备后的 `CompTick()` 不跑
- 所以切换状态机当前只能靠访问时结算

这个宿主事实本身不能忘。

## 七、`Window_TriggerBodySlots` 暴露了几个很重要的领域边界

### 1. 特殊槽和左右手槽不是同一种交互对象

窗口里已经明确：

- 左右手槽可编辑
- 特殊槽只读预览

这说明旧版领域里“特殊槽”并不是普通手槽的简单复制。

### 2. 是否允许玩家管理芯片，是独立开关

比如：

- `allowChipManagement == false`
- 就不显示状态 Gizmo

这说明：

- “芯片存在”
- 和
- “玩家能否直接管理芯片”

是两回事。

### 3. 槽位限制和禁用，不属于 GUI 逻辑

窗口只是读取：

- `slot.isDisabled`
- `triggerBody.IsSideSwitching(side)`
- `CanActivateChip(...)`

说明真正 owner 仍然在领域层。

这点对二次重构很重要：

- UI 只负责投影，不应重新计算业务规则

## 八、这轮对二次重构最有价值的启发

### 1. 不要继承旧 GUI 设计，但要继承它背后暴露出来的状态模型

至少应明确建模：

- 侧切换状态
- 槽位显示状态
- 槽位交互可用状态
- 每侧默认显示代表项

### 2. “显示投影”应和“攻击投影”分离

当前已能看出两类默认值：

- 主攻击默认投影
- 最佳显示槽位投影

二者不是一回事。

### 3. 交互层不该再承担懒求值推进职责

旧版这样做是宿主限制下的折中。

二次重构时应尽量把：

- 状态推进
- 状态查询

分开。

但也必须继续尊重 RimWorld 装备 `CompTick` 不跑这个宿主事实。

### 4. 对外展示仍应尽量回到 RimWorld 原版 UI 通道

自定义窗口可以重做，
但原版这些投影口仍然很有价值：

- Label
- InspectString
- Tooltip
- SpecialDisplayStats
