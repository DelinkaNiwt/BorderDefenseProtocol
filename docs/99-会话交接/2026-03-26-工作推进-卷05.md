## 关键裁定

### 1. 近战和远程共享同一套执行边界语言

- 两者现在都遵守：
  - 正式结果先进入 `AttackExecution`
  - 执行器先整理最小运行时上下文
  - 再决定是直接执行还是交给推进器
- 这保证了“副攻击、组合攻击、多步攻击”以后扩展时，不需要再为近战单独发明另一套边界。

### 2. 近战推进器存在的根因已经明确

- 不是因为“近战都应该上 JobDriver”
- 而是因为以下几类情况天然需要跨 tick 推进：
  - 目标不在贴身范围，要先追
  - 一次计划不是一刀结束，而是连击/连续动作
  - burst 期间不能指望非正式挂载的 Verb 自动推进

### 3. 本轮没有继续膨胀结果层

- 近战正式运行时所需最小信息，已经能从：
  - 正式结果
  - 攻击计划
  - 真实近战 `Verb`
- 三者组合中整理出来。
- 因此没有继续往 `FormalExpressionResult` 塞新的运行时字段。

### 本轮关键裁定

- 为了避免这层退化成“手动入口特判件”，适配层没有把来源原因写死成 `Manual`。
- 现状是显式把 `Reason`（来源原因）和 `DispatchIntent`（派单意图）都作为输入交给适配层。
- 这样它保持的是下面这条通用翻译关系，而不是“手动按钮专用类”：

```text
formal result
    -> AttackExecutionTargetingSource
        -> ITargetingSource
            -> Targeter
                -> OrderForceTarget(...)
                    -> AttackExecution
```

### UI 与性能取舍

- 适配层优先借用当前 resolved `Verb` 的原版 targeting 语义，不自己发明第二套合法性和图标规则。
- 当当前 tick 内重复查询 UI 成员时，优先复用同一份已解析上下文，避免 `OnGUI / Validate / Highlight` 各自重新读一次表达和 Verb。
